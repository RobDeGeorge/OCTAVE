Overview

The SpotifyManager class (src/managers/spotifymanager.{h,cpp} in C++, backend/spotify_manager.py in Python) controls Spotify playback on connected devices (phone, desktop, smart speaker, etc.) via the Spotify Web API. It mirrors the MediaManager signal interface so QML can treat both local and Spotify playback through a unified UI.

SpotifyManager does not play audio directly -- it acts as a remote control for Spotify Connect devices, sending play/pause/skip/seek/volume commands over the API and polling for playback state updates (every 3 seconds while playing, 5 seconds while paused, 10 seconds when no device is active). Spotify is desktop-only: the mobile C++ build ships a stub with the same API.

Credential Setup

Users must provide a Spotify Developer application's Client ID and Client Secret. These are stored in settingsConfigure.json via SettingsManager: 

@Slot(str, str)
def set_credentials(self, client_id, client_secret):
    self._client_id = client_id
    self._client_secret = client_secret
    if self._settings_manager:
        self._settings_manager.save_spotify_credentials(client_id, client_secret)

Credentials are loaded from SettingsManager when connect_settings_manager() is called during app initialization. set_credentials() exists only in the Python backend; QML writes credentials through settingsManager.save_spotify_credentials(), which both backends pick up via spotifyCredentialsChanged.

Security Note
Client ID and Secret are stored in the settings JSON file, not in the OS keychain. Only the OAuth tokens are stored securely via keyring. The redirect URI is hardcoded to http://127.0.0.1:8888/callback.

OAuth2 Authentication Flow

The authenticate() method implements the full OAuth2 Authorization Code flow with CSRF protection:

+------------------+ +------------------+ +------------------+ | OCTAVE QML | | SpotifyManager | | Spotify API | | | | | | | | authenticate() --|---->| Check cached | | | | | | token via | | | | | | KeyringCache | | | | | | | | | | | | If cached: | | | | | | Create client --|---->| Validate token | | | | Start polling | | | | | | | | | | | | If no token: | | | | | | Generate state | | | | authUrlReady <--|-----|- Get auth URL | | | | (open browser) | | Start HTTP srv | | | | | | on :8888 | | | | | | | | | | | | Callback: | | | | | | Validate state | | | | | | Exchange code --|---->| Return tokens | | | | _authCompleted | | | | | | (main thread) | | | +------------------+ +------------------+ +------------------+

Required OAuth Scopes

scope = (
    "user-read-playback-state "
    "user-modify-playback-state "
    "user-read-currently-playing "
    "playlist-read-private "
    "playlist-read-collaborative "
    "user-library-read"
)

The C++ backend requests user-follow-read in place of playlist-read-collaborative; the two token caches are otherwise interchangeable.

CSRF Protection

A cryptographically random state parameter is generated via secrets.token_urlsafe(32) and stored in self._oauth_state. The callback handler validates this state before accepting the authorization code: 

received_state = params.get('state', [None])[0]
if received_state != manager._oauth_state:
    # Return 403 - possible CSRF attack
    manager.errorOccurred.emit("OAuth state mismatch")
    return

Local Callback Server

A one-shot HTTP server runs on 127.0.0.1:8888 in a daemon thread. It handles a single request (the OAuth callback) with a 2-minute timeout, then shuts down. The server class is defined inline as CallbackHandler(BaseHTTPRequestHandler).

Thread-Safe Post-Auth Setup

After the callback receives the token, the auth_manager is stored in _pending_auth_manager and the internal _authCompleted signal is emitted. This signal is connected to _on_auth_completed() which runs on the main thread and sets up the Spotipy client, starts polling timers, and refreshes devices and playlists.

Keyring Token Storage

The KeyringCacheHandler class implements Spotipy's CacheHandler interface to store OAuth tokens securely in the OS keychain:

PlatformStorage Backend
WindowsWindows Credential Manager
macOSmacOS Keychain
LinuxSecret Service (GNOME Keyring / KWallet)
 
class KeyringCacheHandler(_CacheHandlerBase):
    SERVICE_NAME = "OCTAVE_Spotify"
    USERNAME = "spotify_token"

    def get_cached_token(self):
        if KEYRING_AVAILABLE:
            token_string = keyring.get_password(self.SERVICE_NAME, self.USERNAME)
            if token_string:
                return json.loads(token_string)
        # Fallback to file cache
        if os.path.exists(self._cache_file):
            with open(self._cache_file, 'r') as f:
                return json.load(f)
        return None

If keyring is unavailable, tokens fall back to a file-based cache at backend/.spotify_token_cache. The C++ backend always uses a file cache, at <app data dir>/.spotify_token_cache (see SpotifyManager::tokenCachePath()).

Key methods:

  • get_cached_token() - Read from keyring, fall back to file
  • save_token_to_cache(token_info) - Write to keyring, fall back to file
  • delete_cached_token() - Remove from both keyring and file

Async API Call Pattern

In the Python backend all Spotify API calls run asynchronously via a ThreadPoolExecutor with a maximum of 2 concurrent workers (to avoid rate limiting). The C++ backend needs no worker threads: every call is a non-blocking QNetworkReply whose completion callback runs on the main thread (apiGet / apiPut / apiPost). 

self._executor = ThreadPoolExecutor(max_workers=2)

The _run_async() Helper

def _run_async(self, func, success_callback=None, error_msg="Operation failed"):
    def on_done(future):
        if not self._sp:  # Skip if shutting down
            return
        try:
            result = future.result()
            if success_callback:
                QMetaObject.invokeMethod(self, success_callback, Qt.QueuedConnection)
        except Exception as e:
            if self._sp:
                self.errorOccurred.emit(f"{error_msg}: {str(e)}")
    self._executor.submit(func).add_done_callback(on_done)

Optimistic UI Updates

Playback commands (play, pause, shuffle, seek, volume) apply optimistic UI updates -- the local state and QML signals are updated immediately before the API call completes. This makes the UI feel instant even with network latency: 

@Slot()
def play(self):
    # Optimistic UI update
    self._is_playing = True
    self.playStateChanged.emit(True)
    # Actual API call runs in background
    def do_play():
        self._sp.start_playback(device_id=self._active_device_id)
    self._run_async(do_play, error_msg="Play failed")

Playing a Specific Track in Playlist Context

When play_uri() is called with a track URI and a playlist is loaded, it plays the track within the playlist context (so next/previous follow the playlist order): 

if uri.startswith('spotify:track:'):
    if playlist_id:
        playlist_uri = f"spotify:playlist:{playlist_id}"
        # Find the track's offset in the playlist
        for i, track in enumerate(tracks):
            if track.get('uri') == uri:
                offset = i; break
        self._sp.start_playback(context_uri=playlist_uri, offset={"position": offset})
    else:
        self._sp.start_playback(uris=[uri])

Position Interpolation

The Spotify API is polled by _poll_timer (3 s while playing, stretched to 5 s while paused and 10 s when no device is active), but the UI progress bar needs smooth updates. A fast local timer (_interpolation_timer, 250ms interval) interpolates the position between API polls: 

# Poll timer: actual API calls every 3 seconds while playing (5 s paused, 10 s idle)
self._poll_timer = QTimer()
self._poll_timer.setInterval(3000)
self._poll_timer.timeout.connect(self._poll_playback_state)

# Interpolation timer: smooth UI updates 4x per second (no API calls)
self._interpolation_timer = QTimer()
self._interpolation_timer.setInterval(250)
self._interpolation_timer.timeout.connect(self._interpolate_position)

The interpolation uses _last_known_position_ms and _last_poll_timestamp to calculate the estimated current position based on elapsed wall-clock time.

Queue and Side Cards

When no playlist is loaded, SpotifyManager fetches the Spotify queue to populate the 3D album preview side cards. The queue is cached in _cached_queue (list of track dicts with name, artist, album, image) and the previous track is stored in _previous_track.

The queueUpdated signal is emitted when queue data is ready, allowing QML to update side card artwork.

Album Art Theming

Like MediaManager, SpotifyManager supports the "Album Art Capture" theme. When active (_album_art_capture_active), it downloads album art from the Spotify image URL, extracts dominant colors, and pushes the theme JSON to SettingsManager via set_album_art_colors().

A deduplication check (_last_extracted_image_url) prevents re-extracting colors when the same track's art URL is seen again.

Disconnect and Cleanup

Disconnect

QML calls spotifyManager.disconnect() on both backends; in C++ it is an alias of logout().

@Slot()
def disconnect(self):
    self._poll_timer.stop()
    self._interpolation_timer.stop()
    self._sp = None
    self._is_connected = False
    self._cache_handler.delete_cached_token()  # Remove from keychain
    self.connectionStateChanged.emit(False)

Cleanup (App Exit)

@Slot()
def cleanup(self):
    self._poll_timer.stop()
    self._interpolation_timer.stop()
    self._is_connected = False
    self._sp = None
    self._executor.shutdown(wait=False, cancel_futures=True)

Error Handling

Errors are handled at multiple levels:

  • Import failures: SPOTIPY_AVAILABLE and KEYRING_AVAILABLE flags allow graceful degradation
  • Authentication errors: Caught and emitted via errorOccurred signal
  • User-initiated API failures (_refresh_devices, _refresh_playlists, device transfer): logged at error level and surfaced to the UI via errorOccurred
  • Background poll failures (_poll_playback_state): logged at debug level and rate-limited — errorOccurred only fires after POLL_ERROR_THRESHOLD consecutive failures (default 5) and at most once per POLL_ERROR_EMIT_INTERVAL seconds (default 30s). This avoids UI spam during brief network drops while still surfacing persistent issues like expired tokens.
  • Low-priority fetches (queue for side-card art): logged at debug level only — failures here degrade UI chrome but don't block playback
  • Shutdown safety: All callbacks check self._sp before proceeding to avoid crashes during cleanup
  • Duplicate prevention: _poll_in_progress flag prevents overlapping poll requests

The statusProgress signal provides terminal-style feedback with prefixes:

  • [INFO] - Informational messages
  • [SUCCESS] - Successful operations
  • [ERROR] - Error messages
  • [WARN] - Warnings (e.g., no devices found)
  • [FOUND] - Discovery results
  • [DONE] - Operation complete
