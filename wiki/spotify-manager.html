Overview

The SpotifyManager class (src/managers/spotifymanager.{h,cpp} in C++, backend/spotify_manager.py in Python) controls Spotify playback on connected devices (phone, desktop, smart speaker, etc.) via the Spotify Web API. It mirrors the MediaManager signal interface (playStateChanged, currentTrackChanged, durationChanged, positionChanged, …) so QML can treat local and Spotify playback through one UI. It is registered as the QML context property spotifyManager in src/main.cpp / main.py.

SpotifyManager does not play audio -- it is a remote control for Spotify Connect devices. It sends play/pause/skip/seek/volume/shuffle commands over the API and polls GET /v1/me/player for state (every 3 seconds while playing, 5 seconds while paused, 10 seconds when no device is active). Between polls a local 250 ms timer interpolates the progress position so the slider moves smoothly without extra API traffic.

Spotify is desktop-only. The C++ header wraps the real class in #ifndef Q_OS_MOBILE; the mobile build compiles a stub with the same signals and slots so QML bindings stay valid (is_connected() always returns false). The header comment gives the reason: no OAuth URI-scheme redirect handler is wired on mobile, and the project scope keeps Spotify on desktop. The Python backend is desktop-only by policy (see Architecture).

Credential Setup

Users must provide a Spotify Developer application's Client ID and Client Secret. The Spotify card on frontend/settings/MediaSettingsPage.qml writes them with settingsManager.save_spotify_credentials(id, secret); SettingsManager persists them as the spotifyClientId / spotifyClientSecret keys of settingsConfigure.json and emits spotifyCredentialsChanged.

Spotify's Development Mode rules (February 2026). OCTAVE is a personal app, so it runs as a Development Mode app registered by the user. Since Spotify's February 2026 migration (new apps from 11 February, existing apps from 9 March 2026) that means: the app owner must hold an active Spotify Premium subscription (the app stops working if it lapses), one Client ID per developer, and at most five allow-listed users per app. Everything OCTAVE needs survived the migration: the player endpoints (/me/player state, play, pause, next, previous, seek, volume, shuffle, queue, devices, transfer) and /me/playlists are unchanged; playlist contents moved from /playlists/{id}/tracks to /playlists/{id}/items (50 per page, track under item) and are only readable for playlists the user owns or collaborates on, so a followed editorial playlist lists but will not load its tracks. OCTAVE never used the removed browse, recommendations, audio-features or other-user endpoints.

Both backends read the credentials once, when the settings manager is wired (SpotifyManager::setSettingsManager() in C++, connect_settings_manager() in Python): 

void SpotifyManager::loadCredentials()
{
    if (!m_settingsManager) return;
    m_clientId     = m_settingsManager->get_spotify_client_id();
    m_clientSecret = m_settingsManager->get_spotify_client_secret();
}

The Python backend additionally exposes set_credentials(client_id, client_secret), which updates its own copy and calls save_spotify_credentials(); the C++ backend has no such slot and QML does not call it on either backend.

Credentials are read at startup only
Neither backend subscribes to spotifyCredentialsChanged. has_credentials() answers from the copy captured at wiring time, so credentials typed into the settings page during a session are not seen by authenticate() until OCTAVE is restarted (the Connect button reports "Spotify credentials not configured" until then).
Security Note
Client ID and Secret are stored in the settings JSON file, not in the OS keychain. Only the OAuth tokens get keychain treatment, and only on Python (see Token Storage). The redirect URI is hardcoded to http://127.0.0.1:8888/callback on both backends and must be registered verbatim in the Spotify Developer dashboard.

OAuth2 Authentication Flow

authenticate() implements the OAuth2 Authorization Code flow with a CSRF state parameter. It is not PKCE and not Client Credentials: the client secret is sent with the code exchange and with every refresh, which is why the secret has to be entered in the app. Both backends try a cached token first and only open the browser when none is usable.

+------------------+ +------------------+ +------------------+ | OCTAVE QML | | SpotifyManager | | Spotify | | | | | | | | authenticate() --|---->| Cached token? | | | | | | yes: refresh if | | | | | | expired, start | | | | | | polling -------|---->| GET /v1/me/... | | | | | | | | | | no: | | | | | | random state | | | | authUrlReady <--|-----|- build /authorize| | | | (open browser) | | listen on | | | | | | 127.0.0.1:8888 | | | | | | | | | | | | GET /callback | | | | | | ?code&state <---|-----| browser redirect | | | | verify state | | | | | | POST /api/token-|---->| access + refresh | | | | start polling | | | +------------------+ +------------------+ +------------------+

Required OAuth Scopes

Python (spotipy.SpotifyOAuth):

scope = (
    "user-read-playback-state "
    "user-modify-playback-state "
    "user-read-currently-playing "
    "playlist-read-private "
    "playlist-read-collaborative "
    "user-library-read"
)

C++ (tryConnectWithCachedToken()) requests user-library-read user-follow-read playlist-read-private user-read-playback-state user-modify-playback-state user-read-currently-playing -- user-follow-read in place of playlist-read-collaborative. The token caches are not shared between backends (different locations, see below), and spotipy's validate_token() rejects a cached token whose scope set does not cover the requested one, so a token minted by one backend is never reused by the other.

CSRF Protection

Python generates the state with secrets.token_urlsafe(32); C++ uses QUuid::createUuid().toString(QUuid::WithoutBraces). Both store it, compare it on the callback, and emit errorOccurred("OAuth state mismatch - possible CSRF attack") on mismatch. Python answers the browser with HTTP 403 in that case (400 when no code, 500 when the exchange throws); C++ always writes the same 200 "Success!" page and signals failures through errorOccurred only. 

received_state = params.get('state', [None])[0]
if received_state != manager._oauth_state:
    self.send_response(403)
    ...
    manager.errorOccurred.emit("OAuth state mismatch - possible CSRF attack")
    return

Local Callback Server

  • Python: an http.server.HTTPServer bound to 127.0.0.1:8888 runs in a daemon thread and calls handle_request() once (single request, 120 s socket timeout), then exits. The handler is the inline CallbackHandler(BaseHTTPRequestHandler); log_message is overridden to silence stdout. The browser is opened with os.startfile() on Windows, otherwise webbrowser.open(); if both fail the URL is re-emitted via authUrlReady together with an errorOccurred("Could not open browser. Please visit: ..."). authUrlReady is always emitted before the server starts, so the settings page can show the link regardless.
  • C++: a QTcpServer listens on QHostAddress::LocalHost:8888; the first connection's readyRead is parsed by hand (handleOAuthCallback() reads the request line, wraps it in a QUrl, and pulls state/code/error with QUrlQuery). The server is closed after that one request. The browser is opened with QDesktopServices::openUrl(). A failed listen() emits errorOccurred("Failed to start OAuth redirect server on port 8888").

Code Exchange and Refresh

  • Python delegates to spotipy: auth_manager.get_access_token(code) performs the exchange and writes the token through the cache handler; subsequent calls go through spotipy.Spotify(auth_manager=...), and spotipy's validate_token() refreshes an expired token with the refresh token transparently.
  • C++ posts grant_type=authorization_code (with client_id and client_secret in the form body) to https://accounts.spotify.com/api/token, computes expires_at = now + expires_in, and saves the whole token object. Every apiGet / apiPut / apiPost first checks now >= expires_at - 60; if the token is within a minute of expiry it calls refreshAccessToken() and drops the current request rather than queueing it -- the next poll tick (at most 10 s later) re-issues the read, and a dropped command simply needs another tap. A failed refresh clears the access token and emits connectionStateChanged(false), forcing a fresh login.

Post-Auth Setup

Once a token is in hand both backends do the same four things: emit connectionStateChanged(true), start the poll and interpolation timers, and kick off refresh_devices() and a playlist refresh. In Python the callback arrives on the HTTP server thread, so the handler stores the auth_manager in _pending_auth_manager and emits the internal _authCompleted signal; the connected _on_auth_completed() slot builds the spotipy.Spotify client on the main thread. In C++ the QNetworkReply::finished lambda already runs on the main thread, so it finishes the setup inline.

The _run_async() Helper (Python)

Fire-and-forget commands (play, pause, seek, …) go through one helper that only reports failures:

def _run_async(self, func, success_callback=None, error_msg="Operation failed"):
    def on_done(future):
        if not self._sp:  # Skip if shutting down
            return
        try:
            result = future.result()
            if success_callback:
                QMetaObject.invokeMethod(self, success_callback, Qt.QueuedConnection)
        except Exception as e:
            if self._sp:
                self.errorOccurred.emit(f"{error_msg}: {str(e)}")
    self._executor.submit(func).add_done_callback(on_done)

C++: there is no worker thread. apiGet(), apiPut() and apiPost() wrap QNetworkAccessManager, attach the Authorization: Bearer header in buildApiRequest(), and hand the reply to handleApiReply() (parses JSON, treats an empty body as the 204 case) or handleApiReplyNoBody(). Success and error callbacks are std::functions invoked from the reply's finished signal on the main thread. 

void SpotifyManager::apiGet(const QString &endpoint,
                            std::function<void(const QJsonDocument &)> onSuccess,
                            std::function<void(const QString &)> onError)
{
    if (m_accessToken.isEmpty()) return;

    // Auto-refresh if token is about to expire (60s buffer)
    if (QDateTime::currentSecsSinceEpoch() >= m_tokenExpiresAt - 60) {
        refreshAccessToken();
        return;
    }

    QNetworkReply *reply = m_nam->get(buildApiRequest(endpoint));
    connect(reply, &QNetworkReply::finished, this, [this, reply, onSuccess, onError]() {
        handleApiReply(reply, onSuccess, onError);
    });
}

Optimistic UI Updates

Playback commands apply optimistic UI updates on both backends: local state and the corresponding QML signal are updated before the request is sent, so the button flips instantly even on a slow link. The next poll reconciles if Spotify disagreed. 

@Slot()
def play(self):
    if not self._sp:
        return
    # Optimistic UI update
    self._is_playing = True
    self.playStateChanged.emit(True)

    def do_play():
        self._sp.start_playback(device_id=self._active_device_id)

    self._run_async(do_play, error_msg="Play failed")

Playing a Specific Track in Playlist Context

When play_uri() receives a spotify:track: URI and a playlist is loaded, it looks the track up in the loaded track list and plays with context_uri = spotify:playlist:<id> plus an offset.position, so next/previous follow the playlist order. A track that is not in the loaded playlist, or any track when no playlist is loaded, plays standalone via uris=[uri]; album and playlist URIs are passed straight through as context_uri. 

if uri.startswith('spotify:track:'):
    if playlist_id:
        playlist_uri = f"spotify:playlist:{playlist_id}"
        offset = None
        for i, track in enumerate(tracks):
            if track.get('uri') == uri:
                offset = i
                break
        if offset is not None:
            self._sp.start_playback(device_id=device_id, context_uri=playlist_uri,
                                    offset={"position": offset})
        else:
            self._sp.start_playback(device_id=device_id, uris=[uri])
    else:
        self._sp.start_playback(device_id=device_id, uris=[uri])
else:
    self._sp.start_playback(device_id=device_id, context_uri=uri)

Playback State Polling

_poll_timer / m_pollTimer fires GET /v1/me/player (current_playback() in spotipy). A _poll_in_progress / m_pollInProgress flag drops a tick while the previous request is still in flight. The handler then:

  1. Adapts the interval -- an empty response (no active device) sets 10 s; otherwise 3 s while is_playing, 5 s while paused. The interval is only touched when it actually changes.
  2. Diffs state -- playStateChanged, shuffleStateChanged and volumeChanged (from device.volume_percent) are emitted only when the value differs from the cached one.
  3. Re-anchors position -- stores progress_ms and the wall-clock timestamp used by the interpolator, and emits positionChanged.
  4. Detects track changes by track ID: saves the outgoing track as _previous_track, rebuilds the current-track dict (name, comma-joined artists, album, duration, first album image), emits currentTrackChanged and durationChanged, triggers Album Art Capture extraction, and fetches the queue when no playlist is loaded.

Position Interpolation

A 3-10 s poll would make the progress slider jump. A second timer (_interpolation_timer / m_interpolationTimer, 250 ms, "Update UI 4x per second", no API calls) estimates the position from the last poll: last_known_position + (now - last_poll_timestamp), clamped to the track duration, and only emits positionChanged when the estimate moved by at least 200 ms ("avoid spam"). It does nothing while paused or before the first poll. 

# Poll timer: actual API calls every 3 seconds while playing (5 s paused, 10 s idle)
self._poll_timer = QTimer()
self._poll_timer.setInterval(3000)  # Poll every 3 seconds (avoid rate limits)
self._poll_timer.timeout.connect(self._poll_playback_state)

# Fast local timer for smooth position interpolation (no API calls)
self._interpolation_timer = QTimer()
self._interpolation_timer.setInterval(250)  # Update UI 4x per second
self._interpolation_timer.timeout.connect(self._interpolate_position)
void SpotifyManager::onInterpolationTimeout()
{
    if (!m_isPlaying || m_lastPollTimestamp == 0) return;

    const qint64 elapsedMs = QDateTime::currentMSecsSinceEpoch() - m_lastPollTimestamp;
    qint64 estimated = m_lastKnownPositionMs + elapsedMs;

    // Don't exceed track duration
    const int duration = m_currentTrack.value(QStringLiteral("duration_ms")).toInt();
    if (duration > 0 && estimated > duration)
        estimated = duration;

    if (std::abs(estimated - m_currentPositionMs) >= 200) {
        m_currentPositionMs = static_cast<int>(estimated);
        emit positionChanged(m_currentPositionMs);
    }
}

set_position() re-anchors the same two variables immediately, so a seek does not visibly snap back before the next poll confirms it.

Queue and Side Cards

The media room's 3D album carousel shows "previous" and "next" cards. get_next_track_info() / get_previous_track_info() return a JSON string (name, artist, album, image) or an empty string. With a playlist loaded they walk the loaded track list relative to the current track name (wrapping at both ends). Without one they fall back to the Spotify queue (GET /v1/me/player/queue, fetched on every track change while no playlist is loaded and trimmed to the first 5 entries in _cached_queue) for "next", and to _previous_track -- the last track the poller saw before the current one -- for "previous". queueUpdated fires when the queue cache is refreshed so frontend/MediaRoom.qml can re-read the neighbours. Queue fetch failures are logged at debug level only.

Album Art Theming

Like MediaManager, SpotifyManager feeds the "Album Art Capture" theme (see Theme System). It subscribes to SettingsManager.themeSettingChanged, keeps _album_art_capture_active / m_albumArtCaptureActive, and runs the extractor on every track change while the theme is active (and once immediately when the theme is switched on). A _last_extracted_image_url check prevents re-extracting the same artwork.

  1. Fetch the artwork. Python downloads it with urllib.request.urlretrieve to backend/temp/spotify_album_art.jpg inside an executor job; C++ streams it into memory with QNetworkAccessManager.
  2. Downscale to 100×100 RGBA8888 with QImage.
  3. Cluster with a hand-written k-means (k = 5, 10 iterations, seeded 42 -- Python uses a local numpy.random.default_rng(42) so the global RNG is untouched; C++ uses std::mt19937).
  4. Rank by vibrancy (HSV saturation × value) and decide light/dark from the mean luminance of up to 1000 pixels (< 0.5 is dark).
  5. Generate the palette (_generate_theme_from_colors / generateThemeFromColors): accents from the top four colours with saturation/brightness boosts, base/hover/paused/playing shades, WCAG-style luminance and contrast checks (ensure_icon_contrast, minimum ratio 3.0, brightness capped at 0.85), and per-widget entries (bottombar, mediaroom, obd, sliders, text).
  6. Publish via settingsManager.set_album_art_colors(json) and albumColorsExtracted(json).

The Python pipeline runs on the executor and delivers through _colorsReady; the C++ pipeline runs entirely on the main thread (the image is only 10,000 pixels).

Volume Routing

QML never calls spotifyManager.set_volume() for the volume slider; it calls volumeController.applyVolume(percent) (see Architecture). Spotify receives the raw 0-100 percent, not the quadratic linear value. In C++ (src/main.cpp) the forward is debounced through a 300 ms single-shot QTimer -- the comment says "to avoid 429 rate limiting on desktop" -- and only fires when is_connected(). The Python VolumeController (backend/volume_utils.py) forwards every change immediately when connected; each call is an executor job, so the UI never blocks, but a fast slider drag issues one API request per tick.

Disconnect and Cleanup

Disconnect

QML calls spotifyManager.disconnect() on both backends; in C++ it is an inline alias of logout() (the header notes it intentionally shadows QObject::disconnect). Both stop the timers, clear the client/token, devices, current track, queue and previous-track caches, delete the cached token, and emit connectionStateChanged(false) with [INFO]/[DONE] status lines.

@Slot()
def disconnect(self):
    self.statusProgress.emit("[INFO] Disconnecting from Spotify...")
    self._poll_timer.stop()
    self._interpolation_timer.stop()
    self._sp = None
    self._is_connected = False
    self._devices = []
    self._current_track = {}
    self._cached_queue = []
    self._previous_track = {}

    # Remove cached token from OS keychain
    self._cache_handler.delete_cached_token()
    self.statusProgress.emit("[INFO] Cleared cached token")

    self.connectionStateChanged.emit(False)
    self.statusProgress.emit("[DONE] Disconnected from Spotify")

Cleanup (App Exit)

Called from the aboutToQuit handler. It keeps the token cache (so the next launch reconnects silently) but stops the timers and marks the manager disconnected so in-flight callbacks bail out. Python also shuts the executor down with cancel_futures=True; C++ additionally closes a still-open OAuth server.

@Slot()
def cleanup(self):
    self._poll_timer.stop()
    self._interpolation_timer.stop()
    self._is_connected = False
    self._sp = None
    self._executor.shutdown(wait=False, cancel_futures=True)

Error Handling

  • Import failures (Python): SPOTIPY_AVAILABLE / KEYRING_AVAILABLE flags degrade gracefully; authenticate() emits [ERROR] Spotipy library not installed.
  • Authentication errors: caught and emitted via errorOccurred plus an [ERROR] status line.
  • User-initiated API failures (device/playlist refresh, transfer, every playback command): surfaced via errorOccurred("<Action> failed: <reason>"); Python also logs at error level.
  • Background poll failures: logged at debug level and rate-limited. Both backends keep a consecutive-failure counter and only emit errorOccurred("Spotify connection lost: ...") after POLL_ERROR_THRESHOLD (5) failures in a row, at most once per POLL_ERROR_EMIT_INTERVAL (30 s; POLL_ERROR_EMIT_INTERVAL_S in C++). The Python comment explains the intent: polls run every 1-10 s, so raw failures "would spam the UI on a dropped network".
  • Low-priority fetches (queue for side-card art): debug log only.
  • Shutdown safety: every Python callback checks self._sp first; C++ checks m_isConnected / an empty access token.
  • Duplicate prevention: the in-progress flag skips poll ticks while a request is outstanding.

The statusProgress signal drives the terminal-style log on the Spotify settings card (TerminalFeedback) with these prefixes:

  • [INFO] - Informational messages
  • [SUCCESS] - Successful operations
  • [ERROR] - Error messages

Design Decisions

Remote control, not a player

OCTAVE never receives Spotify audio; it drives whichever Spotify Connect device is active (the phone in the cup holder, a speaker, the desktop client). That is why the manager mirrors MediaManager's signals rather than its audio path: the same QML transport, slider and artwork code works for both, and the VolumeController sends Spotify a percent instead of a linear gain.

Authorization Code with a loopback redirect

The flow needs a place for Spotify to redirect to; both backends run a one-shot HTTP listener on 127.0.0.1:8888 and open the system browser, so no embedded web view or custom URI scheme is required on desktop. The header comment on the C++ mobile guard records the flip side: without a URI-scheme handler, Spotify stays off Android/iOS. A random state value is checked on the callback so a forged redirect cannot inject a code.

Adaptive polling plus local interpolation

Spotify state is pull-only. The poll interval is chosen per state (3 s playing / 5 s paused / 10 s idle, each annotated in the source with "avoid rate limits" and "when idle") so a parked car with nothing playing costs six requests a minute instead of twenty. Because a 3 s cadence would still stutter the slider, position is extrapolated locally four times a second with a 200 ms emit threshold -- smooth UI with zero extra traffic.

Optimistic updates and only-on-change emission

Every command flips the cached state before the network round-trip, and the poll handler emits a signal only when a value differs from the cache. Together these keep the head unit responsive on a cellular hotspot and stop QML bindings from re-evaluating on every poll.

Rate-limited error surfacing for background polls

A dropped network would otherwise raise an error toast every few seconds. User-initiated actions still report immediately; only the background poll is throttled (5 consecutive failures, then at most once per 30 s), per the comment in _poll_playback_state.

Thread pool with signal hand-off (Python) vs. no threads (C++)

spotipy is blocking, so Python offloads to a two-worker executor and re-enters the Qt thread through dedicated internal signals -- the constructor comment calls them "thread-safe callbacks", and _run_async uses QMetaObject.invokeMethod(..., QueuedConnection) for the same reason. Qt's network stack is already asynchronous, so the C++ port needs neither the pool nor the relay signals; the chained-callback fetchPlaylistItemsPage() is the price of that choice.

Deferred imports

Commit ee5a23e ("Startup and idle-CPU optimizations") moved spotipy and keyring behind backend/lazy_import.py: about a second of import time across optional libraries was on the Pi's cold-start path for features the user may never touch.

Following the February 2026 Web API change

Commit a37f3ff switched both backends to /playlists/{id}/items with 50-item pages and the item key (falling back to track) after existing Development Mode apps were migrated on 9 March 2026 and playlist loading stopped working. The player and /me/playlists endpoints OCTAVE relies on were unchanged, so nothing else moved.

Debounced volume (C++)

The rotary encoder and slider can emit dozens of values per second. main.cpp coalesces them into one Spotify request 300 ms after the last change -- the comment cites HTTP 429 rate limiting -- while local media volume is applied instantly.
