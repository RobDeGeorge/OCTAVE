Where to Look First

Start with the status text on the affected page and the logs. OCTAVE has no global error-notification layer, but individual views show details (for example, tap a failed download to open its error popup). These are the main places to look:

  1. The Connection Log / status text on the relevant page — the Connection Log on Settings → OBD shows each connection step and rfcomm / permission errors; the Download page shows the error for a failed item and marks its queue row failed; the phone-mirror view shows the adb / authorization message.
  2. Settings → Device → Diagnostics card (diagnosticsManager) — a 2×2 grid: Refresh (last 200 log lines), Copy (last 400 lines to the clipboard), Export logs (copies the log files to the Downloads folder — the way to get logs off a head unit without a shell) and Open folder. The log directory path is printed on the card.
  3. The rotating log files described next. A hung UI, a crash and a dropped adapter all leave a trace there even when the screen shows nothing.
  4. The terminal — the console handler prints the same INFO+ lines (DEBUG+ with --debug) to stdout.

Log Files, Crash Traces & Debug Mode

Log directory

The backend writes to a logs/ subdirectory of the app data directory (get_app_data_dir()):

PlatformPath
Windows%APPDATA%\OCTAVE\logs\
macOS~/Library/Application Support/OCTAVE/logs/
Linux / Raspberry Pi$XDG_CONFIG_HOME/OCTAVE/logs/, by default ~/.config/OCTAVE/logs/

Log files

FileLevelMax sizeBackupsNotes
octave.logINFO+5 MB3backend/logging_config.py, RotatingFileHandler
octave-error.logERROR+2 MB5also receives unhandled-exception tracebacks and faulthandler dumps
octave-debug.logDEBUG+10 MB2only with --debug

Total disk is bounded at roughly 32 MB without debug, ~62 MB with it. WARNINGs (for example the UI watchdog's) are in octave.log, not in octave-error.log.

Line format

# Console (HH:MM:SS):
HH:MM:SS | LEVEL   | octave.module            | message

# File:
YYYY-MM-DD HH:MM:SS | LEVEL   | octave.module | file.py:line | function() | message

Logger names come from get_logger(__name__): octave.obd, octave.media, octave.settings, octave.android_auto[.capture|.embedded], octave.phone_mirror, octave.app for main.py, and octave.<module> for everything else (e.g. octave.ui_watchdog, octave.elm327_protocol, octave.phone_mirror.scrcpy_client). python-obd's own obd logger is attached to the same handlers, so an ELM327 session leaves its write:/read: transcript in octave-debug.log (with --debug). Many OBD messages also carry an [OBD] prefix.

Crash traces

  • sys.excepthook and threading.excepthook log Unhandled exception on the main thread / Unhandled exception in thread '<name>' with the traceback at CRITICAL.
  • faulthandler is enabled on a descriptor of octave-error.log, so a native fault (SIGSEGV, SIGABRT, SIGFPE, SIGBUS, SIGILL — e.g. inside PySide6 or PyAV) dumps every Python thread's stack there.
  • SIGTERM / SIGINT (launcher scripts, systemd, Ctrl-C) are turned into app.quit(), with a 500 ms no-op timer so Python gets to run the handler inside app.exec(); the aboutToQuit cleanup then runs and child processes / adb forwards are not orphaned.

UI watchdog: "UI thread blocked for N s and counting"

A watchdog thread (backend/ui_watchdog.py) posts a ping to the GUI thread every 2 s; if the GUI thread has not answered within 5 s a WARNING is logged under octave.ui_watchdog, once per stall, followed by UI thread responsive again after N s when it recovers. A frozen head unit therefore leaves a timestamped trace even though nothing was drawn. Look at the lines immediately before the warning to see which manager was busy; the watchdog is stopped first in the quit cleanup so shutdown does not show as a stall.

Enabling debug mode

python main.py --debug

Creates octave-debug.log with DEBUG-level output. Useful for: the python-obd TX/RX transcript, serial lines from the ESP32 knob, settings load/save, media library scanning and tag extraction, and the phone-mirror adb / server launch sequence.

Display & Rendering Issues

XCB platform plugin errors (Linux)

Error
qt.qpa.plugin: Could not load the Qt platform plugin "xcb"

Install the X11/XCB libraries. The list setup.py installs on Debian/Ubuntu is the reference:

sudo apt install libxcb1 libxcb-cursor0 libxcb-icccm4 libxcb-image0 libxcb-keysyms1 \
  libxcb-randr0 libxcb-render0 libxcb-render-util0 libxcb-shape0 libxcb-shm0 \
  libxcb-sync1 libxcb-xfixes0 libxcb-xinerama0 libxcb-xkb1 libxcb-util1 \
  libxkbcommon0 libxkbcommon-x11-0

Run with QT_DEBUG_PLUGINS=1 to identify the missing dependency, and check DISPLAY/WAYLAND_DISPLAY.

Wayland vs X11

Qt picks the platform plugin from the session. To force one:

export QT_QPA_PLATFORM=xcb       # force X11 / XWayland
export QT_QPA_PLATFORM=wayland   # force Wayland
python main.py

The developer-local screenshot and recording tools do not care which one is active: they grab the window from inside Qt (grabWindow()) through the command server rather than through the compositor — see Development → Screenshots.

Black UI, missing icons or album art

The nav icons and media controls are SVGs wrapped in ColorOverlay and the album art uses MultiEffect / DropShadow — GPU shader effects that need a real GL context. With QT_QPA_PLATFORM=offscreen these come out blank, so an offscreen run does not show their appearance. On a real display, a black window usually means a broken GL stack: try QT_QUICK_BACKEND=software (slow but reliable) and check the log for module "..." is not installed, which means the PySide6 install lacks a QML module the frontend imports (QtQuick.Effects, Qt5Compat.GraphicalEffects).

Nothing appears at startup

  • QML import path: main.py adds <checkout>/frontend to the import path and loads frontend/Main.qml from its own location, so it works from any working directory. If Main.qml fails to load, main.py exits with code -1; the QML errors are in the log and the terminal.
  • Controls style: main.py assigns os.environ["QT_QUICK_CONTROLS_STYLE"] = "Basic" before importing Qt, overwriting any value you exported, because the sliders are fully custom-drawn.
  • Run with --debug and read the QML warnings in the debug log.

UI scale wrong

The uiScale setting ranges 0.5–2.0 in 0.05 steps (Settings → Display, or edit settingsConfigure.json; an old default of 0.6 is migrated to 1.0 on load). On top of it main.py computes screenAutoScale from the shorter edge of the primary screen's available size divided by 720, clamped to 0.4–3.0 (1.0 when no screen is reported). The startup log line Screen auto-detection: WxH, autoScale=… shows the value used.

Audio Issues

No or very quiet audio

  • The volume slider is mapped through a quadratic curve, (volume/100)^2.0 (backend/volume_utils.py, pinned by tests/test_smoke.py::test_volume_curve_math): 50 % on the slider is 25 % linear gain, 10 % is 1 %. Low slider values are genuinely quiet.
  • Mute: mediaManager.is_muted(). toggle_mute() is guarded by a 150 ms lock (_mute_toggle_locked) so a bouncing ESP32 button or gesture cannot double-toggle; a mute press within 150 ms of the previous one is ignored. OCTAVE's mute also mutes phone-mirror audio.
  • Phone-mirror ducking: while the phone is producing sound, local playback is ducked to scrcpyAudioDuckLevel (default 0.1) when scrcpyAudioDuckEnabled is on (the default), and released after the phone has been quiet for a hold time (AUDIO_HOLD_MS = 1500 in the client). If music seems to drop out during mirroring, this is why.
  • Verify the output device in the system mixer.

PulseAudio / PipeWire (Linux)

pactl list short sinks             # is there a sink at all?
pactl info                         # identifies the audio server (PulseAudio or PipeWire compatibility)

Media backend

The media manager passes FFmpeg-style probe-size / analyzeduration hints to its QMediaPlayer. The backend sets no QT_MEDIA_BACKEND or GStreamer variable; if you set one yourself and playback breaks, unset it.

Playback stalls, a track keeps skipping, or playback stops by itself

An invalid or stalled file is retried at most 2 times (MAX_RECOVERY_ATTEMPTS), then skipped; after 10 consecutive unplayable tracks (MAX_CONSECUTIVE_BAD_TRACKS, or the playlist length if shorter) playback stops and the source is cleared rather than looping forever (N unplayable tracks in a row; stopping playback in the log). The usual cause is an unsupported or truncated file. Extensions scanned: .mp3 .m4a .mp4 .flac .ogg .opus .wav.

OBD Connection Issues

Read the Connection Log on Settings → OBD first: connection steps, rfcomm commands and errors the manager sees are appended there. The status label follows connectionStatusChanged; get_connection_status() returns the last value, starting at Disconnected. Values the Python manager emits include Connecting, Connected, Reconnecting, No Vehicle (adapter answered, vehicle did not), Device Not Found, Device Lost, Stale Connection, Connection Failed, Error and Disconnected.

Which port / address to enter

The single field (obdBluetoothPort, default empty) accepts a Bluetooth MAC, a device path or a COM port. Left empty, the default is /dev/rfcomm0 on Linux, COM3 on Windows and /dev/tty.OBD on macOS. While disconnected the manager rescans every 10 s: Linux globs /dev/rfcomm*, /dev/ttyUSB*, /dev/ttyACM* (/dev/ttyS* is excluded); Windows lists serial ports whose description mentions bluetooth / obd / elm / serial / usb, plus every COM port; macOS looks at tty.OBD*, tty.Bluetooth*, cu.OBD*, cu.Bluetooth*, tty.usbserial*, cu.usbserial* and *ELM*. The OBD scanner does not exclude the ESP32 knob's USB serial port; the knob's own scan does exclude the configured OBD port.

Serial port permissions (Linux)

sudo usermod -aG dialout $USER     # log out and back in, then: groups | grep dialout

Bluetooth ELM327 pairing (Linux)

The adapter picker (obdAdapterFinder, Linux only) pairs over BlueZ and connects with connect_direct(), an rfcomm://<MAC> pyserial URL handled by backend/obd_transports/protocol_rfcomm.py — a direct RFCOMM socket that needs no rfcomm bind (root) and no /dev/rfcommN node. A bare MAC entered through connect_to_adapter() uses the older path: it reuses an existing /dev/rfcommN or runs rfcomm bind to /dev/rfcomm0. To bind by hand and enter the resulting device path:

sudo rfcomm bind 0 XX:XX:XX:XX:XX:XX
ls -la /dev/rfcomm0

"rfcomm bind failed: rfcomm binary not found (install bluez-utils, or pre-bind and enter /dev/rfcomm0)" in the Connection Log means the package that ships rfcomm is missing.

Connection is slow or times out

  • The connect runs on a worker (OBDConnectionWorker on a QThread) so the UI does not block; progress arrives through connectionProgress and the detail text.
  • The python-obd connection timeout is 5 s by default (_connection_timeout); set_connection_timeout(seconds) clamps it to 5–60 s, and no QML calls it. There is no settings key for it.
  • obdFastMode (default on) is passed to python-obd as fast=; polling uses delay_cmds=0.
  • The last successful protocol is cached and passed to python-obd on the next connect; an Input/output error / Errno 5 clears it so the next attempt auto-detects again.
  • obdAutoReconnectAttempts is 0–10 and defaults to 0 = off. With 1–10 the manager retries with a min(10, 2 + 2n) s back-off, then falls back to the passive 10 s device scan, which also runs while it is off.

"Device Lost" / "Bluetooth device disconnected"

A monitor thread checks every 2 s that the configured port still exists (for rfcomm:// URLs it only validates the address) and that python-obd still reports a car connection. A vanished port gives Device Lost; a lost car connection gives Disconnected / "Connection to vehicle lost". Both schedule the auto-reconnect (if enabled) and restart the device scan.

"No Data" for a parameter

  • Two seconds after a successful connect, scan_vehicle() reads python-obd's supported_commands for the live connection (no second connection, polling continues) and reports progress on the OBD settings page. The parameter model then hides or gates what the vehicle does not support; see OBD Manager.
  • Only parameters some visible page asks for are polled (demand-driven via setParameterDemand).
  • Many parameters only report with the engine running.

Data watchdog: "Stale Connection" / "No data received, reconnecting..."

While connected and at least one parameter is being watched, a 5 s timer checks whether any data arrived in the last 30 s. If not, it logs [OBD] Data watchdog triggered, emits the status above, tears the connection down and reconnects after 100 ms. A watchdog trip can reflect the vehicle, the adapter or the transport, so read the python-obd transcript before deciding which.

Reading the ELM327 transcript

Run with --debug and read python-obd's write: / read: lines in octave-debug.log; the extended-PID and VIN decoders that obd_manager imports from backend/elm327_protocol.py log under octave.elm327_protocol.

yt-dlp is the pip package pinned in requirements.txt (yt-dlp==2026.8.19) and runs in-process through the vendored backend/music_dl package; no external yt-dlp binary is used.

Phone Mirror Issues

Mirroring needs adb, the phone server jar and PyAV; phoneMirrorManager.nativeAvailable is true only when all three are present, and getInstallInstructions() names the missing piece. The full design is on the Phone Mirror page.

On ARM boards Google ships no adb; install the distro's (e.g. sudo apt install adb).

"Phone is connected but USB debugging is not authorized. …"adb devices shows unauthorized. Unlock the phone and accept the prompt (tick "always allow"); if the prompt never appears, unplug and replug.

Hardware Sensor Issues

I²C permissions and bus

sudo usermod -aG i2c $USER
sudo raspi-config                  # Raspberry Pi: Interface Options > I2C > Enable
i2cdetect -y 2
# Expected: 0x6A (LSM6DSL), 0x1C (LIS3MDL), 0x77 (BMP388), 0x73 (PAJ7620U2)

The bus number is the constant I2C_BUS = 2 in backend/berryimu_manager.py and backend/gesture_manager.py — there is no setting. Both talk to it through smbus2 (Linux only).

Reconnection behaviour

The BerryIMU and gesture managers retry a failed initialisation up to 5 times with a linear back-off (5, 10, 15, 20, 25 s), then give up. A PermissionError is not retried (it cannot fix itself): fix the group, log out and in, then toggle the sensor off and on in Settings → Accessories or restart. A missing smbus2 is not retried either.

IMU updates look slow

The read/fusion loop keeps running, but the signals emitted to QML drop to 5 Hz (IDLE_EMIT_INTERVAL = 0.2) unless a page that draws them is showing — Main.qml calls berryIMU.setActive() for the Car, Sensors, Sensor Home and OBD menus, and for the home screen when an IMU parameter is on a home card. This is the idle-CPU optimisation, not a fault.

ESP32 volume knob not connecting

  • Confirm the ESP32-S3 dongle appears in dmesg after plugging in and that you are in dialout.
  • esp32VolumePort defaults to empty, which means a port recognised as an ESP32-S3 (Espressif USB id 303a) is auto-selected at startup; the configured OBD port is excluded from the knob's scan. Set the port manually in the Volume Knob settings only if auto-detection picks the wrong one.
  • The reader runs at 115200 baud and blocks in readline() with a 1 s timeout. A serial.SerialException ends the read loop and is handled as a disconnect; with esp32AutoReconnect on (the default) the manager then attempts up to five reconnects.

Performance Issues

UI stuttering

  1. Look for octave.ui_watchdog warnings in octave.log — the watchdog samples every 2 s and warns when the GUI thread has not answered for more than 5 s; shorter stalls are not reported.
  2. With the developer-local profiling modules present, run python main.py --profile and watch the [PERF] line: event-loop latency is green under 5 ms average, yellow under 16 ms, red above (STUTTER); the GIL column is how late a background thread wakes from a 10 ms wait; slots with p95 > 2 ms are listed. Details on Utilities.

High memory usage

  • The cover cache in backend/temp/ is pruned to 500 files at startup (_max_cache_files); filenames hash the album id, not the image contents. The in-memory metadata cache holds up to 1000 entries (_metadata_cache_max); the persistent metadata_cache.json store is separate and not bounded by that limit (see Media Manager).
  • Audio analyzer: the FFT levels are computed for the entire track when it starts, so a long lossless file costs memory and CPU up front.

Slow library scan

The library scan runs on the GUI thread (progress via scanProgress); a very large first scan blocks the UI until it finishes, and can trigger the UI watchdog. Neighbouring-track pre-cache (±3 tracks, 80 ms after a track change) and album-colour extraction run on worker threads.

WSL Display Issues

setup.py skips launching under WSL when neither DISPLAY nor WAYLAND_DISPLAY is set, and prints options (WSLg after wsl --update, an X server, or running on Windows directly). WSLg supports WSL 2 on Windows 10 build 19044+ and Windows 11; follow Microsoft's GUI-app instructions. An external X server needs a DISPLAY value appropriate to its address and WSL network mode; do not assume :0. Software rendering can help diagnose graphics problems, but does not reproduce shader effects or the 3D view:

export QT_QUICK_BACKEND=software
export LIBGL_ALWAYS_SOFTWARE=1
python main.py
