Where to Look First

OCTAVE deliberately has no in-app error pop-ups (TODO/error-notification-ui.md: anything flickering into a driver's peripheral vision is a distraction risk, so errors go to the logs where the person debugging will look). Every subsystem therefore reports through three channels:

  1. The Connection Log / status text on the relevant page — the OBD settings card shows each connection step and rfcomm / permission errors; the Download page shows Error: <name> - <message> and marks the queue row failed; the phone-mirror view shows the adb / authorization message.
  2. Settings → About → Diagnostics card (diagnosticsManager, both backends) — a 2×2 grid: Refresh (last 200 log lines), Copy (last 400 lines to the clipboard), Export logs (copies the log files to the Downloads folder — the way to get logs off an Android tablet or a head unit without a shell) and Open folder (hidden on Android/iOS, where canOpenFolder is false). The log directory path is printed on the card.
  3. The rotating log files described next. A hung UI, a crash and a dropped adapter all leave a trace there even when the screen shows nothing.

Log Files, Crash Traces & Debug Mode

Log directory

Both backends write to a logs/ subdirectory of the app data directory (SettingsManager::getAppDataDir() / get_app_data_dir()):

PlatformPath
Windows%APPDATA%\OCTAVE\logs\
macOS~/Library/Application Support/OCTAVE/logs/
Linux$XDG_CONFIG_HOME/OCTAVE/logs/, i.e. ~/.config/OCTAVE/logs/
AndroidgetAppDataDir() has no Android branch, so the C++ build falls through the Linux rule into the app's private home directory. It is not browsable from a file manager — use Export logs on the Diagnostics card, which writes into Download/. On Android and iOS the message handler also forwards every line to Qt's default handler (stderr goes nowhere on a phone), so adb logcat / os_log show the same messages.

Log files — the two backends use different names

BackendFileLevelMax sizeBackupsNotes
Pythonoctave.logINFO+5 MB3backend/logging_config.py, RotatingFileHandler
Pythonoctave-error.logERROR+2 MB5also receives crash tracebacks and faulthandler dumps
Pythonoctave-debug.logDEBUG+10 MB2only with --debug
C++octave-cpp.logINFO+5 MB3src/util/logger.cpp, custom rotation with the same policy
C++octave-cpp-error.logWARNING+2 MB5also the raw crash descriptor for the signal handler
C++octave-cpp-debug.logeverything10 MB2only with --debug

Because the names differ, a machine that has run both backends has both sets side by side; check the timestamps to see which one produced the session you care about. Total disk is bounded at roughly 32 MB per backend without debug, ~62 MB with it.

Line format

# Python console (HH:MM:SS):
HH:MM:SS | LEVEL   | octave.module            | message

# Python file:
YYYY-MM-DD HH:MM:SS | LEVEL   | octave.module | file.py:line | function() | message

# C++ file and stderr (same shape, millisecond timestamps, Qt category in the module column):
YYYY-MM-DD HH:MM:SS.zzz | LEVEL   | octave.elm327 | obdmanager.cpp:1772 | message

Python logger names come from get_logger(__name__): octave.obd, octave.media, octave.spotify, octave.settings, octave.clock, octave.android_auto[.capture|.embedded], octave.phone_mirror[.host|.capture|.container|.embedded], octave.app for main.py, and octave.<module> for everything else (e.g. octave.ui_watchdog, octave.elm327_protocol). python-obd's own obd logger tree is attached to the same handlers so an ELM327 session leaves its write:/read: transcript in octave-debug.log. The C++ side uses one QLoggingCategory per manager: octave.settings, octave.media, octave.spotify, octave.download, octave.network, octave.phonemirror (+ octave.phonemirror.client for the scrcpy-protocol client), octave.androidauto, octave.embeddeddhu, octave.audioanalyzer, octave.berryimu, octave.gesture, octave.esp32volume, octave.dashboards, octave.diagnostics, octave.ui_watchdog and octave.elm327 (protocol transcript and the Android BLE bridge lines). The exceptions are obdmanager.cpp, clock.cpp and volumecontroller.cpp, which log through plain qDebug()/qWarning() and therefore appear under the category default — so there is no octave.obd category to filter on in the C++ logs; look for the [OBD Worker] message prefix instead. With --debug the C++ build sets the filter rules *.debug=true, qt.*.debug=false; without it *.debug=false, so category-debug output costs nothing.

Crash traces

  • Python: sys.excepthook and threading.excepthook log Unhandled exception on the main thread / in thread '<name>' with the traceback at CRITICAL, and faulthandler is enabled on a descriptor of octave-error.log so a native fault (SIGSEGV, SIGABRT, SIGFPE, SIGBUS, SIGILL — e.g. inside PySide6 or PyAV) dumps every Python thread's stack there.
  • C++ (Unix): a signal handler for the same five signals writes ==== FATAL SIGSEGV - backtrace (addresses; symbolise with addr2line against this build) ==== plus backtrace_symbols_fd() frames to octave-cpp-error.log and stderr, then restores the default action and re-raises so the OS still produces a core / tombstone. The addresses are only meaningful against the exact binary that crashed. The handler never touches Qt (every log line is already flushed as it is written, so it has nothing to flush); a qFatal goes through the message handler first, which flushes the files before Qt aborts, and a normal exit flushes them last in the aboutToQuit cleanup. Windows: SetUnhandledExceptionFilter writes the exception code, address and a CaptureStackBackTrace frame list.
  • SIGTERM / SIGINT (launcher scripts, systemd, Ctrl-C) on desktop Unix are turned into app.quit() through a self-pipe so the aboutToQuit cleanup runs and child processes / adb forwards are not orphaned (src/main.cpp).

UI watchdog: "UI thread blocked for N s and counting"

Both backends run a watchdog thread (src/util/uiwatchdog.cpp, backend/ui_watchdog.py) that posts a ping to the GUI thread every 2 s; if the GUI thread has not answered within 5 s a WARNING is logged under octave.ui_watchdog, once per stall, followed by UI thread responsive again after N s when it recovers. A frozen head unit therefore leaves a timestamped trace even though nothing was drawn. Look at the lines immediately before the warning to see which manager was busy; the watchdog is stopped before Qt tears down the QObjects so a shutdown never shows as a stall.

Enabling debug mode

python main.py --debug      # Python backend
./build/octave --debug      # C++ backend (its only command-line flag)

Creates the -debug.log file with DEBUG-level output. Useful for: the ELM327 TX/RX transcript (C++ logs [OBD Worker] TX/RX lines with round-trip times at debug level under octave.elm327; Python attaches python-obd's transcript), serial data from the ESP32 knob, settings load/save, media library scanning and tag extraction, Spotify API calls and token refresh, and the phone-mirror adb / server launch sequence.

Display & Rendering Issues

XCB platform plugin errors (Linux)

Error
qt.qpa.plugin: Could not load the Qt platform plugin "xcb"

Install the X11/XCB libraries. The list setup.py installs on Debian/Ubuntu is the reference:

sudo apt install libxcb1 libxcb-cursor0 libxcb-icccm4 libxcb-image0 libxcb-keysyms1 \
  libxcb-randr0 libxcb-render0 libxcb-render-util0 libxcb-shape0 libxcb-shm0 \
  libxcb-sync1 libxcb-xfixes0 libxcb-xinerama0 libxcb-xkb1 libxcb-util1 \
  libxkbcommon0 libxkbcommon-x11-0

The AppImage ships its own platform plugins and sets QT_QPA_PLATFORM_PLUGIN_PATH in its AppRun, so this error from an AppImage means an unset DISPLAY/WAYLAND_DISPLAY rather than a missing package.

Wayland vs X11

Qt picks the platform plugin from the session. To force one (either backend, same variable):

export QT_QPA_PLATFORM=xcb       # force X11 / XWayland
export QT_QPA_PLATFORM=wayland   # force Wayland
python main.py                   # or ./build/octave

The dev screenshot and recording tools do not care which one is active: they grab the window from inside Qt (grabWindow()) rather than through the compositor — see Development → Screenshots.

Black UI, missing icons or album art

The nav icons and media controls are SVGs wrapped in ColorOverlay and the album art uses MultiEffect / DropShadow — GPU shader effects that need a real GL context. Under Qt's offscreen platform (used by the smoke tests and the fastest screenshot mode) they paint blank by design. On a real display, a black window usually means a broken GL stack: try QT_QUICK_BACKEND=software (slow but reliable) and check the log for module "..." is not installed, which means the Qt build lacks QtQuick.Effects / Qt5Compat.GraphicalEffects (Building).

Nothing appears at startup

  • QML import path: the Python backend adds <checkout>/frontend to the import path from main.py's own location, so it works from any cwd. The C++ binary looks for frontend/ next to itself, then one level up; running a binary copied elsewhere logs Could not locate frontend/ directory.
  • Controls style: both backends force the Basic style (os.environ["QT_QUICK_CONTROLS_STYLE"] = "Basic" / QQuickStyle::setStyle("Basic")) because the sliders are fully custom-drawn. An externally set QT_QUICK_CONTROLS_STYLE is overridden by the Python side but can surprise a C++ build started through a wrapper.
  • Run with --debug and read the QML warnings in the debug log.

UI scale wrong

The uiScale setting ranges 0.5–2.0 in 0.05 steps (Settings → Display, or edit settingsConfigure.json; an old default of 0.6 is migrated to 1.0 on load). On top of it both backends compute screenAutoScale from the shorter screen edge divided by 720, clamped to 0.4–3.0, so a portrait-reporting Android tablet no longer gets a 3× factor.

Audio Issues

No or very quiet audio

  • The volume slider is mapped through a quadratic curve, (volume/100)^2.0 (src/managers/volumecontroller.cpp / backend/volume_utils.py, pinned by tests/test_smoke.py::test_volume_curve_math): 50 % on the slider is 25 % linear gain, 10 % is 1 %. Low slider values are genuinely quiet.
  • Mute: mediaManager.is_muted() in both backends. toggle_mute() is guarded by a 150 ms lock (_mute_toggle_locked / m_muteToggleLocked) so a bouncing ESP32 button or gesture cannot double-toggle; a mute press within 150 ms of the previous one is ignored.
  • Phone-mirror ducking: while the phone is producing sound, local playback is ducked to scrcpyAudioDuckLevel (default 0.1) and released 1.5 s after the phone goes quiet (scrcpyAudioDuckEnabled, default on). If music seems to drop out during mirroring, this is why.
  • Verify the output device in the system mixer.

PulseAudio / PipeWire (Linux)

pactl list short sinks             # is there a sink at all?
pulseaudio --check || pulseaudio --start

Media backend

OCTAVE assumes Qt Multimedia's FFmpeg backend: the media manager passes probe-size / analyzeduration hints to the player, and the aarch64 AppImage deliberately ships without Qt's GStreamer plugin (Building). Neither backend sets QT_MEDIA_BACKEND or any GStreamer variable; if you set one yourself and playback breaks, unset it.

Playback stalls, a track keeps skipping, or playback stops by itself

Both backends run the same recovery: an invalid or stalled file is retried at most 2 times, then skipped; after 10 consecutive unplayable tracks (or the playlist length, if shorter) playback stops and the source is cleared rather than looping forever. Check the log for the file names; the usual cause is an unsupported container. Extensions scanned: .mp3 .m4a .mp4 .flac .ogg .opus .wav in both backends (.mp4 because yt-dlp names YouTube audio-only streams that way).

OBD Connection Issues

Read the Connection Log on Settings → OBD first: every init step, rfcomm command and error the manager sees is appended there in both backends. The status dot and label above it follow connectionStatusChanged, and get_connection_status() returns the same vocabulary on both backends (initially "Disconnected"; the old python-obd strings "Car Connected" / "No Connection" and the C++ "Not Connected" are gone). The colour map covers Connected (accent), Connecting / Reconnecting / Device Lost / Stale Connection (warning), Device Not Found / Connection Failed / Error (error), Disconnected (grey), No Vehicle (info) and the Android BLE states (No MAC Address, Connecting BLE..., Discovering services..., Initializing ELM327..., Querying PIDs..., BLE connect failed, BLE error, Bluetooth permission denied); anything else renders in the error colour.

Which port / address to enter

The single field (obdBluetoothPort, placeholder "MAC address, /dev path, or COM port") accepts a Bluetooth MAC, a device path or a COM port. Left empty, the default is /dev/rfcomm0 on Linux, COM3 on Windows, /dev/tty.OBD on macOS, and nothing on Android (a MAC is required). While disconnected, both backends rescan every 10 s: Linux globs /dev/rfcomm*, /dev/ttyUSB*, /dev/ttyACM* (/dev/ttyS* is excluded as a false-positive source); Windows filters serial-port descriptions for bluetooth / obd / elm / serial / usb; macOS looks at tty.OBD*, tty.Bluetooth*, cu.*, *ELM*. Note the OBD scanner does not exclude the ESP32 volume knob's USB serial port; the knob's own manager does exclude the OBD port.

Serial port permissions (Linux)

sudo usermod -aG dialout $USER     # log out and back in, then: groups | grep dialout

Bluetooth ELM327 pairing (Linux)

Linux uses classic Bluetooth SPP through rfcomm, not Qt Bluetooth sockets. Pair and trust once with bluetoothctl (scan on, pair XX:XX:XX:XX:XX:XX, trust ...). Then either enter the MAC in the OBD settings — both backends run rfcomm bind 0 <mac> 1 for you (ensureRfcommBound / _ensure_rfcomm_bound) and reuse an existing /dev/rfcommN — or bind manually and enter the device path:

sudo rfcomm bind 0 XX:XX:XX:XX:XX:XX
ls -la /dev/rfcomm0

"rfcomm bind failed: rfcomm binary not found" in the Connection Log means bluez-utils (Arch) / the package that ships rfcomm is missing; the log also tells you to bind once with sudo and enter /dev/rfcomm0.

Connection is slow or times out

  • The connection runs on a dedicated worker thread (OBDConnectionWorker on a QThread in both backends) so the UI never blocks; progress is reported through connectionProgress / connectionDetail.
  • The connection timeout is 5 s by default and is set at runtime through obdManager.set_connection_timeout(seconds) (there is no obdConnectionTimeout settings key in either backend). The Python backend passes it to python-obd; the C++ worker uses it for the vehicle-verify wait (the RPM probe after init) and fixed per-command timeouts otherwise (300–1500 ms for init commands, 500 ms per poll).
  • obdFastMode (default on): C++ polls with a 0 ms interval instead of 50 ms; Python passes python-obd's fast= flag.
  • Only the Python backend caches the last successful protocol and passes it to python-obd on reconnect; the C++ worker always sends its fixed init sequence ending in ATSP0 (auto-detect).
  • obdAutoReconnectAttempts is 0–10 and defaults to 0 = off (shown as "Off" on the slider). With 0, a drop leaves the manager in a passive 10 s port scan; with 1–10 the Python backend retries with a min(10, 2 + 2n) s backoff.

"Adapter stopped responding" / a dead port pegs a CPU core

C++ only (python-obd owns the I/O on the Python side). Commits 953f85f, 0404f7b and 5d76a03 fixed a worker that span at 100 % CPU for the whole command timeout on an rfcomm port that had gone away (gdb on the Pi showed the entire stack inside QSerialPort). Now: non-productive waits are paced to ~10 Hz; after 50 consecutive "readable but zero bytes" polls the worker logs Port reports readable but delivers no data; treating as disconnected, releases the port and emits connectionLost("Adapter stopped responding"); every failed init and the no-vehicle path also release the port so no read notifier stays armed; a USB unplug (ResourceError / DeviceNotFoundError) is treated as connection lost. On the Python side a 2 s monitor thread reports "Device Lost" / "Bluetooth device disconnected" when the port path disappears, and an Errno 5 clears the cached protocol.

"No Data" for a parameter

  • Both backends query the adapter's supported-PID bitmaps (ranges 00/20/40/60/80/A0/C0/E0) automatically 2 s after every successful connect; the OBD settings page shows the scan progress. There is no manual "Scan Vehicle" button.
  • The parameter model (frontend/OBDParameterModel.qml) lists 84 OBD parameters plus 8 BerryIMU-derived ones; the ELM327 PID table in both backends carries every python-obd mode-01 command (82) plus the adapter voltage (ELM_VOLTAGE, ATRV), and parameter toggles apply live without a reconnect. Watching a parameter the vehicle does not support simply yields no value — it is not an error.
  • Many parameters only report with the engine running.

Data watchdog: "Stale Connection" / "No data received, reconnecting..."

While connected and at least one parameter is being watched, both backends check every 5 s whether any data arrived in the last 30 s (DATA_WATCHDOG_TIMEOUT_MS = 30000). If not, they log the messages above, tear the connection down and reconnect after 100 ms (the Python backend refreshes its timestamp from a single watched PID, preferring RPM). Repeated watchdog trips with a healthy adapter usually mean the vehicle stopped answering (ignition off) rather than a link problem.

Reading the ELM327 transcript

C++: TX/RX lines with round-trip times are logged at debug level under octave.elm327 (run with --debug); short responses and decoder exceptions are warnings and always logged. Python: run with --debug and read python-obd's write: / read: lines in octave-debug.log; the parity decoder logs under octave.elm327_protocol.

Android OBD (Bluetooth / BLE)

Android

The C++ APK connects to ELM327 adapters over Bluetooth through android/src/org/octave/app/OctaveOBDBridge.java (Qt's QLowEnergyController is deliberately bypassed). The manifest declares BLUETOOTH_CONNECT, BLUETOOTH_SCAN (neverForLocation, so no location permission is needed on Android 12+) and BLUETOOTH_ADVERTISE; ACCESS_FINE_LOCATION is only declared up to API 30.

SymptomCause / fix
Status "Requesting Bluetooth permission — tap Allow, then tap Connect again"First connect on API 31+: the bridge calls requestPermissions() and returns; answer the system dialog and press Connect again.
Status "Bluetooth permission denied", detail "Grant Bluetooth in Settings -> Apps -> OCTAVE -> Permissions"The permission was refused. Grant it in the system app settings. The permission flow lives entirely in the Java bridge now (OctaveOBDBridge.connect() requests BLUETOOTH_CONNECT); Qt's QBluetoothPermission is no longer involved.
Nothing happens with an empty port fieldAndroid requires the adapter's MAC address; there is no default and no serial scan. Once Bluetooth permission has been granted (first Connect tap), the adapter list on the OBD settings page fills with the phone's paired devices as "<name> · <MAC>" (OctaveOBDBridge.bondedDevices()) — pick the ELM327 there instead of typing the address. An empty list means the permission is still missing or Bluetooth is off.
Where are the BLE logs?The Java side queues I|/W| lines; the OBD manager drains up to 50 per 50 ms poll and re-emits them as [BLE] ... under octave.elm327, so they land in octave-cpp.log, the Connection Log and the Diagnostics export. No adb logcat needed.
Update refuses to installEvery CI release is signed with a fresh key: uninstall org.octave.app first (Building → Android).

Spotify Authentication Issues

Spotify is desktop-only; the Android build compiles a stub so the QML bindings stay valid but nothing connects.

OAuth flow (both backends)

  1. Enter the Client ID and Client Secret in Spotify settings.
  2. Click Connect — OCTAVE starts a local HTTP listener on 127.0.0.1:8888 (Python: stdlib HTTPServer on a thread; C++: a hand-rolled QTcpServer that parses the GET line).
  3. The browser opens Spotify's authorization page.
  4. Spotify redirects to http://127.0.0.1:8888/callback.
  5. OCTAVE exchanges the code for tokens (spotipy / QNetworkAccessManager).

Music Download (yt-dlp) Issues

Where yt-dlp comes from differs per backend: the C++ desktop build runs an external yt-dlp found on PATH or in the app dir, /usr/local/bin, /usr/bin, ~/.local/bin (.exe variants on Windows); the Python backend imports the pip package in-process (yt-dlp==2026.8.19 in requirements.txt); Android uses the youtubedl-android AAR through JNI (sentinel path jni://yt-dlp). A build configured with -DOCTAVE_ENABLE_DOWNLOADS=OFF reports "Downloads disabled in this build".

yt-dlp not found (C++ desktop)Install it (pipx install yt-dlp or the distro package) somewhere on the lookup list above.
"Sign in to confirm you're not a bot"Usually a VPN: YouTube blocklists most shared VPN exit IPs; downloads work again on a residential connection or a dedicated-IP exit node (README). To stay on the VPN, export a Netscape cookies.txt from a logged-in browser (the README walks through the "Get cookies.txt LOCALLY" extension) and save it as youtube_cookies.txt in the Downloads folder: ~/Downloads/ on Linux/macOS, %USERPROFILE%\Downloads\ on Windows, /storage/emulated/0/Download/ on Android. No restart is needed: both backends re-check the file before every download. Both look only at that one path (QStandardPaths::DownloadLocation / _youtube_cookies_default_path()) and log a warning naming it when the file is absent; the C++ backend also retries across several yt-dlp player clients with linear backoff because the wall is per-video. Phone Mirror Issues

Mirroring needs only adb and the phone server jar OCTAVE ships; the full design is on the Phone Mirror page. Symptoms specific to recent behaviour:

SymptomCause / fix
"adb not found. Run scripts/fetch_platform_tools.py or install android-tools."Both backends look for a bundled adb first (platform-tools/ next to the binary, tools/platform-tools/<os>/ in a checkout, Contents/Resources/platform-tools/ in the bundle), then PATH, then common SDK paths. On ARM boards Google ships no adb; install the distro's (sudo apt install adb).
"Phone is connected but USB debugging is not authorized. Unlock the phone and tap 'Allow' on the USB debugging prompt."adb devices shows unauthorized. Unlock, accept the prompt (tick "always allow"); if the prompt never appears, unplug and replug.
Picture freezes for a moment when the cable is bumped, then continuesWorking as designed: for virtual-display sessions the server keeps the session alive for octave_persist_ms = 60 s after the socket drops; the client reattaches to the same session within 55 s with a 4 s deadline, and the view holds the last frame and shows a "Reconnecting to phone…" badge only after 2 s. If the attach fails or the window expires ("No client reconnected within N ms" in the server log) a fresh session starts.
Mirror goes dark when the phone screen is off / shows a black frame with a status barThe phone-side MirrorKeeper reports sleep state; while asleep every incoming frame is dropped and the last good one is held. A stride-2 luma test over the Y plane detects black frames, with a 5 % lenient fraction (a solid status strip is 3–4 % of samples) for 3 s around a reattach.

phoneMirrorManager.nativeAvailable is false (C++)The binary was built without libavcodec; there is no other decoder path. Rebuild with FFmpeg dev packages present.

Hardware Sensor Issues

I²C permissions and bus

sudo usermod -aG i2c $USER
sudo raspi-config                  # Raspberry Pi: Interface Options > I2C > Enable
i2cdetect -y 2
# Expected: 0x6A (LSM6DSL), 0x1C (LIS3MDL), 0x77 (BMP388), 0x73 (PAJ7620U2)

The bus number is a hard-coded constant, I2C_BUS = 2, in both backends (src/managers/berryimumanager.cpp, src/managers/gesturemanager.cpp, backend/berryimu_manager.py, backend/gesture_manager.py) — there is no setting. The Python backend talks through smbus2; the C++ backend opens /dev/i2c-2 directly with ioctl(I2C_SLAVE) (Linux only).

Reconnection behaviour

BerryIMU and gesture managers retry up to 5 times with linear backoff (5, 10, 15, 20, 25 s) in both backends, then give up. Both skip the retries on a permission error (it cannot fix itself): Python on PermissionError, C++ when open() fails with EACCES / EPERM, logging permission denied on /dev/i2c-2 - add the user to the i2c group; not retrying. Fix the group, log out and in, then toggle the sensor off and on in Settings → Accessories. A bus that fails mid-run is reported as "Error" and retried: Python on the first failed read, C++ after 5 consecutive failed block reads (read loop error: 5 consecutive I2C read failures), so one NACK on a marginal cable no longer goes unnoticed as frozen zeros.

IMU updates look slow

Sampling and the Madgwick filter always run at full rate, but the signals emitted to QML drop to 5 Hz (IDLE_EMIT_INTERVAL = 0.2) unless a page that draws them is showing — Car, Sensors, Sensor Home, the OBD menu, or the home screen when an IMU parameter is on a home card — where they run at ~60 Hz. This is the idle-CPU optimisation, not a fault.

ESP32 volume knob not connecting

  • Confirm the ESP32-S3 dongle appears in dmesg after plugging in and that you are in dialout.
  • The knob's manager excludes the OBD adapter's port from its scan; esp32VolumePort defaults to empty, which means the ESP32-S3 is auto-selected at startup — set it manually (Volume Knob settings) only if auto-detection picks the wrong one. A settings file from an older build may still hold the former "COM7" default; clear it.
  • A dongle that disappears is detected in both backends: Python on any SerialException, C++ on QSerialPort's ResourceError / DeviceNotFoundError / PermissionError / ReadError / WriteError or a rejected keepalive write; with esp32AutoReconnect on it then retries five times.
  • Baud rate is 115200 in both backends. The Python reader blocks in readline() on a 1 s port timeout (commit 94d61be, replacing 100 Hz polling); the C++ reader is driven by QSerialPort::readyRead.

Performance Issues

UI stuttering

  1. Look for octave.ui_watchdog warnings in the log — they timestamp every stall longer than 5 s.
  2. Python: run python main.py --profile and watch the [PERF] line: event-loop latency is green under 5 ms average, yellow under 16 ms, red above (STUTTER); GIL jitter is the delay a background thread sees trying to run every 10 ms; slow slots are those with p95 > 2 ms. Details on the Development page. There is no equivalent flag in the C++ build.
  3. Check CPU: if a core is pegged while the OBD adapter is unplugged, see the dead-port note under OBD.

High memory usage

  • Album-art cache: 500 cover files with LRU eviction (_max_cache_files / m_maxCacheFiles), content-addressed cover_<sha256[:16]> files kept across runs and pruned at startup; metadata cache 1000 entries, persisted to <app data dir>/metadata_cache.json.
  • Audio analyzer: the FFT is pre-computed for the entire track when it starts, so a long lossless file costs memory up front.

Slow library scan

The library scan runs synchronously on the GUI thread in both backends (progress via scanProgress); a very large first scan will block the UI until it finishes. Neighbouring-track precache (±3 tracks, 80 ms after a track change) and album-colour extraction run off-thread.

WSL Display Issues

setup.py detects WSL from /proc/version and, when neither DISPLAY nor WAYLAND_DISPLAY is set, prints the options instead of launching: WSLg on Windows 11 (try wsl --update), an X server such as VcXsrv or X410 on Windows 10 followed by export DISPLAY=:0, or running OCTAVE natively on Windows. Once a display exists, python main.py runs normally; if OpenGL fails under an external X server, fall back to software rendering:

export QT_QUICK_BACKEND=software
export LIBGL_ALWAYS_SOFTWARE=1
python main.py
