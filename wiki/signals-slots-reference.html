How managers reach QML
Every manager is a QObject member of AppCore (src/appcore.{h,cpp}), set as a context property by src/main.cpp, and QML reaches it by that name: mediaManager.next_track(), settingsManager.themeSetting, obdManager.onRpmChanged. Other context values are screenAutoScale (float, short screen edge / 720 clamped to 0.4–3.0), isAndroid (bool, true only in the Android build), wikiViewerAvailable (bool: an embedded web viewer is available), and wikiHomeUrl (QUrl: the wiki entry point). The qmlRegisterType'd OCTAVE.AndroidAuto.EmbeddedDhuItem and the QML singletons (OBDParameterModel, WidgetCatalog, …) are documented in Components, not here.

Reading this page

  • Properties are Q_PROPERTY declarations. Almost all are read-only from QML; call the matching save_* / set* slot to change them. Notify signal is what a QML binding or on<Name>Changed handler listens to.
  • Invokables & Slots are Q_INVOKABLE methods and public slots. Signatures show the C++ parameter types without const / &. QVariantList / QStringList arrive in QML as JS arrays, QVariantMap as objects.
  • Signals list the payload the QML handler receives.
  • Android marks members that only do something on Android.
  • Where the class has a separate mobile (Q_OS_MOBILE) stub, the info box at the top of the section lists what the stub lacks.

SettingsManager — settingsManager

src/managers/settingsmanager.h — QML context property settingsManager

Central settings store. Persists settingsConfigure.json in the OS config dir (writes are debounced; flushPendingSave() forces them). Settings with a dedicated property follow a triple: a read-only Q_PROPERTY, a <name>Changed signal and a save_<snake_name>() slot. Types and defaults for every key are in the Settings Reference.

OBDManager — obdManager

src/managers/obdmanager.h — QML context property obdManager

OBD-II diagnostics over an ELM327 adapter: USB / Bluetooth serial on desktop (worker thread), BLE GATT on Android. Base parameters have named signals; extended multi-value parameters use obdParameterChanged(QString, float). PID numbers, command names and decoders come from ELM327Protocol::buildPidTable(), which carries all 82 mode-01 commands plus ELM_VOLTAGE; polling is demand-driven: only the PIDs that registered consumers (dashboard, Parameter Cards, Home, editor, settings list) ask for via setParameterDemand() are polled, plus an RPM heartbeat, filtered to what this session's scan found. Changes apply on a live connection without reconnecting (the worker's poll list is swapped via updatePidsToWatch(), on Android via rebuildAndroidPollList()). See OBD Manager → Which PIDs Get Polled.

Mobile / build-variant differences
On Android the same class bypasses the serial worker and talks BLE through OctaveOBDBridge.java (JNI); the QML-facing API is identical. Connect chains the 0100 through 01C0 supported-PID bitmaps so default PIDs above 0x20 (fuel level, module voltage, oil temperature) and the multi-value PIDs are polled, the first poll slot reads the VIN, and the bridge requests BLUETOOTH_CONNECT on the first Connect tap (the former requestAndroidBluetoothPermission() helper is gone).
