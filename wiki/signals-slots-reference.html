How managers reach QML
Every manager is a QObject registered in src/main.cpp (ctx->setContextProperty(...)) and main.py (engine.rootContext().setContextProperty(...)) under the same name, so QML never knows which backend is running: mediaManager.next_track(), settingsManager.themeSetting, obdManager.onRpmChanged. Two scalar context properties exist as well: screenAutoScale (float, short screen edge / 720 clamped to 0.4–3.0) and isAndroid (bool, always false on Python). The qmlRegisterType'd OCTAVE.AndroidAuto.EmbeddedDhuItem and the QML singletons (OBDParameterModel, WidgetCatalog, …) are documented in Components, not here.

Reading this page

  • Properties are Q_PROPERTY (C++) / Property (Python). Almost all are read-only from QML; call the matching save_* / set* slot to change them. Notify signal is what a QML binding or on<Name>Changed handler listens to.
  • Invokables & Slots are Q_INVOKABLE / public slots (C++) and @Slot (Python). Signatures show C++ types; where the Python declaration differs (arity, types, result) the difference is noted inline in grey. QVariantList / QStringList arrive in QML as JS arrays, QVariantMap as objects.
  • Signals list the payload the QML handler receives.
  • C++ only / Python only mark members that exist in only one backend — QML must not call them without a typeof guard. Android marks members that only do something on Android.
  • Where the C++ class has a separate mobile (Q_OS_MOBILE) stub, the info box at the top of the section lists what the stub lacks.

SettingsManager — settingsManager

src/managers/settingsmanager.h / backend/settings_manager.py — QML context property settingsManager

Central settings store. Persists settingsConfigure.json in the OS config dir (writes are debounced; flushPendingSave() forces them). Every setting follows the same triple: a read-only Q_PROPERTY, a <name>Changed signal and a save_<snake_name>() slot. Types and defaults for every key are in the Settings Reference.

Known parity gaps

Differences found between the two backends on desktop (mechanically diffed from the headers and modules on 2026-09-10). None of them is hit by the current QML — every member the frontend references exists in both backends — but they are drift that the parity rule in CLAUDE.md says should be closed.
