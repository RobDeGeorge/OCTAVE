QML Architecture Overview

OCTAVE's frontend is Qt Quick / QML. Most files import QtQuick 2.15; the 3D vehicle files (CarMenu.qml, JeepVehicle.qml, JeepHinge.qml, JeepLamp.qml, JeepLink.qml) use unversioned Qt 6 imports and QtQuick3D. The QML layer handles all visual presentation, animation, and interaction. Business logic lives in backend manager classes — C++ / Qt 6 in src/ (the shipped binary) or the parallel Python / PySide6 backend in backend/ — exposed to QML as context properties. The same frontend/ directory is loaded at runtime by both backends; no QML file knows which one is running.

Key architectural points:

  • Single window — one ApplicationWindow hosts everything, including full-window overlays (Now Playing Studio, shift-light flash). There are no secondary windows or dialogs.
  • StackView navigation — pages are pushed/popped on a StackView; there is no router. Every page except MainMenu is instantiated on demand with Qt.createComponent().
  • Persistent BottomBar — always visible below (horizontal) or to the left of (vertical "side" mode) the StackView. See Bottom Bar.
  • Singletons declared in qmldir — Style, Spacing, EnvironmentTheme, OBDParameterModel, and dashboards/WidgetCatalog are pragma Singleton objects.
  • No page transitions — all six StackView transitions (pushEnter/Exit, popEnter/Exit, replaceEnter/Exit) are null.
  • No global z-order tricks beyond the ones in the diagram: the StackView sits above the BottomBar (z: 1 vs 0), shadows at z: 2, the studio at z: 5, overlays at z: 999999.

Main.qml Structure

frontend/Main.qml is an ApplicationWindow that orchestrates the entire UI. Its top-level declaration:

import QtQuick 2.15
import QtQuick.Controls 2.15
import QtQuick.Layouts 1.15
import Qt.labs.folderlistmodel 2.15
import "." as App

ApplicationWindow {
    id: mainWindow
    visible: true
    title: deviceName
    minimumWidth: 400
    minimumHeight: 300
    font.family: App.Style.fontFamily !== ""
        ? App.Style.fontFamily : systemDefaultFont

    // Desktop: saved size. Android: leave unset so the OS owns sizing
    // (a hardcoded size defeats the display-cutout pillarboxing).
    width: isAndroid ? undefined : screenWidth
    height: isAndroid ? undefined : screenHeight
}

The window captures systemDefaultFont (its own font.family) in Component.onCompleted before any custom font is applied, and also stores it in Style.systemDefaultFont, so Style.fontFamily always resolves to a real family.

Window Management

Window dimensions are persisted bidirectionally on desktop. On resize, onWidthChanged / onHeightChanged write back to the settings manager and recompute Spacing:

onWidthChanged: {
    if (settingsManager && width > 0 && width >= minimumWidth) {
        settingsManager.save_screen_width(width)
        screenWidth = width
        App.Spacing.updateDimensions(width, height)
    }
}

The reverse direction (settings page → window) is a Connections block on settingsManager handling onScreenWidthChanged / onScreenHeightChanged; both are skipped when isAndroid. Window state (fullscreen / maximized / normal) is restored in Component.onCompleted from settingsManager.get_window_state().

Cleanup on Close
The onClosing handler calls mediaManager._save_playback_state() and spotifyManager.cleanup(), then accepts the close. Nothing else is torn down from QML; managers clean up from their backend destructors / aboutToQuit.

Page Routing Mechanism

OCTAVE uses Qt's StackView for page navigation. The only statically instantiated page is the home screen:

StackView {
    id: stackView
    objectName: "stackView"
    z: 1

    // Cached DownloadPage — created once, reused across all navigations
    property var _cachedDownloadPage: null

    anchors {
        left: isVerticalLayout ? bottomBar.right : parent.left
        right: parent.right
        top: parent.top
        bottom: isVerticalLayout ? parent.bottom : bottomBar.top
    }

    initialItem: MainMenu {
        stackView: stackView
        windowWidth: mainWindow.width
        windowHeight: mainWindow.height
    }

    pushEnter: null;  pushExit: null
    popEnter: null;   popExit: null
    replaceEnter: null; replaceExit: null
}

Lazy loading

Every other page is loaded on demand: the caller runs Qt.createComponent("Foo.qml"), checks component.status === Component.Ready, creates the object with stackView as parent and the page's required properties, then pushes it. There is no preloading of pages and no Loader in Main.qml; a page that is popped is destroyed (the StackView owns it). The one exception is DownloadPage, which MediaRoom.openDownloadPage() and MediaPlayer.openDownloadPage() create once with a null parent and cache on stackView._cachedDownloadPage; later calls pop back to it if it is already on the stack, or push the cached instance again. BottomBar navigation to OBD is representative:

var component = Qt.createComponent("OBDHome.qml")
if (component.status === Component.Ready) {
    var page = component.createObject(stackView, {
        stackView: bottomBar.stackView,
        mainWindow: stackView.parent.Window.window
    })
    if (page) stackView.push(page)
}

Pages declare what they need: MediaPlayer, OBDHome, OBDMenu, OBDDiagnostics, SensorHome, SensorMenu and ClockMenu use required property StackView stackView and required property ApplicationWindow mainWindow; CarMenu requires only stackView; SettingsMenu additionally requires string initialSection; MainMenu, MediaRoom, DownloadPage, PhoneMirrorView and AndroidAutoView use plain (optional) properties. A createObject() that omits a required property returns null, which is why every call site checks the result.

Programmatic navigation

navigateTo(pageName) holds a page map used by the Python command server (backend/command_server.py, enabled with python main.py --profile) and the screenshot sweeper:

function navigateTo(pageName) {
    var pageMap = {
        "MainMenu.qml":        { file: "MainMenu.qml",        props: { stackView, windowWidth, windowHeight } },
        "MediaRoom.qml":       { file: "MediaRoom.qml",       props: { stackView } },
        "MediaPlayer.qml":     { file: "MediaPlayer.qml",     props: { stackView, mainWindow } },
        "OBDHome.qml":         { ... }, "OBDMenu.qml": { ... }, "OBDDiagnostics.qml": { ... },
        "SettingsMenu.qml":    { file: "SettingsMenu.qml",    props: { stackView, mainWindow, initialSection: "displaySettings" } },
        "PhoneMirrorView.qml": { ... }, "AndroidAutoView.qml": { ... },
        "SensorHome.qml":      { ... }, "SensorMenu.qml": { ... }, "CarMenu.qml": { ... },
        "DownloadPage.qml":    { file: "DownloadPage.qml",    props: { stackView } },
        "ClockMenu.qml":       { file: "ClockMenu.qml",       props: { stackView, mainWindow } }
    }   // 14 entries
    ...
}

Companion helpers: navigateHome() (stackView.pop(null)), navigateBack() (pops one if depth > 1), and navigateToSettings(section), which exists because SettingsMenu has a required initialSection; if Settings is already the current page it calls currentItem.navigateToCategory(section) instead of stacking a second copy. Pages are also pushed by string path in two places (MainMenu pushes "OBDMenu.qml"; OBDMenu pushes "dashboards/editor/DashboardEditor.qml").

Every entry passes the properties its page requires — ClockMenu.qml, like SensorMenu.qml (fixed in commit 0c29e64), receives both stackView and mainWindow — so a navigateTo() call never fails on a null createObject(). ClockMenu is only reachable this way: tapping the BottomBar clock pushes SensorHome.qml.

StackView anchoring

When the bottom bar is vertical (side mode) the StackView fills from the bar's right edge to the window's right edge; when horizontal, from the top of the window to the bar's top. The BottomBar itself re-anchors in its onIsVerticalChanged handler in Main.qml (width parent.width * 0.1 when vertical; height parent.height * Spacing.bottomBarHeightPercent when horizontal).

IMU Rate Gating from the StackView

The BerryIMU worker samples the I²C sensors at a ~200 Hz target on its own thread and emits seven signals per tick into QML at 60 Hz (EMIT_INTERVAL = 0.016 in both backends). Pushing ~440 queued signals per second into pages that do not display them pegged the QML thread (the comment in OBDParameterModel.qml records 100 % CPU while idle on the Orange Pi), so Main.qml decides from the current page whether the full-rate stream is needed and calls berryIMU.setActive(bool). Sampling and Madgwick fusion continue at full rate; only the emission into QML drops to IDLE_EMIT_INTERVAL = 0.2 (5 Hz) so the settings status stays fresh (commit 94d61be). The rule, in a Connections block on stackView:

function updateSensorConsumers() {
    if (typeof berryIMU === "undefined" || !berryIMU || !stackView.currentItem)
        return
    var n = stackView.currentItem.objectName
    berryIMU.setActive(n === "carMenu" || n === "sensorMenu" || n === "sensorHome"
                       || n === "obdMenu" || (n === "mainMenu" && _homeShowsImuParam()))
}

_homeShowsImuParam() checks settingsManager.get_home_obd_parameters() for any of PITCH, ROLL, HEADING, ALTITUDE, ACCEL_MAG, LATERAL_G, LONGITUDINAL_G, BARO_TEMP — the IMU-fed entries of OBDParameterModel. The handler runs on onCurrentItemChanged and once at completion. The same handler closes the Now Playing Studio if the user navigates while it is open. This is why page objectNames matter: the gating is keyed on them (commits 94d61be, 2fef514).

Import Path and Singletons

Both launchers add frontend/ to the QML import path and load frontend/Main.qml from the filesystem — the QML is not compiled into the C++ binary:

// src/main.cpp — desktop: frontend/ next to the binary or one level up (build/ -> repo root)
engine.addImportPath(frontendDir.absolutePath());
engine.load(QUrl::fromLocalFile(frontendDir.absoluteFilePath("Main.qml")));
// src/main.cpp — Android: frontend/ is bundled as assets
engine.addImportPath(QStringLiteral("assets:/frontend"));
engine.load(QUrl(QStringLiteral("assets:/frontend/Main.qml")));

# main.py
engine.addImportPath(os.path.join(os.path.dirname(os.path.abspath(__file__)), "frontend"))
engine.load(QUrl.fromLocalFile(qml_file))   # in load_main_qml()

CMakeLists.txt sets QT_QML_IMPORT_PATH to the same directory for tooling (qmllint) and, on Android, QT_QML_ROOT_PATH so the frontend is packed into the APK. Because the directory is on the import path, any QML file in it is importable by type name, and frontend/qmldir declares the singletons:

singleton Style 1.0 Style.qml
singleton Spacing 1.0 Spacing.qml
singleton EnvironmentTheme 1.0 EnvironmentTheme.qml
singleton OBDParameterModel 1.0 OBDParameterModel.qml
singleton WidgetCatalog 1.0 dashboards/WidgetCatalog.qml

Files at the top level use import "." as App and reach the singletons as App.Style, App.Spacing, App.EnvironmentTheme, App.OBDParameterModel; settings/ files use import ".." as App, and dashboards/widgets/ use import "../.." as App. Icon paths are built from Style.assetBase (a readonly property url resolved in frontend/) so subdirectory callers never guess ../ depth. EnvironmentTheme now exposes a single fixed active object (the "Standard" look); the earlier Spacecraft / Deep Sea presets were removed and every EnvironmentTheme.active.X flag such as cornerBrackets, terminalScanlines or cardGlassEffect is permanently false.

Qt Quick Controls "Basic" Style

Both backends force the Qt Quick Controls style to Basic before the engine is created — QQuickStyle::setStyle("Basic") in src/main.cpp, os.environ["QT_QUICK_CONTROLS_STYLE"] = "Basic" at the very top of main.py. Both comments give the same reason — "required for full Slider customization" (C++) / "allows Slider customization" (Python): the app replaces the background, handle and contentItem of its sliders, toggles and popups, which platform styles do not allow. Five files also import QtQuick.Controls.Basic explicitly (MainMenu.qml, MediaRoom.qml, BottomBar.qml, AndroidAutoView.qml, PhoneMirrorView.qml) so their customised controls resolve to the Basic implementations regardless of the platform default.

Guarding Backend Differences with typeof

Context properties that exist in one build but not another are referenced through typeof x !== "undefined" so a missing global is a falsy branch rather than a ReferenceError. The pattern also appears as target: (typeof foo !== "undefined" && foo) ? foo : null on Connections blocks. Where it is used today:

  • isAndroid — BottomBar hides the Android Auto and Phone Mirror buttons when isAndroid is true; SettingsMenu.buildHubModel() drops desktopOnly pages (Accessories) on Android.
  • screenAutoScale — Main.qml only applies it if defined.
  • berryIMU — Main.qml's gating, OBDParameterModel's IMU Connections, the Accessories settings page.
  • dashboardManager — OBDMenu builds its registry with the built-in "grid" sentinel alone when the manager is absent; dashboards/editor/DashboardEditor.qml guards its save/load and draft-rescue paths the same way.
  • esp32VolumeManager, gestureSensor, diagnosticsManager, spotifyManager, mediaManager, settingsManager — settings pages, hub widgets, and the two dashboard media widgets.
  • typeof obj.method === "function" — feature probes on items and managers: currentItem.navigateToHub, mainWindow.openNowPlayingStudio, roomLoader.item.previewTrackTransition, and in the OBD settings page obdManager.connect_to_adapter / set_target_address / platform_hint.

Everything else assumes the manager exists, per the parity rule in CLAUDE.md: a QML binding may only reference a symbol both backends expose, unless it is mobile-only.

GUI Scale

All sizes in the UI are derived from two multipliers held in the Spacing singleton:

property real globalScale: 1.0        // user preference (settingsManager.uiScale)
property real autoScaleFactor: 1.0    // screen detection (screenAutoScale)
property real effectiveScale: autoScaleFactor * globalScale
property real baseScale: 0.6 * globalScale   // for percentage-based properties

function dp(size)          { return Math.round(size * effectiveScale) }
function dpMin(size, floor) { return Math.max(floor, Math.round(size * effectiveScale)) }

screenAutoScale is computed by both launchers as the shorter edge of primaryScreen().availableSize() / 720, clamped to [0.4, 3.0], so the factor is orientation-independent (Android reports the natural portrait size even when locked landscape, and main.py uses min(width, height) to match src/main.cpp). Main.qml applies it as Spacing.autoScaleFactor and then sets Spacing.globalScale = settingsManager.uiScale. Percentage-based tokens (overallMargin, overallText, settingsNavWidth, …) are recomputed from applicationWidth/Height whenever Spacing.updateDimensions(w, h) is called.

Why almost every file has its own dp() / dpMin()
Qt on Android loads QML singletons from assets:/ with their functions un-callable (properties still work). So each page and component defines a local function dp(size) { return Math.round(size * (App.Spacing.effectiveScale || 1.0)) } with identical math to Spacing.dp, and Style.assetBase is a property rather than a function for the same reason. The comment block in MediaPlayer.qml documents the bug; the two-line wrapper is copied verbatim into ~40 files.

Dynamic Font Loading

Main.qml scans frontend/assets/fonts with a FolderListModel (filters *.ttf, *.otf, upper-case variants; sorted by name). For each file it creates a FontLoader from an inline Component, derives a display name from the filename (extension stripped, -/_ → space, so JetBrainsMono-Regular.ttf becomes "JetBrainsMono Regular"), and tracks async loads with pendingFontLoads. When the count reaches zero, Style.registerFonts(names, familyMap) publishes the list for the settings font picker and Style.setFont(settingsManager.fontSetting) applies the saved choice. Two fonts ship in the repo: GoogleSans-Regular and JetBrainsMono-Regular.

Album Art Capture Pipeline

When the "Album Art Capture" theme is active, colors extracted from the current album art become the UI palette. Main.qml listens on three sources:

// settingsManager.albumArtColorsChanged — reads the property, not the argument
function onAlbumArtColorsChanged(themeJson) {
    var colors = settingsManager.albumArtColors
    if (colors && colors.length > 0) App.Style.updateAlbumArtTheme(colors)
}
// mediaManager.albumColorsExtracted (local) and spotifyManager.albumColorsExtracted
function onAlbumColorsExtracted(themeJson) { App.Style.updateAlbumArtTheme(themeJson) }
// Duration-based transition speed on both media managers
function onDurationChanged(durationMs) {
    if (settingsManager.songLengthTransition && durationMs > 0)
        App.Style.colorTransitionMs = durationMs
}

At startup, if the saved theme is Album Art Capture and settingsManager.albumArtColors is non-empty, Main.qml primes Style.updateAlbumArtTheme() before setThemeInstant() so the placeholder palette never paints. Manual theme switches are always instant (Style.setThemeInstant); the transition duration only applies to album-art-driven shifts. The comment on the settings handler records why it reads the property instead of the signal argument: signal arguments were observed not to pass reliably through Connections under PySide6.

Shift Light Overlays

Main.qml implements the window-wide part of the RPM shift light (the per-card light on the home screen lives in HomeOBDView):

  1. Load flags — loadShiftLightFlags() parses the rpm_flags generic setting (JSON array). Each flag may carry rpmLow/rpmHigh (or legacy rpm), color, flash, flashSpeed, fullScreenFlash, fullScreenFlashOpacity, auraFlash, auraFlashOpacity, auraSpread. Flags reload whenever settingsManager.genericSettingChanged(key) fires with a key starting rpm_.
  2. Track RPM — obdManager.rpmChanged.connect(...) is made by hand in Component.onCompleted and updates currentRpm.
  3. Find the active flag — findActiveFlag() walks the array from last (highest priority) to first and picks the first whose range contains currentRpm.
  4. Full-screen flash — globalFullScreenFlash is a Rectangle filling mainContainer at z: 999999, enabled: false so input passes through, colored with the flag's color, opacity from the flag's fullScreenFlashOpacity or the global rpm_fullscreen_flash_opacity (default 0.5).
  5. Aura flash — globalAuraFlash paints four edge gradients (top/bottom/left/right) whose depth is auraSpread × the window size (default 0.18) at auraFlashOpacity (default 0.6), shown when the flag has auraFlash === true.
  6. Flash timer — globalFlashTimer runs while the active flag has flash === true, toggling shiftLightFlashVisible every flashSpeed ms; onActiveShiftFlagChanged resets visibility to true.
Why the overlays are children of mainContainer
The comment in Main.qml explains the placement: the overlay is inside mainContainer as the last children so it renders above the StackView and BottomBar without a separate window or Popup, which keeps it working identically on every platform.

Settings Manager Connections

A Connections { target: settingsManager } block keeps the window in sync with settings changed elsewhere:

  • onThemeSettingChanged — Style.setThemeInstant(newTheme); if the new theme is Album Art Capture and a local file is playing, mediaManager.extract_colors_from_album_art(currentFile).
  • onFontSettingChanged — Style.setFont(...).
  • onSongLengthTransitionChanged — when the feature is turned off, restore Style.colorTransitionMs = settingsManager.colorTransitionMs.
  • onBottomBarOrientationChanged — updates isVerticalLayout and bottomBar.isVertical, re-asserts stackView.z = 1; bottomBar.z = 0, and if the current page is Settings, restarts navReloadTimer (150 ms), which stackView.replace()s the Settings page with a fresh instance on the same section (pendingSection).
  • onScreenWidthChanged / onScreenHeightChanged — resize the window (desktop only).
  • onAlbumArtColorsChanged — see above.

Custom themes are hot-reloaded from a hand-made settingsManager.customThemesChanged.connect(...): the whole Style.customThemes object is rebuilt and assigned in one shot (assigning an empty object first would briefly make the active custom theme fall back to SolarizedLight), then Style.customThemesUpdated() is emitted so pickers refresh. Main.qml also exposes updateDeviceName(), updateTheme(), updateFont(), updateStartupVolume() and updateScreenDimensions() for pages that want to write through the window.

Drop Shadows

The separation between the StackView and the BottomBar is a 12-px gradient strip, not a DropShadow effect — one Rectangle per orientation at z: 2:

Graphical Effects: Qt5Compat vs MultiEffect

Two effect modules coexist:

  • Qt5Compat.GraphicalEffects supplies DropShadow, OpacityMask and ColorOverlay. It is imported by AlbumArtCarousel, CoverflowCard, ThemedIcon, MainMenu, MediaRoom, MediaPlayer, DownloadPage, OBDMenu, BottomBar and several settings components. DropShadow appears in MediaRoom.qml (6), OBDMenu.qml (6), settings/AccessoriesSettingsPage.qml (6), BottomBar.qml (2), settings/SettingsChips.qml (2), and once each in CoverflowCard.qml, MainMenu.qml, settings/SettingsToggle.qml, settings/MediaSettingsPage.qml — 26 in total. The album-art shadow is the only one gated by a user setting (showAlbumArtShadow → CoverflowCard.showShadow), and it is rendered as a layer.effect whose layer.live is switched off while any carousel animation runs. MediaPlayer.qml and ThemedIcon.qml deliberately avoid the effect: the song rows fake depth with an 8 % opacity Rectangle ("using Rectangle instead of effects"), and the icon shadow is a second offset ColorOverlay, "not a blur, so there is no per-frame cost".
  • QtQuick.Effects (MultiEffect) is used for the two blurred album-art backgrounds, in MainMenu.qml and MediaRoom.qml, with blurMax: 64 and blur: min(1, settingsManager.backgroundBlurRadius / 64).
Why blur moved to MultiEffect (commit 3058922)
GaussianBlur is implemented as a .qml file inside Qt5Compat.GraphicalEffects; androiddeployqt only bundles the C++ plugin of that module, so the QML-only type failed with "Type unavailable" and crashed the Android build at startup. The commit message states that C++-implemented types (DropShadow, Glow, OpacityMask) were unaffected, so only the two blur sites were ported to MultiEffect, a native Qt 6 module that deploys reliably. CI installs the qt5compat and qtshadertools modules for the same reason (commits 4cace0c, a89b4ef).

Shaders

There is one custom shader. frontend/shaders/dissolve_squares.frag is a GLSL 4.40 fragment shader used by AlbumArtCarousel's "Dissolve" transition: it hashes each cell of a gridSize×gridSize grid over the texture coordinates to a pseudo-random threshold and reveals the new art with smoothstep(r - smoothness, r + smoothness, progress), so squares pop in at random as progress runs 0→1. The uniform block carries qt_Matrix, qt_Opacity, progress, gridSize, smoothness; the sampler is the hidden Image holding the incoming art. One ShaderEffect with a single draw call replaced an earlier 400-item grid of Rectangles.

Qt 6's RHI does not compile GLSL at runtime; ShaderEffect.fragmentShader must point at a pre-compiled .qsb bundle. The committed dissolve_squares.frag.qsb contains six variants — SPIR-V 1.0, GLSL ES 100, GLSL 120, GLSL 150, HLSL 5.0 and MSL 1.2 (checked with qsb -d) — which is what the standard invocation produces:

qsb --glsl "100 es,120,150" --hlsl 50 --msl 12 \
    -o frontend/shaders/dissolve_squares.frag.qsb frontend/shaders/dissolve_squares.frag

qsb ships with the Qt Shader Tools module (qtshadertools). Regenerate the bundle whenever the .frag changes and commit both files; there is no build step that does it.

How the bundle is located differs by platform, in AlbumArtCarousel.qml:

fragmentShader: Qt.platform.os === "android"
    ? "qrc:/shaders/dissolve_squares.frag.qsb"
    : "shaders/dissolve_squares.frag.qsb"

On desktop (both backends) the path resolves relative to the QML file on disk. On Android the QML is served from assets:/, which the RHI ShaderEffect rejects (only qrc:/ or local files), so CMakeLists.txt compiles the .qsb into the executable with qt_add_resources(octave "shaders" PREFIX "/shaders" ...). frontend/shaders/shaders.qrc lists the same file for tooling; Python never touches it.

objectName Conventions for Dev Scripting

Keyboard Handling

Main.qml installs no Keys handlers and no Shortcuts; the head unit is touch-first. Keyboard input reaches only focused text fields (search box and playlist-name fields in DownloadPage and MediaPlayer, which call forceActiveFocus() when opened) and Popups with closePolicy: Popup.CloseOnEscape | Popup.CloseOnPressOutside (the album-art popup in MediaRoom; the playlist dropdown, song/playlist action menus and new-playlist dialog in MediaPlayer; the playlist dropdown, error and new-playlist popups in DownloadPage; the dashboard chooser, primitives gallery and RPM settings popups in OBDMenu; the volume popups in BottomBar; SettingsChips and the OBD settings adapter popup), so Escape closes them. DownloadPage also draws its own on-screen keyboard (onScreenKeyboard Rectangle, toggled by showKeyboard) for touch-only installs. Developer keyboard controls (simulated OBD, etc.) live in the gitignored dev/ tree (python -m dev.main_dev), not in frontend/.

Initialization Sequence

Component.onCompleted in Main.qml runs, in order:

  1. Capture system font — systemDefaultFont = font.family, mirrored to Style.systemDefaultFont.
  2. Load custom themes — every name in settingsManager.customThemes is fetched with get_custom_theme() and added via Style.addCustomTheme(); this must precede setTheme so a saved custom theme resolves.
  3. Prime album-art palette if the saved theme is Album Art Capture, then apply the theme with Style.setThemeInstant().
  4. Load dimensions — width/height from settings (skipped on Android).
  5. Initialize Spacing — Spacing.updateDimensions(width, height), then autoScaleFactor = screenAutoScale, then globalScale = settingsManager.uiScale.
  6. Color transition speed — Style.colorTransitionMs = settingsManager.colorTransitionMs.
  7. Connect media manager — mediaManager.connect_settings_manager(settingsManager).
  8. Orientation — isVerticalLayout from bottomBarOrientation.
  9. Restore window state — fullscreen / maximized.
  10. Custom-theme hot reload — connect customThemesChanged.
  11. Shift light — loadShiftLightFlags(), then connect obdManager.rpmChanged by hand.

Fonts load independently, driven by the FolderListModel's onStatusChanged / onCountChanged; the IMU gating handler runs from its own Component.onCompleted.

Signal connections made by hand
obdManager.rpmChanged and settingsManager.customThemesChanged are connected with .connect() in JavaScript rather than through Connections blocks. The comments cite reliability of PySide6 signal delivery; the pattern predates the C++ backend and works with both.

Design Decisions

The reasons below are taken from code comments, commit messages and CLAUDE.md, not inferred.

One Main.qml, one StackView, pages created on demand

A single window with a StackView keeps the persistent BottomBar, the shift-light overlays and the Now Playing Studio in one scene graph, so overlays render above every page without secondary windows (the placement comment on globalFullScreenFlash calls this out as the cross-platform requirement). Pages are instantiated with Qt.createComponent() only when navigated to, so an install without the optional QtQuick3D module still boots — SensorHome probes CarMenu.qml once and greys its card out rather than the app failing at load (CMake comment, commit 0c29e64). All six StackView transitions are null ("Disable transitions for better performance"). The DownloadPage is the one cached page ("created once, reused across all navigations"): its search results and download queue are page state, so it is parked on the StackView and re-entered with a refreshed playlist list rather than rebuilt.

Context properties, not a QML module of registered types

Managers are plain QObjects registered by name in both launchers so the identical frontend/ tree runs against C++ or Python; QML never imports a backend module. The parity rule in CLAUDE.md makes the context-property name part of the contract (same class name, same slots/signals/properties in both backends). Registration happens before engine.load() because bindings evaluate on first load (the dashboardManager comment in both launchers). The only registered type is EmbeddedDhuItem in the OCTAVE.AndroidAuto 1.0 module, because the DHU window has to be reparented into a real scene item; everything else is a context property.

"Basic" controls style

Set in both launchers with the same comment: Basic allows full Slider customisation. Platform styles (Fusion, Material, native) reserve parts of their delegates; Basic lets every background / handle / contentItem be replaced, which the themed sliders, toggles and popups depend on.

Explicit image decoding and warm caches

The media views control decoding rather than leaving it to the scene graph: MediaRoom pre-decodes prev/next album art in hidden 1×1 Images with cache: true on the next event-loop tick after a track change, using one batched get_neighbor_album_arts() call that the comment says "halves PySide6 bridge crossings" and keeps backend calls off the animation frame; CoverflowCard decodes at 2 × artSize and turns off smooth while animating; ThemedIcon supersamples SVGs at 2× "so edges stay crisp when the tile scales up"; MediaPlayer's list uses plain Images with sourceSize 1.5× inside a ListView with reuseItems. Heavy work such as FFT analysis is deferred until the carousel's settled signal so it never competes with animation frames.

Quick3D for the car view

The vehicle-attitude view needs a real 3D scene: IMU orientation arrives as a quaternion and is applied directly to a Node (no gimbal lock), the rigged Jeep has hinged doors, hood, tailgate, steering linkage and spinning wheels, and reflections come from an HDR light probe. QtQuick3D provides that with GLB loading through RuntimeLoader. It is deliberately optional: CMake links it when found, CI packages the assetimporters plugin so the glb parser ships, and the QML degrades (greyed card, "Requires the QtQuick3D module") when it is absent. See CarMenu and the Jeep rig.

objectName everywhere a script might look

OCTAVE is daily-driven in a vehicle, so verification is done against the real running app: the command server locates items by objectName, clicks them and grabs the window, and the README/wiki screenshots are produced that way. Naming the page roots also gives the BottomBar and the IMU gating a stable key that does not depend on object identity or file URLs.

Local dp() wrappers and property-only singletons

An Android bug makes singleton functions un-callable when QML is served from assets:/. Rather than fork the QML for mobile, every file carries a two-line local dp(), and anything a singleton must offer to Android is a property (Spacing.effectiveScale, Style.assetBase).

typeof guards only where a backend legitimately differs

Because both backends must expose the same API on desktop, QML checks for a manager's existence only for genuinely optional or mobile-absent globals (isAndroid, hardware managers, dashboardManager, diagnosticsManager); everything else binds directly, so a missing symbol surfaces as a loud error during the parity build instead of silently disabling a feature.
