What the Frontend Is

Everything you see and touch in OCTAVE is written in QML, Qt's language for describing screens. The QML lives in the frontend/ folder. It draws and it reacts to touches; it does not play music, talk to the car or save settings. Those jobs belong to the C++ managers in src/, and the QML asks them by name.

The same frontend/ folder runs on every platform: a dash screen, a desktop window, an Android phone and the browser demo. Nothing in it is compiled, so on a computer you can edit a .qml file and restart the app to see the change.

This page is the map. It starts with what is on the screen and gets more technical as it goes. Each part has its own page for the detail: Pages, Components, Bottom Bar, Theme System, Settings UI and Gauges & Dashboards.

What the Screen Is Made Of

There is one window. It holds three things:

  +--------------------------------------------------------------+
  |                                                              |
  |   the page on top of the stack                               |
  |   (Home, Media, OBD, Sensors, Settings, ...)                 |
  |                                                              |
  |                                                              |
  +--------------------------------------------------------------+
  |   bottom bar:  section buttons | music keys | volume | clock |
  +--------------------------------------------------------------+

   drawn over both: the shift light, the error notice
  • A stack of pages. One page is on top and fills the area above the bar. Home is always at the bottom of the stack. Opening a section puts its page on top; going Home takes the others off.
  • The bottom bar. It is always there: a button for each section, the music keys, the volume and the clock. It can also stand on the left side of the screen (Settings > Display); the pages then fill the area to its right. See Bottom Bar.
  • Overlays. A few things are drawn over both: the shift light's flash and a short error notice. See Things Drawn Over Every Page.

Popups and dialogs open inside the same window. Home itself is one of several things, picked in Settings > Display > Home Screen: a dashboard written as a JSON file, a hand-built screen from frontend/home/, or the classic three panels. See Pages and Gauges & Dashboards.

Moving Around

There are three ways to get from one page to another.

  • Tap a section button on the bottom bar: Home, OBD, Media, Sensors, Settings, and Android Auto when it is turned on in Settings > Phone. The page changes at once, with no animation. OBD and Sensors reopen the page you last used in that section, and a tap while inside the section goes to its hub. Tapping the clock opens the Clock page. The rules for each button are on the Bottom Bar page.
  • Swipe sideways on a page. A quick swipe opens the section whose button is next on the bar: finger to the left opens the one to the right. The new page slides in over the old one. Nothing happens at the first or last button, or on a page no button owns (the Clock page).
  • Tap a card on a page. OBD Home and Sensor Home are hubs: their cards open the pages inside that section.

A swipe counts only if it is quick (under 0.7 seconds), covers at least 18 % of the page's width, and goes at least twice as far sideways as up or down. A swipe that starts on something that drags sideways itself is left to that thing: a slider, a list that scrolls sideways, the mirrored phone's screen, the 3D vehicle.

One page opens by itself: when an iPhone starts mirroring over AirPlay, its picture comes up on screen.

How a Page Gets Its Data

From here on the page is for people writing or changing QML.

Each manager is a C++ object given to QML under a fixed name, such as mediaManager or obdManager. Qt calls such a name a context property: it is visible in every QML file with no import. A page does three things with a manager:

  • Reads a property. Bind to it and the screen follows it: when the manager changes the value, everything bound to it redraws.
  • Calls a method when the user does something.
  • Listens for a signal when something happens that is not a value, such as a lost connection.
import QtQuick 2.15
import "." as App

Item {
    id: myPage

    // A property: the text changes when the song does
    Text {
        text: nowPlaying.title
        color: App.Style.primaryTextColor
    }

    // A method: skip to the next song on tap
    MouseArea {
        anchors.fill: parent
        onClicked: nowPlaying.next()
    }

    // A signal: the car dropped off
    Connections {
        target: obdManager
        function onConnectionLostUnexpectedly(reason) { /* tell the driver */ }
    }
}

Every manager is made in one place, src/appcore.cpp, where a line such as expose("mediaManager", &mediaManager) gives it its name. src/main.cpp hands them all to QML before it loads Main.qml. The same names are what other programs see over the service API, so the QML uses nothing a second frontend could not.

Readings from the car and the sensors

A page never reads a gauge value from obdManager. It asks OBDParameterModel, a QML object that is the same everywhere, by the reading's id: 

Text {
    readonly property real rpm: App.OBDParameterModel.sample("RPM")   // NaN until there is a reading
    text: isFinite(rpm) ? Math.round(rpm) : "--"
}

The car is only asked for readings some page has said it shows. A page says so with obdManager.setParameterDemand("myPage", ["RPM", "SPEED"]) while it is visible, and takes the request back with an empty list when it is hidden. See Which Readings Get Polled for the rules and Gauges & Dashboards for OBDParameterModel.

The motion sensor works the same way. It sends its values to the screen 60 times a second while some page wants them and 5 times a second otherwise. A page that shows pitch, roll, heading or g-force puts one line in its root: 

App.ImuDemand { consumer: "sensorMenu"; wanted: sensorMenu.visible }

Singletons

A singleton is a QML object that exists once and is shared by every file. frontend/qmldir lists six. A file reaches them through import "." as App (or ".." from a subfolder):

SingletonWhat it holds
App.StyleColours and fonts of the theme in force. Never write a colour into a page; take it from here. See Theme System.
App.SpacingSizes, the scale, and whether the window is upright. See Sizes and Scaling.
App.EnvironmentThemeFixed style values that do not change with the theme.
App.OBDParameterModelReadings and what is known about each.
App.WidgetCatalogWhich QML file draws each dashboard widget.
App.MusicDevicePreferenceWhich 3D music device the Media Room shows.

When a name may be missing

Using a name that does not exist is an error that stops the binding it is in. Much of the code therefore checks a name before using it: 

target: (typeof airPlayManager !== "undefined" && airPlayManager) ? airPlayManager : null

The names the developer tools add (perfMonitor, devMode) exist only when those tools are on, so always check them. For the managers, do what the file you are in does.

On a computer the app reads the folder from disk, next to the program or one level up. On Android and in the browser the whole folder is packed into the app, so keep large unused files out of it.

Sizes and Scaling

OCTAVE runs on a 1280×800 dash screen, a 4K monitor and a phone. A size written in plain pixels would be right on one of them. So a size is written as if the screen were 720 pixels on its short side and passed through dp(): 

width: dp(240)              // 240 px on a 720p screen, 360 on 1080p
border.width: dpMin(3, 1)    // scaled, but never under 1 px
font.pixelSize: dp(18)

dp(size) multiplies by Spacing.effectiveScale and rounds. That scale is two numbers multiplied:

NumberWhere it comes from
Spacing.autoScaleFactorThe screen: its shorter side divided by 720, kept between 0.4 and 3. Worked out once at startup (screenAutoScale). It follows the screen, not the window, so making a desktop window smaller does not shrink the text.
Spacing.globalScaleThe user: the UI Scale slider in Settings > Display (uiScale).

How to write a size:

  • A fixed size (a button, a margin, a font): dp().
  • A share of the room (a panel that takes 40 % of the page): a fraction of width or height, or anchors. Do not put a fraction through dp().
  • A thin line: dpMin(size, 1), so it never rounds to nothing.
  • A shared size (row heights, page margins): a token from App.Spacing, so pages agree. See Theme System.

Most pages and components define dp() and dpMin() themselves, as two lines at the top that read App.Spacing.effectiveScale; the gauges and Main.qml call App.Spacing.dp(). The result is the same. Do what the file you are in does, and copy the two lines into a new page.

The hand-built Home screens use a different unit: u, 1 % of the screen's short side, so a screen keeps its proportions at any size.

Upright screens

The app is designed for a wide screen, but a phone is held upright. App.Spacing.isPortrait is true when the window is taller than wide. A page built as side-by-side panels reads it and stacks them instead; Home, the Media Room, the Media Player, the Settings grid, Trouble Codes and the Sensors page all do. A wide layout must look exactly as it did before you added the upright one.

The window's size

On a computer the window opens at the size it had last time, and whether it was full-screen or maximized. Resizing it is what saves the size. It cannot be made smaller than 320×300. On Android the system owns the window, and nothing is saved or restored.

How Pages Are Built and Kept

Building a page is slow: the big ones are two or three thousand lines of QML, and on a small computer that is a visible pause. So a page is built once and kept for as long as the app runs. Showing it again costs one frame.

The stack in Main.qml has the functions for this. Always go through them:

To do thisUse
Show a pagestackView.openPage("OBDMenu.qml"). It builds the page the first time, and afterwards shows the one it kept. If the page is already somewhere in the stack it goes back to it; it never makes a second copy. It returns the page, or null if the file would not load.
Pass a value to a page as it is builtstackView.openPage("SettingsMenu.qml", { initialSection: "obdSettings" }). The values apply only the first time, when the page is made.
Open Settings on a sectionmainWindow.navigateToSettings(section, tile). It works whether or not Settings is already open.
Have a page built ahead of timemainWindow.prewarmPageSoon("CarMenu.qml"), from the page that leads to it.

Every page is handed stackView and mainWindow when it is built, so it can open other pages itself.

Pre-building

After startup, the pages behind the section buttons are built in the background, so even the first tap is quick:

  1. Wait for startup to finish. Pre-building starts when the window has gone quiet, or after 30 seconds at the latest.
  2. Build one page at a time, in small slices between frames: the media page you use, the last Sensors and OBD pages, Settings, the other media page. Pages with a 3D scene go last.
  3. Draw it once, off screen, so the textures and fonts it needs are loaded before you see it.
  4. Rest for twice as long as that page took (between 0.15 and 4 seconds), then take the next. A slow machine therefore spreads the work out. A finger on the screen makes it wait.

A tap that arrives before a page is ready finishes that page at once. A page with a 3D scene asked for with prewarmPageSoon() is pre-built only when a graphics chip is drawing the window (mainWindow.gpuRendered): drawn in software, the 3D vehicle page takes many seconds, so there it is built when you open it. The log shows each step as a [NAV] line.

Adding a Page

  1. Make the file at the top of frontend/, such as MyPage.qml, with an Item as its root and import "." as App.
  2. Give the root an objectName: the file name starting in lower case (myPage). A name that starts with obd or sensor puts the page in that section: its button lights up, and swiping works from it. See Names the Tools Rely On.
  3. Declare stackView and mainWindow as properties. Both are filled in for you.
  4. Open it from a card or button with stackView.openPage("MyPage.qml"). Inside the OBD or Sensors section, use the hub's pushSubpage(), which also remembers it as the last page used.
  5. Take sizes from dp() and colours from App.Style. Check the page upright if it has side-by-side panels.
  6. Ask for data only while visible: setParameterDemand for car readings, ImuDemand for the motion sensor.
  7. Put work that belongs to each visit in StackView.onActivated, not in Component.onCompleted. The page is built once; it is shown many times.
  8. Add it to the list in navigateTo() in Main.qml, so the developer tools and the screenshot scripts can open it.
  9. Check it: run the tests (ctest), and lint the file with the Qt version the releases use (6.7). A newer Qt accepts things 6.7 does not. See Development.
  10. Describe it on the Pages page.

A new settings page, a new gauge and a new hand-built Home screen each have their own, shorter recipe: see Settings UI and Gauges & Dashboards. A page should use only what the managers publish: the test tst_conformance fails when QML uses a manager's member that the API reference does not list.

Performance Rules

The head unit in a car is a small computer, such as a Raspberry Pi or an Orange Pi. These rules keep the screen smooth and the processor idle on one.

  • A hidden page is still alive. Pages are kept, so a timer or an animation that runs "always" runs for the whole drive. Tie every repeating Timer and animation to the page's visible. Calling restart() ignores that tie, so check visible before it too.
  • Ask only for the data you show. Every reading asked for slows the others down, and the motion sensor at full rate sends its values 60 times a second. Give the request back when the page is hidden.
  • A pre-built page is visible for a moment, off screen, before anyone opens it. Code that runs when visible changes will run then. Code in StackView.onActivated will not: that is where to start a stream, reload a list or scroll to the current song.
  • Bind to one value, not to a whole object. OBDParameterModel.liveValue("RPM") redraws when RPM changes. A binding that reads a list of every reading redraws on all of them.
  • Blur and shadows cost every frame they are redrawn. Use them on a few large things, not on each row of a list. The song list draws its depth with a plain Rectangle for this reason. When a shadowed item animates, freeze its layer for the length of the animation.
  • Never write layer.live: in a declaration. Set it with Binding { target: item.layer; property: "live"; value: ... }. On Qt 6.7 the declared form sometimes fails to compile, depending on which file was loaded first, and the page then cannot load until the app restarts.
  • Give every picture a sourceSize close to the size it is shown at, so a large cover is not decoded at full size for a small tile. Long lists use reuseItems: true.
  • 3D is optional and heavy. A page with a 3D scene must still load when the 3D module is missing (hasQuick3D), and must not be built before it is wanted on a machine without a graphics chip.

To measure a page instead of guessing, run with --profile and use the performance tools on the Development page.

Things Drawn Over Every Page

Main.qml draws a few things above the pages and the bar, so they work wherever you are.

WhatWhen it shows
Shift light: full-screen flashThe whole window is tinted in the active flag's colour.
Shift light: auraA glow in from the four edges, leaving the middle readable.
Error notice (ErrorToast.qml)A short message: the car's connection was lost while you were not on an OBD page, or a Spotify control did not work.

Touches pass straight through both shift light overlays. They hold no rules of their own: which flag is active, its colour and when it blinks all come from shiftLightManager, so every lamp in the app blinks in step. The flags and how to set them are under Shift Light.

Main.qml also applies the theme and the font when they change in Settings, and passes album-art colours on to Style. How themes work is on the Theme System page.

Names the Tools Rely On

An objectName is a label on a QML item that code outside it can look up. OCTAVE uses them for two things.

  • The bottom bar reads the name of the page on top to know which section you are in: mainMenu is Home; a name starting with obd is OBD; mediaRoom and mediaPlayer are Media; a name starting with sensor, and carMenu, are Sensors; settingsMenu is Settings. Rename a page's root and its button stops lighting up.
  • The developer tools find items by name to click them, read them and take screenshots (--profile; see Development). stackView is the stack, and root stands for the window.

The convention: a page's root is named after its file, starting in lower case (obdMenu, sensorHome, phoneMirrorView). Trip History is obdTripHistory, so that it counts as an OBD page. The Clock page has no name and belongs to no section. Give a name to any control a script should be able to press.

To keep the page swipe off an item that drags sideways in a way the swipe cannot detect, give the item readonly property bool octaveNoPageSwipe: true. Sliders, sideways lists and a MouseArea with preventStealing are detected without it.

When Something Goes Wrong

  1. A tap on a button does nothing. Look in the log for [NAV] Failed to load followed by the file name and the QML error. A page that does not compile is reported there and the app carries on. Architecture says where the logs are.
  2. "ReferenceError: x is not defined". The page used a manager's name where it does not exist. See When a name may be missing.
  3. Everything is too big or too small. Check the UI Scale slider, then that sizes go through dp().
  4. It works here but not in a release. Releases use Qt 6.7; lint the file with that version.
  5. The processor is busy while nothing moves. Something on a hidden page is still running. See Performance Rules.

Why It Is Built This Way

  • One window, one stack. The bar and the overlays are in the same scene as the pages, so the shift light can flash over anything without a second window, and it behaves the same on every platform.
  • Pages are kept, not rebuilt. Building a page on every tap was the pause between pressing a button and seeing the page. Keeping one copy of each also means no hidden second copies are left running.
  • Pages are loaded by file name, when first wanted. A page that cannot load, because an optional part such as the 3D module is missing, fails by itself and the rest of the app starts.
  • A tap cuts, a swipe slides. A tap should feel instant. A swipe is a movement, so the page follows the finger's direction.
  • Managers by name, not as QML types. The name and what is behind it are the whole contract between the screen and the rest. Other frontends get the same contract over the service API.
  • Rules live in C++, drawing in QML. Where a rule would otherwise be repeated in several pages (the shift light, the volume curve, which source has the music), a manager decides and the pages only show the result.
  • The "Basic" controls style everywhere. It is the one style that lets every part of a slider, toggle or popup be replaced, which the themed controls need.
