Quick Start

Every shipped binary (Windows .exe, macOS .dmg, Linux x86_64 and aarch64 AppImages, Android .apk) is built from the C++ / Qt 6 tree in src/ with CMake. There is no PyInstaller pipeline, no .deb, no Flatpak and no Buildozer — the Python backend is never packaged (see below).

# Configure + build (Debug, current platform)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j

# Run
./build/octave            # Linux/macOS (QML loads from the checkout's frontend/)
./build/octave --debug    # the only C++ command-line flag: DEBUG-level logging + octave-cpp-debug.log
./build/Debug/octave.exe  # Windows MSVC multi-config

# App store build (downloads feature stripped out)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DOCTAVE_ENABLE_DOWNLOADS=OFF
cmake --build build -j
Requirements (all desktops)
CMake 3.21+ (cmake_minimum_required in CMakeLists.txt), Qt 6.7.3 (the CI-pinned version; other 6.7.x / 6.8.x will likely work but are untested), a C++17 compiler (GCC 11+ / Clang 14+ / MSVC 2022), TagLib (required on every desktop platform — find_package(taglib CONFIG) from vcpkg on Windows, pkg-config taglib elsewhere; Android skips it and uses Qt's metadata fallback), and Ninja recommended on Linux/macOS (cmake -G Ninja). FFmpeg (libavcodec/libavutil) and Qt Quick 3D are optional — see CMake Options. Full per-platform package lists live in BUILD.md.

Design Decisions

The build and release pipeline has been rewritten several times. The reasons behind its current shape are recorded here so they are not re-litigated by accident. Sources: CLAUDE.md, comments in CMakeLists.txt and .github/workflows/build.yml, and the commit messages named below.

Why C++ is the only shipped binary

Commit 8211ba8 ("ci: drop Python build jobs — C++ is the only shipped binary") removed the PyInstaller build-windows / build-macos / build-linux jobs. Every release artifact on every platform now comes from src/, which gives one packaging story (CMake + Qt's own deploy tools), native performance on the Orange Pi / Raspberry Pi head unit, and a mobile path — the Android APK is a Qt-for-Android build; there is no Python-on-Android and the buildozer / python-for-android files must not be reintroduced (CLAUDE.md). The release job in the workflow carries the same note: "The Python tree is a developer/tinkerer backend ... only C++ ships."

Why the Python backend stays

CLAUDE.md is explicit that the two backends are deliberate, not a half-finished migration: Python stays for "tinkering, accessibility, rapid prototyping, and hardware hacking on Raspberry Pi / single-board setups where a Python REPL is invaluable". The README makes the same argument ("On a Pi with a new sensor on the I²C bus, a Python REPL beats a compile cycle"). The cost is the parity rule — every desktop feature lands in both trees in the same change set — and CI keeps the Python side honest with lint and test on every push even though nothing Python is packaged. The original Python→C++ migration plan (.claude/plans/wondrous-toasting-biscuit.md) is superseded.

Why AppImage rather than .deb on Linux

v0.9 briefly shipped a .deb (commit fdb7d94). It "installed cleanly but launched a window-less process": the package staged the QML tree at usr/share/octave/frontend/, which the binary's applicationDirPath()/../frontend lookup in src/main.cpp never finds. Commit 14811c5 replaced the .deb job with packaging/linux/build-appimage.sh, whose AppDir layout mirrors the runtime lookup exactly (usr/bin/octave + usr/frontend/), and b9ca3be switched the docs. An AppImage also carries the pinned Qt 6.7.3 with it — distro Qt 6.2 on Ubuntu 22.04 cannot run the frontend at all (see CMake Options) — and the same script produces the aarch64 image for the Orange Pi with no packaging-format work per distro. Flatpak and app-store variants remain deferred (TODO/ci-multiplatform-builds.md).

Why the Linux artifact matters more than the others

The vehicle head unit is an Orange Pi 5 Plus (aarch64). The cpp-build-linux-arm64 job exists specifically so that board gets a first-class binary built against the same Qt 6.7.3 as every other target (workflow comment: "the actual vehicle hardware"). It needed two extra decisions: Google publishes no aarch64 adb, so that build relies on the distro's adb on PATH, and the arm64 Qt package's GStreamer media plugin depends on libgstphotography, which jammy does not ship — OCTAVE uses Qt's FFmpeg media backend anyway, so the plugin is deleted after the CMake configure and before linuxdeploy-plugin-qt walks plugins/ (OCTAVE_DROP_QT_PLUGINS, commits 39dd25b and 10a6afa; it must be after configure because Qt's CMake config refuses to configure when a listed plugin file is missing).

Why the phone-server jar is committed

phone_server/ is OCTAVE's fork of the scrcpy server (Apache-2.0, forked at v3.3.4, package org.octave.phoneserver). Building it needs a JDK plus Android platforms;android-36 and build-tools;36.0.0 — a toolchain no desktop CI runner or Windows/macOS developer otherwise has. Committing the prebuilt tools/phone-server/octave-phone-server lets CMakeLists.txt embed it as a Qt resource (qrc:/phone-server/, "written to a temp file at runtime, so no packaging target has to carry it as a loose file"), and lets the Python backend push the identical bytes. The phone-server CI job rebuilds from source on every push to prove the jar is not stale: it fails if either jar lacks the org.octave.phoneserver.Server class or the 3.3.4-octave version string, and only warns on a hash mismatch, because javac/d8 output differs between toolchain versions (commit 2a971ff: the first strict byte comparison failed when CI built with JDK 17 against a JDK 21 jar — hence the job pins JDK 21).

Why adb is bundled but not scrcpy

Commit 7a8c8b8 removed every external phone-mirror path (scrcpy binary, v4l2loopback, window grab, about 3,000 lines). OCTAVE speaks the scrcpy protocol itself, so the only third-party pieces are the phone server above and adb. scripts/fetch_platform_tools.py downloads Google's pinned platform-tools (37.0.1, SHA-256 verified) and keeps only the files adb needs plus Google's NOTICE.txt; CI ships that directory next to the executable so users install nothing.

Why one artifact naming scheme

Commit d7812ff unified four conventions into OCTAVE-<version>-<platform>[-<arch>].<ext> with the leading v stripped from the tag. The Inno Setup OutputBaseFilename, the macdeployqt rename step, the AppImage script and the APK staging copy all follow it, and the workflow's artifact globs and release file list depend on it.

Why macOS builds on macos-14

The macOS 15 SDK on macos-latest drops the AGL framework that Qt 6.7.3's OpenGL support still links (ld: framework 'AGL' not found). The job is pinned to macos-14 / Xcode 15 until Qt is bumped to 6.8+ (commit f559afc).

Why Qt 6.7.3 specifically

Qt 6.8+ moved behind a login-gated download channel; 6.7.3 is the newest release available through aqtinstall's public mirror path, which is what both CI (jurplel/install-qt-action@v4) and the documented local setup use (BUILD.md). Every job pins version: '6.7.3'.

CMake Options & Layout

CMakeLists.txt declares project(OCTAVE VERSION 0.9.0); the version is compiled in as OCTAVE_VERSION. Every source file is listed explicitly in the qt_add_executable(octave ...) call — a new manager means two new lines there.

Resources vs. filesystem

Only two things are compiled into the binary as Qt resources: the .qsb shader frontend/shaders/dissolve_squares.frag.qsb (qrc:/shaders/ — Qt RHI's ShaderEffect rejects assets:/ URIs on Android, so QML branches on Qt.platform.os) and the phone-server jar with its LICENSE / NOTICE (qrc:/phone-server/). Everything else in frontend/ is loaded from the filesystem at runtime so the tree stays shared with the Python backend. src/main.cpp resolves it as applicationDirPath()/frontend, then applicationDirPath()/../frontend (the build/ case), and on Android as assets:/frontend; every packaging layout must preserve that relationship.

Windows Build

Windows

Requirements

  • Visual Studio 2022 with the "Desktop development with C++" workload
  • Qt 6.7.3 (msvc2019_64 or msvc2022_64) via the Qt online installer; CI uses win64_msvc2019_64 with modules qtmultimedia qtnetworkauth qtserialport qtconnectivity qtquick3d qt5compat qtshadertools qtquicktimeline (qtquicktimeline because windeployqt fails on QtQuick3D without it)
  • vcpkg for taglib:x64-windows and ffmpeg[core,avcodec]:x64-windows
  • (CI only) Inno Setup 6 — pre-installed on windows-latest as ISCC.exe
cmake -S . -B build `
  -DCMAKE_TOOLCHAIN_FILE="$env:VCPKG_INSTALLATION_ROOT/scripts/buildsystems/vcpkg.cmake" `
  -DVCPKG_TARGET_TRIPLET=x64-windows `
  -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j

Output and CI packaging

  • build\Release\octave.exe — the built executable (multi-config MSVC; single-config generators drop it in build\)
  • CI stages dist\OCTAVE\: the exe, vcpkg's tag.dll / avcodec-*.dll / avutil-*.dll / swresample-*.dll, platform-tools\adb.exe (+ AdbWinApi.dll, AdbWinUsbApi.dll, libwinpthread-1.dll), then windeployqt --qmldir frontend --release, then renames the exe to OCTAVE.exe because the .iss expects the capitalised name
  • dist\OCTAVE-<version>-windows-x86_64.exe — Inno Setup installer. CI patches #define MyAppVersion in build_scripts/installer_windows.iss from the git tag (fallback 0.9.0 on a manual dispatch) before running ISCC.exe

build_scripts/installer_windows.iss is the only file left in build_scripts/. It installs to Program Files (admin, Windows 10+), creates Start Menu / optional desktop shortcuts, checks the registry for the VC++ 2015–2022 runtime and shows an informational message with the download link if it is missing, and — note — its [UninstallDelete] section removes %APPDATA%\OCTAVE (settings, dashboards, logs) on uninstall.

macOS Build

macOS

Requirements

  • Xcode Command Line Tools (xcode-select --install)
  • Qt 6.7.3 (Apple Silicon and Intel), e.g. aqt install-qt mac desktop 6.7.3 -O ~/Qt -m qtmultimedia qtnetworkauth qtserialport qtconnectivity qtsensors qtquick3d qt5compat qtshadertools qtquicktimeline
  • brew install taglib ffmpeg pkg-config for tag reading and the phone-mirror decoder
export PATH="$HOME/Qt/6.7.3/macos/bin:$PATH"
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

Output

  • build/octave.app — CMakeLists.txt sets MACOSX_BUNDLE explicitly (bundle id com.waybettersolutions.octave, name OCTAVE); without it qt_add_executable would emit a bare ELF-style binary that macdeployqt cannot bundle
  • dist/OCTAVE-<version>-macos.dmg — CI renames the bundle to OCTAVE.app, copies adb into Contents/Resources/platform-tools/, runs macdeployqt dist/OCTAVE.app -qmldir=frontend -dmg (macdeployqt creates the DMG itself) and renames the result (version fallback 0.0.0)
Code signing
The bundle is unsigned, so Gatekeeper reports it as damaged. Users can bypass with xattr -cr /Applications/OCTAVE.app. For distribution, sign with a Developer ID certificate. iOS is not wired at all (no toolchain in CMake, no CI job — BUILD.md, iOS build).

Linux Build

Linux

Requirements

  • Build essentials, CMake, Ninja, pkg-config, and the X11/XCB dev libraries listed in BUILD.md
  • Qt 6.7.3 via the Qt online installer or aqtinstall (aqt install-qt linux desktop 6.7.3 linux_gcc_64 ...; linux_arm64 for ARM boards). Distro Qt 6.2 cannot run OCTAVE — see CMake Options
  • For a local AppImage on Ubuntu 22.04: libtag1-dev libavcodec-dev libavutil-dev libfuse2 wget file
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# Optional: portable AppImage (same layout CI ships, linked against your distro's glibc)
bash packaging/linux/build-appimage.sh
# -> dist/OCTAVE-<version>-linux-x86_64.AppImage (or -linux-aarch64 on an ARM host)

Output

  • build/octave — the built executable; QML and assets load from the checkout's frontend/
  • dist/OCTAVE-<version>-linux-x86_64.AppImage / -linux-aarch64.AppImage — portable single-file AppImages. The version comes from OCTAVE_VERSION (CI passes the tag), else GITHUB_REF_NAME, else the project() version in CMakeLists.txt

AppImage structure

packaging/linux/build-appimage.sh does a Release Ninja build into build-appimage/, stages AppDir/, then runs linuxdeploy + linuxdeploy-plugin-qt. Both tools are downloaded on first use from their continuous release tag into packaging/linux/tools/ (gitignored, as are build-appimage/, AppDir/ and dist/). The layout must match the runtime asset lookup in src/main.cpp:

AppDir/
  AppRun                    # custom: exports LD_LIBRARY_PATH, QT_PLUGIN_PATH and
                            #   QML2_IMPORT_PATH=usr/qml:usr/frontend (linuxdeploy's own AppRun only knows usr/qml)
  usr/bin/octave            # applicationDirPath()
  usr/bin/platform-tools/   # adb, if scripts/fetch_platform_tools.py ran first
  usr/frontend/             # ../frontend relative to the binary -- the QML tree
                            #   (assets/-src and assets/readme are stripped: not runtime assets)
  usr/lib/, usr/plugins/, usr/qml/   # Qt runtime deployed by linuxdeploy-plugin-qt
  usr/plugins/assetimporters/        # copied by the script from the path CMake recorded (Quick3D's assimp loader)

Other details of the script: it bundles libtag.so explicitly via --library because linuxdeploy occasionally misses it (avoiding an awk ... exit SIGPIPE that set -o pipefail would turn into an abort — commit 0ab7f14), reuses a project icon if one exists or writes a placeholder SVG, sets QML_SOURCES_PATHS so the Qt plugin scans usr/frontend for imports, and honours QMAKE (CI points it at install-qt-action's qmake6 so the plugin does not fall back to a system Qt 5 stub) and OCTAVE_DROP_QT_PLUGINS (space-separated paths under Qt's plugins/ to delete after the CMake build and before deployment). Putting the QML tree anywhere else breaks the lookup and the app exits silently with no window. On Arch the bundled strip rejects modern .relr.dyn sections — pass NO_STRIP=1. AppImages built on Arch will not run on Ubuntu/Debian (newer glibc); let CI on ubuntu-22.04 produce distributable ones.

Desktop launcher (development machines)

scripts/octave-desktop.sh builds and launches the native app straight from a Dropbox-synced checkout (a ~/.local/share/applications/octave-dropbox.desktop menu entry points at it; BUILD.md describes the Mod+D binding). It configures once into build-desktop-<hostname>/ (Release) so two machines syncing the same tree never share a CMake cache, then runs an incremental cmake --build --target octave --parallel 4 (bounded so a desktop launch cannot exhaust memory) and execs the binary. Since commit 037f753 the configure step passes -DQt6_DIR="$(/usr/bin/qmake6 -query QT_INSTALL_LIBS)/cmake/Qt6" because the CMake package registry could otherwise select an installed Android kit for the desktop build. A flock on ~/.local/state/octave/desktop-build.lock stops two menu clicks from building concurrently; failures raise a desktop notification and the log is ~/.local/state/octave/desktop-launch.log ($XDG_STATE_HOME honoured). .gitignore covers build/, build-desktop-*/, build-rhea/, build-android/ and build-appimage/.

Two older Pi launcher scripts also live in scripts/: octave-start.sh (activates the venv and runs the Python backend with DISPLAY=:0 and MESA_GL_VERSION_OVERRIDE=3.3) and octave-update.sh (a git fetch + reset --hard origin/main with 10 s timeouts that skips silently when offline). Both hardcode /home/rob/Roxy/octave and are specific to the original Raspberry Pi installation.

Android APK Build

Android

The Android .apk is built from the C++ / Qt 6 tree using Qt's qt-cmake cross-compile wrapper (or a plain cmake with Qt's qt.toolchain.cmake, as CI does). The Python backend is desktop-only and is never packaged for mobile; platform-specific behaviour is gated behind #ifdef Q_OS_ANDROID in the C++ managers, with the Java side in android/src/org/octave/app/ (OctaveOBDBridge.java for Bluetooth/BLE OBD, OctaveMediaBridge.java for the bundled Python / yt-dlp runtime). The former Buildozer / python-for-android path has been removed.

qt-cmake -S . -B build-android \
    -DCMAKE_BUILD_TYPE=Debug \
    -DANDROID_ABI=arm64-v8a \
    -DANDROID_PLATFORM=android-30 \
    -DQT_ANDROID_SIGN_APK=OFF
    # add -DOCTAVE_ENABLE_DOWNLOADS=OFF only for a Play Store build; sideload builds (and CI) keep downloads ON

cmake --build build-android --target apk -j
adb install build-android/android-build/build/outputs/apk/debug/android-build-debug.apk

Packaging facts from CMakeLists.txt and android/: package org.octave.app; single ABI arm64-v8a; minSdk 30, targetSdk 33 (capped by AGP 7.4.1, Qt 6.7.3's target Gradle plugin — bump with Qt 6.8+); QT_ANDROID_PACKAGE_SOURCE_DIR = android/; QT_QML_ROOT_PATH = frontend/ so the runtime-loaded QML is findable at assets:/frontend/; android/assets/frontend and android/assets/scripts are symlinks into the repo for development. Spotify is excluded from the Android build (desktop-only, TODO/android-cpp-port.md). LGPL Qt is dynamically linked.

What the CI job does

  1. Temurin JDK 17 (AGP 7.4.1 needs 17, not 11 or 21), host Qt 6.7.3 (linux/desktop) and target Qt 6.7.3 (android_arm64_v8a), both with qtmultimedia qtnetworkauth qtserialport qtconnectivity qtsensors qt5compat qtshadertools qtquick3d
  2. android-actions/setup-android@v3, then ndk;26.1.10909125, platforms;android-33, build-tools;33.0.2
  3. Restores a Gradle cache keyed on android/build.gradle + gradle.properties so repeat runs survive Maven Central's intermittent 429s
  4. Runs scripts/build-android-pylib-bundle.sh to produce android/assets/python-packages/ytmusic-bundle.zip (ytmusicapi + requests + their pure-Python deps, native .so/.pyd stripped). The AAR-shipped Python has no pip; OctaveMediaBridge extracts this zip on first launch and runs scripts/ytmusic_search.py from it. Without it YouTube Music search silently fails on the device
  5. Dereferences the android/assets/frontend and scripts symlinks into real copies — APKs cannot contain symlinks; the entries become 0-byte files and the app dies with "Failed to load Main.qml"
  6. cmake -S . -B build-android -DCMAKE_BUILD_TYPE=Release -DCMAKE_TOOLCHAIN_FILE=$QT_ROOT_DIR/lib/cmake/Qt6/qt.toolchain.cmake -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-30 -DQT_HOST_PATH=$HOST_QT
  7. cmake --build build-android --target apk -j, retried up to four times with 20 s doubling backoff (Maven Central rate-limits runner IPs on the youtubedl-android AAR fetch)
  8. Signs the unsigned release APK: generates a fresh RSA keystore, zipalign -p 4, apksigner sign with v1 + v2 + v3 schemes all forced on (apksigner's v3-only default for minSdk ≥ 28 makes many sideload installers report "package appears to be invalid"), apksigner verify, then stages dist/OCTAVE-<v>-android-arm64-v8a.apk (version fallback dev)
Signing identity changes every release
Because the keystore is generated per run, Android refuses to update an installed OCTAVE from one release to the next (INSTALL_FAILED_UPDATE_INCOMPATIBLE) — users must adb uninstall org.octave.app (or uninstall from Settings) first, and the Play Store cannot be targeted. Persisting one keystore as a GitHub Secret is TODO/android-signing-keystore.md; a working TLS backend (OpenSSL bundling) is TODO/android-openssl-bundling.md.
Full local toolchain
See BUILD.md (Android build) for the complete local setup — Qt for Android 6.7.3 via aqtinstall, OpenJDK 17, Android SDK + NDK 26.1.10909125, the environment variables (QT_HOST_PATH is mandatory for the cross-compile), device USB debugging and a troubleshooting table. A condensed walkthrough is on the Getting Started page; the port's remaining work is in TODO/android-cpp-port.md.

Phone Server Jar & adb

No scrcpy binary is bundled or required. Two small Apache-2.0 pieces ship inside OCTAVE:

  • The phone server — phone_server/ (Java, org.octave.phoneserver) built into tools/phone-server/octave-phone-server, embedded in the C++ binary as a resource and pushed by the Python backend from the same file. After editing phone_server/src, rebuild with ANDROID_HOME=~/Android/Sdk ANDROID_PLATFORM=36 ANDROID_BUILD_TOOLS=36.0.0 bash phone_server/build_without_gradle.sh (JDK 21 to match CI; the script compiles with javac -source 1.8 -target 1.8, generates the AIDL stubs, dexes with d8 and writes the jar to build_manual/ or $BUILD_DIR) and commit it together with the source. The version string SCRCPY_VERSION_NAME=3.3.4-octave in the script must equal SERVER_VERSION in backend/phone_mirror/scrcpy_client.py and kServerVersion in src/phone_mirror/scrcpyclient.cpp (both 3.3.4-octave); the server refuses a mismatch. Protocol byte layouts live in docs/PHONE_MIRROR_NATIVE_PLAN.md.
  • adb — python scripts/fetch_platform_tools.py [--os linux|windows|darwin | --all] [--dest DIR] downloads Google's platform-tools 37.0.1, verifies the SHA-256 recorded in the script, and extracts only adb (+ lib64/libc++.so on Linux, the three DLLs on Windows), NOTICE.txt and source.properties into tools/platform-tools/<os>/ (gitignored). CI ships that next to the executable: platform-tools/ beside OCTAVE.exe, usr/bin/platform-tools/ in the AppImage, Contents/Resources/platform-tools/ in the bundle. Google publishes x86_64 only, so ARM boards fall back to the distro's adb on PATH.

libavcodec is an optional build dependency for the H.264 decoder; without it phoneMirrorManager.nativeAvailable is false and there is no fallback path any more.

Python Developer Backend

The Python tree (backend/ + main.py) is a peer backend for tinkering on desktop and Raspberry Pi / Orange Pi. It has no build pipeline: run it from a checkout.

python setup.py              # create venv, install requirements.txt, launch (installs distro packages on Linux via sudo)
python setup.py --no-run     # setup only
python main.py               # run (venv activated); --debug adds octave-debug.log, --profile starts the perf monitor + command server
python -m dev.main_dev       # dev mode: simulated OBD + keyboard controls (dev/ is gitignored -- developer machines only)

setup.py detects the platform (including Raspberry Pi via the device-tree model and WSL via /proc/version), installs the Qt runtime libraries for Arch / Fedora / Debian families, recreates the venv if it was made on another OS or has a broken pip, installs requirements.txt (PySide6, mutagen, numpy, python-obd, spotipy, keyring, av, requests, pyserial, smbus2 on Linux, yt-dlp, ytmusicapi, rapidfuzz) and execvs main.py. It checks for Python 3.8+, while pyproject.toml declares requires-python = ">=3.10,<3.12" and CI runs 3.11 — treat 3.10/3.11 as the supported range.

Do not reintroduce build_scripts/build.py, octave.spec, requirements-build.txt, per-platform build_*.{sh,bat} wrappers, or the Buildozer spec — they were removed deliberately.

Build Troubleshooting

CMake configures against the Android kit on a desktop build

With Qt for Android installed, the CMake package registry can resolve find_package(Qt6) to the Android kit and the desktop build fails at configure. Pass the desktop kit explicitly: -DQt6_DIR="$(qmake6 -query QT_INSTALL_LIBS)/cmake/Qt6" (what scripts/octave-desktop.sh does). The AppImage script has the mirror-image problem for its assetimporters copy, which is why CMake records the real plugin path in build/qt_plugins_path.txt.

"DLL not found" on Windows

Install the Visual C++ Redistributable: Download link. The installer already warns when the registry shows no VC++ runtime.

"App is damaged" on macOS

xattr -cr /Applications/OCTAVE.app

App links but exits at Main.qml load

The Qt you built against lacks QtQuick.Effects or Qt5Compat.GraphicalEffects (both imported by frontend/MainMenu.qml), or the packaged QML tree is not at <binary dir>/frontend or <binary dir>/../frontend. Use the pinned Qt 6.7.3 with the qt5compat module rather than distro Qt 6.2, and keep the AppDir layout above.

3D vehicle model does not load

Failed to load asset import plugin with key: "assimp" means Qt Quick 3D is present but its assimp import plugin is not — on Arch, qt6-quick3d additionally needs the assimp package; in an AppImage it means usr/plugins/assetimporters/ was not copied (CMake did not find Quick3D at configure time).

AppImage won't run

# Make executable
chmod +x OCTAVE-<version>-linux-x86_64.AppImage

# If FUSE unavailable, extract and run
./OCTAVE-<version>-linux-x86_64.AppImage --appimage-extract
./squashfs-root/AppRun

arm64 AppImage build aborts in linuxdeploy-plugin-qt

An unresolved libgstphotography dependency from Qt's GStreamer plugin. Set OCTAVE_DROP_QT_PLUGINS=multimedia/libgstreamermediaplugin.so as the CI job does; OCTAVE uses the FFmpeg media backend and does not need the plugin.

Android: INSTALL_FAILED_UPDATE_INCOMPATIBLE / "package appears to be invalid"

The first is a signing-key change (every CI release uses a new keystore, and a local debug build differs from both): adb uninstall org.octave.app, then install. The second is a v3-only signature on some sideload installers; CI forces v1+v2+v3, so a locally signed APK should do the same.

Android APK build fails fetching the youtubedl-android AAR (HTTP 429)

Maven Central rate-limiting. CI retries four times with backoff and caches ~/.gradle; locally, just re-run cmake --build build-android --target apk.

qmllint fails locally on warnings

qmllint exits 255 on plain warnings. CI only fails on critical entries — reproduce with find frontend -name '*.qml' -exec qmllint -I frontend --json qmllint.json {} + and inspect the JSON rather than the exit code.

Dropbox sync interference

CMake caches are machine-specific. If the checkout is Dropbox-synced between machines, build into a per-host directory (as scripts/octave-desktop.sh does with build-desktop-<hostname>/) rather than sharing build/.
