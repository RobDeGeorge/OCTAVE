What Gets Built

OCTAVE is one C++ / Qt 6 program with a QML screen. CMake, the build tool, turns the source in src/ into one executable called octave. The QML files in frontend/ are not compiled in: the program reads them from a frontend folder when it starts, so you can edit QML and run again without rebuilding.

Every package comes from that same source: the Windows installer, the macOS disk image, the Linux AppImages for x86_64 and aarch64, the Android APK, and the demo that runs in a browser. If you only want to use OCTAVE, download a package instead: see Getting Started.

This page starts with the quickest way to a working build on your own computer and gets more technical as it goes: the other platforms, the options, how releases are made, and what tends to go wrong.

Quick Start: a Desktop Build

You need four things on any desktop:

WhatVersionNotes
CMake3.21 or newerNinja is optional and makes builds faster (-G Ninja).
A C++17 compilerGCC, Clang or Visual Studio 2022
Qt6.7.3The version every release is built with. Modules: qtmultimedia qtserialport qtconnectivity qt5compat qtquick3d qtshadertools qtquicktimeline.
TagLibany recentReads song tags. The build stops without it.

FFmpeg, OpenSSL and libplist are optional. Without them OCTAVE still builds, but phone mirroring, Android Auto and AirPlay are left out: see CMake Options.

On Ubuntu or Debian, install the packages and Qt like this:

sudo apt-get install -y \
  build-essential cmake ninja-build pkg-config \
  libtag1-dev libavcodec-dev libavutil-dev libgl1-mesa-dev libegl1-mesa-dev \
  libxcb-xinerama0 libxcb-cursor0 libxkbcommon-dev \
  libpulse-dev libssl-dev libplist-dev

pipx install aqtinstall
aqt install-qt linux desktop 6.7.3 linux_gcc_64 -O ~/Qt \
    -m qtmultimedia qtserialport qtconnectivity qt5compat qtquick3d qtshadertools qtquicktimeline

Then, from the repository root, three commands:

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH="$HOME/Qt/6.7.3/gcc_64"
cmake --build build -j8
./build/octave

CMAKE_PREFIX_PATH tells CMake which Qt to use. The 8 after -j is the number of files compiled at once: always give a number (see Traps).

Useful ways to run what you built:

CommandWhat it does
./build/octave --simStarts with a simulated car, so every page has data with no adapter. It uses a throwaway settings folder and is in every build.
./build/octave --debugWrites debug-level logs.
./build/octave --helpLists every option.
ctest --test-dir build --output-on-failureRuns the tests. A Debug build includes them. See Development.

A Debug build also contains the developer tools (--dev, --profile), which the Development Guide describes.

Linux and the AppImage

Linux

The Quick Start above is the Linux build. The executable is build/octave, and it finds frontend/ one folder up, in the checkout. For a Release build, change Debug to Release.

The Qt that Ubuntu 22.04 packages (6.2) is too old: the build links, then the screen fails to load. Use 6.7.3. For an ARM board such as a Raspberry Pi or Orange Pi, aqtinstall has a linux_arm64 host with the same version.

Making an AppImage

An AppImage is a single file that carries the program, Qt and the QML with it, and runs without being installed. One script builds it: 

sudo apt-get install -y libfuse2 wget file
python3 scripts/fetch_platform_tools.py --os linux   # optional: puts adb in the package
QMAKE="$HOME/Qt/6.7.3/gcc_64/bin/qmake6" \
OCTAVE_CMAKE_ARGS="-DCMAKE_PREFIX_PATH=$HOME/Qt/6.7.3/gcc_64" \
bash packaging/linux/build-appimage.sh
# -> dist/OCTAVE-<version>-linux-x86_64.AppImage (or -linux-aarch64 on an ARM machine)

The script makes its own Release build in build-appimage/, lays the files out in AppDir/, and packs them with linuxdeploy, which it downloads on first use. These environment variables steer it:

VariableWhat it does
OCTAVE_VERSIONThe version in the file name. Without it, the version in CMakeLists.txt is used.
OCTAVE_CMAKE_ARGSExtra options for the CMake configure step, such as which Qt to use.
QMAKEThe qmake6 of the Qt to package, when it is not the first one on PATH.
NO_STRIP=1Needed on Arch, where the bundled strip fails on current libraries.
OCTAVE_DROP_QT_PLUGINSQt plugins to delete before packaging. The aarch64 build needs it: see Traps.

An AppImage only runs on systems with a C library at least as new as the one it was built on. One built on Arch will not start on Ubuntu or Debian. The released ones are built on Ubuntu 22.04.

AppImage layout

OCTAVE looks for its QML in a frontend folder beside the executable, then one folder up. The package must keep that relationship. If the QML is anywhere else, the program starts and no window appears. 

AppDir/
  AppRun                      # sets the library, plugin and QML paths, then starts octave
  usr/bin/octave
  usr/bin/platform-tools/     # adb, if you fetched it
  usr/frontend/               # the QML: one folder up from the executable
  usr/lib/  usr/plugins/  usr/qml/   # Qt

Running from a synced checkout

scripts/octave-desktop.sh builds what changed and starts the app, for a menu entry on a development machine. It builds into build-desktop-<hostname>/, so two computers that share one checkout through a sync service never share a build folder. Setup is in docs/desktop-source-launch.md. The launcher of the in-car Orange Pi is described in Hardware Setup.

Windows

Windows

You need:

  • Visual Studio 2022 with the "Desktop development with C++" workload.
  • Qt 6.7.3 for MSVC (msvc2019_64) from the Qt online installer, with the modules in the Quick Start.
  • vcpkg, a package manager for C++ libraries, for TagLib, FFmpeg and OpenSSL.

In PowerShell, with VCPKG_INSTALLATION_ROOT set to your vcpkg folder and the Qt path changed to yours:

& "$env:VCPKG_INSTALLATION_ROOT\vcpkg" install taglib:x64-windows "ffmpeg[core,avcodec]:x64-windows" openssl:x64-windows

cmake -S . -B build `
  -DCMAKE_TOOLCHAIN_FILE="$env:VCPKG_INSTALLATION_ROOT/scripts/buildsystems/vcpkg.cmake" `
  -DVCPKG_TARGET_TRIPLET=x64-windows `
  -DCMAKE_PREFIX_PATH="C:/Qt/6.7.3/msvc2019_64"
cmake --build build --config Release -j8

Copy-Item -Recurse -Force frontend build/Release/
./build/Release/octave.exe

Visual Studio puts the executable in build\Release\, where it cannot find frontend/ by itself. The Copy-Item line puts a copy beside it. Run it again after you change QML. To start the program outside a Qt command prompt, the Qt DLLs must be beside it too: windeployqt --qmldir frontend --release build/Release/octave.exe copies them.

The developer tools and the tests are off in a Visual Studio build, because it has no single build type. Turn them on with -DOCTAVE_DEV_TOOLS=ON -DOCTAVE_BUILD_TESTS=ON.

The installer

The release is an Inno Setup installer made from build_scripts/installer_windows.iss. It needs Windows 10 or later and administrator rights, installs to Program Files, and carries Qt, the Visual C++ runtime, FFmpeg, OpenSSL and adb, so the user installs nothing else. Three things to know about it:

  • It adds a Windows Firewall rule named "OCTAVE adb" for the bundled adb.exe, so pairing a phone over Wi-Fi shows no firewall prompt. Uninstalling removes it.
  • Installing over an older copy closes a running OCTAVE and its adb first.
  • Uninstalling asks whether to delete %APPDATA%\OCTAVE too (settings, dashboards, trips and logs). The default is to keep it, and a silent uninstall always keeps it.

macOS

macOS 
xcode-select --install
brew install taglib pkg-config ffmpeg
pipx install aqtinstall
aqt install-qt mac desktop 6.7.3 -O ~/Qt \
    -m qtmultimedia qtserialport qtconnectivity qtquick3d qt5compat qtshadertools qtquicktimeline

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="$HOME/Qt/6.7.3/macos"
cmake --build build -j8

./build/octave.app/Contents/MacOS/octave

The build makes an application bundle, build/octave.app. The executable inside it looks for frontend/ in the bundle's Contents/Resources first (a release) and then beside the build folder (your checkout), so a local build runs with no copying and picks up QML changes at the next start.

The release is a disk image made with Qt's macdeployqt dist/OCTAVE.app -qmldir=frontend -dmg. It is not signed with an Apple Developer ID and not notarized, so macOS may refuse to open it; Troubleshooting covers that message.

The release job copies frontend/ into OCTAVE.app/Contents/Resources/frontend before the disk image is made, and fails if Main.qml is not there.

Check a disk image opens a window
The job's test of the bundle runs without a window. Before handing a .dmg to anyone, open it and see the screen appear.

There is no iOS build yet.

Android

Android

The APK is the same C++ program, cross-compiled on a Linux computer with Qt for Android. It runs on 64-bit ARM phones and tablets with Android 11 or later. The toolchain is large (allow 40 to 60 GB) and version-sensitive:

PieceVersion
Qt for Android6.7.3, kit android_arm64_v8a, plus the desktop kit of the same version for the build tools. Modules: the Quick Start ones plus qtsensors and qtwebview.
JavaJDK 17
Android NDK26.1.10909125
Android SDKplatforms;android-33, build-tools;33.0.2

BUILD.md ("Android build") walks through installing all of it and the environment variables. Once that is done: 

qt-cmake -S . -B build-android \
    -DCMAKE_BUILD_TYPE=Debug \
    -DANDROID_ABI=arm64-v8a \
    -DANDROID_PLATFORM=android-30 \
    -DQT_ANDROID_SIGN_APK=OFF
cmake --build build-android --target apk -j8
adb install build-android/android-build/build/outputs/apk/debug/android-build-debug.apk

qt-cmake is the CMake wrapper inside the Android kit. It needs QT_HOST_PATH to point at the desktop kit, or it reports that Qt was not found.

What goes into the APK

  • The app's package name is org.octave.app. The version name and code come from the version in CMakeLists.txt (0.9.6 becomes code 906). Android only installs an update with a higher code.
  • The QML and the wiki, from android/assets/. In the repository those two entries are symlinks to frontend/ and wiki/. An APK cannot hold a symlink, so the release job replaces them with real copies before it builds.
  • OpenSSL, from android/openssl/. Qt for Android does not include it, and without it nothing can use HTTPS.
  • Qt Quick 3D's model importer. Without it no 3D model loads.

The release job fails if the APK lacks OpenSSL, the model importer, the wiki or the Qt WebView library that shows it.

Signing

Android only installs an update over an app signed with the same key. Releases are signed with one permanent key, held as repository secrets, so each release installs over the last. A build from a fork, which has no secrets, and a local build are signed with other keys: installing one over a release fails with INSTALL_FAILED_UPDATE_INCOMPATIBLE until you run adb uninstall org.octave.app, which also removes the app's data.

Browser (WebAssembly)

The demo at robdegeorge.com/OCTAVE/ is the same program compiled to WebAssembly, the format browsers run. It uses a newer Qt than the other builds:

  • Qt 6.12.0, kit wasm_multithread, and the desktop kit of the same version for the build tools.
  • emsdk 5.0.5, the Emscripten compiler that Qt version asks for.
aqt install-qt all_os wasm 6.12.0 wasm_multithread -O ~/Qt -m qt5compat qtmultimedia qtquick3d qtquicktimeline qtwebsockets qtshadertools
aqt install-qt linux desktop 6.12.0 linux_gcc_64 -O ~/Qt -m qt5compat qtmultimedia qtquick3d qtquicktimeline qtwebsockets qtshadertools
git clone https://github.com/emscripten-core/emsdk ~/emsdk
~/emsdk/emsdk install 5.0.5 && ~/emsdk/emsdk activate 5.0.5

QT_WASM=~/Qt/6.12.0/wasm_multithread QT_HOST=~/Qt/6.12.0/gcc_64 JOBS=8 \
OUT_DIR=/tmp/octave-site packaging/wasm/build.sh

python3 packaging/wasm/serve.py /tmp/octave-site 8080   # then open http://127.0.0.1:8080/

packaging/wasm/build.sh builds into build-wasm/ and, when OUT_DIR is set, copies the finished site there. Set JOBS: its default is one compile per processor core. The site must be served with two HTTP headers (COOP and COEP) that let a page use threads, which serve.py sends and a plain python -m http.server does not. On the published site a small service worker, packaging/wasm/coi-serviceworker.js, adds them, because GitHub Pages cannot.

What is different in this build

  • A browser has no serial ports, Bluetooth stack or processes. Qt SerialPort, Qt Bluetooth and FFmpeg are left out, and src/platform/wasm/ holds what stands in for them.
  • frontend/ is packed into the page's download (octave.data). Keep large unused files out of it: every visitor downloads all of it.
  • TagLib is downloaded and built from source during the build.

In C++, OCTAVE_WASM is defined for this build. Put new hardware code behind it and new QProcess code behind #if QT_CONFIG(process), or this build breaks.

What the demo can connect to is on the pages that own each part: adapters in OBD Manager, the music folder in Media Manager, and the frontend playground in Writing a Frontend. The site is published by its own workflow: see CI and Releases.

Phone Server and adb

Phone mirroring needs two programs that are not part of the C++ build. Both travel with OCTAVE, so the user installs nothing.

The phone server

This is a small Java program that OCTAVE pushes to the phone to capture its screen. Its source is phone_server/, OCTAVE's fork of the scrcpy server. The built file is committed at tools/phone-server/octave-phone-server and compiled into the executable, so an ordinary build needs no Java or Android SDK. Rebuild it only after changing phone_server/src:

  1. Install a JDK (CI uses 21) and the Android SDK packages platforms;android-36 and build-tools;36.0.0.
  2. Run ANDROID_HOME=~/Android/Sdk bash phone_server/build_without_gradle.sh. The result is build_manual/octave-phone-server.
  3. Copy it over tools/phone-server/octave-phone-server and commit it with the source change.

The version string SCRCPY_VERSION_NAME in that script must equal kServerVersion in src/phone_mirror/scrcpyclient.h (both 3.3.4-octave). The server refuses a client with another version.

adb

adb is Google's tool for talking to an Android phone. python3 scripts/fetch_platform_tools.py downloads a pinned release of it, checks its SHA-256, and keeps only adb and its licence notice in tools/platform-tools/<os>/. Pass --os linux, windows or darwin for another system, or --all. The packages carry that folder:

PackageWhere adb is
Windowsplatform-tools\ beside OCTAVE.exe
AppImage (x86_64)usr/bin/platform-tools/
macOSContents/Resources/platform-tools/
AppImage (aarch64)Not included: Google publishes no adb for ARM Linux. Install the system's own (sudo apt install adb).

CMake Options

The page is technical from here on. Pass an option on the configure line as -DNAME=value.

OptionDefaultWhat it does
OCTAVE_DEV_TOOLSON for a desktop Debug build, otherwise OFFBuilds the developer tools in src/dev/: the --dev and --profile options. Off, those options are ignored, and no release contains the tools.
OCTAVE_BUILD_TESTSSame as aboveBuilds the tests in tests/cpp/ for ctest.
OCTAVE_REQUIRE_FFMPEGOFFStops the configure step when FFmpeg is missing, instead of building without phone mirroring. CI and every desktop release set it.
OCTAVE_FFMPEG_ROOTemptyLinux and macOS: use the FFmpeg that packaging/ffmpeg/build-h264-decoder.sh <folder> built into that folder, instead of the system's. Releases set it.
OCTAVE_WERROROFFTreats compiler warnings in OCTAVE's own code as errors.
OCTAVE_SANITIZEemptyA sanitizer list such as address,undefined for OCTAVE's own code and tests (GCC and Clang). Use a separate build folder inside the repository.
OCTAVE_SPOTIFY_CLIENT_IDemptyThe Spotify app ID built into the program. Empty, each user enters their own in Settings. See Media Manager.

"Desktop Debug build" means -DCMAKE_BUILD_TYPE=Debug was given. A configure with no build type, a Visual Studio or Xcode build and an Android build all get OFF unless you pass ON.

What CMake looks for by itself

These features have no switch. Each is built when its libraries are found, and the configure output has a line saying which way it went.

FeatureNeedsLine in the configure outputWithout it
Phone mirroringFFmpeg's libavcodec and libavutil (desktop)Built-in phone mirror decoder (libavcodec): ONPhone mirroring is unavailable.
Built-in Android Auto (OCTAVE_HAVE_NATIVE_AA)The above and OpenSSL (desktop)Native Android Auto receiver (OpenSSL + libavcodec): ONAndroid Auto works only through Google's desktop head unit program.
AirPlay (OCTAVE_HAVE_AIRPLAY)Both of the above and libplist (Linux only)AirPlay receiver (UxPlay + libplist + libavcodec): ONNo AirPlay.
3D vehicle viewThe qtquick3d Qt module, and qtquicktimeline for the 3D music players in the Media RoomQtQuick3D foundThe 3D View card is greyed out.
Wiki reader in the appQt WebEngine on desktop, the qtwebview module on AndroidThe reader says it is unavailable.

Packages for the optional libraries: libavcodec-dev libavutil-dev libssl-dev libplist-dev on Debian and Ubuntu, ffmpeg from Homebrew, and the vcpkg line in the Windows section.

SQLite, which stores the trip history, is compiled in from third_party/sqlite/. There is nothing to install for it on any platform.

The version and the source list

The version is set once, in project(OCTAVE VERSION ...) at the top of CMakeLists.txt. The program, the APK and a locally built AppImage take it from there. The Windows installer script has its own copy (MyAppVersion), which the release job overwrites from the tag: change the two together.

Every source file is listed by name in the qt_add_executable(octave ...) call. A new .h / .cpp pair needs two new lines there.

CI and Releases

GitHub Actions builds and checks OCTAVE. The release workflow is .github/workflows/build.yml.

On every push and pull request to main

JobWhat it checks
lintruff check . over the Python tools, that the generated parameter table in docs/GAUGE_AUTHORING.md is current, and that the published API did not break without a version bump.
cpp-compile-checkA Linux Debug build with Qt 6.7.3 and OCTAVE_REQUIRE_FFMPEG, the whole ctest suite, and qmllint over every QML file. Only QML errors fail it; warnings do not.
phone-serverRebuilds the phone server from source. Fails if either the fresh or the committed file lacks the right class or version string. Warns, without failing, when the two are not byte-identical.
sdkThe TypeScript and Go SDKs: generated files current, type check, tests.

On a version tag

Pushing a tag that starts with v also runs five build jobs, each only after lint and cpp-compile-check pass:

JobRuns onProduces
cpp-build-windowswindows-latestOCTAVE-<version>-windows-x86_64.exe
cpp-build-macosmacos-15OCTAVE-<version>-macos.dmg
cpp-build-linuxubuntu-22.04OCTAVE-<version>-linux-x86_64.AppImage
cpp-build-linux-arm64ubuntu-22.04-armOCTAVE-<version>-linux-aarch64.AppImage
cpp-build-androidubuntu-22.04OCTAVE-<version>-android-arm64-v8a.apk

Each job keeps its package on the run's page for 30 days. A release job then attaches all five to one GitHub Release.

What a desktop package must pass

Before a desktop package is uploaded, the job starts it as a user would, with the build machine's own Qt taken out of the environment, so a package that only works beside an installed Qt fails here.

  • All four desktop packages run --headless --sim --smoke: no window, a simulated car, exit after 5 seconds. The log must show the simulated car answering and the service started. packaging/smoke-sim.sh does this; the Windows job does the same in PowerShell.
  • The Windows package also runs --smoke with its window. It must load the screen, and its log must show phone mirroring available and an LGPL FFmpeg.
  • The Windows job fails on any DLL the package needs and does not carry (packaging/windows/resolve_dlls.py).
  • The x86_64 AppImage and the macOS bundle fail if they carry a GPL codec library.

Making a release

  1. Set the new version in CMakeLists.txt and build_scripts/installer_windows.iss.
  2. To try the packages first without tagging, start the workflow by hand on a branch. platforms picks what to build: all, windows+linux, windows, linux, linux-arm64, macos or android. 
    gh workflow run build.yml --ref <branch> -f platforms=windows+linux
    A run started this way makes no release, and its packages are not named after the new version.
  3. Push the tag, for example v0.9.7. The release appears as a pre-release: public, so test machines can download the exact files, but not marked as the latest.
  4. Install and test those files. Then promote the release and replace the generated notes with your own: 
    gh release edit vX.Y.Z --prerelease=false --latest

The website

.github/workflows/wiki-pages.yml builds the browser demo and publishes it with this wiki at robdegeorge.com/OCTAVE/ (the wiki under /OCTAVE/wiki/). It runs on a push to main that touches the app's source, the QML, the wiki or the web frontends, and has nothing to do with version tags.

Traps

These are problems with building. Problems with installing or starting a package are in Troubleshooting.

What you seeWhy, and what to do
The computer freezes or runs out of memory during a buildA bare -j starts a compile for every file at once. Always give a number: -j8.
A desktop configure fails, or picks up the Android kitWith Qt for Android installed, CMake can find that kit first. Name the desktop one: -DCMAKE_PREFIX_PATH=<desktop kit>, or -DQt6_DIR="$(qmake6 -query QT_INSTALL_LIBS)/cmake/Qt6" as scripts/octave-desktop.sh does.
It builds, then no window appearsEither the program cannot find frontend/ (it must be beside the executable or one folder up, or in Contents/Resources of a macOS bundle: see Windows, macOS and the AppImage layout), or the Qt is too old or lacks the qt5compat module. Look in the log for the QML error.
QML that works on your machine breaks in CI or in a releaseYour Qt is newer than 6.7.3 and accepts things 6.7.3 does not. Check changed QML with the 6.7.3 qmllint before pushing: see Development.
qmllint exits with an error on a clean fileIt exits non-zero for warnings too. CI reads its JSON output and fails only on entries of type critical.
Failed to load asset import plugin with key: "assimp", and the 3D vehicle is missingQt Quick 3D is there but its model importer is not. On Arch, install the assimp package. In an AppImage it means CMake did not find Qt Quick 3D when the package was built.
A package starts, then fails on a missing libQt6QuickTimelineThe Qt kit lacks the qtquicktimeline module. CMake warns about it at configure time; the AppImage script and the Android job refuse to ship that combination.
The AppImage script fails in strip on ArchRun it with NO_STRIP=1.
The aarch64 AppImage build stops in linuxdeploy on libgstphotographyThe ARM Qt kit has a GStreamer plugin that Ubuntu 22.04 cannot satisfy and OCTAVE does not use. Set OCTAVE_DROP_QT_PLUGINS=multimedia/libgstreamermediaplugin.so, as the release job does.
qt-cmake says Qt was not foundQT_HOST_PATH is not set to the desktop kit.
The APK build fails downloading a dependency (HTTP 429)The download server is limiting requests. Run the build command again. The release job retries up to four times.
Gradle complains about the Java versionSomething other than JDK 17 is first on PATH. Set JAVA_HOME.
Builds break on a checkout synced between two computersA CMake build folder belongs to one machine. Give each its own, such as build-<hostname>/. Folders named build-* are ignored by git.
A release test passes but the package fails elsewhereThe test found something on the build machine that the package lacks. Test with the build machine's Qt removed from the environment, as packaging/smoke-sim.sh does.

Why It Is Built This Way

  • One pinned Qt, 6.7.3, for every package. A QML file or a deploy tool that works with one Qt version can fail with another. Changing the version means checking the kits, the QML modules, the deploy tools and the Android Gradle setup together.
  • AppImage, not a .deb. An AppImage carries the pinned Qt (Ubuntu 22.04 packages 6.2, which cannot run OCTAVE) and keeps the QML where the program looks for it. The same script makes the ARM image for the in-car computer. There is no .deb and no Flatpak.
  • The ARM Linux package gets a release job of its own because the car's head unit is an ARM board. It should run the same build as every other platform.
  • The phone server's built file is committed. Building it needs a JDK and the Android SDK, which a desktop build otherwise does not. CI rebuilds it to prove the source still matches. It only warns on a byte difference, because two Java toolchains do not produce identical files.
  • adb is bundled; scrcpy is not used. OCTAVE speaks the mirroring protocol itself, so adb and the phone server are the only outside pieces, and both ship in the package.
  • Releases carry their own small FFmpeg. The FFmpeg from a Linux distribution or Homebrew is a GPL build with many encoders. The release jobs build a static, LGPL one with only the H.264, AAC and ALAC decoders. Windows uses vcpkg's, which is LGPL too. The aarch64 AppImage is the exception: its Qt media plugin needs Ubuntu's FFmpeg, so that is bundled as well, and NOTICE says so.
  • SQLite is compiled in rather than used through Qt's database module. That module loads its SQLite driver as a separate plugin, which a system may not have installed; then no trip is recorded.
  • One naming scheme: OCTAVE-<version>-<platform>[-<arch>].<ext>. The release job finds the files by these names.
  • A release starts as a pre-release. The files users will download are tested as published before anything is marked as the latest.
  • macOS uses a patched Qt find module, cmake/FindWrapOpenGL.cmake. Qt 6.7.3 links a system framework (AGL) that current macOS SDKs no longer have. Delete the file once the pinned Qt no longer needs it.
  • The AppImageHub listing comes from packaging/linux/com.robdegeorge.octave.metainfo.xml. Its screenshots point at README images on main, so renaming one of those breaks the listing.
