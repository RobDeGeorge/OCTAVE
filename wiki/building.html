Running from Source

How the Python backend is run: setup.py, the venv, requirements.txt, per-platform notes, the phone-mirror helpers, ruff and pytest, and the GitHub Actions lint / test jobs. There is no build or packaging step.

Quick Start

The Python backend (backend/ + main.py) runs straight from a checkout. Nothing is compiled and nothing is packaged: there is no installer, no PyInstaller spec and no wheel.

python setup.py              # create ./venv, install requirements.txt, launch main.py (installs distro packages on Linux via sudo)
python setup.py --no-run     # same setup, print the run instructions, don't launch

# Afterwards
source venv/bin/activate      # Windows: venv\Scripts\activate
python main.py               # normal run
python main.py --debug       # DEBUG logging + octave-debug.log

Without setup.py the equivalent is a venv of your own plus pip install -r requirements.txt, then python main.py.

Requirements & Dependencies

  • Python 3.10 or newer. pyproject.toml declares requires-python = ">=3.10" with no upper cap, and setup.py exits with Python 3.10+ required below that. CI runs Python 3.11.
  • A display. main.py creates a QApplication and loads frontend/Main.qml; headless runs need QT_QPA_PLATFORM=offscreen (as the tests use).
  • Platforms: Linux (including Raspberry Pi / Orange Pi), Windows and macOS. The backend is desktop-only; there is no Android or iOS path.

What setup.py Does

  1. Console encoding — if stdout is not UTF-8 (cp1252 on Windows) it reconfigures stdout/stderr to UTF-8 with errors="replace" so the ✓ / ✗ / → glyphs print.
  2. chdir into the checkout, then detect the platform: macos, windows, raspberry (Linux whose /sys/firmware/devicetree/base/model contains "raspberry") or linux, plus WSL (microsoft in /proc/version).
  3. Python version check — exit 1 below 3.10.
  4. System packages (Linux and Raspberry Pi only) — detects the distro family from /etc/os-release (falling back to whichever of pacman / apt / dnf/yum exists) and installs the Qt runtime libraries with sudo: pacman -S --needed --noconfirm on Arch / Manjaro / EndeavourOS, dnf install -y on Fedora / RHEL / CentOS / Rocky, and apt update + apt install -y on Debian / Ubuntu / Mint / Pop!_OS and anything unrecognised. The install command's exit status is ignored, so a package missing on your release does not stop setup. macOS and Windows install nothing here.
  5. venv at <checkout>/venv. An existing one is kept only if pyvenv.cfg exists, was written on the same OS family (it looks for C:\ in the file to tell a Windows venv from a Linux/macOS one) and its pip --version runs. Otherwise it is removed with shutil.rmtree(..., onexc=...); if removal fails the folder is renamed to venv_old_<timestamp>. A new venv is created with venv.create(..., with_pip=True); on failure it suggests python3-venv (Debian) or python (Arch).
  6. Python packages — pip install --upgrade pip, then pip install -r requirements.txt; a failure there exits 1.
  7. Launch — unless --no-run was passed, os.execvs the venv's Python on main.py with no extra arguments. Under WSL with neither DISPLAY nor WAYLAND_DISPLAY set it prints display guidance and skips the launch.
onexc needs Python 3.12
The onexc= keyword of shutil.rmtree was added in Python 3.12. On 3.10 and 3.11 the call raises TypeError, which setup.py catches like any other removal failure, so an invalid venv is renamed to venv_old_<timestamp> instead of deleted. Remove those folders by hand.

Running main.py

main.py parses its flags with argparse.parse_known_args, so Qt's own command-line options pass through untouched.

FlagEffect
--debugThe octave logger and console go to DEBUG, and octave-debug.log is written (see Logging).
--profileCalls setup_perf_profiling() after Main.qml loads: performance monitor, command server on 127.0.0.1:9876 and method instrumentation — each only if its developer-local module is present (see below).
--smokeLoads Main.qml, logs Smoke test: Main.qml loaded, exiting in 5 s, and exits with code 0 five seconds later.

QML and assets are always loaded from frontend/ next to main.py (resolved from __file__), so main.py can be started from any working directory. main.py exits with -1 if Main.qml produced no root object. Developer mode (simulated car, keyboard controls) is python -m dev.main_dev, which needs the developer-local dev/ tree; see Development.

Linux & Raspberry Pi

Linux
  • setup.py installs the X11/XCB, EGL/GL, PulseAudio/ALSA, fontconfig/freetype/harfbuzz and D-Bus runtime libraries listed in install_linux_deps(); on Arch and Fedora it also installs the distro's qt6-base/qt6-multimedia (Arch) or qt6-qtbase/qt6-qtmultimedia (Fedora). PySide6 itself always comes from pip.
  • A Raspberry Pi is detected separately but set up exactly like any other Linux machine. Other boards (Orange Pi) are plain linux.
  • I²C sensors need smbus2 (installed only on Linux), an enabled bus (the managers open bus 2) and membership of the i2c group; serial devices (OBD, ESP32) need the dialout group. See Troubleshooting.
  • The Bluetooth OBD adapter finder talks to BlueZ over D-Bus and the direct rfcomm:// transport uses Bluetooth sockets; both are Linux-only.

Windows

Windows
  • Use a 64-bit Python 3.10+. setup.py installs no system packages.
  • The venv's interpreter is venv\Scripts\python.exe; you can run .\venv\Scripts\python.exe main.py without activating.
  • No I²C (smbus2 is not installed). Android Auto's Desktop Head Unit window is embedded with Win32 calls, so it works only on Windows.

macOS

macOS
  • setup.py prints "system dependencies should be available" and installs nothing beyond the pip requirements.
  • On Apple Silicon use a native arm64 Python so pip installs arm64 PySide6 / PyAV wheels.
  • No I²C and no Android Auto embedding.

Phone Server Jar & adb

Phone mirroring needs three things, which phoneMirrorManager.nativeAvailable checks: PyAV importable, the phone-server jar, and an adb binary. getInstallInstructions() names whichever is missing.

  • The phone server — phone_server/ is OCTAVE's fork of the scrcpy server (Java, Apache-2.0, forked at v3.3.4, package org.octave.phoneserver). The prebuilt jar tools/phone-server/octave-phone-server is committed, so a checkout needs no Java toolchain; backend/phone_mirror/scrcpy_client.py looks for it there (or in phone-server/ beside the checkout root) and pushes it to /data/local/tmp/octave-phone-server.jar each session. The client's SERVER_VERSION is 3.3.4-octave, which must equal SCRCPY_VERSION_NAME in phone_server/build_without_gradle.sh; the server refuses a mismatch. Rebuilding the jar after editing phone_server/src needs a JDK and the Android SDK (platforms;android-36, build-tools;36.0.0): ANDROID_HOME=~/Android/Sdk ANDROID_PLATFORM=36 ANDROID_BUILD_TOOLS=36.0.0 bash phone_server/build_without_gradle.sh, then copy the result over tools/phone-server/octave-phone-server.
  • adb — python scripts/fetch_platform_tools.py downloads Google's platform-tools 37.0.1, verifies the SHA-256 recorded in the script and extracts adb into tools/platform-tools/<linux|windows|darwin>/ (gitignored). The phone-mirror manager tries that bundled copy first, then adb on PATH, then the usual SDK and system locations (~/Android/Sdk/platform-tools/adb, /usr/bin/adb, /usr/local/bin/adb; the SDK and Program Files paths on Windows), preferring the first one new enough for wireless pairing (platform-tools 30+). Google publishes no aarch64 Linux build, so on ARM boards install an adb yourself.

Developer-Local Files

.gitignore excludes backend/perf_monitor.py, backend/perf_patches.py and backend/command_server.py (under "Performance profiling (lives in dev/perf/)"), the whole top-level /dev/ tree (dev mode, mocks, screenshot and MCP tooling) and .mcp.json. They exist only on the developer's machines and are not in a fresh clone. A normal python main.py never imports them; --profile imports each one inside a guard and logs a warning when it is missing. python -m dev.main_dev does not work without dev/. See Utilities and Development.

Lint & Tests

source venv/bin/activate
pip install ruff pytest            # not in requirements.txt; CI pins ruff==0.15.10

ruff check .                       # full ruleset (CI treats this as advisory)
ruff check . --select E722,F821    # the two rules CI enforces: bare except, undefined name

QT_QPA_PLATFORM=offscreen pytest tests/            # headless test suite
pytest tests/ --collect-only -q                    # list the current tests
QT_QPA_PLATFORM=offscreen python -c "import main"  # quick check: runs main.py's module-level startup (every manager) without loading QML

ruff is configured in pyproject.toml: line length 120, target py310, rule sets E, F, W, B (bugbear), UP (pyupgrade) plus E722, with E501, E402, F401, B008 and UP007 ignored; venv, dev, tools, wiki, build directories and the vendored backend/phone_mirror/qrcodegen.py are excluded.

pytest: tests/conftest.py defaults QT_QPA_PLATFORM=offscreen and QT_QUICK_CONTROLS_STYLE=Basic (setdefault, so an exported value wins), puts the repository root on sys.path, provides a session-scoped qapp fixture, and runs gc.collect() on the main thread after every test (leftover QObjects collected on a worker thread used to crash PySide6 6.12 in QTimerInfoList::activateTimers). GitHub Actions CI

.github/workflows/build.yml ("Build OCTAVE") runs on every push and pull request to main, on v* tags and on manual dispatch. Two of its jobs concern the Python backend; they are independent of each other.

JobRunnerSteps
lintubuntu-22.04Python 3.11; pip install ruff==0.15.10; ruff check . || true (full ruleset, warn-only, "legacy noise"); then ruff check . --select E722,F821, which fails the job.
testubuntu-22.04Python 3.11; apt-get install libxcb-xinerama0 libxcb-cursor0 libxkbcommon0 libgl1-mesa-glx libegl1 libpulse0; pip install -r requirements.txt and pytest; then pytest tests/ -v with QT_QPA_PLATFORM=offscreen.

No job builds, packages or releases anything from the Python tree.

Design Decisions

No build pipeline

The Python backend is meant for tinkering and hardware work from a checkout, where editing a file and restarting is the whole loop. A PyInstaller pipeline existed once and was removed; CLAUDE.md on this branch says not to reintroduce build_scripts/build.py, octave.spec, requirements-build.txt or per-platform build_*.{sh,bat} wrappers. Python-on-Android (buildozer / python-for-android) was removed as well.

One script that installs and launches

setup.py exists so a fresh machine needs one command: it checks the interpreter, pulls the Qt runtime libraries a pip-installed PySide6 still needs on Linux, builds the venv and execvs the app. Package-manager failures are tolerated because package names differ between releases of the same distro.

Rebuilding the venv on a mismatch

A venv created on one OS does not run on another (for example in a checkout synced between a Linux and a Windows machine), and a damaged venv can have a broken pip, so setup.py tests both and recreates the venv rather than failing later inside pip.

Lint as a warning, two rules as a gate

The full ruff ruleset reports legacy findings, so CI runs it without failing (|| true) and enforces only E722 (bare except) and F821 (undefined name), the two that indicate real bugs.

A boot test, not only unit tests

tests/test_boot.py starts the real main.py because "import-level and manager probes cannot catch a missing method that only a startup path calls (a removed no-op slot once broke boot while every unit-level check passed)".

Setup Troubleshooting

setup.py recreates the venv every run

Its pyvenv.cfg was written on the other OS family, or pip --version fails. Keep one venv per machine, or use a clone that is not synced between operating systems. Leftover venv_old_* folders come from the rename fallback above.

PySide6 fails to install

Check the interpreter is 64-bit and 3.10 or newer, run pip install --upgrade pip setuptools wheel inside the venv and retry.

"Could not load the Qt platform plugin "xcb""

Missing X11/XCB libraries on Linux. Re-run python setup.py --no-run (it installs them with sudo) or install the Debian list from install_linux_deps() by hand; see Troubleshooting → Display.

The wiki reader or the 3D view is unavailable

The PySide6 install lacks QtWebEngineQuick (then wikiViewerAvailable is false) or Qt Quick 3D (the "3D View" card is greyed out). Both are optional.

WSL: setup finishes but nothing launches

setup.py skips the launch when neither DISPLAY nor WAYLAND_DISPLAY is set; see Troubleshooting → WSL.

--profile does nothing on a fresh clone

Expected: the profiling modules are developer-local (above). The log says --profile: backend/perf_monitor.py not present (gitignored dev tooling), skipping performance monitor and command server.
