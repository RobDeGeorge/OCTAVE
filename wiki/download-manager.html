Overview

The DownloadManager lets the user search YouTube Music from the head unit and save songs into the local media library, where MediaManager picks them up. It is registered as the QML context property downloadManager and driven by frontend/DownloadPage.qml. The two backends reach the same result with different machinery:

  • Python (backend/download_manager.py) wraps the vendored music_dl engine (backend/music_dl/, a trimmed fork of spotdl) that drives yt-dlp and ffmpeg as Python libraries.
  • C++ (src/managers/downloadmanager.{h,cpp}) spawns the yt-dlp executable with QProcess, runs a small Python helper (scripts/ytmusic_search.py) for search, and tags files with TagLib. On Android the same class talks to the youtubedl-android runtime over JNI.
No Spotify Credentials Required
Search goes to YouTube Music (ytmusicapi) on both backends, so Spotify credentials are optional. When they are present, the Python engine additionally resolves pasted Spotify track/album/playlist URLs to songs with full Spotify metadata (ISRC-aware matching). The C++ backend has no Spotify path at all.

The music_dl Engine (Python)

backend/music_dl/ is OCTAVE's fork of spotdl (__version__ = "4.4.3" in _version.py; MIT licence, copyright 2021 spotDL Developers, kept in backend/music_dl/LICENSE). The fork strips the CLI, the web UI and the Rich terminal progress bars: download/progress_handler.py is a "callback-based progress handler" that invokes a function instead of drawing a TUI, and the only audio provider left is providers/audio/ytmusic.py (DOWNLOADER_OPTIONS["audio_providers"] = ["youtube-music"] in utils/config.py). Commit 5fec05d removed Pillow, python-slugify, typing_extensions and text-unidecode from the dependency lists.

Entry Point: MusicDL Class

class MusicDL:
    def __init__(self, client_id, client_secret, user_auth=False, cache_path=None,
                 no_cache=False, headless=False, downloader_settings=None):
        # Initialize spotify client only if credentials are provided
        self.has_spotify = bool(client_id and client_secret)
        if self.has_spotify:
            SpotifyClient.init(client_id=client_id, client_secret=client_secret, ...)
        self.downloader = Downloader(settings=downloader_settings)

    def search(self, query):          # List[str] -> List[Song]   (parse_query)
    def download(self, song):         # -> Tuple[Song, Optional[Path]]
    def download_songs(self, songs):  # -> List[Tuple[Song, Optional[Path]]]
    def cleanup(self):                # SpotifyClient.reset() when used

Settings passed by DownloadManager

_ensure_music_dl() builds the engine on first use with these downloader_settings (every other key is filled from DOWNLOADER_OPTIONS in utils/config.py):

downloader_settings = {
    "output": os.path.join(download_path, "{artists} - {title}.{output-ext}"),
    "format": dl_format,          # downloadFormat setting, default "mp3"
    "bitrate": bitrate,           # downloadBitrate setting, default "auto"
    "threads": 2,
    "overwrite": "skip",
    "_progress_callback": self._on_download_progress,
}
if cookies_path:
    downloader_settings["cookie_file"] = cookies_path

The Downloader constructor pops _progress_callback before validating the settings against the known option keys and installs it as the progress handler's update_callback.

yt-dlp, ytmusicapi and TagLib (C++)

Finding yt-dlp

_findYtDlp() caches its answer. It checks PATH first (QStandardPaths::findExecutable), then the application directory, /usr/local/bin, /usr/bin and ~/.local/bin (yt-dlp.exe variants on Windows). When nothing is found, search() and download_song() emit "yt-dlp not found. Please install yt-dlp." On Android it returns the sentinel jni://yt-dlp.

Search helper

Search runs scripts/ytmusic_search.py -- looked up at <appdir>/../scripts/ (dev build) or <appdir>/scripts/ -- with the project venv/bin/python3 when present, otherwise python3 from PATH. The script calls YTMusic().search(query, filter="songs", limit=25) and prints one JSON object per line in the format _parseSearchOutput() expects. If the script or interpreter is missing, the manager falls back to yt-dlp --dump-json --flat-playlist --no-download ytsearch25:<query>, which the source comment describes as returning "generic YouTube videos (wrong thumbnails, uncurated results)".

Tagging

On desktop, TagLib writes title / artist / album through TagLib::FileRef, then the cover is fetched with QNetworkAccessManager and embedded per container: ID3v2 APIC for mp3, the covr atom for m4a/mp4, a PICTURE block for flac, and METADATA_BLOCK_PICTURE in the Xiph comment for ogg/opus. MIME type is sniffed from the bytes (PNG / RIFF-WebP / JPEG). TagLib is not linked on mobile (#ifndef Q_OS_MOBILE).

Search Flow

downloadManager.search(query) is called from the on-screen keyboard's search field. Both backends emit isSearchingChanged(true), searchInProgress(true) and statusMessage("Searching: …"), reset pagination state, and end with searchResults(jsonArray).

Text Queries

  1. Prepare the engine -- Python lazily builds MusicDL (_ensure_music_dl()) on the first call, reading Spotify credentials and the cookies file at that moment; C++ resolves the yt-dlp path and kills any search still running.
  2. YouTube Music search -- Python: get_ytm_client().search(query, filter="songs", limit=20) on an executor thread. C++: the helper script with limit 25 (or the yt-dlp fallback), asynchronously via QProcess; on Android QtConcurrent::run around runYtMusicSearch(query, 25).
  3. Normalise results -- each entry becomes {name, artist, artists, album_name, duration (s), year, cover_url, url, song_id, explicit, track_number, disc_number}, with url = https://music.youtube.com/watch?v=<videoId> and song_id = the video ID. Python parses the M:SS / H:MM:SS duration string; the C++ parser reads duration, channel/uploader/artist/creator, the last (largest) thumbnail, album, and release_year or the year of upload_date.
  4. Upgrade cover art -- YouTube Music thumbnails are 120 px; Google CDN URLs are rewritten to 800×800 on both backends: 
    if cover_url and "lh3.googleusercontent.com" in cover_url:
    cover_url = re.sub(r"=w\d+-h\d+.*$", "=w800-h800-l90-rj", cover_url)
  5. Mark downloaded -- _mark_downloaded() / _markDownloaded() tags entries that already exist in the library with is_downloaded: true and their downloaded_playlist folder (see Duplicate Detection).
  6. Emit -- the JSON array goes out on searchResults and statusMessage("Showing N result(s)"); the QML keeps the parsed array as its ListView model.

Spotify URL Queries (Python only)

If the query contains open.spotify.com or spotify.link and the engine has Spotify credentials, _do_search() calls MusicDL.search([url]), which resolves the track, album or playlist into Song objects (ISRC included) and converts them with _song_dict_to_result(). Without credentials the URL is sent to YouTube Music as plain text.

Pagination
ytmusicapi has no offset parameter, so everything arrives in one batch and search is single-page on both backends. The search_more() slot (and the C++ alias next_search_page()) still exists and only emits statusMessage("All results shown"), but DownloadPage.qml no longer has a "Load More Results" footer or a hasMoreResults property, so nothing calls it.

Download Pipeline

Tapping a result calls download_song(JSON.stringify(modelData)); the error popup's "Retry" button calls it again with the same JSON. Both backends key everything by song_id so retries and duplicate taps are recognised.

Python

  1. Parse and de-duplicate -- the JSON is decoded; a pending future whose key ends in _<song_id> means "Already downloading". Any prior is_failed / error_message patch is cleared so the row shows the retry immediately.
  2. Announce -- statusMessage("Queuing download: …"), downloadStarted(song_id, "Artist - Title"), activeDownloads += 1.
  3. Build the Song on the executor -- Song.from_url() for a Spotify URL (needs credentials), otherwise Song.from_missing_data(**song_data) with the YouTube Music URL set as download_url so the downloader skips its own search.
  4. Download, convert, tag -- MusicDL.download(song): yt-dlp fetches to a temp directory, ffmpeg converts to the target format (skipped when the source already matches, e.g. m4a→m4a), mutagen embeds tags, cover and lyrics, and the file is moved to the output template.
  5. Resolve -- the 200 ms poll timer sees the finished future and emits downloadComplete(song_id, path) plus an is_downloaded = true patch, or downloadError(song_id, name, "Download failed — no audio source found") plus is_failed / error_message patches. Exceptions raised by the job surface as downloadError with the exception text.

download_from_url(url) (Python only) resolves an album or playlist URL with MusicDL.search() and batch-downloads with download_songs(), reporting "Downloaded N/M song(s)".

C++

  1. Parse and de-duplicate -- a DownloadTask already in queued / downloading state means "Already downloading"; a previous failure is cleared. The url defaults to the YouTube Music URL for the ID.
  2. Queue -- the task is stored in m_downloadTasks, appended to m_downloadQueue, and downloadStarted / downloadQueueChanged / activeDownloadsChanged fire. activeDownloads counts queued plus running tasks.
  3. Start -- _startNextDownload() launches processes while fewer than m_maxConcurrentDownloads (2) are running: 
    yt-dlp -f "bestaudio[ext=m4a]/bestaudio/best" --no-playlist --newline --no-warnings
       [--extract-audio --audio-format mp3|flac|opus|vorbis [--audio-quality <bitrate>]]
       [--cookies <DownloadLocation>/youtube_cookies.txt]
       -o "<downloadPath>/%(artist,uploader)s - %(title)s.%(ext)s"
       https://music.youtube.com/watch?v=<id>
    The conversion flags are added for mp3 (with --audio-quality unless the bitrate is auto or disable), flac, opus and ogg; m4a downloads natively. The source comment explains the template: %(artist,uploader)s falls back to the uploader when YouTube Music's artist field is missing, and the "Artist - Title" shape matches the Python engine so mediaManager.play_downloaded_song() finds files written by either backend.
  4. Finish -- on exit code 0 the last Destination: line in stdout gives the file path (falling back to the newest audio file in the download directory). Desktop then runs _embedMetadata() and _downloadCoverArt(); Android runs runEmbedCover(). downloadComplete, statusMessage("Downloaded: …") and an is_downloaded patch follow. A non-zero exit yields "Download failed (exit code N)"; a missing file yields "Download completed but file not found".

The C++ class also exposes queue control that Python lacks: cancel_download() (kills the process and emits downloadError(…, "Download cancelled")), pause_download() / resume_download() (SIGSTOP / SIGCONT on Unix; kill-and-requeue on Windows; no-ops through the JNI bridge), get_download_queue() and clear_download_queue(). None of these are called by the current QML.

Library refresh

Both entry points connect downloadComplete to a non-resetting MediaManager.scan_library() so the new file appears in the playlist view without a manual rescan.

Progress Reporting

downloadProgress(song_id, fraction) carries a 0.0-1.0 value on every backend; the sources differ.

Python worker thread Python main thread | | | SongTracker.update() | | -> _on_download_progress() | | push (song_id, p/100) | | under _progress_lock | | QTimer 200 ms _poll_futures() | drain _progress_updates | emit downloadProgress(song_id, 0.0-1.0) | resolve finished futures C++ desktop C++ Android yt-dlp --newline stdout JNI call blocks a QThread; no stdout until done readyReadStandardOutput m_mobileProgressPoller (250 ms) regex \[download\]\s+(\d+\.?\d*)% OctaveAndroid::pollProgress() / 100 emit per matching line broadcast to every running task, monotonic
  • Python: the tracker's progress is 0-50 while yt-dlp downloads (downloaded_bytes / total_bytes * 50), 50 during conversion, 95 while tags are written and 100 at the end; _on_download_progress() divides by 100.
  • C++ desktop: only yt-dlp's own [download] percentage is parsed, so the bar reaches 100% before conversion and tagging happen.
  • C++ Android: the AAR's ProgressFn stores one static percentage; the poller divides by 100 (the comment notes the UI rendered "10000%" before that) and never lets a task's value regress.

In-Place Status Patching

Instead of re-sending the whole result array, the manager emits downloadStatusChanged(song_id, field, value_json) for is_downloaded, is_failed, error_message and (C++) status. Python serialises the value with json.dumps; C++ wraps it in a one-element QJsonArray and strips the brackets so booleans, numbers, strings and null all arrive as valid JSON. The QML handler JSON.parses it, patches the matching row, re-assigns the array and restores contentY so the list does not jump.

Android Specifics

Android is C++-only. The relevant pieces live in src/platform/androidprocessadapter.h, src/platform/androidmediabridge.h and android/src/org/octave/app/OctaveMediaBridge.java.

  • Runtime: the youtubedl-android 0.18.1 AAR bundles Python 3.12, yt-dlp and ffmpeg. OctaveMediaBridge.init() initialises both, extracts the ytmusicapi bundle, and kicks off the yt-dlp self-update (below).
  • Process adapter: AndroidProcessAdapter mimics enough of QProcess (start, finished, readAllStandardOutput, kill) that downloadmanager.cpp compiles unchanged via the YtDlpProcess typedef. The JNI call blocks a dedicated QThread and delivers the combined output only at the end; kill() merely flags the thread to suppress its final signal (the AAR has no cancellation hook), and processId() returns 0 so pause/resume are no-ops.
  • Argument marshalling: runYtDlp() splits the flag list into (flag, value) pairs by treating any URL-looking argument as positional, then feeds a YoutubeDLRequest to YoutubeDL.getInstance().execute().
  • Extra yt-dlp flags: --embed-metadata --add-metadata, and for m4a --extract-audio --audio-format m4a (an AAC→m4a rewrap, "no re-encode, no quality loss", needed so the metadata post-processors actually run), plus --extractor-args youtube:player_client=android_vr,ios,tv_embedded,android -- the comment records that YouTube's bot detection is per-video and per-time, so cycling clients and yt-dlp's own retries recover most attempts.
  • Search bundle: the AAR's Python has no pip, so scripts/build-android-pylib-bundle.sh packs ytmusicapi and its pure-Python dependencies into android/assets/python-packages/ytmusic-bundle.zip; the bridge extracts it to filesDir/pylibs/ on first launch (marker .pybundle-v1) and runs ytmusic_search.py with PYTHONPATH pointing there. Commit 3fb687c added the bundle build to the CI Android job after released APKs shipped without it and search "silently failed".
  • yt-dlp self-fetch: the AAR's built-in updateYoutubeDL() is broken on Android (commons-io's Java7Support static initialiser NPEs because getClassLoader() returns null), so its bundled yt-dlp snapshot would go stale. Commit 09f0358 added directDownloadYtDlp(): on a background thread at init it downloads https://github.com/yt-dlp/yt-dlp/releases/latest/download/yt-dlp (the zipapp), sanity-checks the size and shebang, and atomically replaces noBackupFilesDir/youtubedl-android/yt-dlp/yt-dlp. The AAR reads that path on every execute(), so the next download uses the new version. Best-effort and non-fatal.
  • Thumbnails and covers: the APK ships without Qt's OpenSSL backend, so QML cannot load https images. _parseSearchOutput() routes each cover through OctaveAndroid::cacheHttpImage() (Java HttpURLConnection) and substitutes a file:// URL. After download, runEmbedCover() runs scripts/embed_cover.py (mutagen, present in the AAR's site-packages) to replace yt-dlp's 16:9 YouTube thumbnail with that square cover -- the AAR's ffmpeg is a stripped build without video filters, so it cannot crop.
  • Where files land: see Download Path.

YouTube Bot Wall, Cookies and VPNs

As of 2026 YouTube answers many yt-dlp requests with "Sign in to confirm you're not a bot". Commit b25a14a added the same zero-UI bypass to both backends: if a Netscape-format cookies file exists at QStandardPaths::DownloadLocation + "/youtube_cookies.txt", it is handed to yt-dlp.

PlatformPath
Linux / macOS~/Downloads/youtube_cookies.txt
Windows%USERPROFILE%\Downloads\youtube_cookies.txt

  • C++ checks _getYoutubeCookiesPath() for every download and appends --cookies <path>; when absent it logs where to drop the file.
  • Python passes cookie_file (yt-dlp's cookiefile) when _ensure_music_dl() builds the engine, and _refresh_cookies_file() re-checks the path before every download_song() / download_from_url(), pushing it into the live downloader's settings and audio providers -- a file added mid-session is used by the next download, no reset_engine() or restart needed. It logs "Using YouTube cookies from ..." or where to drop the file, like C++.

The README's troubleshooting entry (added in the same commit) positions VPNs as the usual cause -- YouTube blocklists most shared VPN exit IPs -- with cookies as the fallback for users who cannot leave the VPN: export with the "Get cookies.txt LOCALLY" browser extension while logged in to YouTube and save under the name above; the next download picks it up. There is no in-app indication that the file was found; an in-app picker is parked in TODO/yt-cookies-file-picker.md.

Download Path & Playlist Targeting

Downloads are written into a subfolder of the media library:

# mediaFolder / subfolder / "Artist - Title.<ext>"
download_path = os.path.join(media_folder, subfolder)

The subfolder is, in priority order:

  • the runtime override set by set_download_playlist(name) -- MediaPlayer.qml, MediaRoom.qml and the Download page's playlist picker call it whenever the user selects a playlist, so a download lands in the playlist currently being viewed; an empty name clears the override;
  • otherwise the downloadSubfolder setting (default "Downloads").

get_download_playlist() returns the effective name and the downloadPath property returns the full directory (declared CONSTANT; it is evaluated when read). The directory is created on demand. Python also rewrites the live engine's output template when the override changes.

Path Traversal Protection
Python validates the subfolder with is_safe_path() from backend/media_manager.py (realpath containment); C++ compares QDir::cleanPath of the target against the canonical media folder. A subfolder that escapes the media folder falls back to "Downloads" with a warning.

Android storage

On Android the media folder comes from the settings only when the app holds All files access (MANAGE_EXTERNAL_STORAGE, declared in android/AndroidManifest.xml and checked with Environment.isExternalStorageManager()); then POSIX writes into /storage/emulated/0/Music/… work and downloads show up in any file explorer. Otherwise _getDownloadPath() uses getExternalFilesDir("Music") (Android/data/org.octave.app/files/Music), which is scoped-storage-safe but hidden from most explorers. _getDownloadedFiles() scans both roots so is_downloaded tagging sees files wherever they live. hasStorageAccess() / requestStorageAccess() are exposed to QML (the latter opens Android's per-app "All files access" settings screen, since this permission has no runtime dialog). DownloadPage.qml routes every download (result row and the error-popup retry) through its startDownload(songJson) function: on Android, when hasStorageAccess() is false it calls requestStorageAccess(), sets the status text to "Grant \"All files access\" in the settings screen, then tap download again" and returns; otherwise (and always on Python and desktop C++, where access is unconditional) it calls download_song(). Commit d751c9d introduced the storage split so downloads "land in the user-picked folder".

Duplicate Detection

Search results are checked against existing files so the row can show "already in <playlist>" and offer click-to-play instead of a second download. The expected stem "Artist - Title" is sanitised the same way the Python engine sanitises filenames: 

@staticmethod
def _sanitize_for_match(text: str) -> str:
    # Mirror sanitize_string from music_dl/utils/formatter.py
    text = "".join(c for c in text if c not in "/?\\*|<>")
    text = text.replace('"', "'").replace(":", "-")
    return text.lower()

_get_downloaded_files() / _getDownloadedFiles() walk the whole media library and map each lower-cased audio stem to its folder name (root-level files map to "Unsorted"); if the walk finds nothing (fresh install), the configured download folder is probed directly. Python recognises .mp3 .flac .ogg .opus .m4a; C++ additionally treats .mp4 as audio because yt-dlp names YouTube's m4a streams with that extension.

Why m4a on Android
YouTube's bestaudio[ext=m4a] stream is AAC in an MP4 container and can be saved as-is, so no ffmpeg transcode is needed, and TagLib is not available on mobile -- yt-dlp's own --embed-metadata plus the mutagen cover pass do the tagging instead.

App-Store Builds

CMakeLists.txt declares option(OCTAVE_ENABLE_DOWNLOADS "Enable music download feature (disable for app store builds)" ON) and forwards it as a compile definition. The comment above it states the reason: yt-dlp is forbidden on the Apple, Microsoft and Play stores. Configure with -DOCTAVE_ENABLE_DOWNLOADS=OFF and downloadmanager.h compiles a stub class with the same properties, signals and slots: search() emits searchError("Downloads disabled in this build"), download() / download_song() emit the same text through downloadError, everything else is a no-op and get_download_playlist() returns "Downloads". The whole downloadmanager.cpp is wrapped in #ifdef OCTAVE_ENABLE_DOWNLOADS. The Python backend has no equivalent switch because it is never packaged.

Design Decisions

YouTube Music search instead of plain YouTube search

Both backends deliberately query ytmusicapi rather than yt-dlp's ytsearch. The C++ source states why: ytsearch "returns generic YouTube videos (wrong thumbnails, uncurated results)", whereas ytmusicapi returns songs with real album art -- and on Android it answers in "~1-2s" instead of spinning up yt-dlp. The desktop C++ build reuses the same script through python3 so the two backends produce identical result rows; the yt-dlp path survives only as a fallback.

Song IDs as the identity, patches instead of re-emits

Commit 9573c7b reworked downloads "to use unique song IDs instead of display names": every signal and every internal map is keyed by the YouTube video ID, so two results with the same title cannot collide and a retry addresses the same row. The downloadStatusChanged patch signal exists so a status flip does not rebuild the QML ListView (source comment: "patch without full re-emit"), and the QML side restores the scroll position for the same reason.

Main-thread signal emission via a poll timer (Python)

music_dl runs on worker threads and its progress callback fires there. Rather than emitting Qt signals across threads, the callback appends to a locked list and a 200 ms QTimer drains it on the main thread -- the constructor comment calls this "Windows-safe signal emission". The timer is only running while work is pending.

Lazy engine initialisation

MusicDL is built on the first search or download, not at startup, because it may initialise a Spotify client and reads settings that can still change; reset_engine() exists so a credential change can force a rebuild without restarting (the cookies file alone no longer needs it -- it is re-read per download).

A shared filename contract

The Python engine's {artists} - {title}.{output-ext} template and the C++ %(artist,uploader)s - %(title)s.%(ext)s template are kept equivalent on purpose (comment in _startNextDownload()): the shared QML and MediaManager.play_downloaded_song() match files by an "artist - name" stem, so a library written by one backend must be readable by the other.

QProcess-shaped JNI adapter (Android)

Instead of forking downloadmanager.cpp for mobile, AndroidProcessAdapter reproduces the subset of QProcess the manager uses and is swapped in through a typedef. Its header lists the trade-offs honestly: no stdin, no live stdout, and a "kill" that only suppresses the final signal -- "acceptable for MVP". The separate 250 ms progress poller exists precisely because that adapter cannot stream progress.

Zero-UI cookies bypass

The cookies file is auto-detected at one canonical path "so there's no setting/UI churn" (C++ comment). It is "universal, user-accessible, no permissions needed beyond what's already granted for downloaded music" (TODO/yt-cookies-file-picker.md), and it ships identically on both backends. The README steers users to fix the VPN first because that is the common cause.

Bypassing the AAR updater on Android

YouTube's bot detection "rotates faster" than youtubedl-android releases, and the AAR's own updater crashes on Android, so the bridge fetches the latest yt-dlp zipapp from GitHub itself and overwrites the file the AAR executes. It runs on a background thread, tolerates every failure, and takes effect on the next download.

Downloads as a build option

App stores forbid yt-dlp-based downloading, so the feature is a CMake option rather than a runtime setting: the stub keeps every QML binding valid while the binary contains no download code, which is what the store review requires. Default is ON for sideload and desktop builds.
