Overview

The DownloadManager lets the user search YouTube Music from the head unit and save songs into the local media library, where MediaManager picks them up. It is registered as the QML context property downloadManager and driven by frontend/DownloadPage.qml. It is defined in src/managers/downloadmanager.{h,cpp}, with the process-free helpers (search-output parsing, library scan, download staging) in src/managers/downloadutil.{h,cpp}. On desktop it spawns the yt-dlp executable with QProcess, runs a small Python helper script (scripts/ytmusic_search.py) for search, and tags files with TagLib. On Android the same class talks to the youtubedl-android runtime over JNI.

YouTube Only, No Credentials
The manager searches YouTube Music (ytmusicapi) and downloads with yt-dlp. The search path uses no configured account or API key. Downloads may require cookies when YouTube rejects an unauthenticated request.

System Architecture

Desktop:

DownloadManager (src/managers/downloadmanager.cpp) | |-- search: QProcess python3 scripts/ytmusic_search.py <query> 25 | (fallback: yt-dlp --dump-json ytsearch25:<query>) |-- download: QProcess yt-dlp ... -o "<dir>/%(artist,uploader)s - %(title)s.%(ext)s" | stdout parsed live for "[download] NN.N%" (--newline) |-- post: TagLib title/artist/album + QNetworkAccessManager cover -> APIC/covr/PICTURE | |-- QMap<songId, DownloadTask> m_downloadTasks, QQueue m_downloadQueue |-- m_maxConcurrentDownloads = 2

Android (Q_OS_MOBILE):

yt-dlp, ytmusicapi and TagLib

Finding yt-dlp

_findYtDlp() caches a successful result. It first checks a venv/ in the checkout beside or above the application directory (venv/bin/yt-dlp, or venv/Scripts/yt-dlp.exe on Windows), then PATH (QStandardPaths::findExecutable), then the application directory, /usr/local/bin, /usr/bin and ~/.local/bin (yt-dlp.exe variants on Windows). When nothing is found, search() and download() emit "yt-dlp not found. Please install yt-dlp." On Android it returns the sentinel jni://yt-dlp.

Search helper

Search runs scripts/ytmusic_search.py -- looked up at <appdir>/../scripts/ (dev build) or <appdir>/scripts/ -- with <appdir>/../venv/bin/python3 when present, otherwise python3 from PATH. The script calls YTMusic().search(query, filter="songs", limit=25) and prints one JSON object per line in the format _parseSearchOutput() expects. If the script or interpreter is missing, the manager falls back to yt-dlp --dump-json --flat-playlist --no-download ytsearch25:<query>, which the source comment describes as returning "generic YouTube videos (wrong thumbnails, uncurated results)".

Tagging

On desktop, TagLib writes title / artist / album through TagLib::FileRef, then the cover is fetched with QNetworkAccessManager and embedded per container: ID3v2 APIC for mp3, the covr atom for m4a/mp4, a PICTURE block for flac, and METADATA_BLOCK_PICTURE in the Xiph comment for ogg/opus. MIME type is sniffed from the bytes (PNG / RIFF-WebP / JPEG). TagLib is not linked on mobile (#ifndef Q_OS_MOBILE).

Search Flow

downloadManager.search(query) is called from the on-screen keyboard's search field. The manager emits isSearchingChanged(true), searchInProgress(true) and statusMessage("Searching: …"), reset pagination state, and end by resetting the searchResults model from the new hits. The previous results stay in the model while a new search runs.

Text Queries

  1. Prepare -- resolve the yt-dlp path and kill any search still running.
  2. YouTube Music search -- the helper script calls YTMusic().search(query, filter="songs", limit=25); on desktop it runs asynchronously via QProcess (or the yt-dlp fallback), on Android through QtConcurrent::run around runYtMusicSearch(query, 25).
  3. Normalise results -- each entry becomes {name, artist, artists, album_name, duration (s), year, cover_url, url, song_id, explicit, track_number, disc_number}, with url = https://music.youtube.com/watch?v=<videoId> and song_id = the video ID. The script turns an M:SS / H:MM:SS duration string into seconds; DownloadUtil::parseSearchOutput() then reads duration, channel/uploader/artist/creator, the last (largest) thumbnail, album, and release_year or the year of upload_date.
  4. Upgrade cover art -- YouTube Music thumbnails are small; Google CDN URLs are rewritten to 800×800 (by the script for lh3/yt3.googleusercontent.com, and again by the parser for lh3): 
    if (coverUrl.contains(QStringLiteral("lh3.googleusercontent.com"))) {
    static const QRegularExpression resCropRe(QStringLiteral("=w\\d+-h\\d+.*$"));
    coverUrl.replace(resCropRe, QStringLiteral("=w800-h800-l90-rj"));
}
  5. Mark downloaded -- _markDownloaded() tags entries that already exist in the library with is_downloaded: true and their downloaded_playlist folder (see Duplicate Detection).
  6. Publish -- the array is stored in m_allResults, and _publishResults() resets the searchResults model from it (one row per hit) and re-applies the state of any download still running, so a new search shows is_downloading / progress on rows already being fetched. statusMessage("Showing N result(s)") follows; the page's ListView uses the model directly.
Pagination
ytmusicapi has no offset parameter, so everything arrives in one batch and search is single-page. The search_more() slot (and its alias next_search_page()) still exists and only emits statusMessage("All results shown"), but DownloadPage.qml no longer has a "Load More Results" footer or a hasMoreResults property, so nothing calls it.

Download Pipeline

Tapping a result calls download(songId, name); the error popup's "Retry" button calls it again with the same songId. download() looks the id up in the current results (m_allResults) and queues the hit with its artist, album, cover and URL through _queueDownload(); an id that is not among the results is downloaded by id, with the given name as the title. The manager keys everything by song_id so retries and duplicate taps are recognised.

  1. Parse and de-duplicate -- a DownloadTask already in queued / downloading state means "Already downloading"; a previous failure is cleared. The url defaults to the YouTube Music URL for the ID.
  2. Queue -- the task is stored in m_downloadTasks, appended to m_downloadQueue, and downloadStarted / downloadQueueChanged / activeDownloadsChanged fire. activeDownloads counts queued plus running tasks.
  3. Start -- _startNextDownload() launches processes while fewer than m_maxConcurrentDownloads (2) are running: 
    yt-dlp -f "bestaudio[ext=m4a]/bestaudio/best" --no-playlist --newline --no-warnings
       [--extract-audio --audio-format mp3|flac|opus|vorbis [--audio-quality <bitrate>]]
       [--cookies <DownloadLocation>/youtube_cookies.txt]
       -o "<downloadPath>/.octave-partial/<songId>/%(artist,uploader)s - %(title)s.%(ext)s"
       https://music.youtube.com/watch?v=<id>
    The conversion flags are added for mp3 (with --audio-quality unless the bitrate is auto or disable), flac, opus and ogg; m4a downloads natively. The source comment explains the template: %(artist,uploader)s falls back to the uploader when YouTube Music's artist field is missing, and the "Artist - Title" shape is what filename-based matching by mediaManager.play_downloaded_song() expects; artist/title differences from the source can still prevent an exact match. On desktop yt-dlp writes into the hidden staging dir <downloadPath>/.octave-partial/<songId>/ (Android writes straight to <downloadPath>); when nothing else is in flight, a new download first sweeps leftovers from a power cut or mid-download quit out of .octave-partial/. The staging helpers, the yt-dlp search parser and the "already downloaded" library scan (which skips the hidden staging dir) live in src/managers/downloadutil.{h,cpp}, tested by tst_downloadutil.
  4. Finish -- on exit code 0 the last Destination: line in stdout gives the file path (falling back to the newest audio file in the song's staging dir). Desktop then runs _embedMetadata() and _downloadCoverArt() on the staged file; once the cover request ends (embedded or not) _finishDownload() publishes it into <downloadPath>: POSIX uses fsync and rename; Windows removes any existing destination and then renames, without an atomic replacement guarantee. Android runs runEmbedCover(). downloadComplete (on desktop now only after the cover is embedded), statusMessage("Downloaded: …") and an is_downloaded patch follow. A non-zero exit yields "Download failed (exit code N)"; a missing file yields "Download completed but file not found".

The class also exposes queue control: cancel_download() (kills the process and emits downloadError(…, "Download cancelled")), pause_download() / resume_download() (SIGSTOP / SIGCONT on Unix; kill-and-requeue on Windows; no-ops through the JNI bridge) and clear_download_queue() (cancels everything and empties the queue model). None of these are called by the current QML; the queue panel's "Clear" button calls clear_finished_downloads(), which drops complete and failed (including cancelled) rows from downloadQueue together with their tasks.

The two models

Both lists the page shows are VariantListModels (src/util/variantlistmodel.{h,cpp}): QVariantMap rows with one role per key, a count property and a get(row) invokable. A field change is one dataChanged on one row, so the ListView keeps its delegates and scroll position. The role keys are listed in the DownloadModels namespace comment at the top of downloadmanager.h.

ModelRowsRoles
searchResultsOne per search hitsong_id, name, artist, album_name, cover_url, url, duration, explicit, is_downloaded, downloaded_playlist, is_failed, error_message, file_path, plus is_downloading / progress while a download of it runs

_syncTask(songId) mirrors a DownloadTask into its downloadQueue row (appending it the first time) and into its search row (is_downloading, progress, file_path). It runs at every task state change: queue, start, progress, pause, cancel, complete and fail. tst_downloadmanager covers both models.

Library refresh

src/main.cpp connects downloadComplete to a non-resetting MediaManager.scan_library() so the new file appears in the playlist view without a manual rescan.

Progress Reporting

downloadProgress(song_id, fraction) carries a 0.0-1.0 value; where it comes from depends on the platform.

Desktop Android yt-dlp --newline stdout JNI call blocks a QThread; no stdout until done readyReadStandardOutput m_mobileProgressPoller (250 ms) regex \[download\]\s+(\d+\.?\d*)% OctaveAndroid::pollProgress() / 100 emit per matching line broadcast to every running task, monotonic
  • Desktop: only yt-dlp's own [download] percentage is parsed, so the bar reaches 100% before conversion and tagging happen.
  • Android: the AAR's ProgressFn stores one static percentage; the poller divides by 100 (the comment notes the UI rendered "10000%" before that) and never lets a task's value regress.

In-Place Status Patching

_emitStatusPatch() sets is_downloaded, is_failed, error_message and status on the matching entry in m_allResults (so a later publish keeps it) and on its searchResults row with setValue(), which emits one dataChanged for that row and role. The list is not rebuilt, so the page needs no scroll-position save and restore. Until open-backend #9 the manager emitted a downloadStatusChanged JSON patch signal that the QML parsed into a re-assigned JS array; it has been removed.

Android Specifics

The Android-specific pieces live in src/platform/androidprocessadapter.h, src/platform/androidmediabridge.h and android/src-downloads/org/octave/app/OctaveDownloadBridge.java (yt-dlp, ffmpeg, ytmusicapi; general media helpers stay in android/src/org/octave/app/OctaveMediaBridge.java).

  • Runtime: the youtubedl-android 0.18.1 AAR bundles Python 3.12, yt-dlp and ffmpeg. OctaveDownloadBridge.init() initialises both, extracts the ytmusicapi bundle, and kicks off the yt-dlp self-update (below).
  • Process adapter: AndroidProcessAdapter mimics enough of QProcess (start, finished, readAllStandardOutput, kill) that downloadmanager.cpp compiles unchanged via the YtDlpProcess typedef. The JNI call blocks a dedicated QThread and delivers the combined output only at the end; kill() merely flags the thread to suppress its final signal (this adapter does not invoke runtime cancellation), and processId() returns 0 so pause/resume are no-ops.
  • Argument marshalling: runYtDlp() splits the flag list into (flag, value) pairs by treating any URL-looking argument as positional, then feeds a YoutubeDLRequest to YoutubeDL.getInstance().execute().
  • Extra yt-dlp flags: --embed-metadata --add-metadata, and for m4a --extract-audio --audio-format m4a (an AAC→m4a rewrap, "no re-encode, no quality loss", needed so the metadata post-processors actually run). There is deliberately no player_client override: the manager leaves client selection to yt-dlp. The bridge attempts to update yt-dlp on launch; a failed update leaves the existing version in place.
  • Search bundle: the AAR's Python has no pip, so scripts/build-android-pylib-bundle.sh packs ytmusicapi and its pure-Python dependencies into android/assets/python-packages/ytmusic-bundle.zip; the bridge extracts it to filesDir/pylibs/ on first launch (marker .pybundle-v1) and runs ytmusic_search.py with PYTHONPATH pointing there. Commit 3fb687c added the bundle build to the CI Android job after released APKs shipped without it and search "silently failed".
  • yt-dlp self-fetch: the bridge source records a failure in the bundled updater's Java7Support static initialiser on Android and bypasses updateYoutubeDL(). Commit 09f0358 added directDownloadYtDlp(): on a background thread at init it downloads https://github.com/yt-dlp/yt-dlp/releases/latest/download/yt-dlp (the zipapp), sanity-checks the size and shebang, and atomically replaces noBackupFilesDir/youtubedl-android/yt-dlp/yt-dlp. The AAR reads that path on every execute(), so the next download uses the new version. Best-effort and non-fatal.
  • Thumbnails and covers: to support images even when Qt's OpenSSL backend is missing, _parseSearchOutput() routes each cover through OctaveAndroid::cacheHttpImage() (Java HttpURLConnection) and substitutes a file:// URL. After download, runEmbedCover() runs scripts/embed_cover.py (mutagen, present in the AAR's site-packages) to replace yt-dlp's 16:9 YouTube thumbnail with that square cover -- the AAR's ffmpeg is a stripped build without video filters, so it cannot crop.
  • Where files land: see Download Path.

YouTube Bot Wall, Cookies and VPNs

For download failures such as "Sign in to confirm you're not a bot", the manager supports a cookies file: if a Netscape-format cookies file exists at QStandardPaths::DownloadLocation + "/youtube_cookies.txt", it is handed to yt-dlp.

PlatformPath
Linux / macOS~/Downloads/youtube_cookies.txt
Windows%USERPROFILE%\Downloads\youtube_cookies.txt
Android/storage/emulated/0/Download/youtube_cookies.txt

_getYoutubeCookiesPath() is checked for every download, and when the file exists --cookies <path> is appended to the yt-dlp arguments; when it is absent the manager logs where to drop the file. A file added mid-session is used by the next download, no restart needed.

Supply a Netscape-format cookies file under the name above; the next download checks for it. This passes cookies to yt-dlp, but does not guarantee that YouTube will accept a request. There is no in-app indication that the file was found; an in-app picker is parked in TODO/yt-cookies-file-picker.md.

Download Path & Playlist Targeting

Downloads are written into a subfolder of the media library:

// mediaFolder / subfolder / "Artist - Title.<ext>"
QString downloadPath = QDir(mediaFolder).filePath(subfolder);

The subfolder is, in priority order:

  • the runtime override set by set_download_playlist(name) -- MediaPlayer.qml, MediaRoom.qml and the Download page's playlist picker call it whenever the user selects a playlist, so a download lands in the playlist currently being viewed; an empty name clears the override;
  • otherwise the downloadSubfolder setting (default "Downloads").

get_download_playlist() returns the effective name and the downloadPath property returns the full directory (declared CONSTANT; it is evaluated when read). The directory is created on demand.

Subfolder validation
_getDownloadPath() compares QDir::cleanPath of the target with a string prefix of the canonical media folder. A rejected target falls back to "Downloads" with a warning. The prefix comparison does not check a directory boundary or resolve symlinks in the target, so it is not full containment validation.

Android storage

On Android the media folder comes from the settings only when the app holds All files access (MANAGE_EXTERNAL_STORAGE, declared in android/AndroidManifest.xml and checked with Environment.isExternalStorageManager()); then POSIX writes into /storage/emulated/0/Music/… work and downloads show up in any file explorer. Otherwise _getDownloadPath() uses getExternalFilesDir("Music") (Android/data/org.octave.app/files/Music), which is scoped-storage-safe but hidden from most explorers. _getDownloadedFiles() scans both roots so is_downloaded tagging sees files wherever they live. hasStorageAccess() / requestStorageAccess() are exposed to QML (the latter opens Android's per-app "All files access" settings screen, since this permission has no runtime dialog). DownloadPage.qml routes every download (result row and the error-popup retry) through its startDownload(songId, songName) function, which always calls download() first: without All files access the file simply lands in the app-scoped folder, which the library scans. On Android it then shows a one-time status hint ("Saving inside OCTAVE's app folder. To download into your phone's Music folder, allow \"All files access\" for OCTAVE in Android settings"). Until v0.9.2 the first tap instead called requestStorageAccess(), jumped to the system settings page and downloaded nothing — and Android killed the backgrounded app while the user was there. Commit d751c9d introduced the storage split so downloads "land in the user-picked folder".

Duplicate Detection

Search results are checked against existing files so the row can show "already in <playlist>" and offer click-to-play instead of a second download. The expected stem "Artist - Title" is sanitised by _sanitizeForMatch(): / ? \ * | < > are dropped, " becomes ', : becomes -, and the result is lower-cased: 

QString DownloadManager::_sanitizeForMatch(const QString &text)
{
    QString result;
    for (const QChar &c : text) {
        if (c == '/' || c == '?' || c == '\\' || c == '*' ||
            c == '|' || c == '<' || c == '>')
            continue;
        if (c == '"')      result.append('\'');
        else if (c == ':') result.append('-');
        else               result.append(c);
    }
    return result.toLower();
}

_getDownloadedFiles() (via DownloadUtil::scanDownloadedFiles()) walks the whole media library and map each lower-cased audio stem to its folder name (root-level files map to "Unsorted"); if the walk finds nothing (fresh install), the configured download folder is probed directly. It recognises .mp3 .flac .ogg .opus .m4a and also .mp4, because yt-dlp names YouTube's m4a streams with that extension. The walk skips hidden directories (such as .octave-partial/), and .part staging files never match an audio extension.

Why m4a on Android
YouTube's bestaudio[ext=m4a] stream is AAC in an MP4 container and can be saved as-is, so no ffmpeg transcode is needed, and TagLib is not available on mobile -- yt-dlp's own --embed-metadata plus the mutagen cover pass do the tagging instead.

App-Store Builds

CMakeLists.txt declares option(OCTAVE_ENABLE_DOWNLOADS "Enable music download feature (disable for app store builds)" ON) and forwards it as a compile definition. It is intended for builds that omit the downloading feature. Configure with -DOCTAVE_ENABLE_DOWNLOADS=OFF and downloadmanager.h compiles a stub class that preserves the core download properties, signals and slots: search() emits searchError("Downloads disabled in this build"), download() emits the same text through downloadError, everything else (including clear_finished_downloads()) is a no-op, the searchResults and downloadQueue models exist with the same roles but stay empty, and get_download_playlist() returns "Downloads". The stub omits hasStorageAccess() and requestStorageAccess(); the QML guards those optional methods. The manager is still constructed and registered, and its downloadsAvailable property is false (true in the full class), which hides the download buttons in MediaRoom.qml and MediaPlayer.qml so a store build shows no download entry point. The whole downloadmanager.cpp is wrapped in #ifdef OCTAVE_ENABLE_DOWNLOADS.

On Android the flag also reaches Gradle: CMake writes octaveEnableDownloads=true|false to <build>/octave-android-features.properties, and android/build.gradle reads it (failing the build if it is missing). With the flag off the APK leaves out the youtubedl-android AAR, android/src-downloads/ (OctaveDownloadBridge), the assets/python-packages and assets/scripts helpers, and, through the android/store-manifest/ overlay, the MANAGE_EXTERNAL_STORAGE permission. The C++ wrappers for the download bridge (androidmediabridge.h) and androidprocessadapter.h compile out with it. The arm64 store APK is about 60 MB against 118 MB with downloads on.

Design Decisions

YouTube Music search instead of plain YouTube search

The manager deliberately queries ytmusicapi rather than yt-dlp's ytsearch. The source states why: ytsearch "returns generic YouTube videos (wrong thumbnails, uncurated results)", whereas ytmusicapi returns songs with real album art -- and on Android it answers in "~1-2s" instead of spinning up yt-dlp. Desktop runs the same script through python3, so both platforms share one result shape; the yt-dlp path survives only as a desktop fallback.

Song IDs as the identity, row patches instead of rebuilds

Commit 9573c7b reworked downloads "to use unique song IDs instead of display names": every signal and every internal map is keyed by the YouTube video ID, so two results with the same title cannot collide and a retry addresses the same row. Results and the queue are list models patched row by row, so a status flip or a progress tick is one dataChanged and does not rebuild the QML ListView or move its scroll position.

A shared filename contract

The %(artist,uploader)s - %(title)s.%(ext)s output template is fixed on purpose (comment in _startNextDownload()): MediaManager.play_downloaded_song() and the duplicate check above both match files by an "artist - name" stem, so every download must be written under that name.

QProcess-shaped JNI adapter (Android)

Instead of forking downloadmanager.cpp for mobile, AndroidProcessAdapter reproduces the subset of QProcess the manager uses and is swapped in through a typedef. Its header lists the trade-offs honestly: no stdin, no live stdout, and a "kill" that only suppresses the final signal -- "acceptable for MVP". The separate 250 ms progress poller exists precisely because that adapter cannot stream progress.

Zero-UI cookies bypass

The cookies file is auto-detected at one canonical path "so there's no setting/UI churn" (source comment). The path is derived from Qt's Downloads location; reading it still requires filesystem access, particularly for shared storage on Android.

Bypassing the AAR updater on Android

The bridge bypasses the updater failure recorded in its source comments by fetching the latest yt-dlp zipapp from GitHub and replacing the file the AAR executes. It runs on a background thread; a failed update leaves the existing version in place, while a successful update takes effect on the next download.

Downloads as a build option

The feature is controlled by a CMake option rather than a runtime setting. Turning it off compiles the manager stub instead of its implementation. This build switch does not establish compliance with any store's current policies. The CMake default is ON.
