Overview

The DownloadManager (backend/download_manager.py) lets the user search YouTube Music from the head unit and save songs into the local media library, where MediaManager picks them up. It is registered in main.py as the QML context property downloadManager and driven by frontend/DownloadPage.qml.

The work is done by the vendored music_dl engine (backend/music_dl/, a trimmed fork of spotdl). It searches with ytmusicapi, downloads with yt-dlp used as a Python library, launches the ffmpeg executable for conversion and writes tags and cover art with mutagen.

YouTube Only, No Credentials
Search uses the anonymous ytmusicapi client and needs no account or API key. Downloads may need a cookies file when YouTube rejects an unauthenticated request (see Bot Wall).

System Architecture

DownloadManager (backend/download_manager.py) | |-- MusicDL engine (lazy init on first search/download) | |-- Downloader (download/downloader.py) | | |-- providers/audio/base.py yt-dlp YoutubeDL (library call) | | |-- providers/audio/ytmusic.py YouTubeMusic (ytmusicapi, used when a song has no URL) | | |-- utils/ffmpeg.py conversion (ffmpeg subprocess) | | |-- utils/metadata.py mutagen tags + cover embedding | | |-- download/progress_handler.py callback -> _on_download_progress() | |-- utils/search.py get_ytm_client() used by DownloadManager search | |-- ThreadPoolExecutor (2 workers) search + downloads |-- QTimer _poll_timer (200 ms) drains progress list, resolves futures |-- _progress_updates + _progress_lock

Every slot runs on the GUI thread and hands the blocking work to the two-worker executor. Futures are kept in _pending_futures under the key "__search__" or "dl_<counter>_<song_id>". The 200 ms timer runs only while a future or a progress update is pending.

The music_dl Engine

backend/music_dl/ is OCTAVE's fork of spotdl (__version__ = "4.4.3" in _version.py; MIT licence, copyright 2021 spotDL Developers, kept in backend/music_dl/LICENSE). The fork strips the CLI, the web UI, SponsorBlock, lyrics providers, the non-YouTube sources and the Rich terminal progress bars: download/progress_handler.py is a "callback-based progress handler" that invokes a function instead of drawing a TUI, and the only audio provider left is providers/audio/ytmusic.py (DOWNLOADER_OPTIONS["audio_providers"] = ["youtube-music"] in utils/config.py).

Entry Point: MusicDL Class

class MusicDL:
    def __init__(self, downloader_settings=None):
        self.downloader = Downloader(settings=downloader_settings)

    def get_download_urls(self, songs):  # YouTube Music URL per song (multi-threaded)
    def download(self, song):         # -> Tuple[Song, Optional[Path]]
    def download_songs(self, songs):  # -> List[Tuple[Song, Optional[Path]]]
    def cleanup(self):                # nothing to release; kept for the shutdown path

DownloadManager only calls download() and cleanup().

Settings passed by DownloadManager

_ensure_music_dl() builds the engine on first use with these downloader_settings (every other key is filled from DOWNLOADER_OPTIONS in utils/config.py):

downloader_settings = {
    "output": os.path.join(download_path, "{artists} - {title}.{output-ext}"),
    "format": dl_format,          # downloadFormat setting, default "mp3"
    "bitrate": bitrate,           # downloadBitrate setting, default "auto"
    "threads": 2,
    "overwrite": "skip",
    "_progress_callback": self._on_download_progress,
}
if cookies_path:
    downloader_settings["cookie_file"] = cookies_path

The Downloader constructor reads _progress_callback before the settings are filtered to the known option keys and installs it as the progress handler's update_callback. The constructor also locates ffmpeg: ffmpeg on PATH, else an ffmpeg binary in the music_dl data directory. When neither exists it raises DownloaderError("ffmpeg is not installed"); _ensure_music_dl() catches that, emits statusMessage("Download engine error: ffmpeg is not installed") and leaves the engine unset, so search is unavailable too until ffmpeg is installed. A successful build emits "Download engine ready".

Working directories

get_music_dl_path() in utils/config.py is ~/.config/music_dl on Linux, ~/Library/Application Support/music_dl on macOS and ~/.music_dl elsewhere (Windows). yt-dlp downloads into its temp/ subfolder as <videoId>.<ext>; a failed ffmpeg conversion writes its command and output to errors/ffmpeg_error_<timestamp>.txt.

Search Flow

downloadManager.search(query) is called from the Download page's search field (Enter or the search button). An empty or whitespace-only query is ignored.

  1. Prepare the engine -- _ensure_music_dl() builds MusicDL on the first call, reading the download settings and the cookies file at that moment. If it fails, the search stops there.
  2. Announce -- pagination state is reset, then isSearchingChanged(true), searchInProgress(true) and statusMessage("Searching: …") are emitted.
  3. YouTube Music search -- _do_search() on an executor thread calls get_ytm_client().search(query, filter="songs", limit=20).
  4. Normalise results -- _parse_ytm_results() drops anything whose resultType is not "song" and turns each item into {name, artist, artists, album_name, duration (s), year, cover_url, url, song_id, explicit, track_number, disc_number}, with url = https://music.youtube.com/watch?v=<videoId>, song_id = the video ID, artist = the first artist, and the M:SS / H:MM:SS duration string parsed to seconds. track_number and disc_number are always 0.
  5. Upgrade cover art -- ytmusicapi thumbnails are small; Google CDN URLs are rewritten to 800×800 for display: 
    if cover_url and re.search(r"(lh3|yt3)\.googleusercontent\.com", cover_url):
    cover_url = re.sub(r"=w\d+-h\d+.*$", "=w800-h800-l90-rj", cover_url)
    The cover embedded in the file is fetched separately at up to 2000×2000 (hires_cover_url() in utils/metadata.py).
  6. Mark downloaded -- still on the worker, _mark_downloaded() tags entries that already exist in the library with is_downloaded: true and their downloaded_playlist folder (see Duplicate Detection).
  7. Emit -- the poll timer sees the finished future; _handle_search_result() emits isSearchingChanged(false), searchInProgress(false), the JSON array on searchResults and statusMessage("Showing N result(s)"). The QML keeps the parsed array as its ListView model. An exception in the job emits searchError(text) and "Search failed: …" instead.
Pagination
ytmusicapi has no offset parameter, so everything arrives in one batch and search is single-page. The search_more() slot still exists and only emits statusMessage("All results shown") (after any search), and the append-and-deduplicate branch in _handle_search_result() is never reached because the offset is always 0 for a new search. DownloadPage.qml has no "Load More Results" footer, so nothing calls search_more().

Download Pipeline

Tapping a result's download button calls startDownload(JSON.stringify(modelData)) in DownloadPage.qml, which calls download_song(songJson); the error popup's "Retry" button goes through the same function with the same JSON. Everything is keyed by song_id (the YouTube video ID) so retries and duplicate taps are recognised.

  1. Prepare -- _ensure_music_dl(), then _refresh_cookies_file() (see Bot Wall).
  2. Parse and de-duplicate -- the JSON is decoded (invalid JSON emits downloadError("", "Unknown", "Invalid song data: …")); a pending future whose key ends in _<song_id> means statusMessage("Already downloading: …") and nothing else. Any prior is_failed / error_message patch is cleared so the row shows the retry immediately.
  3. Announce -- statusMessage("Queuing download: Artist - Title"), downloadStarted(song_id, "Artist - Title"), downloadQueueChanged(), activeDownloads += 1. With two executor workers, at most two downloads (or one download and a search) run at once; further ones wait in the executor's queue.
  4. Build the Song on the executor -- _do_download() requires name, artists and artist in the JSON (else ValueError), calls Song.from_missing_data(**song_data) and, for a youtube.com / music.youtube.com URL, sets it as download_url so the downloader skips its own provider search.
  5. Skip check -- create_file_name() expands the output template; with overwrite: "skip" an existing file at that name ends the job as "Skipped" and returns that path as if it had been downloaded.
  6. Download -- yt-dlp (get_download_metadata(url, download=True)) writes <music_dl>/temp/<videoId>.<ext>.
  7. Convert or move -- the result goes to a hidden staging file next to the final one, .<Artist - Title.ext>.part. When the bitrate is auto or disable and the temp file already has the target extension (e.g. m4a→m4a) it is moved there as-is; otherwise ffmpeg converts it, with -f <muxer> because the .part name does not carry the format. The temp file is then deleted.
  8. Tag -- embed_metadata() writes title, artists, album artist, album and the cover, plus the source URL and track/disc fields where the container has a tag for them (lyrics too, if the Song carries any; search results never do), into the staging file.
  9. Publish -- publish_partial() fsyncs the staging file, os.replaces it to the final name and, outside Windows, fsyncs the directory. Any exception before that deletes the staging file. A power cut leaves a stray hidden .part file rather than a truncated song that "skip" mode would treat as already downloaded; nothing removes such leftovers automatically.
  10. Resolve -- the 200 ms poll timer sees the finished future and _handle_download_result() emits downloadComplete(song_id, path), statusMessage("Downloaded: …") and an is_downloaded = true patch, or downloadError(song_id, name, "Download failed — no audio source found"), "Failed: …" and is_failed / error_message patches; then downloadQueueChanged().
Error messages are generic
search_and_download() catches every exception from yt-dlp, ffmpeg and tagging, logs it and returns no path, so all of those failures (bot wall, network, conversion) reach the UI as "Download failed — no audio source found"; the real cause is in the log. Only exceptions raised outside the engine (for example the ValueError for missing fields) surface with their own text, through downloadError(song_id, "", text) and "Download failed"; that path does not emit downloadQueueChanged().

There is no cancel, pause or queue snapshot: once submitted, a download runs to completion.

Library refresh

main.py connects downloadComplete to media_manager.scan_library(reset_display_names=False) so the new file appears in the playlist view without a manual rescan.

Progress Reporting

downloadProgress(song_id, fraction) carries a 0.0-1.0 value.

worker thread main thread | | | SongTracker.update() | | -> _on_download_progress() | | append (song_id, p/100) | | under _progress_lock | | QTimer 200 ms _poll_futures() | drain _progress_updates | emit downloadProgress(song_id, 0.0-1.0) | resolve finished futures

The tracker's progress is 0-50 while yt-dlp downloads (downloaded_bytes / total_bytes * 50, falling back to total_bytes_estimate), 50 during conversion, 95 while tags are written and 100 at the end (also 100 for a skip or an error); _on_download_progress() divides by 100. On the page the value drives the row's progress bar and the download queue list.

In-Place Status Patching

Instead of re-sending the whole result array, _mark_result_status_by_id() updates the stored result and emits downloadStatusChanged(song_id, field, value_json) for is_downloaded, is_failed and error_message, with the value serialised by json.dumps. The QML handler JSON.parses it, patches the matching row, re-assigns a copy of the array and restores contentY so the list does not jump.

YouTube Bot Wall and Cookies

For download failures such as "Sign in to confirm you're not a bot", the manager supports a Netscape-format cookies file exported from a logged-in YouTube session. If a file exists at QStandardPaths.writableLocation(DownloadLocation) + "/youtube_cookies.txt", it is handed to yt-dlp as cookiefile.

PlatformPath
Linux / macOS~/Downloads/youtube_cookies.txt
Windows%USERPROFILE%\Downloads\youtube_cookies.txt

_ensure_music_dl() passes cookie_file when it builds the engine, and _refresh_cookies_file() re-checks the path before every download_song(), pushing a changed value into the live downloader's settings and its audio providers. Each download builds its own AudioProvider from those settings, so a file added mid-session is used by the next download, no restart needed. The manager logs "Using YouTube cookies from ..." or where to drop the file.

This passes cookies to yt-dlp but does not guarantee that YouTube will accept a request. There is no in-app indication that the file was found; an in-app picker is parked in TODO/yt-cookies-file-picker.md.

Download Path & Playlist Targeting

Downloads are written into a subfolder of the media library:

# mediaFolder / subfolder / "Artist - Title.<ext>"
download_path = os.path.join(media_folder, subfolder)

media_folder is the mediaFolder setting, or ~/Music when it is empty (~/Music/Downloads if no settings manager is connected). The subfolder is, in priority order:

  • the runtime override set by set_download_playlist(name) -- MediaPlayer.qml, MediaRoom.qml and the Download page's playlist picker call it whenever the user selects a playlist, so a download lands in the playlist currently being viewed; an empty name clears the override;
  • otherwise the downloadSubfolder setting (default "Downloads").

get_download_playlist() returns the effective name and the downloadPath property returns the full directory (declared constant, but computed on every read). The directory is created on demand. When the override changes after the engine exists, set_download_playlist() rewrites the live engine's output template too.

Subfolder validation
_get_download_path() validates the subfolder with is_safe_path() from backend/media_manager.py, which resolves both paths with realpath and requires the target to equal the media folder or start with it plus a path separator. A rejected target falls back to "Downloads" with a warning.

Duplicate Detection

Search results are checked against existing files so the row can show "already in <playlist>" and offer click-to-play (mediaManager.play_downloaded_song()) instead of a second download. The expected stem "Artist - Title" is sanitised the same way the engine sanitises filenames: 

@staticmethod
def _sanitize_for_match(text: str) -> str:
    # Mirror sanitize_string from music_dl/utils/formatter.py
    text = "".join(c for c in text if c not in "/?\\*|<>")
    text = text.replace('"', "'").replace(":", "-")
    return text.lower()

_get_downloaded_files() walks the whole media library and maps each lower-cased audio stem to its folder name (root-level files map to "Unsorted"); if the walk finds nothing (fresh install), the configured download folder is listed directly. It recognises .mp3 .flac .ogg .opus .m4a, skips hidden directories, and .part staging files never match an audio extension.

Multi-artist songs
The match uses the result's first artist (artist), while the engine's {artists} template writes every artist joined with ", ". A song with several artists is therefore not recognised as downloaded by a later search, although the row is flagged right after its own download through the is_downloaded patch.

No settings UI for format and bitrate
No QML page binds downloadFormat or downloadBitrate; both are read with their defaults and can only be changed by editing settingsConfigure.json. downloadSubfolder is likewise JSON-only, but the per-session playlist override covers the common case.

Design Decisions

YouTube Music search instead of plain YouTube search

Search queries ytmusicapi with the songs filter rather than yt-dlp's generic YouTube search, so results are curated songs with album art, artists and durations, and the video ID is a direct download URL. Because every result carries that URL, the engine never runs its own provider search for a tapped result.

Song IDs as the identity, patches instead of re-emits

Commit 9573c7b reworked downloads "to use unique song IDs instead of display names": every signal and every future key carries the YouTube video ID, so two results with the same title cannot collide and a retry addresses the same row. The downloadStatusChanged patch signal exists so a status flip does not rebuild the QML ListView (source comment: "patch without full re-emit"), and the QML side restores the scroll position for the same reason.

Main-thread signal emission via a poll timer

music_dl runs on worker threads and its progress callback fires there. Rather than emitting Qt signals across threads, the callback appends to a locked list and a 200 ms QTimer drains it on the main thread -- the constructor comment calls this "Windows-safe signal emission". The timer is only running while work is pending.

Lazy engine initialisation

MusicDL is built on the first search or download, not at startup, so backend.music_dl (and yt-dlp, ytmusicapi, mutagen with it) is imported only when the feature is used. The cookies file is re-read per download, so it needs no rebuild.

Stage, then rename

The engine never writes a song at its final name until it is converted, tagged and fsynced. With overwrite: "skip", a truncated file at the final name would otherwise be treated as already downloaded forever (module docstring of tests/test_download_partial_file.py).

A shared filename contract

The engine's {artists} - {title}.{output-ext} template, the manager's _sanitize_for_match() and MediaManager.play_downloaded_song() all build the same sanitised "artist - title" stem, which is how the Download page finds and plays a song that is already in the library.

Zero-UI cookies bypass

The cookies file is auto-detected at one fixed path in the user's Downloads folder, so there is no setting or UI for it; dropping the file in place is enough for the next download.
