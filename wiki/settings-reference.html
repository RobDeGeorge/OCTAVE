Overview

Settings are owned by SettingsManager (src/managers/settingsmanager.{h,cpp}) and persisted to settingsConfigure.json in the OS-specific config directory:

  • Windows: %APPDATA%/OCTAVE/settingsConfigure.json
  • macOS: ~/Library/Application Support/OCTAVE/settingsConfigure.json
  • Linux / Raspberry Pi / Orange Pi: ~/.config/OCTAVE/settingsConfigure.json (or $XDG_CONFIG_HOME/OCTAVE/)
  • Android / iOS: the Linux rule applied to QDir::homePath()

buildDefaultSettings() defines 96 top-level default keys. Settings are read once at startup, validated against the defaults, served from memory, and written back atomically 500 ms after the last change. The mechanics are on the Settings Manager page; this page is the key catalogue.

How to read the tables:

  • Property: the QML-visible property name (same as the JSON key) or how QML reaches a key that has no property.
  • Type: the C++ property type, or for keys without a property the JSON type (string, object, list) as stored.
  • Default: the literal in buildDefaultSettings().
  • Range / Values: what the save slot enforces (clamp or whitelist), and in parentheses the range the UI control offers when it is narrower. A dash means the slot stores whatever it is given.
  • UI: the page under frontend/settings/ (Display, Media, OBD, Accessories, Device, About) or the other QML file that writes the key. See Settings UI.
Pinnable settings
25 of these keys are also registered in the settings registry (buildSettingsRegistry()) and can be pinned to the Quick Panel. They are marked pinnable in the description; the registry itself is documented on the Settings Manager page.

Android Auto, Phone Mirror and AirPlay

Accessories page, Phone Dock sub-section. The scrcpy* keys are pushed into PhoneMirrorManager at startup and the gain, duck and screen-off signals are connected to its setters, so they apply to a running session.

They have defaults in buildDefaultSettings() (so they are type-validated) but no property or dedicated slot: the Android Auto card writes them with save_setting() and AndroidAutoManager reads them with get_setting_with_default() at every connection attempt, so a change applies to the next connection (androidAutoBackend at once, through genericSettingChanged → backendChanged).

Persistence and File Format

One JSON object, 4-space indented, containing the 96 default keys (nested objects for obdParameters, gestureMapping, customThemes, settingsMenuVisibility, expandedCards) plus any QML-only keys. Writes are:

  1. Validated once into the in-memory copy (types checked against the defaults; unknown keys kept)
  2. Coalesced behind a 500 ms single-shot timer, flushed at quit
  3. Written through QSaveFile to a temp file in the same directory, fsynced and renamed over the real file in one step by QSaveFile::commit(); on failure the existing file is left untouched
  4. chmod 600 on Unix

On load, a missing file is created from the defaults, a corrupt file is moved to settingsConfigure.json.corrupt and restored from the last known-good settingsConfigure.json.bak (defaults only if that fails too), and wrong-typed values are replaced individually. Keys of removed features (spotifyClientId, spotifyClientSecret, mediaSource, scrcpyAudioEnabled) are deleted from the file at startup, together with the old Spotify login token. Full detail: Settings Manager: JSON Persistence and Validation.
