ESP32 Volume Manager

ESP32VolumeManager provides wireless rotary-encoder volume control. Per the module docstring two ESP32 boards are involved: an encoder unit with the knob, and an ESP32-S3 "receiver dongle" that plugs into the computer over USB and forwards the encoder's commands as newline-terminated text. OCTAVE only ever talks to the dongle.

Linux Windows macOS
Firmware is not in this repository
The ESP32 sketches are not part of the OCTAVE tree (there are no .ino / PlatformIO sources here). What this page documents is the contract the manager implements: the serial parameters, the incoming command grammar and the outgoing LED commands. The wireless link and LED behaviour are up to the firmware.

Serial Communication

The port is opened with serial.Serial(port, baudrate=115200, timeout=1, write_timeout=1); everything else is pyserial's default (8 data bits, no parity, one stop bit, no flow control). A daemon thread runs _read_loop:

  • readline() blocks for up to the 1 s port timeout (the GIL is released while it waits); a timeout returns b"" and the loop re-checks _stop_thread.
  • Bytes are decoded as UTF-8 (errors ignored) into a buffer and split on \n; a readline() that times out mid-line returns the partial bytes, which stay in the buffer until the newline arrives. Each non-empty line is stripped, upper-cased and handed to _process_command().
  • If the buffer still holds more than ESP32_MAX_LINE_BYTES (256) with no newline, it is line noise: it is dropped with one warning per connection, and the reader resyncs by discarding everything up to the next \n. Covered by tests/test_esp32_read_buffer.py.
  • A serial.SerialException logs serial read error, queues _handle_disconnect on the GUI thread with run_on_main() and ends the thread. Any other exception is logged and the loop continues after 100 ms.
def _read_loop(self):
    buffer = ""
    while not self._stop_thread and self._serial_connection:
        try:
            data = self._serial_connection.readline()
            if not data:
                continue
            buffer += data.decode('utf-8', errors='ignore')   # (overflow resync omitted)
            while '\n' in buffer:
                line, buffer = buffer.split('\n', 1)
                line = line.strip()
                if line:
                    self._process_command(line)
        except serial.SerialException as e:
            run_on_main(self._handle_disconnect)   # hop to the GUI thread
            break

volumeChangeRequested and muteToggleRequested are emitted from the read thread and delivered to the main.py handlers on the GUI thread.

Startup sequence

  1. connect_settings_manager() wires the five esp32*Changed settings signals (port, enabled, step size, auto-reconnect, LED sleep), reads esp32VolumeStepSize, and starts a 3 s one-shot startup timer.
  2. _initial_connect() runs a scan. If esp32VolumeEnabled is false it stops here.
  3. The port comes from esp32VolumePort. Only if that setting is empty does auto-selection happen: the detected ESP32-S3 port is saved via save_esp32_volume_port(); failing that, the first scanned port that is not the OBD port is saved and used.
  4. With a port, connect_device() is called; without one the detail becomes "No port configured - select one above".
Default port is empty = auto-select
The settings manager defaults esp32VolumePort to "", so a fresh install runs the auto-selection above and connects to the detected ESP32-S3 on the first start. Picking a port in Settings → Accessories → Volume Knob (the list marks the ESP32-S3 "(Recommended)") saves it, which disconnects and reconnects 500 ms later.

connect_device()

  1. Returns early if already connected, if there is no settings manager, or if esp32VolumeEnabled is false.
  2. Empty port → status "Not Configured", detail "No port configured", and the 10 s background scan timer starts.
  3. Otherwise status "Connecting" ("Connecting to <port>...") and the port is opened.
  4. Success → "Connected" ("Connected to ESP32 on <port>"), reconnect counter reset, read thread started, keepalive timer started only if esp32LedSleepEnabled is false, background scan stopped.
  5. serial.SerialException → "Error" ("Connection failed: …") and _schedule_reconnect().

Background scanning (_scan_timer, 10 s) runs only while disconnected: it is started when there is no port, when auto-reconnect is disabled, or when the retry budget is exhausted, and stopped on connect or when the feature is disabled. Turning esp32VolumeEnabled on calls connect_device(); turning it off disconnects and stops the scan.

LED Feedback

Volume debounce

send_volume_update() stores the value as pending and starts a 50 ms single-shot timer if one is not already running; when it fires, the most recent pending value is written (and logged at info). This caps LED traffic at 20 updates/s during a fast knob spin or slider drag ("to prevent LED flickering" per the source comment) while guaranteeing the final value is always sent.

Keepalive and LED sleep

The manager assumes firmware that turns its LEDs off after a 5 s silence (source comment: "ESP32 timeout is 5s"). With esp32LedSleepEnabled off, a 2 s keepalive timer re-sends V<currentVolume> so the ring stays lit; with it on (the default — "LEDs turn off when OCTAVE closes"), no keepalives are sent and the ring sleeps. Toggling the setting while connected starts or stops the timer immediately. Keepalives are not logged.

Colour source (wiring in main.py)

  • esp32LedColorMode == "theme" (default): settingsManager.albumArtColorsChanged → sync_theme_to_esp32() parses the album-art colour JSON and sends its accent colour (#00FFFF when the key is missing; nothing on a parse error).
  • esp32LedColorMode == "static": esp32LedStaticColorChanged → the chosen hex colour (default #00FFFF).
  • Switching modes (esp32LedColorModeChanged) runs send_current_led_color(), which re-sends the colour for the new mode; a missing or unparsable colour falls back to cyan (0, 255, 255).
  • On every transition to "Connected", a 500 ms single-shot timer sends the current volume (settingsManager.currentVolume), mute state (mediaManager.is_muted()) and colour so a freshly plugged dongle matches the app; the delay gives the firmware time after the port opens.

The volume itself reaches the ring through VolumeController (below), so a slider drag, a gesture and the knob all light the ring the same way.

_handle_disconnect() (a no-op if already disconnected) flips to "Disconnected" / "Connection lost" and calls _schedule_reconnect(). It does not close the port or stop the keepalive timer; the next connect_device() opens a fresh serial.Serial.

VolumeController

backend/volume_utils.py holds the volume curve and the VolumeController QObject. Every hardware input (knob ticks, gesture volume_up/volume_down) and the QML volume sliders (BottomBar.qml, MediaRoom.qml) end in volumeController.applyVolume(percent): 

def to_linear(percent) -> float:
    pct = max(0.0, min(100.0, float(percent)))
    return (pct / 100.0) ** 2.0

@Slot(int)
def applyVolume(self, percent):
    percent = max(0, min(100, int(percent)))
    linear = to_linear(percent)
    self._settings.setCurrentVolume(percent)     # persists currentVolume
    self._media.setVolume(linear)
    self._phone_mirror.setVolume(linear)
    self._esp32.send_volume_update(percent)     # raw percent for the LED ring
  • The constructor takes the settings, media, phone-mirror and ESP32 managers; any of them may be None, and a None output is skipped.
  • main.py calls applyVolume(settings_manager.currentVolume) once after the managers are constructed so all outputs start in sync; BottomBar.qml also applies the saved volume on completion.
  • toLinear(percent) exposes the bare curve as a QML slot without dispatching; no QML file calls it today.

BerryIMU v3 Manager

BerryIMUManager reads the accelerometer, gyroscope, magnetometer and barometer on the BerryIMU v3 over I2C in a background thread, fuses accelerometer + gyroscope with a Madgwick AHRS filter into a quaternion, strips yaw, applies a user-set tare, and emits orientation plus gauge values to QML. The quaternion drives the rigged Jeep TJ on CarMenu; the scalar values feed SensorMenu, OBD dashboards and the home cards through OBDParameterModel.

Linux (Raspberry Pi / Orange Pi)

The chip set and default I2C addresses are documented by the BerryIMU manufacturer. The LSM6DSL scale and rate constants also match ST's driver header.

BMP388 calibration and compensation

_init_bmp388() unpacks the 21 calibration bytes with struct.unpack into 14 coefficients in this order and width: T1 u16, T2 u16, T3 i8, P1 i16, P2 i16, P3 i8, P4 i8, P5 u16, P6 u16, P7 i8, P8 i8, P9 i16, P10 i8, P11 i8. _read_baro() runs the floating-point temperature compensation (the partial terms) and then the pressure polynomial (out1 + out2 + out3 with the eleven pp terms). Pressure is converted to hPa and altitude uses the barometric formula with SEA_LEVEL_PRESSURE = 1013.25: 

altitude = 44330.0 * (1.0 - (pressure_hpa / 1013.25) ** (1.0 / 5.255))

Altitude is therefore relative to standard sea-level pressure, not a locally corrected QNH.

Startup & Reconnection

  1. The constructor schedules _start() with a 1 s single-shot timer; connect_settings_manager(), called right after construction in main.py, reads imuEnabled first.
  2. If disabled: log "disabled in settings, skipping start", emit connectionStatusChanged("Disabled"), stop.
  3. Any previous read thread is joined (2 s timeout) and the bus closed before a (re)connect.
  4. Import smbus2, open the bus, initialise LSM6DSL, LIS3MDL, BMP388 in that order — all on the GUI thread.
  5. Success: log "all sensors initialized successfully", reset the retry counter, emit "Connected", start the read thread. "Connected" is emitted before gyro calibration, which is the first thing the thread does (~1 s).

Retry policy (identical in the gesture manager): up to 5 attempts with linear backoff 5000 ms × attempt = 5 s, 10 s, 15 s, 20 s, 25 s, scheduled with run_on_main(self._start, delay) so it works from the read thread too; then "max retries reached, giving up". The status stays at whatever was last emitted. setEnabled(true) from the settings toggle resets the counter and starts over; cleanup() sets _shutting_down, which suppresses further retries.

Madgwick AHRS Filter

MadgwickAHRS (a class in the same file) implements Sebastian Madgwick's gradient-descent orientation filter. It integrates the gyro rate into a quaternion and applies a beta-scaled corrective step towards the accelerometer's gravity vector (and, when magnetometer data is supplied, the magnetic field).

The filter runs in 6DOF mode — the magnetometer is not fused
The read loop calls update(gx, gy, gz, ax, ay, az, 0.0, 0.0, 0.0, dt). With a zero magnetic vector m_norm < 0.001, so the filter always takes its "6DOF fallback — accel only correction (no heading)" branch; the full 9DOF (MARG) code path is present but never exercised. The source comment gives the reason: in-car magnetic interference (alternator, speakers, steel body) would pull the quaternion around, and enabling 9DOF fusion "needs on-vehicle testing first". The magnetometer is read every iteration and used only for the compass heading, computed directly as atan2(my, mx) ("not from filter — avoids drift"). Because yaw is stripped from the output quaternion anyway (see Quaternion Output), the model never depends on magnetic heading.

Update cycle

def update(self, gx, gy, gz, ax, ay, az, mx, my, mz, dt):
    # 1. Gyro quaternion rate of change (rad/s)
    # 2. Normalise accelerometer; if |a| < 0.001 integrate gyro only and return
    # 3. Normalise magnetometer; use_mag = |m| > 0.001   (always False in OCTAVE)
    # 4. Gradient-descent step s0..s3 (9DOF branch or 6DOF accel-only branch), normalised
    # 5. qdot -= beta * s
    # 6. q += qdot * dt; normalise

get_euler() exists on the filter but the read loop derives pitch and roll from the tared output quaternion instead (below), so the helper is unused.

The 200 Hz Paced Read Loop

The thread first runs the gyro calibration (below), then each iteration:

  1. now = time.monotonic(); dt = now - last (1 ms if not positive). The filter integrates with the measured dt, so its tuning is independent of the loop rate.
  2. Service a pending tare / reset-tare request (threading.Events → _apply_tare() / _apply_tare_reset()).
  3. Three I2C block reads: accel, gyro, mag.
  4. Subtract the gyro bias; apply the deadband per axis; convert to rad/s.
  5. Only if at least one gyro axis is non-zero call ahrs.update(…). When the vehicle is still the quaternion is frozen "so the accel correction doesn't cause visible settling".
  6. Remember ax, ay for tare capture; compute |a|.
  7. If the emit interval has elapsed, emit the seven orientation/gauge signals (see emission gating). The first emission is logged once: first emit — pitch=… roll=… heading=… g=… q=[…] (the q shown is the yaw-stripped quaternion before the tare).
  8. If BARO_INTERVAL has elapsed (it has on the first iteration, because last_baro starts at 0), read the BMP388 and emit altitudeChanged + baroTempChanged. The first successful read is logged once: baro — alt=…m temp=…C.
  9. remaining = SAMPLE_INTERVAL - (time.monotonic() - now); sleep it if positive.
What the source records (Orange Pi 5 Plus)
The comment above SAMPLE_INTERVAL: the three I2C block reads cost about 4.3 ms per iteration, so the loop is bus-bound and settles around 172 Hz with about 8 % CPU on the worker thread — "that CPU is the cost of reading the sensor, not a bug". Setting SAMPLE_INTERVAL below the read cost makes remaining negative, so the sleep is skipped and the loop reads continuously. Raising it to 0.01 (100 Hz) roughly halves bus traffic and CPU while still giving the filter about 1.7 samples per 60 Hz emit; below about 100 Hz "the filter starts to starve". Actual rates depend on the board and bus.

The loop exit is logged as read loop exited after N reads.

Emission Gating (60 Hz vs 5 Hz)

Every emit tick sends seven cross-thread signals into QML bindings (orientationChanged, pitchChanged, rollChanged, headingChanged, accelMagnitudeChanged, lateralGChanged, longitudinalGChanged). setActive(bool) keeps sampling and fusion at full rate, but while no page consumes the stream the effective interval becomes max(emit_interval, IDLE_EMIT_INTERVAL) — 5 Hz. The flag is a plain attribute read by the loop on each iteration.

frontend/Main.qml drives it from the StackView: a Connections { target: stackView } calls updateSensorConsumers() on onCurrentItemChanged and on completion, and inspects stackView.currentItem.objectName: 

readonly property var _imuParamIds: ["PITCH", "ROLL", "HEADING", "ALTITUDE",
                                      "ACCEL_MAG", "LATERAL_G", "LONGITUDINAL_G", "BARO_TEMP"]
function updateSensorConsumers() {
    var n = stackView.currentItem.objectName
    berryIMU.setActive(n === "carMenu" || n === "sensorMenu" || n === "sensorHome"
                       || n === "obdMenu" || (n === "mainMenu" && _homeShowsImuParam()))
}

The full-rate set covers the three sensor pages, OBDMenu (dashboards can contain compass / G-force gauges that read the IMU through OBDParameterModel) and the main menu whenever one of the home OBD cards (settingsManager.get_home_obd_parameters()) is one of the eight IMU parameter IDs. Pages need no code of their own.

setEmitRate(hz) clamps to 10–120 Hz and sets the active interval to 1 / hz. SensorMenu.qml calls it on load with the sensorEmitRate setting (default 60), and the Accessories settings slider (10–120, step 5) saves the setting and calls it live. The interval is stored on the manager (_emit_interval) and read by the loop, so a call before the sensor starts or across a retry is not lost.

Quaternion Output

At each emit tick the filter quaternion goes through two transforms before leaving the thread:

  1. Yaw stripping. Decompose q = q_yaw × q_tilt (yaw = rotation about the sensor Z axis) and keep only the tilt, so heading drift can never rotate the car model: 
    yaw_norm = sqrt(qw² + qz²)          # if <= 0.001 use yw=1, yz=0
yw, yz   = qw / yaw_norm, qz / yaw_norm
# q_tilt = [yw, 0, 0, -yz] * q
tw = yw*qw + yz*qz
tx = yw*qx + yz*qy
ty = yw*qy - yz*qx
tz = yw*qz - yz*qw
  2. Tare. q_out = q_tare × q_tilt (full Hamilton product) where q_tare is the conjugate of the tilt captured at ZERO time (identity until then).

orientationChanged(ow, ox, oy, oz) carries the tared tilt. Pitch and roll for the gauges are extracted from that same tared quaternion (pitch = asin(2(w·y − z·x)), ±90° when the argument reaches ±1; roll = atan2(2(w·x + y·z), 1 − 2(x² + y²))), so the numbers on screen agree with the model. Heading is atan2(my, mx) in degrees, normalised to 0–360. Lateral G is ay − accel_bias_y, longitudinal G is ax − accel_bias_x; accel magnitude is the raw |a| (about 1.0 g at rest, not bias-corrected).

Gyro Calibration, Zero & Reset

Gyro bias (automatic, every start)

The first thing the read thread does is _calibrate_gyro(): 200 gyro samples 5 ms apart (~1 s) while the vehicle should be stationary; the mean of each axis becomes the bias subtracted from all later samples. The result is logged as gyro calibrated — bias x=… y=… z=… dps. Because "Connected" was already emitted, the UI shows the sensor connected while this runs.

ZERO (calibrateTare()) — "level the vehicle"

Captures the current yaw-stripped tilt, stores its conjugate (w, -x, -y, -z) as the tare quaternion, and captures the current ax, ay as the G-force zero so lateral / longitudinal G read 0 on the mounting slope. Logged as tare set — q=[…] accel_bias=[…]. The slot only sets a threading.Event (_tare_requested); the read loop services it at the top of its next iteration in _apply_tare(), so the quaternion and accel snapshot are read on the thread that writes them. While the loop is not running the request is ignored with the log line "tare requested while not running, ignored". The tare is not persisted; it resets to identity on every app start.

RESET (resetTare())

Restores the identity tare and zero accel biases: through _tare_reset_requested while the loop runs, or directly when it does not (there is nothing to race). Logged as tare reset to identity.

Both buttons appear on CarMenu (rectangles with objectName: "imuZero" / "imuReset") and on SensorMenu.

Gesture Manager

GestureManager drives a PixArt PAJ7620U2 gesture sensor over I2C for touchless control. A background thread polls the sensor's two gesture-flag registers, resolves nine gestures, maps each to an action string and emits it; main.py turns actions into media / volume calls.

Linux (Raspberry Pi / Orange Pi)

PAJ7620U2 Sensor

Same bus as the IMU (I2C_BUS = 2), address 0x73. The manager prefers smbus2 and falls back to the legacy smbus module (the IMU manager does not).

RegisterAddressPurpose
REG_BANK_SEL0xEFBank select (0 or 1); writing 0 also serves as the wake-up
REG_CHIP_ID_L / _H0x00 / 0x01Chip ID, expected 0x7620 ((high << 8) | low)
REG_GESTURE_00x43Directional + rotation flags
REG_GESTURE_10x44Wave flag (bit 0)

Initialisation (after the 1 s start delay, on the GUI thread)

  1. Open the bus, sleep 50 ms.
  2. Wake up: write 0xEF ← 0x00, sleep 10 ms. If the first write raises OSError, wait 50 ms and try once more.
  3. Verify chip ID: select bank 0, read 0x00 and 0x01; anything but 0x7620 raises "Expected chip ID 0x7620, got 0x…".
  4. Write the init table: INIT_REGISTER_ARRAY, the DFRobot reference configuration — 219 register/value pairs starting with a bank-0 select and switching to bank 1 midway.
  5. Select bank 0 again for gesture reading; log PAJ7620U2 initialized (chip ID: 0x7620); emit "Connected"; start the read thread.

Failure handling and retries (5 × linear 5 s, none on a permission error or a missing I2C module) are the same as the IMU manager; the log prefix is GestureSensor:.

Read Loop & Two-Pass Disambiguation

ConstantValuePurpose
POLL_INTERVAL0.02 s (~50 Hz)Sleep between polls
GESTURE_COOLDOWN0.3 sDefault minimum gap between gestures; overridden by the gestureCooldown setting
GES_FORWARD_WAIT0.30 sSettle time after an initial FORWARD flag
GES_BACKWARD_WAIT0.40 sSettle time after an initial BACKWARD flag
GES_POST_FLUSH0.10 sRead-and-discard window after a confirmed gesture

Each iteration reads both flag registers in one 2-byte block read from 0x43, then:

  1. No flag set → sleep POLL_INTERVAL, continue.
  2. Cooldown gate: if no more than the cooldown has passed since the last accepted gesture, ignore and sleep.
  3. FORWARD flag: sleep 300 ms, re-read. If the re-read decodes to a gesture other than FORWARD/BACKWARD, use it (the approach was really the start of a swipe); otherwise it is a FORWARD.
  4. BACKWARD flag: same with a 400 ms wait.
  5. Anything else (directional, rotation, wave): sleep 20 ms and read again as a confirmation. Per the source comment the PAJ7620 clears 0x43/0x44 on read, so a clean gesture re-reads as the same flag or as nothing — both accept the first reading. A different gesture on the re-read means the sensor is still settling on some other motion, so the sample is discarded (logged at debug level as "discarding <first> — confirmation read saw <second>").
  6. Accept: bump the count, stamp last_gesture_time, emit gestureDetected(name); look up the action; if it is not "none" emit actionTriggered(action) and log <gesture> -> <action> (#n).
  7. Post-flush: for 100 ms read and discard the flag registers every 10 ms so the tail of the same hand motion cannot fire twice.
  8. Sleep POLL_INTERVAL.

Any exception in the loop logs "read loop error", emits "Error" (from the read thread), closes the bus and schedules a retry. The loop exit is logged as read loop exited after N gestures.

Design Decisions

Each rationale below is taken from source comments, not inferred.

Background threads for I2C, a blocking read for serial

The IMU and gesture loops run on dedicated daemon threads rather than QTimer ticks on the GUI thread: one IMU iteration blocks on the bus for about 4.3 ms (the measurement in the SAMPLE_INTERVAL comment), and the gesture loop deliberately sleeps 300–400 ms mid-detection. Initialisation still runs on the GUI thread. The price is that every emitted value crosses threads as a queued signal, which is what the emission gating below manages. The ESP32 knob sends a few bytes per second, so its thread blocks in readline() with the GIL released "instead of polling in_waiting at 100 Hz for a knob that sends a few bytes a second".

A paced loop instead of "read as fast as you can"

The IMU loop sleeps out the rest of a 5 ms period after its reads, so it never busy-spins; the barometer is read on a time-based interval "so it doesn't drift with loop rate". The source comment documents the trade-off of the period in both directions (below the read cost the sleep disappears; 100 Hz halves bus traffic but approaches the point where the filter starves).

Emission gating rather than stopping the sensor

"Sampling and fusion continue at full rate; only the emission into QML slows down while nothing on screen consumes it." Stopping the loop instead would lose the gyro-integrated attitude and the tare context; 5 Hz keeps the settings status fresh "without seven queued signals per frame into idle bindings" (the Main.qml comment). Driving it from Main.qml's StackView keeps the consumer list a property of what is on screen.

One quaternion, yaw stripped, heading from the raw magnetometer

The module docstring states the goal: "outputs a quaternion directly to the 3D model, completely avoiding gimbal lock. No Euler angle clamping, no cascaded EMA stages. One filter, one quaternion, 1:1 mapping." Yaw is removed so heading drift can never rotate the model; the compass value comes from the magnetometer directly because that "avoids drift"; and the magnetometer stays out of the fusion because of in-car magnetic interference. Freezing the filter when the deadbanded gyro is zero stops the accelerometer correction from producing visible settling on a parked vehicle.

Tare over persistent mounting calibration

Rather than a mounting-angle setting, the user presses ZERO on a level surface. The tare is a quaternion captured in the same yaw-stripped domain as the output "so the tare operates in the same domain as the values it's applied to", and it captures the accelerometer bias at the same moment so the G displays zero with it. Gyro bias is re-measured on every start; the tare is not persisted.

A single volume entry point

backend/volume_utils.py explains it: "Before this module existed, the curve was hardcoded in ~9 call sites across main.py and QML. If the curve ever changed, every site had to change in lockstep. This module centralizes both the math and the dispatch." Hardware handlers therefore never call a manager's setVolume; they call applyVolume(currentVolume + delta). The delta accumulator in main.py exists because the knob step can be as small as 0.25 %, and applyVolume takes an integer percent.

LED debounce, keepalive and sleep

The 50 ms trailing debounce ("max 20 updates/sec") exists to prevent LED flickering while always delivering the final value. The 2 s keepalive is sized against the dongle's 5 s LED timeout, and LED sleep is implemented by simply not sending keepalives, so the firmware needs no extra command and the ring goes dark on its own when OCTAVE exits ("LEDs turn off when OCTAVE closes" is the default's comment).

Two-pass gesture disambiguation and post-flush

From the source: forward/backward "are compound gestures (hand approaching/leaving) that the sensor often initially reports as directional. Wait and re-read to let the sensor settle on the final gesture." The waits (300 / 400 ms) and the init table follow the DFRobot reference driver. The 100 ms flush after a confirmed gesture keeps "the same motion" from firing twice, and the user-tunable cooldown is the coarse guard above that.

Linear retries, permission errors excluded

Both I2C managers retry five times at 5 s × n. A missing /dev/i2c-2 may appear later, so it is retried; a PermissionError is not, because only the user can fix group membership. Inside the loop the first failed read ends it and starts the retry cycle, since smbus2 raises on any I2C error.
