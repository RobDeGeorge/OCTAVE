ESP32 Volume Manager

The ESP32VolumeManager in backend/esp32_volume_manager.py provides wireless rotary encoder volume control via a two-ESP32 setup communicating over ESP-NOW. An ESP32-S3 "receiver dongle" plugs into the computer via USB and forwards commands from a remote ESP32 encoder unit over serial.

Linux Windows macOS

ESP-NOW Wireless Protocol

+-------------------+ ESP-NOW +-------------------+ | ESP32 Encoder | ~~~~~~~~~~~~~~~~~~~~~~> | ESP32-S3 Dongle | | (Rotary Knob) | (Wireless) | (USB Receiver) | | - Rotary encoder | | - USB Serial | | - Button press | | - LED ring | +-------------------+ +--------+----------+ | USB Serial 115200 baud | +--------v----------+ | OCTAVE | | ESP32VolumeManager| +-------------------+

ESP-NOW is Espressif's low-latency peer-to-peer wireless protocol. The encoder unit detects rotary knob rotation and button presses, then transmits simple text commands to the receiver dongle wirelessly. The dongle forwards these over USB serial to OCTAVE.

Serial Communication

The serial connection uses 115200 baud with a 1-second read/write timeout. A dedicated background thread (_read_loop) reads incoming data, buffering until complete newline-terminated lines are received: 

def _read_loop(self):
    buffer = ""
    while not self._stop_thread and self._serial_connection:
        if self._serial_connection.in_waiting > 0:
            data = self._serial_connection.read(
                self._serial_connection.in_waiting
            )
            buffer += data.decode('utf-8', errors='ignore')
            while '\n' in buffer:
                line, buffer = buffer.split('\n', 1)
                self._process_command(line.strip())
        else:
            time.sleep(0.01)  # Prevent CPU spinning

Device Discovery

The manager scans for serial ports using pyserial's list_ports utility. ESP32-S3 devices are identified by Espressif's USB Vendor ID 0x303A or keywords like "JTAG" in the device description.

PlatformDetection MethodCommon Paths
Windows COM port enumeration, VID:PID matching COM3, COM4, etc.
macOS VID matching + glob patterns /dev/tty.usbmodem*, /dev/cu.usbserial*
Linux VID matching + glob patterns /dev/ttyUSB*, /dev/ttyACM*

The OBD-II Bluetooth port is excluded from results to prevent conflicts. Background scanning runs every 10 seconds when disconnected, and stops while connected.

On startup (after a 3-second delay), the manager auto-selects the ESP32-S3 port if detected. If no ESP32-S3 is found, it falls back to the first available USB serial port.

LED Color Sync

The ESP32 receiver has an LED ring that displays volume level. OCTAVE sends:

  • Volume updates -- Rate-limited to max 20 updates/sec (50ms debounce timer) to prevent LED flickering during rapid slider drags
  • Theme colors -- send_theme_color(r, g, b) sends the current album art theme color to the LED ring
  • Mute state -- send_mute_state(muted) syncs the mute indicator

Keepalive System

The ESP32 has a 5-second LED timeout. When LED sleep is disabled, OCTAVE sends keepalive volume updates every 2 seconds. When LED sleep is enabled, keepalives are stopped, allowing the LEDs to turn off after the timeout.

Auto-Reconnect

On connection loss (serial read error), the manager schedules automatic reconnection with exponential backoff: 

delay = min(10000, 3000 * attempt_number)  # 3s, 6s, 9s, 10s, 10s

Maximum 5 reconnect attempts before giving up. The attempt counter resets on successful connection. Auto-reconnect can be disabled via settings.

BerryIMU v3 Manager

The BerryIMUManager in backend/berryimu_manager.py reads accelerometer, gyroscope, magnetometer, and barometer data from the BerryIMU v3 board via I2C. It uses a Madgwick AHRS 9DOF sensor fusion algorithm to output a quaternion -- completely avoiding gimbal lock -- for driving a 3D car model in the QML UI.

Linux (Raspberry Pi)

I2C Sensor Chips

The BerryIMU v3 contains three sensor chips on I2C bus 2:

ChipI2C AddressSensorsInit Rate
LSM6DSL 0x6A Accelerometer (+/-4g) + Gyroscope (245 dps) 416 Hz
LIS3MDL 0x1C Magnetometer (+/-8 gauss, ultra-high performance) 155 Hz
BMP388 0x77 Barometric pressure + Temperature ~5 Hz (read every 80th loop)

Sensor Initialization

def _init_lsm6dsl(self):
    self._bus.write_byte_data(LSM6DSL_ADDR, 0x10, 0x68)  # Accel: 416Hz, +/-4g
    self._bus.write_byte_data(LSM6DSL_ADDR, 0x11, 0x60)  # Gyro: 416Hz, 245dps
    self._bus.write_byte_data(LSM6DSL_ADDR, 0x12, 0x44)  # BDU + auto-inc

def _init_lis3mdl(self):
    self._bus.write_byte_data(LIS3MDL_ADDR, 0x20, 0xFE)  # Ultra-high perf, 155Hz
    self._bus.write_byte_data(LIS3MDL_ADDR, 0x21, 0x20)  # +/-8 gauss
    self._bus.write_byte_data(LIS3MDL_ADDR, 0x22, 0x00)  # Continuous
    self._bus.write_byte_data(LIS3MDL_ADDR, 0x23, 0x0C)  # Ultra-high Z

BMP388 Calibration

The barometer requires reading 21 bytes of factory calibration data (12 coefficients: T1-T3, P1-P11) from register 0x31. These are used in a multi-stage compensation algorithm to convert raw ADC readings into calibrated pressure (hPa) and temperature (C). Altitude is derived using the barometric formula with SEA_LEVEL_PRESSURE = 1013.25 hPa.

Madgwick AHRS 9DOF Filter

The MadgwickAHRS class implements Sebastian Madgwick's gradient descent orientation filter, fusing accelerometer, gyroscope, and magnetometer into a single quaternion.

Why Madgwick?
Unlike complementary filters or Kalman filters, Madgwick AHRS produces a quaternion directly, avoiding Euler angle representation entirely. This eliminates gimbal lock and provides smooth 1:1 mapping to QML's 3D model rotation.

Key Parameters

MADGWICK_BETA0.03Filter gain. Lower = smoother/less jitter, higher = more responsive

The filter automatically falls back to 6DOF (accel-only correction, no heading) when magnetometer data is invalid (m_norm < 0.001).

Quaternion Output

The raw filter quaternion undergoes two post-processing steps before emission:

  1. Yaw stripping -- Decomposes the quaternion into yaw and tilt components, keeping only pitch and roll. This prevents heading drift from affecting the 3D car model: 
    # q = q_yaw * q_tilt
# We want q_tilt = q_yaw_inverse * q
yaw_norm = math.sqrt(qw*qw + qz*qz)
yw = qw / yaw_norm
yz = qz / yaw_norm
# Quaternion multiply: [yw, 0, 0, -yz] * [qw, qx, qy, qz]
  2. Tare offset -- A stored reference quaternion (_tare_q) is applied via quaternion multiplication to zero out a reference orientation. This lets the user set "level" at any mounting angle.

The final quaternion (w, x, y, z) is emitted via orientationChanged at ~60 Hz.

Calibration & Tare

Gyro Calibration (Automatic)

On startup, the gyroscope is sampled 200 times over ~1 second while stationary. The average readings become the bias offsets, subtracted from all subsequent readings.

Tare (User-Triggered)

The calibrateTare() slot captures the current yaw-stripped quaternion and stores its conjugate as the tare offset. It also captures the current accelerometer readings as G-force zero reference for the lateral/longitudinal G displays. 

# Inverse of a unit quaternion is its conjugate: (w, -x, -y, -z)
self._tare_q = [tw, -tx, -ty, -tz]
self._accel_bias_x = self._last_ax
self._accel_bias_y = self._last_ay

Read Loop

The background thread targets a ~200 Hz sample rate (SAMPLE_INTERVAL = 5 ms). After each round of I2C reads it sleeps for the remainder of the period rather than spinning. In practice the loop is I2C-bound: on the Orange Pi 5 Plus the three block reads take ~4.3 ms, so it settles around 172 Hz and the worker thread costs ~8% CPU, which is simply the price of reading the sensor. Raising SAMPLE_INTERVAL to 10 ms (100 Hz) roughly halves that; lowering it below the read cost makes the loop spin. Key behaviors:

  • Deadband gating -- Gyro readings below GYRO_DEADBAND (0.4 deg/s) are zeroed. The Madgwick filter is only updated when there is actual motion, freezing the quaternion when stationary to prevent visible settling.
  • Signal emission -- Orientation, pitch, roll, heading, accel magnitude, lateral G, and longitudinal G are emitted at ~60 Hz
  • Barometer -- Read every 200 ms (BARO_INTERVAL, ~5 Hz), emitting altitude and temperature
  • Heading -- Computed directly from raw magnetometer (atan2(my, mx)), not from the Madgwick filter, to avoid drift

Gesture Manager

The GestureManager in backend/gesture_manager.py drives a PAJ7620U2 gesture sensor over I2C for touchless control of OCTAVE. It recognizes 8 gesture types and maps them to configurable actions like next track, volume control, and play/pause.

Linux (Raspberry Pi)

PAJ7620U2 Sensor

The PAJ7620U2 is a PixArt gesture recognition sensor communicating over I2C bus 2 at address 0x73. It uses an infrared LED and photodiode array to detect hand gestures.

Initialization

  1. Wake up -- Write to bank select register (0xEF) to wake the sensor from sleep. Includes a retry on OSError.
  2. Verify chip ID -- Read registers 0x00 and 0x01, expect 0x7620
  3. Write init table -- Program 220 register pairs (DFRobot reference configuration) across Bank 0 and Bank 1. This configures sensitivity, detection thresholds, and gain parameters.

Action Mapping System

Each gesture maps to an action string via a configurable dictionary. The default mapping: 

DEFAULT_GESTURE_MAPPING = {
    "RIGHT":             "next_track",
    "LEFT":              "previous_track",
    "UP":                "volume_up",
    "DOWN":              "volume_down",
    "FORWARD":           "play_pause",
    "BACKWARD":          "mute_toggle",
    "CLOCKWISE":         "volume_up",
    "COUNTER-CLOCKWISE": "volume_down",
    "WAVE":              "play_pause",
}

Users can remap gestures via setGestureAction(gesture, action). Custom mappings are persisted through the SettingsManager.

Two-Pass Disambiguation

Forward and backward gestures are compound motions (hand approaching/leaving) that the sensor often initially reports as directional. The read loop implements a two-pass disambiguation strategy:

  1. Initial detection -- If GES_FORWARD flag is set, wait 300ms (GES_FORWARD_WAIT). If GES_BACKWARD, wait 400ms (GES_BACKWARD_WAIT).
  2. Re-read -- Read gesture registers again. If a different directional gesture resolved, use that instead. Otherwise confirm the forward/backward gesture.
  3. Confirmation for directional gestures -- Non-compound gestures get a 20ms confirmation read to reject single-sample glitches.
  4. Post-flush -- After confirming any gesture, the sensor is flushed for 100ms (GES_POST_FLUSH) to prevent echo/ghost detections from the same hand motion.

Cooldown

A configurable cooldown (GESTURE_COOLDOWN = 0.3s default) rejects duplicate detections within the window. The sensor is polled at ~50 Hz (POLL_INTERVAL = 0.02s).

Reconnection

Both the BerryIMU and Gesture managers share the same reconnection pattern: linear backoff with _retry_delay_ms * attempt_number (5s, 10s, 15s, 20s, 25s), maximum 5 retries. The I2C bus is cleaned up between attempts.
