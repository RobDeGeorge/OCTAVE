ESP32 Volume Manager

ESP32VolumeManager provides wireless rotary-encoder volume control. Two ESP32 boards are involved: an encoder unit with the knob, and an ESP32-S3 "receiver dongle" that plugs into the computer over USB and forwards the encoder's commands as newline-terminated text. OCTAVE only ever talks to the dongle.

Linux Windows macOS
Firmware is not in this repository
The ESP32 sketches are not part of the OCTAVE tree (there are no .ino / PlatformIO sources here). What this page documents is the contract both backends implement: the serial parameters, the incoming command grammar and the outgoing LED commands. Any firmware that speaks this protocol works.

Serial Communication

Both backends open the port at 115200 baud. C++ sets 8 data bits, no parity, one stop bit, no flow control explicitly (QSerialPort::Data8 / NoParity / OneStop / NoFlowControl); Python relies on pyserial's defaults (also 8N1) and adds a 1 s read and write timeout. Incoming bytes are buffered and split on \n; each non-empty line is trimmed, upper-cased and handed to the command parser.

The two backends read the port very differently:

def _read_loop(self):
    buffer = ""
    while not self._stop_thread and self._serial_connection:
        try:
            # Block in readline() (1 s port timeout, GIL released) instead of
            # polling in_waiting at 100 Hz for a knob that sends a few bytes a second.
            data = self._serial_connection.readline()
            if not data:
                continue
            buffer += data.decode('utf-8', errors='ignore')
            while '\n' in buffer:
                line, buffer = buffer.split('\n', 1)
                line = line.strip()
                if line:
                    self._process_command(line)
        except serial.SerialException as e:
            QTimer.singleShot(0, self._handle_disconnect)  # hop to the main thread
            break

Device Discovery & Startup

ESP32-S3 boards enumerate with Espressif's USB Vendor ID 0x303A. Both backends put a port whose VID matches (or whose description contains jtag, esp32-s3 or esp32s3) at the front of the list and remember it as _esp32_s3_port / m_esp32S3Port. The OBD serial port (settingsManager.obdBluetoothPort) is always excluded so the two features cannot fight over one device. Results are de-duplicated and sorted; availablePortsChanged fires only when the list actually changes.

Startup sequence

  1. connect_settings_manager() wires the five esp32*Changed settings signals, reads esp32VolumeStepSize, and starts a 3 s one-shot startup timer.
  2. _initial_connect() / initialConnect() runs a scan. If esp32VolumeEnabled is false it stops here.
  3. The port comes from esp32VolumePort. Only if that setting is empty does auto-selection happen: the detected ESP32-S3 port is saved via save_esp32_volume_port(); failing that, the first non-OBD port in the scan list is saved and used.
  4. With a port, connect_device() is called; without one the detail becomes "No port configured - select one above".
Default port is "COM7" on every platform
Both settings managers default esp32VolumePort to "COM7". Because auto-selection only runs when the setting is empty, a fresh install on Linux or macOS will try to open COM7, fail, burn its five reconnect attempts, and never fall back to the detected ESP32-S3. Pick the port once in Settings → Accessories → Volume Knob (the list marks the ESP32-S3 "(Recommended)"), which calls save_esp32_volume_port() and triggers a reconnect 500 ms later.

connect_device()

  1. Returns early if already connected, if there is no settings manager, or if esp32VolumeEnabled is false.
  2. Empty port → status "Not Configured", detail "No port configured", and the 10 s background scan timer starts.
  3. Otherwise status "Connecting" ("Connecting to <port>...") and the port is opened.
  4. Success → "Connected" ("Connected to ESP32 on <port>"), reconnect counter reset, read thread started (Python) / read buffer cleared (C++), keepalive timer started only if esp32LedSleepEnabled is false, background scan stopped.
  5. Failure → "Error" ("Connection failed: …") and scheduleReconnect().

Background scanning (_scan_timer, 10 s) runs only while disconnected: it is started when there is no port, when auto-reconnect is disabled, or when the retry budget is exhausted, and stopped on connect or when the feature is disabled.

LED Feedback

Volume debounce

send_volume_update() stores the value as pending and starts a 50 ms single-shot timer if one is not already running; when it fires, the most recent pending value is written. This caps LED traffic at 20 updates/s during a fast knob spin or slider drag ("to prevent LED flickering" per the source comment) while guaranteeing the final value is always sent.

Keepalive and LED sleep

The dongle turns its LEDs off after a 5 s silence (per the source comment "ESP32 timeout is 5s"). With esp32LedSleepEnabled off, a 2 s keepalive timer re-sends V<currentVolume> so the ring stays lit; with it on (the default — "LEDs turn off when OCTAVE closes"), no keepalives are sent and the ring sleeps. Toggling the setting while connected starts or stops the timer immediately. Keepalives are not logged. C++ falls back to volume 50 if the currentVolume property is unreadable.

Colour source (Python wiring in main.py)

  • esp32LedColorMode == "theme" (default): settingsManager.albumArtColorsChanged → sync_theme_to_esp32() parses the album-art colour JSON and sends its accent colour.
  • esp32LedColorMode == "static": esp32LedStaticColorChanged → the chosen hex colour (default #00FFFF).
  • Switching modes (esp32LedColorModeChanged) re-sends the current colour; any parse failure falls back to cyan (0, 255, 255).
  • On every transition to "Connected", a 500 ms timer sends the initial volume, mute state and colour so a freshly plugged dongle matches the app.
C++ backend: the LED wiring is missing
src/main.cpp connects the knob's volumeChangeRequested and muteToggleRequested, but nothing in the C++ tree calls send_theme_color(), and VolumeController::volumeApplied is connected only to MediaManager and a Spotify debounce — not to send_volume_update(), and not to the phone mirror. On the C++ build the ring therefore receives V only from the 2 s keepalive (LED sleep off) and M only after a knob press; theme / static colours and the on-connect sync never happen. This is a known parity gap; the Python wiring above is the intended behaviour.

VolumeController

Every hardware input (knob ticks, gesture volume_up/volume_down) and every QML slider ends in volumeController.applyVolume(percent). It clamps to 0–100, persists currentVolume through the SettingsManager, converts the percent through the quadratic curve linear = (percent / 100)², and pushes the result to every audio output. toLinear(percent) exposes the bare curve to QML for previews without dispatching.

BerryIMU v3 Manager

BerryIMUManager reads the accelerometer, gyroscope, magnetometer and barometer on the BerryIMU v3 over I2C in a worker thread, fuses accelerometer + gyroscope with a Madgwick AHRS filter into a quaternion, strips yaw, applies a user-set tare, and emits orientation plus gauge values to QML. The quaternion drives the rigged Jeep TJ on CarMenu; the scalar values feed SensorMenu, OBD dashboards and the home cards through OBDParameterModel.

Linux (Raspberry Pi / Orange Pi) Android (QtSensors variant)

I2C Sensor Chips & Register Map

The bus number and the three addresses are constants in both backends (I2C_BUS = 2; there is no setting to change them). Python uses smbus2.SMBus(2); C++ opens /dev/i2c-2 with O_RDWR and selects each chip with ioctl(I2C_SLAVE, addr), then does raw write(reg) / read(n) pairs (readBlockData) — the same wire traffic as read_i2c_block_data.

BMP388 calibration and compensation

The 21 calibration bytes unpack to 14 coefficients in this order and width: T1 u16, T2 u16, T3 i8, P1 i16, P2 i16, P3 i8, P4 i8, P5 u16, P6 u16, P7 i8, P8 i8, P9 i16, P10 i8, P11 i8 (C++ BMP388Calib struct, Python struct.unpack). _read_baro() / readBaro() runs the floating-point temperature compensation (three partial terms) and then the pressure polynomial (out1 + out2 + out3 with the eleven pp terms). Pressure is converted to hPa and altitude uses the barometric formula with SEA_LEVEL_PRESSURE = 1013.25: 

altitude = 44330.0 * (1.0 - (pressure_hpa / 1013.25) ** (1.0 / 5.255))

Altitude is therefore relative to standard sea-level pressure, not a locally corrected QNH.

Startup & Reconnection

  1. The constructor schedules _start() / startSensor() with a 1 s single-shot timer; connect_settings_manager() reads imuEnabled first.
  2. If disabled: log "disabled in settings, skipping start", emit connectionStatusChanged("Disabled"), stop.
  3. Any previous thread is joined (2 s timeout) and the bus closed before a (re)connect.
  4. Open the bus, initialise LSM6DSL, LIS3MDL, BMP388 in that order.
  5. Success: log "all sensors initialized successfully", emit "Connected", reset the retry counter, start the read loop. Note that "Connected" is emitted before gyro calibration, which is the first thing the loop does (~1 s).

Retry policy (same in both, and identical to the gesture manager): up to 5 attempts with linear backoff 5000 ms × attempt = 5 s, 10 s, 15 s, 20 s, 25 s, then "max retries reached, giving up". The status stays at whatever was last emitted; nothing marks the sensor "unavailable". setEnabled(true) from the settings toggle resets the counter and starts over.

Threading model. Python runs _read_loop in a daemon threading.Thread. C++ moves a BerryIMUWorker QObject to a QThread; QThread::started triggers run(), and the worker's signals are forwarded 1:1 to the manager's public signals (queued connections, so QML always receives them on the GUI thread). stopWorker() sets the atomic m_running false, quits the thread, waits up to 2 s and deletes both objects.

Madgwick AHRS Filter

MadgwickAHRS (a class in the same file in both backends) implements Sebastian Madgwick's gradient-descent orientation filter. It integrates the gyro rate into a quaternion and applies a beta-scaled corrective step towards the accelerometer's gravity vector (and, when magnetometer data is supplied, the magnetic field).

The filter runs in 6DOF mode — the magnetometer is not fused
Both read loops call update(gx, gy, gz, ax, ay, az, 0.0, 0.0, 0.0, dt). With a zero magnetic vector m_norm < 0.001, so the filter always takes its "6DOF fallback — accel only correction (no heading)" branch. The full 9DOF (MARG) code path is present but never exercised. The magnetometer is read every iteration and used only for the compass heading, computed directly as atan2(my, mx) ("not from the filter — avoids drift"). Because yaw is stripped from the output quaternion anyway (see Quaternion Output), the model never depended on magnetic heading.

    # 1. Gyro quaternion rate of change (rad/s)
    # 2. Normalise accelerometer; if |a| < 0.001 integrate gyro only and return

The 200 Hz Paced Read Loop

Introduced in commit ed826ed and re-measured in f1eb526. Each iteration:

  1. now = monotonic(); dt = now - last (floored at 1 ms). The filter integrates with the measured dt, so its tuning is independent of the loop rate.
  2. C++ only: service a pending tare / reset-tare request (atomic flags → mutex-protected m_tareQ).
  3. Three I2C block reads: accel, gyro, mag.
  4. Subtract the gyro bias; apply the deadband per axis; convert to rad/s.
  5. Only if at least one gyro axis is non-zero call ahrs.update(…). When the vehicle is still the quaternion is frozen "so the accel correction doesn't cause visible settling".
  6. Remember ax, ay for tare capture; compute |a|.
  7. If the emit interval has elapsed, emit the seven orientation/gauge signals (see emission gating). The very first emission is logged once: first emit - pitch=… roll=… heading=… g=… q=[…].
  8. If BARO_INTERVAL has elapsed (it has on the first iteration, because last_baro starts at 0), read the BMP388 and emit altitudeChanged + baroTempChanged. The first successful read is logged once: baro - alt=…m temp=…C (a baro_logged flag; the older readCount <= 80 guard fired three times after the loop was re-paced). C++ skips the emit when the compensated pressure is 0 (failed read); Python logs a debug message on exception.
  9. remaining = SAMPLE_INTERVAL - (monotonic() - now); sleep it if positive.
What was measured (Orange Pi 5 Plus, strace -T)
The three block reads cost about 4.3 ms per iteration, so the loop is I2C-bound: it settles around 172 Hz with ~1.5 ms of sleep, and the worker thread's ~8 % CPU "is the cost of reading the sensor, not a spin". The earlier fixed 1 ms sleep kept the bus saturated for no benefit: the LSM6DSL output data rate is 416 Hz and emission is 60 Hz. 200 Hz stays below the ODR (no duplicate samples) and still gives the filter 3+ samples per emit. The source warns not to set SAMPLE_INTERVAL below the read cost (the sleep is skipped and the loop really does spin) and notes that 0.01 (100 Hz) is where a real CPU saving lives (~1.7 samples per emit; below ~100 Hz the filter starts to starve).

The loop exit is logged as read loop exited after N reads.

Emission Gating (60 Hz vs 5 Hz)

Every emit tick sends seven queued cross-thread signals into QML bindings (orientationChanged, pitchChanged, rollChanged, headingChanged, accelMagnitudeChanged, lateralGChanged, longitudinalGChanged). Commit 94d61be added setActive(bool): sampling and fusion continue at full rate, but while no page consumes the stream the effective interval becomes max(emit_interval, IDLE_EMIT_INTERVAL) — 5 Hz, enough to keep the status line in Settings fresh. In C++ the flag is an std::atomic<bool> m_idle on the worker, also applied when the worker is (re)created.

frontend/Main.qml drives it from the StackView: a Connections { target: stackView } calls updateSensorConsumers() on onCurrentItemChanged and on completion, and inspects stackView.currentItem.objectName:

setEmitRate(hz) clamps to 10–120 Hz and sets the active interval to 1 / hz. SensorMenu.qml calls it on load with the sensorEmitRate setting (default 60), and the Accessories settings slider (10–120, step 5) saves the setting and calls it live. In Python the interval is stored on the manager and survives reconnects; in C++ it is forwarded to the current worker only, so a worker created later (initial start or a retry) begins at the 60 Hz default until the page calls setEmitRate again.

Quaternion Output

At each emit tick the filter quaternion goes through two transforms before leaving the worker:

  1. Yaw stripping. Decompose q = q_yaw × q_tilt (yaw = rotation about the sensor Z axis) and keep only the tilt, so heading drift can never rotate the car model: 
    yaw_norm = sqrt(qw² + qz²)          # if < 0.001 use yw=1, yz=0
yw, yz   = qw / yaw_norm, qz / yaw_norm
# q_tilt = [yw, 0, 0, -yz] * q
tw = yw*qw + yz*qz
tx = yw*qx + yz*qy
ty = yw*qy - yz*qx
tz = yw*qz - yz*qw
  2. Tare. q_out = q_tare × q_tilt (full Hamilton product) where q_tare is the conjugate of the tilt captured at ZERO time (identity until then).

orientationChanged(ow, ox, oy, oz) carries the tared tilt. Pitch and roll for the gauges are extracted from that same tared quaternion (pitch = asin(2(w·y − z·x)) clamped to ±90°, roll = atan2(2(w·x + y·z), 1 − 2(x² + y²))), so the numbers on screen always agree with the model. Heading is atan2(my, mx) in degrees, normalised to 0–360. Lateral G is ay − accel_bias_y, longitudinal G is ax − accel_bias_x; accel magnitude is the raw |a| (about 1.0 g at rest, not bias-corrected).

Gyro Calibration, Zero & Reset

Gyro bias (automatic, every start)

The first thing the read loop does is _calibrate_gyro(): 200 gyro samples 5 ms apart (~1 s) while the vehicle should be stationary; the mean of each axis becomes the bias subtracted from all later samples. The result is logged as gyro calibrated - bias x=… y=… z=… dps. Because "Connected" was already emitted, the UI shows the sensor connected while this runs.

ZERO (calibrateTare()) — "level the vehicle"

Captures the current yaw-stripped tilt, stores its conjugate (w, -x, -y, -z) as the tare quaternion, and captures the current ax, ay as the G-force zero so lateral / longitudinal G read 0 on the mounting slope. Logged as tare set - q=[…] accel_bias=[…]. The tare is not persisted; it resets to identity on every app start.

Android: QtSensors Implementation

Under Q_OS_MOBILE the same header declares a different BerryIMUManager backed by QAccelerometer, QCompass and QPressureSensor (the Sensors Qt module is added to the build only for Android). Same QML name, same signals and slots, but:

  • No Madgwick, no quaternion: orientationChanged is declared but never emitted. Pitch = atan2(ay, √(ax²+az²)), roll = atan2(−ax, az) from the accelerometer alone; the tare is a pair of angle offsets subtracted from them.
  • Lateral G = ax / 9.81, longitudinal G = ay / 9.81, magnitude = |a| / 9.81 (QtSensors reports m/s²).
  • Heading = compass azimuth, normalised to ≥ 0 because some Android devices report −180…180.
  • Altitude from the pressure sensor (Pa, against 101 325 Pa) at 10 Hz; baroTempChanged and hasTemperature only turn on once a non-zero temperature arrives (most phones report 0).
  • Rates: accelerometer and compass run at setEmitRate() (default 60, clamped 1–120) and drop to 5 Hz when setActive(false) — here it throttles the sensors themselves rather than the emission.
  • Status is "Connected" if the accelerometer starts, otherwise "Unavailable"; setEnabled() starts/stops the sensors but does not persist imuEnabled.

Gesture Manager

GestureManager drives a PixArt PAJ7620U2 gesture sensor over I2C for touchless control. A worker thread polls the sensor's two gesture-flag registers, resolves nine gestures, maps each to an action string and emits it; the application wiring turns actions into media / volume calls.

Linux (Raspberry Pi / Orange Pi)

PAJ7620U2 Sensor

Same bus as the IMU (I2C_BUS = 2), address 0x73. Python prefers smbus2 and falls back to the legacy smbus module (the IMU manager does not); C++ uses the same raw ioctl/read/write helpers as the IMU worker.

RegisterAddressPurpose
REG_BANK_SEL0xEFBank select (0 or 1); writing 0 also serves as the wake-up
REG_CHIP_ID_L / _H0x00 / 0x01Chip ID, expected 0x7620 ((high << 8) | low)
REG_GESTURE_00x43Directional + rotation flags
REG_GESTURE_10x44Wave flag (bit 0)

Initialisation (worker thread, after the 1 s start delay)

  1. Open the bus (Python sleeps 50 ms first).
  2. Wake up: write 0xEF ← 0x00, sleep 10 ms. If the first write raises OSError / fails, wait 50 ms and try once more (the chip is asleep until addressed).
  3. Verify chip ID: select bank 0, read 0x00 and 0x01; anything but 0x7620 is an init error ("Expected chip ID 0x7620, got 0x…").
  4. Write the init table: INIT_REGISTER_ARRAY, the DFRobot reference configuration — 219 register/value pairs (the source comment says 220) starting with a bank-0 select, switching to bank 1 midway. It sets the sensor's gain, thresholds and gesture-engine parameters.
  5. Select bank 0 again for gesture reading; log PAJ7620U2 initialized (chip ID: 0x7620); emit "Connected".

Failure handling, retries (5 × linear 5 s) and the permission-error difference are identical to the IMU manager.

Read Loop & Two-Pass Disambiguation

ConstantValuePurpose
POLL_INTERVAL0.02 s (~50 Hz)Sleep between polls
GESTURE_COOLDOWN0.3 sDefault minimum gap between gestures; overridden by the gestureCooldown setting
GES_FORWARD_WAIT0.30 sSettle time after an initial FORWARD flag
GES_BACKWARD_WAIT0.40 sSettle time after an initial BACKWARD flag
GES_POST_FLUSH0.10 sRead-and-discard window after a confirmed gesture

Each iteration reads both flag registers in one 2-byte block read from 0x43, then:

  1. No flag set → sleep POLL_INTERVAL, continue.
  2. Cooldown gate: if less than the cooldown has passed since the last accepted gesture, ignore and sleep.
  3. FORWARD flag: sleep 300 ms, re-read. If the re-read decodes to a gesture other than FORWARD/BACKWARD, use it (the approach was really the start of a swipe); otherwise it is a FORWARD.
  4. BACKWARD flag: same with a 400 ms wait.
  5. Anything else (directional, rotation, wave): sleep 20 ms and read again as a "confirmation". As written, all three outcome branches (first == second, second different, second empty) assign gesture = first, so the confirmation read currently acts as a 20 ms delay and never changes the result.
  6. Accept: bump the count, stamp last_gesture_time, emit gestureDetected(name); look up the action; if it is not "none" emit actionTriggered(action) and log <gesture> -> <action> (#n).
  7. Post-flush: for 100 ms read and discard the flag registers every 10 ms so the tail of the same hand motion cannot fire twice.
  8. Sleep POLL_INTERVAL.

Python: an exception in the loop emits "Error", closes the bus and schedules a retry. C++: failed reads return zeros and the loop continues (same asymmetry as the IMU).

Design Decisions

Each rationale below is taken from source comments or commit messages, not inferred.

Worker threads for I2C, an event loop for serial

The IMU and gesture drivers run their loops on dedicated threads (Python threading.Thread, C++ QThread + worker QObject) rather than QTimer ticks on the GUI thread. The measurement in f1eb526 is the reason it has to be that way: one IMU iteration blocks on the bus for ~4.3 ms (80 %+ of the period), and the gesture loop deliberately sleeps 300–400 ms mid-detection. Neither can share the thread that paints QML at 60 fps. The price is that every emitted value crosses threads as a queued signal, which is exactly what the emission gating below manages. The ESP32 knob, by contrast, sends a few bytes per second: C++ lets QSerialPort integrate with the event loop (readyRead), and Python (94d61be) blocks in readline() with the GIL released "instead of polling in_waiting at 100 Hz for a knob that sends a few bytes a second".

A paced loop instead of "read as fast as you can"

ed826ed: the loops used to sleep a fixed 1 ms, which "with three I2C reads per iteration kept the bus saturated and left the worker thread in D-state at ~9 % CPU on the Orange Pi. The LSM6DSL ODR is 416 Hz and the emit rate is 60 Hz, so reading that fast bought nothing." The 5 ms period is chosen to stay under the sensor ODR (no duplicate samples) while giving the filter 3+ samples per emit, and sleeping out the remainder makes the cadence independent of bus speed. Moving the barometer from "every 80th iteration" to a time-based interval removed a cadence that only approximated 5 Hz at the old loop rate. f1eb526 then corrected the record: the old loop was not spinning, it was bus-bound, so the CPU shown is the cost of reading the sensor; the explicit period is kept for its predictability and the 100 Hz option is documented for anyone who wants the CPU back.

Emission gating rather than stopping the sensor

94d61be keeps "sampling and Madgwick fusion at full rate, but the seven queued signals per tick into QML drop from 60 Hz to 5 Hz" when nothing consumes them. Stopping the loop instead would lose the gyro-integrated attitude and the tare context, and would make the first frame after opening CarMenu wrong; 5 Hz still keeps the Settings status line and hub tiles honest. Driving it from Main.qml's StackView means pages "need no changes". 2fef514 widened the full-rate set once dashboards and home cards started reading the IMU through OBDParameterModel, so the consumer list is a property of what is on screen, not of which page type it is.

One quaternion, yaw stripped, heading from the raw magnetometer

The module docstring states the goal: "outputs a quaternion directly to the 3D model, completely avoiding gimbal lock. No Euler angle clamping, no cascaded EMA stages. One filter, one quaternion, 1:1 mapping." Yaw is removed because the model only needs pitch and roll and heading drift must never rotate it; the compass value is computed from the magnetometer directly because that "avoids drift". Freezing the filter when the deadbanded gyro is zero stops the accelerometer correction from producing visible settling on a parked vehicle. The magnetometer is left out of the fusion entirely (zeros are passed), which is consistent with those two choices even though it leaves the 9DOF code idle.

Tare over persistent mounting calibration

Rather than a mounting-angle setting, the user presses ZERO on a level surface. The tare is a quaternion captured in the same yaw-stripped domain as the output "so the tare operates in the same domain as the values it's applied to", and it captures the accelerometer bias at the same moment so the G displays zero with it. Gyro bias is re-measured on every start because it is temperature-dependent; the tare is not persisted.

A single volume entry point

backend/volume_utils.py explains it: "Before this module existed, the curve was hardcoded in ~9 call sites across main.py and QML. If the curve ever changed, every site had to change in lockstep. This module centralizes both the math and the dispatch" (commit d2b047b, "volume curve de-duplication"). Hardware handlers therefore never call a manager's setVolume; they call applyVolume(currentVolume + delta). The C++ header adds the reason for the signal-based fan-out: "VolumeController doesn't need pointers to managers that may not exist yet." The delta accumulator exists because the knob step can be as small as 0.25 %, and applyVolume takes an integer percent.

LED debounce, keepalive and sleep

The 50 ms trailing debounce ("max 20 updates/sec") exists "to prevent LED flickering during rapid slider drags" while always delivering the final value. The 2 s keepalive is sized against the dongle's 5 s LED timeout, and LED sleep is implemented by simply not sending keepalives, so the firmware needs no extra command and the ring goes dark on its own when OCTAVE exits ("LEDs turn off when OCTAVE closes" is the default's rationale).

Two-pass gesture disambiguation and post-flush

From the source: forward/backward "are compound gestures (hand approaching/leaving) that the sensor often initially reports as directional. Wait and re-read to let the sensor settle on the final gesture." The waits (300 / 400 ms) and the init table follow the DFRobot reference driver. The 100 ms flush after a confirmed gesture keeps "the same motion" from firing twice, and the user-tunable cooldown is the coarse guard above that.

Linear retries, permission errors excluded

Both I2C managers retry five times at 5 s × n. A missing /dev/i2c-2 may appear later (overlay loading, hot-plug), so it is retried; a PermissionError in Python is not, because only the user can fix group membership. The C++ worker cannot distinguish the two (open() just fails) and retries both.

Compile-time stubs for mobile

Rather than #ifdef-ing every QML binding, each hardware header carries a mobile stub with the same names; 78ab72c added the signals "QML Connections handlers reference" to those stubs so the shared frontend loads unchanged on Android. The IMU is the one manager with a real mobile implementation because a phone has the sensors on board.
