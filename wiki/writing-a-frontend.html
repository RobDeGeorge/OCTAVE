What a Frontend Is

OCTAVE has two halves. The core holds everything that matters: the connection to the car, the music, the phone, the settings. A frontend is the screen on top. The screen OCTAVE ships with is one frontend; any other program can be one too, by talking to the core over a socket. That socket is called the service. 

  your frontend        the built-in screen       a script, a phone page
  (any language)             (QML)
        |                      |                          |
        |   JSON over TCP or WebSocket, port 9876         |
        +----------------------+--------------------------+
                               |
                   +-----------+-----------+
                   |      OCTAVE core      |
                   |  car - music - phone  |
                   +-----------------------+

The built-in screen uses nothing your frontend cannot reach, and a test (tst_conformance) keeps it that way. So a frontend can be a whole replacement screen, a remote on a phone, a second display, or a ten-line script that skips a track.

This page is a walkthrough: follow it top to bottom and you end with a working frontend installed in OCTAVE. The list of every object and member is the Service API Reference; five complete frontends to read are in the Frontend Gallery.

The Five-Minute Start

You need neither a car nor a build of OCTAVE. Download a release from GitHub Releases (or build it; see Building). Below, octave stands for that program.

1. Run the core with a simulated car

octave --headless --sim

--headless starts the core and the service with no window: your frontend is the screen. --sim adds a simulated car (a real OBD connection to a simulated adapter, with every reading, a VIN and trouble codes), motion-sensor readings that move with it, and three short test tracks. It runs on a throwaway config folder that is deleted on exit, so it never touches an OCTAVE you use. --config DIR keeps the config in DIR instead. Leave out --headless to see the same car in the built-in screen next to yours.

The service now listens on 127.0.0.1:9876.

2. Talk to it by hand

The protocol is one JSON object per line over TCP. Open a connection with nc 127.0.0.1 9876 and type the lines below (send the first within 10 seconds, or the connection is closed). Lines marked ← are what comes back. 

{"op":"hello","id":1}
← {"id":1,"ok":true,"result":{"protocolVersion":3,"auth":"trusted","loopbackOpen":true,"scopes":["full"],
     "app":{"version":"...","build":"release","headless":true},"objects":["airPlayManager", ...]}}

{"op":"get","object":"volumeController","property":"percent","id":2}
← {"id":2,"ok":true,"result":32}

{"op":"call","object":"obdManager","method":"setParameterDemand","args":["my-frontend",["RPM","SPEED"]],"id":3}
← {"id":3,"ok":true,"result":null}

{"op":"subscribe","object":"paramStore","properties":["RPM","SPEED"],"throttleMs":500,"id":4}
← {"id":4,"ok":true,"result":{"sub":1}}
← {"event":"params","sub":1,"object":"paramStore","values":{"RPM":800,"SPEED":0},"t":51234}
← ... another whenever a value changes, at most every 500 ms

{"op":"call","object":"sim","method":"setThrottle","args":[60],"id":5}
← {"id":5,"ok":true,"result":true}
← ... and the RPM and speed in the events climb

What just happened:

  1. hello says who you are talking to. Check protocolVersion: it is 3.
  2. get read one value, the volume in percent.
  3. call ran a method. OCTAVE only asks the car for readings somebody shows, so you told it which two you want, under a name of your own.
  4. subscribe asked for those readings as they change. The reply carries a subscription id; every event after it carries the same sub.
  5. Another call pressed the simulated accelerator.

Every request has an op. The id is optional and is echoed in the reply, so you can send several requests without waiting. Every reply has ok; a failure is {"ok":false,"error":"..."}, sometimes with a code a program can act on (Rules of the Road). A message with an event key is not a reply, and can arrive between a request and its reply.

3. The same in an SDK

The Python client needs nothing but Python 3.8 and a copy of the repository. From the repository root, with the core from step 1 still running: 

import sys; sys.path.insert(0, "sdk/python")
from octave_client import Client

with Client() as octave:                 # 127.0.0.1:9876; says hello and checks the version
    print(octave.get("volumeController", "percent"))
    octave.call("obdManager", "setParameterDemand", "my-frontend", ["RPM", "SPEED"])
    octave.subscribe("paramStore", properties=["RPM", "SPEED"], throttle_ms=500)
    octave.call("sim", "setThrottle", 60)
    for event in octave.events(timeout=5):   # runs until you press Ctrl+C
        print(event.get("values"))

That is the whole pattern: read, subscribe, call. For a complete small frontend to copy, go to Starter Projects and SDKs.

The Ideas

Objects. The core is a set of named objects, one per feature: nowPlaying, volumeController, obdManager, settingsManager and about thirty in all. hello lists their names.

Properties are an object's state. Read one with get. A few are writable and take set, which answers with the value read back: 

{"op":"set","object":"volumeController","property":"muted","value":true}
{"op":"set","object":"settingsManager","property":"showClock","value":false}

Methods do things, and are what the touch screen calls too. Most state is read-only and changes through a method. args is a list in the method's order; the reply is the return value, or null. A method runs on the app's main thread, so a slow one holds the built-in screen just as a tap would. 

{"op":"call","object":"nowPlaying","method":"next"}
{"op":"call","object":"volumeController","method":"applyVolume","args":[40]}

Signals are moments: a track changed, an export finished. You cannot ask for one; you subscribe and wait.

describe: what an object offers

{"op":"describe","object":"nowPlaying"} answers with that object's properties (type, writable or not), methods (parameters, return type) and signals, and the permission each change needs. Without object it describes every object and lists the ops this server understands. The same data is in the repository as docs/api/<object>.json, and as a page in the API reference, so you can write code against the files and check at run time. docs/api/protocol.json describes the protocol itself (every op, reply, event and error) as JSON Schema, for writing a client in a language with no SDK.

Subscriptions

One subscribe follows any number of properties and signals of one object: 

{"op":"subscribe","object":"nowPlaying","properties":["title","artist","playing"],"signals":["trackChanged"],"throttleMs":250,"id":6}
← {"id":6,"ok":true,"result":{"sub":2}}
← {"event":"property","sub":2,"object":"nowPlaying","name":"title","value":"Dream On","t":61200}
← {"event":"signal","sub":2,"object":"nowPlaying","name":"trackChanged","args":[],"t":93410}

Each property arrives once at the start with its current value, then on every change, so you never need a get first. throttleMs limits each property to one event per interval, carrying the latest value. The reply with your sub id always comes before the first event. {"op":"unsubscribe","sub":2} ends one; closing the connection ends them all.

Live readings from the car

Readings from the car and the motion sensor live in one object, paramStore, keyed by ids such as RPM, SPEED and COOLANT_TEMP. Subscribe with the ids as properties and you get params events, each holding the values that changed. Two things to know:

  • Ask for what you show. OCTAVE polls the car only for readings somebody wants. Call obdManager.setParameterDemand("my-frontend", [ids]) for what is on your screen, and again with an empty list when it leaves. Pick a name of your own. If your connection closes, OCTAVE releases your demand for you.
  • Values are in the car's native unit (°C, MPH, kPa). docs/api/parameters.json lists every id with its title, unit and range. To show the units the user picked, read parameterCatalog.displayParameters and convert with parameterCatalog.toDisplay(id, value).

Rows

The protocol can serve long lists as models: get answers a summary, the rows op gives the rows, and a subscription sends model events (reset, insert, update, remove) to replay in order. No object serves a list this way yet; the lists there are (trips, dashboards, the phone's queue) are ordinary properties.

Streams: the phone's screen

Video does not fit in JSON, so it comes as binary records on the same connection. Ask with {"op":"stream","object":"phoneMirrorManager","name":"video"} for the mirrored phone (H.264), or androidAutoManager / frames for Android Auto (JPEG pictures). A browser decodes the H.264 with WebCodecs; touches go back through phoneMirrorManager.injectTouch(pointerId, action, relX, relY). To develop without a phone, run --headless --sim and call sim.setVideo(true), which plays a test clip into the phone stream. The record layout and the rules for joining and falling behind are in docs/api/README.md, "Streams".

Pictures and files over HTTP

The service port also answers a few HTTP GET requests. /art is the cover of what is playing (404 when there is none). Subscribe to nowPlaying.artRevision, which goes up with every new cover, and put it in the address so the browser does not show a stale one: <img src="/art?rev=12">. /art?song=<file name> is the cover of a song in the library and /art?queue=<id> of an item in the phone's queue.

Exports work in two steps: ask the core to export, then download the result. tripRecorder.exportTrip(id) then /export/trip (add ?format=json for JSON), dashboardManager.exportDashboard(id) then /export/dashboard, diagnosticsManager.exportLogs() then /export/logs. Only the last export of each kind is served.

Pairing and Permissions

A program on the same device as OCTAVE is trusted and needs none of this. A client anywhere else, such as a phone on the car's Wi-Fi, has to pair once, the way a Bluetooth speaker does.

First the service has to be on and reachable. It is off unless one of these turns it on:

octave --service                      # the built-in screen, plus the service
octave --service 9900                 # on another port
octave --headless                     # no screen at all
octave --service --service-bind 0.0.0.0   # reachable from other devices, not only this one

The Service switch in Settings > Device > Developer turns it on at every start (the serviceEnabled setting). Then:

  1. The user opens Settings > Device > Developer > Service and taps Show a code under Pair a device. A 6-digit code shows for 2 minutes and works once.
  2. Your client sends {"op":"pair","code":"123456","name":"Kitchen tablet","scopes":["media"]} and gets {"token":"...","scopes":["read","media"]}. The connection is trusted from that moment. Store the token.
  3. Every later connection starts with {"op":"hello","token":"..."}. If hello answers "auth":"untrusted","tokenRejected":true, the user revoked the device: show your pairing screen again.

Until it pairs, a client gets "code":"unauthorised" for every op but hello and pair. With no screen to read the code from (--headless), run octave --pair-code on the device: it prints a code from the running OCTAVE. Under --sim, sim.pairingCode() over a local connection does the same.

Scopes are the permissions a paired device holds. Every paired device can read. Changing something needs the scope of that method or property, which describe and the API reference list; without it the answer is "code":"forbidden". Ask only for what your frontend changes: leaving scopes out of pair asks for full.

ScopeLets a device change
readNothing. Reading, and the demand calls a reading client needs, are always allowed.
mediaPlayback, volume, the queue
vehicleThe OBD connection and trouble codes, adapters, sensors, the shift light
phonePhone mirroring and Android Auto. Their video streams need it too.
settingsSettings
filesThe library and playlists, dashboards, trips, logs, and the /export downloads
systemRestart, shut down, installing frontends
fullEverything

The user sees each paired device under Paired devices on the same Settings card and can make it read only or revoke it; a revoked device's connections close at once.

Pictures and downloads. Off the device, /art and /export/... need trust too. A program sends Authorization: Bearer <token>. A browser page asks {"op":"mediaTicket"} for a ticket that lasts 10 minutes and uses /art?ticket=.... Never put the token itself in an address.

Browsers. A web page can connect only if OCTAVE itself served it, and only when opened by IP address (http://192.168.1.20:9876/, not a name). This stops a website open on the same machine from driving the car. To have OCTAVE serve your page, start it with --web-root DIR, the folder holding your index.html. Your page then opens a WebSocket to ws://<same host>:9876/ and sends the same JSON, one message per text frame. Programs that are not browsers are not restricted this way. More in the service protocol.

Traffic is not encrypted
Pairing keeps strangers out, but anyone on the network can read what passes. Use --service-bind only on a network you control.

Installing Your Frontend

Once your frontend works, OCTAVE can show it as its screen. Add a file named octave-frontend.json at the top of its folder: 

{
  "id": "com.example.dash",          // lower case, digits, . _ -
  "name": "Example Dash",
  "version": "1.2.0",
  "description": "Big gauges for the track",
  "preview": "preview.png",          // optional: its picture in Settings (.png, .jpg, .webp, up to 4 MB)
  "protocol": [2, 3],                // the protocol versions it speaks, lowest and highest
  "scopes": ["read", "media"],       // the permissions it asks for
  "web":  {"root": "dist"}           // a web frontend: the folder with index.html
  // or
  "exec": {"linux":   ["bin/dash", "--fullscreen"],
           "windows": ["dash.exe"],
           "macos":   ["bin/dash"]}  // a program frontend: what to run on each platform
}

Give exactly one of web and exec. Paths are relative to the folder and cannot leave it. An exec program is either inside the folder or a bare name found on PATH (python3, with your script as an argument); {dir} in an argument becomes the folder's path. Unknown keys are ignored.

  1. Open Settings > Device > Developer > Frontends.
  2. Tap Install from folder or Install from zip. OCTAVE checks the manifest, copies the frontend into <config>/frontends/<id>/ and runs nothing. It refuses a folder with links in it, more than 10,000 files or more than 256 MB, so install your built output, not your source tree.
  3. Each installed frontend is a box with its picture, name and permissions. Tap the box to make it the screen from the next start; Restart now applies it at once. The Built-in box goes back.
  4. For a program frontend, Try restarts OCTAVE on it and comes back to the current screen by itself after two minutes.

The same over the service, with the system scope: frontendManager.installFromFolder(path), installFromZip(path), setActive(id) ("" is the built-in screen), tryFrontend(id, seconds), restartNow(), remove(id). frontendManager.frontends is the list and lastError says why something was refused. The two starters with a manifest (templates/hello-car-js, templates/hello-car-python) install as they are.

When a web frontend is the screen

OCTAVE serves it at http://<address>:9876/ in place of the reference page, and turns the service on to do so. The built-in screen stays on the display; your page is opened in a browser, on the device or on a phone. In a browser on the device it holds exactly the scopes in its manifest. In a browser elsewhere it pairs as usual.

When a program frontend is the screen

OCTAVE starts with no screen of its own and runs your program in its folder. Not on Android, iOS or the browser demo. Your program finds the service in its environment:

VariableHolds
OCTAVE_HOST, OCTAVE_PORTWhere to connect (127.0.0.1 and the service port)
OCTAVE_TOKENA token for this run, holding exactly your manifest's scopes. Send it with hello first.
OCTAVE_PROTOCOL, OCTAVE_SCOPES, OCTAVE_FRONTEND_DIRThe protocol version, your scopes (comma separated), your folder

What OCTAVE expects of it:

  • Use the token. During such a run no local program is trusted without one, so a frontend cannot get more than it asked for by leaving the token out. Other programs on the device need to pair too (octave --pair-code).
  • Exit code 0 means the user quit, and OCTAVE quits too. Any other ending is a crash: OCTAVE starts your program again after 1 second, then 2, 4, up to 30. Quitting within 3 seconds of starting also counts as a crash.
  • Five crashes in a row, each within a minute of starting, and OCTAVE goes back to the built-in screen and stays there until the user picks a screen again.
  • Quit when asked. When OCTAVE wants your program to stop, it closes your standard input and sends SIGTERM (Linux, macOS) or WM_CLOSE to your windows (Windows). A console program on Windows gets neither signal nor message, so watch for standard input ending, as templates/hello-car-python/hello_car.py does. A program still running after 3 seconds is killed.
  • Log sparingly. Your output goes to OCTAVE's log, up to 200 lines a second; the rest is dropped.
  • During a trial, frontendManager.trialSecondsLeft counts down. Show it, with a "Keep this screen" button that calls frontendManager.keepTrial().
The driver's way back
Pressing mute five times within four seconds always returns to the built-in screen, from the volume knob, the gesture sensor or your own mute button. It works even if your frontend hangs. Do not use five quick mute presses for anything else. From a keyboard, octave --qml starts the built-in screen for one run.

The scopes limit what a program frontend does over the socket, not what it does as a process: it runs as OCTAVE's own user and can read the config folder. Install only frontends you trust.

Frontends in the Browser Demo

The browser demo is the real core compiled to WebAssembly, so a web frontend runs against it with nothing installed.

The frontend playground (robdegeorge.com/OCTAVE/playground.html) runs one web frontend beside the core and its simulated car. It offers the bundled ones (the JavaScript starter, glass, sunlight, arcade, retro-cluster), and playground.html?frontend=<url> loads yours from any host that allows cross-origin requests (GitHub Pages does). That makes a link enough to show someone your frontend running. The page asks the visitor before it runs a frontend that came in a link. Your frontend needs no changes: it opens its WebSocket as usual. What is missing there: localStorage (it throws), /art and /export, video streams, and pairing.

The web frontends list. In the demo itself, Settings > Device > Developer > Frontends lists the site's web frontends the way a head unit lists installed ones. Tapping one shows it over the built-in screen at once. Its OCTAVE button, or five mute presses, brings the built-in screen back. Program frontends are listed greyed out: they cannot run in a browser. Nothing can be installed or removed there.

Rules of the Road

Versions. The protocol version is 3. It goes up only when something breaks: a member removed, renamed or retyped. Additions do not change it, so ignore fields, objects and events you do not know. Accept the versions you were written for and refuse a later one you have never seen. What each version changed is in docs/api/CHANGELOG.md.

  • A member marked deprecated in describe still works and says what to use instead. The older snake_case method names (next_track) are deprecated in favour of camelCase (nextTrack).
  • A member or object marked "stability":"experimental", such as sim, may change in any release.
  • Requests that use an action key instead of op are developer tooling. They exist only in developer builds and are not part of the API. Do not build on them.

Limits. One client can never slow the car's screen, so each connection has limits. A well-behaved frontend never meets them.

LimitWhat happens past it
200 requests a second, 400 in a burstThe request does not run and answers "code":"rateLimited" with retryAfterMs. Wait that long and send it again.
Events you have not readThe oldest are dropped, and {"event":"dropped","count":N} says how many. A client that stays behind for 15 seconds is disconnected.
64 connections in all, 8 from one network addressFurther ones are closed at once.
Silence: 10 seconds before the first byte, 60 seconds while unpairedClosed.
One request: 1 MBClosed.

When a connection drops, reconnect with a growing delay (1 second, doubling), then say hello and subscribe again: subscriptions do not survive a connection. The three error codes a program should act on are unauthorised (pair first), forbidden (a missing scope) and rateLimited. Every other failure is a message for a person in error.

Not available yet:

  • Encryption of the connection.
  • A sandbox for installed program frontends.
  • Program frontends on Android, iOS and in the browser demo.
  • The Go SDK as a published module.

Your Frontend, Your License

OCTAVE itself (the core and the built-in screen) is GPL-3.0-or-later. Everything you would copy into a frontend is MIT: the clients in sdk/, the starters in templates/ and the examples in examples/frontends/, each with its own LICENSE. Copy them, keep the MIT notice, and license the rest of your frontend however you like, open or closed.

A frontend that only talks to OCTAVE over the service is a separate program: it neither links OCTAVE's code nor copies it. The project's intent, and its reading of the GPL, is that such a frontend is not a derivative work and need not be GPL, however it is installed or started. That is a statement of intent, not legal advice. What does fall under the GPL: changes to OCTAVE's own code (src/, frontend/) and a fork of the built-in screen.
