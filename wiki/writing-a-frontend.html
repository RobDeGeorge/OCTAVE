Writing a Frontend

Build your own OCTAVE screen, remote or script in any language: start the service, connect, discover, read, subscribe, control. The QML UI is one client of this API; yours can be another.

What You Get

Every manager the bundled UI uses: settings, media and now playing, volume, OBD and the live value of every PID and IMU reading, the black box, the shift light, phone mirroring control, downloads, dashboards. Each one's properties, methods and signals are listed with their types in the generated Service API Reference (docs/api/); what they mean is in Signals & Slots API. tst_conformance guarantees the bundled UI uses nothing outside that list, so whatever it can do, your frontend can too.

Three working clients come with the repo: sdk/web/index.html (plain JavaScript, about 250 lines), sdk/python/octave_client (stdlib only) and sdk/typescript (an npm package for browsers and Node, with types generated from docs/api/ so a wrong call fails to compile). Read one of them next to this page.

Whole frontends in other languages live in frontends/ (index and a feature-by-feature parity matrix in frontends/README.md and frontends/PARITY.md):

  • frontends/glass/: TypeScript + Svelte, served by the app itself with --web-root frontends/glass/dist, with every page of the bundled UI (media, vehicle, dashboards and their editor, trips, settings, downloads, phone); its client is src/lib/octave.ts.
  • frontends/console/: a Python + Textual operator console on the Python SDK: every PID with per-row demand, the OBD connection and trouble codes, trips, every setting (found with describe), downloads and an API explorer.
  • frontends/sunlight/: a Go + Gio high-contrast screen for direct sunlight that draws the user's dashboards from their JSON specs with its own gauge code, with a plain net + encoding/json client in link/.
  • frontends/retro-cluster/: a Rust + egui 1980s instrument cluster (live gauges, every PID, trouble codes, trips, a spectrum analyzer, the tape deck) whose protocol client is one file, src/link.rs.

1. Start the Service

It is off by default. Any of these turns it on, listening on 127.0.0.1:9876: For the smallest possible client, see frontends/arcade/: C + SDL2, an 8-bit arcade dashboard (drive, media with the cover from GET /art, trouble codes) whose client is src/link.c, POSIX sockets and cJSON.

./build/octave --service              # the normal UI, plus the service
./build/octave --service 9900         # another port
./build/octave --headless             # no UI at all: your frontend is the screen

Or set "serviceEnabled": true in settingsConfigure.json (Settings Reference) to have it at every start. For a phone or a second screen on the car's network add --service-bind 0.0.0.0; read Versioning and Security first. A developer build's --dev --profile also starts it, with a simulated car that makes the OBD values move.

2. Connect

Two transports on the same port carry the same JSON messages:

  • TCP, one JSON object per line, for any language with sockets. Requests carry op and an optional id, which the reply echoes so you can send several at once.
  • WebSocket (ws://host:9876/), one object per text frame, for browsers. A browser may only connect from the service's own page, i.e. served by the app at http://host:9876/ and opened by IP address. To host your own page there, start the app with --web-root DIR (your built frontend: the directory holding its index.html; or the serviceWebRoot setting) and open http://host:9876/; see the service protocol for what it serves and refuses. Non-browser WebSocket clients send no Origin and are not restricted.
# a whole session by hand
$ printf '{"op":"hello","id":1}\n{"op":"get","object":"volumeController","property":"percent","id":2}\n' | nc -q1 127.0.0.1 9876
{"id":1,"ok":true,"result":{"app":{"build":"release","headless":false,"version":"1.0.0"},"objects":["settingsManager",...],"protocolVersion":1}}
{"id":2,"ok":true,"result":32}

Every reply has ok; a failure has "ok": false and an error string. Anything with an event key is not a reply but a subscription event, and can arrive between replies.

3. Discover

  • hello: the protocol version (check it), the app version, whether it is headless, and the object names.
  • describe {object}: that object's properties (type, writable, notify signal, enum keys), methods (parameter types, return type) and signals. describe with no object returns all of them (about 110 KB). It is the same data as docs/api/<object>.json, so you can code against the files and check them at run time.
  • docs/api/parameters.json (or get parameterCatalog parameters): every OBD PID and IMU reading with its title, native unit, range and decimals.

4. Read and Subscribe

{"op":"get","object":"nowPlaying","property":"title","id":3}
{"op":"subscribe","object":"nowPlaying","properties":["title","artist","playing","positionMs"],"throttleMs":250,"id":4}
← {"id":4,"ok":true,"result":{"sub":1}}
← {"event":"property","sub":1,"object":"nowPlaying","name":"title","value":"Dream On","t":12345}   # the current value at once, then each change
  • Order: the subscribe reply, with your sub id, always arrives before any event of that subscription, on both TCP and WebSocket, even with requests pipelined. Your client still has to handle the reply before it reads the next message: a JavaScript client that resolves a promise in onmessage and registers the sub in a later .then can see the first event before the registration.
  • Properties: a property event with the value at once and on every change. throttleMs caps it at one event per property per interval, carrying the latest value.
  • Signals: "signals": ["trackChanged"] gives signal events with the arguments.
  • Live OBD and IMU values: subscribe to paramStore with the ids you show as properties. You get params events, {"values": {"RPM": 2210, "SPEED": 41}}, in the native unit. OCTAVE only polls the car for what someone shows: call obdManager.setParameterDemand("my-frontend", ["RPM","SPEED"]) for the ids on your screen, and an empty list when they leave it. If your connection closes (or the client is killed), the app releases every consumer that connection registered through setParameterDemand, setBackgroundDemand and berryIMU.setDemand, so pick a consumer name of your own: one the QML UI also uses would be released with yours.
  • Lists (search results, the download queue): get gives a summary, rows the rows, and a subscription sends model events (reset, insert, update, remove) to replay in order.

A connection's subscriptions end with it. If you stop reading, the oldest events are dropped and a {"event":"dropped","count":N} says how many.

5. Control

{"op":"call","object":"nowPlaying","method":"next","id":5}
{"op":"call","object":"volumeController","method":"applyVolume","args":[40],"id":6}
{"op":"set","object":"volumeController","property":"muted","value":true,"id":7}
{"op":"call","object":"settingsManager","method":"save_show_clock","args":[false],"id":8}

Most state is read-only and changes through a method, the same one the touch screen calls: settings through their save_* slots, media through nowPlaying, volume through volumeController. Arguments are converted to the declared types (an enum by name or number), and overloads are told apart by argument count. Methods run on the app's GUI thread, so a slow one holds the bundled UI just as a tap would.

Your First Frontend in 60 Lines

Everything above, in one page on the TypeScript SDK (sdk/typescript): it connects to the app that serves it, pairs when the browser is not on the head unit, shows two live readings, the track with transport, and the cover. The whole thing is sdk/typescript/examples/first-frontend/: index.html (a status line, a pair form, two gauges, a now-playing row) and this app.js, no framework and no bundler.

cd sdk/typescript && npm install && examples/first-frontend/build.sh      # builds the SDK, copies it to lib/
./build/octave --dev --service --web-root sdk/typescript/examples/first-frontend   # a simulated car; open http://127.0.0.1:9876/
// A first OCTAVE frontend with the TypeScript SDK, in 60 lines: connect, pair
// when this browser is not on the head unit, two live gauges, a now-playing
// line with transport, the cover. Build the SDK, then serve this folder from
// the app (see README.md).
import { OctaveClient, obj } from './lib/index.js'

const $ = (id) => document.getElementById(id)
const client = new OctaveClient({ token: localStorage.getItem('token') ?? undefined })   // ws://<this page's host>/
const obd = obj(client, 'obdManager')
const now = obj(client, 'nowPlaying')

client.on('status', (s) => { $('status').textContent = s === 'online' ? `OCTAVE ${client.hello?.app.version}` : s })
client.on('hello', (h) => {
  // Protocol 2: over the network we must pair once; on the head unit nothing to do.
  if (h.tokenRejected) localStorage.removeItem('token')
  $('pair').style.display = h.auth === 'untrusted' ? 'block' : 'none'
  if (h.auth !== 'untrusted') start()
})
$('pair').onsubmit = async (e) => {
  e.preventDefault()
  try {
    localStorage.setItem('token', await client.pair($('code').value, 'First frontend'))
    client.close(); client.connect()                         // a fresh, trusted connection re-issues everything
  } catch (err) { $('pairError').textContent = err.message }
}

let started = false
async function start() {
  if (started) return
  started = true
  // Live readings: the app polls the car only for what someone asks for.
  await obd.call('setParameterDemand', 'first-frontend', ['SPEED', 'RPM'])
  client.params(['SPEED', 'RPM'], (v) => { for (const id in v) $(id).textContent = v[id] === null ? '–' : Math.round(v[id]) }, 100)
  // Now playing: the properties arrive at once, then on every change.
  now.subscribe({ properties: ['hasTrack', 'title', 'artist', 'playing', 'artRevision'], throttleMs: 250 }, (e) => {
    if (e.event !== 'property') return
    if (e.name === 'title' || e.name === 'hasTrack') $('title').textContent = e.name === 'hasTrack' && !e.value ? 'Nothing playing' : e.value || $('title').textContent
    if (e.name === 'artist') $('artist').textContent = e.value
    if (e.name === 'playing') $('play').textContent = e.value ? '⏸' : '▶'
    if (e.name === 'artRevision') cover(e.value)
  })
}
async function cover(rev) {
  // Over the network /art needs a short-lived ticket; on the head unit it is harmless.
  const t = client.hello?.loopbackOpen && location.hostname === '127.0.0.1' ? '' : `&ticket=${(await client.mediaTicket()).ticket}`
  $('cover').src = rev > 0 ? `/art?rev=${rev}${t}` : ''
}
$('play').onclick = () => now.call('togglePlay')
$('next').onclick = () => now.call('next')
$('prev').onclick = () => now.call('previous')
client.connect()

What each part leans on:

  • Connect. new OctaveClient() defaults to the page's own host, so the page works wherever the app serves it; connect() reconnects with backoff and re-issues the subscriptions on each new link. A token from an earlier pairing goes with hello.
  • Pair when untrusted. On the head unit hello says "auth": "trusted" and the form stays hidden. Over the network it says untrusted: the page asks for the 6-digit code (Settings, Service, Pair a device), client.pair(code, name) returns the token to keep, and a fresh connection carries it. A token the app rejects (tokenRejected) is dropped.
  • Live readings. obdManager.setParameterDemand("first-frontend", ["SPEED", "RPM"]) makes the app poll those two PIDs (it polls only what someone shows); client.params([...], cb, 100) delivers them in native units, at most ten times a second.
  • Now playing. One subscription to nowPlaying's properties: the current values arrive at once, then every change. The buttons call togglePlay, next, previous through the typed facade (obj(client, 'nowPlaying')): a method that does not exist does not compile.
  • The cover. GET /art?rev=N with nowPlaying.artRevision as the cache key; over the network the URL also carries a short-lived ticket from mediaTicket, never the token.

Run against a developer build with --dev --service-bind 0.0.0.0 and opened by the machine's LAN address, the page showed the pair form, took a code from sim_pairing_code, and then read the simulated car and the cover like a page on the head unit.

Being the Only UI

octave --headless runs every manager and the service with no QML engine and no window (the offscreen Qt platform), using about a fifth less memory than the full app. Music, OBD polling, the black box, the knob, gestures and the IMU all keep working; your frontend is the screen. It needs the service, so it exits if the service can't start. hello reports "headless": true.

In a developer build (OCTAVE_DEV_TOOLS, the default for Debug) octave --headless --dev adds the simulated car behind the real OBDManager and simulated IMU motion, so OBD values, the G-force and the compass move with no adapter and no QML UI. Drive it with the dev-only sim_* actions on the same port, for example {"action":"sim_throttle","args":{"value":80}} or {"action":"sim_scenario","args":{"name":"overheat"}} (Development); never send them from a shipped frontend.

The SDK's launch_headless() starts one with a throwaway config, the easiest way to test a frontend or a script: sdk/python/tests/test_client.py does exactly that.

Versioning and Security

  • Versioning. protocolVersion is 2. Accept the versions you know and refuse an unknown later one; it changes only on a breaking change (something removed, renamed or retyped, or, for 2, pairing). Additions don't change it, so ignore fields, objects and events you don't know. The rule, the history and what version 2 broke are in docs/api/README.md.
  • Pairing. On the head unit itself nothing is needed (unless serviceLoopbackOpen is off). Over the network your client pairs once: the user opens Settings > Service > Pair a device, you send {"op":"pair","code":"123456","name":"My dash"} and keep the token; later connections start with {"op":"hello","token":"..."} (a revoked or unknown token gets "auth": "untrusted", "tokenRejected": true: pair again). Until then every op but hello and pair answers "code": "unauthorised". For <img> and downloads ask {"op":"mediaTicket"} and use /art?ticket=...; never put the token in a URL. A revoked device's connections are closed. Details: docs/api/README.md, "Pairing".
  • The network. Bind beyond loopback (--service-bind) only on a network you control: pairing keeps strangers out, but traffic is not encrypted.
  • Browsers are held to the app's own page, opened by IP address (the Origin rule), so a website open on the same machine can't drive the car.
  • Dev-only actions (navigate, click, screenshot, sim_*) exist only in developer builds with --profile, aren't versioned, and drive the bundled UI rather than the managers. Don't build on them.

Changing settings

Each setting has a save_* slot that validates it and notifies (settingsManager.save_theme_setting("NeonMatrix")). To change several at once call settingsManager.apply_settings({"backgroundGrid": "Normal", "backgroundBlurRadius": 40}): every key goes through its own slot, values must already have the right JSON type, and the reply lists applied keys and refused ones with the reason. The Now Playing presets are settingsManager.nowPlayingPresets; apply one with applyNowPlayingPreset("Cinema"). serviceEnabled and serviceWebRoot can't be set over the service at all: they are edited in settingsConfigure.json.

Choosing the music folder

With no native folder picker, browse with mediaManager.browse_music_folders(path): "" gives the browse roots ({roots: [{name, path}]}: your Music folder (not the whole home folder), /media, /mnt, /run/media, /storage, the current music folder), a path inside them {path, parent, dirs, audioFiles, truncated} (names only, no hidden entries, at most 2000), anything outside them {error}, symlinks resolved first. Then settingsManager.save_media_folder(path).

The user's theme

Subscribe to themeCatalog.activeTheme: the palette the user has chosen, already resolved (an album-art palette, a saved custom theme, or a built-in), as {base, baseAlt, accent, text: {primary, secondary}, states, sliders, bottombar, mediaroom, mainmenu, obd} with #RRGGBB colours; activeThemeName names it. Every built-in palette is in themeCatalog.themes (picker order in lightThemeNames / darkThemeNames), custom ones in settingsManager.customThemeData; choose one with settingsManager.save_theme_setting(name). Keys: Theme Object Structure.

Waveform bars

Call audioAnalyzer.setDemand("my-frontend", true) while your bars are on screen (and false when they leave; a closed connection releases it), then subscribe to audioAnalyzer.levels: a list of numBars (96) numbers from 0 to 8, for local tracks and phone audio alike, changing at most 10–20 times a second; pass throttleMs to thin it further. Nothing is analysed while nobody asks.

Album art

nowPlaying.artUrl is a file on the head unit; fetch the picture itself from GET http://host:9876/art (local and phone art alike, typed by its bytes: JPEG, PNG, GIF, WebP or BMP; 404 when there is none). Subscribe to nowPlaying.artRevision, which goes up by one on every new cover, and use it as your cache key: <img src="/art?rev=12"> from a --web-root page, or refetch when it changes. For a list, /art?song=<file name> (URL-encoded, a song in the library, as the playlist APIs name it) gives that song's cover and /art?queue=<id> a phone queue item's (phoneMirrorManager.mediaQueue ids). The request only names a song or an item; the app looks the file up itself and serves nothing outside its own art folders.

Video: the phone mirror and Android Auto

Send {"op":"stream","object":"phoneMirrorManager","name":"video"} (or androidAutoManager / frames for JPEG). The reply gives your stream id; then binary records arrive on the same connection: H.264 access units in Annex-B, every keyframe carrying its SPS and PPS, with a streamConfig event (codec string, width, height) whenever those change. A browser decodes them with WebCodecs: decoder.configure({codec}), then one EncodedVideoChunk per record. Touch goes back through phoneMirrorManager.injectTouch(pointerId, action, relX, relY), with 0 to 1 coordinates over the picture. The record layout, the join and drop rules and a phone-free test source (sim_video in a developer build) are in docs/api/README.md, "Streams".

Exports

An export writes to the head unit's Downloads folder; a remote client then fetches it over HTTP. Call tripRecorder.exportTrip(id) and, after its exportFinished, download GET /export/trip (the CSV; ?format=json for the JSON); dashboardManager.exportDashboard(id) then GET /export/dashboard; diagnosticsManager.exportLogs() then GET /export/logs (the list of files) and /export/logs?file=octave-cpp.log. Only the last export of each kind is served, never a path you name.

Head-unit only, by design

A few things act on the head unit's own desktop and have no service API: copying a dashboard to the clipboard (copyDashboardToClipboard, importDashboardFromClipboard: use importDashboardFromText and /export/dashboard instead), opening the log folder in a file manager (openLogFolder: use /export/logs), and the window's size and state. A remote client has its own clipboard and window.
