SettingsMenu Orchestrator

frontend/SettingsMenu.qml is pushed onto the StackView by the bottom bar's Settings button with initialSection set to the last visited section. It renders no settings itself; it owns the page model, the visible-page model, the navigation API, and a Loader that instantiates one of four layout engines:

Item {
    id: settingsMenu
    objectName: "settingsMenu"
    required property var stackView
    required property var mainWindow
    required property string initialSection

    property string currentSection: ""
    property bool updateAvailable: networkManager && networkManager.updateStatus === "update-available"
    property string layoutStyle: settingsManager ? settingsManager.settingsLayoutStyle : "Sidebar"
    property bool isInitialLoad: true
}

function layoutSourceForStyle(style) {
    switch (style) {
        case "Carousel":  return "SettingsCarouselLayout.qml"
        case "Sidebar":   return "SettingsSidebarLayout.qml"
        case "Hub":       return "SettingsHubLayout.qml"
        case "Dashboard": return "SettingsDashboardLayout.qml"
        default:          return "SettingsSidebarLayout.qml"
    }
}

In Component.onCompleted it pre-loads the card-state cache (ExpandedCards.load(settingsManager)), builds hubModel, and adopts initialSection if it is a visible section. The layout Loader's onLoaded hands the layout a reference to the orchestrator and a live binding to hubModel; for the Carousel it also sets the initial currentIndex.

Navigation API

  • navigateToCategory(section) — sets currentSection, persists it with settingsManager.set_last_settings_section(), then either sets the Carousel's currentIndex or calls the layout's own navigateToCategory().
  • navigateToSubSection(section, sub) — delegates to the layout if it implements it (Dashboard does), otherwise falls back to the category.
  • navigateToHub() — called by the bottom bar when Settings is tapped while already open; forwards to the layout (Hub and Dashboard return to their card grid).
  • A Connections on settingsLayoutStyleChanged sets isInitialLoad = false and swaps the layout; the new engine then keeps currentSection instead of restoring the saved one.
  • A 16 ms polling Timer (scrollToSectionTimer) scrolls the Carousel's current page to a card found by findChildByObjectName() when pendingScrollTarget is set.

The Settings Pages

Five of the six pages are Flickables that declare a tileModel — an array of { cardId, title, iconSource, component } — and put each card's body in its own Component. The same components serve two renderings: the page's own stacked SettingsCard list, and the tile grid + popup that the Sidebar and Carousel layouts build when they detect a tileModel (see Tile Grids). About has no tiles and renders as a plain scrolling page in every layout. Every page also declares the local dp()/dpMin() wrappers.

OBD — settings/OBDSettingsPage.qml

(warning) and No MAC Address, BLE connect failed, BLE error, Bluetooth permission denied (error). Anything else falls back to statusError.

Tile Grids and the Card Popup

Commit 93d0fc9 gave every page a tile grid. Three components implement it:

  • settings/SettingsTilePage.qml — a GridLayout of SettingsTiles driven by tileModel. Four tiles form a 2×2 grid; any other count uses max(2, ceil(sqrt(n))) columns. It emits tileSelected(cardId, originRect) with the tile's rectangle mapped into the grid's parent, and hides the tile whose cardId equals hiddenCardId while its popup is open.
  • settings/SettingsTile.qml — a rounded rectangle (primaryTextColor at 5 %, 10 % on hover, accent at 18 % when pressed, scale 0.97 while pressed) with a static bevel (1 px white 10 % top line, 1 px black 20 % bottom line), a ThemedIcon tinted with the accent (or, when iconSource is empty, a Unicode glyph over an offset shadow copy), the title at overallText × 1.6, and an optional status dot (statusColor, statusVisible). Emits tileClicked(cardId).
  • settings/SettingsCardPopup.qml — a contentColor panel with a header row (a "→" glyph and the title, both turning accent on hover; tapping anywhere on the header emits backRequested()), an accent gradient rule, and a Flickable body whose Loader instantiates the tile's component. contentOpacity lets the host fade the header and body independently of the panel geometry.

The host (Sidebar's content area or a Carousel SettingsHubCard) detects a tile page in Loader.onLoaded by typeof item.tileModel !== "undefined", sets item.visible = false to hide the page's own stacked rendering, and shows the grid instead. Opening a tile records detailTile, detailCardId and originRect; the popup then morphs from the tile:

SettingsCardPopup {
    property real openProgress: contentArea.detailCardId === "" ? 0.0 : 1.0
    x: contentArea.originRect.x * (1.0 - openProgress)
    y: contentArea.originRect.y * (1.0 - openProgress)
    width:  contentArea.originRect.width  + (parent.width  - contentArea.originRect.width)  * openProgress
    height: contentArea.originRect.height + (parent.height - contentArea.originRect.height) * openProgress
    contentOpacity: Math.max(0.0, (openProgress - 0.45) / 0.55)   // content resolves in the second half
    Behavior on openProgress { enabled: _animEnabled; NumberAnimation { duration: 320; easing.type: Easing.OutCubic } }
}

_animEnabled is set with Qt.callLater after creation so the popup never animates at startup. closeTile() clears detailCardId and nulls detailTile so the popup's Loader unloads and the body's Component.onDestruction runs — without that, page-scoped resources such as the Now Playing live preview would keep rendering after the user backed out.

Now Playing Studio

The Media page's "Now Playing" tile (cardId === "media_now_playing") is special-cased in both tile hosts: instead of openTile() they map the tile rectangle to scene coordinates and call mainWindow.openNowPlayingStudio(rect). frontend/NowPlayingStudio.qml is instantiated once in Main.qml at z: 5, above the StackView. It performs the same hero-morph from the tile's rectangle to its target rectangle, which Main.qml sizes to exclude the bottom bar (so navigation stays usable) and, when the Sidebar layout is active, the settings sidebar (App.Spacing.settingsNavWidth) so the user can switch sections without closing the studio. Any stackView.currentItemChanged or sidebar navigation closes it. Its header comment defines a visual standard for the rows inside (named spacing tokens, labels left / controls right) and the helper components NowPlayingMiniToggle, NowPlayingVSlider and NowPlayingButtonGrid exist for it. Commit 484bc76 ("now playing settings update") introduced this arrangement and removed the last environment-preset files.

Layout Engines

Four engines render the same pages with different navigation. Sidebar is the default (settingsLayoutStyle defaults to "Sidebar" in both backends and in the orchestrator's fallback); the others are labelled experimental in the Display page and hidden behind a toggle. Each engine receives settingsMenu and hubModel from the orchestrator, defines the local dp() helpers, and shows the update dot on the About entry. When a page is loaded, every engine binds item.mainWindow, item.stackView and item.currentSection if the page declares those properties.

Sidebar Layout (default)

frontend/SettingsSidebarLayout.qml is a RowLayout: a sidebarColor panel of width App.Spacing.settingsNavWidth (30 % of the window width × the 0.6 design factor) on the left, and a contentColor content area on the right.

Navigation List

A ListView of hubModel rows, each App.Spacing.settingsButtonHeight tall. The selected row has an accent background at 25 %, two stacked "elevation" rectangles behind it (6 % and 12 % black), a 1 px lit top edge, an accent bar on the left (navAccentBarWidth = 3, half the row height, animated), bold primaryTextColor; other rows use secondaryTextColor with a hover tint. The panel also has a subtle top-to-bottom lighting gradient, a 1 px lit top edge and a 10 px shadow on its right edge. Tapping a row saves the current page's scroll offset, closes the Now Playing studio if it is open, and sets settingsMenu.currentSection (persisted through set_last_settings_section).

Content Area

A Loader with settingsContentMargin margins loads sourceForSection(currentSection). For tile pages it hides the page and shows the SettingsTilePage + SettingsCardPopup pair described above; for the About page it restores the saved scroll position through a 16 ms polling timer that waits for the Flickable to have a valid contentHeight. Scroll offsets are saved continuously from contentYChanged.

Carousel Layout

frontend/SettingsCarouselLayout.qml shows a tab strip and a SwipeView. The strip is a Row of equal-width, dp(28)-tall tabs ((width - dp(4)×(n-1)) / n), each with a ThemedIcon (no shadow) and the page name; the current tab has an accent 20 % fill and 40 % border, others fade to 0.6 opacity. Tapping a tab sets swipeView.currentIndex; swiping updates currentSection and persists it.

Each swipe page is a settings/SettingsHubCard.qml: a translucent contentColor surface (92 %) with frosted highlight gradients, a lit top edge and an accent bottom rule, radius hubCardRadius. Its Loader is active only while the card is the current item (isCenter), so off-screen pages are not instantiated. The card mirrors the Sidebar's tile-mode state machine (grid + morph popup, Now Playing hand-off) and closes any open popup when it scrolls away from centre.

Hub Layout

frontend/SettingsHubLayout.qml has two states, "hub" and "detail", chosen in onSettingsMenuChanged: stay in detail after a mid-session layout switch, resume the last section on first launch if it is visible, otherwise show the hub. State changes cross-fade (150 ms out, 200 ms in).

The hub is a GridLayout of settings/SettingsHubGridCard.qmls, 3 columns when wider than 800 px else 2, with card heights computed to fill the view without scrolling. Each card shows the page name, a chevron, and passive info lines from getWidgetForSection():

SectionInfo lines
displaySettingsTheme: themeSetting; Scale: round(uiScale × 100)%
mediaSettingsSource: Spotify / Local; Autoplay; Visualizer
obdSettingsStatus: obdManager.get_connection_status(); Port; Fast
accessoriesSettingsKnob: connected / disconnected (esp32VolumeManager.is_connected()); Gestures; Phone Dock (Android Auto or Phone Mirror enabled)

The card model is rebuilt on hubModel changes, on return to the hub, and live on obdManager / esp32VolumeManager connectionStatusChanged while the hub is showing. The detail state has a heading bar ("← Section name", tapping it returns to the hub) over a page Loader with the same scroll-memory handling as the Sidebar. Hub detail does not use tile mode: pages render their stacked SettingsCard list.

Dashboard Layout

frontend/SettingsDashboardLayout.qml uses the same hub/detail state machine (without fade transitions). Its hub arranges cards in two rows: a featured top row of displaySettings, mediaSettings and obdSettings (in that order, only those visible) and a bottom row of the remaining visible pages in page-model order. Every card is a settings/SettingsDashboardCard.qml with cardSpan: 1 — there is no column spanning.

A dashboard card is a glassy contentColor surface (55 %) with a hover glow; its title row navigates to the page and its body is a Loader for the page's widget. When the widget exposes a navigateToSubSection(sub) signal the card connects it and re-emits subSectionSelected(section, sub); the layout then loads the page and, once the Flickable has laid out, scrolls to the SettingsCard whose objectName equals the sub-section name (16 ms polling timer). The detail view adds a dp(40) scroll rail on the left with a draggable accent handle (minimum dp(50) tall) whose position maps to contentY — a touch-friendly alternative to flicking a long page.

Section Visibility

buildHubModel() filters pageModel through settingsManager.is_settings_section_visible(section) (and drops desktopOnly pages on Android):

function buildHubModel() {
    var model = []
    var android = (typeof isAndroid !== "undefined" && isAndroid)
    for (var i = 0; i < pageModel.length; i++) {
        var page = pageModel[i]
        if (page.desktopOnly && android) continue
        if (!isVisible(page.section)) continue
        model.push({ name: page.name, section: page.section, source: page.source, icon: page.icon,
                     iconSource: page.iconSource || "", group: page.group || "", widget: page.widget || "" })
    }
    hubModel = model
}

Both backends persist the map as settingsMenuVisibility and expose is_settings_section_visible(section) (unknown sections are treated as visible) and save_settings_section_visibility(section, visible), which emits settingsMenuVisibilityChanged; the orchestrator rebuilds hubModel on that signal. The shipped defaults are exactly the six pageModel sections — displaySettings, mediaSettings, obdSettings, accessoriesSettings, deviceSettings, about — all true, and a section missing from a stored settingsConfigure.json is filled in as visible when the file loads, so every page shows until the user hides it. The UI that writes the map is the "Toggle View" popup, opened by press-and-hold on the bottom bar's Settings button (see Bottom Bar).

Card State and Scroll Memory

ExpandedCards.js

A .pragma library module — one JavaScript instance shared by every importer — caching the expanded/collapsed state of SettingsCards:

// SettingsMenu.onCompleted, once per settings visit (guarded by _loaded)
ExpandedCards.load(settingsManager)     // reads generic setting "expandedCards"

// SettingsCard
property bool expanded: ExpandedCards.isExpanded(cardId)   // false when unknown
onExpandedChanged: { ExpandedCards.setExpanded(cardId, expanded); _saveTimer.restart() }   // 500 ms debounce
// _saveTimer → ExpandedCards.save(settingsManager) → settingsManager.save_setting("expandedCards", copy)

The cache exists so that creating a card never touches the disk and so the card does not hold a settingsManager binding (the comment cites binding re-evaluation cascades). Both backends implement the generic get_setting_with_default(key, default) / save_setting(key, value) pair the module uses.

ScrollMemory.js

Two lines: .pragma library and var positions = {}. Layouts store positions[section] = flickable.contentY on every scroll and restore it after the page loads. Because it is a library singleton the offsets survive layout switches within a session but not an app restart.

  1. Create the page in frontend/settings/MySettingsPage.qml as a Flickable with the local dp() wrappers, a tileModel, one Component per card body, and the stacked fallback: 
    property var tileModel: [
    { cardId: "my_first", title: "First", iconSource: App.Style.assetBase + "tile_first.svg", component: firstContent },
    // ... aim for 4 tiles so the grid reads as 2x2
]

Component {
    id: firstContent
    ColumnLayout {
        width: parent ? parent.width : 0
        SettingCategory { title: "..."; /* controls */ }
    }
}

// Default rendering for Hub / Dashboard / About-style hosts; the tile hosts hide this.
ColumnLayout {
    width: parent.width
    Repeater {
        model: pageRoot.tileModel
        SettingsCard {
            Layout.fillWidth: true
            objectName: modelData.title      // sub-section lookup key
            cardId: modelData.cardId
            title: modelData.title
            Loader { Layout.fillWidth: true; sourceComponent: modelData.component }
        }
    }
    Item { Layout.fillHeight: true; Layout.minimumHeight: App.Spacing.bottomBarHeight }
}
    Declare property var mainWindow, stackView or currentSection only if you need them; the layouts bind them when present.
  2. Draw the tile icons: one 600×600 SVG per tile in frontend/assets/, a single <g fill="#FFFFFF"> of filled primitives, centred in the viewBox (see tile_layout.svg). ThemedIcon recolours it; a second colour collapses into the tint.
  3. Optionally create a widget in frontend/settings/widgets/MyWidget.qml with a cardSpan property and, if it offers chips, a navigateToSubSection(string) signal whose values equal tile titles.
  4. Register in pageModel with subSections equal to the tile titles, and add desktopOnly: true if the page depends on desktop-only managers.
  5. Backends: add every new save_* slot and property to both SettingsManagers and to Settings Reference; add the section to the settingsMenuVisibility defaults in both if it should be hideable.
  6. Test all four layouts (Display → Layout → "Show experimental layouts").

Design Decisions

DecisionRationale (from code comments and commit history)
Card bodies as Components shared by two renderings Page comment: "shared between the Flickable rendering (below) and the SettingsCardPopup in the Sidebar layout". One definition of each setting serves the stacked list, the tile popup and the Carousel card.
Tile grids with a hero-morph popup instead of long scrolling pages Commit 93d0fc9: "tile grids for every page". Four large touch targets per page suit a dash-mounted screen; the popup "grows from the clicked tile's rect" so the user keeps spatial context, and content fades in only once "there's enough room for them".
Sidebar is the only non-experimental layout The Display page's description reads "Sidebar is the default. The other layouts are experimental." The experimental toggle is derived from the active layout "so the picker is always consistent — no extra persisted setting", and turning it off falls back to Sidebar so the user is not "stranded on a now-invisible choice".
Now Playing takes over the window Comments in SettingsHubCard and Main.qml: the studio "needs every pixel" and covers the StackView, but Main.qml reserves the bottom bar (and the sidebar in Sidebar layout) so navigation and section switching stay available; any page change closes it "so it doesn't hang on top of an unrelated screen".
Live MediaRoom preview instead of a mock MediaRoomLivePreview renders "a real MediaRoom instance at the host window's design dimensions" so Now Playing changes are seen exactly as they will look, and unloads it while hidden to avoid "double-rendering vinyl rotation / FFT analysis".
closeTile() nulls the tile component Comment: without it "page-scoped resources (e.g. the Now Playing live PiP) would persist after the user backs out of the tile"; destroying the content is invisible because the body has already faded.
Pages hide themselves in tile hosts The host sets item.visible = false rather than the page knowing about layouts; a page only declares tileModel and works in all four engines.
subSections must equal tile titles Sub-navigation looks cards up by objectName, which pages set from modelData.title; a mismatch silently fails to scroll.
Card state in a .pragma library cache with a debounced write "Avoids disk I/O during card creation"; the card holds no settingsManager binding "to avoid binding re-evaluation cascades"; the 500 ms timer "coalesces rapid expand/collapse into a single disk write".
Carousel pages load only while centred pageLoader.active: hubCard.isCenter keeps five off-screen pages (each with terminals, live previews and OBD scans) from being instantiated.
Sliders drag-only, no track clicks SettingsSlider comment: "Block track clicks — only allow dragging the handle." A stray touch on a long track would otherwise jump a setting.
Scale slider commits on release Mid-drag updates re-lay out the slider itself (commit fe567f3); see Theme System.
Diagnostics buttons in a 2×2 grid Commit 7fd8405: four labels side by side overflowed at 1276 px on the Pi and "a Layout cannot shrink a SettingsButton below its label".
Two-step confirmations with a 5 s reset Shutdown and self-update both require a second tap within five seconds, with a pulsing warning text, instead of a modal dialog — cheaper to hit on a touchscreen and impossible to trigger with one accidental tap.
Themed SVG icons via Style.assetBase Commit 93d0fc9 and the Style.qml comment: settings pages and layouts sit at different directory depths, so a URL resolved in frontend/ avoids guessing ../ segments; a property rather than a function because of the Android singleton-function bug.
Accessories page is desktopOnly The serial knob, I²C sensors and adb-based phone dock are desktop hardware paths; Android is C++-only and omits those managers, so the page is dropped from the model rather than guarded control by control.
Update dot repeated on every layout's About entry The bottom bar's dot leads the user into Settings; each layout re-draws it on the About entry so the trail continues to the update controls.
