What It Is

Settings is the screen behind the gear button on the navigation bar. It is one grid of tiles, like the quick-settings panel of a phone: a column for each section (Display, Media, OBD and so on), and in it a tile for each group of settings. A tile shows its name and, under it, how things stand right now: "Connected", "12 albums · Autoplay", "°F · mph". Tap a tile and it grows into a card with the settings themselves.

Every change is saved as you make it. There is no Save button and nothing to confirm, except for the few actions that cannot be taken back (Shut Down, Forget, Clear history), which ask for a second tap.

This page starts with how to use the screen and gets more technical as it goes: first what is where, then how to add a setting of your own, then how the screen is built.

This page lists what is on the screen. What each setting does, its key in the settings file and its default are in the Settings Reference.

Finding a Setting

  • Read the tiles. The whole of Settings is on one screen, so there is nothing to search or page through. The line under a tile's name is its state, and a tile is tinted in the accent colour when its thing is on or connected. A coloured dot before the state means a connection: connected, waiting, or not there.
  • Go back from a card by tapping its title bar (the arrow and the name at the top), or by tapping the Settings button on the navigation bar again.
  • Some screens take you straight to the right card. The Connect button on the OBD page opens OBD > Connection. The phone widget on Home opens Phone > Phone Mirror. The vehicle card on Home opens Device > Vehicle. The music screens' Spotify button opens Media > Spotify until you are signed in.
  • An orange dot on the About tile means an update is available.
  • Open Wiki (About > Documentation) opens this wiki in your browser. It needs an internet connection.

Hiding Sections

If you never use a section (no sensors, no phone), you can take it off the Settings screen.

  1. Press and hold the Settings button on the navigation bar. A panel called Toggle View opens.
  2. Tap a section to hide it or show it again. The grid behind changes at once.
  3. Tap Close.

Hiding a section only removes its column from the screen. Its settings keep their values and keep working. Every section is shown until you hide it.

The choice is stored under the settingsMenuVisibility key as one true / false per section id. The seven ids are displaySettings, mediaSettings, obdSettings, phoneSettings, accessoriesSettings, deviceSettings and about. From code, read one with settingsManager.is_settings_section_visible(id) (an id it has never heard of counts as visible) and change one with settingsManager.save_settings_section_visibility(id, visible). The panel itself belongs to the Bottom Bar.

The Controls

From here on the page is for people adding to the Settings screen or changing it.

A card is built from a small set of ready-made parts in frontend/settings/. Use them and a new setting looks and behaves like every other one. They are QML files in the same folder as the pages, so a page uses them by name with no import; the snippets below assume the page's usual import ".." as App for App.Style and App.Spacing.

The pattern is the same for every control: bind what it shows to the setting, and write the setting when the user acts. The control then follows the setting wherever it changes from, including a paired device or a knob. Reading and writing a setting is explained in Settings Manager.

Boxes that hold a setting

PartWhat it is for
SettingCategoryThe box for one setting: a title, an optional one-line description, and the control. Put a switch in inlineContent and it sits on the right of the title; anything else goes inside and stacks under the title.
SettingSubcategoryA box inside a box, for controls that belong to one choice. With togglable: true it has its own switch and shows its contents only while checked; it emits toggled(bool).
SettingsCardA larger box with a slightly stronger background, for a whole tool inside a tile (Custom PIDs, Diagnostics). Give it no cardId and it is always open with no header: put a SettingLabel first as its title.
SettingsDividerA thin line between groups in a card that is not split into boxes.
SettingLabel, SettingDescriptionText in the settings' own sizes and colours: a label, and smaller grey text that wraps.

A switch

SettingCategory {
    title: "Show on Home"
    description: "Beside the readings."

    inlineContent: SettingsToggle {
        compact: true
        checked: settingsManager.homeVehicleCard
        onToggled: function(checked) { settingsManager.homeVehicleCard = checked }
    }
}

SettingsToggle has checked, compact (the small switch, which is what the settings cards use), an optional text label and the signal toggled(bool). A tap does not change checked by itself: it emits toggled with the state asked for and waits for your binding to follow. So keep checked bound to the setting and never assign it. In a SettingCategory's inlineContent, a tap anywhere on the box flips the switch; if the box also has controls under the title, only the title and description do.

A slider

SettingCategory {
    title: "Storage cap"

    RowLayout {
        Layout.fillWidth: true
        SettingsSlider {
            id: capSlider
            from: 50; to: 5000; stepSize: 50
            value: settingsManager.blackBoxMaxMB
            onMoved: settingsManager.blackBoxMaxMB = Math.round(value)
        }
        ValueDisplay { text: Math.round(capSlider.value) + " MB"; Layout.fillWidth: false }
    }
}

SettingsSlider is a Qt Quick Slider with the app's look and one rule: it moves only when you drag the handle. A tap on the track does nothing, so a stray touch in a moving car cannot jump a setting. Write the setting in onMoved (the user's drags only), not in onValueChanged. ValueDisplay is the read-out beside it. A slider whose value changes the layout while you drag, as UI Scale does, should write on release instead.

A choice of a few: segments

SettingCategory {
    title: "Nav Bar Position"

    SettingsSegmentedControl {
        options: ["bottom", "side"]
        currentValue: settingsManager.bottomBarOrientation
        onSelected: function(value) { settingsManager.bottomBarOrientation = value }
    }
}

For two to four choices that fit on one row. onSelected here is a property you give a function to, not a signal: write it exactly as above. What an option says on screen is the string in options, so map it to the stored value in onSelected if the two differ.

A choice of many: chips

SettingCategory {
    title: "Font"

    SettingsChips {
        options: App.Style.availableFonts
        currentValue: settingsManager.fontSetting
        onSelected: function(value) { settingsManager.fontSetting = value }
    }
}

SettingsChips wraps onto as many rows as it needs. All the text chips of one control are the same width and line up in columns; a label too long for its chip is cut with an ellipsis. As with segments, onSelected is a function property. The optional extras:

PropertyWhat it adds
chipPalettesA colour swatch for an option: { "Name": ["#base", "#alt", "#accent"] }. The theme picker uses it.
chipImagesA picture for an option: { "Name": "file:///..." }. Picture chips get a row of their own.
chipFontsThe option drawn in a font: { "Name": "Family" }.
chipColorsA text colour per option.
deletableItems, onItemDeletedOptions the user may delete, and the function called when one is. The control asks before it calls.

Text, buttons, and actions that cannot be undone

SettingsTextField {
    Layout.fillWidth: true
    text: settingsManager.deviceName
    onEditingFinished: if (text.trim() !== "") mainWindow.updateDeviceName(text)
}

SettingsButton {
    text: "Refresh"
    Layout.preferredHeight: dp(44)          // a button has no height of its own
    onClicked: networkManager.refreshNetwork()
}

ConfirmButton {
    label: "Forget"; confirmLabel: "Confirm forget"
    Layout.preferredHeight: dp(44)
    onConfirmed: phoneMirrorManager.forgetWireless()
}
  • SettingsTextField is a Qt Quick TextField in the app's look. Save in onEditingFinished, not on every key.
  • SettingsButton has text, buttonColor (the accent colour unless you set it), tooltipText and clicked(). Always give it a height (height, or Layout.preferredHeight in a layout): it has none of its own and would not show.
  • ConfirmButton is for anything that cannot be taken back. The first tap turns it to the theme's danger colour and shows confirmLabel; a second tap within four seconds (armMs) emits confirmed(). Left alone, it goes back. There is no dialog, so there is nothing new to aim at in a moving car.

NowPlayingButtonGrid also lives in this folder: a two-column grid of equal buttons for picking one of several options, with a selected(value) signal. The Now Playing look editor uses it, and that editor opens from the Media Room, not from Settings; see Pages & Views.

Rules Every Card Follows

  • One setting, one box. Each setting gets its own SettingCategory.
  • The state of a connection comes first in its card, before the settings.
  • A switch sits on the right of the title, with no "On" / "Off" text beside it.
  • A description only where the title does not say it, in one line. The how-to belongs in this wiki, not on the card.
  • Anything that cannot be taken back is a ConfirmButton.
  • A tool few people need does not get a tile. It goes in an Advanced or Developer tile as an always-open SettingsCard.
  • Sizes go through dp(). Every page and control declares its own small dp() / dpMin() functions at the top; copy them into a new file. They follow the UI Scale setting.

Adding a Setting, a Tile or a Section

A setting in an existing card

  1. Add the setting itself to SettingsManager, if it is new. The steps are in Settings Manager.
  2. Find the card. Each page in frontend/settings/ has one Component per tile (layoutContent, clockContent, connectionContent…). Its top-level ColumnLayout is the card.
  3. Add a SettingCategory with the control from the section above, where it belongs in the order of the card.
  4. Update the docs: the table on this page and the Settings Reference.

A new tile

A page's tiles are its tileModel list. Add an entry and a Component for the card. The example is made up; there is no Night Mode setting: 

property var tileModel: [
    // ...
    { cardId: "display_night", title: "Night Mode", component: nightContent,
      summary: function() {
          return { state: settingsManager.nightMode ? "On" : "Off",
                   active: settingsManager.nightMode }
      } }
]

Component {
    id: nightContent
    ColumnLayout {
        width: parent ? parent.width : 0
        spacing: App.Spacing.sectionSpacing
        SettingCategory { title: "..." /* the control */ }
    }
}
FieldWhat it is
cardIdThe tile's id, unique across all pages (display_clock, obd_connection). Other code opens the card by it.
titleThe name on the tile and on the card. About fourteen characters fit on a line; a longer title wraps to a second line.
componentThe card's contents.
summaryOptional. A function returning any of state (the line under the name; keep it to about fourteen characters), active (true tints the tile: only for something that is on or connected) and status (a colour for the dot, such as App.Style.statusConnected). The tile updates by itself whenever a property the function reads changes. Leave state out rather than fill it with an instruction.

A section holds at most four tiles: one column of the grid, whose heights only divide evenly for one to four. Make room by folding a little-used tile into another as a SettingsCard, the way Advanced and Developer do.

A new section

  1. Create the page, frontend/settings/MySettingsPage.qml, by copying the smallest existing one (MediaSettingsPage.qml). Keep its tileModel, its renderCards property and the dp() functions. Declare property var mainWindow or stackView only if the page needs them; they are filled in when present.
  2. List it in pageModel in frontend/SettingsMenu.qml: its name (the caption over the column), its section id and its source. Columns appear in the order of this list. Add desktopOnly: true if it has no place on Android.
  3. Teach the settings store the id: add it to kSettingsSections and to the settingsMenuVisibility defaults in src/managers/settingsmanager.cpp.
  4. Add it to the Toggle View panel: the list of sections in frontend/BottomBar.qml is separate from pageModel.
  5. Update this page. Nothing needs adding to CMakeLists.txt: the files in frontend/ are loaded at run time.

How It Is Built

The problem to solve: a lot of settings, on a touchscreen in a car, where long scrolling lists and nested menus are slow to use. The answer is two levels and no more. Level one is the grid, which shows everything at once with its state. Level two is one card. Nothing is deeper than one tap from the grid.

Four pieces do it:

PieceJob
frontend/SettingsMenu.qmlThe Settings screen as the rest of the app sees it. It holds the list of sections (pageModel), works out which are visible, and offers the calls other screens use to open a card. It draws nothing itself.
frontend/SettingsSidebarLayout.qmlThe grid and the card popup. This is the only layout; the file is named after a sidebar it replaced.
The section pages, frontend/settings/*SettingsPage.qml and AboutPage.qmlWhat is in each section: the tileModel and a Component per card.
The controls, frontend/settings/The parts described above, plus the tile, the tile grid and the popup.
 
  SettingsMenu            pageModel: 7 sections --buildHubModel()--> hubModel: the visible ones
       |
  SettingsSidebarLayout   loads each visible section's page, hidden, and reads its tileModel
       |
       +-- SettingsTilePage     the grid: one SettingsTile per tileModel entry, a column per section
       |
       +-- SettingsCardPopup    grows out of the tapped tile and shows that entry's component

From the list of sections to the grid

  1. pageModel lists the seven sections in order, each with its name, section id and page source.
  2. buildHubModel() goes through that list and leaves out a section the user has hidden (is_settings_section_visible) and, on Android, one marked desktopOnly (Phone, Accessories). The result is hubModel. It is rebuilt whenever settingsManager emits settingsMenuVisibilityChanged, which is why the grid changes while the Toggle View panel is still open.
  3. The layout loads every page in hubModel, invisibly. It never shows a page: it only needs each page's tileModel and the card components that live inside the page.
  4. It lays the tiles out a column per section, top to bottom, at most four to a column. A column with fewer tiles stretches them to fill its height, so a short section leaves no gap. About has no tiles of its own, so it gets one tile whose card is the whole About page. That tile finishes the last column when there is room (the bottom-right corner), and otherwise gets a column of its own.
  5. A tap on a tile opens the popup with that tile's component.

Opening Settings from other code

To do thisUse
Open Settings on a card, from anywheremainWindow.navigateToSettings(section, cardId), for example navigateToSettings("obdSettings", "obd_connection"). It works whether or not Settings is already open.
Open a card when Settings is the current pageopenTile(cardId) on the Settings page. If the tiles are still loading, the card opens when they are ready.
Know which card is openopenTileId(): the cardId, or an empty string.
Close the open cardnavigateToHub(). The navigation bar's Settings button calls it.
Open AboutnavigateToCategory("about"), or openTile("section:about").

Cards have been merged over time, and old ids still work. The layout keeps a small table, movedCards, from a retired id to the tile that now holds it: obd_adapters opens obd_connection; obd_custom_pids and obd_bus_monitor open obd_advanced; device_frontends, device_service and device_diagnostics open device_developer; accessories_phone_dock opens phone_mirror. When you fold a tile into another, add its id there.

Tiles and the Card Popup

A tile (SettingsTile) has no icon. It shows the setting's name and its current state under it, the way Android's quick settings and Apple's Home tiles do, because the state is what you came to see. The tile calls its summary function inside a binding, so it stays live without the page doing anything: the Clock tile ticks, the Connection tile turns to "Connected" when the car answers.

The grid (SettingsTilePage) places the tiles. The Settings screen uses two of its three modes: columns of sections in landscape (rows), and a scrolling list of sections, two tiles across, in portrait (sections). In both it reports a tap as tileSelected(cardId, rect), with the tile's rectangle, so the popup knows where to grow from.

The popup (SettingsCardPopup) is the card. It grows out of the tapped tile until it fills the Settings area, and shrinks back into the tile when closed, so you keep track of where you are. Its title bar (an arrow and the tile's name) is the back button, and the body scrolls when the card is taller than the screen. The host only sets four things: open, originRect, title and contentComponent; and listens for backRequested().

Three things keep the animation smooth; keep them if you change it:

  • The card is laid out once, at its full size, and clipped while the popup grows, so text does not re-wrap on every frame.
  • The tile stays drawn underneath and the popup's background fades in over it. Hiding the tile instead leaves a blank block where it was.
  • The contents are kept until the popup has fully closed. Only then is the card's component destroyed, so anything it started (a live preview, a timer) stops in its Component.onDestruction.

Details and Special Cases

  • Changing Nav Bar Position rebuilds Settings. The grid was laid out for the old shape of the screen, so when bottomBarOrientation changes while Settings is open, Main.qml notes the open card (openTileId()), builds a fresh Settings page a moment later, swaps it in and destroys the old one. The new page is given the card as initialTile and reopens it once the tiles have loaded, so you stay in Display > Layout, where the switch is. If Settings is not on screen, its cached copy is simply thrown away.
  • A card's contents exist only while it is open. The pages are loaded for the life of the Settings screen, but with renderCards: false, so none of their cards are built until a tile is tapped. A page's own stacked list of cards (the Repeater at the bottom of each page file) is for a host that shows the page by itself; nothing does today.
  • A SettingsCard with a cardId is collapsible and remembers whether it was open, in the expandedCards setting (through ExpandedCards.js). The Settings screen does not use this now: its cards are either popups or always open.
  • Unused fields. pageModel entries also carry icon, iconSource, group and subSections. The grid uses none of them. The settingsLayoutStyle setting is likewise not read by the screen.
  • The Now Playing look editor is not in Settings. It opens from the Media Room; see Pages & Views.

The Settings screen is QML only: it has no manager of its own. What it reads and writes belongs to the managers, above all settingsManager, whose every property and method is in the API reference.

Why It Is Built This Way

  • One grid, not a menu of pages. Large tiles are easy to hit on a dash-mounted screen, and seeing every section at once means nothing has to be searched for.
  • Tiles show state, not icons. "Connected" or "Off" answers most visits to Settings without opening anything.
  • The card grows out of its tile. You see where the card came from and where Back will put you.
  • The page owns its cards; the layout only places them. A page declares tileModel and knows nothing about the grid, so the layout can change without touching a single setting.
  • A switch asks, the setting answers. The switch never sets its own state, so it cannot disagree with a setting that was changed from somewhere else.
  • Phone and Accessories are dropped whole on Android (desktopOnly) rather than guarded control by control.
