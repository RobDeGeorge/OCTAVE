Overview

The SettingsManager class (src/managers/settingsmanager.{h,cpp} in C++, backend/settings_manager.py in Python) is the central configuration store for all of OCTAVE. It inherits from QObject and exposes every user-configurable option to QML through Q_PROPERTY / @Property getters, change signals, and save_* slots. Both backends define the same 92 default keys, the same 75 properties, the same 79 signals and the same slot names, and they read and write the same file: settingsConfigure.json in the OS-specific app data directory. The QML frontend never knows which backend is behind settingsManager.

Beyond the typed properties, the manager provides a settings registry (25 entries) that maps a setting ID to its label, category, control type and save slot. The Quick Panel and the pin system render settings from this metadata, so a slider or toggle can be pinned without any per-setting QML.

Since the 2026-09 performance sweep the manager is memory-served: the file is read once in the constructor, every getter answers from the in-memory copy, and every setter updates that copy and arms a 500 ms single-shot timer that performs one atomic write for the whole burst. Details in Startup, In-Memory Cache and Coalesced Writes.

def get_app_data_dir():
    app_name = "OCTAVE"
    if sys.platform == 'win32':
        base = os.environ.get('APPDATA', os.path.expanduser('~'))
        data_dir = os.path.join(base, app_name)
    elif sys.platform == 'darwin':
        data_dir = os.path.join(os.path.expanduser('~'), 'Library', 'Application Support', app_name)
    else:
        base = os.environ.get('XDG_CONFIG_HOME', os.path.join(os.path.expanduser('~'), '.config'))
        data_dir = os.path.join(base, app_name)
    os.makedirs(data_dir, exist_ok=True)
    return data_dir

Property / Signal / Slot System

Every setting with a dedicated property follows the same three-part pattern in both languages:

  1. Signal declaration named <key>Changed (e.g. themeSettingChanged), carrying the new value where the value is scalar and no argument for dict/list settings
  2. Read-only property with the camelCase JSON key as its name and the signal as notify
  3. Save slot named save_<snake_case> that updates the backing member, calls update_setting() / updateSetting(), and emits the signal

Python (backend/settings_manager.py):

# 1. Signal declaration (class level)
themeSettingChanged = Signal(str)

# 2. Property with notify signal
@Property(str, notify=themeSettingChanged)
def themeSetting(self):
    return self._theme_setting

# 3. Slot for QML to call
@Slot(str)
def save_theme_setting(self, theme):
    logger.debug(f"Saving theme setting: {theme}")
    self._theme_setting = theme
    self.update_setting("themeSetting", theme, self.themeSettingChanged)

C++ (src/managers/settingsmanager.{h,cpp}), same three parts:

// header
Q_PROPERTY(QString themeSetting READ themeSetting NOTIFY themeSettingChanged)
signals:
    void themeSettingChanged(const QString &value);
public slots:
    void save_theme_setting(const QString &theme);

// source
void SettingsManager::save_theme_setting(const QString &theme)
{
    qCDebug(lcSettings) << "Saving theme setting:" << theme;
    m_themeSetting = theme;
    updateSetting(QStringLiteral("themeSetting"), theme);
    emit themeSettingChanged(theme);
}

The slot names are deliberately snake_case on both sides (save_theme_setting, not saveThemeSetting): the Python backend came first, the QML was written against it, and the C++ port kept the names so no QML had to change. The one camelCase slot is the shutdown flush, flushPendingSave() on both sides (Python also keeps a flush_pending_save() alias), which only the two main entry points call.

update_setting() / updateSetting() is the single funnel every simple setter goes through: 

def update_setting(self, key, value, signal=None):
    settings = self.load_settings()      # copy of the in-memory dict
    settings[key] = value
    self.save_settings(settings)         # validate into the cache, arm the 500 ms timer
    if signal:
        signal.emit(value)

Setters that touch several keys at once (save_playback_state, save_spotify_credentials, the gesture-mapping and section-visibility slots) call load_settings() / save_settings() directly so the burst becomes one write, and setters with an enumerated or bounded domain validate before saving: save_settings_layout_style, save_window_state, save_music_button_default_page, save_album_art_transition, save_esp32_led_color_mode, set_media_source and set_last_settings_section silently ignore unknown values, while the numeric sliders clamp (qBound / max(min())) to the ranges listed in the Settings Reference.

Property types used
Properties are str/QString, bool, int, float (C++ float for uiScale, startUpVolume, fuelTankCapacity; double for the others) and 'QVariantList' / QVariantList for homeOBDParameters, directoryHistory, customThemes (a list of theme names) and pinnedSettings. Two properties are JSON strings rather than maps so QML parses them with JSON.parse: settingsMenuVisibility and albumArtColors. Dict-valued settings (obdParameters, gestureMapping, expandedCards, customThemes contents) have no property at all; QML reads them through dedicated getters or get_setting_with_default().

Startup, In-Memory Cache and Coalesced Writes

The constructor performs the only unconditional disk read of the manager's lifetime:

  1. Build _default_settings / buildDefaultSettings() (92 keys) and the registry.
  2. load_settings(): the file is opened with a shared lock, parsed and passed through _validate_settings(). A missing file is created from the defaults immediately; a corrupt file (JSON parse error) is logged and the defaults are used in memory without overwriting the file.
  3. Migrations, applied in memory (only the first two write back):
    • uiScale == 0.6 (an old default) becomes 1.0 and is saved straight away.
    • fontSetting == "Google Sans" (the pre-0.9 default, which Style.setFont() rejects because Main.qml derives the display name "GoogleSans Regular" from the bundled GoogleSans-Regular.ttf, silently leaving the app in the system font) becomes "GoogleSans Regular" and is saved straight away.
    • obdBluetoothPort == "/dev/rfcomm0" (the former desktop placeholder, meaningless on Android where the field holds a MAC address) is cleared to "".
    • lastSettingsSection == "clockSettings" (a removed page) becomes "displaySettings".
    • obdParameters: every PID present in the defaults but missing from the file is added, so new PIDs appear after an upgrade without discarding the user's toggles.
    • settingsMenuVisibility: sections missing from the stored dict are filled in as true (visible) in both backends, matching is_settings_section_visible().
  4. Every backing member is populated from the loaded dict with the default as fallback (_load_members_from_settings() / populateMembers(), which reset_to_defaults() reuses).
  5. mediaFolder defaults to "" on disk and is resolved at load: C++ uses QStandardPaths::MusicLocation (falling back to ~/Music) and creates the directory on desktop only; Python uses ~/Music and always creates it.
  6. currentVolume (never persisted) is derived from startUpVolume by inverting the volume curve: round(sqrt(startUpVolume) * 100), e.g. the default 0.1 gives 32 %. See Architecture for the quadratic curve.
  7. Two single-shot timers are created: the 500 ms settings write timer and the 800 ms OBD-parameter debounce timer.

After that, _settings_loaded / m_settingsLoaded is true and the manager works entirely from memory:

QML slot call ──► save_xxx()
                    │  update member, validate domain / clamp
                    ▼
              update_setting()  ──► load_settings()   (returns the in-memory copy, no I/O)
                    │              settings[key] = value
                    ▼
              save_settings()   ──► _validate_settings()  (types checked against defaults)
                    │              self._settings = validated
                    │              _save_pending = True ; _save_timer.start()   (500 ms, restarted on every call)
                    ▼
              signal.emit(value) ──► QML bindings update immediately
                    ⋮
        500 ms of quiet  ──► flushPendingSave() ──► _write_settings_to_disk()   (atomic temp + rename)
        aboutToQuit      ──► flushPendingSave()      (main.py / main.cpp, after MediaManager saves playback state)

Consequences worth knowing: a slider drag that fires twenty save_* calls costs one write; album-art colours pushed on every track change cost one write per track at most; and if the process is killed (not quit) within 500 ms of a change, that change is lost. The OBD parameter toggles add their own layer: save_obd_parameter_enabled() only updates the in-memory map and restarts the 800 ms timer; when it fires, _flush_obd_parameters() copies the map into the settings dict (which arms the 500 ms timer) and emits obdParametersChanged once for the whole batch.

JSON Persistence and Validation

Atomic Write

_write_settings_to_disk() / writeSettingsToDisk() receives an already validated object and never re-validates (commit 037f753 aligned the C++ side with Python on this):

  1. Create a temporary file in the same directory (tempfile.mkstemp(dir=..., suffix='.json') / QTemporaryFile("settings_tmp_XXXXXX.json")) so the final rename is on one filesystem
  2. Take an exclusive, non-blocking lock on it (fcntl.flock(LOCK_EX | LOCK_NB) or msvcrt.locking(LK_NBLCK) in Python; flock() or LockFileEx(LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY) in C++). A lock failure is logged and the write proceeds
  3. Write the JSON with 4-space indentation (json.dump(indent=4) / QJsonDocument::Indented)
  4. Set permissions to owner read/write only (chmod 600; skipped on Windows, where the user account protects the file)
  5. Rename over settingsConfigure.json. On Windows the old file is deleted first because rename cannot overwrite
  6. If any step fails, fall back to a direct (non-atomic) write of the same content, and remove the temp file

Validation

_validate_settings() / validateSettings() runs at exactly two points: once on the initial read and once inside every save_settings() (i.e. on the in-memory copy, before the timer is armed). It starts from a copy of the defaults and accepts a stored value only if its type matches the default's type; anything else keeps the default. Keys that have no default are copied through untouched so newer builds and QML-only keys survive older builds.

Default typePython ruleC++ rule
boolaccepted only if isinstance(val, bool); checked first because bool is a subclass of intQJsonValue::isBool()
intbool rejected; int kept; float truncated with int(val)any JSON number (isDouble()); ints and floats are not distinguished
floatbool rejected; int or float coerced with float(val)
strisinstance(val, str)isString()
dict / listisinstance of the default's type; contents are not inspectedisObject() / isArray(); contents are not inspected
not a dict at top leveldefaults returnedempty object → defaults returned
Float settings need float defaults
Under the Python rule above an integer default truncates every stored float. esp32VolumeStepSize used to default to the integer 1, so a 0.25 / 0.5 / 0.75 knob step became 0 on disk under the Python backend; its default is now the float literal 1.0 in both backends. Keep new float settings' defaults as float literals (1.0, not 1).

File Locking

def _lock_file(self, f, exclusive=True):
    if sys.platform == 'win32':
        msvcrt.locking(f.fileno(), msvcrt.LK_NBLCK if exclusive else msvcrt.LK_NBRLCK, 1)
    else:
        fcntl.flock(f.fileno(), (fcntl.LOCK_EX if exclusive else fcntl.LOCK_SH) | fcntl.LOCK_NB)

Reads take a shared lock, writes an exclusive one on the temp file. The locks are advisory and non-blocking; they exist to keep a second OCTAVE process (for example the Python backend and a C++ build pointed at the same config dir, or dev/ tooling) from interleaving partial writes, not to serialise access within one process, which is single-threaded for settings.

Default Settings

All defaults live in self._default_settings (Python __init__) and buildDefaultSettings() (C++). The dict is the schema: any key absent from the loaded JSON gets its default, and any stored value of the wrong type is replaced by it. Both backends define the same 92 top-level keys with identical literal values (verified key by key in the 2026-09 audit). The nested obdParameters dict holds 86 PIDs, 20 enabled by default. Section Visibility System

Settings-menu sections can be hidden. Visibility state is the nested settingsMenuVisibility dict, exposed to QML as a JSON string (property and get_settings_menu_visibility()) plus a per-section boolean query: 

"settingsMenuVisibility": {
    "displaySettings": true,
    "mediaSettings": true,
    "obdSettings": true,
    "accessoriesSettings": true,
    "deviceSettings": true,
    "about": true      // every section visible by default
}
  • is_settings_section_visible(section) returns the stored flag, or true for a section that is not in the dict
  • save_settings_section_visibility(section, visible) stores the flag and emits settingsMenuVisibilityChanged (no arguments)
  • get_settings_menu_visibility() returns the whole dict as JSON

The toggles live in the settingsVisibilityPopup defined in frontend/BottomBar.qml, opened by a press-and-hold on the settings navigation button (a tap navigates as before), and frontend/SettingsMenu.qml filters its page model through is_settings_section_visible(). The default keys are exactly the menu's six sections: displaySettings, mediaSettings, obdSettings, accessoriesSettings (Volume Knob, IMU, Gesture and Phone Dock sub-sections; desktop only), deviceSettings and about, all true. A file written by an older build may still carry the retired per-feature keys (androidAutoSettings, phoneMirrorSettings, volumeKnobSettings, gestureSensorSettings); they are kept but nothing reads them, and any current section missing from the file reads as visible in both backends. See Settings UI for the layouts.

Pinned Quick Settings

Users can pin registry entries to the Quick Panel. Pinned IDs are stored in the pinnedSettings list (property, is_setting_pinned(id), toggle_pin_setting(id)). Only IDs present in the registry can be pinned: 

@Slot(str)
def toggle_pin_setting(self, setting_id):
    if setting_id in self._pinned_settings:
        self._pinned_settings.remove(setting_id)
    else:
        if setting_id in SETTINGS_REGISTRY:
            self._pinned_settings.append(setting_id)
    settings = self.load_settings()
    settings["pinnedSettings"] = self._pinned_settings
    self.save_settings(settings)
    self.pinnedSettingsChanged.emit()

get_pinned_settings_metadata() returns a JSON array of the pinned registry entries, each extended with id and currentValue. The value is resolved through _key_to_attr() / keyToAttr(), a 13-entry map from camelCase key to backing-member name (Python then getattrs _<attr>; C++ switches on the attr name); any key not in that map falls back to the in-memory settings dict, which is equally current, so the map is an optimisation, not a requirement.

Generic Setting Access

For values that do not warrant a dedicated property, QML uses the generic accessors. They read and write the same in-memory dict, so a generic key and a property-backed key are persisted identically; the differences are that generic keys have no type validation unless they also appear in the defaults, and that change notification is the single genericSettingChanged(key) signal instead of a per-key signal. 

@Slot(str, result='QVariant')
def get_setting(self, key, default_value=None):
    return self._settings.get(key, default_value)

@Slot(str, 'QVariant', result='QVariant')
def get_setting_with_default(self, key, default_value):
    return self._settings.get(key, default_value)

@Slot(str, 'QVariant')
def save_setting(self, key, value):
    settings = self.load_settings()
    settings[key] = value
    self.save_settings(settings)
    self.genericSettingChanged.emit(key)

Two families of keys use this path today:

  • Keys with a default but no property: the IMU display keys (sensorEmitRate, sensorDecimalPlaces, sensorTempUnit, sensorAltitudeUnit, sensorShow*), expandedCards, and the three download keys, which DownloadManager reads with get_setting(). These are type-validated like any other default.
  • QML-only keys with no backend default: the RPM shift-light configuration (rpm_*), obdCardStyleCircular, lastOBDPage, lastSensorPage, activeDashboard and dashboardEditorDraft. Their defaults live in the QML call sites and they survive validation through the forward-compatibility copy. The full list with defaults is in the Settings Reference.
Both backends must still know a key
A QML-only key needs no backend code, but it also gets no validation: a corrupted value is passed to QML as-is. Anything with a meaningful type or range should get a default in both backends in the same commit, which is all the validation needs.

Album Art Colors

When the "Album Art Capture" theme is active, the palette extracted from the current cover is pushed to SettingsManager as a JSON string. This is the single distribution point: MediaManager and SpotifyManager both call set_album_art_colors(), QML binds settingsManager.albumArtColors (see Theme System), and main.py forwards the same signal to the ESP32 knob's LEDs when esp32LedColorMode is "theme". 

@Property(str, notify=albumArtColorsChanged)
def albumArtColors(self):
    return self._album_art_colors

@Slot(str)
def set_album_art_colors(self, colors_json):
    self._album_art_colors = colors_json
    self.update_setting("albumArtColors", colors_json, self.albumArtColorsChanged)

The JSON is persisted under the albumArtColors key so the last palette is reapplied at the next startup before a fresh extraction finishes, which avoids flashing the placeholder theme. Because extraction runs on every track change, this is the setter that benefits most from the coalesced write.

Connection to QML and Other Managers

SettingsManager is constructed first and registered as the QML context property settingsManager in main.py and src/main.cpp: 

settings_manager = SettingsManager()
engine.rootContext().setContextProperty("settingsManager", settings_manager)
SettingsManager settingsManager;
ctx->setContextProperty("settingsManager", &settingsManager);

It is then handed to nearly every other manager, either through the constructor (Clock, VolumeController, OBDManager) or a connect_settings_manager() / setSettingsManager() call (MediaManager, SpotifyManager, ESP32VolumeManager, BerryIMUManager, GestureManager, DownloadManager). PhoneMirrorManager is primed from the get_scrcpy_* getters and its scrcpyAudioGainChanged, scrcpyAudioDuckEnabledChanged, scrcpyAudioDuckLevelChanged and scrcpyPhoneScreenOffChanged signals are wired straight into the manager's setters, so those Accessories-page sliders apply live.

QML accesses settings directly:

// Read a property (binding updates on the notify signal)
text: settingsManager.deviceName

// Write via slot
settingsManager.save_device_name(newName)

// React to changes
Connections {
    target: settingsManager
    function onThemeSettingChanged(theme) { /* ... */ }
    function onGenericSettingChanged(key) { if (key === "lastOBDPage") { /* ... */ } }
}

// Generic key with a QML-side default
property bool shiftLightEnabled: settingsManager.get_setting_with_default("rpm_shift_light_enabled", true)

Shutdown order in both entry points, from aboutToQuit: mediaManager._save_playback_state() first (its own debounce may be pending), then settingsManager.flushPendingSave() so the playback state is inside the final write.

Design Decisions

One JSON file, not QSettings or a database

A single human-readable JSON document is the format both backends can produce and consume byte-for-byte (json.dump(indent=4) and QJsonDocument::Indented both emit 4-space indented UTF-8), which is what makes the CLAUDE.md rule "JSON persistence formats are shared on disk" enforceable: a Jeep head unit on the Python backend and a laptop on the C++ build can swap the file. QSettings would have put the data in the Windows registry, macOS plists and INI files with Qt-specific escaping, and PySide6 and C++ do not agree on type round-tripping through it. JSON also carries nested dicts (obdParameters with 86 PIDs, gestureMapping, customThemes with embedded theme objects) without flattening keys, and a tinkerer can edit it in a text editor on the Pi, which is one of the reasons the Python backend exists.

Defaults dict as the schema, validation by type

Rather than a separate schema file, the defaults dict is the schema: a key's presence declares it, its default value declares its type, and adding a setting is one line. Validation compares stored values against that type and falls back to the default rather than refusing to load, because a head unit that boots into defaults after a bad write is usable and one that shows an error dialog at 60 mph is not. Unknown keys are kept ("for forward compatibility", per the comment in both validators) so an older build never destroys a newer build's settings, or the QML-only keys, when both touch the same file.

Memory-served reads, one coalesced write

Before the 2026-09 sweep every getter re-read and re-validated the file and every setter wrote it. On the Orange Pi that meant a parse+validate+write on every slider release and on every track change (album colours), all on the GUI thread, and a steady stream of small writes to an SD card. The commit that changed this (ee5a23e) states the rationale in the code comments: after the constructor the in-memory dict is authoritative because every setter goes through save_settings(), so re-reading "always returned what we had just written". The 500 ms single-shot timer is restarted on every call, which turns a burst of any length into one atomic write and also spares the SD card. The trade-off, accepted deliberately, is that a hard kill within the window loses the last change; a normal quit flushes.

Validation at save time, not write time

save_settings() validates into the cache and the disk writer takes the object as given (2605d93 in Python, 037f753 for C++ parity). Validating once at the boundary where data enters the cache means the cache can never hold an ill-typed value, every getter and every get_setting() call is guaranteed clean without re-checking, and the deferred write does not pay for a second pass over 92 keys plus 86 PIDs. Per-setter domain checks (enumerated strings, clamped sliders) sit even earlier, in the slot, because the type check cannot express "one of four layout names" or "2 to 32 pixels".

Debounced OBD toggles with an in-memory fast path

The OBD parameter page has 86 toggles and a "scan vehicle" action that flips many at once. save_obd_parameter_enabled() writes only to the in-memory map so the toggle animates instantly, and get_obd_parameter_enabled() reads that same map, so the page never waits for persistence. The 800 ms debounce predates the general 500 ms coalescing and is kept because it also batches the obdParametersChanged signal, which OBDManager connects to its watcher refresh (_refresh_watchers / onSettingsParametersChanged); one refresh per batch instead of one per toggle.

Registry metadata instead of per-setting QML

The Quick Panel, the pin system and the dashboard widgets all need "render this setting as a control". Putting label, control type and slot name in one dict per backend means a new pinnable setting is a registry entry plus the normal property/slot triple, and QML renders it generically from get_settings_registry(). The registry lives in the backend rather than QML so both backends stay the source of truth for what is pinnable and toggle_pin_setting() can refuse unknown IDs.

Snake_case slots, camelCase properties, string-typed JSON properties

The API shape is the Python original's: properties use the JSON key name so QML bindings read like the file, slots use Python naming, and the C++ port copied both verbatim so that not a single QML file changed when the C++ backend became the shipped one. Dict-shaped state (settingsMenuVisibility, albumArtColors, obdSavedAdapters) crosses to QML as JSON strings: a string property needs no QVariantMap marshalling on either side and serialises to the file unchanged, so the property, the getter and the on-disk value are the same bytes; QML pays one JSON.parse.

How to Add a New Setting

Do every step in both backends in the same commit (CLAUDE.md parity rule), then add the key to Settings Reference and, if it is user-facing, to Signals & Slots Reference. Python steps shown; the C++ equivalents are the default in buildDefaultSettings(), a Q_PROPERTY, a signal, a member initialised in the constructor, a getter, and the save_* slot.

  1. Add the default value to self._default_settings in __init__. Use a float literal for float settings: 
    "myNewFeature": False,
  2. Declare the change signal at the class level: 
    myNewFeatureChanged = Signal(bool)
  3. Initialize the backing attribute from loaded settings in __init__: 
    self._my_new_feature = self._settings.get("myNewFeature", self._default_settings["myNewFeature"])
  4. Add the Property: 
    @Property(bool, notify=myNewFeatureChanged)
def myNewFeature(self):
    return self._my_new_feature
  5. Add the save Slot (clamp or whitelist here if the value has a domain): 
    @Slot(bool)
def save_my_new_feature(self, enabled):
    self._my_new_feature = enabled
    self.update_setting("myNewFeature", enabled, self.myNewFeatureChanged)
  6. (Optional) Add to SETTINGS_REGISTRY if the setting should be pinnable / appear in the Quick Panel: 
    "my_new_feature": {
    "key": "myNewFeature", "label": "My New Feature",
    "category": "mediaSettings",
    "controlType": "toggle", "saveSlot": "save_my_new_feature"
},
  7. (Optional) Add to _key_to_attr / keyToAttr() so currentValue resolves from the member (the settings-dict fallback works without it): 
    "myNewFeature": "my_new_feature",
  8. Emit its signal from reset_to_defaults() — the member itself is reloaded by _load_members_from_settings() / populateMembers(), but the signal list in reset_to_defaults() is explicit.
  9. Wire the UI on the owning page under frontend/settings/ and, if it is a Now Playing visual, in frontend/NowPlayingStudio.qml (which carries a commented template for exactly this).
Tip
If the setting is only read by one QML component and has no meaningful validation, the generic save_setting(key, value) / get_setting_with_default(key, default) pair needs no backend change at all; genericSettingChanged(key) notifies listeners. Still add a default to both backends when the value has a type worth protecting.
