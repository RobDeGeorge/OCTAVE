What It Is

Everything you change in Settings (the theme, the clock, the music folder, which OBD adapter to use) is kept in one text file, settingsConfigure.json. The settings manager is the part of OCTAVE that owns that file: it reads it once when the app starts, hands every setting to the screens and to the other parts of the app, and writes the file again when something changes.

The file is plain JSON, the same on every platform, so you can copy it to another machine, read it and edit it in a text editor. The folder it lives in is what the rest of this wiki calls the config folder: logs, trip history, your dashboards and vehicles are kept beside it.

This page starts with how to use it and gets more technical as it goes. The list of every setting, with its default and range, is the Settings Reference; the settings screens are described in Settings UI.

Back Up, Reset, Edit by Hand

Quit OCTAVE first for all three. The app reads the file once, at start, and from then on writes the whole file from what it holds in memory: a change you make to the file while the app runs is overwritten at the next save.

ToDo this
Back up your settingsCopy settingsConfigure.json somewhere safe. To keep trips, dashboards and vehicles too, copy the whole config folder
Move settings to another machineCopy the file into that machine's config folder. Paths in it (the music folder, serial ports) belong to the old machine: set them again in Settings
Reset everythingDelete or rename settingsConfigure.json. The next start writes a new one with the defaults. There is no reset button in the app
Reset one settingDelete its line from the file. A missing key gets its default
Change a setting by handEdit its value and save. Key names and allowed values are in the Settings Reference

What happens to a hand edit that is not quite right:

  • A value of the wrong type (text where a number belongs): that setting gets its default.
  • A number outside its range: for most settings it is brought to the nearest limit. A few slider settings (interface scale, clock size, colour transition time, background blur, startup volume) are kept as written.
  • A word that is not one of the choices (a window state that does not exist): that setting gets its default.
  • A key OCTAVE does not know: it is kept, untouched.
  • Broken JSON (a missing comma or brace): the whole file is set aside as settingsConfigure.json.corrupt and the settings from settingsConfigure.json.bak come back. Your edit is in the .corrupt file; fix it there and copy it back.
The file is private
On Linux, macOS and Android the file is readable by your user only. It names the devices paired with the service API, so do not post it whole when asking for help.

How Code Reads and Writes a Setting

From here on the page is technical: it is for people writing QML, another frontend, or C++ in src/.

The class is SettingsManager. QML and the service API see it as the object settingsManager (a context property: a C++ object QML can use by name anywhere). C++ managers get a pointer to it when they are built. Every setting is read from memory, so reading one costs nothing.

There are three kinds of setting, and each is used a little differently:

KindExamplesHow to use it
Plain setting: one on/off, number or text. Most settingsshowClock, uiScale, themeSettingA property of the same name. Read it, bind to it, assign to it
List or mapcustomThemes, gestureMapping, obdSavedAdaptersA read-only property plus methods that change it (save_custom_theme(), save_gesture_action(), add_obd_saved_adapter())
Key with no propertyhomeScreen, lastOBDPage, the airPlay* and rpm_* keysBy name: get_setting_with_default() and save_setting()

A plain setting

In QML, a plain setting is an ordinary property. Bind to it and the binding follows every change:

// Read: this text follows the setting
Text { text: settingsManager.deviceName }

// Write: assign to it
Switch {
    checked: settingsManager.showClock
    onToggled: settingsManager.showClock = checked
}

In C++, call the getter and the save slot, and connect to the signal named <key>Changed:

if (m_settings->obdFastMode()) { /* ... */ }

m_settings->save_obd_fast_mode(false);

connect(m_settings, &SettingsManager::obdFastModeChanged, this, [this](bool on) { /* ... */ });

Each plain setting also has a save_<key> slot (save_show_clock(true)) and some have a get_<key>() method. They do exactly what the property does. For QML and for service clients they are deprecated aliases that go away in protocol 5; most of the app's own QML still calls them. New QML should use the property.

Two signal names do not follow the key: clockFormat24Hour announces with clockFormatChanged, and startUpVolumeChanged carries the number as text, so read the startUpVolume property rather than the signal's argument.

What a write goes through

However a plain setting is written (assignment, save slot, save_setting(), apply_settings(), the service's set), it takes one path:

  1. Type. The value becomes the setting's type. From save_setting(), apply_settings() and the service it must already be that type: the text "true" is not a bool. A fractional number for a whole-number setting is rounded.
  2. Rule. Each setting has a rule. A number is either brought into its range or refused when outside it; a choice is refused unless it is one of the allowed words. The rule for each key is in the Settings Reference.
  3. Unchanged? The same value again stops here: nothing is written and no signal is sent.
  4. Store, save, announce. The value is stored in memory, a save to disk is scheduled, and the setting's signal is emitted.

A refused value changes nothing and writes a warning to the log (Setting uiScale refused: ...). The call itself does not fail, so after writing a value from outside, read the property back if you need to know.

A key with no property

Some keys are only ever read by one screen or one manager and have no property. Use them by name, and give the default at the place you read it: 

property string homeScreen: settingsManager.get_setting_with_default("homeScreen", "")

settingsManager.save_setting("homeScreen", "cockpit")

Connections {
    target: settingsManager
    function onGenericSettingChanged(key) {
        if (key === "homeScreen")
            homeScreen = settingsManager.get_setting_with_default("homeScreen", "")
    }
}

A call is not a binding: the value does not follow later changes by itself, which is why the example listens for genericSettingChanged(key). A key used this way needs no C++ at all, and gets no checking either, unless it has a default in the code: then a value of another type is dropped for the default.

save_setting() and get_setting() also work on a plain setting, by the same path as its property: save_setting("uiScale", 1.5) moves settingsManager.uiScale and emits uiScaleChanged as well as genericSettingChanged("uiScale"). get_setting() returns undefined for a key that does not exist.

Every property, method and signal, with its types and the permission it needs, is in the generated API reference. A device paired over the service API needs the settings permission to change a setting and only read to read one.

How a Change Reaches the Screen

There is no "apply" step. A setting changes in memory at once and announces itself with a signal; the disk write follows later (see How Saving Works).

  1. Something writes the setting: a control on a Settings page, another manager, or a client of the service API.
  2. The manager checks the value, stores it and emits <key>Changed.
  3. Every QML binding that reads settingsManager.<key> re-evaluates. The clock disappears, the theme changes, the slider on another page moves.
  4. C++ managers that connected to the signal act on it: the phone mirror takes the new audio level, the gauges take the new units, the volume knob's LEDs take the new colour.

Three things follow from this:

  • A screen never needs to be told that a setting changed. If it shows a stale value, it copied the value into a property of its own instead of binding to it.
  • Writing the same value twice is free: the second write is dropped before any signal.
  • A key with no property has no binding to re-evaluate. Whoever shows it must listen for genericSettingChanged(key), as in the example above.

Managers receive the settings manager when the app is put together in src/appcore.cpp, which is also where settings that one manager owns and another needs are wired across (the phone mirror's audio levels, the gauge units).

How to Add a New Setting

If only one screen reads the value and it needs no checking, you do not need any of this: use save_setting() and get_setting_with_default() with a new key name, as in A key with no property. For a real setting with a property, a default and a rule:

  1. Add a row to the settings table, OCTAVE_SETTINGS near the top of src/managers/settingsmanager.cpp: key, type, default, rule, signal, save slot. The row is the setting's default, its loading, its limits and its reset. 
    X(myNewFeature, QMetaType::Bool, false, any(), N_BOOL(myNewFeatureChanged), "save_my_new_feature", Plain) \
    The rules: any() takes every value of the type, clampTo(lo, hi) brings a number into range, within(lo, hi) refuses a number outside it, oneOf({...}) refuses any other word, custom(fn) is a function that may change or refuse the value.
  2. Declare it in settingsmanager.h: the property, the getter, the signal and the slot. 
    Q_PROPERTY(bool myNewFeature READ myNewFeature WRITE save_my_new_feature NOTIFY myNewFeatureChanged)
    bool myNewFeature() const;
signals:
    void myNewFeatureChanged(bool value);
public slots:
    void save_my_new_feature(bool enabled);
  3. Write the two one-line bodies in the .cpp: 
    bool SettingsManager::myNewFeature() const { return row(R_myNewFeature).toBool(); }
void SettingsManager::save_my_new_feature(bool enabled) { setRow(R_myNewFeature, enabled); }
  4. Mark the slot as a deprecated alias of the property, beside the others at the top of the header: 
    Q_CLASSINFO("octave.deprecated.save_my_new_feature", "use the myNewFeature property; goes in protocol 5")
  5. Put a control on a Settings page under frontend/settings/, bound to settingsManager.myNewFeature.
  6. Build and run the tests. tst_settingsmanager fails if a row has no matching property, signal or slot, or a writable property has no row.
  7. Regenerate the published API in the same commit (tst_apidocs fails otherwise): 
    ./build/octave --dump-api docs/api && venv/bin/python wiki/build_api_reference.py \
  && npm --prefix sdk/typescript run generate && (cd sdk/go && go generate ./...)
  8. Add the key to the Settings Reference, and to Settings UI if it has a control.

You do not write anything for loading, saving, validation or reset: the row does all of it. A setting that is a list or a map is not a row; follow an existing one (gestureMapping) instead.

How Saving Works

The manager keeps every setting in memory and treats the file as a copy of that. Reads never touch the disk. Writes are collected and done in one piece, so the file is always whole.

At start

  1. No file: one is written with the defaults. This is a fresh install.
  2. A file that parses: it is copied to settingsConfigure.json.bak, once per run. That copy is the last file known to be good.
  3. A file that does not parse (typically power cut mid-write): it is renamed to settingsConfigure.json.corrupt, the .bak copy is loaded and written back as the live file. With no usable backup, the defaults are used.
  4. Each value is checked against its default's type and its rule, as described under editing by hand. A bad value costs that one setting, never the whole file.
  5. Old files are brought up to date (below).

Saving a change

A change does not write the file straight away. It starts a 500 ms timer, and every further change restarts it; when the settings have been quiet for half a second, the file is written once. Dragging a slider, or a new album-art colour palette on every track, costs one write rather than dozens, which also spares an SD card.

On a normal quit the pending write is done before the app exits, after the music player has stored where playback stopped. If the app is killed or the power goes within that half second, the last change is lost; everything before it is safe.

The write itself

The file is never written in place. The new contents go to a temporary file in the same folder, are flushed to disk, and the temporary file is then renamed over settingsConfigure.json in one step. A power cut leaves the old file or the new one, never half of one. If the write fails, the existing file is left alone and the next save tries again. The file is JSON indented by four spaces, readable by its owner only (except on Windows).

Files from older versions

An older file is fixed up when it is loaded. Nothing needs doing by hand.

  • A setting added since the file was written gets its default; the rest of the file is kept.
  • Settings of removed features (the old Spotify keys, the music downloader, the phone audio toggle) are deleted from the file.
  • A few old values are replaced: an interface scale of 0.6 (an old default) becomes 1.0, the font name Google Sans becomes GoogleSans Regular, the OBD port /dev/rfcomm0 (an old placeholder) is cleared.
  • A key the app does not know is kept as it is, so a newer build's settings survive a run of an older one.

Details and Special Cases

Keys only the file can set

Four keys control the service API: serviceEnabled, serviceWebRoot, serviceLoopbackOpen and serviceTokens (the paired devices). save_setting() and apply_settings() refuse them, get_setting() will not return them, and reset_to_defaults() leaves them as they are. A client of the service must not be able to switch the service on for the next start, change what it serves, or read the pairing list. Change them by editing the file. See Architecture for the service.

The music folder

mediaFolder is empty in a new file. Empty means the system's music folder (~/Music on most desktops), which OCTAVE creates if it is missing, except on Android.

Hidden Settings sections

Press and hold the Settings button on the bottom bar to choose which sections of the Settings menu show. The choice is the settingsMenuVisibility map; a section missing from it is visible.

Values the app stores for itself

Not everything in the file is a preference. The app also keeps state there so it can pick up where it left off: the last song and position, the last Settings section, the window size, the remembered OBD adapters, and the colours taken from the last album cover (albumArtColors, so the Album Art Capture theme does not flash a placeholder at start). These are set by the managers that own them: Media Manager, OBD Manager, Theme System.

settingsManager.currentVolume is the live volume, 0 to 100. It starts from the startup volume and is never saved. Do not set it yourself: all volume changes go through the volume controller (Architecture).

Pinnable settings

The manager holds a short list of settings that a frontend can draw as a control without knowing them in advance (30 of them: toggles, sliders and choice chips for media, display, OBD and sensor settings). get_settings_registry() returns the list as JSON. Each entry gives the setting's key, a label, a category, a controlType (toggle, slider or chips), the slider's range or the chips' options in params, and its saveSlot.

A user's picks from that list are the pinnedSettings setting. toggle_pin_setting(id) pins or unpins one (an id not in the list is ignored), and get_pinned_settings_metadata() returns the pinned entries with their current values. No screen of the built-in QML frontend shows pinned settings at present; the console example frontend (examples/frontends/console/) uses the list.

Left over

  • The folder history (directoryHistory) is stored and has an API, but nothing in the app reads or writes it.
  • obdParameters, a map of readings switched on and off, is kept for old files. What gets polled is decided by which screens are showing (OBD Manager).
  • homeOBDParameters and homeVehicleCard belong to the classic Home screen and are deprecated: Home is a dashboard (Gauges & Dashboards).
  • The three scrcpyBitRate* settings are stored and announced, but nothing acts on them: the phone mirror picks its video bit rate itself.

When Something Goes Wrong

  1. A setting does not stick. Look in logs/octave-cpp-error.log in the config folder for Setting <key> refused: the value was the wrong type or outside what the setting takes.
  2. A hand edit disappeared. The app was running when you edited, and it wrote its own copy over yours. Quit first.
  3. All settings went back to an earlier state. The file was damaged and the backup was restored. The log says Settings file corrupted and Restored settings from backup, and the damaged file is beside the live one as .corrupt.
  4. All settings went back to defaults. Either the file was missing (a different config folder: check --config, XDG_CONFIG_HOME and whether --sim or --dev was used), or it was damaged with no usable backup (No usable settings backup in the log).
  5. The last change before a power cut is gone. Expected: it was inside the half-second before the write. In a car, cut power to the head unit after OCTAVE has quit, or accept losing the last tap.
  6. A screen shows an old value. It read the setting once instead of binding to it. See How a Change Reaches the Screen.

The full API is generated from the code: API reference, settingsManager.

tst_settingsmanager covers, among others: the table against the declared properties (tableMatchesTheMetaObject), that the by-name and the property path agree for every setting (genericAndTypedPathsAgreeForEveryRow), that every setting survives a restart, that refused and unchanged values write nothing, recovery from a damaged file (corruptSettingsRestoredFromBackup), a failed write leaving the file intact, and that the service keys stay file-only. Run it with ctest --test-dir build -R tst_settingsmanager. A test that builds a SettingsManager must point XDG_CONFIG_HOME at a temporary folder first, or it writes into your real settings (Development).

Why It Is Built This Way

  • One JSON file, not the platform's settings store. Qt's QSettings would put the values in the registry on Windows and a plist on macOS. One JSON file is the same everywhere, holds nested values (themes, gesture bindings) as they are, and can be read, copied and edited by hand on the head unit.
  • One table, one way in. Every plain setting is a row, and every way of writing it ends in the same function. A property write, a save slot and a write by name cannot disagree about a setting's type, range or current value.
  • A bad value costs one setting, not the file. A head unit that starts with one default is usable; one that refuses to start is not. The same reasoning restores the backup rather than stopping on a damaged file.
  • Memory first, one delayed write. Reading the file on every read and writing it on every change put a parse and a write on the interface thread for each slider step. Since every change goes through the manager, memory is always right, and the file only has to catch up. The price is the half second a hard power cut can lose.
  • Unknown keys are kept. Screens can keep small state by name without any C++, and an older build never destroys a newer build's settings.
  • The service's own switches are out of its clients' reach. A paired device with the settings permission can change preferences, but cannot enable the service for the next start or point it at another folder to serve.
