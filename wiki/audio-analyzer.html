Pipeline Overview

backend/audio_analyzer.py (Python) and src/managers/audioanalyzer.{h,cpp} (C++) pre-compute FFT visualization data for an entire audio track on a worker thread, then serve time-indexed levels to QML based on the playback position. Nothing is computed in real time during playback. Both backends expose the same audioAnalyzer API, use 96 bars and 100 ms chunks, and produce the same 0-8 integer levels; where their internals differ this page says so.

Bar Count and the Single Toggle

The visualizer renders a fixed 96 frequency bars (m_numBars = 96 / _num_bars = 96) and MediaRoom polls the position every 16 ms (about 60 updates per second). Earlier versions had tiered quality settings; commit 118f484 collapsed them into the single showWaveformVisualizer setting (default true, see Settings Reference). The MediaRoom container hard-codes what used to be the top tier: 96 bars, 16 ms timer, 120 ms InOutSine bar animations and pill-shaped "fancy" bars. There are no quality tiers left in either backend or the QML.

Audio Decoding

Python: PyAV

The Python backend decodes with PyAV, so virtually any container FFmpeg understands works. Every frame is converted to an ndarray; multi-channel frames are averaged to mono:

container = av.open(file_path)
audio_stream = next((s for s in container.streams if s.type == 'audio'), None)

samples = []
sample_rate = audio_stream.rate or 44100

for frame in container.decode(audio_stream):
    frame_data = frame.to_ndarray()
    if len(frame_data.shape) > 1:
        frame_data = frame_data.mean(axis=0)   # stereo -> mono
    samples.append(frame_data)

container.close()

Python preprocessing

  1. Concatenate - all decoded frames are joined into one float32 array
  2. Normalize - divide by the global maximum absolute value to get a [-1, 1] range
  3. Decimate - keep every Nth sample with N = sample_rate // 8000, so a 44.1 kHz file becomes 8820 Hz and a 48 kHz file 8000 Hz (effective_rate = sample_rate // N). There is no anti-aliasing filter; for a visualizer that is acceptable and it cuts the FFT work roughly five-fold.
all_samples = np.concatenate(samples).astype(np.float32)
max_val = np.max(np.abs(all_samples))
if max_val > 0:
    all_samples = all_samples / max_val

downsample_factor = max(1, sample_rate // 8000)
all_samples = all_samples[::downsample_factor]
effective_rate = sample_rate // downsample_factor

C++: QAudioDecoder

The C++ backend asks Qt Multimedia's QAudioDecoder for 8 kHz, mono, Int16 output directly, so the channel mix-down and resampling happen inside the platform decoder and the analyzer never sees the original rate. Int16 is requested rather than Float because some Android MediaCodec configurations reject float sample formats; the buffer is converted to normalized float32 (× 1/32768) afterwards. Because the worker has no event loop of its own, the decode runs a local QEventLoop that quits on finished or error, with a 30 s single-shot watchdog so a stalled codec cannot hang the worker forever. An error or an empty buffer makes the analysis fail (no data, bars stay at zero).

QAudioDecoder decoder;
QAudioFormat fmt;
fmt.setSampleRate(8000);
fmt.setChannelCount(1);
fmt.setSampleFormat(QAudioFormat::Int16);
decoder.setAudioFormat(fmt);
decoder.setSource(QUrl::fromLocalFile(filePath));

QEventLoop loop;
QObject::connect(&decoder, &QAudioDecoder::bufferReady, &decoder, [&]() {
    while (decoder.bufferAvailable()) {
        QAudioBuffer buf = decoder.read();
        rawInt16.append(buf.constData<char>(), buf.byteCount());
    }
});
QObject::connect(&decoder, &QAudioDecoder::finished, &loop, &QEventLoop::quit);
QTimer::singleShot(30000, &loop, &QEventLoop::quit);   // watchdog
decoder.start();
loop.exec();

FFT Pipeline

The preprocessed audio is split into 100 ms chunks (chunk_duration = 0.1, 10 chunks per second). In Python chunk_size = int(effective_rate * 0.1) (882 samples for a 44.1 kHz source, 800 for 48 kHz); in C++ it is always 800 samples, zero-padded to the next power of two (1024) because the radix-2 FFT needs a power-of-two length. Each chunk is analyzed independently:

chunk_size = int(effective_rate * self._chunk_duration)
num_chunks = len(all_samples) // chunk_size
window = np.hanning(chunk_size)     # pre-computed once

Per-Chunk Processing

  1. Window function - a Hann window (np.hanning / hannWindow()) reduces spectral leakage at chunk boundaries: 
    windowed = chunk * window
  2. FFT and magnitude - both backends keep the magnitudes of every positive-frequency bin except DC, i.e. bins 1 .. N/2, which at the 8 kHz effective rate is 0-4 kHz: 
    fft_len = chunk_size // 2
fft = np.abs(np.fft.rfft(windowed))[1:1 + fft_len]   # skip DC
    Python gets chunk_size // 2 bins (441 at 10 Hz for an 882-sample chunk, 400 for 800 samples); C++ runs the complex radix-2 FFT on the 1024-point padded buffer and keeps fftSize / 2 = 512 magnitudes at 7.8 Hz per bin. (An earlier Python version halved the rfft output a second time and so only showed 0-2 kHz; the two visualizers now cover the same range.)
  3. Logarithmic frequency bands - the bins are grouped into 96 bands with logarithmic spacing, giving more resolution to low frequencies. The edges are computed once per file by _log_band_edges(fft_len, num_bars) / logBandEdges(fftLen, numBars), since they depend only on the bin count: 
    edges = [0] * (num_bars + 1)
for i in range(1, num_bars + 1):
    idx = int(fft_len ** (i / num_bars))      # the np.logspace(0, log10(N), 97) curve
    idx = max(idx, edges[i - 1] + 1)          # every band at least one bin wide
    edges[i] = min(idx, fft_len)
edges[num_bars] = fft_len
    Edge i is N^(i/96) truncated, but forced to be strictly greater than the previous edge, so the first bands are one bin each (linear) until the log curve overtakes them.
  4. Band averaging - each band's value is the mean of its bins; because the edges are strictly increasing, every band has at least one bin

Global Normalization (Two-Pass)

After the raw magnitudes of every chunk are known, a second pass normalizes and quantizes:

# 95th percentile of every non-zero band value in the track
all_values = [v for chunk in raw_fft_data for v in chunk if v > 0]
global_max = np.percentile(all_values, 95) if all_values else 1.0

for levels in raw_fft_data:
    for level in levels:
        norm = level / global_max
        norm = min(1.0, norm) ** 0.6   # power curve for visual balance
        quantized = int(norm * 8)      # 0-8 integer levels

C++ sorts the values and takes the element at index 0.95 × n instead of numpy's interpolated percentile; the difference is negligible for a visualizer.

Why 95th percentile? Using the maximum value would compress the entire visualization to accommodate rare peaks. The 95th percentile allows occasional clipping at 8 but keeps the overall visualization dynamic and visually interesting.
Why power curve 0.6? The ** 0.6 exponent compresses the dynamic range, boosting quiet passages and taming loud ones. Without it, most bars would hover near zero with occasional spikes. The value was tuned by eye for visual balance.

Frequency Band Distribution

Linear spacing would dedicate most bars to high frequencies, which are less musically interesting; logarithmic spacing mirrors how pitch is perceived. Boundary i of 96 sits at bin N^(i/96) (truncated to an integer, then bumped to at least the previous boundary + 1), where N is the number of magnitude bins covering 0-4 kHz: 512 in C++ (7.8 Hz/bin), 400 or 441 in Python depending on whether the source decimated to 8000 or 8820 Hz (10 Hz/bin). Approximate boundaries for the 8 kHz case:

BarC++ (N = 512, 7.8 Hz/bin)Python (N = 400, 10 Hz/bin)
1-24one bin each (linear), 8-188 Hzone bin each (linear), 10-240 Hz
48bin 48, ~375 Hzbin 48, ~480 Hz
72bin 107, ~836 Hzbin 89, ~890 Hz
96bin 512, ~4 kHzbin 400, ~4 kHz
Why the first bands are linear. Truncated to an integer, N^(i/96) stays at 1 for roughly the first dozen boundaries, which used to leave those bands with no bins at all -- the leftmost bars of the visualizer were permanently 0 in both backends. The edge builder now forces every band to be at least one bin wide, so the low bars are consecutive single bins (a linear stretch that lasts until about bar 65, where N^(i/96) finally outgrows i) and only the upper third is truly logarithmic.

Data Flow

Once analysis is complete, the playback position is mapped to a chunk on every call:

@Slot(float)
def update_position(self, position_seconds: float):
    if not self._fft_data or not self._is_active:
        return

    chunk_index = int(position_seconds * 10)     # 10 chunks per second
    chunk_index = max(0, min(chunk_index, len(self._fft_data) - 1))

    new_levels = self._fft_data[chunk_index]
    if new_levels != self._current_levels:     # only emit on change
        self._current_levels = new_levels
        self.fftDataChanged.emit(new_levels)

The change detection prevents a signal (and 96 QML property writes) when the position is still inside the same chunk. The C++ version builds a QVariantList and compares it with the last emitted one the same way. set_active(false) emits a list of 96 zeros to clear the display; clear() drops the data and remembered file.

Threading Model

Decoding and FFT of a whole track take seconds and must not block the Qt event loop, so both backends run _analyze_audio() / analyzeAudio() off the GUI thread and only touch Qt objects on the GUI thread afterwards.

Python

self._executor = ThreadPoolExecutor(max_workers=1)

# analyze_file(): submit, then poll from the main thread
self._pending_future = self._executor.submit(self._analyze_audio, file_path)
self._poll_timer.start()          # 100 ms QTimer

def _check_analysis_done(self):
    if self._pending_future is None or not self._pending_future.done():
        return
    self._poll_timer.stop()
    future, self._pending_future = self._pending_future, None
    self._analyzing = False
    result = future.result()
    if result is not None:
        self._fft_data = result
        self.analysisComplete.emit()

The worker returns a plain list of lists (or None on failure); the poll timer collects it on the main thread where emitting Qt signals is safe.

C++

QFuture<AnalysisResult> future = QtConcurrent::run(
    [filePath, bars, chunkDur]() {
        return AudioAnalyzer::analyzeAudio(filePath, bars, chunkDur);   // static, no member access
    });
m_watcher.setFuture(future);        // finished -> onAnalysisDone() on the GUI thread

analyzeAudio() is a static function that receives everything it needs as arguments; QFutureWatcher::finished delivers the result to onAnalysisDone() on the GUI thread. The destructor cancels and waits for the watcher so the app can quit mid-analysis.

Thread Safety: the worker functions must NOT touch member state or Qt GUI objects. They take the file path (and bar count) as arguments and return the computed data; all signal emissions and member writes happen on the GUI thread in _check_analysis_done() / onAnalysisDone().

Guard Conditions

  • Missing file: an empty or non-existent path is rejected with a warning
  • Skip if already analyzed: if the same path is requested and data exists, nothing happens
  • Busy: if an analysis is running, the Python backend drops the new request; the C++ backend remembers the latest requested file (m_pendingFile) and onAnalysisDone() chains into it, so a fast skip sequence does not leave the visualizer on the old track's data (or blank if the old track was never analyzed). A request that lands during the chained analysis replaces the pending file again.
  • Graceful degradation: if NumPy or PyAV are not installed the Python analyzer logs a warning and returns; the C++ analyzer needs only Qt Multimedia

QML Integration

The only consumer is the waveform container in frontend/MediaRoom.qml, visible when settingsManager.showWaveformVisualizer is on, the local player (not Spotify) is the source, and the playlist is not empty. The pieces, quoted from the QML:

// Analysis is deferred until the album-art carousel has settled, so decoding
// does not compete with animation frames (called from the carousel's settled signal)
function _doTrackChangeWork() {
    if (audioAnalyzer && mediaManager && !useSpotify) {
        var fullPath = mediaManager.get_full_file_path(mediaManager.get_current_file())
        if (fullPath) audioAnalyzer.analyze_file(fullPath)
    }
}

// 96 bars, one Rectangle each; the Row is cached as a single texture while the
// card animation runs (layer.live is off then) to collapse 96 draw calls into one blit
Row {
    layer.enabled: true
    layer.live: !mediaRoom._cardAnimBusy
    property int numBars: audioAnalyzer ? audioAnalyzer.get_num_bars() : 96
    Repeater { model: waveformBars.numBars
        Rectangle { height: Math.max(2, (barLevel / 8) * waveformContainer.height)
                    Behavior on height { NumberAnimation { duration: 120; easing.type: Easing.InOutSine } } }
    }
}

// Levels arrive by signal and are written straight into the bars
Connections {
    target: audioAnalyzer
    enabled: waveformContainer.visible && !mediaRoom._cardAnimBusy
    function onFftDataChanged(levels) {
        for (var i = 0; i < waveformRepeater.count; i++)
            waveformRepeater.itemAt(i).barLevel = (levels && levels[i]) || 0
    }
}

// Position is polled at the visualizer frame rate while playing
Timer {
    interval: 16
    running: waveformContainer.visible && waveformContainer.isPlaying && !mediaRoom._cardAnimBusy
    repeat: true
    onTriggered: if (audioAnalyzer.is_analyzed())
                     audioAnalyzer.update_position(mediaManager.get_position() / 1000.0)
}

// Play/pause toggles emission; pausing clears the bars
function onPlayStateChanged(playing) {
    waveformContainer.isPlaying = playing
    audioAnalyzer.set_active(playing)
}

Track Changes

On a track change MediaRoom snaps every bar to zero (dropBars(), with the Behavior animations disabled while _cardAnimBusy is true so the drop is instant) and leaves the visualizer visible. The bars sit at zero until the new analysis lands and then animate up on the next data tick. An earlier version faded the whole visualizer out for the duration of the analysis, which on Android (where MediaCodec decoding is slower than desktop FFmpeg) meant several seconds of a missing visualizer that looked broken. The QML also calls initializeWaveform() whenever the container becomes visible, which re-requests the current file (a no-op if already analyzed) and syncs set_active with mediaManager.is_playing().

Performance Considerations

Analysis Time

Working at 8 kHz is the primary optimization. A 3-minute song at 44.1 kHz has about 8 million samples; at 8 kHz that is about 1.4 million, split into roughly 1800 chunks of 800-882 samples, each an O(N log N) FFT. Python decimates after decoding the full-rate stream; C++ lets the platform decoder resample, so it never holds the full-rate audio at all.

Memory Usage

A 3-minute song at 96 bars holds about 1800 × 96 = 172,800 small integers: roughly 0.7 MB as C++ std::vector<int> rows, about twice that as Python lists of object references. Only the current track's data is kept; a new analysis replaces it.

QML Rendering Impact

Each of the 96 bars is a separate Rectangle with an animated height, updated at most 10 times per second by data but re-laid out every animation frame. The Row is rendered through a cached layer (layer.enabled), which is frozen (layer.live: false) during the card animation so the 96 gradient draws collapse into one texture blit. On low-powered devices the remaining cost is the bar animations themselves; disable the visualizer with showWaveformVisualizer if a target cannot keep up.

Signal Emission Throttling

MediaRoom polls every 16 ms, but since chunks span 100 ms and update_position() only emits when the levels differ from the last emission, the visualizer receives at most 10 updates per second.

Dependencies and Graceful Degradation

The Python AudioAnalyzer needs two optional libraries, both listed in requirements.txt (numpy>=1.26.0, av>=12.0.0) and installed by python setup.py. Since commit ee5a23e they are imported lazily through backend/lazy_import.py: importing them at startup cost about 0.2 s before the first frame, so they load on the first analyze_file() instead.

from backend.lazy_import import available, lazy_module

NUMPY_AVAILABLE = available("numpy")
if not NUMPY_AVAILABLE:
    logger.warning("NumPy not available - waveform visualization will be disabled")
np = lazy_module("numpy")

AV_AVAILABLE = available("av")
if not AV_AVAILABLE:
    logger.warning("PyAV not available - waveform visualization will be disabled")
av = lazy_module("av")

If either library is missing, analyze_file() logs a warning and returns; no data is ever produced, so the bars simply stay at zero. OCTAVE therefore runs on a Python environment without NumPy or PyAV with no errors, just without the visualizer. The C++ backend has no dependency beyond Qt Multimedia, which is already linked for QMediaPlayer.

Installation: numpy and av come from requirements.txt. PyAV's binary wheels bundle their own FFmpeg libraries, so no system FFmpeg is needed.

Design Decisions

ChoiceWhy (from code comments and commit history)
Pre-compute the whole track instead of analyzing liveThe class docstring states the design: "Pre-computes FFT for entire track, then provides data based on playback position." Playback then costs one list lookup per poll regardless of device, and there is no need to tap the audio output on any platform.
No animation in the backendThe first version interpolated the bars toward target levels on its own timer inside the analyzer, which was the visualizer "eating CPU" (commit e25ea66 removed _animation_timer / _target_levels). Now update_position() emits only when the chunk's levels differ ("No intermediate animation — QML handles any smoothing it needs"), and the QML Behavior animations do the easing on the scene graph.
8 kHz, 100 ms chunks, 0-8 levelsThe code comments give the reason for the rate ("Downsample to ~8kHz for faster processing"); the spectrum is analysed up to the 4 kHz Nyquist limit in both backends, 100 ms chunks give 10 data frames per second, which the 120 ms bar animations bridge, and nine discrete integer levels make "did anything change?" a cheap list comparison so unchanged chunks emit nothing.
Analysis after the card animationMediaRoom calls analyze_file from the carousel's settled signal so decoding and the first FFT do not compete with animation frames; the bars drop to zero and stay visible meanwhile.
QAudioDecoder in C++Qt Multimedia is already linked for QMediaPlayer and supplies the native codec on every target (including MediaCodec on Android, where shipping FFmpeg would be a separate build). An earlier C++ version shelled out to an ffmpeg CLI to mirror PyAV; the decoder route removed the external binary (Android sweep, commit d751c9d) and the source comments and log lines no longer mention ffmpeg. Running the decoder inside a local QEventLoop on the worker, with a watchdog, is what makes it usable off the GUI thread.
Int16 rather than Float from the decoderSome Android MediaCodec configurations reject float sample formats; Int16 works everywhere and converting to float is one multiply per sample.
Own radix-2 FFTThe header labels the helpers "FFT helpers (no external deps)": a 1024-point transform ten times per second of audio does not justify another library across nine build targets, and zero-padding 800 samples to 1024 is the only cost.
Pending-file chaining (C++)Rapid skip presses used to drop every request after the first, leaving the visualizer on the previous track's FFT or blank; remembering only the latest request and chaining into it when the current job ends fixes that without cancelling decoders mid-flight.
Poll timer instead of callbacks (Python)A concurrent.futures callback would run on the worker thread, where Qt signals must not be emitted; a 100 ms QTimer keeps every Qt interaction on the main thread with no cross-thread signal plumbing.
One toggle, no quality tiersCommit 118f484 removed the visualizerQuality setting and its plumbing from both SettingsManagers, both analyzers (the bar count is now a constant) and the settings page, leaving only showWaveformVisualizer; the QML keeps the former top tier as constants.
Lazy NumPy / PyAV importBoth are only needed once a track is analyzed; importing them before Qt started cost ~0.2 s of cold start on the Pi (ee5a23e), and a missing library must degrade to "no visualizer", not a crash.
