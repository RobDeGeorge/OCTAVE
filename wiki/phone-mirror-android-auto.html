Overview

OCTAVE supports two methods of integrating a connected Android phone into the infotainment display:

  • Phone Mirror -- Mirrors the entire phone screen using scrcpy, providing full access to all phone apps
  • Android Auto -- Runs Google's Desktop Head Unit (DHU) to provide the standard Android Auto car experience

Both systems use the same architectural pattern: launch an external process, capture its window content, and display it within OCTAVE's QML interface via custom QQuickImageProvider subclasses. This avoids file I/O for frame transfer.

Windows
Platform Limitation
Window capture and embedding currently use Windows-specific APIs (GDI, PrintWindow, SetParent). The capture classes check platform.system() == "Windows" and emit errors on other platforms. Linux/macOS support would require alternative capture backends.

scrcpy & ADB Discovery

Both executables are discovered using a priority-based search:

  1. Bundled location -- Check tools/scrcpy/ relative to the project root (or PyInstaller _MEIPASS)
  2. System PATH -- shutil.which("scrcpy") / shutil.which("adb")
  3. Common install locations -- Platform-specific paths (e.g., C:\scrcpy\, /usr/bin/scrcpy, Android SDK paths)

Every candidate (bundled, PATH, common locations) is validated by running scrcpy --version; the parsed version is exposed as scrcpyVersion. A candidate that does not run is skipped. A version below 2.0 is still found (so the settings page can show it) but startScrcpy() refuses it with "scrcpy 1.21 at /usr/bin/scrcpy is too old (need >= 2.0)" -- distro packages are frequently that old (Ubuntu 22.04 ships 1.21, which also cannot mirror Android 14+ at all). A custom path can be set via setScrcpyPath(path).

scrcpy Process Lifecycle

Launch

The startScrcpy() slot launches scrcpy with these arguments: 

scrcpy
    --video-codec=h264
    --video-bit-rate=8M
    --max-fps=60
    --stay-awake
    --new-display=1280x800   # displaySize, if set and the phone is Android 11+ (SDK 30)
    --window-borderless      # captureMode "window" (Windows)
    --no-window --v4l2-sink=/dev/video10   # captureMode "v4l2" (Linux)
    --no-audio               # unless audio forwarding is enabled
    -s DEVICE_SERIAL         # if a specific device serial is known

Before launching, the manager checks the scrcpy version, then getDeviceState(), and emits a specific scrcpyError for each failure. It also runs adb shell pkill -f com.genymobile.scrcpy so a stale device-side server (they can outlive a crashed client) cannot conflict with the new session; the same kill runs after stopScrcpy().

scrcpy's stderr is drained line by line into the log (prefix scrcpy:, warnings for ERROR/WARN lines). Readiness depends on the capture mode:

  • window (Windows) -- a background thread polls for the scrcpy window (up to 10 s, every 100 ms) by enumerating windows and matching the process id via GetWindowThreadProcessId.
  • v4l2 (Linux) -- scrcpyStarted(pid) fires when stderr shows v4l2 sink started, or after 8 s alive as a fallback. A New display ... id N line sets displayId; if scrcpy did not print one, adb shell dumpsys display is searched for the logical display named scrcpy. If the process exits before that, scrcpyError carries scrcpy's own ERROR lines.

Virtual display (--new-display)

By default OCTAVE does not mirror the phone's own screen. It asks scrcpy to create a separate landscape 1280x800 virtual display on the phone (Android 11+), which suits a dash screen and leaves the handset usable. setDisplaySize() only snaps the dimensions to even numbers (H.264 encoders require that); the raw-BGRA reader carries an explicit stride, so any width renders correctly. A new virtual display is static from birth, so on capture start the reader sends an 8 px horizontal swipe to it (nudgeDisplay()) to make it draw a first frame immediately. Touch injection maps to the virtual display's geometry (no portrait/landscape swap) and targets it with adb shell input -d <displayId>.

Singleton Guard

The manager prevents duplicate scrcpy instances. If startScrcpy() is called while already running, it re-emits the existing window handle. An _is_starting flag prevents race conditions during the window-finding phase.

Stop

stopScrcpy() terminates the process with SIGTERM, waits 2 seconds, then falls back to SIGKILL if still running.

ScrcpyCapture & Frame Streaming

The ScrcpyCapture class in backend/phone_mirror/scrcpy_capture.py captures the scrcpy window at 60 FPS and provides frames to QML via an image provider.

Linux: v4l2 mode

On Linux there is no window to grab: scrcpy runs headless and writes decoded frames into a v4l2loopback node, and ScrcpyCapture reads that node back with an ffmpeg subprocess (ffmpeg -f v4l2 -i /dev/video10 -f rawvideo -pix_fmt bgra -), wrapping each raw frame in a QImage and pushing it into the same ScrcpyFrameProvider the Windows path uses, so frontend/PhoneMirrorView.qml is identical on both platforms. The frame size comes from the virtual display when one is active, otherwise from v4l2-ctl --get-fmt-video / ffprobe; if ffmpeg exits (format change, rotation) the reader restarts it, and gives up with a clear error after 20 s without a frame. A path that does not start with /dev/ is treated as a media file and looped, which lets developers without a phone test the view with a synthetic clip.

Two behaviours learned the hard way: Android emits no buffers for a virtual display whose content is not changing, so the continuous stream can legitimately deliver zero frames on an idle phone -- the reader therefore seeds the first frame with a one-shot ffmpeg -frames:v 1 grab that runs concurrently with the stream and never treats "no new frames" as an error. Note that a cold reader only receives a frame when the producer writes one, and a bare home screen repaints only when its status-bar clock ticks -- so the first picture can take up to a minute on an untouched phone (the seed waits 90 s). The reader therefore also nudges the virtual display with a tiny swipe so it draws at once. And both scrcpy and ffmpeg are spawned with PR_SET_PDEATHSIG on Linux (SIGTERM for scrcpy so it tears down its virtual display, SIGKILL for ffmpeg, which ignores SIGTERM while blocked in the v4l2 driver on an idle device), so they die with OCTAVE even when it is killed without running cleanup; the Python entry point additionally routes SIGTERM/SIGINT through app.quit() so aboutToQuit cleanup runs from launcher scripts.

QtMultimedia's Camera/MediaDevices is deliberately not used: Qt snapshots the V4L2 device list on first use per process and never refreshes it, and a loopback node is only visible while a producer is streaming -- so an app that touched Qt Multimedia at startup (OCTAVE does, for audio) could never see the device. Requirements learned on real hardware (Orange Pi 5 Plus, Ubuntu 22.04):

  • Load the module with exclusive_caps=0: sudo modprobe v4l2loopback exclusive_caps=0 card_label=OCTAVE video_nr=10.
  • ffmpeg (and ideally v4l-utils) installed; scrcpy 2.0 or newer (3.3+ for Android 16 phones) -- build it from source on distros that ship 1.x.

Windows: capture strategy

The scrcpy window is kept off-screen at coordinates (-3000, -3000) to hide it from the user. Its content is captured using the Windows GDI API:

  1. Hide from taskbar -- Set WS_EX_TOOLWINDOW style, remove WS_EX_APPWINDOW
  2. Position off-screen -- SetWindowPos(hwnd, 0, -3000, -3000, ...)
  3. Show (required for capture) -- ShowWindow(hwnd, SW_SHOWNOACTIVATE)
  4. Capture loop -- QTimer at 60 FPS calls _capture_frame()

Frame Capture (Windows GDI)

# Each frame:
1. GetClientRect(hwnd)          # Get window dimensions
2. GetDC(hwnd)                  # Get device context
3. CreateCompatibleDC/Bitmap    # Memory DC for capture
4. PrintWindow(hwnd, memDC,     # Capture (PW_RENDERFULLCONTENT
              PW_RENDERFULLCONTENT) #   for hardware-accelerated)
5. GetDIBits()                  # Extract BGRA pixel data
6. QImage(buffer, Format_ARGB32) # Create Qt image
7. frame_provider.update_frame() # Push to image provider
8. frameReady.emit()            # Trigger QML refresh

If PrintWindow fails (some GPU-accelerated windows), it falls back to BitBlt with SRCCOPY.

Touch Input Forwarding

Touch events from the QML display are forwarded to the phone using ADB shell input commands. This approach bypasses all window manipulation issues that arise with off-screen windows.

Coordinate Mapping

QML sends relative coordinates (0.0-1.0) which are converted to device pixel coordinates. The system handles orientation correctly: 

def _convert_to_device_coords(self, rel_x, rel_y):
    is_landscape = self._last_width > self._last_height
    if is_landscape:
        # Landscape: effective resolution is height x width
        device_x = int(rel_x * self._device_height)
        device_y = int(rel_y * self._device_width)
    else:
        # Portrait: direct mapping
        device_x = int(rel_x * self._device_width)
        device_y = int(rel_y * self._device_height)

Tap vs Swipe Detection

The sendTouchEvent slot tracks press and release positions. If the finger moved more than 5% of the screen in either axis, it is classified as a swipe; otherwise it is a tap. 

# Tap threshold: 5% of screen in either axis
if self._touch_moved and (dx > 0.05 or dy > 0.05):
    self.sendSwipe(start_x, start_y, end_x, end_y, 200)
else:
    self.sendTap(start_x, start_y)

ADB commands run in background threads to avoid blocking the UI: 

# Tap:  adb -s SERIAL shell input tap X Y
# Swipe: adb -s SERIAL shell input swipe X1 Y1 X2 Y2 DURATION_MS

EmbeddedScrcpyItem

The EmbeddedScrcpyItem in backend/phone_mirror/embedded_widget.py provides an alternative display method: directly embedding the scrcpy window as a child of the OCTAVE Qt window using SetParent. 

# Embedding steps:
1. ShowWindow(hwnd, SW_HIDE)           # Hide to prevent flicker
2. SetWindowLongW(hwnd, GWL_STYLE,     # Remove decorations,
     WS_CHILD | WS_VISIBLE)             #   make child window
3. SetWindowLongW(hwnd, GWL_EXSTYLE,   # Hide from taskbar
     WS_EX_TOOLWINDOW)
4. SetParent(hwnd, qt_window_handle)    # Reparent into OCTAVE
5. MoveWindow(hwnd, x, y, w, h, True)  # Position within layout
6. ShowWindow(hwnd, SW_SHOW)            # Show embedded

A 16ms update timer (~60 FPS) continuously repositions the embedded window to track QML layout changes. The item connects to geometry change signals (widthChanged, heightChanged, xChanged, yChanged) for immediate updates.

Detach / Reattach

When the user navigates away from the phone mirror view, detach() hides the embedded window and stops the update timer. When returning, reattach() re-embeds and shows it. This prevents the embedded window from being visible over other QML pages.

ScrcpyFrameProvider

The ScrcpyFrameProvider extends QQuickImageProvider to serve captured frames directly to QML without file I/O: 

class ScrcpyFrameProvider(QQuickImageProvider):
    def __init__(self):
        super().__init__(QQuickImageProvider.Image)
        self._current_image = None
        self._lock = threading.Lock()

    def requestImage(self, id, size, requestedSize):
        with self._lock:
            if self._current_image:
                return self._current_image
            return QImage(720, 1280, QImage.Format_RGB32)

QML accesses frames via the image://scrcpyframe/ URI scheme. A frame counter is appended to force cache invalidation on each new frame.

Google DHU Integration

Google's Desktop Head Unit (DHU) is part of the Android SDK and provides a complete Android Auto head unit implementation. OCTAVE discovers it at the standard SDK path: 

# SDK_PATH / extras / google / auto / desktop-head-unit[.exe]

# Common SDK locations checked:
Windows: %LOCALAPPDATA%\Android\Sdk
macOS:   ~/Library/Android/sdk
Linux:   ~/Android/Sdk, /opt/android-sdk

DHU Configuration

Before launching, a config file is written to ~/.android/headunit.ini: 

[general]
resolution = 1920 1080
dpi = 160

ADB Connection Setup

The _prepare_adb_connection() method handles the full ADB setup sequence:

  1. Check device -- Run adb devices and verify at least one device is connected and not offline.
  2. Port forwarding -- Remove existing forwards with adb forward --remove-all, then set up adb forward tcp:5277 tcp:5277 (the DHU communication port).
  3. Head unit server -- Check if the head unit server is running on the phone via dumpsys activity services. If not running, attempt to start it via:
    • am start -n com.google.android.projection.gearhead/.companion.MainActivity
    • Fallback: am startservice -n ...DeveloperHeadUnitNetworkService
    If neither works, wait up to 60 seconds for the user to manually start it.

DhuCapture & Frame Provider

The DhuCapture class in backend/android_auto/dhu_capture.py captures the DHU window at 30 FPS using the same Windows GDI approach as ScrcpyCapture, with PrintWindow(hwnd, memDC, PW_CLIENTONLY).

DhuFrameProvider

The DhuFrameProvider extends QQuickImageProvider identically to ScrcpyFrameProvider. It returns a default 800x480 placeholder when no frame is available. QML accesses frames via the image://dhuframe/ URI scheme.

DHU Window Hiding

The DHU is launched minimized (SW_MINIMIZE via STARTUPINFO). An aggressive poll loop (every 100ms, up to 5 seconds) finds the window by title ("Desktop Head Unit" or "Android Auto") and immediately: 

# 1. Make it a tool window (hide from taskbar)
SetWindowLongW(hwnd, GWL_EXSTYLE, old_style | WS_EX_TOOLWINDOW)

# 2. Move off-screen
SetWindowPos(hwnd, 0, -3000, -3000, ...)

# 3. Restore from minimized (needed for PrintWindow)
ShowWindow(hwnd, SW_RESTORE)

# 4. Ensure it stays off-screen after restore
SetWindowPos(hwnd, 0, -3000, -3000, ...)

Touch Input Forwarding

DHU click forwarding is more complex than phone mirror because the DHU window expects direct mouse clicks (not ADB shell input). The sendMouseClick method:

  1. Save state -- Capture current cursor position and foreground window
  2. Scale coordinates -- Map from QML's 1920x1080 coordinate space to the actual DHU client area dimensions
  3. Make nearly invisible -- Set WS_EX_LAYERED with alpha=1 (nearly transparent)
  4. Move on-screen -- Position at screen edge (needed for real mouse clicks)
  5. Activate and click -- SetForegroundWindow, convert to screen coords, SetCursorPos, mouse_event
  6. Restore -- Set alpha back to 255, move off-screen, restore cursor and foreground window
Why Real Clicks?
Unlike scrcpy (which uses ADB), the DHU expects standard Windows mouse input. SendMessage-based clicks (WM_LBUTTONDOWN/WM_LBUTTONUP) are available via sendMouseEvent() as an alternative for simpler cases.

EmbeddedDhuItem

The EmbeddedDhuItem in backend/android_auto/embedded_dhu.py mirrors the EmbeddedScrcpyItem pattern -- it embeds the DHU window as a child of the OCTAVE Qt window. The embedding removes decorations (caption, border, system menu, minimize/maximize boxes) and continuously repositions at ~60 FPS.

It connects to the AndroidAutoManager via connectToManager() and listens for dhuWindowReady and dhuEmbeddedChanged signals. Detach/reattach behavior is identical to the phone mirror embedded widget.

Image Providers

Both frame providers are registered on the QML engine in main.py:

ProviderURI SchemeClassDefault SizeFPS
Phone Mirror image://scrcpyframe/ ScrcpyFrameProvider 720x1280 (portrait) 60
Android Auto image://dhuframe/ DhuFrameProvider 800x480 (landscape) 30

Both providers use a thread-safe lock to protect the current frame image, since the capture timer runs on the main thread while QML's image loading may happen on a render thread.

QML Usage Pattern

// In QML, refresh the image by changing the source URL
Image {
    source: "image://scrcpyframe/" + captureItem.frameCounter
    cache: false
}
