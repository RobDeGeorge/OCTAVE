Overview

OCTAVE supports two methods of integrating a connected Android phone into the infotainment display:

  • Phone Mirror -- Mirrors the phone (or a virtual display on it) with OCTAVE's built-in scrcpy-protocol client -- nothing to install, real multitouch
  • Android Auto -- Runs Google's Desktop Head Unit (DHU) to provide the standard Android Auto car experience

Both systems use the same architectural pattern: launch an external process, capture its window content, and display it within OCTAVE's QML interface via custom QQuickImageProvider subclasses. This avoids file I/O for frame transfer.

Windows
Platform Limitation
Window capture and embedding currently use Windows-specific APIs (GDI, PrintWindow, SetParent). The capture classes check platform.system() == "Windows" and emit errors on other platforms. Linux/macOS support would require alternative capture backends.

Phone Mirror

Phone Mirror shows an Android phone inside OCTAVE and lets the user drive it from the dash with real multitouch. OCTAVE is its own scrcpy-protocol client: it pushes the bundled phone server jar (tools/phone-server/octave-phone-server) to the phone with adb, starts it, decodes the H.264 stream itself and injects input over the control socket. The server is OCTAVE's fork of the scrcpy server (phone_server/, Apache-2.0, forked at v3.3.4, Java package org.octave.phoneserver, version 3.3.4-octave); it needs shell privileges, which only an adb-launched process gets, so it cannot be an installed app. The phone-server CI job rebuilds the jar from source on every push and fails if the committed jar differs. Nothing has to be installed by the user: adb is shipped next to the binary (scripts/fetch_platform_tools.py; on ARM boards the distro's adb on PATH is used), the decoder is PyAV in the Python backend and libavcodec in C++. There is no scrcpy binary, no v4l2loopback, no ffmpeg subprocess and no adb shell input any more.

ScrcpyClient: session and protocol

  1. Push the server jar to /data/local/tmp/octave-phone-server.jar (every session: the server deletes it on exit).
  2. Tunnel: remove any stale localabstract:scrcpy_* forward for the device (a hard-killed OCTAVE leaves one in the adb server), then adb forward tcp:PORT localabstract:scrcpy_SCID with a random 31-bit scid.
  3. Start app_process … org.octave.phoneserver.Server 3.3.4-octave scid=… tunnel_forward=true video=true audio=false control=true video_codec=h264 max_fps=60 stay_awake=true cleanup=true send_device_meta=true send_frame_meta=true send_codec_meta=true send_dummy_byte=true [new_display=WxH]. On Linux the child gets PR_SET_PDEATHSIG so it dies with OCTAVE.
  4. Connect: the tunnel accepts before the server listens, so connect until the dummy byte arrives (video socket), then open the control socket. The server sends device/codec meta only once every socket is connected -- reading before opening control deadlocks.
  5. Meta: 64-byte device name, then codec id (u32) + width + height (u32 each, big-endian).
  6. Frames: [u64 pts|flags][u32 size][data]; bit 63 = config packet (SPS/PPS, prepended to the next packet), bit 62 = key frame. Decoded YUV420P planes are copied into a QVideoFrame and handed to the sink on the GUI thread, coalescing if it falls behind.
  7. Audio (setting scrcpyAudioEnabled): a third socket, connected between video and control, carries a 4-byte codec id ("raw" = PCM s16le 48 kHz stereo, requested with audio_codec=raw so no decoder is needed; 0 = the phone could not capture, video continues) followed by the same [pts][size][data] packets. Chunks are queued (bounded to ~250 ms, oldest dropped) and written to a QAudioSink on the GUI thread with a ~200 ms device buffer; the sink volume is OCTAVE's linear volume, so the knob and mute apply. Phones capture at their own media level, typically well under loudness-mastered local music, so a gain (setting scrcpyAudioGain, default +6 dB, soft-limited with tanh) is applied to the PCM inside OCTAVE; the phone's own volume is deliberately never changed (a crash could leave it at maximum). The default capture source is the phone's remote submix, which captures every app (playback is muted on the handset itself). Expect lip-sync to trail the picture slightly.
  8. Control: 32-byte INJECT_TOUCH_EVENT (type 2) with pointer id, x/y in frame pixels, screen size, pressure; 14-byte INJECT_KEYCODE (type 0). Coordinates are relative to the mirrored display, so a virtual display needs no display-id routing.
  9. Teardown: close sockets, terminate the child, remove the forward. The server destroys the virtual display itself (cleanup=true). The Python entry point routes SIGTERM/SIGINT through app.quit() and the C++ one installs a self-pipe signal handler, so launcher scripts get a clean exit too.

Byte layouts were verified against the scrcpy v3.3.4 source. Changing the server is a deliberate step: edit phone_server/src, rebuild the jar (BUILD.md), bump SCRCPY_VERSION_NAME and both clients' SERVER_VERSION together, and re-check the message layouts in DesktopConnection, ControlMessageReader and Streamer.

Touch and navigation

PhoneMirrorView.qml uses a MultiPointTouchArea (mouse arrives as one point) and forwards every point's down/move/up through injectTouch(), mapped through VideoOutput.contentRect so letterboxing is accounted for. Tap, drag, scroll and long-press are verified on hardware; multi-finger gestures are implemented but untested (the test rig has no touchscreen). Back / Home / Recents buttons sit at the bottom of the view because a virtual display has no reachable gesture nav bar.

Errors and recovery

A missing prerequisite is reported with getInstallInstructions() naming it. Phone-side failures (unplugged, offline, USB debugging not authorized) get a one-line message and the view polls getDeviceState() every 2 s while it is open, restarting on its own when the phone is back -- a nudged cable in a vehicle is the normal case. A cable pull mid-session surfaces as "Phone disconnected. Reconnect the USB cable.".

Why not QtMultimedia's Camera? An earlier design streamed scrcpy into a v4l2loopback node and read it with QCamera. Qt snapshots the V4L2 device list on first use per process and never refreshes it, the loopback only appears while a producer streams, and Qt's V4L2 path sheared frames whose width was not a multiple of 64 -- all irrelevant now, but the reasons the built-in client exists.

Google DHU Integration

Google's Desktop Head Unit (DHU) is part of the Android SDK and provides a complete Android Auto head unit implementation. OCTAVE discovers it at the standard SDK path: 

# SDK_PATH / extras / google / auto / desktop-head-unit[.exe]

# Common SDK locations checked:
Windows: %LOCALAPPDATA%\Android\Sdk
macOS:   ~/Library/Android/sdk
Linux:   ~/Android/Sdk, /opt/android-sdk

DHU Configuration

Before launching, a config file is written to ~/.android/headunit.ini: 

[general]
resolution = 1920 1080
dpi = 160

ADB Connection Setup

The _prepare_adb_connection() method handles the full ADB setup sequence:

  1. Check device -- Run adb devices and verify at least one device is connected and not offline.
  2. Port forwarding -- Remove existing forwards with adb forward --remove-all, then set up adb forward tcp:5277 tcp:5277 (the DHU communication port).
  3. Head unit server -- Check if the head unit server is running on the phone via dumpsys activity services. If not running, attempt to start it via:
    • am start -n com.google.android.projection.gearhead/.companion.MainActivity
    • Fallback: am startservice -n ...DeveloperHeadUnitNetworkService
    If neither works, wait up to 60 seconds for the user to manually start it.

DhuCapture & Frame Provider

The DhuCapture class in backend/android_auto/dhu_capture.py captures the DHU window at 30 FPS using the same Windows GDI approach as the former phone-mirror screen grab, with PrintWindow(hwnd, memDC, PW_CLIENTONLY).

DhuFrameProvider

The DhuFrameProvider extends QQuickImageProvider identically to ScrcpyFrameProvider. It returns a default 800x480 placeholder when no frame is available. QML accesses frames via the image://dhuframe/ URI scheme.

DHU Window Hiding

The DHU is launched minimized (SW_MINIMIZE via STARTUPINFO). An aggressive poll loop (every 100ms, up to 5 seconds) finds the window by title ("Desktop Head Unit" or "Android Auto") and immediately: 

# 1. Make it a tool window (hide from taskbar)
SetWindowLongW(hwnd, GWL_EXSTYLE, old_style | WS_EX_TOOLWINDOW)

# 2. Move off-screen
SetWindowPos(hwnd, 0, -3000, -3000, ...)

# 3. Restore from minimized (needed for PrintWindow)
ShowWindow(hwnd, SW_RESTORE)

# 4. Ensure it stays off-screen after restore
SetWindowPos(hwnd, 0, -3000, -3000, ...)

Touch Input Forwarding

DHU click forwarding is more complex than phone mirror because the DHU window expects direct mouse clicks (not ADB shell input). The sendMouseClick method:

  1. Save state -- Capture current cursor position and foreground window
  2. Scale coordinates -- Map from QML's 1920x1080 coordinate space to the actual DHU client area dimensions
  3. Make nearly invisible -- Set WS_EX_LAYERED with alpha=1 (nearly transparent)
  4. Move on-screen -- Position at screen edge (needed for real mouse clicks)
  5. Activate and click -- SetForegroundWindow, convert to screen coords, SetCursorPos, mouse_event
  6. Restore -- Set alpha back to 255, move off-screen, restore cursor and foreground window
Why Real Clicks?
Unlike scrcpy (which uses ADB), the DHU expects standard Windows mouse input. SendMessage-based clicks (WM_LBUTTONDOWN/WM_LBUTTONUP) are available via sendMouseEvent() as an alternative for simpler cases.

EmbeddedDhuItem

The EmbeddedDhuItem in backend/android_auto/embedded_dhu.py embeds the DHU window as a child of the OCTAVE Qt window. The embedding removes decorations (caption, border, system menu, minimize/maximize boxes) and continuously repositions at ~60 FPS.

It connects to the AndroidAutoManager via connectToManager() and listens for dhuWindowReady and dhuEmbeddedChanged signals. Detach/reattach behavior is identical to the phone mirror embedded widget.

Custom QML Types

Both systems register custom QML types via qmlRegisterType in main.py: 

# Phone Mirror

# Android Auto
qmlRegisterType(EmbeddedDhuItem,    "OCTAVE.AndroidAuto", 1, 0, "EmbeddedDhuItem")

QML imports these as: 

import OCTAVE.PhoneMirror 1.0
import OCTAVE.AndroidAuto 1.0

Image Providers

Both frame providers are registered on the QML engine in main.py:

ProviderURI SchemeClassDefault SizeFPS
Android Auto image://dhuframe/ DhuFrameProvider 800x480 (landscape) 30

Both providers use a thread-safe lock to protect the current frame image, since the capture timer runs on the main thread while QML's image loading may happen on a render thread.

QML Usage Pattern

// In QML, refresh the image by changing the source URL

    source: "image://dhuframe/" + frameCounter
    cache: false
