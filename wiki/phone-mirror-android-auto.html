Overview

OCTAVE has two ways of putting a connected Android phone on the dash:

  • Phone Mirror -- OCTAVE is its own scrcpy-protocol client. It pushes OCTAVE's forked scrcpy server to the phone over adb, decodes the H.264 stream itself, plays the phone's audio, and injects real multitouch over the control socket. Nothing has to be installed by the user. Both backends implement it in full; it is desktop-only (the Android build registers a stub).
  • Android Auto -- Runs Google's Desktop Head Unit (DHU) as a separate process and embeds its window. In practice this works only with the Python backend on Windows; see What actually works.

The two paths share nothing but adb. Phone Mirror pushes decoded frames into a QVideoSink bound to a QML VideoOutput; Android Auto embeds a native window (Python/Windows) and additionally registers a QQuickImageProvider (image://dhuframe/) that no QML currently reads.

Phone Mirror

Phone Mirror shows an Android phone inside OCTAVE and lets the user drive it from the dash with real multitouch. OCTAVE is a scrcpy-protocol client: it pushes the bundled phone server jar (tools/phone-server/octave-phone-server) to /data/local/tmp/octave-phone-server.jar with adb, starts it with app_process, decodes the H.264 stream and injects input over the control socket. The server is OCTAVE's fork of the scrcpy server (phone_server/, Apache-2.0, forked at v3.3.4, Java package org.octave.phoneserver, version string 3.3.4-octave). It needs shell privileges, which only an adb-launched process gets, so it cannot be an installed app. There is no scrcpy binary, no v4l2loopback, no ffmpeg subprocess and no adb shell input anywhere in the path (all removed in commit 7a8c8b8).

Numbers and history: docs/PHONE_MIRROR_NATIVE_PLAN.md.

PhoneMirrorManager

Owns the single session (one phone at a time), the adb probes the UI needs, and the settings that shape a session. Identical public surface in both backends; the mobile C++ build compiles a stub with the same members that reports nativeAvailable = false and "Phone mirroring is desktop-only".

Session lifecycle

Everything below runs on the client's worker thread (C++ std::thread named scrcpy-client; Python daemon thread of the same name). The sequence and the launch arguments are identical in both backends.

  1. Preflight (manager, GUI thread): nativeAvailable, then getDeviceState() must be "device", then the serial. C++ additionally extracts the embedded jar to <temp>/octave-phone-server-3.3.4-octave (reused when the size matches). Unless attaching to a persisted session, a stale server is killed first: adb shell pkill -f org.octave.phoneserver.
  2. Push the jar to /data/local/tmp/octave-phone-server.jar -- every session, because cleanup=true starts a CleanUp helper that unlinks the pushed jar as soon as the server is up.
  3. Tunnel: pick a random 31-bit scid (C++ QRandomGenerator::system(), Python secrets.randbits(31) -- not the global random module, which other modules seed and which once made every session's scid identical), formatted as 8 hex digits. Reap stale forwards first (adb forward --list, remove every localabstract:scrcpy_* entry for this serial -- forwards live in the adb server, so a hard-killed OCTAVE strands one listening port per session), then adb forward tcp:PORT localabstract:scrcpy_SCID with an ephemeral local port (OCTAVE_SCRCPY_PORT overrides it for the fake-server tests; C++ falls back to 27183 if the probe listen fails).
  4. Launch: 
    adb -s SERIAL shell "CLASSPATH=/data/local/tmp/octave-phone-server.jar nohup app_process / org.octave.phoneserver.Server 3.3.4-octave \
  scid=SCID tunnel_forward=true video=true audio=true|false control=true clipboard_autosync=false \
  video_codec=h264 audio_codec=raw max_size=0 video_bit_rate=8000000 max_fps=60 stay_awake=true cleanup=true \
  send_device_meta=true send_frame_meta=true send_codec_meta=true send_dummy_byte=true log_level=info \
  octave_persist_ms=60000|0 [new_display=WxH] 2>&1 & wait"
    The CLASSPATH= assignment must come before nohup (an assignment after it is exec'd as a literal command; commit bba3de6). nohup ... & wait keeps the adb shell relaying stdout for as long as the server lives, while the server survives adbd killing that shell on a USB dropout (it is reparented to init). octave_persist_ms is 60000 for a virtual-display session and 0 (exit like scrcpy) when mirroring the phone screen. On Linux the adb child gets PR_SET_PDEATHSIG=SIGTERM (C++ setChildProcessModifier, Python preexec_fn) so it dies with OCTAVE. The child's merged stdout/stderr is the server log; a New display: ... (id=N) line yields the virtual display id used by pressHome().
  5. Connect: with tunnel_forward the local TCP connect succeeds before the server listens and then EOFs, so connect every 100 ms until the dummy byte actually arrives; that socket is the video socket. Deadline 20 s from the click (4 s when attaching); if the server process exits meanwhile the failure is "scrcpy server exited during startup (see log)". Then open the audio socket (only if audio is on) and the control socket (both with TCP_NODELAY). The server sends device and codec meta only once every socket it expects is connected (DesktopConnection.open accepts them in order), so reading before opening control would deadlock. A connection that received no dummy byte is closed, otherwise the server would later hand it out as the audio or control socket.
  6. Handshake on the video socket: 64-byte NUL-padded device name, then codec id (u32 FourCC h264), width and height (u32 each, big-endian). frameSizeChanged and connected fire; the manager emits scrcpyStarted(1) and, 500 ms later, sends the keeper policy (the server powers the device on asynchronously at start).
  7. Stream: the worker thread demuxes and decodes video until stop or EOF; a scrcpy-devmsg thread reads device messages on the control socket; a scrcpy-audio thread reads PCM. Control messages are written to the control socket from any thread under a send mutex (C++ writes the raw descriptor with ::send()).
  8. Teardown: close the sockets, terminate the adb child (2 s, then kill), adb forward --remove tcp:PORT (also repeated from stop() so a clean exit never strands a port). The server destroys the virtual display itself (cleanup=true) unless it is persisting. A stream that ends without a requested stop surfaces as "Phone disconnected. Reconnect the USB cable.". Both entry points route SIGTERM/SIGINT through the normal quit path (Python signal.signal(..., app.quit); C++ a self-pipe socketpair handler) so launcher scripts and systemd get this cleanup too.

Video decode and frame delivery

A config packet (SPS/PPS) is not decoded on its own; it is prepended to the next packet, as the scrcpy client does. C++ decodes with libavcodec (avcodec_find_decoder(AV_CODEC_ID_H264), FF_THREAD_SLICE | FF_THREAD_FRAME, packets padded with AV_INPUT_BUFFER_PADDING_SIZE); Python with PyAV (av.CodecContext.create("h264", "r"), thread_type = "AUTO"). Both produce YUV420P (Python reformats if the decoder returns anything else; C++ accepts YUV420P/YUVJ420P and drops other formats) and copy the three planes row by row into a QVideoFrame(Format_YUV420P) -- no RGB conversion, the GPU does the colour conversion in VideoOutput. The frame is stored as "latest" under a mutex and frameReady is emitted; a queued slot on the GUI thread pulls the latest frame and calls QVideoSink::setVideoFrame(), so a slow GUI thread coalesces rather than queues frames. Neither client ever clears the sink: the last frame stays on the VideoOutput across a reconnect.

Why libavcodec and not QMediaPlayer::setSourceDevice(): Qt's FFmpeg backend refuses a raw Annex-B QIODevice (FormatError "Could not open file" after 1.5 MB fed, Phase 0 spike). C++ therefore links libavcodec/libavutil when CMake finds them (OCTAVE_HAVE_FFMPEG, pkg-config on Linux/macOS, vcpkg on Windows; without them the build still succeeds and nativeAvailable is false); Python gets it for free because av is already in requirements.txt. Software H.264 at 1280x800 costs 12–15 % of one RK3588 core.

Black-frame holding

A dozing phone streams pure black frames (status bar still drawn) until it is woken, and the first composite of a reattached stream is black plus a strip of status icons. Rather than flash the dash black, both clients decide per decoded frame whether to hand it to the sink:

  • Test: maximum luma over every other pixel in both directions of the Y plane (stride 2), early exit on the first sample above 20. Point grids (8x8, then 24x24) were tried first and missed a 2 px icon stroke, so a dark app with small bright UI was held as if the phone were dozing (commit 7090531). ~256k byte reads on 1280x800, under 1 ms. Frames narrower or shorter than 24 px are never "black". Python uses numpy (y[::2, :w:2].max()); without numpy it falls back to a 24x24 point grid.
  • Lenient mode (attached stream, first 3 s of decode): the frame is black if fewer than 5 % of samples are bright -- a solid status strip is 3–4 % of samples (commit cfc1d4c). Normal viewing keeps the strict test so a dark app with a bright toolbar is never held.
  • Hold rules: while the keeper reports the phone asleep, every frame is held (the doze fade is a uniformly dimmed composite, neither black nor content; commit 525882f). Otherwise a run of black frames is held for 3 s (kBlackHoldMs / BLACK_HOLD_S); a black run that outlives that is real content and is shown. The very first frame of a fresh session is always shown (the test only applies once a frame has been delivered, or when attached).

Audio and ducking

With setting scrcpyAudioEnabled the server is started with audio=true audio_codec=raw; the server's default source is AudioSource.OUTPUT, i.e. REMOTE_SUBMIX, which captures every app and mutes playback on the handset. Raw PCM means no decoder on our side. The audio socket is read on its own thread (scrcpy-audio) so video never waits on it:

  1. Each chunk's peak before gain is measured; a peak of 164 or more (about −46 dBFS; a silent remote submix is exact zeros, so this only rejects dither) flags "sound seen".
  2. Gain (setting scrcpyAudioGain, default 2.0 = +6 dB, clamped 0.25..8) multiplies the samples through a tanh soft limiter so a hot source cannot clip harshly. Phones capture at their own media level, measured ~10 dB under local music on the Pi; the phone's own volume is deliberately never touched (an earlier attempt used adb shell media volume, which does not exist on the test handset and would leave the phone at maximum after a crash; commit 19c3b10).
  3. Chunks are queued with a cap of 48000 bytes (~250 ms); when the GUI thread falls behind the oldest are dropped so audio stays close to the picture. audioReady wakes a queued slot on the GUI thread.
  4. On the GUI thread a QAudioSink (48 kHz, stereo, Int16, default output device, ~200 ms device buffer) is created lazily; chunks are written only while bytesFree() allows, never blocking. setVolume() from VolumeController sets the sink volume, so the knob and mute apply. If the default device is missing or refuses the format, a warning is logged and audio is silently skipped.
  5. The same GUI slot turns "sound seen" into audioPlaying = true and (re)arms a single-shot 1.5 s release timer; silence longer than that drops it. Long enough to bridge the gaps between navigation sentences, short enough that music comes back promptly after a prompt.

Ducking (settings scrcpyAudioDuckEnabled, default on; scrcpyAudioDuckLevel, default 0.1 = −20 dB): the manager computes duckingFactor = duckLevel while audioPlaying && duckEnabled, else 1.0, and emits duckingChanged on change. main.cpp / main.py connect it to MediaManager.setDucking(), which ramps the local output (80 ms attack, 500 ms release) independently of the user's volume and mute. Spotify is deliberately not ducked: it plays on its own Spotify Connect device, usually the very phone being mirrored, so its sound already arrives through the mirror stream. Expect lip-sync to trail the picture slightly. Validated on the Pi by measurement (+6 dB = x1.89 RMS, live slider, clean teardown with zero underruns); whether −20 dB is enough against a loudness-mastered MP3 in the car is still an open question in the plan doc.

Phone screen, sleep and the MirrorKeeper

Measured on the S22 Ultra / Android 16: the virtual display requests VIRTUAL_DISPLAY_FLAG_OWN_DISPLAY_GROUP but lands in power group 0, so a power press dozes it with the phone -- app content stops compositing (black frames) and injected touch is silently dropped, with nothing on the wire to notice. The only way to keep mirroring is to wake the phone again. Doing that from the dash (an adb poll every second, then a keyevent) left ~1 s of black and a visible panel relight, so the logic moved into the phone: phone_server/.../control/MirrorKeeper.java (commit 67809d1). OCTAVE only sets the policy, can take the phone back, and shows the state; it no longer runs adb while a session is up.

Policy: OCTAVE_SET_KEEPER(enabled=1, panelDark=scrcpyPhoneScreenOff, graceMs=8000), sent 500 ms after the handshake and again whenever the setting changes (the server's own default grace is 5000 ms if a client never sets one). The keeper is a process-wide singleton on the phone: Controller attaches it on the first OCTAVE_SET_KEEPER, swaps the message sender per client session, and its in-use / panel state survives a reconnect.

Sensing: a DisplayListener on display 0 plus a 250 ms poll on its own HandlerThread, reading PowerManager.isScreenOn(0) (interactive) and IWindowManager.isKeyguardLocked() through the server's wrappers. The panel is blanked or lit with Device.setDisplayPower(0, on) (SurfaceControl power mode -- the phone stays awake, stream and touch keep working) and CleanUp is told to restore it when the server process ends. Waking uses KEYCODE_WAKEUP (224, wakes and never toggles off), rate-limited to one per 500 ms.

Decisions (what a power press meant):

  • Start: an awake, unlocked phone is in the user's hand (in use); an awake, locked one is in the cradle and gets the panel policy; an asleep one is woken.
  • Press while locked (phone in the cradle): wake it, then force the panel on once interactive (the wake alone does not reliably relight a SurfaceControl-dark panel; commit 2cdd28e) and leave it lit for the 8 s grace window. If the keyguard is dismissed in that window (or at any time), or the phone turns out to be unlocked already (a lock-after delay had not run), or the button is pressed again within grace + 2 s (nothing visible happened for them the first time, so they are trying to get in), the phone is in use: panel on, locks not undone. If the grace passes still locked, the press meant "screen off" and the panel is blanked.
  • In use: the mirror keeps working (DeX on the virtual display is independent of the panel). It ends when the keyguard re-engages (lock shortcut or lock-after delay: grace, then blank) or on OCTAVE_TAKE_BACK.
  • Press while in use: the user is putting the phone down -- no grace, the panel-off goes out before the wake and again the instant the phone is interactive, so it never relights.
  • In-use is edge-triggered on the keyguard transition (locked → unlocked enters, unlocked → locked leaves); a level check raced Samsung's 5 s lock-after delay and undid resumeMirroring() on the next poll (commit e1fa1c4).

Every change is reported as PHONE_STATE(asleep, inUse, panelDark). Both managers map it to phoneAsleep / phoneInUse, tell the client to hold every frame while asleep, and reset both on disconnect. PhoneMirrorView dims the held frame with a "Phone is asleep -- Waking it up... tap to retry" overlay only if the phone is still asleep after 1.5 s; a normal press resolves in about a second and dimming the dash for that read as a flash (commit a4aa9a6). Tapping the overlay calls wakePhone().

Lock-after delay
Phones with a lock-after-screen-off delay (Samsung default 5 s) stay unlocked for that long after a power press, so a wake inside it shows no keyguard and no unlock edge; the keeper treats "woke to an unlocked phone" as in use. Setting lock-after to "Immediately" gives the crispest behaviour.

Persistent sessions and USB drops

The phone re-enumerates on the bus now and then (picked up, put down, a nudged cable). adbd then kills the server's shell; with the stock scrcpy design the server exits, the virtual display goes with it (VIRTUAL_DISPLAY_FLAG_DESTROY_CONTENT_ON_REMOVAL) and the user lands on a fresh DeX home screen. Two layers keep what they had open (commit 2992d67):

Server (option octave_persist_ms): Server.scrcpy runs a session loop on a sessions thread while the main looper serves handlers for the whole process. One NewDisplayCapture marked persistent is shared across sessions -- its release() only detaches the encoder surface (virtualDisplay.setSurface(null)), the real destroy() runs at process exit. Each client connection gets a fresh Controller, encoder and streamer and re-sends device meta. After a client drops, DesktopConnection.open(..., acceptTimeoutMs) re-listens on the same localabstract:scrcpy_<scid> for up to octave_persist_ms; because closing a LocalServerSocket does not reliably unblock accept() on Android, a watchdog thread sets a flag and pokes the socket with a connection of its own (commit 0a26f8e). No reconnect within the window: "No client reconnected within N ms; exiting", the display is destroyed and MirrorKeeper.shutdown() runs.

Client: on a mid-stream disconnect of a ready virtual-display session the manager remembers the scid and a deadline of now + 60 s − 5 s. The next startScrcpy() inside that window attaches: no push, no pkill, re-forward the same scid, connect with a 4 s deadline, and follow the server log with adb logcat -v raw -T 1 -s scrcpy:I (its stdout went with the old shell). The reattached stream uses the lenient black test for its first 3 s so the handover never shows black. If the attach fails, the manager starts fresh on the next event-loop turn (which kills the old server). A deliberate stopScrcpy() always kills the server.

View: PhoneMirrorView treats a device error that arrives mid-stream (regex /disconnected|No Android device|not authorized|offline/i, while a frame has been shown) as a quiet reconnect: the last frame stays up, the view polls getDeviceState() every second and restarts the moment it is "device" again (typically 2 s), shows a "Reconnecting to phone..." badge only after 2 s, and falls back to the error page after 10 s. Because the keeper is process-wide, in-use / panel state survives the reconnect too.

Touch and navigation

PhoneMirrorView.qml uses a MultiPointTouchArea (mouseEnabled, 1–10 points; mouse arrives as one point) and forwards every point's pressed/updated/released (and canceled, as a release) through injectTouch(pointId, action, relX, relY), mapped through VideoOutput.contentRect so letterboxing is accounted for and clamped to 0..1. Tap, drag, scroll and long-press are verified on hardware; multi-finger gestures are implemented but untested (the test rig has no touchscreen).

Navigation row (◁ ○ ▢ → pressBack / pressHome / pressAppSwitch) sits on the bottom edge of the picture (not the letterbox band, where a translucent button on black is invisible) and is shown only when mirroring the phone's own screen: a virtual display draws system decorations, i.e. Samsung's DeX taskbar with its own back/home/recents exactly where the row would sit. HOME and APP_SWITCH are system keys that Android routes to the default display, so injecting them does nothing on a virtual one (Back is dispatched to the focused window and works); pressHome() therefore runs adb shell am start --display <id> -a android.intent.action.MAIN -c android.intent.category.HOME when a virtual display id is known (C++ via an async QProcess, Python on a one-shot thread) and falls back to the keycode otherwise. Samsung's recents UI renders empty on a secondary display.

Errors and recovery

A missing prerequisite is reported with getInstallInstructions() naming it and the view shows a "Setup" block. Phone-side failures (unplugged, offline, USB debugging not authorized) get the one-line describeDeviceState() text; the error page then polls getDeviceState() every 2 s while it is on screen and restarts on its own when the phone is back -- a nudged cable in a vehicle is the normal case. The bottom-bar button pops back to an existing PhoneMirrorView (found by objectName) instead of stacking a second one, and the view resumes a session that is already running.

Why not QtMultimedia's Camera? The design before the built-in client streamed scrcpy into a v4l2loopback node and read it with QCamera. Qt snapshots the V4L2 device list on first use per process and never refreshes it, the loopback only appears while a producer streams, and Qt's V4L2 path sheared frames whose width was not a multiple of 64. That knowledge still applies to camera enumeration; the path itself is gone.

The phone server fork and the version invariant

phone_server/ is scrcpy's server/ tree at v3.3.4 with the package renamed to org.octave.phoneserver (LICENSE and NOTICE kept, phone_server/LICENSE.scrcpy). OCTAVE's additions are marked with // OCTAVE comments: control/MirrorKeeper.java, the TYPE_OCTAVE_* control and device messages, Options.octavePersistMs, the session loop in Server.scrcpy, DesktopConnection.open(..., acceptTimeoutMs), NewDisplayCapture.setPersistent()/destroy(), and the WindowManager.isKeyguardLocked wrapper.

Build: phone_server/build_without_gradle.sh (upstream's no-Gradle script) generates BuildConfig.VERSION_NAME = "3.3.4-octave" from SCRCPY_VERSION_NAME, compiles against platforms;android-36 / build-tools;36.0.0 and produces octave-phone-server (a jar of classes.dex, ~96 KB). The result is committed at tools/phone-server/octave-phone-server; the C++ binary embeds it as the Qt resource :/phone-server/octave-phone-server (CMake qt_add_resources) so no packaging target carries a loose file; Python reads it from the checkout.

Version invariant: Options.parse throws "The server version (3.3.4-octave) does not match the client (...)" unless the first argument equals BuildConfig.VERSION_NAME. So SCRCPY_VERSION_NAME in the build script, kServerVersion in scrcpyclient.h and SERVER_VERSION in scrcpy_client.py must be bumped together. The CI job phone-server rebuilds the jar under JDK 21 on every push and errors if either the fresh or the committed jar lacks the org/octave/phoneserver/Server class or the 3.3.4-octave string; a byte-level difference between the two is reported as a warning only (javac/d8 output can differ across toolchains). Changing the server is a deliberate step: edit phone_server/src, rebuild, commit the jar with the source, bump the version in all three places if the protocol changed, and re-verify the byte layouts above against DesktopConnection, ControlMessageReader, DeviceMessageWriter and Streamer.

Bundled adb: scripts/fetch_platform_tools.py downloads Google's platform-tools 37.0.1 (SHA-256 verified), keeps only what adb needs plus Google's NOTICE under tools/platform-tools/<linux|windows|darwin>/ (gitignored). The Windows, macOS and Linux x86_64 CI jobs run it and ship the result next to the binary (platform-tools/ beside the executable, Contents/Resources/platform-tools in the .app, usr/bin/platform-tools in the AppImage). Google publishes x86_64 only, so the aarch64 AppImage and ARM boards fall back to the distro's adb on PATH.

Design decisions

Grounded in the code comments, commit messages and docs/PHONE_MIRROR_NATIVE_PLAN.md.

Why a built-in client instead of the scrcpy binary

The first working path (commit 0f9ecaa) chained the scrcpy desktop binary, a v4l2loopback kernel module, an ffmpeg subprocess reading the loopback node, adb shell input for touch, and on Windows a GDI window grab. Every link was an install step or a failure mode on someone else's box: distro scrcpy versions are years old (Ubuntu 22.04's 1.21 cannot mirror Android 14+), v4l2loopback needs DKMS and boot parameters and is Linux-only, the loopback starves on a static display so first paint took 4–60 s, adb shell input costs ~130 ms per event with no multitouch, long-press, drag or pinch, and the window grab kept a hidden scrcpy window alive. The scrcpy server is the part that is hard to replace and does not need replacing (it creates the virtual display, captures without a consent dialog, encodes on the phone's hardware encoder and injects input); the desktop client is what OCTAVE replaced with code of its own inside each backend. Result: first paint 0.4–0.8 s, touch at socket latency, and the only external pieces are two Apache-2.0 files OCTAVE ships itself.

Why fork the server

Pinning an upstream jar was enough for the protocol, but the in-car problems (a power press dozing the virtual display, USB dropouts destroying the display and its apps) needed behaviour the phone-side program does not have. Forking under org.octave.phoneserver (commit 200c8c8) gave a place for the MirrorKeeper, the persistent session loop and the TYPE_OCTAVE_* messages (numbered from 100 to stay clear of upstream), while the version string 3.3.4-octave keeps the mismatch check loud. Upstream changes are pulled deliberately and the byte layouts re-verified.

Why a virtual display

new_display=1280x800 gives a landscape surface sized for the dash instead of a portrait phone screen, keeps the phone's own screen free (and dark) for the passenger, and on Samsung draws DeX with a taskbar that replaces the nav row. Coordinates are relative to the mirrored display so touch needs no display-id routing. The costs are documented rather than hidden: HOME/APP_SWITCH do nothing there (hence am start --display), the display shares the phone's power group, and Android 11+ is required (the manager falls back to the phone screen below SDK 30).

Why the keeper logic lives on the phone

From the dash the reaction is an adb round trip on a 1 s poll: ~1 s of black frames and a visible relight per press, plus adb processes spawned while a session is up. Inside the device a DisplayListener and a 250 ms poll react within a frame or two, the keyguard is read directly from IWindowManager, and the state survives a client reconnect because the keeper is process-wide. OCTAVE keeps only policy (OCTAVE_SET_KEEPER), an escape hatch (OCTAVE_TAKE_BACK) and display (PHONE_STATE).

Why the phone's volume is never touched

Gain is applied to the PCM inside OCTAVE. The alternative -- raising the phone's media volume for the session -- failed silently on the test handset and would leave the phone at maximum after a crash. A crash in the car must not change the phone's state.

Why hold frames instead of clearing the sink

Every transition (doze, wake, reconnect, reattach) was measured with a 30 fps capture of the dash and each sub-second artifact fixed at its source: the last good frame is the correct thing to show until real content arrives, so neither client ever clears the VideoOutput, black and doze-fade frames are held, and overlays appear only after a delay (1.5 s asleep, 2 s reconnect badge).

Why raw PCM audio

audio_codec=raw means PCM s16le 48 kHz stereo on the wire and no audio decoder in either backend (the code comment on the launch option); the 192 KB/s it costs over USB is small next to the 8 Mbit/s video stream.

What actually works

Platform status
Python on Windows is the only combination that shows Android Auto inside OCTAVE. The DHU window is found with EnumWindows and re-parented into the Qt window with SetParent; input reaches it as ordinary mouse input because it is a real child window. On Python / Linux / macOS, _find_dhu_window() returns 0 (Windows API only) so _setup_seamless_capture() retries every second for as long as the DHU runs and nothing is embedded; DhuCapture.startCapture() would emit "Screen capture only supported on Windows" anyway. The C++ port launches and stops the DHU and performs the adb setup, but never locates its window: on Windows the poll times out after 5 s and uses the process id as a stand-in handle without starting capture; on other platforms it captures the whole primary screen (QScreen::grabWindow(0)) into the image provider, which no QML reads, and its EmbeddedDhuItem only counts frames. In both C++ cases the view ends up black behind the close button. sendMouseClick() is a stub in C++. The C++ header comments call this out as intentional ("DHU is rarely used").

The parity that does hold: property, signal and slot names, the DHU/adb search paths, headunit.ini, the adb sequence, the 100 ms x 50 hide poll on Windows, the 3 s delayed capture setup elsewhere, and cleanup().

ADB Connection Setup

_prepare_adb_connection() / prepareAdbConnection() runs synchronously on the GUI thread:

  1. Check device -- adb devices must list at least one line containing the substring device (no state parsing like the phone mirror's getDeviceState()).
  2. Port forwarding -- adb forward --remove-all, then adb forward tcp:5277 tcp:5277 (the DHU's port). --remove-all also removes a live phone-mirror forward, so launching Android Auto during a mirror session breaks the mirror's tunnel.
  3. Head unit server -- dumpsys activity services com.google.android.projection.gearhead/.companion.DeveloperHeadUnitNetworkService must show a ServiceRecord. If not, OCTAVE tries am start -n com.google.android.projection.gearhead/.companion.MainActivity -a com.google.android.gms.car.action.START_HEAD_UNIT_SERVER (wait 2 s), then am startservice -n ...DeveloperHeadUnitNetworkService (wait 1 s). If neither works it polls once a second for up to 60 s for the user to start "Head unit server" in Android Auto's developer settings, reporting the remaining time every 5 s through connectionProgress.

DhuCapture & Frame Provider

DhuCapture captures a window at 30 FPS on a QTimer into DhuFrameProvider. Python uses Windows GDI: GetClientRect, a compatible DC and bitmap, PrintWindow(hwnd, memDC, PW_CLIENTONLY), GetDIBits into a top-down 32-bit buffer, copied into a QImage(Format_ARGB32). C++ uses the portable QScreen::grabWindow(WId). In practice neither capture runs against a real DHU window (see What actually works): Python's Windows path embeds the window natively instead of capturing it, and its non-Windows path never finds a window.

DhuFrameProvider

A QQuickImageProvider registered as image://dhuframe/ in both entry points. It returns the latest frame under a lock (the timer runs on the GUI thread, QML may request images from a render thread), or an 800x480 placeholder (black in C++, uninitialised in Python) when none is available. No QML file currently references image://dhuframe/.

DHU Window Hiding (Python, Windows)

The DHU is launched minimized (SW_MINIMIZE via STARTUPINFO). A poll every 100 ms for up to 5 s finds the window by process id and title ("Desktop Head Unit" or "Android Auto") and immediately: 

# 1. Make it a tool window (hide from taskbar)
SetWindowLongW(hwnd, GWL_EXSTYLE, old_style | WS_EX_TOOLWINDOW)

# 2. Move off-screen
SetWindowPos(hwnd, 0, -3000, -3000, ...)

# 3. Restore from minimized (a minimized window cannot be captured or embedded)
ShowWindow(hwnd, SW_RESTORE)

# 4. Ensure it stays off-screen after restore
SetWindowPos(hwnd, 0, -3000, -3000, ...)

Two seconds later dhuWindowReady(hwnd) and dhuEmbeddedChanged(true) are emitted; the embedding itself is done by EmbeddedDhuItem. The C++ port starts the process with CREATE_NO_WINDOW + SW_MINIMIZE but has no EnumWindows, so its poll always times out.

Touch Input Forwarding

With the window re-parented into OCTAVE (Python/Windows), touches land on the DHU as normal mouse input and nothing has to be forwarded. DhuCapture.sendMouseClick(x, y) exists for the capture-based design and is not called by any QML; it synthesises a real click because the DHU ignores SendMessage-style input:

  1. Save state -- cursor position and foreground window
  2. Scale coordinates -- from the 1920x1080 space of headunit.ini to the DHU client area
  3. Make nearly invisible -- WS_EX_LAYERED with alpha 1
  4. Move on-screen -- to the bottom-right screen edge (real clicks need an on-screen window)
  5. Activate and click -- SetForegroundWindow, ClientToScreen, SetCursorPos, mouse_event down/up
  6. Restore -- alpha 255, move off-screen, restore cursor and foreground window

sendMouseEvent(x, y, pressed) (WM_LBUTTONDOWN/WM_LBUTTONUP via SendMessageW) remains as the simpler alternative. Both are Python-only; the C++ sendMouseClick logs and returns.

EmbeddedDhuItem

Python (backend/android_auto/embedded_dhu.py): a QQuickItem that, on dhuWindowReady, hides the DHU window, strips WS_POPUP | WS_CAPTION | WS_THICKFRAME | WS_BORDER | WS_SYSMENU | WS_MINIMIZEBOX | WS_MAXIMIZEBOX, adds WS_CHILD | WS_VISIBLE and WS_EX_TOOLWINDOW, calls SetParent(hwnd, octaveWindow.winId()), and then keeps the child positioned over the item with MoveWindow on a 16 ms timer and on every geometry change. detach() hides the child (SW_HIDE) when the view is not visible; reattach() re-embeds it 50 ms later. isStreaming is true while embedded and not hidden.

C++ (src/items/embeddeddhuitem.{h,cpp}): no window embedding. It connects to the manager's dhuWindowReady / dhuEmbeddedChanged and to DhuCapture.frameReady, exposes isStreaming and a frameCounter property (frameRefresh signal) intended for an Image { source: "image://dhuframe/" + frameCounter } that AndroidAutoView.qml does not contain.

Both connect via connectToManager(androidAutoManager) from the item's Component.onCompleted and pick up a DHU that is already running when the user navigates back to the view.

// src/main.cpp
