Design Decisions

Why dev mode wraps production instead of duplicating it

python -m dev.main_dev imports main, which runs the whole production start-up at import time (app, engine, every manager, every signal connection) and stops short of loading the QML, because load_main_qml() and app.exec() only run under main.py's if __name__ == "__main__" guard. Dev mode then swaps in the mock OBD through main.install_obd_manager(), registers its context properties, calls main.load_main_qml() and reparents an overlay into the real window. The docstring of dev/main_dev.py records why: the old dev/dev_main.py "duplicated 85% of main.py and constantly drifted out of parity". Everything except obdManager is the production object.

Why a TCP command server and MCP servers for performance work

The head unit runs in a Jeep; the problems that matter are stutter, stalls and regressions that show up when the app is driven the way a driver drives it. A JSON-over-TCP command server (backend/command_server.py, only started by --profile) lets a script or an agent navigate pages, toggle settings, skip tracks, drive the simulator and read the perf counters while the perf monitor measures the event loop, so a test is repeatable and comparable between changes. The two MCP servers expose the same channel to a coding agent so it can reproduce a report, bisect a regression or benchmark a setting without a human clicking.

Where the tooling lives

The developer tooling is not in git: dev/ (dev runtime, mock OBD, screenshot / story / collage / perf scripts, MCP servers) and the three in-app modules backend/command_server.py, backend/perf_monitor.py and backend/perf_patches.py are listed in .gitignore and synced between the developer machines outside git. A fresh clone does not have them. main.py imports the three modules only inside setup_perf_profiling() (run for --profile) and guards each import: a missing module logs a warning and the app keeps starting — see Troubleshooting. The dev overlay QML that dev/dev_runtime.py loads (DevOverlay.qml, which embeds DevToolsPanel.qml) is read from src/dev/qml/.

The launchers in dev/ do not start the Python app unless told to; every use below therefore either runs python -m dev.main_dev / python main.py --profile directly or sets OCTAVE_BACKEND=python (or passes --backend python where a script has that flag).

Why screenshots are grabbed from inside Qt

The first screenshot tool (dev/screenshots/core.py, scenarios.py, cli.py) used xdotool + mss and broke under Wayland. The current one asks the running app to capture itself: the screenshot and record_start actions call grabWindow() on the GUI thread, which works the same on Wayland, X11 and Xvfb, and the HUD can be hidden first with set_dev_chrome. It also gives deterministic window sizes for README assets (dev/docs/SCREENSHOTS.md).

Why ruff runs warn-only

The full ruleset (E F W E722 B UP) is enabled in pyproject.toml, but the CI step is ruff check . || true, labelled "warn-only — full ruleset has legacy noise". A second CI step, ruff check . --select E722,F821, is blocking: bare except: and undefined names fail the build.

Why errors do not surface in the UI

Errors are reported through logs and page-specific status text. There is no application-wide error notification layer; TODO/error-notification-ui.md records that deferred design. Individual views can show error details on request (tapping a failed download opens its error popup). The rotating logs, the UI watchdog (backend/ui_watchdog.py) and the Diagnostics card (backend/diagnostics_manager.py) support troubleshooting after a session.

Dev Mode Setup & Usage

Dev mode provides a simulated vehicle and keyboard controls for testing without an OBD-II adapter.

source venv/bin/activate
python -m dev.main_dev                  # mock OBD + overlay
python -m dev.main_dev --profile        # + perf monitor, command server :9876, sim_* and collage_* actions
python main.py --profile               # production mode, real OBD, perf monitor + command server

main.py parses its flags with parse_known_args(), so dev.main_dev accepts the same --debug / --profile / --smoke. The app writes the real config directory; for a throw-away run set XDG_CONFIG_HOME on Linux (get_app_data_dir() honours it), as the story and collage tools do with their own profile directory.

dev/main_dev.py step by step

dev/main_dev.py puts the project root on sys.path, makes it the working directory, imports main (production start-up runs at import), then:

  1. install_dev_runtime(main) — main.install_obd_manager(MockOBDManager(main.settings_manager)) registers the mock as obdManager (and hands it to obdAdapterFinder), and registers devKeyboardController (KeyboardController), devToolsManager and devMode = true as context properties.
  2. main.load_main_qml() — the production frontend/Main.qml loads.
  3. install_dev_overlay(main, root_window) — creates the dev overlay QML with a QQmlComponent, sets QQmlEngine.CppOwnership and the root window as its QObject parent (so the JS GC cannot collect it), reparents it into contentItem(), and gives the window to DevToolsManager for grabWindow().
  4. With --profile: main.setup_perf_profiling(), then install_sim_commands(main) (the sim_* actions through a SimBridge that marshals them onto the GUI thread) and install_collage_commands(main) from dev/collage/bridge.py.
  5. sys.exit(main.app.exec()).

Keyboard controls

The overlay forwards Keys.onPressed / onReleased to devKeyboardController.handle_key(key, pressed), which tracks held keys and drives the mock; Tab is handled in the overlay itself.

Mock OBD Manager

dev/mock_obd_manager.py: MockOBDManager(settings_manager) mirrors the live-data signals and the QML-called slots of the real OBDManager (getters such as coolantTemp(), voltage(), speedMPH(), rpm(); reconnect, force_connect, is_connected, get_connection_status, scan_vehicle, read_dtc, clear_dtc, read_freeze_frame, diagnostic mode, ...) and generates the data itself. Its docstring calls it a "Bluetooth ELM327 simulator". It does not implement setParameterDemand or the vehicle-gate properties (vehicleScanComplete, vehicleSupportedParameters); the QML guards those calls, and the mock emits its values regardless of demand.

Simulation

  • Connect sequence: starts 300 ms after construction and walks phases (BT scan, SPP connect, ATZ reset, ELM config, protocol detect, PID query, connected) through connectionStatus / detail / progress signals, about 5 s in all, so the OBD settings card's progress UI can be exercised (_begin_connect_sequence / _advance_connect).
  • Physics (_update_sim, a 16 ms QTimer): throttle sets an RPM target (800 + throttle × 5500) and accelerates the speed (up to 140 mph); with no throttle RPM returns to 800 and speed coasts down; brake decelerates; the gear follows the speed (thresholds 15 / 30 / 45 / 65 / 90 mph). Load, MAF, MAP and timing advance follow throttle and RPM, AFR richens above 70 % throttle, O2 oscillates with RPM. Coolant and oil temperatures hold the scenario's base value plus ±0.5 noise; voltage is 14.2 ± 0.1.
  • Scenarios: cold start (coolant and oil 20, RPM 1100), overheating (coolant 115, oil 130), low fuel (fuel level 5), reset to normal (90 / 95, idle, fuel 72, engine on).
  • Emit cadence: in realistic mode five timers emit at different rates (200 ms RPM; 300 ms speed, throttle, load, MAP; 1 s temperatures, voltage, MAF, AFR, O2; 3 s fuel and trims; 5 s catalyst / EGR / uncommon PIDs) with values quantised like the ELM (_q_rpm, _q_int, _q_v01) and 2 % of polls dropped (_failure_rate, _drop()). set_realistic_mode(False) switches to one uniform 100 ms timer with no drops (useful for clean screenshots).
  • Dropouts: off by default; set_simulate_dropouts(True) schedules a 2–4 s blip every 90–180 s with an abbreviated reconnect; trigger_dropout_now() and set_failure_rate(rate) are also slots.
  • VIN and codes: VIN 1J4FA49S03P123456; mock DTCs P0300 and P0420, freeze frame P0420.

sim_* actions

With --profile in dev mode, install_sim_commands() registers on the command server: sim_throttle / sim_brake (value), sim_rev (intensity, default 50), sim_engine (on; toggles only if the state differs, or always without on), sim_gear (gear), sim_upshift, sim_downshift, sim_speed (mph), sim_rpm (rpm), sim_scenario (name: cold | hot | low_fuel | normal), sim_realistic (enabled), sim_imu (on) and sim_status. All but sim_status are emitted to the GUI thread through a queued signal and answer {"queued": name} at once; a failure there is only printed. sim_status returns the mock's speed, RPM, gear, engine, throttle and brake state plus the IMU feed status.

sim_imu drives dev/mock_imu.py (MockIMUFeed, 30 Hz GUI-thread timer), which emits the real berryIMU manager's signals from a synthetic drive tied to the mock speed: the road winds (heading), lateral G follows speed × turn rate, longitudinal G the change in speed, the body rolls and pitches, the road climbs and dips for altitude. It is off until sim_imu {"on": true} arrives, so a dev-mode run on a machine with a real IMU is not masked.

Command Server (TCP)

backend/command_server.py (gitignored)

A socketserver TCP server (ThreadingMixIn, one daemon thread per client) on 127.0.0.1:9876 that accepts newline-delimited JSON commands. setup_perf_profiling() in main.py creates it as main.cmd_server, starts it with the managers {"media", "obd", "settings"}, the perf monitor and the engine, and stops it on aboutToQuit. The port is the module's DEFAULT_PORT; main.py does not offer a flag to change it.

  • CommandServer.register(action, handler) adds an action after start(); handler(args) runs on the connection thread, and the docstring says to marshal to the GUI thread yourself if it touches Qt objects (the sim_* and collage_* bridges do). Registered actions are checked before the built-in ones.
  • GUI work goes through NavigationBridge, a QObject living on the GUI thread: navigation is invoked with Qt.QueuedConnection (the reply does not wait for it); screenshots, recording and UI driving use Qt.BlockingQueuedConnection and read the result back from the bridge.
  • The media, settings and OBD actions call the manager methods directly on the connection thread, not on the GUI thread. set_volume calls mediaManager.setVolume(linear) with a 0.0-1.0 value (default 0.5), bypassing VolumeController and the saved currentVolume.

Protocol

// Client sends JSON + newline:
{"action": "next_track"}

// Server responds with JSON + newline:
{"ok": true, "result": null}

// With arguments:
{"action": "navigate", "args": {"page": "media_player"}}

// Error response (an exception in the handler, or unparsable JSON):
{"ok": false, "error": "Unknown action: foo"}

Actions (the list_actions response)

  • App: ping (returns "pong"), list_actions (registered extensions first, then the built-ins)
  • Performance: get_metrics (loop_avg_ms, loop_p99_ms, gil_avg_ms, cpu_percent, mem_mb, thread_count, summary), get_detailed_report, get_slot_timings (avg_ms, p95_ms, max_ms, count per label)
  • Navigation: navigate (page), go_back, go_home, get_current_page (the objectName of the stackView's current item), list_pages, open_settings (section), list_settings_sections
  • Screenshots / recording: screenshot (path, required; returns {"saved", "path"}), set_dev_chrome (visible: the overlay's overlayVisible), set_window_size (width, height; default 1280×720), record_start (path, fps), record_stop, record_status
  • UI driving: find_item (name: geometry, centre, effective visibility walking the parent chain, opacity, hiddenBy; the first visible match wins, popups included; "root" is the window), find_text (text, optional prop such as placeholderText; first visible item whose property equals it, case-insensitive), list_items (prefix), get_prop / set_prop (name, prop, value), call (name, method: a no-arg method such as forceActiveFocus), click (x, y), long_press (x, y, ms default 1000), type_text (text, enter, field: objectName or placeholder; key events are sent straight to the item), drag (x1, y1, x2, y2, steps default 12).   • Media: next_track, previous_track, toggle_play, pause, toggle_mute, toggle_shuffle, set_volume (volume), get_media_status, get_track_info, skip_tracks (count)
  • OBD: obd_status, obd_reconnect
  • Settings: get_settings, get_all_settings (20 keys), toggle_setting / set_bool_setting (12 boolean keys such as show_waveform, vinyl_mode, auto_play), set_numeric_setting (10 keys with clamped ranges, e.g. ui_scale 0.5-2.0, blur_radius 0-100), set_string_setting (theme, font, album_art_transition, bottom_bar_orientation, mediaFolder), and the list_toggle_settings / list_numeric_settings / list_string_settings discovery calls

Recording

record_start starts a PreciseTimer on the GUI thread that grabs the window at fps (clamped 1-60; the docstring advises 30 or below) and pipes raw RGBA into ffmpeg -c:v libx264 -preset veryfast -crf 18 -pix_fmt yuv420p; width and height are rounded down to even. Grabs are scaled to the window's logical size, so a device pixel ratio above 1 does not crop the video. Frames are paced by wall clock: when rendering misses ticks the last frame is repeated, so clips play at real speed. record_status reports frames, dropped, repeated, seconds and error ("ffmpeg not found", "already recording", ...).

UI-driving scripts

dev/tests/drive_dashboard_editor.py drives the dashboard editor end to end (place, bind, move, resize, options, save, edit, duplicate, delete, draft rescue; about 40 assertions, about 3 minutes) in xvfb (default) | visible | offscreen mode, writes screenshots to dev/screenshots/output/editor/, removes its test-dash*.json dashboards and exits 1 on any failure. dev/tests/drive_dashboard_features.py reuses its helpers for per-widget overrides, enum options, drag-to-resize, share / import, swipe between dashboards and the empty Parameter Cards state. Both start the app through dev/app_launch.py; run them with OCTAVE_BACKEND=python. The other files in dev/tests/ are stand-alone checks: test_dtc.py / clear_dtc.py (python-obd against /dev/rfcomm0) and test_album_art_colors.py (needs Pillow and numpy).

MCP Servers

dev/mcp_server.py (octave-perf) and dev/mcp_benchmark.py (octave-benchmark) are MCP servers (MCPServer from mcp 2.x, falling back to FastMCP on 1.x) that let a coding agent drive OCTAVE through the command server. Every tool sends one JSON action to 127.0.0.1:9876 (10 s timeout) and formats the reply; a refused connection returns a message telling you to start the app with --profile. mcp_benchmark.py only serves MCP when given --mcp; without it, it runs the suite once from the command line.

Setup

pip install mcp                       # in the venv; not in requirements.txt
python -m dev.main_dev --profile       # simulator; or python main.py --profile for real OBD
python dev/mcp_server.py              # stdio MCP server; normally launched by the agent from .mcp.json
python dev/mcp_benchmark.py --mcp     # the benchmark server

The local .mcp.json is gitignored; point its server commands at the venv's Python and this checkout's script paths.

Performance Profiling

backend/perf_monitor.py and backend/perf_patches.py (gitignored)

python main.py --profile               # production mode
python -m dev.main_dev --profile       # dev mode

setup_perf_profiling() runs after load_main_qml(). It creates PerfMonitor(csv_path, log_path) writing dev/perf/logs/perf_<YYYYMMDD_HHMMSS>.csv and .log (the directory is created), registers it as the perfMonitor context property, starts it, starts the command server, and applies perf_patches.apply_patches(). On quit it stops the monitor, prints the log and CSV paths and the detailed report. Each import is guarded: a missing backend/perf_monitor.py logs --profile: backend/perf_monitor.py not present (gitignored dev tooling), skipping performance monitor and command server and returns; a missing backend/command_server.py skips only the command server; a missing backend/perf_patches.py skips only the instrumentation.

What is measured

MetricMethodThreshold
Event-loop latencyThe gap between firings of a zero-interval PreciseTimer on the GUI thread (gaps of 500 ms or more are discarded); mean, p50, p95, p99 and max per one-second windowavg < 5 ms green (OK), < 16 ms yellow (WARN), otherwise red (STUTTER)
GIL jitter (gil_avg_ms)_GILProbe, a daemon thread that waits 10 ms on an Event and records how late it wakes: an approximation of how long other threads held the GILHigher = threads starved
Per-slot timing@timed_slot, PerfMonitor.begin() / end(start, label), and the wrappers perf_patches installs; ring buffers of the last 200 calls per labelLabels with p95 > 2 ms are printed as slow every 5 s and logged; the detailed report lists p95 > 1 ms
CPU / RSS / threadspsutil.Process() (optional; without it CPU and memory stay 0 and a hint to install it is printed) and threading.active_count()CPU is psutil's per-process percentage (can exceed 100 %)

perf_patches.apply_patches() wraps these instance methods: media._kmeans_colors, media._update_position, media.next_track, media.previous_track, audio._analyze_audio (FFT), obd._monitor_connection, esp32._read_serial, settings.save_settings, and media._extract_colors if such a method exists (MediaManager's method is _extract_album_colors, so that label stays empty). A method that does not exist on the instance is skipped. Because the wrapper is set on the instance, it times Python calls made through the attribute; connections made before the patch keep the original method.

Outputs

  • Terminal: a colour-coded [PERF] line overwritten every second; slow slots every 5 s.
  • CSV: columns timestamp, loop_avg_ms, loop_p50_ms, loop_p95_ms, loop_p99_ms, loop_max_ms, gil_avg_ms, gil_p99_ms, cpu_pct, mem_mb, threads.
  • Perf log: plain text with OK / WARN / STUTTER tags and SLOW lines, then the detailed report at stop.
  • QML properties (notify metricsUpdated): loopLatencyMs, loopP99Ms, gilJitterMs, cpuPercent, memMb, threadCount, summaryText; getDetailedReport() is a slot.
  • Command server: get_metrics, get_detailed_report, get_slot_timings.

Manual instrumentation

from backend.perf_monitor import timed_slot, PerfMonitor

@timed_slot

    ...

Screenshots & Video Stories

UI collage

python -m dev.collage builds one HTML page of every screen, every popup and every QML file in frontend/, rendered by the running app: it navigates to every page and settings section, opens each Popup / Dialog / Drawer / Menu found in the live object tree, and instantiates every frontend/**/*.qml on a blank host surface with the real managers on the context (required properties get placeholder values; creation errors and QML warnings are recorded on the tile). It needs the collage_* actions, so the app must be in dev mode with --profile; run it with OCTAVE_BACKEND=python, or start python -m dev.main_dev --profile yourself and pass --no-launch. Options: --visible, --offscreen, --size, --settle, --only screens,popups,components, --filter TEXT, --real-profile, --keep, --no-open, --port. Output: dev/collage/output/<timestamp>/index.html and a latest link.

How to Add a Feature

  1. Manager module: add backend/foo.py with a QObject subclass. Expose state with Signal and Property(type, notify=...), and QML-callable methods with @Slot(...) (give the result type: @Slot(str, result=bool)). Log through get_logger(__name__) from backend/logging_config.py. Store files under get_app_data_dir() from backend/settings_manager.py, and write any file that is rewritten while driving with atomic_write_text() / atomic_write_bytes() from backend/atomic_io.py. Import heavy optional libraries with lazy_module() / available() from backend/lazy_import.py.
  2. Threads: keep blocking I/O off the GUI thread. A worker hands results back through a signal connected with Qt.QueuedConnection (as MediaManager does) or with run_on_main(fn) from backend/qt_threading.py; Qt objects are only touched on the GUI thread.
  3. Register in main.py: import the class, instantiate it, call its connect_settings_manager(settings_manager) if it needs settings, and engine.rootContext().setContextProperty("fooManager", foo_manager) before load_main_qml() so the first binding evaluation sees it. Add a cleanup step to the steps list in cleanup_on_quit() if it owns threads, processes or open devices.
  4. Settings: add the key and default to _default_settings in backend/settings_manager.py, a Signal, a Property and a save_xxx slot (existing setters go through update_setting(key, value, signal)), and an entry in SETTINGS_REGISTRY at the top of the module if it should appear in the Quick Panel. Document it in the Settings Reference.
  5. QML: build the view in frontend/; settings pages go under frontend/settings/; gauges and dashboards follow docs/GAUGE_AUTHORING.md. Guard calls to managers that may be absent with typeof fooManager !== "undefined".
  6. Dev tooling: if the feature depends on hardware, add a simulator in dev/ and wire it in dev/dev_runtime.py; add command-server actions with main.cmd_server.register(name, handler) (marshalling to the GUI thread) and MCP tools if an agent should drive it; add a perf_patches wrap or a @timed_slot for a new hot path.
  7. Test: add a test under tests/; run QT_QPA_PLATFORM=offscreen pytest tests/ and ruff check . --select E722,F821; at least QT_QPA_PLATFORM=offscreen python -c "import main" catches import errors.
  8. Wiki: update the manager page and Signals & Slots Reference, and rebuild the search index.

Running the tests

source venv/bin/activate
QT_QPA_PLATFORM=offscreen pytest tests/ -v

tests/conftest.py sets QT_QPA_PLATFORM=offscreen and QT_QUICK_CONTROLS_STYLE=Basic as defaults, puts the repo root on sys.path, provides a session-scoped qapp fixture (QApplication), and runs gc.collect() on the main thread after every test (an autouse fixture): its comment explains that QObjects collected on a worker thread left timers that later fired into freed memory (a segfault in QTimerInfoList::activateTimers on PySide6 6.12). Several tests run Qt in a separate subprocess for the same isolation.

Manual testing workflow

  1. Dev mode: python -m dev.main_dev for iteration with the simulator and keyboard controls; --profile to script it.
  2. Profile mode: python main.py --profile and watch loop latency and GIL jitter; run dev/docs/perf_test_plan.md through the MCP server before and after a change that touches a hot path.
  3. UI-driving scripts: OCTAVE_BACKEND=python python dev/tests/drive_dashboard_editor.py; write new ones against the find_item / click / drag actions.
  4. Logs: --debug for verbose output and octave-debug.log.
  5. Hardware: OBD, IMU, gesture, ESP32 and phone-mirror changes need the real devices (see Hardware Setup).

Continuous Integration

.github/workflows/build.yml runs on every push and pull request to main, on v* tags and on manual dispatch. Its two Python jobs:

  • lint — Ubuntu 22.04, Python 3.11, pip install ruff==0.15.10; step 1 ruff check . || true (advisory), step 2 ruff check . --select E722,F821 (blocking).
  • test — Ubuntu 22.04, Python 3.11; installs libxcb-xinerama0 libxcb-cursor0 libxkbcommon0 libgl1-mesa-glx libegl1 libpulse0 with apt, then pip install -r requirements.txt and pip install pytest, and runs pytest tests/ -v with QT_QPA_PLATFORM=offscreen.

The same workflow file also contains jobs that do not involve the Python backend.
