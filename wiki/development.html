Design Decisions

Two backends, one frontend

The C++ tree (src/) is what ships; the Python tree (backend/, main.py) is the development and hardware-hacking backend. Both expose the same managers, context-property names, slots, signals, properties and on-disk JSON to the shared QML in frontend/, which must never know which one is running (the only allowed difference is a typeof fooManager !== "undefined" guard for a feature legitimately absent on one platform). This is the standing policy in CLAUDE.md; the rationale and the packaging consequences are on the Building page. Practically, it means the Python side is where most tooling lives: the command server, perf monitor, mock OBD and MCP servers are Python, and they exercise the same QML the C++ binary runs.

Why dev mode wraps production instead of duplicating it

python -m dev.main_dev imports main, which runs the whole production start-up (app, engine, every manager, every signal connection) and stops short of loading the QML because that lives under main.py's if __name__ == "__main__" guard. Dev mode then swaps in the mock OBD, registers its context properties, calls main.load_main_qml() and reparents an overlay into the real window. The docstring in dev/main_dev.py records why: the old dev/dev_main.py "duplicated 85% of main.py and constantly drifted out of parity". Same code path as production, extra layers bolted on afterwards.

Why a TCP command server and MCP servers for performance work

The head unit runs in a Jeep; the problems that matter are stutter, stalls and regressions that only show up when the app is driven the way a driver drives it. A JSON-over-TCP command server (backend/command_server.py, only started by --profile) lets a script or an agent navigate pages, toggle every setting, skip tracks, drive the simulator and read the perf counters while the perf monitor measures the event loop, so a test is repeatable and comparable between commits (dev/docs/perf_test_plan.md, dev/perf/run_perf_loop.py). The two MCP servers expose the same channel to a coding agent so it can reproduce a report, bisect a regression or benchmark a setting without a human clicking. The README makes the same point: "The same command channel is exposed as MCP tools, so a coding agent can navigate the app, change settings, read performance counters and record clips."

Why the tooling is gitignored

dev/, .mcp.json, backend/command_server.py, backend/perf_monitor.py and backend/perf_patches.py are all in .gitignore ("Developer mode tools (completely isolated from main codebase)", "Performance profiling"). They are synced between the developer machines through Dropbox, not git, so the shipped tree carries no simulator, no TCP listener and no monkey-patching; main.py imports them lazily and only under --profile. The consequence is that a fresh clone cannot run --profile or dev mode — see Troubleshooting.

Why screenshots are grabbed from inside Qt

The first screenshot tool used xdotool + mss (X11 input and capture) and broke under Wayland. The current one asks the running app to capture itself: screenshot and record_start run root.grabWindow() on the GUI thread, which works identically on Wayland, X11 and Xvfb, and hides the dev HUD automatically. It also gives deterministic window sizes for README assets (dev/docs/SCREENSHOTS.md).

Why ruff runs warn-only

The full ruleset (E F W E722 B UP) is enabled in pyproject.toml, but the CI step is ruff check . || true because the legacy tree still has noise (long lines, import ordering, unused re-exports — already ignored as E501 E402 F401 B008 UP007, with more remaining). Only the two rules that indicate a real bug, E722 (bare except) and F821 (undefined name), are blocking. The workflow step is labelled "warn-only — full ruleset has legacy noise"; CLAUDE.md calls this the Phase 1 cleanup and expects E722/F821 to stay blocking while the enforced set widens as the code is cleaned up.

Why errors do not surface in the UI

Every backend routes errors to logs and status text, never to pop-ups, because a notification flickering in a driver's peripheral vision is a distraction risk (TODO/error-notification-ui.md). The trade-off is that developers must be able to get at the logs after the fact, which is why both backends have rotating files, crash handlers, a UI watchdog and the Diagnostics card (Troubleshooting).

Dev Mode Setup & Usage

Dev mode provides a simulated vehicle and keyboard controls for testing without an OBD-II adapter. Python only; the C++ binary has no simulator.

# Launch dev mode (from the project root, venv active)
python -m dev.main_dev

# Dev mode + perf monitor + command server, with the simulator exposed as sim_* actions
python -m dev.main_dev --profile

dev/main_dev.py imports main (production start-up runs at import), then dev/dev_runtime.py does the rest:

  1. install_dev_runtime(main) — main.install_obd_manager(MockOBDManager(...)) replaces the real OBDManager (every QML binding to obdManager now sees the mock), and registers devKeyboardController, devToolsManager and devMode = true as context properties.
  2. main.load_main_qml() — the production Main.qml loads; there is no separate dev entry QML.
  3. install_dev_overlay(main, root_window) — instantiates dev/DevOverlay.qml with the engine's root context, pins it to C++ ownership and gives it both a QObject parent and a visual parent (the window's contentItem) so the JS garbage collector cannot reclaim it, then hands the window to DevToolsManager for grabWindow().
  4. With --profile: main.setup_perf_profiling() then install_sim_commands(main), which registers the sim_* actions on the command server through a SimBridge that marshals them onto the GUI thread (the mock's timers live there).

Mock OBD Manager

dev/mock_obd_manager.py

MockOBDManager(settings_manager) provides the same signal and slot surface as the real OBDManager but generates data from keyboard / command input and a simple physics model. It also simulates the connection sequence (_begin_connect_sequence / _advance_connect) so the OBD settings card's progress UI can be exercised, and can inject dropouts.

Simulation features

  • Throttle drives RPM, which drives speed through six gear ratios; manual shifting via Q/R or gear 1–6
  • Coolant and oil temperatures rise with load and cool at idle; fuel level falls with load
  • Emitters run at several rates (_emit_fast ... _emit_slowest) so the parameter cards see realistic update cadences; values are quantised like a real adapter (_q_rpm, _q_int, _q_v01)
  • Scenario presets: cold start, overheating (high temps, low voltage), low fuel, reset to normal
  • Dropout simulation: set_simulate_dropouts(bool), set_failure_rate(float), trigger_dropout_now(); per-PID drops via _drop()
  • The QML-callable getters of the real manager (coolantTemp(), voltage(), speedMPH(), ...) are mirrored as slots

Control methods

set_throttle(percent) / set_brake(percent)   # 0-100
rev_engine(intensity=50)                       # throttle blip
toggle_engine()
set_gear(n) / upshift() / downshift()
set_speed(mph) / set_rpm(rpm)                  # direct overrides
set_realistic_mode(enabled)
simulate_cold_start() / simulate_overheating() / simulate_low_fuel() / reset_to_normal()

Over the command server (dev mode with --profile) the same controls are sim_throttle / sim_brake (value), sim_rev (intensity), sim_engine (on), sim_gear, sim_upshift, sim_downshift, sim_speed (mph), sim_rpm, sim_scenario (name: cold | hot | low_fuel | normal), sim_realistic (enabled) and sim_status.

Command Server (TCP)

backend/command_server.py (gitignored)

A socketserver-based TCP server on 127.0.0.1:9876 (DEFAULT_PORT) that accepts newline-delimited JSON commands. It is created by main.setup_perf_profiling(), i.e. only when python main.py --profile (or dev.main_dev --profile) is used, receives the media / spotify / obd / settings managers, the perf monitor and the QML engine, and is stopped on aboutToQuit. main.cmd_server exposes it as a module attribute so dev tooling can register(action, handler) extra actions (commit b1db87c).

Protocol

// Client sends JSON + newline:
{"action": "next_track"}

// Server responds with JSON + newline:
{"ok": true, "result": null}

// With arguments:
{"action": "navigate", "args": {"page": "media_player"}}

// Error response:
{"ok": false, "error": "Unknown action: foo"}

Actions (the list_actions response)

  • App: ping (returns "pong"), list_actions
  • Performance: get_metrics, get_detailed_report, get_slot_timings
  • Navigation: navigate (page id), go_back, go_home, get_current_page, list_pages, open_settings (section id), list_settings_sections
  • Screenshots / recording: screenshot (path), set_dev_chrome (show/hide the HUD), set_window_size, record_start (path, fps), record_stop, record_status
  • UI driving: find_item (geometry + effective visibility of any QML item by objectName, popups included), list_items (prefix match), get_prop / set_prop, call (invoke a no-arg method such as forceActiveFocus), click (x, y) and drag (x1, y1, x2, y2, steps) — synthetic mouse events delivered through the window's normal event path, so MouseArea drag thresholds and Flickable behave as they would for a finger. Closed popups leave the item tree, and pages pushed via navigate are not destroyed on go_home, so tests should prefer the visible instance (the server does) and scroll targets into view before clicking.
  • Media: next_track, previous_track, toggle_play, pause, toggle_mute, toggle_shuffle, set_volume, get_media_status, get_track_info, skip_tracks
  • Spotify: spotify_toggle_play, spotify_next, spotify_previous, spotify_status
  • OBD: obd_status, obd_reconnect
  • Settings: get_settings, get_all_settings, set_media_source, toggle_setting, set_bool_setting, set_numeric_setting, set_string_setting, and the list_toggle_settings / list_numeric_settings / list_string_settings discovery calls
  • Extensions: whatever was register()ed — in dev mode the sim_* simulator actions

Navigation bridge and valid pages

NavigationBridge lives on the GUI thread; the TCP handler thread reaches it with QMetaObject.invokeMethod (queued for navigation, BlockingQueuedConnection for captures and UI driving so the result can be read back). Because QML function foo(arg) parameters are untyped and register as QVariant, the bridge calls root.navigateTo(page) directly instead of Q_ARG(str, ...), which would match nothing and fail silently. Page ids map to QML files:

home, media_room, media_player, obd, obd_home, obd_diagnostics, sensor_home,
settings, phone_mirror, android_auto, sensors, car, download, clock
# settings sections for open_settings:
displaySettings, mediaSettings, obdSettings, accessoriesSettings, deviceSettings, about

Example consumer: dev/tests/drive_dashboard_editor.py drives the whole dashboard editor (place, bind, drag, resize, options, save, edit, duplicate, delete, draft rescue, hot reload; ~40 assertions, ~3 min) under Xvfb (xvfb | visible | offscreen modes), writes screenshots to dev/screenshots/output/editor/, cleans up its test-dash*.json dashboards, and exits 1 on any failed assertion. The other scripts in dev/tests/ are stand-alone hardware checks: test_dtc.py / clear_dtc.py (python-obd against /dev/rfcomm0) and test_album_art_colors.py.

MCP Servers

dev/mcp_server.py (octave-perf) and dev/mcp_benchmark.py (octave-benchmark) are FastMCP servers that let a coding agent such as Claude Code drive OCTAVE through the command server. Both need pip install mcp in the venv and the app running with --profile; every tool just sends a JSON action to 127.0.0.1:9876.

Setup

pip install mcp                       # in the venv; not in requirements.txt
python main.py --profile              # or: python -m dev.main_dev --profile for the simulator
python dev/mcp_server.py              # stdio MCP server; normally launched by the agent from .mcp.json

.mcp.json (gitignored) declares octave-perf and octave-benchmark with the absolute path of this machine's venv/bin/python, plus -rob and -zion variants pointing at the other machines' checkouts — the tree is Dropbox-synced, so each machine has entries for the others that fail to spawn locally. That is expected; use the unsuffixed pair.

Performance Profiling

backend/perf_monitor.py (gitignored) — Python backend only.

python main.py --profile

setup_perf_profiling() in main.py creates PerfMonitor(csv_path, log_path) writing dev/perf/logs/perf_<YYYYMMDD_HHMMSS>.csv and .log, registers it as the perfMonitor context property, starts the command server, then applies backend/perf_patches.py (method instrumentation for the media, audio-analyzer, Spotify, OBD, IMU, gesture, ESP32 and settings managers) if the file is present — otherwise it logs a warning and continues.

What is measured

MetricMethodThreshold
Event-loop latencyA zero-interval QTimer probe; samples kept in a 300-entry ring buffer with p50/p95/p99/maxavg < 5 ms green, < 16 ms yellow (WARN), otherwise red (STUTTER)
GIL contention_GILProbe thread sleeps 10 ms and records how late it wakesHigher jitter = a Python thread holding the GIL
Per-slot timing@timed_slot decorator and PerfMonitor.begin() / end(label)Slots with p95 > 2 ms are reported as slow (detailed report lists p95 > 1 ms)
CPU / RSS / threadspsutil (optional import) and threading.active_count()—

Outputs

  • Terminal: a colour-coded [PERF] line refreshed every second; slow slots every 5 s.
  • CSV: columns timestamp, loop_avg_ms, loop_p50_ms, loop_p95_ms, loop_p99_ms, loop_max_ms, gil_avg_ms, gil_p99_ms, cpu_pct, mem_mb, threads.
  • Perf log: plain text with OK / WARN / STUTTER tags and slow-slot details.
  • QML HUD: perfMonitor.summaryText.
  • Command server: get_metrics, get_detailed_report, get_slot_timings.

Manual instrumentation

from backend.perf_monitor import timed_slot, PerfMonitor

@timed_slot
def my_expensive_slot(self):
    ...

t = PerfMonitor.begin()
... # code to measure
PerfMonitor.end(t, "my_section")

The C++ build has no profiling flag; use the UI watchdog log lines and a native profiler.

Video stories (README / demo clips)

python -m dev.screenshots.stories --list
python -m dev.screenshots.stories                          # all stories

Launches the dev app with its own settings profile (dev/screenshots/profile/, so demos never touch your real config), drives it over the command server (navigation, media, sim_*) and records with record_start / record_stop: a GUI-thread QTimer calls root.grabWindow() per frame and pipes raw RGBA into ffmpeg -c:v libx264 -crf 18 (keep fps ≤ 30; 1280x720 at 30 fps drops no frames on a desktop GPU). Each story yields <story>.mp4, an 800 px animated .webp at 15 fps (the README asset), a palettegen .gif and the requested stills under dev/screenshots/output/stories/, plus manifest.json. Stories are step lists in stories.py (("nav", page), ("settings", section), ("wait", s), ("still", name), ("rec", name) / ("stop",), ("media", action), ("sim", action, args)) registered in STORIES: tour, drive, media, settings.

python -m dev.screenshots.optimize <png|mp4> --width N --out frontend/assets/readme rescales (lanczos) and recompresses with ffmpeg, then pngquant if installed. Keep animated assets under ~3 MB. The same operations are the run_story, record_*, sim and optimize_assets MCP tools.

How to Add New Features (Parity Workflow)

Every feature lands in both backends in the same change set for desktop functionality; mobile-only code lives behind #ifdef Q_OS_ANDROID / Q_OS_IOS in C++ and needs no Python mirror. The sequence from CLAUDE.md:

  1. Pick the leading backend — usually C++ for performance-sensitive work, Python for quick iteration — and implement it there.
  2. C++ manager: add src/managers/foo.h / foo.cpp (a QObject with Q_PROPERTY, Q_INVOKABLE, signals; log through a QLoggingCategory), list both files in CMakeLists.txt's qt_add_executable, instantiate in src/main.cpp and ctx->setContextProperty("fooManager", &fooManager).
  3. Python manager: add backend/foo.py with the same class name, mirroring every property / invokable / slot / signal as PySide6 Property / Slot / Signal with the same names and types; get_logger(__name__) for logging; instantiate in main.py and register under the same context-property name. Use get_app_data_dir() for storage (matches SettingsManager::getAppDataDir()) so JSON files are shared on disk.
  4. Settings: add the key with its default to both SettingsManagers in the same commit (C++ defaults table + Q_PROPERTY + save_xxx; Python _default_settings + Property + Signal + save_xxx slot), and to the settings registry if it should appear in the Quick Panel.
  5. QML: build the view in frontend/; every new fooManager.bar() binding must resolve on both backends before it ships (grep the QML for the symbol and check both). Settings pages go under frontend/settings/. Gauges and dashboards follow docs/GAUGE_AUTHORING.md.
  6. Dev mode / tooling: if the feature depends on hardware, add a mock in dev/ and register it in dev_runtime.py; add command-server actions and MCP tools if an agent should be able to drive it.
  7. Verify both: cmake --build build -j, QT_QPA_PLATFORM=offscreen pytest tests/ (or at least python -c "import main"), then run each backend against the QML.
  8. Wiki: update the manager page and Signals & Slots Reference, the Settings Reference for new keys, and rebuild the search index. Stale docs are treated as worse than missing docs.
  9. If parity genuinely cannot land now (e.g. a C++-only library), gate the QML with typeof fooManager !== "undefined", write a TODO/ file for the missing half and say so in the PR.

Testing & Linting

Minimal automation, by choice
OCTAVE ships a headless smoke suite under tests/ and a ruff configuration in pyproject.toml; both run in CI on every push and PR to main. The suite catches import-time crashes, a broken start-up path and drift in a few load-bearing invariants; behaviour is still tested manually and on hardware. The menu of tests we would add next, ordered by value, is TODO/future-tests.md.

Linter (ruff)

[tool.ruff]: line length 120, target py310, excludes venv dev dist build build-android tools wiki. [tool.ruff.lint] selects E, F, W, E722, B (bugbear, incl. B904 raise-from) and UP (pyupgrade); ignores E501 (long lines), E402 (imports after the sys.path twiddling in main.py), F401 (re-exports / conditional imports), B008 (function call in default arg, a common Qt pattern) and UP007; per-file E402 ignores for main.py and tests/*.

source venv/bin/activate
ruff check .                        # full ruleset (advisory)
ruff check . --select E722,F821     # the two rules CI enforces

CI pins ruff==0.15.10; a newer local ruff may report rules the pinned one does not.

Smoke test suite (21 tests)

  • tests/conftest.py sets QT_QPA_PLATFORM=offscreen and QT_QUICK_CONTROLS_STYLE=Basic as defaults, puts the repo root on sys.path and provides a session-scoped qapp.
  • tests/test_smoke.py: 16 parametrised import tests (one per backend module, including backend.phone_mirror, backend.android_auto, backend.dashboard_manager); QApplication initialises headlessly; the quadratic volume curve is pinned (to_linear(50) == 0.25, clamping); SettingsManager, AudioAnalyzer and NetworkManager construct with HOME / XDG_CONFIG_HOME / APPDATA redirected to a temp dir; DashboardManager discovers the built-in presets in frontend/dashboards/presets/ (so a preset added on the C++ side without its JSON breaks the test) and round-trips duplicate → save → delete with the built-in protected.
  • tests/test_boot.py: launches python main.py offscreen with OCTAVE_SMOKE_BOOT=1 and asserts it is still alive after 12 s with no Traceback in its output — added because "a removed no-op slot once broke boot while every unit-level check passed".

Hardware-bound managers (OBD, ESP32, BerryIMU, Gesture, PhoneMirror, AndroidAuto) are imported but never instantiated; MediaManager is excluded because QAudioOutput hangs without an audio backend. There are no C++ unit tests; the C++ tree is validated by compiling it and by qmllint over the shared QML.

Manual testing workflow

  1. Dev mode: python -m dev.main_dev for rapid iteration with the simulator and keyboard controls; --profile to script it.
  2. Profile mode: python main.py --profile and watch loop latency / GIL jitter; run dev/docs/perf_test_plan.md through the MCP server before and after a change that touches a hot path.
  3. UI-driving scripts: dev/tests/drive_dashboard_editor.py for the editor; write new ones against the find_item / click / drag actions.
  4. Both backends: run the C++ binary (./build/octave) and the Python backend against the same QML; --debug on either for verbose logs.
  5. Hardware: the Orange Pi 5 Plus head unit in the Jeep is the reference for OBD, IMU, gesture, ESP32 and phone-mirror changes (the aarch64 AppImage exists for it); the Galaxy Tab S6 / S22 Ultra are the Android targets named in TODO/android-cpp-port.md.
  6. Before tagging: cmake --build build -j and QT_QPA_PLATFORM=offscreen pytest tests/; CI then builds every platform on a v* tag.

Continuous Integration

.github/workflows/build.yml has four always-on jobs and a tag-gated release matrix (full detail on the Building page):

  • lint — ruff 0.15.10 on Ubuntu 22.04 / Python 3.11: full ruleset advisory, E722 + F821 blocking.
  • test — the 21-test headless suite with requirements.txt installed.
  • cpp-compile-check — Debug CMake/Ninja build of the C++ tree against Qt 6.7.3, then qmllint over frontend/ failing only on critical entries, so a C++ or QML break cannot sit on main until the next tag.
  • phone-server — rebuilds the phone-server jar from source (JDK 21) and checks the committed jar carries the same class and version string; hash mismatch is a warning.
  • cpp-build-windows / cpp-build-macos / cpp-build-linux / cpp-build-linux-arm64 / cpp-build-android — Release builds and installers, only on v* tags or manual dispatch, each gated on lint + test.
  • release — attaches the five installers to a single GitHub Release on a version tag.
