Dev Mode Setup & Usage

Dev mode provides simulated vehicle data and keyboard controls for testing without a physical OBD-II adapter.

# Launch dev mode
python -m dev.main_dev

The dev/ directory is gitignored and fully isolated from production code. Dev mode:

  • Replaces OBDManager with MockOBDManager
  • Adds a KeyboardController exposed to QML as devKeyboardController
  • Sets devMode = true as a QML context property
  • Loads dev/DevMain.qml with keyboard handler overlay
  • Adds DevToolsManager for screenshots and diagnostics

Mock OBD Manager

dev/mock_obd_manager.py

The MockOBDManager provides the same Signal interface as the real OBDManager but generates simulated data based on keyboard input and physics modeling.

Signal Compatibility

Emits all 87+ OBD signals identical to the real manager: rpmChanged(float), speedMPHChanged(float), coolantTempChanged(float), etc. Plus all connection status signals. QML code works identically with both.

Simulation Features

  • Physics-based RPM/speed: Throttle input drives RPM, which drives speed through gear ratios
  • Gear simulation: 6 gears with realistic ratios, manual shifting via Q/R
  • Temperature modeling: Coolant and oil temp rise with engine load, cool at idle
  • Fuel consumption: Fuel level decreases proportional to load
  • Scenario presets: Cold start (low coolant, rich fuel), overheating (high temps, low voltage), low fuel

Key Methods

set_throttle(percent)    # 0-100 throttle input
set_brake(percent)       # 0-100 brake input
rev_engine(percent)      # Quick throttle blip
toggle_engine()          # Engine on/off
upshift() / downshift()  # Gear changes
simulate_cold_start()   # Preset scenario
simulate_overheating()  # Preset scenario
simulate_low_fuel()     # Preset scenario
reset_to_normal()       # Reset all values

Screenshot Capture

Uses Qt's grabWindow() for cross-platform screenshots (works on Wayland and X11):

MCP Server for Remote Control

dev/mcp_server.py

The MCP (Model Context Protocol) server lets an AI agent (like Claude Code) remote-control OCTAVE for automated testing.

Setup

# Install MCP dependency
pip install mcp

# Start OCTAVE with command server enabled
python main.py --profile

# In another terminal, start the MCP server
python dev/mcp_server.py

How It Works

  AI Agent (Claude Code)
       |
       v
  MCP Server (dev/mcp_server.py)
       |  TCP socket (127.0.0.1:9876)
       v
  Command Server (backend/command_server.py)
       |  QMetaObject.invokeMethod
       v
  OCTAVE Managers (media, settings, OBD, etc.)

Available MCP Tools

ToolArgumentsDescription
ping()-Check if OCTAVE is running
navigate(page)page nameNavigate to a specific page (home, media_room, obd, settings, etc.)
go_back()-Navigate back in the stack
go_home()-Return to home screen
list_actions()-List all available actions

Plus media controls (next_track, toggle_play, etc.), Spotify controls, OBD controls, and settings manipulation tools. See dev/mcp_server.py for the full list.

Benchmark Tool: dev/mcp_benchmark.py provides automated benchmark sequences that the MCP server can run for repeatable performance testing.

backend/perf_monitor.py

Launch with Profiling

python main.py --profile

Output Formats

  • Terminal: Color-coded live metrics every 1 second (overwrites line). Slow slots reported every 5 seconds.
  • CSV file: Machine-readable metrics log for spreadsheet analysis. Columns: timestamp, loop_avg_ms, loop_p50_ms, loop_p95_ms, loop_p99_ms, loop_max_ms, gil_avg_ms, gil_p99_ms, cpu_pct, mem_mb, threads.
  • Perf log file: Human-readable plain text log with health tags (OK/WARN/STUTTER) and slow slot details.
  • QML HUD: summaryText property for on-screen display

Command Server (TCP)

backend/command_server.py

A TCP server on 127.0.0.1:9876 that accepts JSON commands for remote control. Only active when --profile is passed.

Protocol

// Client sends JSON + newline:
{"action": "next_track"}

// Server responds with JSON + newline:
{"ok": true, "result": null}

// With arguments:
{"action": "navigate", "args": {"page": "media_player"}}

// Error response:
{"ok": false, "error": "Unknown action: foo"}

Action Categories

The command server dispatches 40+ actions organized by category:

  • App: ping, list_actions
  • Performance: get_metrics, get_detailed_report, get_slot_timings
  • Navigation: navigate, go_back, go_home, get_current_page, list_pages
  • Media: next_track, previous_track, toggle_play, pause, toggle_mute, toggle_shuffle, set_volume, get_media_status, get_track_info, skip_tracks
  • Spotify: spotify_toggle_play, spotify_next, spotify_previous, spotify_status
  • OBD: obd_status, obd_reconnect
  • Settings: get_all_settings, toggle_setting, set_bool_setting, set_numeric_setting, set_string_setting, and list_* variants
  • UI driving: find_item (geometry + effective visibility of any QML item by objectName, popups included), list_items (prefix match), get_prop / set_prop, call (invoke a no-arg method such as forceActiveFocus), click (x, y) and drag (x1, y1, x2, y2, steps) — synthetic mouse events delivered through the window's normal event path, so MouseArea drag thresholds and Flickable behave as they would for a finger. Closed popups leave the item tree, and pages pushed via navigate are not destroyed on go_home, so tests should prefer the visible instance (the server does) and scroll targets into view before clicking.

Example consumer: dev/tests/drive_dashboard_editor.py drives the whole dashboard editor (place, bind, drag, resize, options, save, edit, duplicate, delete, draft rescue, hot reload) under Xvfb and exits non-zero on any failed assertion.

Navigation Bridge

The NavigationBridge class provides thread-safe QML navigation. Commands from the TCP handler thread are dispatched to the GUI thread via QMetaObject.invokeMethod with QueuedConnection.

Video stories (README / demo clips)

python -m dev.screenshots.stories [tour|drive|media|settings] --visible launches the dev app with its own settings profile, drives it over the command server (navigation, media, the OBD simulator's sim_* actions) and records the window with the command server's record_start / record_stop (a GUI-thread grabWindow() per frame piped into ffmpeg, so it works on Wayland, X11 and Xvfb). Each story yields an MP4, an 800 px animated WebP and a GIF plus stills under dev/screenshots/output/stories/; python -m dev.screenshots.optimize rescales and recompresses assets for frontend/assets/readme/. The same operations are MCP tools (run_story, record_start, sim, optimize_assets). Details in dev/docs/SCREENSHOTS.md.

How to Add New Features

OCTAVE follows a consistent pattern for every feature. Here is a step-by-step guide:

  1. Create a Manager class in backend/:
    Inherit from QObject. Define Signals for state changes, Properties for QML binding, and Slots for QML-callable methods. Use get_logger(__name__) for logging.
  2. Add settings if needed:
    Add defaults to _default_settings in backend/settings_manager.py. Add a Property + Signal + save_xxx Slot. Optionally register in SETTINGS_REGISTRY for Quick Panel support.
  3. Register in main.py:
    Instantiate the manager, call engine.rootContext().setContextProperty("myManager", manager). Wire up any cross-manager signal connections.
  4. Create QML view in frontend/:
    Access the manager directly: myManager.someSlot(), bind to properties. Add navigation in BottomBar.qml or the appropriate menu.
  5. Add settings UI if needed:
    Create a settings section in frontend/settings/ and register it in the settings menu visibility system.
  6. Add dev mode support:
    If the feature uses hardware, create a mock manager. Register it in dev/main_dev.py. (The Python backend is desktop-only; mobile/Android support lives in the C++ backend behind #ifdef Q_OS_ANDROID, not in Python.)
  7. Add to command server (optional):
    Add actions in backend/command_server.py dispatch method. Add MCP tools in dev/mcp_server.py.
  8. Test manually:
    Run in dev mode (python -m dev.main_dev) and production mode (python main.py). Test on target platform if using hardware.

Testing & Linting

Minimal automation: OCTAVE ships with a headless smoke test suite under tests/ and a ruff linter configured in pyproject.toml. Both run in CI on every push and PR to main. Most testing is still manual — the smoke suite only catches import-time crashes and basic manager instantiation.

Linter (ruff)

Ruff is configured in pyproject.toml under [tool.ruff] with a conservative rule set: pycodestyle (E, W), pyflakes (F), bare-except detection (E722), bugbear (B), and pyupgrade (UP). Initial ignores cover long lines (E501), out-of-order imports (E402), and unused imports (F401) since the existing codebase has known patterns for each.

# Run ruff locally
source venv/bin/activate
ruff check .

# Check only critical rules (bare except + undefined names)
ruff check . --select E722,F821
Critical rules are enforced in CI: E722 (bare except) and F821 (undefined name) are hard failures in the lint job. The full ruff ruleset runs in warn-only mode (|| true) — existing long lines and style noise are tracked but don't block merges. Broaden enforcement as the codebase cleans up.

Smoke Test Suite

The tests/ directory contains a minimal pytest suite that proves:

  • Every backend manager module imports cleanly (no syntax errors, no import-time crashes)
  • QApplication can initialize headlessly under QT_QPA_PLATFORM=offscreen
  • Hardware-free managers (SettingsManager, AudioAnalyzer, NetworkManager) can be constructed without touching the developer's real config directory

Hardware-bound managers (OBD, ESP32, BerryIMU, Gesture, PhoneMirror, AndroidAuto) are imported but not instantiated — instantiation would probe for hardware and is not safe on headless runners. MediaManager is also excluded because QAudioOutput hangs without a real audio backend.

# Run smoke tests locally
source venv/bin/activate
QT_QPA_PLATFORM=offscreen pytest tests/ -v

Continuous Integration

The .github/workflows/build.yml workflow has three always-on jobs and a tag-gated release matrix:

  • lint — runs ruff on Ubuntu 22.04 (Python 3.11). Triggered on every push/PR to main.
  • test — runs the headless pytest smoke suite on Ubuntu 22.04. Triggered on every push/PR to main.
  • cpp-compile-check — configures and builds the C++ tree with Qt 6.7.3 on Ubuntu 22.04, then runs qmllint over frontend/ and fails on any QML error. Triggered on every push/PR to main, so a C++ or QML break cannot sit on main until the next release tag.
  • cpp-build-windows / cpp-build-macos / cpp-build-linux / cpp-build-android — CMake + Qt 6 release builds (.exe zip, .dmg, AppImage, .apk). Gated on lint + test passing, and only run on version tags (v*) or manual workflow_dispatch.
  • release — publishes every artifact to a single GitHub Release when the trigger is a version tag.

Manual Testing Workflow

  1. Dev mode testing: Use python -m dev.main_dev for rapid iteration with simulated OBD data and keyboard controls
  2. Profile mode: Use python main.py --profile to verify no performance regressions (watch event-loop latency, GIL jitter)
  3. MCP automation: Use the MCP server for repeatable test sequences (navigate pages, change settings, verify state)
  4. Cross-platform: Test on Windows, macOS, and Linux. Use python main.py --debug for verbose logging when debugging platform-specific issues.
  5. Hardware testing: Test with physical OBD adapter, ESP32 volume knob, BerryIMU, and gesture sensor when making changes to those subsystems
  6. Build testing: Build the C++ tree (cmake --build build -j) and run the headless smoke suite (QT_QPA_PLATFORM=offscreen pytest tests/) before tagging; CI then builds every platform on a v* tag

Debug Mode

python main.py --debug

Enables DEBUG level logging, creates octave-debug.log (10MB, 2 backups) with full stack traces and verbose output from all modules.
