What This Page Covers

OCTAVE is a C++ / Qt 6 program with a QML user interface. You do not need a car, an OBD adapter or any other hardware to work on it: the app carries a simulated car that you drive from the keyboard, and it behaves like the real one all the way down to the adapter.

This page takes you from a fresh clone to that running build, then through the tests and the checks a change has to pass. After that it describes the tools for driving the app from a script, measuring its performance and taking screenshots. It gets more technical as it goes.

How to build installers and how to build for Android or the browser is on the Building page. How the app is put together is on the Architecture page.

From Clone to a Running App

  1. Install the build requirements: CMake, Qt 6, a C++17 compiler and TagLib. The Building page and BUILD.md list the packages for each platform.
  2. Configure a Debug build. Debug matters: it is what switches on the developer tooling and the tests. 
    cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
  3. Build. Give -j a number. A bare -j starts as many compilers as it likes and can run a desktop out of memory. 
    cmake --build build -j8
  4. Run it with the simulated car. 
    ./build/octave --dev
    The app opens as usual, connected to a simulated 2003 Jeep, with a "DEV MODE" banner on top. On Windows and macOS the QML files have to be copied next to the executable first: see Building.
  5. Drive. Click the window so it has the keyboard, then use the keys below. Open the OBD section to watch the gauges follow.
KeyWhat it does
W or UpFull throttle while held
S or DownFull brake while held
SpaceA quick rev
EEngine on / off
Q / RShift down / up
1 to 6Pick a gear
F1 / F2 / F3Cold start / overheating / low fuel
F4Back to normal
TabShow or hide the overlay

--dev runs on your usual settings. To keep a dev run away from them, give it a folder of its own: ./build/octave --dev --config /tmp/octave-dev.

When something does not start, run with --debug and read the logs. Where they are is on the Architecture page.

Ways to Start the App

Everything is one binary. Flags decide what it starts. ./build/octave --help prints all of them and exits.

CommandWhat you getWorks in
octaveThe app as a driver sees it, on your real settings.Every build
octave --simThe app with the simulated car, simulated motion sensor and a few generated test songs, on a throwaway config that is deleted at exit.Every build
octave --headless --simThe same car with no window: the managers and the service API only. This is what a frontend author develops against.Every build (desktop and the Pi)
octave --devThe simulated car on your usual config, plus the overlay and the keyboard driving.Debug builds
octave --dev --profileThe above, plus the performance monitor and the command server with its actions for driving the UI. This is what the scripts and MCP tools start.Debug builds
octave --profileThe performance monitor and command server on the real car, with no simulator.Debug builds
octave --serviceThe app with the service API switched on, and none of the developer actions.Every build

Flags that go with them:

FlagWhat it does
--config DIRKeep settings, trips, dashboards and logs in DIR instead of the usual config folder. With --sim it replaces the throwaway config, so the run keeps its state.
--service PORT, --command-port PORTListen on another port than 9876. Use one when a second copy of the app is already running.
--debugDebug logging, also written to octave-cpp-debug.log.
--smokeStart, run for 5 seconds, exit 0. CI uses it to prove the app boots.
--dump-api DIRWrite the published API to DIR and exit. See Making a Change.

"Debug builds" means a build with the CMake option OCTAVE_DEV_TOOLS on. It is on by default only for a desktop -DCMAKE_BUILD_TYPE=Debug build. Any other build ignores --dev and --profile with a warning, so no released binary contains the overlay, the performance monitor or the actions that drive the UI. The simulator and the service API are in every build.

The service API, its ports, pairing and --service-bind are described under Service protocol.

The Simulated Car

The simulator does not feed made-up numbers to the gauges. It is a pretend ELM327 adapter (the small device that plugs into a car's diagnostic port) with a pretend car behind it. The real OBD code connects to it, sets it up, polls it and decodes its answers exactly as it does in a car. What you test with the simulator is the code that ships.

There are three ways to start it:

  • --sim or --dev on the command line.
  • In the app, open the OBD section, tap Connect and pick Simulated car. This works in every build, including releases, phones and the browser demo, and the car then drives itself. See Simulated Car on the OBD page.
  • From code: connect to the port sim://elm327.

What the simulated car is and does:

ThingBehaviour
The carA 2003 Jeep with the VIN 1J4FA49S03P123456. Throttle raises engine speed and road speed, the brake slows it, and the other readings follow from those.
ReadingsIt answers every reading OCTAVE knows and reports all of them as supported, so no gauge is hidden in a simulated run.
Trouble codesP0300 and P0420 are stored and P0300 is pending. Clearing them works, and they stay cleared until the app restarts.
Scenarioscold, hot, low_fuel, normal: the F1 to F4 keys.
The linkRealistic by default: each answer takes 35 to 70 ms, like Bluetooth, and 2 % of requests get no data. It can also be made instant, made to drop out for 2 to 4 seconds every 90 to 180 seconds, or unplugged until you plug it back in.
Motion sensorA simulated drive (heading, G-forces, roll, pitch, altitude) tied to the car's speed, so the sensors page, the compass and the 3D vehicle move. On from the start with --sim and --headless. A --dev window leaves it off so a real sensor on a Pi is not hidden.
MusicThe throwaway config of --sim comes with three generated 20-second songs, and the volume knob and gesture sensor switched off.

Because the simulated adapter answers at the speed of a real one, a page that asks for every reading at once (Live Data) takes a few seconds to fill. It does in the car too.

A program drives the car through the sim object of the service API: setThrottle, setBrake, setSpeed, scenario, dropoutNow, setLinkUp, setImu and so on. The full list is in the API reference. The object is experimental, and when no simulated car is running every call returns false and does nothing. With --dev --profile the command server also takes the same controls as sim_* actions (sim_throttle, sim_scenario, sim_link, sim_status ...), which the scripts use.

The tests are in tests/cpp/. They are built with the app in a Debug build (the CMake option OCTAVE_BUILD_TESTS) and need no display, no hardware and no car.

ctest --test-dir build -R tst_obdsim            # one, by name
build/tests/cpp/tst_obdsim                      # or run its program directly

Writing a test

  • Add tests/cpp/tst_yourthing.cpp (QtTest) and an octave_add_test() entry in tests/cpp/CMakeLists.txt that lists the source files it needs. There is no library of the managers: each test compiles what it uses.
  • Anything that touches settings must point XDG_CONFIG_HOME (and HOME) at a temporary folder first, so a test run never writes your real config.
  • Phone-mirror tests use tests/cpp/fake-adb.sh in place of adb. Its behaviour is set through FAKE_ADB_* variables, documented in the script.

Test against the release Qt

Releases and CI build with Qt 6.7.3. When the Qt on your machine is newer, a change can pass every local check and still fail there. The usual cause is QML that only the older parser rejects: a variable named native, for example, is a reserved word to 6.7 and fine to later versions, and one such line stops a QML file from loading at all. Before a push that matters, lint the QML you changed with a 6.7 qmllint: 

~/Qt/6.7.3/gcc_64/bin/qmllint -I frontend frontend/YourFile.qml

Better, build and run the tests against 6.7.3 itself:

aqt install-qt linux desktop 6.7.3 linux_gcc_64 -m qtmultimedia qtserialport qtconnectivity qt5compat qtquick3d qtshadertools qtquicktimeline
Q=~/Qt/6.7.3/gcc_64
cmake -S . -B build-qt673 -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH=$Q
cmake --build build-qt673 -j8
LD_LIBRARY_PATH=$Q/lib QT_PLUGIN_PATH=$Q/plugins QML2_IMPORT_PATH=$Q/qml ctest --test-dir build-qt673

Linting the Python tools

The app has no Python in it, but some tools around it are Python (the docs builders, the scripts in scripts/ and tools/). They are listed in requirements.txt and linted with ruff: 

python3 -m venv venv && venv/bin/pip install -r requirements.txt
venv/bin/ruff check .

Making a Change

Each feature of the backend is a manager: a C++ class in src/managers/ whose properties, methods and signals the QML and the service API both see. The Architecture page explains the pattern.

  1. Write the C++. For a new manager, add foo.h and foo.cpp to src/managers/ and list both in CMakeLists.txt (sources are listed by hand). Add it as a member of AppCore in src/appcore.h, then wire it and call expose("fooManager", &fooManager) in src/appcore.cpp. That one call makes it available to QML and to the service API under that name.
  2. Say who may call it. A manager declares the permission a paired device needs with Q_CLASSINFO("octave.scope", "..."). --dump-api refuses a manager without it.
  3. Write the QML in frontend/; settings pages go in frontend/settings/. Gauges and dashboards follow docs/GAUGE_AUTHORING.md.
  4. Make hardware testable. If the feature depends on a device, give it a simulated one in src/sim/, so it can be tried and tested without the device.
  5. Build, test, run. cmake --build build -j8 && ctest --test-dir build, then look at it with ./build/octave --dev. Add a test for any logic that can run without a screen.
  6. Regenerate the published API when a manager's properties, methods or signals changed, in the same commit: 
    ./build/octave --dump-api docs/api
venv/bin/python wiki/build_api_reference.py
npm --prefix sdk/typescript run generate
(cd sdk/go && go generate ./...)
    tst_apidocs and the SDK checks in CI fail otherwise. A change that breaks something already published also needs a new protocol version and a changelog entry; python tools/api/check_compat.py --draft lists what it sees. The rules are in docs/api/README.md.
  7. Update the wiki page for the feature and, for a new setting, the Settings Reference, then rebuild the search index with venv/bin/python wiki/build_search_index.py. How pages are written is in docs/WIKI_STYLE.md.

Three rules that are easy to miss:

  • Code for one platform goes behind #ifdef Q_OS_ANDROID, Q_OS_IOS or OCTAVE_WASM. New hardware access that is not guarded breaks the browser build.
  • The phone-server jar is committed. After changing anything under phone_server/src, rebuild it as Building describes and commit both.
  • After adding a reading to the parameter catalog, run python scripts/gen_gauge_param_docs.py. It rewrites the parameter table in docs/GAUGE_AUTHORING.md, and CI fails when the table is behind.

Continuous Integration

.github/workflows/build.yml runs four checks on every push and pull request to main:

JobWhat fails it
lintA ruff finding in the Python tools; a parameter table in docs/GAUGE_AUTHORING.md that is behind the catalog; a breaking change to the published API with no version bump and changelog entry (tools/api/check_compat.py).
cpp-compile-checkThe Debug build on Linux with Qt 6.7.3, any ctest test, or a critical qmllint finding in frontend/. Plain lint warnings do not fail it.
phone-serverThe phone-server jar no longer building from source, or the committed jar missing its main class or version string.
sdkThe TypeScript or Go client being out of step with docs/api/, or failing its own tests.

The release builds for Windows, macOS, Linux (x86_64 and arm64) and Android run only on a version tag (v*) or when started by hand, and only after lint and cpp-compile-check pass. On a tag, the release job attaches what they built to one GitHub Release, marked as a pre-release. The details are under GitHub Actions CI/CD on the Building page.

A second workflow, .github/workflows/wiki-pages.yml, builds the browser demo and publishes it with this wiki at robdegeorge.com/OCTAVE/ when a push to main touches the app, the wiki or the web frontends. Building the browser version yourself is under WebAssembly.

How the Tooling Fits Together

From here on the page is about the tools for driving and measuring the app. You can work on OCTAVE without any of them.

The problems that matter in a car are stutter, stalls and things that only break when the app is used the way a driver uses it. To find those repeatably, a script has to be able to do what a finger does, and something has to measure the app while it happens. The tooling has two halves:

HalfWhereWhat it is
Inside the appsrc/dev/, in the repositoryThe overlay, the keyboard driving, the performance monitor, and actions that tap, type, navigate and take screenshots. Compiled only into Debug builds, and idle without --dev or --profile.
Outside the appdev/, not in the repositoryPython scripts that send those actions over a socket: screenshot and video tools, performance loops, MCP servers, usability testers. The folder is gitignored, so a fresh clone does not have it. Everything described below that lives in dev/ is there only on the maintainers' machines.

            +-----------------+-----------------+

                    +---------+----------+
                    |   command server   |   in the app
                    +---------+----------+
                              |
        +---------------------+----------------------+
        |                     |                      |
   UI actions            performance            simulated car
   tap, type,            monitor                (sim_* actions)

The scripts in dev/ find the binary through dev/app_launch.py: the OCTAVE_BIN environment variable if set, otherwise build-desktop-<user>/octave, then build/octave. They start it with --dev --profile.

Command Server

The command server is a TCP socket on 127.0.0.1:9876. A client sends one JSON object per line and gets one JSON object per line back. It is the same socket as the service protocol, which every build has; a Debug build started with --profile adds the developer actions below to it. 

{"action": "ping"}
{"ok": true, "result": "pong"}

{"action": "navigate", "args": {"page": "media_player"}}
{"ok": true, "result": ...}

{"action": "foo"}
{"ok": false, "error": "Unknown action: foo"}

list_actions returns every action the running app takes. By group:

GroupActions

Navigationnavigate (page), go_back, go_home, get_current_page, list_pages, open_settings (section, and optionally tile, a card in it), list_settings_sections

Touching themclick, long_press, drag, wheel, type_text. These are real mouse and key events through the window, so drag thresholds and scrolling behave as they do for a finger.

Picturesscreenshot (path), set_window_size, set_dev_chrome (show or hide the overlay), record_start (path, fps), record_stop, record_status

Things to know when writing a script against it:

  • Every client gets its own connection thread, so a slow call on one connection does not hold up get_metrics on another.
  • A call that needs the user interface waits for it for up to 30 seconds, then returns an error instead of hanging.
  • Navigation and the sim_* controls are queued and answer at once; give the app a moment before reading the result back.
  • A closed popup leaves the screen's item tree, and a page you navigated away from may still exist. Find the visible one, and scroll a target into view before clicking it.
  • Your own app may already be on 9876. Start a second copy with --command-port and a --config of its own.

Performance Profiling

--profile (Debug builds) starts the performance monitor. It prints one coloured [PERF] line a second in the terminal and writes the same numbers to dev/perf/logs/perf_<date>_<time>.csv and .log in the checkout.

MeasuredHowHow to read it
Event-loop latencyHow late a 5 ms timer fires on the user-interface thread. Reported as average, p50, p95, p99 and max for each second.Average under 5 ms is fine (green, OK). Under 16 ms is a warning (yellow, WARN). Above that, longer than one frame at 60 Hz, it shows as stutter (red, STUTTER).
Thread jitterA background thread sleeps and records how late it wakes. The CSV columns are gil_avg_ms and gil_p99_ms.High values mean the machine is short of CPU, not that one function is slow.
Time in a functionFunctions marked with OCTAVE_PERF_SCOPE.One with a p95 above 2 ms is reported as slow.
CPU, memory, threadsFrom the operating system.CPU is per core, so it can pass 100 %.

The numbers depend on the machine and the build type. Compare a run only with a baseline taken on the same machine with the same build.

To time a function of your own, put a scope at its top:

#include "../util/perfscope.h"

void Foo::bar()
{
    OCTAVE_PERF_SCOPE("foo.bar");
    ...
}

The scope compiles to nothing in a build without the developer tooling and costs almost nothing when the app is not profiling. It is safe on any thread. get_slot_timings on the command server returns what the scopes measured. Scopes exist today on track changes, playback position updates, album-art colour extraction, the audio FFT, the OBD connection monitor, the volume knob's serial read and saving settings.

The Dev Overlay

--dev lays an overlay over the app (src/dev/qml/DevOverlay.qml): the "DEV MODE" banner, a readout of the simulated car and the list of keys. Tab hides it. Clicking the banner opens a small panel that takes a screenshot of the window. Pictures are saved to dev/screenshots/output/ in the checkout, with a manifest.json listing them.

MCP Servers

MCP is a protocol that lets a coding agent, such as Claude Code, call tools. Two servers in dev/ turn the command server's actions into such tools, so an agent can navigate the app, change settings, drive the simulated car and read the performance numbers without a person clicking.

ServerScriptTools
octave-perfdev/mcp_server.pyThe command server's actions one for one, plus scripted tests (idle baseline, track skipping, navigation, settings toggles, slider sweeps), recording and stories.
octave-benchmarkdev/mcp_benchmark.py --mcpBenchmarks of a page, a setting or a transition, a full suite, and saving a baseline and comparing against it. Without --mcp the script runs the suite once from the command line.
  1. Install the Python tools: python3 -m venv venv && venv/bin/pip install -r requirements.txt.
  2. Register the servers in .mcp.json at the root of the checkout, with the full path of venv/bin/python as the command and the full path of the script as its argument. The file is gitignored because those paths differ on every machine.
  3. Start the app with ./build/octave --dev --profile. The servers only talk to an app that is already running on port 9876.

Screenshots and Video Stories

The pictures and clips in the README are made by scripts in dev/screenshots/. They start the app themselves with the simulated car, drive it over the command server, and ask the app to capture its own window, which works the same on Wayland, X11 and a virtual display. Their own documentation is dev/docs/SCREENSHOTS.md.

CommandWhat it makes
python -m dev.screenshotsA still of every page and settings section, in dev/screenshots/output/. --visible uses a real window, --no-launch an app you started yourself with --profile, --size WxH another window size than 1280x720.
python -m dev.screenshots.stories --listThe list of stories. A story is a scripted sequence (go here, wait, press this, record) that yields an .mp4, an animated .webp and stills.

python -m dev.screenshots.readmeEvery README picture in one run: it fills a profile with mock drives, runs the stories, copies the results into frontend/assets/readme/ and checks that README.md points only at pictures that exist. check alone runs only that last step.
python -m dev.screenshots.optimize FILE --width N --out DIRA smaller, recompressed copy of a picture or clip.
  • The stories run on a settings profile of their own (dev/screenshots/profile/), so they never touch your config.
  • With no window to draw to, use a virtual display (xvfb-run; the tools pick it when it is installed). Qt's offscreen platform draws no shader effects, so tinted icons and blurred album art come out blank there.
  • Recording needs ffmpeg. Keep it at 30 frames a second or less.
  • tools/trips/make_mock_trip.py, which is in the repository, writes mock drives into the black box so Trip History has something to show without driving: one 28-minute drive by default, or --drives N --days D --drift thermostat|alternator|lean|none for a history with a part wearing out. Run it with OCTAVE closed.

AI Usability Testers

dev/ux/ has AI agents use the app the way a person does, to find where the screens confuse or slow people down. Each tester plays a kind of user and is given a goal in plain words ("mute the sound", "find out if the car has trouble codes"). It sees only a screenshot with a numbered tag on every control, and can only tap, long-press, swipe, scroll and type. The script around it then checks from the app's own state whether the goal was really reached. Every run gets its own copy of the app on its own port and config, so runs can go in parallel.

CommandWhat it does
venv/bin/python dev/ux/run.pyRuns the testers through a local vision model in Ollama. -t picks tasks, -p personas, -m the model, --parallel N and --repeat N as named. Tasks and their success checks are in dev/ux/tasks.json.
venv/bin/python dev/ux/audit.pyA sweep by rule, with no model: tap targets under 56 px, overlapping tap areas, controls with no text or icon, screens with more than 35 controls.
venv/bin/python dev/ux/backlog.pyCombines the latest run and audit into one list of evidence to triage.

The cycle is: run, triage, fix one thing, run the same tasks again and see whether more testers succeed or need fewer taps. See dev/ux/README.md.

Deferred Work: the TODO Folder

TODO/ holds one markdown file for each piece of work that was scoped and then put off on purpose. Each is written so that someone can pick it up cold: its status, why it is parked, the files involved, what has to happen first, and a recommended order. TODO/README.md is the index, ordered from quick wins to new subsystems, with the effort and the device each plan needs.

These are plans, not descriptions of how the app works. Check a plan against the code before acting on it, and delete the file when the work is done.

Why It Is Built This Way

  • Dev mode is a flag on the real binary. --dev builds every manager exactly as a normal start does and puts a simulated adapter underneath. Nothing in the OBD code is replaced, so what you test is what ships.
  • The simulator is in every build; the UI-driving tools are not. A frontend author can download a release and run octave --headless --sim without building anything. The actions that tap and type on the screen have no place in a car, so only Debug builds contain them.
  • A socket, not a test framework inside the app. The app is driven from outside over JSON lines, so a script, a coding agent and a person at a terminal all use the same channel, and a test is repeatable from one commit to the next.
  • The app takes its own screenshots. Capturing the window from inside Qt works the same on Wayland, X11 and a virtual display, gives the same window size every time, and can hide the overlay first. Tools that capture from outside break when the display system changes.
  • The outside half is not in the repository. The scripts in dev/ are tied to the maintainers' machines and change daily. The in-app half is committed because the build has to list it.
  • The 5 ms timer. The performance monitor measures a timer that should fire every 5 ms. A timer with no interval would keep the event loop spinning, use a whole core and spoil the CPU figure it sits next to.
  • Tests cover logic; people and scripts cover the screen. The suite holds what can be proven without a display: start-up, the OBD code against the simulator, the rules that were once broken in the car. How a screen feels is checked on a screen.
