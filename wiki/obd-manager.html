Overview

The OBDManager class in backend/obd_manager.py provides real-time vehicle diagnostics via the OBD-II protocol. It connects to an ELM327-compatible adapter (USB, Bluetooth, or WiFi), monitors over 80 engine parameters, and supports diagnostic trouble code (DTC) reading and clearing.

The C++ peer, src/managers/obdmanager.cpp with src/managers/elm327protocol.cpp, exposes the same API and is what the Android build uses (OBD over Bluetooth). The Python backend is desktop-only.

Connection Flow

The connection process is entirely non-blocking, using a QThread worker pattern:

  1. Startup: A single-shot 50ms timer (_startup_timer) defers the initial connection from the constructor
  2. Device scan: _scan_for_devices() checks for available serial ports (platform-specific patterns)
  3. Port check: _check_port_exists() verifies the configured port is present
  4. Worker creation: An OBDConnectionWorker is created and moved to a QThread
  5. Blocking connection: The worker calls obd.Async() on its thread
  6. Result handling: Signals deliver the result back to the main thread:
    • CAR_CONNECTED: Sets up watchers, starts data polling, begins connection monitor
    • ELM_CONNECTED: Adapter found but no vehicle; schedules retry
    • Failed: Emits error status, schedules auto-reconnect
  7. Auto-scan: 2 seconds after successful connection, scan_vehicle() runs to detect supported parameters

Threaded Connection Worker

The OBDConnectionWorker class runs the blocking obd.Async() call in a separate QThread to avoid freezing the UI: 

class OBDConnectionWorker(QObject):
    connectionComplete = Signal(object, object)  # (connection, status)
    connectionProgress = Signal(int, str)        # (progress, message)
    connectionError = Signal(str)

    def do_connect(self):
        connection = obd.Async(
            portstr=self._port,
            fast=self._fast_mode,
            timeout=self._timeout,
            delay_cmds=0,  # MAXIMUM SPEED
            protocol=self._cached_protocol
        )
        status = connection.status()
        self.connectionComplete.emit(connection, status)

The worker is wired up via Qt's thread affinity pattern:

self._worker = OBDConnectionWorker()
self._worker.set_params(port, fast_mode, timeout, cached_protocol)
self._worker_thread = QThread()
self._worker.moveToThread(self._worker_thread)
self._worker.connectionProgress.connect(self._on_connection_progress)
self._worker.connectionComplete.connect(self._on_connection_complete)
self._worker.connectionError.connect(self._on_connection_error)
self._worker_thread.started.connect(self._worker.do_connect)
self._worker_thread.start()

Port lifecycle (C++): never leave a dead port open

On Linux an rfcomm node whose remote is gone (adapter unpaired, engine off) keeps POLLIN set while read() returns 0 bytes. QSerialPort has no "readable but empty ⇒ disconnected" handling, so an open port leaves a read notifier armed in the worker thread's event loop that spins at 100 % of a core between commands -- with no OCTAVE frame on the stack, which is why guards inside sendCommand() cannot fix it. (The 100 ms pacing inside sendCommand() applies only to waits that returned no bytes; a chunk that arrived without the > prompt yet is followed up immediately, otherwise every PID cost an extra 100 ms.) Measured on the Orange Pi: ~20,000 ppoll+read pairs per second; fixed in 0404f7b). The C++ worker therefore calls releasePort() (close + delete) on every init-failure path, including "Connected to adapter, no vehicle response", and treats 50 consecutive empty reads during polling as a lost connection. The passive scanner reopens the port only every 10 s. If obd-worker ever shows up hot in top -H again, check whether an rfcomm fd is still held (ls -l /proc/<pid>/fd | grep rfcomm) before reading any loop. The Python backend (pyserial, blocking reads with its own timeouts) does not have this failure mode.

Speed Optimizations

OCTAVE applies several optimizations for faster OBD communication:

Protocol Caching
After a successful connection, the protocol name is cached in _last_successful_protocol. On reconnect, this is passed to obd.Async() to skip the slow auto-detection phase. The cache is cleared on I/O errors (errno 5) since the rfcomm link may have dropped.

Device Discovery

The _scan_for_devices() method runs on a 10-second timer and checks platform-specific paths:

PlatformScanned Paths
WindowsAll COM ports via serial.tools.list_ports (filters for Bluetooth/OBD/ELM/USB keywords)
macOS/dev/tty.OBD*, /dev/tty.Bluetooth*, /dev/cu.OBD*, /dev/tty.usbserial*, /dev/tty.*ELM*
Linux/dev/rfcomm*, /dev/ttyUSB*, /dev/ttyACM* (ttyS* excluded as false positives)

When a new port matching the configured port appears, an automatic connection attempt is triggered. The availablePortsChanged signal notifies QML of discovered ports.

Auto-Reconnect

Auto-reconnect is configurable via SettingsManager's obdAutoReconnectAttempts (0 = disabled, 1-10 = max attempts). The backoff schedule is linear: 2s, 4s, 6s, 8s, 10s max. 

delay = min(10, 2 + (self._connection_attempts * 2))
QTimer.singleShot(int(delay * 1000), self._start_connection)

After max attempts, the system falls back to passive device scanning. A _force_stop_reconnect flag prevents reconnect attempts during shutdown.

Data Watchdog

A watchdog timer checks every 5 seconds whether data callbacks have been received in the last 30 seconds. If no data arrives despite having active watchers, the connection is considered stale and an automatic reconnect is triggered: 

self._data_watchdog_timer = QTimer()
self._data_watchdog_timer.setInterval(5000)
self._data_watchdog_timer.timeout.connect(self._check_data_watchdog)
# ...
self._data_watchdog_timeout = 30.0  # seconds without data

For efficiency, only one watcher callback is wrapped with the watchdog timestamp update (preferably RPM, as it is typically always enabled). This avoids overhead on every single parameter callback.

Watcher System

The _setup_watchers() method registers OBD parameter callbacks based on user settings. Each parameter is checked against SettingsManager: 

def _setup_watchers(self):
    commands_to_watch = self._get_all_commands()
    for param, (command, callback) in commands_to_watch.items():
        should_watch = self._settings_manager.get_obd_parameter_enabled(param, default_enabled)
        if should_watch:
            self._connection.watch(command, callback=callback, force=True)

When OBD parameter settings change, _refresh_watchers() is called (connected to obdParametersChanged). It stops the connection, unwatches all, re-sets watchers, and restarts -- without a full reconnection.

Callback Pattern

All parameter callbacks follow the same pattern:

def _update_coolant(self, r):
    if not r.is_null():
        self._coolant_temp = float(r.value.magnitude)
        self.coolantTempChanged.emit(self._coolant_temp)

The r.is_null() check prevents emitting signals for empty/error responses. Values are extracted via r.value.magnitude (python-obd uses the Pint units library).

Vehicle Scanning

The scan_vehicle() slot queries the vehicle for all supported Mode 01 PIDs and updates the UI with a terminal-style output via scanOutputChanged. Scan results are persisted via SettingsManager's save_supported_obd_parameters() for future reference.

Scanning runs automatically 2 seconds after a successful connection: 

QTimer.singleShot(2000, self.scan_vehicle)

Diagnostics (DTC)

OBDManager supports reading and clearing Diagnostic Trouble Codes. DTC operations use thread-safe internal signals forwarded to public signals:

Internal SignalPublic SignalPurpose
_emitDtcCodesdtcCodesChangedList of DTC tuples [(code, description), ...]
_emitDtcCountdtcCountChangedNumber of DTCs found
_emitMilStatusmilStatusChangedCheck Engine Light (MIL) on/off
_emitDtcClearResultdtcClearResultSuccess/failure of DTC clear (bool, message)
_emitFreezeFramefreezeFrameChangedFreeze frame DTCs

A _diagnostic_mode flag pauses the async polling loop during DTC operations. A separate synchronous connection (_diagnostic_sync_conn) is used for diagnostic commands to avoid conflicts with the async watcher system. A threading lock (_diagnostic_mode_lock) protects the mode flags on rapid menu switching.

Cancellation handshake: enter_diagnostic_mode sets _diagnostic_mode_transitioning = True under the lock, releases it to do blocking I/O (connection.stop() plus a 200 ms sleep), then re-checks the flag. If exit_diagnostic_mode runs in that window and clears the flag, enter_diagnostic_mode bails out and restores async polling — this is how rapid menu switches are cancelled mid-transition rather than racing to completion.

elm327_protocol.py

backend/elm327_protocol.py is a pure-Python module (no I/O) that handles ELM327 command formatting, response parsing, and PID decoding. It is used primarily by the Android variant but is platform-independent.

ELM327 Initialization Sequence

INIT_COMMANDS = [
    (b"ATZ\r",  1.5),   # Reset (needs long timeout)
    (b"ATE0\r", 0.5),   # Echo off
    (b"ATL0\r", 0.3),   # Linefeeds off
    (b"ATS0\r", 0.3),   # Spaces off
    (b"ATH0\r", 0.3),   # Headers off
    (b"ATAT2\r", 0.3),  # Aggressive adaptive timing (fastest)
    (b"ATSP0\r", 0.5),  # Auto protocol
]

PID Table

The PID_TABLE dictionary maps (mode, pid) tuples to (name, signal_name, decoder_func, num_bytes). Decoder functions handle the raw byte math for each PID: 

# RPM: ((A * 256) + B) / 4
def _rpm(a):
    return round((a[0] * 256.0 + a[1]) / 4.0, 1)

# Coolant Temp: A - 40
def _offset40(a):
    return float(a[0] - 40)

# Percentage: A * 100 / 255
def _pct(a):
    return round(a[0] * 100.0 / 255.0, 1)

# Speed: A * 0.621371 (km/h to mph)
(1, 0x0D): ("Speed", "speedMPHChanged", lambda a: round(a[0] * 0.621371, 1), 1)

ResponseBuffer

The ResponseBuffer class accumulates bytes from the ELM327 until a complete response (terminated by > prompt) is available. It includes a 4KB safety limit to prevent buffer overflow from corrupted data.

Protocol logging

A failed OBD session can be reconstructed from the logs. Python: the OBD manager drives the adapter through python-obd, whose obd.* loggers are attached to OCTAVE's handlers by setup_logging(); with --debug every write: b'010C\r' / read: ... pair lands in octave-debug.log, and its errors always reach octave-error.log. C++: the octave.elm327 category logs TX/RX lines (response truncated to 200 chars, with the round-trip time) from OBDConnectionWorker::sendCommand, a WARNING when a command gets no response within its timeout, and in ELM327Protocol adapter error responses, unparseable responses, short responses and decoder failures. On Android the Java BLE bridge (OctaveOBDBridge) queues its connection / service-discovery / error lines and the same 50 ms poll that drains notifications forwards them as [BLE] ... INFO/WARNING lines in octave-cpp.log, so a BLE drop in the car is in the file the Diagnostics card exports. Debug-level lines need --debug (see the logging section of Architecture).

Unified Adapter API

The OBD settings page renders pixel-identically on every OS. All platform variation (BLE on Android, rfcomm bind on Linux/Pi, COM enumeration on Windows, paired-list on macOS) lives inside the manager — never in QML — and is exposed through a single shape both backends implement.

Slot / PropertySignatureDescription
availableAdaptersproperty: listList of {name, identifier, kind} maps. kind is one of ble, serial-rfcomm, serial-usb, com, tty, serial.
availableAdaptersChangedsignal(list)Emitted alongside availablePortsChanged with the rich shape.
scan()Trigger a discovery sweep — paired-list on Android, paired+/dev-glob on Linux, QSerialPortInfo on Windows. Alias of refresh_ports.
connect_to_adapter(identifier: str)One-shot connect entry point. Classifies the identifier (MAC vs /dev path vs COM), saves it, runs rfcomm bind on Linux when given a MAC, then calls force_connect. The QML calls this for both adapter-row taps and the manual-entry "Go" button.
platform_hint() -> strReturns "linux" / "macos" / "windows" / "android" / "ios". The QML uses this only to pick a hint string under the entry field — never for structural branching.
connectionLogLineAppendedsignal(str)One-line-at-a-time live log. The settings page binds this into the Connection Log card so users see rfcomm bind failures, BLE state transitions, etc. without needing adb logcat or a terminal.
Linux/Pi: automatic rfcomm bind

When connect_to_adapter receives a MAC on Linux, the manager runs rfcomm bind 0 <mac> 1 itself before opening the resulting /dev/rfcomm0 node. If the rfcomm binary is missing, fails with permission errors, or the user doesn't belong to the bluetooth group, the failure reason and a suggested fix are pushed to connectionLogLineAppended. The user can always bypass auto-bind by entering /dev/rfcomm0 directly after a manual sudo rfcomm bind.
