Overview

OBDManager provides real-time vehicle data over the OBD-II port through an ELM327-compatible adapter. It lives in src/managers/obdmanager.{h,cpp}, talks ELM327 directly, and is registered as the QML context property obdManager. On desktop an OBDConnectionWorker owns a serial port or direct RFCOMM transport on its own thread; on Android the same class switches (behind #ifdef Q_OS_ANDROID) to a BLE GATT link provided by the Java helper android/src/org/octave/app/OctaveOBDBridge.java.

The QML (OBDMenu, OBDHome, OBDDiagnostics, HomeOBDView, the OBD settings page and the gauge/dashboard system) sees the same signals, slots and properties on every platform. Where the desktop and Android paths differ, this page says so explicitly.

Connection Flow

The main-thread lifecycle is driven by four QTimers created in the constructor:

TimerIntervalPurpose
m_startupTimer50 ms single-shotDefers the first scan + connection attempt out of the constructor so app startup is not blocked.
m_deviceScannerTimer10 sPassive port discovery while disconnected; stopped once connected.
m_portChangeTimer1 s single-shotDebounces obdBluetoothPortChanged from settings into one reconnect().
m_dataWatchdogTimer5 sStale-connection detection (30 s without data).
  1. Startup: the 50 ms timer fires onStartupTimer(): scan for ports, start the 10 s scanner, call startConnection().
  2. Guard: a mutex-protected m_isConnecting flag drops re-entrant attempts ("Already connecting -- skipping"). cleanupConnection() clears the flag, because the attempt it abandons has its initComplete disconnected and would never clear it. Before 2026-10-03 a reconnect() during an attempt left OBD stuck in "Connecting" with no worker. The abandoned worker logs connect to X abandoned (superseded by a newer connect) on octave.elm327. The attempt counter increments and the UI gets connectionStatusChanged("Connecting"), connectionStatusDetailChanged("Attempt N..."), connectionProgressChanged(10).
  3. Port check: checkPortExists(). Unix: the device file exists; Windows: the port is listed by QSerialPortInfo::availablePorts(); Android: the configured string matches the MAC regex ^[0-9A-Fa-f]{2}(:[0-9A-Fa-f]{2}){5}$. A missing port emits "Device Not Found", devicePresenceChanged(false), and schedules auto-reconnect.
  4. Worker: progress 15, "Found <port>, connecting...", then a fresh OBDConnectionWorker is moved to a new QThread and its started signal invokes the blocking connect (next section). On Android the manager skips this and calls startAndroidConnection() instead.
  5. Result (delivered to the main thread by queued signals):
    • Success: m_connected = true, attempts reset, "Connected" + progress 100, polling starts, the data watchdog starts, the device scanner stops, and scan_vehicle() is queued 2 s later.
    • Adapter but no vehicle: "No Vehicle" / "Connected to adapter, waiting for vehicle...", progress 50, then auto-reconnect scheduling. (The init worked but the RPM probe returned nothing.)
    • Failure: "Connection Failed" / "Could not connect to OBD adapter", progress 0, auto-reconnect scheduling.
  6. Post-diagnostic retries: when m_reconnectingAfterDiagnostic is set, a failed attempt retries every 2 s up to 3 times even if auto-reconnect is disabled in settings.

Threaded Connection Worker

OBDConnectionWorker owns the serial port for the whole session

The worker is a long-lived object: it creates the QSerialPort (or an RfcommSocket for an rfcomm:// port) on its own thread (38400 baud, 8N1, no flow control, 4 KB read buffer), runs the init sequence, then keeps polling, answering DTC requests and running scans until doDisconnect(). The thread is named obd-worker so it is attributable in top -H. Every request from the main thread is a QMetaObject::invokeMethod(..., Qt::QueuedConnection), every result comes back as a queued signal:

connectionLost(reason)onWorkerConnectionLost"Disconnected", watchdog stopped, scanner restarted, auto-reconnect scheduled.

ELM327 Init Sequence and Vehicle Probe

The init table is ELM327Protocol::initCommands() (timeouts in ms): 

ATZ    1500 ms   # reset (needs the long timeout)
ATE0    500 ms   # echo off
ATL0    300 ms   # linefeeds off
ATS0    300 ms   # spaces off
ATH0    300 ms   # headers off
ATAT2   300 ms   # aggressive adaptive timing
ATSP0   500 ms   # auto protocol

Desktop (sendInitSequence()): each command is sent with sendCommand() and its own timeout, except that ATZ gets at least 5 s: a bound /dev/rfcommN opens instantly, but the kernel only brings the Bluetooth link up on the first write, so the reset's answer also includes the link-up (about 2.2 s for a NEXAS in the Jeep). An ATZ reply without ELM only logs a warning (clones omit the banner), and the function always returns true. The real test is the vehicle probe that follows: one 010C (RPM) request that waits up to the connection timeout (m_timeout, 5 s unless set_connection_timeout() changed it). An empty reply, NO DATA or UNABLE means "adapter but no vehicle": the worker releases the port and emits initComplete(false, "Connected to adapter, no vehicle response"). Note the header comment claims ELM327Protocol::defaultPids() lists "the 16 most common"; that list is not used by the worker -- the poll list is built from consumer demand by buildPidsToWatch() (see Which PIDs Get Polled).

Android: the same table is walked by a single-shot QTimer (sendNextAndroidInitCommand() / onAndroidInitStep()): each command is written, the timer armed with that command's timeout, and the next command sent when the timer fires regardless of whether a reply arrived. After ATSP0 the code sends 0100; while still connecting, each supported-PID bitmap whose bit 32 is set chains the next range (0120, 0140, 0160, up to 01C0) so the supported set covers the extended PIDs too. 2 s after 0100 it calls finalizeAndroidConnection().

Poll Loop and Pacing

startPolling() starts m_pollTimer (constructed with the worker as parent, so moveToThread() carries it along; before 2026-10-03 it stayed on the GUI thread and Qt refused to start it with “Timers cannot be started from another thread”) on the worker thread with interval 0 ms when obdFastMode is on (the default -- "poll as fast as possible") or 50 ms otherwise. Each tick (onPollTimer()) sends the next PID in round-robin order with a 500 ms timeout, parses it with ELM327Protocol::parseResponse() / decodePid(), and emits dataReceived. The ELM_VOLTAGE pseudo-PID (kElmVoltageKey) is special-cased: the tick sends ATRV instead and parses the "12.6V" text reply with parseElmVoltage() into elmVoltageChanged. Because sendCommand() blocks inside the tick, the effective rate is one PID per adapter round-trip.

sendCommand() clears the ResponseBuffer, logs TX, writes + flushes, then loops until timeoutMs:

  • waitForReadyRead(100) returned bytes with a complete >-terminated response: log RX with the round-trip time and return. Bytes without the prompt yet: loop again immediately ("productive read: the prompt is probably next, do not pace") -- pacing here cost 100 ms per PID because the ELM327 often sends the data and the prompt as separate chunks (ee5a23e).
  • Readable but zero bytes 50 times in a row: the port is dead (see next section) -- stopPolling(), releasePort(), connectionLost("Adapter stopped responding").
  • The port's error is cleared before every command (QSerialPort errors are sticky; before 2026-10-03, one transient error during rfcomm link-up made every later init command fail in the same millisecond). Only a fatal error (ResourceError, DeviceNotFoundError, PermissionError, NotOpenError) breaks out; anything else is cleared and the wait continues. onSerialError reports ResourceError / DeviceNotFoundError as connectionLost, and logs every error except TimeoutError on octave.elm327 at WARNING, alongside the port open result (INFO / WARNING), so a failed connect is visible without debug logging.
  • Every iteration that delivered no data sleeps out the remainder of 100 ms, so the loop never spins faster than ~10 Hz while waiting.

On timeout a WARNING is logged (octave.elm327) and whatever partial response the buffer holds is returned. refresh_values() simply queues one extra onPollTimer() tick.

Port Lifecycle: Never Leave a Dead Port Open

On Linux an rfcomm node whose remote is gone (adapter unpaired, engine off) keeps POLLIN set while read() returns 0 bytes. QSerialPort has no "readable but empty means disconnected" handling, so an open port leaves a read notifier armed in the worker thread's event loop that spins at 100 % of a core between commands -- with no OCTAVE frame on the stack, which is why guards inside sendCommand() alone cannot fix it. Measured on the Orange Pi with strace: ~20,000 ppoll+read pairs per second. Three commits on 2026-09-09 closed this in layers:

  • 953f85f: sleep out the remainder of the 100 ms wait instead of re-polling immediately, stop on a real port error, name the worker threads.
  • 5d76a03: apply the 100 ms floor to readable-but-empty polls too (the first guard only covered waitForReadyRead() returning false), and abandon a command after 50 consecutive empty reads.
  • 0404f7b: releasePort() (close + deleteLater + clear buffer) on every init-failure path -- open failure, init failure, and "Connected to adapter, no vehicle response" -- so nothing holds the port open while OCTAVE is not actively talking to a live adapter.

If obd-worker ever shows up hot in top -H again, check whether an rfcomm fd is still held (ls -l /proc/<pid>/fd | grep rfcomm) before reading any loop.

Linux/Pi: automatic rfcomm bind

startRfcommBind(): if any /dev/rfcomm0..7 already exists it is used as-is ("using existing", no check that it is bound to the same MAC -- surfacing the real open() failure was judged better than guessing). Otherwise it runs rfcomm bind 0 <mac> 1 (channel 1 is the hard-coded fallback; the adapter finder can discover a different channel), waits up to 1 s for the node to appear, and saves /dev/rfcomm0 as the active port so the worker opens the node, not the MAC. A missing binary, non-zero exit or missing node is reported to the connection log with a fix ("add user to bluetooth group, or run sudo rfcomm bind 0 <mac> once and enter /dev/rfcomm0"), and the status becomes "Error" / rfcomm bind failed -- see Connection Log. A missing binary is detected through QProcess::FailedToStart.

The bind never blocks the GUI thread: it is an async QProcess killed by a 5 s timer, after which the manager polls for the node every 100 ms. A timeout or crash counts as failure, and a newer connect_to_adapter() call supersedes an in-flight bind (its result is ignored). Once bound, force_connect() is called from the completion handler.

Direct Bluetooth (rfcomm://, Linux)

A port of the form rfcomm://<MAC> or rfcomm://<MAC>/<channel> (channel 1 by default) skips the bound /dev/rfcommN node and opens a Bluetooth Classic RFCOMM socket straight to the adapter. It needs no rfcomm bind (root), connects explicitly with a timeout and a real error (Host is down, Connection refused), and nothing else on the system (blueman) can release it underneath us. It came out of 2026-10-03 on the Pi: the NEXAS (classic SPP, channel 1) never connected through /dev/rfcomm0, but a raw socket reached it in about 1.1 s and the Jeep's ECU answered.

  • src/managers/rfcommsocket.{h,cpp}, class RfcommSocket (a QIODevice over an AF_BLUETOOTH socket; the three constants and sockaddr_rc are spelled out so the build needs no libbluetooth-dev). The worker picks it in doConnect() when RfcommSocket::isUrl(port) and otherwise calls openSerialPort(). Everything after that talks through m_io, whichever device is open. connectTo() waits up to max(10, timeout) s in 100 ms slices, so a reconnect can abandon it. An EBUSY (one link per channel, still held by the previous worker or by a process with /dev/rfcommN open) is retried every 250 ms for up to 3 s, since switching transports releases the old link on its own thread. A hang-up or failed read sets isBroken(), which sendCommand() turns into connectionLost. On other platforms connectTo() fails with only supported on Linux.
  • checkPortExists only validates the URL, since there is no node to look for. The passive device scan (every 10 s) retries a configured rfcomm:// adapter whenever we're not connected, connecting, closed or in diagnostic mode. The dongle is usually only powered with the ignition on, and while it's off the connect fails within a few seconds (Host is down).

Adapter Finder: Scan, Pair, Connect

OBDAdapterFinder (QML obdAdapterFinder, src/managers/obdadapterfinder.{h,cpp}, with BlueZ pairing in src/platform/bluezpairer.{h,cpp}) lets someone connect an adapter without knowing its MAC or pairing it in the OS first. The "Connect Bluetooth OBD2" button on the empty Parameter Cards page and "Find Bluetooth Adapters" in Settings → OBD → Adapters both open frontend/OBDAdapterSheet.qml, which starts a scan. Phase 1 of TODO/obd-adapter-discovery.md: the full flow runs on desktop Linux (Pi / Orange Pi included). On every other platform supported is false and the sheet lists obdManager.availableAdapters instead (the ports and paired devices the OS already knows), with an "OBD Settings" shortcut.

Startup never waits on BlueZ. The QtBluetooth objects (QBluetoothLocalDevice, the discovery agent, BluezPairer) are created only once org.bluez is owned on the system bus, a check the bus daemon answers at once (isServiceRegistered, which never activates a service). A QDBusServiceWatcher creates them when BlueZ appears later. Creating them eagerly, as 0.9.5-rc1 did, made QBluetoothLocalDevice's constructor D-Bus-activate an org.bluez that never came up (BlueZ installed, no adapter or bluetoothd stopped), which blocked the GUI thread for about 45 s before the window appeared. Without BlueZ, bluetoothOn is false and startScan() reports "Bluetooth is not available: the Bluetooth service is not running."

  1. Scan (startScan()): QBluetoothDeviceDiscoveryAgent, Classic + LE, 15 s. Unnamed devices (BlueZ names them after their address) are dropped. likelyObd is set when the name matches the common ELM327 adapters (OBDII / OBD2 / V-LINK / OBDLink / Vgate iCar / Veepeak / BAFX / Konnwei / NEXAS / LELink / Viecar / ...) or a BLE device advertises one of the ELM327 BLE services (FFF0, FFE0/FFE1, ISSC). The sheet shows likely adapters only, sorted by signal, with "Show All Devices (N)" for the rest. A dual-mode adapter keeps every mode seen during the scan (the NEXAS reports Classic once and LE-only afterwards).
  2. Pair (connectAdapter(address), Classic only): the scan stops, then BluezPairer registers its own org.bluez.Agent1 on the system bus and calls Device1.Pair(). BlueZ sends the PIN request to the agent of the client that called Pair(), so OCTAVE answers it and the desktop's own PIN dialog never appears. On AuthenticationFailed it retries with the next PIN: 1234, 0000, 6789, 1111. Already-paired devices skip this step.
  3. Trust: Device1.Trusted = true, so the adapter reconnects later without being asked again. If pairing failed but the adapter answered (refused PIN, timeout), it is still trusted and the connection is tried anyway, because some adapters (the NEXAS) accept RFCOMM from a trusted host without pairing. If that connection also fails, the pairing error is shown.
  4. Channel: an SDP lookup for the Serial Port service (QBluetoothServiceDiscoveryAgent, 8 s); channel 1 if it finds nothing.
  5. Hand-off: obdManager.connect_direct(mac, channel) (see Direct Bluetooth), and add_obd_saved_adapter(name, url) so the saved chip shows the adapter's name. The finder then follows connectionStatusChanged. It ignores the Disconnected that force_connect() emits first, then reports Connected to <name>, ... isn't answering, turn the ignition on (No Vehicle), or the failure.

BLE-only devices are listed but greyed out on desktop ("Bluetooth LE adapters aren't supported on this device yet"): the desktop OBD worker has no GATT transport. BLE ELM327 adapters connect on Android through OctaveOBDBridge. Signals and properties are listed in the signals & slots reference.

Auto-Reconnect and Passive Scanning

scheduleAutoReconnect() reads obdAutoReconnectAttempts from settings (0 = disabled, which is the default; 1-10 = max attempts). The backoff is linear and capped: 

int delay = qMin(10, 2 + m_connectionAttempts * 2);   // 4 s, 6 s, 8 s, 10 s, 10 s ... after attempt 1, 2, 3, 4, ...
QTimer::singleShot(delay * 1000, this, &OBDManager::startConnection);

When auto-reconnect is disabled, or the attempt count reaches the maximum, the manager emits "Auto-reconnect disabled" / "Max retries reached. Scanning..." and falls back to the 10 s device scanner. For serial device nodes, passive scanning re-attempts a connection when the discovered port list changes and the configured port is in it. Direct rfcomm:// connections are an exception: they retry on every 10 s scan while disconnected, even when the configured attempt limit is zero. For a serial-node connection, an adapter that is plugged in but has no vehicle response is tried once at startup and then left alone until the user taps Connect, changes the port, or the port disappears and reappears. A m_forceStopReconnect flag set by close() blocks all scheduling during shutdown.

While connected, a lost link is detected by the worker's serial errors and the empty-read detector (Poll Loop), which report connectionLost.

Data Watchdog

On desktop, every 5 s while connected and at least one PID is being watched, the watchdog compares the last-data timestamp with now. More than 30 s without a timestamp refresh triggers status "Stale Connection" / "No data received, reconnecting...", the connection is cleaned up, the attempt counter reset, and a fresh attempt starts 100 ms later. 

m_dataWatchdogTimer.setInterval(5000);
static constexpr int DATA_WATCHDOG_TIMEOUT_MS = 30000;

The timestamp is refreshed whenever decoded base or extended values arrive. This detects missing callbacks or values, not every kind of vehicle failure. The watchdog is paused on entering diagnostic mode so DTC work cannot trigger a false reconnect. On Android it is never started; the BLE path has its own per-PID watchdog (below).

Extended PIDs 0x61 and up (37 values from 23 PIDs)

The extended table adds values from PIDs 0x61–0xB2 beyond OCTAVE's 83 base commands. Several replies contain multiple values and support bits. They are decoded from one table, ELM327Protocol::extendedPidTable(): each value names its data bytes, any required support bit in byte A, and the minimum reply length. Values with a required support bit are skipped when that bit is clear. The mappings below describe the checked-in decoders, covered by decodeExtendedPid and everyExtendedParameterIsWired in tests/cpp/tst_elm327protocol.cpp; they are not a claim that every vehicle implements them. EGT 0x78/0x79, turbo RPM/temperature 0x74–0x76, exhaust pressure 0x73, DPF 0x7A–0x7C and the gear number in 0xA4 are not included.

Values reach QML through one signal, obdParameterChanged(paramId, value), instead of a signal per parameter; OBDParameterModel routes it into paramValues. Replies longer than one CAN frame are joined by parseResponseLines(). The vehicle scan reads the 0160-01C0 support bitmaps too, so it can report these PIDs. Boost pressure is absolute; subtract BAROMETRIC_PRESSURE for gauge boost.

Vehicle identity (VIN)

After a successful connect the manager attempts to read Mode 09 PID 02 once (desktop: OBDConnectionWorker::doReadVin() before polling starts; Android: the first poll slot) and expose vin, vehicleMake and vehicleModelYear with vinChanged; read_vin() reads it again. parseVin() accepts the CAN multi-frame reply and the five numbered pre-CAN messages. decodeVin() takes the make from the world manufacturer identifier (first 3 characters, about 120 entries, then a 2-character fallback) and the model year from position 10 (30-year cycle; an alphabetic position 7 selects 2010+). An unsupported or invalid VIN response leaves vin and vehicleMake empty and vehicleModelYear at 0. The OBD settings Connection card shows a Vehicle row when a VIN is known.

Which PIDs Get Polled

Polling is demand-driven: OCTAVE polls what is on screen, not a list of parameters switched on in settings. Every consumer registers the parameter ids it shows with obdManager.setParameterDemand(consumer, ids) (an empty list removes the consumer). The QML consumers are "dashboard" (the active dashboard's PIDs), "cards" (every supported PID while Parameter Cards is open), "home" (the Home screen OBD tiles), "editor" (the dashboard editor canvas), "settings" (the OBD settings parameter list while it is shown) and "carMenu" (RPM and SPEED for the 3D Jeep's engine and driveline while CarMenu is on screen).

The poll set is built by buildPidsToWatch():

  • Union of every consumer's ids. BerryIMU ids (PITCH, ROLL, HEADING, ...) and unknown ids are dropped.
  • Filtered to vehicleSupportedParameters once this session's scan produced a result (an unknown or empty result filters nothing).
  • A multi-value PID (0x61+) is polled when any of its signals is wanted.
  • Heartbeat: RPM is always polled (ELM_VOLTAGE when the car has no RPM), which keeps the data watchdog fed and the global RPM shift light working on every screen.

A second, low-priority list comes from setBackgroundDemand(consumer, ids): the same rules (OBDManager::backgroundPidsToWatch()) minus the heartbeat and minus anything already in the foreground. The worker polls one background PID after each full pass of the foreground list (plain round-robin over the background list when the foreground is empty), so a 40-PID sweep costs the live gauges one request per cycle instead of slowing every gauge to a crawl. The only consumer is the black box, which asks for every PID the vehicle scan found. Android interleaves the same way in pollNextAndroidPid().

Changes are debounced for 250 ms (one re-watch per page switch) and applied live, without a reconnect. A scan completing also re-applies the set, since the supported filter changed.

buildPidsToWatch() / applyPollList()

The rules themselves are the public static OBDManager::pidsToWatch(demand, vehicleSupported), which buildPidsToWatch() calls with the current state; tst_obdmanager pins them.

startConnection() hands the current QList<PidKey> (sorted by PID so the round-robin order is deterministic) to the worker before the thread starts. The debounce timer calls applyPollList(): while connected it rebuilds the list and queues OBDConnectionWorker::updatePidsToWatch(), which swaps it in place. On Android it calls rebuildAndroidPollList() (additionally filtered by the 0100 bitmap, falling back to ATRV) and restarts the response-driven chain if it had died. While disconnected the change applies to the next connection; in diagnostic mode it is deferred to the reconnect exit_diagnostic_mode() performs anyway.

The per-parameter obdParameters enable settings no longer drive polling. The keys are still read and written (enable_all_supported() / enable_scanned_parameters() keep working) so existing settings files stay compatible.

Black Box: Trip Recorder

TripRecorder (src/managers/triprecorder.{h,cpp}, QML context property tripRecorder) records every decoded OBD value of every drive, with its time, into a SQLite database (SQLite compiled in from third_party/sqlite/, no Qt Sql driver plugin involved), and writes each drive out as a CSV + JSON pair when it ends. It is the vehicle's black box: the pages on screen decide what is polled fast, the recorder makes sure everything the car supports is recorded at least slowly, and a power cut loses at most the last two seconds.

Data path

  • OBDManager::parameterSampled(paramId, value) fires once for every decoded reading (base PIDs, multi-value PIDs and ELM_VOLTAGE), keyed by the OBDParameterModel id. The recorder is its only consumer today; it never touches the 84 per-parameter signals.
  • On top of the on-screen demand, the recorder registers a background demand (setBackgroundDemand("blackbox", vehicleSupportedParameters), see Which PIDs Get Polled) so every PID the scan found is swept, one per pass of the foreground list. Off with the blackBoxSweepAll setting.
  • Readings are coalesced on the GUI thread (a value that has not changed is stored again only every 5 s, so a held value still shows as held) and handed to TripStore (src/managers/tripstore.{h,cpp}) on its own thread every 2 s or 1000 samples, one transaction per batch.
  • Trip boundaries: a trip starts on the first RPM > 0 reading (any reading when the scan says the car has no RPM PID) and ends after 2 min of RPM 0, 2 min without the adapter (a shorter dropout is logged as an event and does not split the trip), when recording is switched off, on "End trip" in the viewer, or at shutdown (shutdown() blocks until the files are written, before obdManager.close()). Within a trip, sample times are start + monotonic elapsed, so an NTP step on the head unit cannot fold the trace.
  • Events (disconnected / reconnected / connection_lost, mil, dtc, dtc_clear, trip_end with its reason) go into the same trip.

Vehicle Scanning

On desktop, scan_vehicle() runs automatically 2 s after a successful connection. The API is also callable directly, but the current QML has no manual scan button. It emits terminal-style lines through scanOutputChanged ([SCAN], [INFO], [OK] NAME, a ==== summary), progress through scanProgressChanged(pct, "Checking NAME..."), and finishes with supportedCommandsChanged(list) + scanCompleteChanged(list) + scanProgressChanged(100, "Found N supported parameters"). The list is persisted under the supportedOBDParameters settings key. The same list (base command names plus multi-value signal ids, in OBDParameterModel vocabulary) becomes this session's vehicleSupportedParameters and sets vehicleScanComplete (true even for an empty result); both reset on disconnect, connection loss and close(), and are never loaded from the persisted key, so they always describe the car connected right now. They drive the QML "supported by this vehicle" gate and filter the poll set.

  • Desktop: doScanVehicle() on the worker pauses polling, sends 0100, 0120, 0140, ... 01E0 (stopping at the first range whose bitmap does not set bit 32 = "next range supported"), collects the supported PID numbers with parseSupportedPids(), and builds the final result through supportedCommandNames(): base command names and extended value IDs whose PIDs are supported, plus ELM_VOLTAGE. An entirely empty bitmap result returns an empty list. Polling resumes afterwards.
  • Android: no worker, so scan_vehicle() answers from the supported-PID bitmaps read during connect (ELM327Protocol::supportedCommandNames(m_androidSupportedPids)), emitting the same [SCAN] / [INFO] / [OK] / [DONE] lines and completing through onWorkerScanComplete() (which clears m_isScanning and persists the list), answering from what connect already learned. An empty bitmap set reports No supported PIDs found. The automatic post-connect scan is still desktop-only (it hangs off onWorkerInitComplete). Android has no automatic scan report or QML scan button; the live poll list still uses the initializer's supported-PID bitmaps.

Android: BLE via OctaveOBDBridge

On Android the desktop worker is never created. startAndroidConnection() validates the MAC (missing/invalid gives "No MAC Address" / Enter your ELM327 MAC in OBD Settings, then tap Connect), resets the BLE state, and calls OctaveOBDBridge.connect(context, mac) through QJniObject. From then on a 50 ms QTimer (onAndroidBlePoll()) drains the bridge:

  1. pollLog() up to 50 lines per tick: W| lines become qCWarning(lcElm327) "[BLE] ...", I| lines qCInfo -- so a BLE drop in the car lands in octave-cpp.log and the Diagnostics export instead of only logcat (3858c5c).
  2. pollResponse() until empty: each notification chunk is fed to the same ResponseBuffer, and every complete >-terminated response goes to processAndroidResponse().
  3. stateCode(): only on a transition. 0 DISCONNECTED (log lastEvent, status Disconnected, reconnect if we were connected), 1 CONNECTING, 2 DISCOVERING (progress 50, Discovering services...), 3 READY (progress 70, Initializing ELM327..., start the init state machine after 500 ms), 4 ERROR (log lastError, BLE error, reconnect).

Inside the Java bridge: BluetoothAdapter.getRemoteDevice(mac) then connectGatt(ctx, autoConnect=false, callback, TRANSPORT_LE); on connect it runs service discovery and tries three vendor profiles in priority order -- ISSC Transparent UART (49535343-FE7D-..., separate notify/write characteristics; NEXAS, Vgate iCar Pro, OBDLink CX), FFF0 (FFF1 notify + FFF2 write, or a single read/notify/write FFF1; Konnwei, some BAFX), and FFE0/FFE1 (one characteristic both ways; HM-10 style clones). The first one with both roles wins; notifications are enabled through the CCCD descriptor and the state flips to READY. Writes use WRITE_TYPE_NO_RESPONSE when the characteristic allows it. Incoming bytes are queued in a ConcurrentLinkedQueue (GATT callbacks run on a Binder thread; the manager polls from the Qt main thread). Verified end-to-end on a NEXAS adapter over the FFF0 path (f1901d9).

Permissions (08e8245): on API 31+ connect() checks BLUETOOTH_CONNECT / BLUETOOTH_SCAN; if either is missing it casts the context to Activity, calls requestPermissions() (request code 7301) so the system dialog appears, sets the error "Requesting Bluetooth permission -- tap Allow, then tap Connect again", goes to state ERROR and returns false. Fresh installs (CI sideloads, Play builds) therefore get a working second tap instead of a silent SecurityException from connectGatt(). The same grant unlocks bondedDevices(), so the adapter list populates right after it. The older requestAndroidBluetoothPermission() (which wrestled Qt's QBluetoothPermission cache) has been removed.

Writes: writeAndroidBytes() drops data unless the last seen state is READY and chunks every write to 20 bytes (the default 23-byte ATT MTU minus 3). Init: the timer-driven sequence described above, then 0100 and a 2 s wait. Finalize: m_connected = true, Connected, progress 100, and rebuildAndroidPollList() builds the poll list: buildPidsToWatch() (consumer demand plus heartbeat, extended values included) intersected with the supported-PID bitmaps collected through PID C0 if the vehicle answered them (ELM_VOLTAGE always passes); an empty result falls back to ELM_VOLTAGE (ATRV) alone. Because connect chains 0120/0140/0160, requested PIDs at or above 0x21 (FUEL_LEVEL, CONTROL_MODULE_VOLTAGE, OIL_TEMP) survive the intersection and are polled. Polling is response-driven: pollNextAndroidPid() writes one request and arms a 500 ms single-shot watchdog; the next request goes out when a response is decoded or the watchdog fires. Ten consecutive watchdog fires (5 s stale) flush the response buffer. Reconnect after an unexpected DISCONNECTED/ERROR: up to 3 attempts, delay min(2000 * n, 10000) ms, counter reset on success.

What the Android path does not do

read_dtc, read_current_dtc, read_status, clear_dtc and read_freeze_frame go through invokeWorker(), which logs "no worker thread on this transport, ignoring" once per call and returns; refresh_values is likewise a no-op without a worker. enter_diagnostic_mode only stops the watchdog. The data watchdog does not apply (the BLE path has its own per-PID watchdog); the 10 s device scanner runs and is what refreshes the bonded-device rows.

ELM327 Protocol Module

src/managers/elm327protocol.{h,cpp} is pure protocol code (no I/O): the 83 PID entries (82 mode-01 commands plus ELM_VOLTAGE), the extended table, decoders, error tokens and public parsing helpers. The desktop worker, the Android path and the dev-mode simulator all use it; tests/cpp/tst_elm327protocol.cpp covers it without a vehicle.

PID table

Maps (mode, pid) to (name, signalName, commandName, decoder, expectedBytes); commandName is the established OBD command name (python-obd's vocabulary, e.g. COOLANT_TEMP, AMBIANT_AIR_TEMP), i.e. the settings key and the scan-result vocabulary. The decoder takes the data bytes after the 41 XX header: 

static double decRpm(const QVector<uint8_t> &a) {
    return std::round((a[0] * 256.0 + a[1]) / 4.0 * 10.0) / 10.0;
}
t[{1, 0x0C}] = {"RPM", "rpmChanged", "RPM", decRpm, 2};
t[kElmVoltageKey] = {"ELM Voltage", "elmVoltageChanged", "ELM_VOLTAGE", nullptr, 0};   // {0, 0}: "ATRV", text reply

The 16 wide-range O2 entries are generated in a loop (O2_S1_WR_VOLTAGE .. O2_S8_WR_VOLTAGE at 0x24-0x2B, O2_S1_WR_CURRENT .. O2_S8_WR_CURRENT at 0x34-0x3B, four data bytes each; the lambda ratio in bytes A/B is ignored and the voltage / current is decoded from C/D as (256C + D) × 8 / 65535 V and (256C + D) / 256 - 128 mA).

Accumulates bytes until a > prompt. It trims to the last 1 KB if it grows past 4 KB without a prompt (corrupt stream guard), splits the response on \r, and returns the last non-empty line that is not an AT echo and not OK.     for (int i = lines.size() - 1; i >= 0; --i)
        if (!lines[i].startsWith("AT") && lines[i] != "OK")
            return lines[i];
    return lines.isEmpty() ? QString() : lines.last();
}

Protocol Logging

A failed OBD session can be reconstructed from the logs (commit 86c8c3c). The octave.elm327 category logs TX/RX lines (response truncated to 200 chars, with the round-trip time) from OBDConnectionWorker::sendCommand, a WARNING when a command gets no response within its timeout, and in ELM327Protocol adapter error responses and unparseable responses at debug, short responses and decoder failures at warning. On Android the Java bridge's queued event/error lines are forwarded as [BLE] ... INFO/WARNING lines by the 50 ms poll. Debug-level lines need --debug (see the logging section of Architecture). The live in-app connection log is a separate, user-facing channel.

OBDParameterModel and IMU Parameters

frontend/OBDParameterModel.qml centralizes parameter values for gauges, cards and dashboards. A Connections { target: obdManager } block with one handler per base signal (84), plus onObdParameterChanged(paramId, value) for the extended values, writes into the model with updateParamValue(paramId, value); a second, guarded Connections on berryIMU (typeof berryIMU !== "undefined") does the same for PITCH, ROLL, HEADING, ALTITUDE, ACCEL_MAG, LATERAL_G, LONGITUDINAL_G and BARO_TEMP from the IMU's pitchChanged .. baroTempChanged signals (see Hardware Managers). The IMU values are ordinary parameters from that point on: any gauge can bind them, the PID picker lists them, demo mode sweeps them.

Coalesced writes (486a809): updateParamValue() only stores into _pendingValues and arms a one-shot 33 ms Timer; the timer folds the pending map into a fresh paramValues object with Object.assign. Replacing paramValues is what re-evaluates every gauge binding, and the IMU alone fires about 420 orientation/gauge signals per second (7 signals at 60 Hz), plus barometer updates -- copying the whole dictionary on each one pegged the QML thread at 100 % on an idle Orange Pi (V4 string allocation + GC churn, found with py-spy). Bindings now re-evaluate at most ~30 times a second and only while data arrives. hasParameter(id), getParamInfo(id), parameterInfo (with short titles for the home cards) and allParameters (the C++ ParameterCatalog: id, title, short title, unit, min, max, kind, decimals) are documented on the Gauges & Dashboards page.

Shift Light, Full-Screen Flash and Aura

The rules live in ShiftLightManager (src/managers/shiftlightmanager.{h,cpp}), fed by rpmChanged in main.cpp; the QML below only draws its activeFlag and lit. Its configuration is a list of flags stored as a JSON string under the rpm_flags setting and edited in the RPM settings popup inside frontend/OBDMenu.qml. Each flag is {rpmLow, rpmHigh, color, flash, flashSpeed, fullScreenFlash, fullScreenFlashOpacity, auraFlash, auraFlashOpacity, auraSpread} (new flags default to flash: false, flashSpeed: 100, fullScreenFlashOpacity: 0.5, auraFlashOpacity: 0.6, auraSpread: 0.18); the popup keeps the list sorted by rpmLow, keeps rpmLow <= rpmHigh and clamps ranges to rpm_max_rpm (default 8000). The manager migrates the old single-rpm format once on load to rpmLow = rpm, rpmHigh = rpm_max_rpm (the redline, not "no limit") and writes it back.

  • Active flag: the last flag (highest priority) whose [rpmLow, rpmHigh] range contains the current RPM, only while rpm_shift_light_enabled is on. activeFlag has every field filled in (defaults above; fullScreenFlashOpacity falls back to rpm_fullscreen_flash_opacity).
  • Flash: one C++ timer at the flag's flashSpeed toggles lit, so the card disc and both overlays flash in step; a newly active flag always starts lit.
  • Card indicator (HomeOBDView.qml): a disc on the RPM home card (rpm_show_on_home_card) coloured by the active flag, with glow (rpm_glow_size, rpm_glow_intensity), size (rpm_shift_light_size), colour transition (rpm_color_transition_speed), optional 800 ms pulse (rpm_pulse_enabled), dark while not lit.
  • Global full-screen flash (Main.qml, globalFullScreenFlash): a z: 999999 rectangle over the whole window in the flag colour at the flag's fullScreenFlashOpacity (fallback rpm_fullscreen_flash_opacity), visible while lit and the flag has fullScreenFlash; enabled: false so touches pass through.
  • Aura overlay (globalAuraFlash): the same trigger with auraFlash, but rendered as four edge gradients (top/bottom/left/right) that fade from the flag colour to transparent over auraSpread of the window (default 18 %) at auraFlashOpacity -- a perimeter glow that leaves the centre readable.

The manager re-reads every rpm_* setting whenever settingsManager.genericSettingChanged reports one, so editor changes apply live. Tests: tests/cpp/tst_shiftlightmanager.cpp.

Design Decisions

  • Two transports, one class. OCTAVE keeps the Android BLE path inside OBDManager behind #ifdef Q_OS_ANDROID rather than a subclass, so main.cpp, the signal dispatch table and the QML surface are identical on every platform (2d05676).
  • Bypass Qt Bluetooth on Android. Qt 6.7's QBluetoothPermission aggregator reports Denied on Android 16 even with every runtime grant present, and QLowEnergyController reads that cache before initialising the adapter. BluetoothAdapter.getRemoteDevice + connectGatt do not consult it, so a 400-line Java helper polled over JNI was cheaper and more reliable than fighting the framework (f1901d9). Polling at 50 ms instead of registering native JNI callbacks keeps the Java side free of Qt headers.
  • Three BLE profiles, priority ordered. ELM327 BLE clones ship ISSC, FFF0 or FFE0 firmware; trying all three at service-discovery time made one APK work with NEXAS, Vgate, Veepeak, Konnwei and HM-10 boards without a per-adapter setting.
  • The worker owns the port. QSerialPort must live on the thread that reads it, and blocking waitForReadyRead inside the worker is simpler than an async state machine; the price is that every request from the main thread is a queued invokeMethod. The 2026-09-09 spin fixes (above) are all consequences of that choice: a port left open is a live notifier in that thread's event loop.
  • Release the port on every failure. Rather than trying to detect a dead rfcomm remote, the rule is "nothing may hold the port open while we are not actively talking to a live adapter" (0404f7b). It is a policy, not a heuristic, so it holds for USB and Bluetooth alike.
  • Live poll-list swaps. The worker copies the poll list before the thread starts and updatePidsToWatch() swaps it live when demand changes, so a page switch changes polling without a reconnect.
  • One PID table, standard numbering. The decoders used to sit beside three hand-copied name maps that drifted from each other and from the standard PID numbers (mis-numbered PIDs, a 0x59 mix-up, 23 names that could never be polled). Giving PidEntry a commandName column and iterating the table everywhere (buildPidsToWatch(), the scans, the Android list, the dev simulator) made the one table the single reference, and tst_elm327protocol checks it without a vehicle.
  • Diagnostics pause polling. ELM327 adapters are half-duplex request/response devices; interleaving Mode 03/04 traffic with a running PID loop corrupts both. OCTAVE therefore stops live data during DTC work and does a full reconnect afterwards to restore a clean adapter state.
  • Auto-reconnect defaults to off. The scanner-driven passive mode reconnects when a port appears, which is what happens when a Pi boots before the adapter pairs; unbounded retries against an adapter with no vehicle just spin the port (see the spin bug). Users who want scheduled retries set 1-10 attempts. Direct RFCOMM connections also retry through the 10 s scanner.
  • Unified adapter API. The settings page used to branch on isAndroid; moving MAC/COM/tty classification and the rfcomm bind into the managers made the page render identically everywhere and gave the manager a single connect entry point to test.
  • Observability over logcat. The in-app connection log (542b446), the ELM327 transcript category (86c8c3c) and the BLE log forwarding (3858c5c) all exist because the head unit is in a vehicle where neither a terminal nor adb logcat is reachable -- failures must land in the files the Diagnostics card exports.
  • Coalesced model writes. OBDParameterModel buffers into a plain object and flushes at 30 Hz because the alternative -- one dictionary copy per signal -- was measured at 100 % of a core on the Orange Pi with the adapter unplugged (486a809). Needle animations only need ~30 updates a second anyway.
