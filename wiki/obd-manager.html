Overview

OBDManager provides real-time vehicle data over the OBD-II port through an ELM327-compatible adapter. It exists in both backends and is registered as the QML context property obdManager:

  • backend/obd_manager.py (Python, desktop only) drives the adapter through the python-obd library: obd.Async() owns the serial port, does protocol negotiation, and calls back into the manager for every watched PID.
  • src/managers/obdmanager.{h,cpp} (C++, every shipped binary) talks ELM327 directly: on desktop an OBDConnectionWorker owns a QSerialPort on its own thread; on Android the same class switches (behind #ifdef Q_OS_ANDROID) to a BLE GATT link provided by the Java helper android/src/org/octave/app/OctaveOBDBridge.java.

Both expose the same signals, slots and properties, so the shared QML (OBDMenu, OBDHome, OBDDiagnostics, HomeOBDView, the OBD settings page and the gauge/dashboard system) never knows which one is running. Where the two backends genuinely differ, this page says so explicitly.

Connection Flow

Both backends run the same main-thread lifecycle, driven by four QTimers created in the constructor:

TimerIntervalPurpose
_startup_timer / m_startupTimer50 ms single-shotDefers the first scan + connection attempt out of the constructor so app startup is not blocked.
_device_scanner_timer / m_deviceScannerTimer10 sPassive port discovery while disconnected; stopped once connected.
_port_change_timer / m_portChangeTimer1 s single-shotDebounces obdBluetoothPortChanged from settings into one reconnect().
_data_watchdog_timer / m_dataWatchdogTimer5 sStale-connection detection (30 s without data).
  1. Startup: the 50 ms timer fires _initial_connect() / onStartupTimer(): scan for ports, start the 10 s scanner, call _start_connection() / startConnection().
  2. Guard: a mutex-protected _is_connecting flag drops re-entrant attempts ("Already connecting -- skipping"). The attempt counter increments and the UI gets connectionStatusChanged("Connecting"), connectionStatusDetailChanged("Attempt N..."), connectionProgressChanged(10).
  3. Port check: _check_port_exists() / checkPortExists(). Unix: the device file exists; Windows: QSerialPortInfo::availablePorts() / serial.tools.list_ports; Android: the configured string matches the MAC regex ^[0-9A-Fa-f]{2}(:[0-9A-Fa-f]{2}){5}$. A missing port emits "Device Not Found", devicePresenceChanged(false), and schedules auto-reconnect.
  4. Worker: progress 15, "Found <port>, connecting...", then a fresh OBDConnectionWorker is moved to a new QThread and its started signal invokes the blocking connect (next section). On Android the C++ side skips this and calls startAndroidConnection() instead.
  5. Result (delivered to the main thread by queued signals):
    • Success: _connected = true, attempts reset, "Connected" + progress 100, polling starts, the data watchdog starts, the device scanner stops, and scan_vehicle() is queued 2 s later.
    • Adapter but no vehicle: "No Vehicle" / "Connected to adapter, waiting for vehicle...", progress 50, then auto-reconnect scheduling. (Python: python-obd status ELM_CONNECTED; C++: the init worked but the RPM probe returned nothing.)
    • Failure: "Connection Failed" / "Could not connect to OBD adapter", progress 0, auto-reconnect scheduling. Python additionally routes exceptions through connectionError to _on_connection_error(), which emits "Error" and clears the cached protocol when the message contains Input/output error or Errno 5.
  6. Post-diagnostic retries: when _reconnecting_after_diagnostic is set, a failed attempt retries every 2 s up to 3 times even if auto-reconnect is disabled in settings.

Threaded Connection Worker

Python: OBDConnectionWorker wraps obd.Async

The worker exists only to move python-obd's blocking constructor off the UI thread. It emits connectionProgress(20, "Initializing OBD adapter...") (or "Connecting with cached protocol..."), builds the connection, emits connectionProgress(80, "Checking connection status...") and hands the object back through connectionComplete(connection, status); any exception becomes connectionError(str). After the result is handled, _cleanup_worker_thread() quits the thread (2 s wait) -- the worker does not outlive the connection attempt, because obd.Async runs its own polling thread afterwards. 

class OBDConnectionWorker(QObject):
    connectionComplete = Signal(object, object)  # (connection, status)
    connectionProgress = Signal(int, str)        # (progress, message)
    connectionError = Signal(str)

    def do_connect(self):
        connection = obd.Async(
            portstr=self._port,
            fast=self._fast_mode,
            timeout=self._timeout,          # 5 s
            delay_cmds=0,                   # MAXIMUM SPEED
            protocol=self._cached_protocol  # skip auto-detect on reconnect
        )
        status = connection.status()
        self.connectionComplete.emit(connection, status)

The obd module itself is imported lazily (backend/lazy_import.py) because python-obd pulls in pint, which cost about 0.5 s on the Pi before Qt even started (commit ee5a23e).

C++: OBDConnectionWorker owns the serial port for the whole session

The C++ worker is a long-lived object: it creates the QSerialPort on its own thread (38400 baud, 8N1, no flow control, 4 KB read buffer), runs the init sequence, then keeps polling, answering DTC requests and running scans until doDisconnect(). The thread is named obd-worker so it is attributable in top -H. Every request from the main thread is a QMetaObject::invokeMethod(..., Qt::QueuedConnection), every result comes back as a queued signal:

dataReceived(signalName, value)onWorkerDataReceivedStamps m_lastDataReceived and dispatches to the matching parameter signal via m_signalDispatch (a QHash<QString, std::function> built once in buildSignalDispatch()).

scanProgress, scanComplete, scanOutputonWorkerScan*Forwarded; scanComplete also persists the list through save_supported_obd_parameters().

ELM327 Init Sequence and Vehicle Probe

The init table is identical in ELM327Protocol::initCommands() and elm327_protocol.INIT_COMMANDS (timeouts in ms / s): 

ATZ    1500 ms   # reset (needs the long timeout)
ATE0    500 ms   # echo off
ATL0    300 ms   # linefeeds off
ATS0    300 ms   # spaces off
ATH0    300 ms   # headers off
ATAT2   300 ms   # aggressive adaptive timing
ATSP0   500 ms   # auto protocol

C++ desktop (sendInitSequence()): each command is sent with sendCommand() and its own timeout; an ATZ reply without ELM only logs a warning (clones omit the banner), and the function always returns true. The real test is the vehicle probe that follows: one 010C (RPM) request with a 3 s timeout. An empty reply, NO DATA or UNABLE means "adapter but no vehicle": the worker releases the port and emits initComplete(false, "Connected to adapter, no vehicle response"). Note the header comment claims ELM327Protocol::defaultPids() lists "the 16 most common"; that list is not used by the worker -- the poll list is built from settings (see Which PIDs Get Polled).

C++ Android: the same table is walked by a single-shot QTimer (sendNextAndroidInitCommand() / onAndroidInitStep()): each command is written, the timer armed with that command's timeout, and the next command sent when the timer fires regardless of whether a reply arrived. After ATSP0 the code sends 0100, waits 2 s and calls finalizeAndroidConnection().

Python: python-obd performs its own ELM327 initialisation and protocol auto-detection inside obd.Async(); the table in elm327_protocol.py is reference only.

Poll Loop and Pacing (C++)

startPolling() starts m_pollTimer on the worker thread with interval 0 ms when obdFastMode is on (the default -- "poll as fast as possible, like delay_cmds=0") or 50 ms otherwise. Each tick (onPollTimer()) sends the next PID in round-robin order with a 500 ms timeout, parses it with ELM327Protocol::parseResponse() / decodePid(), and emits dataReceived. Because sendCommand() blocks inside the tick, the effective rate is one PID per adapter round-trip.

sendCommand() clears the ResponseBuffer, logs TX, writes + flushes, then loops until timeoutMs:

  • waitForReadyRead(100) returned bytes with a complete >-terminated response: log RX with the round-trip time and return. Bytes without the prompt yet: loop again immediately ("productive read: the prompt is probably next, do not pace") -- pacing here cost 100 ms per PID because the ELM327 often sends the data and the prompt as separate chunks (ee5a23e).
  • Readable but zero bytes 50 times in a row: the port is dead (see next section) -- stopPolling(), releasePort(), connectionLost("Adapter stopped responding").
  • Any real QSerialPort error other than TimeoutError breaks out; onSerialError reports ResourceError / DeviceNotFoundError as connectionLost.
  • Every iteration that delivered no data sleeps out the remainder of 100 ms, so the loop never spins faster than ~10 Hz while waiting.

On timeout a WARNING is logged (octave.elm327) and whatever partial response the buffer holds is returned. refresh_values() simply queues one extra onPollTimer() tick.

Port Lifecycle: Never Leave a Dead Port Open

On Linux an rfcomm node whose remote is gone (adapter unpaired, engine off) keeps POLLIN set while read() returns 0 bytes. QSerialPort has no "readable but empty means disconnected" handling, so an open port leaves a read notifier armed in the worker thread's event loop that spins at 100 % of a core between commands -- with no OCTAVE frame on the stack, which is why guards inside sendCommand() alone cannot fix it. Measured on the Orange Pi with strace: ~20,000 ppoll+read pairs per second. Three commits on 2026-09-09 closed this in layers:

  • 953f85f: sleep out the remainder of the 100 ms wait instead of re-polling immediately, stop on a real port error, name the worker threads.
  • 5d76a03: apply the 100 ms floor to readable-but-empty polls too (the first guard only covered waitForReadyRead() returning false), and abandon a command after 50 consecutive empty reads.
  • 0404f7b: releasePort() (close + deleteLater + clear buffer) on every init-failure path -- open failure, init failure, and "Connected to adapter, no vehicle response" -- so nothing holds the port open while OCTAVE is not actively talking to a live adapter.

If obd-worker ever shows up hot in top -H again, check whether an rfcomm fd is still held (ls -l /proc/<pid>/fd | grep rfcomm) before reading any loop. The Python backend (pyserial inside python-obd, blocking reads with its own timeouts) does not have this failure mode.

Results are de-duplicated and sorted. Only when the list changes does the manager emit availablePortsChanged(list) and availableAdaptersChanged(list of maps), and -- if not connected and the configured port is now present -- reset the attempt counter and start a connection; if the configured port is absent it emits "Device at X not found. Android adapter list is effectively empty
m_androidPermissionGranted is only ever set inside requestAndroidBluetoothPermission(), and nothing calls that function any more (the runtime permission request moved into the Java bridge in 08e8245). So listAndroidPairedDevices() returns nothing and the adapter rows on Android never populate; users type the MAC into the manual entry field, which is what the per-OS hint tells them to do.

Unified Adapter API

The OBD settings page renders identically on every OS. All platform variation (BLE on Android, rfcomm bind on Linux/Pi, COM enumeration on Windows, /dev/tty.* on macOS) lives inside the manager -- never in QML -- and is exposed through one shape both backends implement:

Names: Bluetooth · MAC, Bluetooth (bound) · /dev/rfcommN, USB ELM327 · /dev/ttyUSBn, Serial · COMn.
availableAdaptersChangedsignal(list)Emitted alongside availablePortsChanged with the rich shape.

connect_to_adapter(identifier: str)One-shot connect: trims, classifies, logs connect → <name> to the connection log, saves the identifier with save_obd_bluetooth_port() (and add_obd_saved_adapter() for MACs), runs the rfcomm bind on Linux when given a MAC, then calls force_connect(). The QML calls this for adapter-row taps, saved-adapter chips and the manual-entry "Go" button.
platform_hint() -> strC++: "windows" / "macos" / "linux" / "android"; Python: "windows" / "macos" / "linux". The QML uses it only to pick the hint string under the entry field, never for structural branching. (The QML also has an "ios" branch; neither backend returns it today.)
connectionLogLineAppendedsignal(str)One-line-at-a-time live log (added in 542b446). OBDHome keeps the last 40 lines, the settings page the last 60, both auto-scrolling. Linux/Pi: automatic rfcomm bind

ensureRfcommBound() / _ensure_rfcomm_bound(): if any /dev/rfcomm0..7 already exists it is used as-is ("using existing", no check that it is bound to the same MAC -- surfacing the real open() failure was judged better than guessing). Otherwise it runs rfcomm bind 0 <mac> 1 (channel 1 is the universal SPP channel for ELM327 clones), waits up to 1 s for the node to appear, and saves /dev/rfcomm0 as the active port so the worker opens the node, not the MAC. A missing binary, non-zero exit or missing node is reported to the connection log with a fix ("add user to bluetooth group, or run sudo rfcomm bind 0 <mac> once and enter /dev/rfcomm0"), and the status becomes "Error" / rfcomm bind failed -- see Connection Log. C++ detects a missing binary through QProcess::waitForStarted, Python through shutil.which.

Auto-Reconnect and Passive Scanning

_schedule_auto_reconnect() / scheduleAutoReconnect() reads obdAutoReconnectAttempts from settings (0 = disabled, which is the default; 1-10 = max attempts). The backoff is linear and capped: 

delay = min(10, 2 + attempts * 2)   # 4 s, 6 s, 8 s, 10 s, 10 s ... after attempt 1, 2, 3, 4, ...
QTimer.singleShot(delay * 1000, self._start_connection)

When auto-reconnect is disabled, or the attempt count reaches the maximum, the manager emits "Auto-reconnect disabled" / "Max retries reached. Scanning..." and falls back to the 10 s device scanner. Note what passive scanning actually does: it re-attempts a connection only when the discovered port list changes and the configured port is in it. With the default settings, an adapter that is plugged in but has no vehicle response is tried once at startup and then left alone until the user taps Connect, changes the port, or the port disappears and reappears. A _force_stop_reconnect flag set by close() blocks all scheduling during shutdown.

Python only: a daemon threading.Thread (_monitor_connection) polls connection.status() and the port file every 2 s while connected and reports "Connection to vehicle lost" / "Device Lost" (via QTimer.singleShot(0, ...) to hop back to the main thread). C++ relies on the worker's serial errors and the empty-read detector instead.

Data Watchdog

Every 5 s, while connected and at least one PID is being watched, the watchdog compares the last-data timestamp with now. More than 30 s without data means the connection is stale: status "Stale Connection" / "No data received, reconnecting...", the connection is cleaned up, the attempt counter reset, and a fresh attempt starts 100 ms later. 

self._data_watchdog_timer.setInterval(5000)
self._data_watchdog_timeout = 30.0          # Python
static constexpr int DATA_WATCHDOG_TIMEOUT_MS = 30000;  // C++

The watchdog is paused on entering diagnostic mode (both backends) so DTC work cannot trigger a false reconnect. On Android it is never started; the BLE path has its own per-PID watchdog (below).

The C++ / pure-protocol PID table has no decoder for the four narrow-band O2 sensors S3/S4 (PIDs 18-1B), the 16 wide-range O2 voltage/current PIDs (24-2B, 34-3B), ELM_VOLTAGE (an ATRV AT command, not a Mode-01 PID) or FUEL_RAIL_PRESSURE_ABS as a settings name. Enabling those in the settings page has no effect on the C++ backend. In addition, pidToCommand maps PID 0x59 to LONG_O2_TRIM_B2, while the decoder table (correctly, per SAE J1979, as its own comment notes) decodes 0x59 as fuel-rail absolute pressure and emits fuelRailPressureAbsChanged -- so enabling Long O2 Trim B2 in C++ polls the wrong PID and lights up the Fuel Rail Abs parameter instead. The Python backend, via python-obd, handles all 83.

Which PIDs Get Polled

Python: _setup_watchers()

def _setup_watchers(self):
    commands_to_watch = self._get_all_commands()
    for param, (command, callback) in commands_to_watch.items():
        default_enabled = param in ORIGINAL_17
        should_watch = self._settings_manager.get_obd_parameter_enabled(param, default_enabled)
        if should_watch:
            self._connection.watch(command, callback=final_callback, force=True)

Callbacks follow one pattern -- if not r.is_null(): self._x = float(r.value.magnitude); self.xChanged.emit(self._x) -- so null/error responses never reach QML (python-obd uses Pint quantities, hence .magnitude). When the settings page toggles a parameter, SettingsManager debounces the change for 800 ms and emits obdParametersChanged; the manager's _refresh_watchers() then does stop(), unwatch_all(), _setup_watchers(), start() without reconnecting. refresh_values() re-runs every callback with conn.query(command), which on an Async connection returns the cached response without touching the adapter -- the home screen calls it after homeOBDParametersChanged so newly enabled tiles show a value immediately.

C++: PID list built once per connection

startConnection() walks the static pidToCommand map, asks get_obd_parameter_enabled(name, isDefault) for each, and hands the resulting QList<PidKey> to the worker before the thread starts. The map iteration order is QHash order, so the round-robin sequence is arbitrary but stable within a run. onSettingsParametersChanged() only logs "will take effect on next connection": enabling a parameter in C++ requires a reconnect (Connect button, port change, or the next automatic reconnect). Parity gap with the Python hot-refresh.

Vehicle Scanning

scan_vehicle() runs automatically 2 s after a successful connection and from the OBD settings page. It emits terminal-style lines through scanOutputChanged ([SCAN], [INFO], [OK] NAME, a ==== summary), progress through scanProgressChanged(pct, "Checking NAME..."), and finishes with supportedCommandsChanged(list) + scanCompleteChanged(list) + scanProgressChanged(100, "Found N supported parameters"). The list is persisted under the supportedOBDParameters settings key, and enable_all_supported() / enable_scanned_parameters(list) flip the matching parameter toggles on.

  • Python: _do_vehicle_scan() runs on a daemon thread but sends nothing to the adapter -- it reads connection.supported_commands, the frozen set python-obd filled during obd.Async() init, and intersects it with _get_all_commands(). This keeps the live stream uninterrupted (an earlier version opened a second sync connection on the same port). Results are hopped to the main thread with QTimer.singleShot(0, ...), and _refresh_watchers() is queued 500 ms later so watchers registered before supported_commands was populated are re-applied.
  • C++: doScanVehicle() on the worker pauses polling, sends 0100, 0120, 0140, ... 01E0 (stopping at the first range whose bitmap does not set bit 32 = "next range supported"), collects the supported PID numbers with parseSupportedPids(), and reports every pidToCommand entry whose PID number is in the set. Polling resumes afterwards.
  • Android: the automatic scan is never queued (it hangs off onWorkerInitComplete, which the BLE path does not use) and a manual scan_vehicle() sets m_isScanning but has no worker to run on -- see Android.

Android: BLE via OctaveOBDBridge

On Android the desktop worker is never created. startAndroidConnection() validates the MAC (missing/invalid gives "No MAC Address" / Enter your ELM327 MAC in OBD Settings, then tap Connect), resets the BLE state, and calls OctaveOBDBridge.connect(context, mac) through QJniObject. From then on a 50 ms QTimer (onAndroidBlePoll()) drains the bridge:

  1. pollLog() up to 50 lines per tick: W| lines become qCWarning(lcElm327) "[BLE] ...", I| lines qCInfo -- so a BLE drop in the car lands in octave-cpp.log and the Diagnostics export instead of only logcat (3858c5c).
  2. pollResponse() until empty: each notification chunk is fed to the same ResponseBuffer, and every complete >-terminated response goes to processAndroidResponse().
  3. stateCode(): only on a transition. 0 DISCONNECTED (log lastEvent, status Disconnected, reconnect if we were connected), 1 CONNECTING, 2 DISCOVERING (progress 50, Discovering services...), 3 READY (progress 70, Initializing ELM327..., start the init state machine after 500 ms), 4 ERROR (log lastError, BLE error, reconnect).

Inside the Java bridge: BluetoothAdapter.getRemoteDevice(mac) then connectGatt(ctx, autoConnect=false, callback, TRANSPORT_LE); on connect it runs service discovery and tries three vendor profiles in priority order -- ISSC Transparent UART (49535343-FE7D-..., separate notify/write characteristics; NEXAS, Vgate iCar Pro, OBDLink CX), FFF0 (FFF1 notify + FFF2 write, or a single read/notify/write FFF1; Konnwei, some BAFX), and FFE0/FFE1 (one characteristic both ways; HM-10 style clones). The first one with both roles wins; notifications are enabled through the CCCD descriptor and the state flips to READY. Writes use WRITE_TYPE_NO_RESPONSE when the characteristic allows it. Incoming bytes are queued in a ConcurrentLinkedQueue (GATT callbacks run on a Binder thread; C++ polls from the Qt main thread). Verified end-to-end on a NEXAS adapter over the FFF0 path (f1901d9).

Permissions (08e8245): on API 31+ connect() checks BLUETOOTH_CONNECT / BLUETOOTH_SCAN; if either is missing it casts the context to Activity, calls requestPermissions() (request code 7301) so the system dialog appears, sets the error "Requesting Bluetooth permission -- tap Allow, then tap Connect again", goes to state ERROR and returns false. Fresh installs (CI sideloads, Play builds) therefore get a working second tap instead of a silent SecurityException from connectGatt(). The older C++ requestAndroidBluetoothPermission() (which wrestled Qt's QBluetoothPermission cache) is still in the source but no longer called.

Writes: writeAndroidBytes() drops data unless the last seen state is READY and chunks every write to 20 bytes (the default 23-byte ATT MTU minus 3). Init: the timer-driven sequence described above, then 0100 and a 2 s wait. Finalize: m_connected = true, Connected, progress 100, and the poll list is built from settings -- but only from the 17 default commands (the Android pidToCommand map has no extended entries), intersected with the PID-00/20/40/60 bitmaps if the vehicle answered them; an empty result falls back to the 17 defaults. Polling is response-driven: pollNextAndroidPid() writes one request and arms a 500 ms single-shot watchdog; the next request goes out when a response is decoded or the watchdog fires. Ten consecutive watchdog fires (5 s stale) flush the response buffer. Reconnect after an unexpected DISCONNECTED/ERROR: up to 3 attempts, delay min(2000 * n, 10000) ms, counter reset on success.

What the Android path does not do

read_dtc, read_current_dtc, read_status, clear_dtc, read_freeze_frame, refresh_values and scan_vehicle all forward to m_worker, which is null on Android, so they are silent no-ops (and scan_vehicle leaves m_isScanning stuck at true). enter_diagnostic_mode only stops the watchdog. Extended PIDs are never polled on Android. The data watchdog and device scanner do not apply.

ELM327 Protocol Module

src/managers/elm327protocol.{h,cpp} and its Python twin backend/elm327_protocol.py are pure protocol code (no I/O) kept line-for-line equivalent -- the same 61 PID entries, the same decoders, the same error tokens. The C++ one is what the desktop worker and the Android path use; the Python one is a reference/parity module.

ResponseBuffer

Accumulates bytes until a > prompt. It trims to the last 1 KB if it grows past 4 KB without a prompt (corrupt stream guard), splits the response on \r, and returns the last non-empty line that is not an AT echo and not OK. That is why echo-on adapters and the SEARCHING... line preceding a first reply do not break parsing. 

class ResponseBuffer:
    def feed(self, data):
        self._buffer += data
        if len(self._buffer) > 4096:
            self._buffer = self._buffer[-1024:]

    def get_response(self):
        idx = self._buffer.find(b">")
        if idx == -1:
            return None
        response = self._buffer[:idx].decode("ascii", errors="ignore").strip()
        self._buffer = self._buffer[idx + 1:]
        lines = [l.strip() for l in response.split("\r") if l.strip()]
        for line in reversed(lines):
            if line and not line.startswith("AT") and line != "OK":
                return line
        return lines[-1] if lines else ""

Protocol Logging

A failed OBD session can be reconstructed from the logs (commit 86c8c3c). Python: python-obd performs the I/O and already logs every write/read on its own obd.* logger tree; setup_logging() attaches OCTAVE's handlers to it (DEBUG with --debug, INFO otherwise, no propagate), so with --debug every write: b'010C\r' / read: ... pair lands in octave-debug.log and its errors always reach octave-error.log. C++: the octave.elm327 category logs TX/RX lines (response truncated to 200 chars, with the round-trip time) from OBDConnectionWorker::sendCommand, a WARNING when a command gets no response within its timeout, and in ELM327Protocol adapter error responses and unparseable responses at debug, short responses and decoder failures at warning. On Android the Java bridge's queued event/error lines are forwarded as [BLE] ... INFO/WARNING lines by the 50 ms poll. Debug-level lines need --debug (see the logging section of Architecture). The live in-app connection log is a separate, user-facing channel.

OBDParameterModel and IMU Parameters

frontend/OBDParameterModel.qml is the only QML that listens to obdManager's parameter signals. A Connections { target: obdManager } block with one handler per signal (84) writes into the model with updateParamValue(paramId, value); a second, guarded Connections on berryIMU (typeof berryIMU !== "undefined") does the same for PITCH, ROLL, HEADING, ALTITUDE, ACCEL_MAG, LATERAL_G, LONGITUDINAL_G and BARO_TEMP from the IMU's pitchChanged .. baroTempChanged signals (both backends expose them; see Hardware Managers). The IMU values are ordinary parameters from that point on: any gauge can bind them, the PID picker lists them, demo mode sweeps them.

Coalesced writes (486a809): updateParamValue() only stores into _pendingValues and arms a one-shot 33 ms Timer; the timer folds the pending map into a fresh paramValues object with Object.assign. Replacing paramValues is what re-evaluates every gauge binding, and the IMU alone fires ~440 signals per second (7 signals at 60 Hz) -- copying the whole dictionary on each one pegged the QML thread at 100 % on an idle Orange Pi (V4 string allocation + GC churn, found with py-spy). Bindings now re-evaluate at most ~30 times a second and only while data arrives. hasParameter(id), getParamInfo(id), parameterInfo (with short titles for the home cards) and allParameters (id, title, unit, min, max, kind) are documented on the Gauges & Dashboards page.

Shift Light, Full-Screen Flash and Aura

The shift light is pure QML driven by rpmChanged. Its configuration is a list of flags stored as a JSON string under the rpm_flags setting and edited in the RPM settings popup inside frontend/OBDMenu.qml. Each flag is {rpmLow, rpmHigh, color, flash, flashSpeed, fullScreenFlash, fullScreenFlashOpacity, auraFlash, auraFlashOpacity, auraSpread} (new flags default to flash: false, flashSpeed: 100, fullScreenFlashOpacity: 0.5, auraFlashOpacity: 0.6, auraSpread: 0.18); the popup keeps the list sorted by rpmLow, keeps rpmLow <= rpmHigh, clamps ranges to rpm_max_rpm (default 8000), and migrates the old single-rpm format to rpmLow/rpmHigh on load.

  • Active flag: the last flag (highest priority) whose [rpmLow, rpmHigh] range contains the current RPM.
  • Card indicator (HomeOBDView.qml): a disc on the RPM home card (rpm_show_on_home_card) coloured by the active flag, with glow (rpm_glow_size, rpm_glow_intensity), size (rpm_shift_light_size), colour transition (rpm_color_transition_speed), optional 800 ms pulse (rpm_pulse_enabled), and a flash timer at flashSpeed ms when the flag's flash is set.
  • Global full-screen flash (Main.qml, globalFullScreenFlash): a z: 999999 rectangle over the whole window in the flag colour at the flag's fullScreenFlashOpacity (fallback rpm_fullscreen_flash_opacity), visible when the flag has fullScreenFlash and rpm_shift_light_enabled is on; enabled: false so touches pass through. A window-level timer toggles it at flashSpeed when flash is set.
  • Aura overlay (globalAuraFlash): the same trigger with auraFlash, but rendered as four edge gradients (top/bottom/left/right) that fade from the flag colour to transparent over auraSpread of the window (default 18 %) at auraFlashOpacity -- a perimeter glow that leaves the centre readable.

Main.qml connects obdManager.rpmChanged with an explicit .connect() in Component.onCompleted rather than a Connections element (the comment cites PySide6 reliability), and reloads the flags whenever settingsManager.genericSettingChanged reports a key starting with rpm_.

Design Decisions

  • Two transports, one class. C++ keeps the Android BLE path inside OBDManager behind #ifdef Q_OS_ANDROID rather than a subclass, so main.cpp, the signal dispatch table and the QML surface are identical on every platform; the deleted Python AndroidOBDManager was the template (2d05676).
  • Bypass Qt Bluetooth on Android. Qt 6.7's QBluetoothPermission aggregator reports Denied on Android 16 even with every runtime grant present, and QLowEnergyController reads that cache before initialising the adapter. BluetoothAdapter.getRemoteDevice + connectGatt do not consult it, so a 400-line Java helper polled over JNI was cheaper and more reliable than fighting the framework (f1901d9). Polling at 50 ms instead of registering native JNI callbacks keeps the Java side free of Qt headers.
  • Three BLE profiles, priority ordered. ELM327 BLE clones ship ISSC, FFF0 or FFE0 firmware; trying all three at service-discovery time made one APK work with NEXAS, Vgate, Veepeak, Konnwei and HM-10 boards without a per-adapter setting.
  • The worker owns the port. QSerialPort must live on the thread that reads it, and blocking waitForReadyRead inside the worker is simpler than an async state machine; the price is that every request from the main thread is a queued invokeMethod. The 2026-09-09 spin fixes (above) are all consequences of that choice: a port left open is a live notifier in that thread's event loop.
  • Release the port on every failure. Rather than trying to detect a dead rfcomm remote, the rule is "nothing may hold the port open while we are not actively talking to a live adapter" (0404f7b). It is a policy, not a heuristic, so it holds for USB and Bluetooth alike.
  • python-obd on the Python side. The Python backend is the tinkerer's backend; delegating protocol negotiation, unit handling and command definitions to python-obd keeps it small, at the cost of a Pint import (moved to first use) and a second sync connection for DTC work. The pure-Python elm327_protocol.py exists so the C++ decoders have a reviewable twin.
  • Watchers, not a poll loop, in Python. obd.Async already runs a polling thread; OCTAVE just registers callbacks with force=True and re-registers them on settings changes. In C++ the equivalent list is fixed per connection because the worker copies it before the thread starts.
  • Diagnostics pause polling. ELM327 adapters are half-duplex request/response devices; interleaving Mode 03/04 traffic with a running PID loop corrupts both. Both backends therefore stop live data during DTC work and do a full reconnect afterwards -- the Python comment records that "simply calling start() on the old connection won't work reliably" after a sync connection shared the port.
  • Auto-reconnect defaults to off. The scanner-driven passive mode reconnects when a port appears, which is what happens when a Pi boots before the adapter pairs; unbounded retries against an adapter with no vehicle just spin the port (see the spin bug). Users who want retries set 1-10 attempts.
  • Unified adapter API. The settings page used to branch on isAndroid; moving MAC/COM/tty classification and the rfcomm bind into the managers made the page render identically everywhere and gave both backends a single connect entry point to test.
  • Observability over logcat. The in-app connection log (542b446), the ELM327 transcript category (86c8c3c) and the BLE log forwarding (3858c5c) all exist because the head unit is in a vehicle where neither a terminal nor adb logcat is reachable -- failures must land in the files the Diagnostics card exports.
  • Coalesced model writes. OBDParameterModel buffers into a plain object and flushes at 30 Hz because the alternative -- one dictionary copy per signal -- was measured at 100 % of a core on the Orange Pi with the adapter unplugged (486a809). Needle animations only need ~30 updates a second anyway.
