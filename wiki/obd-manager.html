Overview

OBDManager (backend/obd_manager.py) provides real-time vehicle data over the OBD-II port through an ELM327-compatible adapter. main.py creates it with the settings manager and registers it as the QML context property obdManager through install_obd_manager(), which dev mode uses to swap in a simulator instead (below).

The adapter I/O is done by the python-obd library (obd>=0.7.3 in requirements.txt; the descriptions of library behaviour on this page were checked against 0.7.3). obd.Async owns the serial port, initialises the ELM327, negotiates the protocol, polls the watched commands on its own thread and calls back into the manager for every reply. The manager adds what python-obd does not do: a non-blocking connect, port discovery, reconnect policy, demand-driven watch lists, multi-value PIDs above 0x5F, VIN decoding, a diagnostic mode and the QML-facing signals.

The QML pages (OBDMenu, OBDHome, OBDDiagnostics, HomeOBDView, the OBD settings page, the adapter sheet and the gauge/dashboard system) talk only to obdManager and obdAdapterFinder.

Desktop: Linux, Windows, macOS, Raspberry Pi

Connection Flow

The lifecycle runs on the GUI thread, driven by four QTimers created in the constructor (plus the 250 ms demand debounce described below):

TimerIntervalPurpose
_startup_timer50 ms single-shotDefers the first scan + connection attempt out of the constructor.
_device_scanner_timer10 sPassive port discovery while disconnected; stopped once connected.
_port_change_timer1 s single-shotDebounces obdBluetoothPortChanged from settings into one reconnect().
_data_watchdog_timer5 sStale-connection detection (30 s without data).
  1. Startup: the 50 ms timer fires _initial_connect(): scan for ports, start the 10 s scanner, call _start_connection().
  2. Guard: an _is_connecting flag, checked and set under a threading.Lock, drops re-entrant attempts ("Already connecting - skipping"). The attempt counter increments and the UI gets connectionStatusChanged("Connecting"), connectionStatusDetailChanged("Attempt N..."), connectionProgressChanged(10).
  3. Port check: _check_port_exists(). An rfcomm:// URL only has to parse; on Windows the port must be in serial.tools.list_ports.comports() (if that lookup raises, the port is assumed present); elsewhere the device file must exist. A missing port emits "Device Not Found" / Port X not available, progress 0, devicePresenceChanged(false), and goes to auto-reconnect scheduling.
  4. Worker: devicePresenceChanged(true), progress 15, "Found <port>, connecting..."; the previous worker thread is cleaned up (1 s wait), then a fresh OBDConnectionWorker is moved to a new QThread whose started signal calls do_connect() (next section). The port in use is remembered as _active_port.
  5. Result (_on_connection_complete(connection, status) on the GUI thread):
    • OBDStatus.CAR_CONNECTED: _connected = true, attempts reset, the protocol name is cached, "Connected" / OBD interface connected successfully + progress 100, then _setup_watchers(), connection.start(), the connection monitor thread, scan_vehicle() queued 2 s later, the data watchdog started and the device scanner stopped.
    • OBDStatus.ELM_CONNECTED: the connection object (and the port python-obd left open) is kept but _connected stays false; "No Vehicle" / Connected to adapter, waiting for vehicle..., progress 50, then auto-reconnect scheduling.
    • Anything else (NOT_CONNECTED, OBD_CONNECTED): the connection is closed; "Connection Failed" / Could not connect to OBD adapter, progress 0, auto-reconnect scheduling. For an rfcomm:// port that ended NOT_CONNECTED the connection log also gets Bluetooth: could not reach <MAC> (adapter off or out of range?), because python-obd swallows the socket error.
  6. Exceptions from the worker arrive as connectionError(str) in _on_connection_error(): status "Error" / Error: <message>, progress 0, auto-reconnect scheduling. A message containing Input/output error or Errno 5 also clears the cached protocol.
  7. Post-diagnostic retries: while _reconnecting_after_diagnostic is set, a "No Vehicle" or failed attempt retries every 2 s while fewer than 3 attempts have been made, even if auto-reconnect is disabled in settings.

In every branch _is_connecting is cleared and the worker thread is cleaned up.

Threaded Connection Worker

OBDConnectionWorker exists to move python-obd's blocking constructor off the GUI thread. It emits connectionProgress(20, "Initializing OBD adapter...") (or "Connecting with cached protocol..."), registers the rfcomm:// handler when the port is a direct Bluetooth URL (progress 15, Connecting over Bluetooth...), builds the connection, emits connectionProgress(80, "Checking connection status...") and, when the car answered, reads the VIN and the extended supported-PID bitmaps (progress 90, Reading vehicle information...) before handing the object back: 

class OBDConnectionWorker(QObject):
    connectionComplete = Signal(object, object)  # (connection, status)
    vehicleInfo = Signal(str, object)          # (vin, set of supported PIDs 0x61+)
    connectionProgress = Signal(int, str)        # (progress, message)
    connectionError = Signal(str)

    def do_connect(self):
        ...
        connection = obd.Async(
            portstr=self._port,
            fast=self._fast_mode,
            timeout=self._timeout,          # 5 unless set_connection_timeout() changed it
            delay_cmds=0,                   # MAXIMUM SPEED
            protocol=self._cached_protocol if self._cached_protocol else None
        )
        status = connection.status()
        if status == obd.OBDStatus.CAR_CONNECTED:
            vin, supported = probe_vehicle(connection)
            self.vehicleInfo.emit(vin, supported)
        self.connectionComplete.emit(connection, status)

vehicleInfo is emitted before connectionComplete, so the manager already has the VIN and the extended support set when the connection is accepted. Any exception becomes connectionError(str).

Abandoned workers. A worker can still be blocked inside obd.Async() when a newer attempt starts. _cleanup_worker_thread() disconnects the worker's signals from the manager, connects its connectionComplete to _close_orphan_connection() (so a connection it opens later is closed instead of holding the port), quits the thread and waits (2 s by default, 1 s from _start_connection()). A thread that is still busy is parked in _retired_threads until it finishes, because dropping the last reference to a running QThread makes Qt abort the process.

ELM327 Initialisation and Connection Status

python-obd performs the ELM327 initialisation inside obd.Async(). In 0.7.3 its ELM327 class opens the port with serial.serial_for_url(port, timeout=10), detects the baud rate, then sends ATZ, ATE0, ATH1 (headers on) and ATL0; after that the status is ELM_CONNECTED. Because OCTAVE leaves check_voltage at its default, it next sends AT RV: a reading below 6 V stops there (status stays ELM_CONNECTED, logged as OBD2 socket disconnected); otherwise the status becomes OBD_CONNECTED and python-obd sets the protocol (auto-detect, or the protocol passed in). Success gives CAR_CONNECTED, after which python-obd reads the supported-PID bitmaps into supported_commands.

python-obd statusTypical causeOCTAVE status
CAR_CONNECTEDAdapter and ECU answeredConnected
ELM_CONNECTEDAdapter answered but AT RV read under 6 V (the port stays open)No Vehicle
OBD_CONNECTEDAdapter powered from the OBD port (6 V or more) but no protocol found, e.g. ignition offConnection Failed
NOT_CONNECTEDPort could not be opened, the adapter never answered, or an init step (including an unusable AT RV reply) failed; python-obd closes the portConnection Failed

The INIT_COMMANDS table in backend/elm327_protocol.py (ATZ, ATE0, ATL0, ATS0, ATH0, ATAT2, ATSP0) is reference data; nothing sends it at runtime.

_scan_for_devices() runs at startup, every 10 s while the scanner timer runs, and on demand (scan(), get_available_ports()):

PlatformScanned
WindowsAll COM ports via serial.tools.list_ports; a port is included if its description contains bluetooth, obd, elm, serial or usb, or its name starts with COM (in practice: every COM port).

Unified Adapter API

The OBD settings page and the adapter sheet render the same on every desktop OS. Platform variation (rfcomm bind on Linux/Pi, COM enumeration on Windows, /dev/tty.* on macOS) lives in the manager; QML uses platform_hint() only for entry hints and to show the Linux Direct button.

_ensure_rfcomm_bound(mac, log): if any /dev/rfcomm0..7 already exists it is used as-is (rfcomm: using existing /dev/rfcommN; there is no check that it is bound to the same MAC). Otherwise, if shutil.which("rfcomm") finds the binary, it runs rfcomm bind 0 <mac> 1 (channel 1 is hard-coded here) with a 5 s subprocess timeout, then waits up to 1 s (10 × 100 ms) for /dev/rfcomm0. A missing binary, timeout, non-zero exit (with the tip add user to bluetooth group, or run sudo rfcomm bind 0 <mac> once and enter /dev/rfcomm0) or missing node is written to the connection log, and the status becomes "Error" / rfcomm bind failed — see Connection Log.

The bind runs on an obd-rfcomm-bind daemon thread; log lines and the result come back to the GUI thread through run_on_main, in order. On success _finish_rfcomm_bind() saves the node as the OBD port and calls force_connect(). A newer connect_to_adapter() bumps _rfcomm_bind_generation, so the result of an older bind is ignored. Covered by tests/test_rfcomm_bind_async.py.

Direct Bluetooth (rfcomm://, Linux)

A port of the form rfcomm://<MAC> or rfcomm://<MAC>/<channel> (channel 1-30, default 1) skips the bound /dev/rfcommN node and opens a Bluetooth Classic RFCOMM socket straight to the adapter. It needs no rfcomm bind (root), connects explicitly with a timeout and a real error (Host is down, Connection refused), and per the module docstring nothing else on the system (blueman) can release the link underneath it.

  • backend/obd_transports/__init__.py holds the URL helpers (is_rfcomm_url, parse_rfcomm_url, make_rfcomm_url) and register_handlers(), which adds the package to serial.protocol_handler_packages (idempotent). The manager imports only these helpers, so pyserial is not imported until a connect needs it.
  • backend/obd_transports/protocol_rfcomm.py: Serial subclasses pyserial's protocol_socket.Serial and replaces open() with an AF_BLUETOOTH / BTPROTO_RFCOMM connect (10 s socket timeout). python-obd opens rfcomm:// through serial_for_url() unchanged; the worker calls register_handlers() just before obd.Async(). An EBUSY (one link per channel, still held by a previous connection or by a process with /dev/rfcommN open) is retried every 250 ms for up to 3 s. Where socket.AF_BLUETOOTH does not exist the open fails with Direct Bluetooth (rfcomm://) is only supported on Linux.
  • _check_port_exists() only validates the URL, since there is no node to look for. The passive scan (every 10 s) retries a configured rfcomm:// adapter whenever the manager is not connected, connecting, closed or in diagnostic mode. The dongle is usually only powered with the ignition on, and while it is off the connect fails within seconds.

Adapter Finder: Scan, Pair, Connect

OBDAdapterFinder (QML obdAdapterFinder, backend/obd_adapter_finder.py) lets someone connect an adapter without knowing its MAC or pairing it in the OS first. main.py creates it before the OBD manager exists and install_obd_manager() hands it the manager (real or mock) through set_obd_manager(). The "Connect Bluetooth OBD2" button on the empty Parameter Cards page and "Find Bluetooth Adapters" in the OBD settings both open frontend/OBDAdapterSheet.qml, which starts a scan. supported is a constant: true on Linux when PySide6.QtBluetooth is importable. Elsewhere the sheet lists obdManager.availableAdapters instead (the ports the OS already knows) and calls obdManager.scan().

Startup never waits on BlueZ. The QtBluetooth objects (QBluetoothLocalDevice, the discovery agent, _BluezPairer) are created in _ensure_bluetooth() only once org.bluez has an owner on the system bus, a question the bus daemon answers at once (isServiceRegistered, which never starts a service). A QDBusServiceWatcher creates them when BlueZ registers later. The source comment gives the reason: with bluetoothd stopped (or no adapter) QBluetoothLocalDevice's constructor D-Bus-activates org.bluez and blocks the GUI thread for the activation timeout, twice (about 45 s). Without BlueZ, bluetoothOn is false and startScan() reports Bluetooth is not available: the Bluetooth service is not running.

  1. Scan (startScan()): QBluetoothDeviceDiscoveryAgent with ClassicMethod | LowEnergyMethod and a 15 s LE discovery timeout. Devices without a name (or named after their own address, as BlueZ does) and the all-zero address are dropped. likelyObd is set when the name matches the common ELM327 adapter names (obd, elm327, v-link, vgate, icar, veepeak, bafx, konnwei, nexas, lelink, viecar, kiwi, carista, panlong, scan tool, ...) or a BLE device advertises one of the ELM327 BLE service UUIDs (FFF0, FFE0, FFE1, ISSC 49535343-FE7D-...). Rows are sorted likely-OBD first, then by signal strength (a cached device with RSSI 0 sorts after live ones), then by name; the sheet shows likely adapters only, with a "Show All Devices" toggle. A dual-mode adapter keeps every mode seen during the scan (the source names the NEXAS NexLink, which reports Classic once and LE-only afterwards).
  2. Pair (connectAdapter(address), Classic only): the scan stops, then _BluezPairer.start() finds the BlueZ device object (/org/bluez/hci0..hci3), and if it is not already paired registers _BluezPinAgent (org.bluez.Agent1 exported at /org/octave/obd_pin_agent, capability KeyboardDisplay) and calls Device1.Pair() asynchronously with a 45 s timeout. BlueZ sends the PIN request to the agent of the client that called Pair(), so OCTAVE answers it and the desktop's own PIN dialog never appears. On AuthenticationFailed / AuthenticationRejected it waits 1.5 s and retries with the next PIN: 1234, 0000, 6789, 1111. AlreadyExists counts as paired. The agent is unregistered when pairing finishes.
  3. Trust: Device1.Trusted = true, so the adapter reconnects later without being asked again. If pairing failed for any reason other than InProgress, ConnectionAttemptFailed or NoReply, the adapter is still trusted and the connection is tried anyway, because some adapters (the NEXAS, per the source) accept RFCOMM from a trusted host without pairing. If that connection also fails, the pairing error is shown.
  4. Channel: an SDP lookup for the Serial Port service (QBluetoothServiceDiscoveryAgent, full discovery, 8 s timeout); channel 1 if it finds nothing, errors or times out.
  5. Hand-off: obdManager.connect_direct(mac, channel) (see Direct Bluetooth), and add_obd_saved_adapter(name, url) so the saved chip shows the adapter's name. The finder then follows connectionStatusChanged: it ignores everything until it has seen Connecting or Reconnecting (so the Disconnected that force_connect() causes does not count), then reports Connected to <name>, <name> is connected, but the vehicle isn't answering. Turn the ignition on. (No Vehicle), or the failure.

BLE-only devices are listed but not connectable ("Bluetooth LE adapters aren't supported on this device yet"): the OBD connection path here is a serial port or an RFCOMM socket, with no GATT transport. The finder's logic is covered by tests/test_obd_adapter_finder.py. Signals and properties are listed in the signals & slots reference.

Auto-Reconnect, Passive Scanning and the Connection Monitor

_schedule_auto_reconnect() reads obdAutoReconnectAttempts from settings (0 = disabled, which is the default; up to 10 attempts). The backoff is linear and capped: 

delay = min(10, 2 + attempts * 2)   # 4 s, 6 s, 8 s, 10 s, 10 s ... after attempt 1, 2, 3, 4, ...
QTimer.singleShot(int(delay * 1000), self._start_connection)

The detail line shows Retry in Ns... (n/max). When auto-reconnect is disabled, or the attempt count reaches the maximum, the manager emits Auto-reconnect disabled / Max retries reached. Scanning... and starts the 10 s device scanner. For device nodes, passive scanning re-attempts a connection when the discovered port list changes and the configured port is in it; an adapter that is plugged in but not answering is therefore tried once and then left alone until the user taps Connect, changes the port, or the node disappears and reappears. Direct rfcomm:// connections are retried on every 10 s scan while disconnected, even with the attempt limit at zero. A _force_stop_reconnect flag set by close() blocks all scheduling during shutdown.

Connection monitor. While connected, the daemon thread _monitor_connection checks every 2 s:

  • connection.status() dropping from CAR_CONNECTED: vehicle support is reset and the GUI thread gets "Disconnected" / Connection to vehicle lost, progress 0, auto-reconnect scheduling and the device scanner (all through run_on_main()).
  • The configured port disappearing (_check_port_exists() false): "Device Lost" / Bluetooth device disconnected, progress 0, devicePresenceChanged(false), auto-reconnect scheduling and the device scanner; the monitor then exits.

The monitor also exits on any exception. python-obd's own polling thread stops by itself when is_connected() turns false (Async thread terminated because device disconnected).

Data Watchdog

Every 5 s while connected and at least one command is watched, _check_data_watchdog() compares the last-data timestamp with now. More than 30 s without a refresh triggers status "Stale Connection" / No data received, reconnecting...; the watchdog stops and 100 ms later _trigger_watchdog_reconnect() cleans up the connection, resets the attempt counter and starts a fresh attempt. 

self._data_watchdog_timer.setInterval(5000)
self._data_watchdog_timeout = 30.0

The timestamp is refreshed by the one wrapped base-command callback (see python-obd Settings), on every reply including null replies. It therefore detects python-obd's loop stalling, not every kind of vehicle failure. The watchdog is stopped on entering diagnostic mode so DTC work cannot trigger a false reconnect.

Extended PIDs 0x61 and up (37 values from 23 PIDs)

python-obd's command table stops at PID 0x5F. The extended table adds values from PIDs 0x61-0xB2; several replies carry multiple values and support bits. EXTENDED_PID_TABLE in backend/elm327_protocol.py lists, per value, its id, data bytes, the support bit in byte A that must be set (or none) and the minimum reply length. The manager wraps each PID in an obd.OBDCommand built (and cached) by extended_command(mode, pid), named OCTAVE_01xx, whose decoder calls decode_extended_pid() on the message data after the mode/PID bytes; python-obd joins multi-frame CAN replies before the decoder sees them. The callback _update_extended emits one obdParameterChanged(paramId, value) per decoded value; OBDParameterModel routes it into paramValues. Values whose support bit is clear or whose bytes are missing are skipped. The decoders are exercised by tests/test_obd_extended_pids.py; that is not a claim that every vehicle implements them. EGT 0x78/0x79, turbo RPM/temperature 0x74-0x76, exhaust pressure 0x73, DPF 0x7A-0x7C and the gear number in 0xA4 are not included. Boost pressure is absolute; subtract BAROMETRIC_PRESSURE for gauge boost.

Vehicle identity (VIN)

probe_vehicle() also queries Mode 09 PID 02 once through the OCTAVE_VIN command, and read_vin() repeats the probe on a daemon thread (stopping and restarting async polling around it, or using the diagnostic connection in diagnostic mode). OCTAVE does not use python-obd's own VIN decoder: per the source comment its strip set is written b'\\x00', which strips the characters \ x 0 1 2 from both ends and turns every US VIN (1...) into 16 characters. Instead _decode_vin_message() keeps the ASCII letters and digits after the mode/PID bytes (dropping the CAN item count and pre-CAN zero padding) and takes the last 17. decode_vin() from backend/elm327_protocol.py then validates it (17 characters, no I/O/Q), takes the make from the world manufacturer identifier (first 3 characters, about 120 entries, then a 2-character fallback) and the model year from position 10 (30-year cycle; an alphabetic position 7 selects 2010+, and a year more than one year in the future falls back 30 years). vin, vehicleMake and vehicleModelYear notify on vinChanged, which is emitted only when the VIN changes. An unsupported or invalid VIN leaves vin and vehicleMake empty and vehicleModelYear at 0. The OBD settings Connection card shows a Vehicle row when a VIN is known.

Which PIDs Get Polled

Polling is demand-driven: OCTAVE polls what is on screen, not a list of parameters switched on in settings. Every consumer registers the parameter ids it shows with obdManager.setParameterDemand(consumer, ids) (an empty list removes the consumer; an unchanged set is ignored). The QML consumers are "dashboard" (the active dashboard's PIDs), "cards" (every supported PID while Parameter Cards is open), "home" (the Home screen OBD tiles), "editor" (the dashboard editor canvas), "settings" (the OBD settings parameter list while it is shown) and "carMenu" (RPM and SPEED while CarMenu is visible).

The poll set is computed by the module-level compute_poll_params(demand, supported, base_params):

  • Union of every consumer's ids. BerryIMU ids (IMU_PARAM_IDS: PITCH, ROLL, HEADING, ...) and unknown ids are dropped.
  • Filtered to vehicleSupportedParameters once this session's scan produced a non-empty result (an empty or unknown result filters nothing).
  • A multi-value PID (0x61+) is polled when any of its values is wanted.
  • Heartbeat: the first of HEARTBEAT_PARAMS = ("RPM", "ELM_VOLTAGE") that passes the support filter is always added, which keeps the global RPM shift light working on every screen.
  • Returns sorted base ids and sorted extended (mode, pid) keys. Covered by tests/test_obd_poll_demand.py.

Demand changes are debounced for 250 ms (_demand_debounce, one re-watch per page switch) and applied live, without a reconnect. A completed vehicle scan also re-applies the set, since the support filter changed. While disconnected the new set applies to the next connection.

_setup_watchers() / _refresh_watchers()

_setup_watchers() watches the base commands with watch(command, callback, force=True) (one of them wrapped for the data watchdog) and each extended PID with extended_command(mode, pid) and _update_extended, then sets _has_active_watchers. The debounce timer calls _refresh_watchers(), which does stop(), unwatch_all(), _setup_watchers(), start() (python-obd refuses watch() while its loop runs). Base callbacks follow one pattern -- if not r.is_null(): self._x = float(r.value.magnitude); self.xChanged.emit(self._x) -- so null replies never reach QML (python-obd returns Pint quantities, hence .magnitude). refresh_values() re-runs every base callback with conn.query(command), which on an Async connection returns the last stored reply for a watched command (and a null reply for anything else) without touching the adapter.

The per-parameter obdParameters enable settings no longer drive polling. The keys are still read and written (enable_all_supported() / enable_scanned_parameters() keep working) so existing settings files stay compatible.

Vehicle Scanning

scan_vehicle() runs automatically 2 s after a successful connection (it refuses with Not connected to vehicle when not connected and ignores a call while a scan runs). The current QML has no manual scan button. _do_vehicle_scan() runs on a daemon thread but sends nothing to the adapter: it reads connection.supported_commands, the set python-obd filled during obd.Async() init, and checks each of the 83 base commands against it; then it adds every extended value whose PID is in _extended_supported_pids. This keeps the live stream running (the source notes that an earlier version opened a second sync connection on the same port). python-obd seeds supported_commands with its base commands, which include ELM_VOLTAGE, so that name is always reported once the car connected.

Output goes through scanOutputChanged as terminal-style lines ([SCAN], [INFO], [OK] NAME, a ==== summary with [DONE]), progress through scanProgressChanged(pct, "Checking NAME..."), and the scan finishes with scanProgressChanged(100, "Found N supported parameters"), supportedCommandsChanged(list) and scanCompleteChanged(list), all sent to the GUI thread with run_on_main(). The list is persisted under the supportedOBDParameters settings key and becomes this session's vehicleSupportedParameters, with vehicleScanComplete set (true even for an empty result). Both reset on _cleanup_connection() (reconnect, close, watchdog reconnect) and when the monitor sees the vehicle drop; they are never loaded from the persisted key, so they describe the car connected right now. They drive the QML "supported by this vehicle" gate (tests/test_vehicle_gate_qml.py) and filter the poll set. _refresh_watchers() is queued 500 ms after a successful scan.

Diagnostics (DTC)

The Diagnostics page owns a diagnostic mode, entered with enter_diagnostic_mode() and left with exit_diagnostic_mode(). python-obd decodes the codes and their descriptions.

EnterOnly while connected. Stops the data watchdog, connection.stop(), sleeps 200 ms, then opens a second synchronous obd.OBD(port, fast=False, timeout=10) (_diagnostic_sync_conn) on the configured port; if it does not report connected it is closed and set to None. This runs on the GUI thread, so the window freezes for the sleep plus python-obd's connect.

In diagnostic mode it uses the sync connection; otherwise it stops async polling, opens a temporary sync connection the same way (after another 200 ms sleep), and in finally closes it and restarts async polling. ExitCloses the sync connection, then -- if there was a connection -- closes the old async connection (the source: "the diagnostic sync connection likely corrupted the async connection's serial port state ... simply calling start() on the old connection won't work reliably"), emits "Reconnecting" / Reconnecting after diagnostic mode..., clears a stuck _is_connecting, resets the attempt counter and after 1 s runs _delayed_reconnect_after_diagnostic(), which clears the cached protocol, sets _reconnecting_after_diagnostic (up to 3 retries regardless of the auto-reconnect setting) and starts a fresh connection.

A null reply or an error emits an empty list (and dtcClearResult(false, ...) / MIL false and count 0 for the other calls). A successful clear emits dtcClearResult(true, "DTCs cleared successfully"), an empty list, count 0 and MIL false.

Cancellation handshake: enter_diagnostic_mode sets _diagnostic_mode_transitioning = True under _diagnostic_mode_lock, releases the lock for the blocking work, then re-checks the flag after the 200 ms sleep. If exit_diagnostic_mode cleared it in that window, entry restores async polling and the watchdog and returns. Both slots are called from QML on the GUI thread, and the sleep blocks that thread, so the window only matters for a caller on another thread.

ELM327 Protocol Module

backend/elm327_protocol.py is pure protocol code (no I/O). Its PID numbers and command names follow python-obd's commands.py. The running app uses three things from it -- EXTENDED_PID_TABLE, decode_extended_pid() and decode_vin(); everything else is reference code exercised by tests/test_elm327_dtc.py and tests/test_obd_extended_pids.py. (The module docstring still says nothing imports it at runtime; that predates the extended PIDs.)

Base PID table

PID_TABLE maps (mode, pid) to (name, signal_name, command_name, decoder, num_bytes): 83 entries, the 82 Mode-01 commands of OCTAVE's base set plus ELM_VOLTAGE under the pseudo-key ELM_VOLTAGE_KEY = (0, 0) (text reply to ATRV, no decoder). command_name is the python-obd command name, i.e. the settings key and scan vocabulary. The decoder takes the data bytes after the 41 XX header: 

def _rpm(a):
    return round((a[0] * 256.0 + a[1]) / 4.0, 1)

PID_TABLE = {
    (1, 0x0C): ("RPM", "rpmChanged", "RPM", _rpm, 2),
    ...
}
PID_TABLE[ELM_VOLTAGE_KEY] = ("ELM Voltage", "elmVoltageChanged", "ELM_VOLTAGE", None, 0)

The 16 wide-range O2 entries are generated in a loop (O2_S1_WR_VOLTAGE .. O2_S8_WR_VOLTAGE at 0x24-0x2B, O2_S1_WR_CURRENT .. O2_S8_WR_CURRENT at 0x34-0x3B, four data bytes each; the lambda ratio in bytes A/B is ignored and the voltage / current decoded from C/D as (256C + D) × 8 / 65535 V and (256C + D) / 256 - 128 mA, python-obd's sensor_voltage_big / current_centered).

ResponseBuffer

Reference code, not used at runtime. Accumulates bytes until a > prompt, trims to the last 1 KB if it grows past 4 KB without a prompt (corrupt stream guard), keeps every non-empty line of the last response in last_lines, and returns the last line that is not an AT echo and not OK. 

class ResponseBuffer:
    def feed(self, data):
        self._buffer += data
        if len(self._buffer) > 4096:
            self._buffer = self._buffer[-1024:]

    def get_response(self):
        idx = self._buffer.find(b">")
        if idx == -1:
            return None
        response = self._buffer[:idx].decode("ascii", errors="ignore").strip()
        self._buffer = self._buffer[idx + 1:]
        lines = [l.strip() for l in response.split("\r") if l.strip()]
        self.last_lines = lines
        for line in reversed(lines):
            if line and not line.startswith("AT") and line != "OK":
                return line
        return lines[-1] if lines else ""

Protocol Logging

The manager logs on octave.obd (get_logger(__name__) maps backend.obd_manager to that name) with an [OBD] prefix; the adapter finder logs on octave.obd_adapter_finder with [OBD-BT]. python-obd performs the I/O and logs every write/read on its own obd.* logger tree; setup_logging() in backend/logging_config.py attaches OCTAVE's handlers to the obd logger (DEBUG with --debug, INFO otherwise, no propagation), so with --debug every write: ... / read: ... pair lands in octave-debug.log and python-obd's errors (Adapter connected, but the ignition is off, ...) reach octave-error.log. See the logging section of Architecture. The live in-app connection log is a separate, user-facing channel.

OBDParameterModel and IMU Parameters

frontend/OBDParameterModel.qml centralizes parameter values for gauges, cards and dashboards. A Connections { target: obdManager } block with one handler per base signal (84), plus onObdParameterChanged(paramId, value) for the extended values, writes into the model with updateParamValue(paramId, value); a second, guarded Connections on berryIMU (typeof berryIMU !== "undefined", ignoreUnknownSignals: true) does the same for PITCH, ROLL, HEADING, ALTITUDE, ACCEL_MAG, LATERAL_G, LONGITUDINAL_G and BARO_TEMP from the IMU's pitchChanged .. baroTempChanged signals (see Hardware Managers). The IMU values are ordinary parameters from that point on: any gauge can bind them, the PID picker lists them, demo mode sweeps them.

Coalesced writes: updateParamValue() only stores into _pendingValues and arms a one-shot 33 ms Timer; the timer folds the pending map into a fresh paramValues object with Object.assign. Replacing paramValues is what re-evaluates every gauge binding, and the IMU alone emits seven orientation/gauge signals per emit tick (about 60 Hz by default), so bindings re-evaluate at most about 30 times a second instead of once per signal. hasParameter(id), getParamInfo(id), parameterInfo and allParameters (id, title, unit, min, max, kind) are documented on the Gauges & Dashboards page.

Shift Light, Full-Screen Flash and Aura

The shift light is pure QML driven by rpmChanged. Its configuration is a list of flags stored as a JSON string under the rpm_flags setting and edited in the RPM settings popup inside frontend/OBDMenu.qml. Each flag is {rpmLow, rpmHigh, color, flash, flashSpeed, fullScreenFlash, fullScreenFlashOpacity, auraFlash, auraFlashOpacity, auraSpread} (new flags default to flash: false, flashSpeed: 100, fullScreenFlashOpacity: 0.5, auraFlashOpacity: 0.6); the popup keeps the list sorted by rpmLow, keeps rpmLow <= rpmHigh, clamps ranges to rpm_max_rpm (default 8000), and migrates the old single-rpm format to rpmLow/rpmHigh on load.

  • Active flag: the last flag (highest priority) whose [rpmLow, rpmHigh] range contains the current RPM.
  • Card indicator (HomeOBDView.qml): a disc on the RPM home card (rpm_show_on_home_card) coloured by the active flag, with glow (rpm_glow_size, rpm_glow_intensity), size (rpm_shift_light_size), colour transition (rpm_color_transition_speed), optional 800 ms pulse (rpm_pulse_enabled), and a flash timer at flashSpeed ms when the flag's flash is set.
  • Global full-screen flash (Main.qml, globalFullScreenFlash): a z: 999999 rectangle over the whole window in the flag colour at the flag's fullScreenFlashOpacity (fallback rpm_fullscreen_flash_opacity), visible when the flag has fullScreenFlash and rpm_shift_light_enabled is on, and transparent to touches.
  • Aura overlay (globalAuraFlash): the same trigger with auraFlash, rendered as edge gradients that fade from the flag colour to transparent over auraSpread of the window at auraFlashOpacity -- a perimeter glow that leaves the centre readable.

Main.qml connects obdManager.rpmChanged with an explicit .connect() in Component.onCompleted rather than a Connections element (the comment cites reliability with PySide6 signals).

Known Gaps

Behaviour in this backend that does not do what the code or QML intends
  • No connected property. Three QML files test obdManager.connected === true, which is always false here: OBDAdapterSheet.qml never auto-closes 1.5 s after the adapter comes up, the empty Parameter Cards grid in OBDMenu.qml always reads "No vehicle connected" (never "Reading your vehicle's PIDs…" or "No supported PIDs reported"), and CarMenu.qml's liveDrive is only true while the dashboard demo data runs, so live RPM / SPEED never drive the 3D Jeep's engine and wheels.
  • Protocol cache. The cached value is protocol_name() (for example ISO 15765-4 (CAN 11/500)), but python-obd 0.7.3's set_protocol() accepts only the IDs "1" through "A"; anything else logs ... is not a valid protocol and fails, so the attempt cannot reach CAR_CONNECTED. The cache is set after every successful connect and is cleared only by an errno-5 error or a post-diagnostic reconnect, so a reconnect(), force_connect(), port change or data-watchdog reconnect after a good connection carries it. protocol_id() would return the accepted form.
  • enter_diagnostic_mode() blocks the GUI thread for its 200 ms sleep plus a synchronous python-obd connect with a 10 s serial timeout.

Design Decisions

  • python-obd does the protocol. Delegating ELM327 initialisation, protocol negotiation, unit handling and command definitions to python-obd keeps the manager focused on lifecycle and UI, at the cost of a pint import (moved to first use) and a second sync connection for DTC work. The pure-Python elm327_protocol.py supplies what python-obd lacks (PIDs above 0x5F, a correct VIN decode) and keeps reviewable reference decoders and parsers.
  • A worker per attempt. obd.Async() blocks for the whole adapter handshake, so it runs on a fresh QThread; once it returns, python-obd's own thread does the polling and the worker is discarded. Abandoned workers are parked rather than dropped, because Qt aborts on destroying a running QThread.
  • Watchers, not a poll loop. obd.Async already runs a polling thread; OCTAVE registers callbacks with force=True and re-registers them when consumer demand or vehicle support changes, so a page switch changes polling without a reconnect.
  • Poll what is on screen. An ELM327 answers one request at a time, so every extra PID slows the rest. The demand union plus the RPM heartbeat keeps the loop short; the heartbeat keeps the shift light working everywhere.
  • Scan from what connect already learned. The vehicle scan reads python-obd's supported_commands and the extended bitmaps read at connect, instead of interrupting the live stream with a second connection.
  • Diagnostics pause polling. ELM327 adapters are half-duplex request/response devices; interleaving Mode 03/04 traffic with a running PID loop corrupts both. The manager therefore stops live data during DTC work and does a full reconnect after diagnostic mode.
  • Auto-reconnect defaults to off. The scanner-driven passive mode reconnects when a port appears, which covers a Pi that boots before the adapter pairs; users who want scheduled retries set 1-10 attempts. Direct RFCOMM connections retry through the 10 s scanner, because the dongle only has power with the ignition on.
  • Unified adapter API. MAC/COM/tty classification and the rfcomm bind live in the manager, so the settings page renders the same everywhere and has one connect entry point.
  • Observability in the files. The in-app connection log and python-obd's transcript in octave-debug.log exist because the head unit is in a vehicle where no terminal is reachable; failures must land in the files the Diagnostics card exports.
  • Coalesced model writes. OBDParameterModel buffers into a plain object and flushes at about 30 Hz, so a burst of signals costs one dictionary copy instead of one per signal; needle animations only need about 30 updates a second.
