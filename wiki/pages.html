MainMenu.qml

frontend/MainMenu.qml (563 lines) is the home screen and the initialItem of the StackView: "Media on left (1/3), OBD on right (2/3)". It imports QtQuick.Controls.Basic, Qt5Compat.GraphicalEffects and QtQuick.Effects — the only file besides MediaRoom that uses both effect modules.

Media panel

  • Blurred album art background — an Image of the current art with layer.effect: MultiEffect { blurEnabled: true; blurMax: 64; blur: min(1, settingsManager.backgroundBlurRadius / 64) } under a #C0000000 overlay; the panel border is drawn by a separate border-only rectangle at z: 10 so it stays crisp above the blur.
  • Foreground album art with the file's single DropShadow (offset 4/4, radius 12, 25 samples).
  • Scrolling title and "artist • album" — two copies of the Flickable + 3 s Timer + 5 s InOutQuad NumberAnimation ping-pong on contentX, running only while the text is wider than its container.
  • Seek slider — a custom Slider (accent fill, round handle, userSeeking flag) that on release calls spotifyManager.set_position() when useSpotify is true and mediaManager.set_position() otherwise, flanked by position/duration labels.
  • Dual source — useSpotify is settingsManager.mediaSource === "spotify" && spotifyManager.is_connected(); currentArt/Title/Artist/Album pick Spotify values or private _local* copies ("to avoid binding loops"). Missing art falls back to assets/missing_art.png.
  • Tap to open the player — a TapHandler, not a MouseArea, pushes MediaPlayer.qml or MediaRoom.qml according to settingsManager.musicButtonDefaultPage. The comment explains: the layout is full of a Flickable title, a Flickable metadata row and a Slider, "all of which consume MouseArea clicks. TapHandler observes taps without interfering with those drag interactions".

OBD panel

Hosts HomeOBDView; a MouseArea over the whole panel pushes "OBDMenu.qml" by string with { stackView, mainWindow } — straight to the gauges, bypassing OBDHome. Component.onCompleted and onHomeOBDParametersChanged call obdManager.refresh_values() so the cards are populated immediately.

Backend managers used

mediaManager, spotifyManager, settingsManager, obdManager (through HomeOBDView only settingsManager). No clock is drawn on this page; the clock lives in the BottomBar.

MediaRoom.qml

frontend/MediaRoom.qml (1880 lines) is the "now playing" view: large album art in an AlbumArtCarousel, transport controls, seek bar, an optional FFT visualizer and a blurred art background. Properties stackView / mainWindow are plain, so the BottomBar can push it with stackView alone.

Key features

  • Carousel — bound to the settings albumArtTransition (ten styles: Crossfade, Slide, Vinyl Lift, Dissolve, Flip, Coverflow, Conveyor, Stack, Depth, Swing), show3DAlbumPreview, roundedAlbumArt, albumArtCornerRadius, vinylRecordMode, sideCardAngle, sideCardOpacity, showAlbumArtShadow. onArtClicked opens albumArtPopup; onArtLoadFailed swaps in missing_art.png.
  • Blurred background — a Grid of repeated art tiles (backgroundGrid = "Normal" 1×1, "2x2", "4x4") with one MultiEffect blur applied to the whole grid ("16x cheaper on 4x4"), blurMax: 64, blur: backgroundBlurRadius / 64, layer.live: !_cardAnimBusy so the blur freezes during card animation, autoPaddingEnabled: false so the halo cannot bleed under the BottomBar (the StackView does not clip), and a black overlay at backgroundOverlayOpacity / 100.
  • Scrolling metadata — title and "artist • album" marquees whose scroll duration is settingsManager.textScrollSpeed (default 5000 ms).
  • Transport — Previous / Play-Pause / Next Controls with an X-axis "3D tilt" on press (show3DButtonTilt, buttonTiltDuration; 15° and scale 0.9 for prev/next, 25° and 0.85 for play), a Shuffle button bottom-left, a volume slider with mute icon at the top (routed through volumeController.applyVolume()), a Local/Spotify source toggle (green #1DB954 when Spotify) and a Spotify "Connect" button. There is no repeat button.
  • Seek bar — 75 % wide, commits on release to mediaManager.set_position() or spotifyManager.set_position().
  • Waveform visualizer — visible when showWaveformVisualizer && !useSpotify && !playlistEmpty; audioAnalyzer.get_num_bars() bars (fallback 96) as pill-shaped gradient rectangles in a Row with layer.enabled so 96 gradient draws collapse into one texture blit; fed by onFftDataChanged(levels), driven by analyze_file(), is_analyzed(), set_active(), update_position(). See Audio Analyzer.
  • Empty playlist — playlistEmpty = !useSpotify && localSongCount === 0 hides controls, seek bar, shuffle and visualizer and shows "No songs in this playlist yet"; the top-right download button is always visible. When the list goes from empty to non-empty (onMediaListChanged) the first file auto-plays.
  • Album-art popup — modal, CloseOnEscape | CloseOnPressOutside; on open it calls mediaManager.extract_colors_from_album_art() and offers "Save as Theme", which stores Style.albumArtTheme through settingsManager.save_custom_theme(name, json, artPath).
  • previewTrackTransition(direction, style) — runs one transition without a track change, temporarily overriding transitionStyle; the Now Playing Studio's live preview calls it when a chip is tapped.

Side-card preloading

Two hidden 1×1 Images (prevArtPreloader / nextArtPreloader, sourceSize 2×artSize, asynchronous, cache: true) decode the neighbouring art so a 3D transition never waits on a decode. sideCardRefreshTimer (interval: 0) fires on the next event-loop tick after any track, shuffle, queue or source change and makes one batched call, mediaManager.get_neighbor_album_arts() → [prev, next]; the comment says this "halves PySide6 bridge crossings" and keeps backend calls off the animation frame. For Spotify it parses get_previous_track_info() / get_next_track_info() instead.

MediaPlayer.qml

frontend/MediaPlayer.qml (2242 lines) is the library browser: a playlist dropdown, sortable column headers and a ListView of songs. Both stackView and mainWindow are required, which is why the BottomBar and MainMenu add mainWindow to the props only when pushing this page. The comment block at the top documents the Android singleton-function bug behind the local dp() wrappers.

Key features

  • Playlists — playlistNames (local) and spotifyPlaylistNames are merged into combinedPlaylists ({name, type}) for one dropdown popup; a 100 ms dropdownCooldown timer stops CloseOnPressOutside from immediately re-opening it. Long-pressing a local playlist (not "All Music" / "Unsorted" / Spotify) opens a delete dialog. A "new playlist" popup grows from dp(420) to 92 % × 82 % of the window when its inline QWERTY keyboard is toggled; every key handler ends with newPlaylistInput.forceActiveFocus().
  • Forced rebinding — playlistRefreshCounter is incremented when switching between local and Spotify lists (and by a 300 ms albumArtRefreshTimer); delegates read it in their bindings (var _ = mediaPlayer.playlistRefreshCounter) so art, title, artist, album and duration re-evaluate.
  • Song rows — ListView with reuseItems: true, cacheBuffer: height * 0.5, displayMarginBeginning/End: dp(40). Each row has a faint full-row art texture (opacity 0.10 when current, 0.03 otherwise, randomly offset by a name hash) and a thumbnail Image with sourceSize 1.5× its size, asynchronous, cache: true. Depth is faked with an 8 % opacity rectangle "instead of effects".
  • Highlighting — the current song's card is filled with App.Style.accent at 35 % alpha with a 2 px accent border and a left accent strip; while playing, a 6 dp accent bar pulses 0.7 ↔ 1.0 every 800 ms; the title turns accent-coloured. (The playingHighlightColor / pausedHighlightColor tokens in Style are not used here or anywhere else.)
  • Sorting — clickable TITLE / ARTIST / ALBUM headers with ↑/↓ arrows call mediaManager.sort_media_files(column, ascending).
  • Row actions — tap pauses the other source, sets settingsManager.mediaSource, plays, and pushes MediaRoom.qml unless returnToLibraryAfterSelection is set; a 600 ms long-press opens songActionMenu (move to playlist → move_song_to_playlist(), delete → confirm → delete_song()), local files only. No search field, no drag reorder.
  • Initial scroll — calculateScrollPosition() estimates the current row's offset from Spacing.mediaPlayerRowHeight, then scrollToCurrentTrack() sets contentY once the real list height is known (50 ms timer, onHeightChanged, after Spotify tracks load).
  • Download page — openDownloadPage() uses the same stackView._cachedDownloadPage pattern as MediaRoom but pre-selects the current local playlist (skipping "All Music" and "Unsorted") through syncDownloadPlaylist() → downloadManager.set_download_playlist().

Backend managers used

mediaManager, spotifyManager, settingsManager, downloadManager.

DownloadPage.qml

frontend/DownloadPage.qml (1951 lines) is the YouTube Music search-and-download screen backed by DownloadManager. It is never pushed by the BottomBar: MediaRoom.openDownloadPage() / MediaPlayer.openDownloadPage() create it once with a null parent, cache it on stackView._cachedDownloadPage, and on later calls pop back to it if it is already on the stack or push the cached instance again, refreshing downloadPlaylists from mediaManager.get_movable_playlist_names() each time. The page therefore keeps its search results and queue while the user navigates elsewhere.

Key features

  • Header — "Download Music", a status line that fades out 10 s after it changes, a "+" new-playlist button and a "SAVE TO" dropdown that calls downloadManager.set_download_playlist().
  • Search — a TextField whose onAccepted and the "Search" button both call downloadManager.search(text.trim()); a "⌨" button toggles the on-screen keyboard and calls searchInput.forceActiveFocus().
  • On-screen keyboard — onScreenKeyboard rectangle (visible: showKeyboard) with rows 1–0, Q–P, A–L, Z–M and a bottom row of ⌫ (1.5 keys), SPACE (4.5), red CLR (1.5) and SEARCH (2), keys sized dynamically for "5 rows (4 letter + 1 bottom), 10 keys wide". It exists for touch-only installs; the new-playlist dialog has a second inline keyboard.
  • Results — a ListView of 72 dp cards: cover thumbnail (or "♪"), title, artist, album, m:ss duration, an "E" explicit badge and, once downloaded, the playlist it landed in. The right-hand circle is the state: download icon, a Canvas progress ring with a percentage while downloading, green "✓" when downloaded, red "✗" when failed. Tapping a downloaded row pauses Spotify if needed, forces settingsManager.set_media_source("local"), plays via mediaManager.play_file_at_path(path) (falling back to play_downloaded_song()) and pushes MediaRoom; a failed row opens errorPopup with Retry; anything else (and the popup's Retry) goes through the page's startDownload(songJson), which calls downloadManager.download_song(songJson). There is no cancel control.
  • Android storage gate — startDownload() first checks downloadManager.hasStorageAccess() when isAndroid is true and the slot exists (only the C++ backend has it; on Python and desktop C++ access is always granted). If it is false it calls downloadManager.requestStorageAccess(), sets the status line to "Grant \"All files access\" in the settings screen, then tap download again" and returns without downloading.
  • Single-page search — results are whatever one search() returns; there is no "Load More" footer (ytmusicapi has no offset pagination, so neither backend can page).
  • Queue panel — a right-hand column (25 % of the width, clamped 200–350 dp) visible whenever queueModel.count > 0, with per-item status glyph, name, animated progress bar and a "Clear" button that removes completed/failed rows; completed rows are tappable to play.

Download manager signals handled

Connections {
    target: downloadManager
    function onSearchResults(jsonStr)                        // JSON array → searchResults
    function onSearchInProgress(inProgress)
    function onSearchError(msg)
    function onDownloadStarted(songId, songName)             // seeds activeDownloads[songId] = 0.0, queueModel row
    function onDownloadProgress(songId, progress)            // 0.0 .. 1.0
    function onDownloadComplete(songId, filePath)            // remembers the path for click-to-play
    function onDownloadError(songId, songName, errorMsg)
    function onDownloadStatusChanged(songId, field, valueJson) // patches one result, keeps contentY
    function onStatusMessage(msg)
}

Everything is keyed by song_id: activeDownloads (progress), downloadNames, downloadedPaths. The page does not guard downloadManager with typeof; both launchers register it unconditionally (the C++ app-store build compiles the manager out but still registers a stub, see Download Manager).

Backend managers used

downloadManager, mediaManager, spotifyManager, settingsManager.

OBDHome.qml

frontend/OBDHome.qml (427 lines) is the OBD hub the BottomBar's OBD button opens. Above a 2×2 card grid it shows a 48 dp status row — a dot that is green when connected, amber and pulsing while the status contains "Connecting", red otherwise — with the status text and an elided detail string, and beneath it a rolling connection log (connectionLogLineAppended, capped at 40 lines, monospace ListView that positionViewAtEnd()s). The comment explains the log: "Most useful on Android where the BLE state machine has many steps and silent failures are easy unless we surface each transition."

OBDMenu.qml

frontend/OBDMenu.qml (3198 lines) is the live-data page. Since the dashboards work it is a host for one active dashboard chosen from a registry, of which the original "Parameter Cards" grid is the built-in entry:

// Dashboard registry — built-in "grid" (parameter-cards view in this
// file) plus every JSON-defined dashboard enumerated by DashboardManager
// (presets + user-authored files).
readonly property var _gridSentinel: ({ id: "grid", label: "Parameter Cards", builtIn: true })
property var dashboardRegistry: _rebuildRegistry()     // [_gridSentinel].concat(dashboardManager.dashboards)
property string activeDashboardId: settingsManager.get_setting_with_default("activeDashboard", "grid")

The registry is rebuilt from dashboardManager.dashboardsChanged (every reference to dashboardManager is behind typeof so the page loads without the manager) and falls back to "grid" if the active id disappears. A Dashboards.DashboardRenderer fills the page with dashboardManager.loadDashboard(activeDashboardId) whenever the id is not "grid"; otherwise the GridLayout below is shown. The registry, chooser and editor hand-off are documented in depth in Gauges & Dashboards → OBDMenu Integration; this section covers the page itself.

The Parameter Cards grid

  • Repeater { model: App.OBDParameterModel.allParameters } — one card per parameter, hidden (and collapsed to zero size) unless settingsManager.get_obd_parameter_enabled(id, true); values come from App.OBDParameterModel.paramValues, so IMU ids appear as ordinary cards.
  • Column count is imperative, in updateLayout() behind a 100 ms debounce timer that also runs on resize: 2 columns for ≤4 enabled parameters, 3 for ≤9, 4 above that.
  • Behavior on displayValue { NumberAnimation { duration: 50; easing.type: Easing.Linear } } — "fast rolling effect".
  • Two card styles from the obdCardStyleCircular setting (live-switched via genericSettingChanged): a square card with title, value and a progress bar (100 ms OutCubic width behaviour), or a circular card whose 270° background/value arcs are QtQuick.Shapes PathAngleArcs ("GPU-accelerated Shape (no layer overhead)").
  • Colours come from the OBD tokens obdBoxBackground, obdBarColor, obdValueColor, obdLabelColor.
  • Only the RPM card is clickable: it opens the shift-light popup.

Header and chooser

A header strip shows the active dashboard's label. The square Dashboards button (objectName: "dashboardsButton", icon assets/dashboard_button.svg, hit area twice its size) is anchored to the outer content rectangle with the same margins as MediaPlayer's download button "so it sits pixel-for-pixel" in the same place across pages. It opens the modal chooser popup (up to 960 dp wide, CloseOnEscape | CloseOnPressOutside): a two-column grid of cards with live scaled miniatures (a second DashboardRenderer per card, pre-loaded from aboutToShow and faded in after a 180 ms settle so the gauges' start-up animation is hidden; the grid entry shows a 3×3 schematic). Scriptable names: newDashboardButton ("+ New" pushes dashboards/editor/DashboardEditor.qml with { stackView, callerPage }), resumeDraftButton ("▲ Draft", shown when the dashboardEditorDraft setting is non-empty), chooserScroll, dashCard_<id> and dashCard_<id>_edit / _duplicate / _delete (Copy on every JSON dashboard, Edit and Delete only when builtIn === false, Delete is a two-tap "Sure?" with a 3 s timer). openDashboardChooser() / closeDashboardChooser() exist for the command server's call action. A second, unnamed button in the chooser header opens the Primitives Gallery popup: eight GalleryTiles showing CircularGauge, ArcGauge, BarGauge (horizontal and vertical), LinearGauge, DigitalReadout, SparklineGauge and three WarningLights with hard-coded values — a dev screen marked for removal.

RPM shift-light popup

Clicking the RPM card opens a 92 % × 95 % modal editor for the shift-light flags: "Enable Shift Light" and "Show Indicator on Home" toggles, a Redline slider (rpm_max_rpm, clamping existing flags), an RPM bar with coloured range segments, "+ Add Flag", and per-flag controls — RPM low/high sliders, colour, flash + flash speed, full-screen overlay + opacity, aura overlay + opacity + spread. onOpened migrates the legacy single-rpm flag format to rpmLow/rpmHigh. It writes rpm_flags, rpm_shift_light_enabled, rpm_show_on_home_card, rpm_max_rpm and activeDashboard; the appearance keys it reads (rpm_shift_light_size, rpm_glow_size, rpm_glow_intensity, rpm_color_transition_speed, rpm_pulse_enabled, rpm_fullscreen_flash_opacity) have no UI anywhere and therefore stay at their defaults. The six DropShadows in this file are all inside this popup (its background and five toggle handles). Consumers of the flags are HomeOBDView and Main.qml.

Backend managers used

settingsManager, dashboardManager. OBDMenu does not reference obdManager at all — live values arrive through the OBDParameterModel singleton, and connection status is OBDHome's job.

OBDDiagnostics.qml

frontend/OBDDiagnostics.qml (685 lines) is the trouble-code reader. A 4×2 GridLayout holds four command buttons across the top — Read DTCs (read_dtc()), Current DTCs ("Active this drive cycle", read_current_dtc()), Read Status ("CEL & DTC count", read_status()), Freeze Frame (read_freeze_frame()) — a three-column terminal panel on the second row, and a red Clear DTCs button that opens a Dialog ("This will also reset the Check Engine Light and clear freeze frame data", "may affect emissions testing readiness") before calling clear_dtc(). There is no permanent-code (mode 0A) reader.

Output is the terminal

Every result is rendered as text in an inline terminal (QtObject { id: terminalOutput } with lines, maxLines: 50, appendLine(), clear(); #1a1a1a panel, "DIAGNOSTIC OUTPUT" header, a 3 % scanline canvas, a 530 ms blinking cursor, "> Awaiting command..." when empty, a BusyIndicator while isLoading). Lines are colour-coded by prefix ([ERROR], [DONE]/[SUCCESS], [INFO]/[SCAN], [WARN], [FOUND], [CLEAR], [DTC]). The page stores dtcCodes, dtcCount, milStatus and freezeFrameData, but none of them has a dedicated widget — freeze-frame data, for instance, is printed as one [DTC] line per entry. This page does not use the reusable TerminalFeedback component.

Connections {

Diagnostic mode lifecycle

Diagnostics need the polling loop paused. Component.onCompleted calls obdManager.enter_diagnostic_mode() and runs read_status(); onVisibleChanged re-enters or exits the mode as the page is covered and uncovered, because "StackView.push() doesn't destroy the page, so Component.onDestruction won't be called when navigating away"; Component.onDestruction is the fallback for real destruction. See OBD Manager → Diagnostics.

Backend managers used

obdManager only.

SensorMenu.qml

frontend/SensorMenu.qml (232 lines) is a 3×2 grid of BerryIMU readouts: SensorCards for PITCH, ROLL (bar = (value + 90) / 180), HEADING (value plus cardinal from headingToCardinal(), bar = value / 360), ALTITUDE and TEMPERATURE, and a GForceDisplay for lateral / longitudinal / magnitude. Below the grid, ZERO (berryIMU.calibrateTare()) and RESET (resetTare()) buttons appear while the IMU is connected.

Settings read in Component.onCompleted

KeyDefaultEffect
sensorDecimalPlaces1toFixed() precision everywhere
sensorTempUnit"F"Celsius → Fahrenheit conversion in tempDisplay()
sensorAltitudeUnit"m""ft" multiplies by 3.28084 in altDisplay()
sensorShowPitch, sensorShowRoll, sensorShowHeading, sensorShowGForce, sensorShowAltitude, sensorShowTemperaturetrueCard visibility; the temperature card is also hidden when berryIMU.hasTemperature === false

Emit rate, not sample rate
sensorEmitRate controls how often the IMU manager emits its signals into QML (10–120 Hz, default 60). The sensor read loop and the Madgwick filter keep running at their ~200 Hz target on the manager's own thread regardless; the setting only throttles the queued signal traffic. Main.qml separately drops the emission to 5 Hz whenever no page is showing IMU values (IMU Rate Gating, Hardware Managers → IMU emission).

The page subscribes to pitchChanged, rollChanged, headingChanged, altitudeChanged, accelMagnitudeChanged, lateralGChanged, longitudinalGChanged, baroTempChanged and connectionStatusChanged directly on berryIMU (it does not go through OBDParameterModel).

Backend managers used

berryIMU, settingsManager.

CarMenu.qml

frontend/CarMenu.qml (458 lines) renders the rigged 2003 Jeep TJ in a Qt Quick 3D View3D and rotates it with the live IMU attitude. It uses unversioned Qt 6 imports plus QtQuick3D, so it only loads when the optional module is present (CMake links Quick3D when found; SensorHome greys the card out otherwise). It requires stackView only; mainWindow is a plain property.

Scene

  • SceneEnvironment — clear colour #18232F, MSAA medium, no AO, lightProbe: Texture { source: "./assets/vehicle_studio.hdr" } at probeExposure: 0.8; a key DirectionalLight (brightness 1.3, ambient #777777) and a cool blue fill light (#C3D9FF, 0.7). No shadows.
  • Node { id: cameraOrbit } rotated by cameraPitch / cameraYaw (defaults −25 / −35) carries a PerspectiveCamera (45° FOV) whose distance is the larger of cameraDistance (200) and a value computed from jeep.radius and the view's aspect ratio to "fit the vehicle's rotation envelope even in a narrow view". A MouseArea over the view orbits the camera by drag (yaw 0.5°/px, pitch 0.3°/px clamped to ±89°).
  • Node { id: carModel; scale: 30 } — "Metre-scale TJ, +Z forward / +Y up, pivot at chassis centre" — containing JeepVehicle { id: jeep }, the rig described in Components → The Jeep TJ Rig.

IMU drives the body, buttons drive the rest

    function onRollChanged(val) { currentRoll = val }
    function onHeadingChanged(val) { currentHeading = val }
    function onAltitudeChanged(val) { currentAltitude = val }
    function onAccelMagnitudeChanged(val) { currentGForce = val }
    function onBaroTempChanged(val) { currentBaroTemp = val }
    function onConnectionStatusChanged(status) { imuConnected = (status === "Connected") }
}

The whole-body rotation is the only thing the sensor controls. A Flow of Buttons above the viewport (enabled once jeep.ready) toggles Driver door, Passenger door, Rear glass, Tailgate, Hood, Headlights, Fog lights, Brake lights and Reverse lights (each objectName: "jeepControl_<key>", checkable, bound to the matching jeep.* boolean), plus "Open all" (jeepOpenAll), "Close all", a Steer slider (jeepSteering, −1..1, sign-inverted into jeep.steeringInput), "Center wheels" (centerWheels), a "Spin wheels" toggle (jeepSpinWheels, 0 ↔ 10 km/h) and a wheel-speed slider (jeepWheelSpeed, −30..30 km/h) with a km/h label. While the rig is loading, a centred label reads "Loading Jeep…" or "Unable to load Jeep: <error>".

Bottom control panel

A #333333 bar at the bottom shows one of two rows. Connected: a green LIVE badge, ZERO (objectName: "imuZero" → berryIMU.calibrateTare()) and RESET (imuReset → resetTare()) buttons, and text readouts for pitch, roll, heading with cardinal, altitude in metres and barometer temperature in °C (the received G magnitude is not displayed). The two objectNames were added in commit 19d8904 so a script can level the vehicle before a capture. No IMU: a grey "NO IMU" badge, Start/Stop Sim, Reset and manual Pitch / Roll sliders (±90°); the simulation is a 50 ms timer writing 30·sin(t) pitch and 45·cos(1.5t) roll into carModel.eulerRotation.x/z, and it only runs while simulationRunning && !imuConnected. There are no gauge overlays around the viewport.

Backend managers used

berryIMU only (connected, the signals above, calibrateTare(), resetTare()). The page reads no settings.

ClockMenu.qml

frontend/ClockMenu.qml (137 lines) is a full-screen clock on a hard-coded #2c3e50 background: a dp(72) bold digital time, the date as Qt.formatDate(new Date(), "dddd, MMMM d, yyyy") in dp(24), and an analog face — a dp(200) circle with a white 3 dp border, hour hand dp(4) × 30 %, minute hand dp(2) × 40 %, a red 1 px second hand at 45 %, all with transformOrigin: Item.Bottom anchored to the centre, and an 8 dp centre dot.

There is no Timer: a Connections { target: clock } handles onTimeChanged(time), shows the string as-is, splits it on ":" and sets hourHand.rotation = (h % 12) * 30 + m / 2, minuteHand.rotation = m * 6 + s / 10, secondHand.rotation = s * 6. The string is "HH:mm[:ss][ AM|PM]" — the seconds field is absent when clockShowSeconds is off and the whole string is empty when showClock is off — so each field is read as parseInt(parts[i]) || 0 and a missing one counts as 0 instead of letting NaN reach the rotations. The page reads no settings; 12/24-hour formatting is whatever the clock manager emits (it follows clockFormat24Hour on the backend side).

The file declares required property StackView stackView and required property ApplicationWindow mainWindow and has no objectName. The only code path that instantiates it is Main.navigateTo("ClockMenu.qml"), whose map passes both stackView and mainWindow; no button in the UI leads here (tapping the BottomBar clock opens SensorHome). See Page Routing.

Backend managers used

clock.

PhoneMirrorView.qml

frontend/PhoneMirrorView.qml (538 lines): "OCTAVE's built-in scrcpy-protocol client streams the phone (or a virtual display on it) straight onto the VideoOutput below and forwards touch over the control socket. No external tools involved." It imports QtQuick.Controls.Basic and QtMultimedia. The BottomBar shows its button only when !isAndroid && settingsManager.phoneMirrorEnabled, reuses an instance already on the stack (found by the phoneMirrorView objectName it assigns at createObject), and otherwise creates a new one.

  • Video — a VideoOutput (PreserveAspectFit) whose videoSink is handed to the manager in Component.onCompleted (phoneMirrorManager.videoSink = videoSink); decoded frames land on it directly. frameCounter is bumped on every frameReady ("proof of life"); hasVideo = frameCounter >= 1.
  • Touch — a MultiPointTouchArea (1–10 points, mouseEnabled) maps each point through the letterboxed video.contentRect to 0..1 and calls phoneMirrorManager.injectTouch(pointId, action, relX, relY) with 0 pressed, 2 updated, 1 released/cancelled — real multitouch; mouse input arrives as one point.
  • Nav buttons — ◁ / ○ / ▢ call pressBack(), pressHome(), pressAppSwitch(); shown only while mirroring the phone's own screen (activeDisplaySize === ""), because a virtual display "shows system decorations, i.e. Samsung's DeX taskbar with its own back/home/recents along the bottom, which this row would cover".
  • Overlays — "Connecting..." until the first frame; a "Reconnecting to phone…" badge after 2 s of quiet reconnect; a "Phone is asleep / Waking it up… tap to retry" scrim (after 1.5 s of phoneAsleep, tap → wakePhone()); an "X" that calls stopScrcpy() and pops.
  • Errors and recovery — onScrcpyError(error) classifies device errors with /disconnected|No Android device|not authorized|offline/i. If video was already flowing, the view keeps the last frame and enters reconnecting: a 1 s timer polls getDeviceState() === "device" and restarts, giving up after reconnectGraceMs (10 s) — "a USB blip (the phone re-enumerates when picked up / put down) kills the session". On the error page, if setupOk (decoder, server and adb present via environmentOk()) and the failure was the phone, a 2 s timer keeps polling and restarts mirroring automatically ("a nudged cable in a vehicle is the normal case"); otherwise it shows getInstallInstructions(). Both timers run only while the page is StackView.Active.

Manager surface used: startScrcpy(), stopScrcpy(), isRunning, videoSink, activeDisplaySize, phoneAsleep, wakePhone(), injectTouch(), pressBack/Home/AppSwitch(), getDeviceState(), environmentOk(), getInstallInstructions(), nativeAvailable, serverVersion, adbPath, signals scrcpyStarted, scrcpyStopped, scrcpyError, frameReady. Protocol and manager details: Phone Mirror & Android Auto.

Backend managers used

phoneMirrorManager.

NowPlayingStudio.qml

frontend/NowPlayingStudio.qml (806 lines) is not a StackView page: Main.qml instantiates it once at z: 5 above the StackView and drives it through openNowPlayingStudio(originRect) / closeNowPlayingStudio(). The Media page's "Now Playing" tile (cardId === "media_now_playing", in both SettingsSidebarLayout and SettingsHubCard) maps its rectangle to window coordinates and opens it; any stackView.currentItemChanged or sidebar navigation closes it. Its header comment is the spec: "PiP locks top-right; left panel runs full height; BACKGROUND lives in the strip directly below the PiP. No nav bar, no settings tabs", followed by a visual standard (every setting is a full-width row, named spacing tokens, "adding a 30th setting adopts the same rhythm as the first") and copy-paste recipes.

  • Hero-morph — openProgress (0 = collapsed onto the originating tile, 1 = filling the target rect) interpolates x/y/width/height between originRect and targetX/Y/Width/Height, which Main.qml sets to exclude the BottomBar and, in the Sidebar layout, the settings rail; content opacity is max(0, (openProgress − 0.45) / 0.55) so "the user sees the card grow first and the controls resolve once there's room"; 320 ms OutCubic, disabled for the first frame so the studio does not appear to open itself at launch. Main.qml keeps it visible until openProgress returns to 0.
  • Header box — "→ Now Playing" with an accent underline, mirroring SettingsCardPopup's header, is the back control (closeRequested()); there is no X button.
  • Left panel sections — BACKGROUND (backgroundGrid Normal/2x2/4x4, backgroundBlurRadius, backgroundOverlayOpacity), ALBUM ART (roundedAlbumArt + albumArtCornerRadius, showAlbumArtShadow, vinylRecordMode, showWaveformVisualizer), 3D PREVIEW (show3DAlbumPreview, sideCardAngle, sideCardOpacity), ANIMATION & TEXT (textScrollSpeed, show3DButtonTilt, buttonTiltDuration) — built from SettingCategory, SettingSubcategory, SettingsSlider, SettingsToggle (compact), SettingLabel, ValueDisplay and NowPlayingButtonGrid. Every control writes the matching settingsManager.save_*() immediately and mirrors changes back through a Connections block.
  • PiP and strip — a MediaRoomLivePreview pinned top-right (height = 50 % of the studio, min dp(180)), with PRESETS (Minimal, Vinyl, Showcase 3D, Cinema — each a dict fanned out through applyPreset()) and TRACK TRANSITION chips beneath it "so the live PiP above shows the chosen animation fire as soon as a chip is tapped" (centerPip.previewTrackTransition(1, style)).

NowPlayingMiniToggle and NowPlayingVSlider exist in settings/ but the studio does not instantiate them (the mini toggle appears only in a recipe comment). More on the tile hosts in Settings UI → Now Playing Studio.

Design Decisions

Reasons recorded in the files' own comments or in the commits that introduced them.

Hub pages in front of feature pages

OBDHome and SensorHome exist so that the BottomBar has a stable landing place and a place to show connection state and logs, while still letting the button jump straight to the last-used subpage. Commit 0c29e64 shaped the rule that the hub records the subpage only after a successful push and that the BottomBar falls back to the hub and clears the stale key — a "sensor button that silently does nothing" was the alternative. Placeholder cards ("Coming soon") reserve the grid for planned features without hiding the layout.

One cached DownloadPage

Search results and the download queue are page state, and downloads keep running while the user drives elsewhere in the UI. Creating the page once with a null parent and parking it on the StackView (_cachedDownloadPage, "created once, reused across all navigations") keeps that state alive across navigations; every re-entry re-syncs the playlist list because it "may have changed while the page was cached".

Grid-as-a-dashboard

Rather than replace the original parameter-card grid when JSON dashboards arrived, OBDMenu registers it as the built-in "grid" entry with a schematic preview; existing ids "still resolve to the same dashboards — they just render from JSON via DashboardRenderer now". The active choice is one generic setting, and every reference to dashboardManager is guarded so the page still loads if the manager is absent.

Chooser actions as visible buttons

Card actions are always-visible buttons rather than long-press menus because long-press is "discoverability-hostile in a glance-and-go in-car UI"; the two-tap delete keeps a destructive action safe without a modal.

Diagnostics pause polling by visibility

OBDDiagnostics enters and leaves diagnostic mode from onVisibleChanged, not from creation/destruction, because a page underneath another on the StackView is neither destroyed nor visible; polling resumes as soon as it is covered.

Recover in the vehicle, not on the error page

PhoneMirrorView's quiet-reconnect and auto-restart timers exist because USB blips and nudged cables are the normal failure in a car; the last frame stays on screen and the session restarts itself the moment adb reports the device again, with the setup instructions reserved for genuinely missing tooling.

TapHandler over MouseArea on composite panels

MainMenu's media panel is a scrollable title, a scrollable metadata row and a slider; a MouseArea would steal their drags, so a TapHandler observes taps without interfering.

A window-level studio instead of a settings page

Editing Now Playing visuals needs the real MediaRoom in view while sliders move. NowPlayingStudio is a single overlay in Main.qml with a live MediaRoomLivePreview, opened with the same hero-morph as the settings card popups so it reads as "the tile grew", and sized to leave the BottomBar (and the sidebar) usable so navigation still works while it is open.
