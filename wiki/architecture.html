High-Level Architecture

OCTAVE is a backend/frontend split joined by Qt's signals and slots. The C++ / Qt 6 backend in src/ — built into every shipped binary (Windows .exe, macOS .dmg, Linux x86_64 and aarch64 AppImages, Android .apk) — owns all business logic, hardware I/O, network calls and data processing; the QML frontend in frontend/ owns rendering, animation and interaction.

Backend / Frontend Split

LayerTechnologyLocationResponsibility
Backend C++17 / Qt 6.7.3 (CMake 3.21+) src/managers/, src/util/, src/phone_mirror/, src/items/, src/platform/ Business logic, hardware I/O, API calls, data processing, state
Frontend QML (Qt Quick, Qt Quick 3D for the vehicle view) frontend/ UI rendering, animation, interaction, layout — loaded from disk at runtime (Android bundles it as assets:/frontend)
Bridge src/main.cpp src/ Instantiates managers, registers context properties and custom types, wires cross-manager signals, owns shutdown

Managers own hardware access and application state; QML consumes that state through the registered API. Some integrations explicitly cross the rendering boundary, such as frame providers, video sinks, and developer UI-driving tools. The only contract between them is the set of context-property names, signals, slots and properties (see Design Decisions).

Mobile builds
Android/iOS-specific code lives behind #ifdef Q_OS_ANDROID / Q_OS_MOBILE. Desktop-only managers keep their QML-facing API as stubs there, so QML needs nothing beyond typeof fooManager !== "undefined" guards for features legitimately absent on one platform.

The Manager Pattern

Every backend feature is a manager class inheriting QObject. It exposes state through Q_PROPERTY, Q_INVOKABLE / public slots and signals: 

// src/managers/examplemanager.h
class ExampleManager : public QObject {
    Q_OBJECT
    Q_PROPERTY(int value READ value NOTIFY valueChanged)
public:
    int value() const { return m_value; }
public slots:
    void setValue(int v) { m_value = v; emit valueChanged(v); }
signals:
    void valueChanged(int);
private:
    int m_value = 0;
};

Key principles:

  • Signals notify the UI (and other managers) when backend state changes
  • Slots are methods QML can call — many use snake_case names rather than the usual C++ camelCase (next_track, scan_library, connect_settings_manager), and QML calls them as written
  • Properties expose values with automatic binding updates
  • Managers are self-contained: each owns its state, timers and threads
  • src/appcore.cpp (AppCore, every manager as a member, no QML engine) wires cross-manager signals and passes dependencies where needed, for example settings references, the VolumeController fan-out to its outputs, and OBDAdapterFinder handing a connection to OBDManager.

Backend-QML Communication

Context Properties

Managers are registered as QML context properties on the engine's root context. That makes them globally visible in every QML file without an import: 

// src/main.cpp
QQmlContext *ctx = engine.rootContext();
ctx->setContextProperty("mediaManager", &mediaManager);
// QML
Button {
    onClicked: mediaManager.next_track()
}
Text {
    text: mediaManager.get_display_name(mediaManager.get_current_file())
}

Every context property must exist before engine.load(Main.qml): bindings are evaluated at first load, and an unregistered name is an error, not a late binding. src/main.cpp therefore builds the AppCore and exposes every manager (including dashboardManager, the last one) ahead of the load, and the dev runtime's beforeLoad() hook runs before it too, so --dev can point the real OBDManager at its simulated ELM327 before the QML is loaded.

Signals and Slots

Signals are the notification mechanism. QML reacts to them declaratively: 

// QML — react to a backend signal
Connections {
    target: mediaManager
    function onCurrentMediaChanged(filename) {
        albumArt.source = mediaManager.get_album_art(filename)
    }
}

Slots are methods QML calls, declared under public slots: or marked Q_INVOKABLE; a return value goes back to QML as a JS value:

Q_INVOKABLE QVariant loadDashboard(const QString &id);

Qt Properties

Properties combine a getter, an optional setter and a notify signal into one bindable value. QML re-evaluates any binding that reads the property when its notify signal fires. CONSTANT properties (e.g. diagnosticsManager.logDir) never notify and are read once.

Custom QML Types

One component is embedded as a QML item rather than a context property: the Android Auto frame item, registered with qmlRegisterType under the OCTAVE.AndroidAuto module: 

// src/main.cpp — src/items/embeddeddhuitem.h, a QQuickItem
qmlRegisterType<EmbeddedDhuItem>("OCTAVE.AndroidAuto", 1, 0, "EmbeddedDhuItem");
// QML
import OCTAVE.AndroidAuto 1.0

EmbeddedDhuItem { anchors.fill: parent }

Phone mirroring does not use a custom type: it binds a stock VideoOutput's videoSink to phoneMirrorManager.videoSink (see video paths). The frontend's own singletons (Style, Spacing, EnvironmentTheme, OBDParameterModel, WidgetCatalog, MusicDevicePreference) are declared in frontend/qmldir.

Application Startup Sequence

src/main.cpp runs logging first, then settings, then everything that depends on settings, then Main.qml, then the cross-manager signal wiring:

src/main.cpp

  1. Logging + crash handlers first — argv is scanned for --debug (and --smoke, which exits 0 five seconds after Main.qml loads; CI uses it to launch the packaged Windows build) and OctaveLog::install(debug) runs before QGuiApplication exists, so anything a manager constructor logs (and any crash) reaches the files.
  2. QGuiApplication — organization/application name OCTAVE; QQuickStyle::setStyle("Basic") so sliders are fully customisable.
  3. Auto-scale — screenAutoScale = min(width, height) / 720, clamped to 0.4–3.0. It scales off the shorter edge because Android reports the natural (portrait) size even when the app is locked landscape; using height alone gave a ~3× factor there.
  4. Scalar context properties — screenAutoScale, isAndroid.
  5. Phase 1 — SettingsManager (everything depends on it), UiWatchdog started, DiagnosticsManager, Clock, NetworkManager, VolumeController.
  6. Phase 2 — MediaManager, AudioAnalyzer. On Android the youtubedl-android bridge is initialised off-thread with QtConcurrent::run (first launch extracts Python + yt-dlp + ffmpeg, 10–20 s) and runtime permissions (READ_MEDIA_AUDIO, BLUETOOTH_CONNECT, BLUETOOTH_SCAN, …) are requested; a granted audio permission triggers a library scan.
  7. Phase 3 — empty (the "Online Features" header is left over; DownloadManager is created in Phase 5).
  8. Phase 4 — OBDManager, ShiftLightManager (fed by its rpmChanged), OBDAdapterFinder, ESP32VolumeManager, BerryIMUManager, GestureManager.
  9. Phase 5 — AndroidAutoManager + the dhuframe image provider, PhoneMirrorManager with its settings wiring (audio enable/gain, ducking → MediaManager::setDucking, phone-screen-off), qmlRegisterType<EmbeddedDhuItem>, DownloadManager (+ downloadComplete → scan_library(false)).
  10. Volume fan-out — VolumeController::volumeApplied → mediaManager.setVolume(linear), phoneMirrorManager.setVolume(linear), esp32VolumeManager.send_volume_update(percent) (desktop only; the ESP32 manager rate-limits itself). Then applyVolume(settingsManager.currentVolume()) restores the saved volume.
  11. QML import path — assets:/frontend on Android; on desktop frontend/ next to the binary, or one directory up (so build/octave finds the checkout's frontend/).
  12. assetStore (src/util/assetstore.{h,cpp}) — localUrl(relativePath) returns a file:// URL for a file under frontend/assets/. Needed because Quick3D's RuntimeLoader hands the path to Assimp, which cannot read assets:/ files inside an Android APK ("IO Error: File not found" in v0.9.2); on Android the file is extracted once into the app data directory (asset-cache/, re-extracted when its size changes after an update), on desktop the path is simply resolved. MusicDeviceScene.qml (modelUrl()) and JeepHinge.qml load every .glb through it; Qt's own loaders (images, HDR light probes, fonts) keep using assets:/ directly.
  13. Offline wiki — registers wikiViewerAvailable and wikiHomeUrl. Desktop WebEngine builds prefer the local wiki, then qrc:/wiki/index.html; Android WebView reads file:///android_asset/wiki/index.html. Without the relevant Qt module the reader is unavailable.
  14. Phase 6 — DashboardManager with setPresetsDir(frontend/dashboards/presets) and setUserDir(<appdata>/dashboards).
  15. Developer tooling (OCTAVE_DEV_TOOLS builds only) — OctaveDev::Runtime::beforeLoad() reads --dev / --profile / --command-port; without them it does nothing. A build without the option warns and ignores the flags. See Profiling and the Command Server.
  16. Load Main.qml — returns -1 if no root object was created; then Runtime::afterLoad() (dev overlay, perf monitor, command server) and setQuitOnLastWindowClosed(true).
  17. Hardware wiring — gesture actions → media / volume (track actions go to the phone while phoneMirrorManager.mediaActive()); ESP32 volumeChangeRequested(float) through a fractional accumulator; muteToggleRequested; on desktop the ESP32 LED colour sync (albumArtColorsChanged in theme mode, esp32LedStaticColorChanged in static mode, esp32LedColorModeChanged re-sends the current colour, cyan (0, 255, 255) when a colour is missing or unparsable) and, 500 ms after the knob reports "Connected", a push of the current volume, mute state and colour.
  18. Signals — on Unix desktop, SIGTERM/SIGINT are turned into QCoreApplication::quit() with the self-pipe trick (socketpair + QSocketNotifier) so the aboutToQuit cleanup still runs under systemd or Ctrl-C.
  19. app.exec().

Threading Model

The UI runs on the Qt main thread. Long-running work generally uses workers or asynchronous Qt APIs, with queued signals or timers returning results. There are exceptions: library scanning and parts of hardware initialization still execute on the GUI thread. The table describes the main paths:

ManagerThreading
OBDOBDConnectionWorker on a dedicated QThread owns a serial port or direct RFCOMM transport and a poll QTimer (interval 0 in fast mode, 50 ms otherwise). Android: the main thread owns the BLE link through the OctaveOBDBridge JNI class; no worker thread.
NetworkQNetworkAccessManager + QProcess (git) with QTimers.
DownloadDesktop: search and download run as QProcesses (scripts/ytmusic_search.py or yt-dlp). Android: search runs on QtConcurrent::run through the JNI bridge, and a QTimer polls the bridge for download progress.
MediaLibrary scan runs synchronously on the GUI thread. Desktop neighbour pre-cache and album-colour extraction use QtConcurrent::run; Android pre-cache is synchronous. Timers handle position, saved state and cache scheduling.
AudioAnalyzerQtConcurrent::run decodes with QAudioDecoder and runs an in-house radix-2 FFT; never touches GUI objects.
BerryIMU / GestureWorker QObject on its own QThread doing ioctl I²C reads (/dev/i2c-N).
ESP32 knobEvent-driven QSerialPort::readyRead on the main thread; reconnect / scan / keepalive / send-debounce QTimers.
Phone mirrorScrcpyClient runs the video/audio socket loops on a std::thread, decodes with libavcodec and pushes QVideoFrames to the sink.
UI watchdogQThread pinging the GUI thread.

OBD Worker Thread

Connecting to an ELM327 takes seconds (reset, protocol negotiation, supported-PID discovery), so it runs on a worker and reports progress by signal. The diagram is schematic (Android uses its JNI BLE bridge instead):

Main Thread OBD Worker Thread (QThread) │ │ │── create worker ──────────────►│ │ moveToThread(thread) │ │ thread.start() │ │ │── open port, ATZ / ATE0 ... │◄── connectionProgress(20, …) ─│ │ │── negotiate protocol │◄── connectionProgress(60, …) ─│ │ │── query supported PIDs │◄── connectionProgress(100, …)─│ │◄── connectionComplete ────────│ │ │ │ (watchdog QTimer on main) │── poll loop: TX cmd / RX reply │◄── value signals ─────────────│ (QTimer on the worker)

Every command and reply is logged on the octave.elm327 category (TX ... / RX ... (N ms)), so a failed session leaves a protocol transcript in the debug log (see logging).

Thread Pools and QtConcurrent

Short-lived work with a single result (an API call, a decode, a colour extraction) uses a pool rather than a hand-rolled thread: QtConcurrent::run + QFutureWatcher, whose finished signal arrives on the main thread. 

// MediaManager colour extraction
auto *watcher = new QFutureWatcher<QVariantMap>(this);
watcher->setFuture(QtConcurrent::run([this, imagePath]() {
    return _extract_album_colors(imagePath);
}));

Sensor Read Loops

The I²C sensors are read in a loop on their own thread (a BerryIMUWorker / gesture worker on a QThread), with values delivered to the main thread by signal. QTimers are used for the surrounding lifecycle — delayed start (1 s after construction), retry back-off, reconnect, the ESP32's 10 s port scan and 2 s keepalive — not for the sampling itself.

UI Watchdog

UiWatchdog (src/util/uiwatchdog.cpp) is started right after SettingsManager and stopped first in cleanup (after the dev runtime, when present). A worker thread posts a queued call to the GUI thread every 2 s and records when it is answered; if the GUI thread has been silent for more than 5 s it logs UI thread blocked for N s and counting on octave.ui_watchdog, then responsive again after N s when the loop drains. It is purely observational — it never kills or restarts anything.

Volume System

Volume uses a quadratic curve: the 0–100 slider percent becomes a linear 0.0–1.0 gain through 

linear = std::pow(percent / 100.0, 2.0);   // src/managers/volumecontroller.cpp  VolumeController::toLinearStatic()

The curve and its dispatch live in exactly one class, VolumeController, registered as volumeController. applyVolume(percent) clamps, stores the raw percent in SettingsManager (setCurrentVolume, idempotent), computes the linear value and fans it out:

OutputConnection to volumeApplied(percent, linear) in main.cpp
Local mediamediaManager.setVolume(linear)
Phone mirror audiophoneMirrorManager.setVolume(linear)
ESP32 LED ringesp32VolumeManager.send_volume_update(percent) (compiled out under Q_OS_MOBILE)

One call therefore drives all three outputs. The ESP32 manager adds its own 50 ms debounce, so the ring never sees more than 20 updates a second.

Every source of a volume change routes through the same entry point:

SourceCall
UI sliders (BottomBar.qml, MediaRoom.qml)volumeController.applyVolume(Math.round(value))
ESP32 knobSerial → volumeChangeRequested(delta) → accumulator in main → applyVolume(currentVolume + change)
Gesture sensorI²C → actionTriggered("volume_up"/"volume_down") → applyVolume(currentVolume ± gestureVolumeStep)
Startupmain.cpp calls applyVolume(settingsManager.currentVolume()) once, after the outputs exist

The knob sends fractional deltas; main.cpp accumulates them until a whole step is available:

// src/main.cpp
static float accumulator = 0.0f;
accumulator += delta;
if (std::abs(accumulator) >= 1.0f) {
    int change = static_cast<int>(accumulator);
    accumulator -= change;
    volumeController.applyVolume(settingsManager.currentVolume() + change);
}
Rule: never call mediaManager.setVolume(), phoneMirrorManager.setVolume() or esp32VolumeManager.send_volume_update() directly for a user-driven change, and never re-implement the curve. Go through volumeController.applyVolume() (or toLinear() for pure math in QML).

Video into QML: Image Provider vs QVideoSink

Two external video sources reach the scene graph by two different mechanisms, chosen by how the frames arrive:

Android Auto — image://dhuframe

Google's Desktop Head Unit is a separate process with its own window. OCTAVE launches it and captures the window with QScreen::grabWindow(). findDhuWindow() returns zero, so automatic embedded capture is incomplete (on Linux and macOS the capture falls back to the whole screen). See Android Auto limitations. Captured frames are plain QImages, so a QQuickImageProvider named dhuframe serves the latest one and QML re-requests it: 

// src/main.cpp
engine.addImageProvider(QStringLiteral("dhuframe"), androidAutoManager.frameProvider());

// QML
Image { source: "image://dhuframe/frame"; cache: false }

Phone mirror — QVideoSink

The phone streams H.264 over a TCP socket that OCTAVE decodes itself with libavcodec. Decoded YUV420P planes are wrapped in a QVideoFrame without an RGB conversion and pushed to the QVideoSink that QML's VideoOutput exposes, so the GPU does the colour conversion and the frame never becomes a QImage: 

// QML (PhoneMirrorView.qml) — inside the VideoOutput
Component.onCompleted: if (phoneMirrorManager) phoneMirrorManager.videoSink = videoSink

videoSink is a Q_PROPERTY(QObject*) on PhoneMirrorManager. Audio comes over a second socket as PCM and is played through a QAudioSink with a client-side gain (scrcpyAudioGain); sound detected in that PCM drives duckingChanged → MediaManager.setDucking() so local music dips under navigation prompts.

The Phone Server Fork

The Java program that runs on the phone during mirroring is OCTAVE's own fork of the scrcpy server (Apache-2.0, forked at v3.3.4, package org.octave.phoneserver), source in phone_server/. The prebuilt jar tools/phone-server/octave-phone-server is committed alongside it with its LICENSE and NOTICE; the build embeds all three as Qt resources (:/phone-server/) and writes the jar to a temp file at runtime, so no packaging target has to carry a loose file. The client pushes the jar over adb every session (the server's clean-up helper deletes it from /data/local/tmp once it is running) and speak the scrcpy 3.x protocol to it.

  • The version string must agree in two places or the server refuses to start: SCRCPY_VERSION_NAME in phone_server/build_without_gradle.sh and kServerVersion in src/phone_mirror/scrcpyclient.h — both 3.3.4-octave.
  • The phone-server CI job rebuilds the jar from source on every push and fails if the committed jar does not carry the expected package and version (a byte-level difference is reported as a warning because javac/d8 output differs across toolchains).
  • adb itself is bundled: scripts/fetch_platform_tools.py downloads Google's pinned platform-tools (SHA-256 verified) into the gitignored tools/platform-tools/<os>/, and CI ships it beside the binary. Google publishes no aarch64 build, so ARM boards fall back to the distro's adb.
  • Protocol byte layouts are documented in docs/PHONE_MIRROR_NATIVE_PLAN.md; re-verify them against DesktopConnection, control/ControlMessageReader and device/Streamer when pulling upstream changes.

Settings Persistence

All user settings live in one JSON file, settingsConfigure.json, under the directory returned by SettingsManager::getAppDataDir(). The same directory holds logs/, dashboards/ (user dashboards), metadata_cache.json (the media manager's persistent tag/cover store).

PlatformPath
Windows%APPDATA%\OCTAVE\
macOS~/Library/Application Support/OCTAVE/
Linux / Raspberry Pi$XDG_CONFIG_HOME/OCTAVE/, default ~/.config/OCTAVE/
AndroidSame code path as Linux: QDir::homePath() + "/.config/OCTAVE/", which resolves inside the app's private storage

Reads happen once: after the constructor has loaded and validated the file, the in-memory object is authoritative (loadSettings() returns m_settings without touching disk). Writes are coalesced: every setter calls saveSettings(), which updates memory, marks a pending flag and (re)starts a 500 ms single-shot timer; when it fires, flushPendingSave() writes the whole object atomically (QSaveFile: temp file, fsync, rename). Writes are not serialized across running application instances. OBD parameter selections have a separate 800 ms debounce, which flushPendingSave() does not drain. main.cpp explicitly flushes the main settings store on shutdown, but simultaneous instances can overwrite each other's settings. See Settings Manager for the registry, validation and every key.

Dashboards: JSON Specs + DashboardManager

OBD dashboards are data, not code. A dashboard is a JSON object with id, label, schema, a grid size and a list of cells, each naming a widget type from frontend/dashboards/WidgetCatalog.qml, a PID id from OBDParameterModel, a grid rectangle and per-widget props: 

{
  "id": "sport", "label": "Sport", "schema": 1,
  "gridColumns": 12, "gridRows": 8,
  "cells": [
    { "type": "DigitalReadout", "paramId": "SPEED",
      "col": 0, "row": 0, "colSpan": 6, "rowSpan": 7,
      "props": { "valueScale": 7.0, "padDigits": 3 } },
    ...
  ]
}
  • Sources — built-in presets in frontend/dashboards/presets/ (fullgrid, minimal, performance, sport, tj-wrangler) and user files in <appdata>/dashboards/. Ids must be unique across both; a user file that collides with a built-in id is rejected at load.
  • API (src/managers/dashboardmanager.h) — dashboards property (list of {id, label, builtIn, path}, built-ins first), loadDashboard(id), isBuiltIn(id), saveDashboard(spec), deleteDashboard(id) (hides a built-in), restoreBuiltInDashboards(), hiddenBuiltInCount, duplicateDashboard(sourceId, newLabel), refresh(), dashboardsChanged.
  • Hot reload — a QFileSystemWatcher on the user directory, debounced and compared against a (name, mtime, size) signature so OCTAVE's own atomic saves do not double-fire.
  • Rendering — frontend/dashboards/DashboardRenderer.qml instantiates the cells from the spec; the chooser in OBDMenu.qml shows every dashboard as a live miniature; frontend/dashboards/editor/DashboardEditor.qml is the in-app drag-and-drop editor (pure QML on top of the manager's save/duplicate/delete; an abandoned draft is rescued into settings and offered on the next chooser open).
  • Primitives — frontend/gauges/: CircularGauge, ArcGauge, BarGauge, LinearGauge, DigitalReadout, SparklineGauge, WarningLight, plus the self-binding GForceGauge and CompassGauge.

The full spec (binding API, every prop, parameter bindings, recipes) is docs/GAUGE_AUTHORING.md; the wiki page is Gauges & Dashboards.

The 3D Vehicle (CarMenu)

frontend/CarMenu.qml shows a rigged, lifted soft-top 2003 Jeep TJ (frontend/JeepVehicle.qml) in a Qt Quick 3D scene, rolled and pitched live by berryIMU, with working doors, hood, tailgate, lights, steering and spinning wheels. The model is an original reconstruction: the full frontend/assets/jeep_tj_2003.glb plus per-part GLBs under frontend/assets/jeep_tj/ with generated Rig.js / rig.json pivot metadata, built by tools/vehicle/build_jeep_tj.py and build_jeep_twin.py, then exported by export_jeep_twin.py (Blender, not needed at runtime). The photo references and the corrections they informed are catalogued in docs/vehicle/references.md.

Qt Quick 3D is optional at build time: CMakeLists.txt probes for it, and frontend/SensorHome.qml probes by creating the CarMenu.qml component and greys out the "3D View" card with "Requires the QtQuick3D module" when it fails. RuntimeLoader also needs Qt's assimp asset-import plugin; on distro Qt that is often a separate package (see BUILD.md). JeepVehicle.qml assembles the part GLBs with public Qt APIs rather than reaching into an imported scene's internals, so a rebuild of the asset set does not break the QML.

Logging, Crash Handlers and Diagnostics

OCTAVE runs in a car with no console attached, so "it was in the terminal" is not observability. It therefore writes rotating log files, leave a trace on crash, notice a hung UI, and let the user get the files off the head unit from the screen.

Log files — src/util/logger.cpp

OctaveLog::install(debug) runs before QGuiApplication and installs a qInstallMessageHandler that routes every qDebug/qCDebug/qInfo/ qWarning/qCritical/qFatal and every QML console.* call into the same logs/ directory while still echoing to stderr on desktop (on Android and iOS, where stderr goes nowhere, the line is handed to Qt's default handler instead so it reaches logcat / os_log). Managers use one Q_LOGGING_CATEGORY each (octave.media, octave.download, octave.elm327, octave.dashboards, octave.ui_watchdog, …). Without --debug the filter rule *.debug=false discards debug messages at the source, so they cost nothing.

Crash handlers

  • Unix: SIGSEGV/SIGABRT/SIGFPE/SIGILL/SIGBUS handlers write a ==== FATAL SIGSEGV ==== block and a backtrace_symbols_fd backtrace to octave-cpp-error.log over a raw descriptor opened at install time (no Qt in the signal path — not even OctaveLog::flush(), which the log files do not need because every line is flushed as it is written), then restore the default action and re-raise so the OS still produces its core / tombstone. Windows uses SetUnhandledExceptionFilter + CaptureStackBackTrace. Symbolise with addr2line -e octave against the same build. qFatal passes through the message handler first, which calls OctaveLog::flush() after a fatal message, so assertion text is on disk before the abort; the aboutToQuit handler calls the same flush last on a normal exit.

Getting logs out of the vehicle — DiagnosticsManager

Settings → Device → Diagnostics (frontend/settings/DeviceSettingsPage.qml) is backed by diagnosticsManager: recentLogLines(200) shows the tail of the main log followed by the error log; copyLogsToClipboard(400) prepends a version/device header; exportLogs() copies every current and rotated log file plus a device-info.txt into <Downloads>/OCTAVE-logs-<timestamp>/ (so on the Android head unit they can be attached from any mail or files app) and updates lastExportPath; openLogFolder() opens the directory in the OS file manager where canOpenFolder is true. Constant properties logDir, appVersion (from OCTAVE_VERSION, 0.9.5), backendName and deviceInfo feed the page header.

Profiling and the Command Server

Developer tooling lives in src/dev/, compiled in only with the OCTAVE_DEV_TOOLS CMake option (default on only for Debug desktop builds) and inert without its flags. --profile creates a PerfMonitor (event-loop latency, a thread-wake jitter probe, per-label timings, CPU / memory) writing CSV and log files to dev/perf/logs/, registers it as the perfMonitor context property, and starts a command server: a TCP server on 127.0.0.1:9876 (--command-port N to move it) that accepts newline-delimited JSON actions and runs the UI-driving ones (navigate, click, drag, capture, record) on the GUI thread. Both are stopped first on aboutToQuit and the report is written to the log. Dev mode (--dev) adds a simulated car.

  • OctaveDev::Runtime is created in main.cpp after the managers; the simulated car talks to the real OBDManager through a fake ELM327 QIODevice (OBDConnectionWorker::setCustomTransport(), OBDManager::setPortOverride()).
  • Hot paths are timed with OCTAVE_PERF_SCOPE (src/util/perfscope.h), which compiles to nothing without the option.

See Development for the protocol, the action list and the clients (MCP servers, screenshot and perf scripts in dev/) that drive the app over it.

Shutdown & Cleanup

src/main.cpp connects a cleanup handler to aboutToQuit. The dev runtime (when compiled in) and the watchdog stop first; the managers clean up next; playback state, the metadata store and settings are flushed after manager cleanup, and the log is flushed last: 

// src/main.cpp
QObject::connect(&app, &QGuiApplication::aboutToQuit, [&]() {
    devRuntime.shutdown();                 // OCTAVE_DEV_TOOLS builds only
    uiWatchdog.stop();
    androidAutoManager.cleanup();  phoneMirrorManager.cleanup();
    esp32VolumeManager.cleanup();  berryIMU.cleanup();  gestureSensor.cleanup();
    obdManager.close();
    downloadManager.cleanup();     networkManager.cleanup();
    mediaManager._save_playback_state();   // before the settings flush
    mediaManager.flush_metadata_store();
    settingsManager.flushPendingSave();
    OctaveLog::flush();                    // last: everything the cleanup logged reaches disk
});

On Unix desktop, SIGTERM/SIGINT reach this handler too (through the self-pipe), otherwise adb forwards, the DHU and the phone server would be orphaned when a launcher script or systemd stops the app. With --profile, OctaveDev::Runtime::shutdown() stops the command server and the perf monitor and writes the report.

Design Decisions — Why It Is Built This Way

Each rationale below is taken from a code comment, CLAUDE.md, BUILD.md or a design doc in the repository, not inferred.

One C++ tree for every platform

Every shipped artefact, including the Android APK, is built from one CMake tree by one CI matrix, so there is one packaging story (CMake plus Qt's own deploy tools) and native performance on the Orange Pi / Raspberry Pi head unit. The QML frontend is a separate layer that talks to the managers only through their registered names, so the UI can change without touching the backend and vice versa.

A manager per feature, registered as a context property

One QObject per feature keeps ownership obvious: each manager owns its state, timers and threads and cleans them up in cleanup(). Context properties (rather than QML singletons or qmlRegisterSingletonInstance) were chosen so the objects are constructed in a controlled order in one place, can be handed to each other before the QML exists (Clock(settingsManager), connect_settings_manager()), can be reconfigured by the dev runtime before the load (OBDManager::setPortOverride()), and are reachable in every QML file with no import. Custom QML types are reserved for things that must be items in the scene graph (the DHU frame item).

Mobile stubs in the headers instead of typeof checks everywhere

On Android, desktop-only managers such as ESP32, gesture, phone mirror and Android Auto expose stub APIs under Q_OS_MOBILE. These preserve the QML-facing names, though calls may report unavailability. BerryIMU is different: Android uses a QtSensors implementation. Some signal wiring is also platform-guarded. CMake currently defines Q_OS_MOBILE for Android; iOS builds are not wired up.

Threading rule: I/O off the main thread, results only by queued signal

The OBD connect, the sensor read loops, decoding and HTTP all run elsewhere because a 30 ms stall is visible on a dashboard gauge. Managers never call into QML from a worker; they emit signals, and Qt delivers them queued on the GUI thread. The UI watchdog exists because a frozen head unit in a car has nobody watching a terminal.

Settings in memory, one coalesced atomic write

Re-reading the JSON per key "cost a parse + validate on every slider release and every track change, and always returned what we had just written" (settingsmanager.cpp). The in-memory copy is now authoritative and disk writes are debounced 500 ms and written temp-file-then-rename, which also "spares the SD card on the Pi".

Volume curve in one place

A quadratic curve gives a more natural perceptual response than linear at low volume, but every output must apply the same curve or they drift apart as the slider moves. Centralising both the math and the dispatch in VolumeController means a curve change is a one-line edit and a new output is one more connection. The controller uses a signal fan-out (volumeApplied) rather than holding pointers so the controller could be constructed in Phase 1 before the outputs existed.

Image provider for the DHU, QVideoSink for the phone

The DHU is a foreign window that can only be captured, producing QImages at a timer rate; an image provider is the natural fit. The phone mirror is a stream OCTAVE decodes itself, so it hands YUV frames straight to the video sink and skips both the RGB conversion and the disk. Qt's own FFmpeg backend was rejected for the mirror because it refuses a raw Annex-B H.264 QIODevice (docs/PHONE_MIRROR_NATIVE_PLAN.md, Phase 0); libavcodec decodes at 12–15 % of one RK3588 core and paint the first frame in about a second.

Fork the phone server, bundle adb

The goal of the native mirror was "no user-installed dependencies": no scrcpy binary, no v4l2loopback, no ffmpeg on PATH, no adb shell input for touch. Forking the server (package renamed, version 3.3.4-octave) lets OCTAVE change the phone side (the keeper that survives locks and cable blips, the screen-off policy) while CI checks the committed jar's package and version (hash mismatches only warn). Bundling platform-tools avoids a separate adb installation on the desktop targets that bundle it; Linux aarch64 needs a compatible adb installed separately.

Dashboards as JSON, primitives as QML

Hand-written dashboard QML files could not be created by the user in the car. Moving the layout into a JSON spec rendered by DashboardRenderer made the in-app editor possible (pure QML on top of saveDashboard/duplicateDashboard/deleteDashboard), keeps built-ins and user files in the same format, and lets a file dropped into the user directory appear without a restart. The gauge primitives stay as QML because that is where the drawing belongs; the spec only names them.

QML loaded from disk, not compiled in

frontend/ is added to the import path and Main.qml is loaded from the file system (from assets:/frontend on Android) so a QML edit does not require a rebuild. The one exception is the .qsb shader, which must be a Qt resource because RHI's ShaderEffect rejects assets:/ URIs on Android.

Observability first

Logging is installed before the application object, crash handlers use raw descriptors so they work when Qt cannot, the watchdog records stalls, and DiagnosticsManager exists so the driver can export the logs from the screen. All of that follows from OCTAVE being daily-driven in a vehicle: in-car reliability and after-the-fact debuggability are first-order requirements, not polish. Errors are logged and surfaced through page-specific status text; a global notification layer is parked in TODO/error-notification-ui.md.
