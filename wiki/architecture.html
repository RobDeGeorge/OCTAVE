What OCTAVE Is Made Of

OCTAVE is one program written in C++ with Qt 6. It has two layers. Underneath is a core: a set of objects called managers, one per feature (music, the car's data, the phone, settings and so on). Each manager owns its feature completely: its state, its hardware, its files. On top is the screen, written in QML, Qt's language for user interfaces. The screen draws and reacts to touches. It holds no logic of its own: it reads values from the managers and calls their methods.

The same managers are also offered to other programs over a network protocol, the service. A web page, a script or a completely different screen can read and drive OCTAVE exactly as the built-in screen does. 

   the QML screen (frontend/)              other programs
   pages, gauges, the bottom bar           a web page, a script, another screen
            |                                        |
            |  by name: mediaManager, obdManager     |  the service protocol:
            |  (context properties)                  |  JSON over TCP or WebSocket
            v                                        v
  +---------------------------------------------------------------------+
  |  the core (AppCore): every manager, in one registry                 |
  |                                                                     |
  |  settingsManager   mediaManager   nowPlaying     volumeController   |
  |  obdManager        paramStore     tripRecorder   dashboardManager   |
  |  phoneMirrorManager   androidAutoManager   berryIMU   ...           |
  +---------------------------------------------------------------------+
            |
            |  worker threads, serial ports, Bluetooth, I2C, adb, the network
            v
   the car's OBD adapter, sensors, the volume knob, the phone, the music folder

Every build of OCTAVE comes from this one C++ tree: Windows, macOS, Linux (the Raspberry Pi and Orange Pi included), Android and the browser demo. There is no other backend.

This page is the map. Each manager has its own page with the detail; the table below links to them.

What a Manager Is

A manager is a C++ class that inherits from QObject, Qt's base class. Qt lets such a class publish three kinds of members that code outside it can use without knowing the class:

KindWhat it isExample
PropertyA value that announces when it changes.nowPlaying.title
Method (a slot, or a function marked Q_INVOKABLE)Something you can ask the manager to do.nowPlaying.togglePlay()
SignalAn event the manager announces.obdManager.connectionLostUnexpectedly(reason)

These three kinds are the whole contract between the core and anything that uses it. The screen and the service both work from them, which is why they see exactly the same thing.

Managers do not reach into each other. Where one needs another, AppCore either passes it in when it is built (most managers are given settingsManager) or connects a signal of one to a method of the other. For example, the OBD manager announces every reading, and AppCore connects that signal to paramStore, which holds the latest value of each reading for the gauges. All of these connections are in src/appcore.cpp, so there is one place to look to see who talks to whom.

To add a manager:

  1. Add its .h and .cpp to src/managers/ and list both in CMakeLists.txt.
  2. Add a member to AppCore in src/appcore.h. Members are built in the order they are declared, so put it after everything it needs.
  3. In the AppCore constructor, connect it and call expose("myManager", &myManager). That one line gives it its name on the screen and in the service.
  4. Say who may use it over the service with Q_CLASSINFO("octave.scope", "...") in the class. The scopes are explained in Utilities.
  5. Regenerate the published API. The commands are in Development.

How a Screen Talks to a Manager

At startup every manager in the registry is given to the QML engine as a context property: a name that is visible in every QML file with no import. From then on QML uses the manager by that name. 

Text {
    text: nowPlaying.title                 // a property: updates by itself when the track changes
}

Button {
    onClicked: nowPlaying.togglePlay()     // a method
}

Connections {                              // a signal
    target: obdManager
    function onConnectionLostUnexpectedly(reason) { notice.show(reason) }
}

Three things are worth knowing:

  • A binding to a property stays up to date. When the manager announces a change, QML evaluates the binding again. Nothing polls.
  • Every name must exist before Main.qml loads. A missing name is an error on first load, not something that fills in later. So the core is complete before the screen is created.
  • Many methods have two names. Older methods were written with underscores (next_track). Each now has a camelCase twin (nextTrack), and the underscore name is deprecated. Use camelCase in new code. The API reference marks the deprecated ones.

A few values the screen needs are not managers and are set directly in src/main.cpp: screenAutoScale (the screen's short side divided by 720, kept between 0.4 and 3), isAndroid, assetStore (file addresses for bundled assets), servicePairing (pairing codes for the service; on the screen only, never offered over the service), hasQuick3D and hasQuick3DAssetUtils (whether the 3D modules are installed), and wikiHomeUrl.

Two C++ types are registered as QML types, not as names: EmbeddedDhuItem (module OCTAVE.AndroidAuto), an item that draws Android Auto frames, and OBDManager (module OCTAVE.OBD), only so QML can use its connection-state values such as OBDManager.Connecting. The screen's own shared objects (Style, Spacing, EnvironmentTheme, OBDParameterModel, WidgetCatalog, MusicDevicePreference) are QML singletons listed in frontend/qmldir.

The Service: Other Programs

The QML screen is the reference screen, not the only possible one. The service offers every manager in the table above to other programs: lines of JSON over TCP, or WebSocket frames, on port 9876. A client can list what exists (describe), read a property (get), change one (set), call a method (call) and be told about changes (subscribe).

  • It is off unless you turn it on: with --service, or the serviceEnabled setting. It listens on this device only (127.0.0.1) unless --service-bind gives another address.
  • A program on another device must pair with a 6-digit code, and is given permission scopes (read, media, vehicle, ..., full) that decide what it may change.
  • octave --headless runs the core and the service with no screen at all. Another program is the screen. Desktop and Pi only.
  • The published API in docs/api/ is generated from the managers themselves (octave --dump-api) and has a version number, so a client knows what it can rely on.

The protocol, pairing, scopes and limits are in Utilities. Writing a Frontend is the walkthrough, and the API reference lists every member.

Startup

From here on the page is for people changing the code. This is what src/main.cpp does in a normal run, in order:

  1. Quick answers. --help, --version and --pair-code print and exit before anything is created. An unknown option gets a warning.
  2. Choose the config folder. Normally the one for your system (below); --config DIR picks another. --sim without --config uses a throwaway folder, so trying the simulator never touches a real install.
  3. Start logging and the crash handlers. This comes before any manager exists, so whatever a manager says while it is being built, and any crash, reaches the log files.
  4. Create the Qt application and the QML engine. The Qt Quick Controls style is set to Basic, which is what lets OCTAVE draw its own sliders.
  5. Find frontend/. Next to the program, or one folder up (so a build in build/ finds the checkout's). On Android it is inside the app package.
  6. Start the UI watchdog, then build the core. AppCore creates every manager, settings first, connects them, and enters each in the registry. Each manager is then given to the QML engine by name.
  7. Set up what only the screen needs: the Android Auto image provider, the two QML types, the QML import path, and the non-manager values listed above.
  8. Start the simulated car if --sim or --dev asked for it.
  9. Create the service if it was asked for. It does not listen yet.
  10. Load Main.qml. If it fails to load, OCTAVE logs why and exits.
  11. Start the service listening, now that the screen exists.
  12. Run. The event loop runs until the window closes or OCTAVE is told to stop. On Linux and macOS, Ctrl-C and a stop from systemd go through the same clean shutdown.

Managers start their own slow work after the event loop is running (looking for the OBD adapter, probing the sensors), so none of it delays the first frame.

Three runs take a different path after step 3 and never create a QML engine:

RunWhat happens
--headlessBuilds the core, starts the service, and runs with no window. If the service cannot start, it exits: nothing could reach it.
An installed program is the chosen screenThe same as --headless, and OCTAVE starts that program and watches it. If it keeps failing, OCTAVE starts again on the QML screen. --qml forces the QML screen for one run.
--dump-api DIRBuilds the core in a throwaway config folder, writes the published API to DIR and exits.

Threads

The screen and every manager's properties, methods and signals live on one thread, the main thread. If it waits on anything, the screen freezes. So anything slow or blocking runs on another thread and sends its result back as a signal, which Qt delivers on the main thread. A worker never touches QML or a manager's state directly.

WorkWhere it runs
Talking to the OBD adapterIts own thread, obd-worker. On Android there is no worker: a Java helper does it. See OBD Manager.
The black box's databaseIts own thread, trip-store.
The motion sensor and the gesture sensorOne thread each, reading the sensor in a loop.
Phone mirroringThe client's own threads for video, audio and messages from the phone. Video is decoded there and handed straight to the screen.
Built-in Android AutoIts own thread for the connection and the video decoder.
Reading tags and album art, album colours, the visualizer's analysis of a trackQt's shared thread pool: short jobs with one result.
The serviceOne thread for the server and one per connected client. Anything a client asks of a manager is run on the main thread.
The volume knob, the networkThe main thread. These are event-driven and never wait.
Rule: pass every new worker thread to sleepWhenIdle()
A thread that runs an event loop must be passed to sleepWhenIdle(thread) (src/util/threadidle.h). It does nothing on a normal build. In the browser build, such a thread with no running timer does not sleep: it uses a whole CPU core for as long as the page is open. The OBD worker and the black box's thread already do this.

The UI Watchdog

A frozen screen in a car has nobody watching a terminal. So a small thread asks the main thread to answer every 2 seconds. If no answer comes for 5 seconds it writes UI thread blocked for N s and counting to the log, and responsive again after N s when the screen comes back.

On desktop Linux it also acts (not on Android, where nothing would start the app again). After 15 seconds it writes what every thread was doing to hang-<time>.txt in the log folder (this needs gdb installed). After 30 seconds it ends the program so the launcher can start it again, which is better than a dead screen that only pulling the power clears. It never does this in the first 2 minutes after launch, when a first scan of a large music library can keep the main thread busy.

Volume System

Volume has one entry point: volumeController.applyVolume(percent), with 0 to 100. Mute is volumeController.toggleMute(). The sliders on the screen, the volume knob, the gesture sensor and the service all call these two and nothing else.

The controller turns the percent into a gain with a quadratic curve, (percent / 100)², which sounds more even to the ear than a straight line: 50 % is a quarter of full gain. It then sends the result to every output at once: OCTAVE's own player, the mirrored phone's audio, Android Auto, AirPlay, Spotify while it is the source, and the knob's light ring.

Rule: never set an output's volume yourself
Do not call a manager's own setVolume or setMuted for a change the user made, and do not write the curve anywhere else. If every output does not use the same curve, they drift apart as the slider moves. In QML, bind to volumeController.percent and muted.

The mute rules and the rest of the controller are in Utilities.

Video on the Screen

Video from a phone reaches the screen in one of two ways, depending on how the frames arrive.

SourceHow it gets to the screen
Phone mirroring, built-in Android Auto, AirPlayOCTAVE receives a compressed video stream (H.264) and decodes it itself with one shared decoder (src/util/h264decoder). Each decoded frame goes straight to the video sink of a QML VideoOutput, which the manager exposes as its videoSink property. The graphics card does the colour conversion.
Android Auto through Google's Desktop Head UnitThat is a separate program with its own window. OCTAVE captures its picture and serves the latest one to QML through an image provider, image://dhuframe.

The built-in Android Auto receiver is the code in src/android_auto/. It makes OCTAVE the car's head unit: it speaks the Android Auto protocol to the phone, with no Google software on the OCTAVE side. It is only compiled when the build has OpenSSL and FFmpeg, on desktop (build options). How to use it, what works and how it is put together are in Phone Mirror & Android Auto.

File or folderWhat

Settings are read from disk once, at startup. After that the copy in memory is the truth. A change is written back half a second later, so a slider being dragged causes one write, not hundreds. The write goes to a temporary file that then replaces the real one, so a power cut in the middle leaves the old file whole. Pending changes are written on shutdown.

Logging

OCTAVE runs in a car with no terminal attached, so everything it has to say goes to files. They are in logs/ inside the config folder:

FileWhat is in itSize limitOld copies kept
octave-cpp.logEverything at info level and above. Start here.5 MB3
octave-cpp-error.logWarnings and errors only, and the trace of a crash.2 MB5
octave-cpp-debug.logEverything, including debug messages. Only written when OCTAVE is started with --debug.10 MB2

When a file reaches its limit it is renamed with .1 at the end, the older copies move up a number, and the oldest is deleted. A line looks like this: 

2026-09-10 12:00:00.123 | INFO    | octave.media | mediamanager.cpp:123 | Library scan complete

The third column is the category, which says which part of OCTAVE wrote the line: octave.media, octave.elm327, octave.dashboards, octave.ui_watchdog and so on. Search for it to follow one part. Messages from QML (console.log) land in the same files.

  • On a computer every line is also printed to the terminal. On Android it goes to logcat as well as the files.
  • Without --debug, debug messages are dropped before they are even built, so they cost nothing.
  • When OCTAVE crashes, it writes a block starting ==== FATAL SIGSEGV (or the signal that happened) and the list of code addresses it was in to octave-cpp-error.log, then lets the system handle the crash as usual. Turn the addresses into function names with addr2line -e octave against the same build.
  • When the screen freezes, the UI watchdog says so in the same log.

Getting the logs out of the car. Settings > Device > Developer > Diagnostics shows the end of the log on the screen, copies it to the clipboard, or exports every log file with a description of the device to an OCTAVE-logs-<time> folder in Downloads. See Utilities for the details and Troubleshooting for what to look for.

In C++, log through a category (Q_LOGGING_CATEGORY with qCInfo, qCWarning, qCDebug), not bare qDebug(), so the line can be found by its category.

Platforms

All platforms build from the same code. A feature that a platform cannot have is replaced by a stand-in with the same name and members that does nothing, so the screen never has to ask which platform it is on.

PlatformWhat is different
Linux, Raspberry Pi, Orange PiEverything is available. This is the platform the car's head unit runs.
Windows, macOSNo AirPlay, and no built-in Bluetooth pairing for OBD adapters (pair in the system's settings). The motion and gesture sensors are read over Linux's I2C interface, so they are not available.
AndroidThe volume knob, gesture sensor, phone mirroring and Android Auto are stand-ins. The motion readings come from the phone's own sensors. The car is reached over Bluetooth LE through a Java helper. No --headless.
Browser demoA browser has no serial ports, no Bluetooth as Qt knows it, and cannot start other programs. An OBD adapter is reached through the browser's own Web Bluetooth or Web Serial, or you pick the simulated car. The service is offered to the page itself, not on a network port. See Building.
iOSNot built yet.

In the code, Q_OS_MOBILE is defined for Android and the browser and selects the stand-ins; OCTAVE_WASM marks the browser alone. New code that starts another program must be inside #if QT_CONFIG(process), and new hardware code must be kept out of the browser build with OCTAVE_WASM, or that build breaks. Optional parts are switched by what the build finds: OCTAVE_HAVE_FFMPEG (the video decoder), OCTAVE_HAVE_NATIVE_AA (built-in Android Auto), OCTAVE_HAVE_AIRPLAY. See Building.

Simulator and Developer Tools

OptionIn which buildsWhat it does
--simEvery buildA simulated car. It is a simulated adapter underneath the real OBD manager, so the real code runs. Uses a throwaway config folder unless --config is given.
--devDebug buildsThe simulated car on your usual config, and a developer overlay on the screen.
--profileDebug buildsA performance monitor, and the service with extra actions that drive the screen (navigate, tap, capture) for test scripts.

The developer tools are in src/dev/ and are compiled only with the OCTAVE_DEV_TOOLS build option, which is on by default for desktop Debug builds and off for everything else. A build without them warns and ignores --dev and --profile. To time a piece of code, put OCTAVE_PERF_SCOPE("label") at the top of the function; it compiles to nothing without the option. Everything else is in Development.

Shutdown

When OCTAVE quits, things stop in an order chosen so that nothing is cut off mid-write:

  1. The developer tools, when present, so a performance report or recording is finished.
  2. The service, so no client reaches a manager that is shutting down.
  3. The UI watchdog.
  4. The managers (AppCore::shutdown()): Spotify is paused, then the phone connections, the knob and the sensors stop. The black box closes the current drive and writes its files before the OBD connection closes. Last, the playback position, the library data and any pending settings are written.
  5. The log is flushed.
  6. The QML engine is destroyed while the managers still exist, so no binding is left reading a manager that is gone.

Closing the window, Ctrl-C and a stop from systemd all take this path. That matters: without it the programs OCTAVE started and its adb connections to the phone would be left running.

Why It Is Built This Way

  • One C++ tree for every platform. One build system, one set of packages, and native speed on the small computer in the car.
  • One manager per feature. It is always clear who owns a piece of state, a timer or a thread, and who must clean it up.
  • The core knows nothing about QML. Because AppCore builds and connects everything without a QML engine, the same core runs headless, serves other screens, and can be tested without a window.
  • One registry for the screen and the service. A manager is entered once and both see it, so the two can never disagree about what exists.
  • Managers are named objects created in one place, not QML singletons. That gives a fixed build order, lets managers be handed to each other before any QML exists, and lets the simulator be plugged in before the screen loads.
  • Stand-ins for missing features. A platform without a feature gets an object with the same members that does nothing, so the QML is the same everywhere.
  • Slow work off the main thread, results by signal. A stall of a few hundredths of a second is visible on a gauge needle.
  • Volume in one place. Every output must use the same curve. One controller that sends to all of them makes a new output one more connection and a change of curve one edit.
  • The QML is loaded from files, not compiled in. A change to the screen needs no rebuild.
  • Failures must reach the log files. OCTAVE is driven daily in a car. Logging starts before anything else, crashes and freezes leave a trace, and the logs can be exported from the screen, so a problem on the road can be understood afterwards.
