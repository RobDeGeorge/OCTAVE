High-Level Architecture

OCTAVE is a backend/frontend split joined by Qt's signals and slots. The Python / PySide6 backend in backend/ + main.py owns all business logic, hardware I/O, network calls and data processing; the QML frontend in frontend/ owns rendering, animation and interaction. The backend runs on desktop platforms only (Linux, Raspberry Pi / Orange Pi, Windows, macOS).

Backend / Frontend Split

LayerTechnologyLocationResponsibility
Backend Python 3.10+ / PySide6 6.8+ backend/ Business logic, hardware I/O, API calls, data processing, state. Runs from a checkout; never packaged.
Frontend QML (Qt Quick, Qt Quick 3D for the vehicle view) frontend/ UI rendering, animation, interaction, layout — loaded from disk at runtime
Bridge main.py repo root Instantiates managers, registers context properties, the custom type and the image provider, wires cross-manager signals, owns shutdown

Managers own hardware access and application state; QML consumes that state through the registered API. A few integrations cross the rendering boundary on purpose: the embedded Android Auto window, the phone mirror's video sink, and the developer-local command server that drives the UI. The contract between the two layers is the set of context-property names, signals, slots and properties. Where QML branches on isAndroid, the branch is never taken here: main.py sets it to False.

The Manager Pattern

Every backend feature is a manager class inheriting QObject that exposes state through PySide6's Property, Slot and Signal: 

# backend/example_manager.py (illustrative)
from PySide6.QtCore import QObject, Signal, Slot, Property

class ExampleManager(QObject):
    valueChanged = Signal(int)          # QML listens to these

    def __init__(self):
        super().__init__()
        self._value = 0

    @Slot(int)                          # callable from QML
    def setValue(self, v):
        self._value = v
        self.valueChanged.emit(v)

    @Property(int, notify=valueChanged)  # bindable from QML
    def value(self):
        return self._value

Key principles:

  • Signals notify the UI (and other managers) when backend state changes
  • Slots are methods QML can call; names follow what the QML calls, so camelCase and snake_case both occur (applyVolume, next_track, scan_library)
  • Properties expose values with automatic binding updates
  • Managers are self-contained: each owns its state, timers and threads and releases them in cleanup() (or close() for OBD)
  • main.py wires cross-manager signals and passes dependencies: Clock(settings_manager), connect_settings_manager(settings_manager) on the media, ESP32, BerryIMU, gesture and download managers, the output managers handed to VolumeController, and OBDAdapterFinder.set_obd_manager()

Backend-QML Communication

Context Properties

Managers are registered as QML context properties on the engine's root context. That makes them globally visible in every QML file without an import: 

# main.py
engine.rootContext().setContextProperty("mediaManager", media_manager)
// QML
Button {
    onClicked: mediaManager.next_track()
}
Text {
    text: mediaManager.get_display_name(mediaManager.get_current_file())
}

Every context property must exist before engine.load(Main.qml): bindings are evaluated at first load. main.py therefore registers every manager (dashboardManager last) at module level, and keeps the two steps that differ in dev mode behind functions: install_obd_manager(manager) registers obdManager and hands it to the adapter finder, and load_main_qml() loads frontend/Main.qml.

Signals and Slots

Signals are the notification mechanism. QML reacts to them declaratively: 

// QML — react to a backend signal
Connections {
    target: mediaManager
    function onCurrentMediaChanged(filename) {
        albumArt.source = mediaManager.get_album_art(filename)
    }
}

Slots are methods QML calls, declared with @Slot(); result= declares the return type:

# backend/dashboard_manager.py
@Slot(str, result='QVariant')
def loadDashboard(self, dashboard_id: str):
    ...

A slot declared with argument types (@Slot(int, result=str)) needs those arguments from QML even when the Python function has defaults, which is why the QML always passes them (diagnosticsManager.recentLogLines(200)).

Qt Properties

A Property combines a getter, an optional setter and a notify signal into one bindable value. QML re-evaluates any binding that reads the property when its notify signal fires. constant=True properties (e.g. diagnosticsManager.logDir) never notify and are read once.

Custom QML Types

One component is embedded as a QML item rather than a context property: the Android Auto embedding item, a QQuickItem in backend/android_auto/embedded_dhu.py, registered under the OCTAVE.AndroidAuto module: 

# main.py
qmlRegisterType(EmbeddedDhuItem, "OCTAVE.AndroidAuto", 1, 0, "EmbeddedDhuItem")
// QML
import OCTAVE.AndroidAuto 1.0

EmbeddedDhuItem { anchors.fill: parent }

Phone mirroring does not use a custom type: it binds a stock VideoOutput's videoSink to phoneMirrorManager.videoSink (see video paths). The frontend's own singletons (Style, Spacing, EnvironmentTheme, OBDParameterModel, WidgetCatalog, MusicDevicePreference) are declared in frontend/qmldir.

Application Startup Sequence

main.py does its work in a fixed order — logging first, then the Qt application and engine, then settings, then everything that depends on settings, then signal wiring, then Main.qml. Everything up to the signal handlers runs at module level when the file is imported; only the OBD manager, the QML load, the smoke timer, profiling and app.exec() sit under if __name__ == "__main__":.

main.py, step by step

  1. Environment — QT_QUICK_CONTROLS_STYLE=Basic is set before any Qt import, so sliders are fully customisable.
  2. Arguments — argparse with --debug, --profile and --smoke (load Main.qml, run 5 s, exit 0); parse_known_args, so Qt flags pass through.
  3. Logging first — setup_logging(debug=args.debug) runs before any other backend import; it also installs the crash handlers and gives python-obd's logger the same handlers. The detected OS is logged.
  4. Imports — every manager is imported unconditionally; there is no platform branching here. Heavy optional libraries are deferred inside the modules via backend/lazy_import.py (see why).
  5. Offline wiki — if PySide6.QtWebEngineQuick imports, QtWebEngineQuick.initialize() runs (on Linux, after appending --disable-gpu to QTWEBENGINE_CHROMIUM_FLAGS unless already present) and wikiViewerAvailable becomes true.
  6. QApplication (from QtWidgets) — auto-scale is min(width, height) / 720 of the primary screen's availableSize(), clamped 0.4–3.0 (1.0 with no screen). Using the shorter edge gives the same factor for a landscape or portrait report.
  7. Engine — QQmlApplicationEngine; context properties wikiViewerAvailable, wikiHomeUrl, screenAutoScale; qmlRegisterType(EmbeddedDhuItem, ...); frontend/ import path; isAndroid = False; assetStore.
  8. Managers in dependency order — SettingsManager; UiWatchdog.start(); DiagnosticsManager; Clock; MediaManager (+ connect_settings_manager); AudioAnalyzer; OBDAdapterFinder(None, settings_manager) (its OBD manager arrives later); AndroidAutoManager + engine.addImageProvider("dhuframe", ...); PhoneMirrorManager + its settings and media wiring; ESP32VolumeManager; VolumeController (holding settings, media, phone mirror and ESP32) and applyVolume(settings_manager.currentVolume); BerryIMUManager; GestureManager; NetworkManager; DownloadManager (+ rescan on downloadComplete); DashboardManager with setPresetsDir(frontend/dashboards/presets) and setUserDir(<appdata>/dashboards).
  9. Signal wiring — gesture actions, ESP32 accumulator + mute, ESP32 LED colour sync (album-art accent or static colour), initial ESP32 state 500 ms after it reports "Connected" (see the graph).
  10. Shutdown hooks — cleanup_on_quit() on aboutToQuit; SIGTERM/SIGINT call app.quit(), with a 500 ms no-op QTimer (_signal_pump) so the interpreter gets a chance to run the signal handler while blocked in app.exec().
  11. __main__ — install_obd_manager(OBDManager(settings_manager)); load_main_qml() (sys.exit(-1) without root objects); with --smoke a 5 s single-shot app.exit(0); with --profile setup_perf_profiling(); sys.exit(app.exec()).
Why the OBD manager is installed late
main.py is importable. The developer-local dev/main_dev.py does import main (which runs all the module-level startup above), then dev/dev_runtime.install_dev_runtime(main) calls install_obd_manager(MockOBDManager(...)), and only then main.load_main_qml(). Keeping the registration behind one function and the QML load behind another lets developer mode swap in simulated OBD data without patching the production entry point. The headless boot test (tests/test_boot.py) runs the real __main__ path offscreen.

Threading Model

The UI runs on the Qt main thread. Long-running work generally runs on worker threads, with queued signals, run_on_main() (backend/qt_threading.py) or a polling QTimer bringing results back. There are exceptions: the library scan and parts of hardware initialisation run on the GUI thread. The main paths:

OBD Worker Thread

Connecting to an ELM327 takes seconds (adapter reset, protocol negotiation, supported-PID discovery inside python-obd), so OBDConnectionWorker.do_connect() runs on a QThread and reports progress by signal:

Main Thread OBD Worker Thread (QThread) │ │ │── OBDConnectionWorker() ──────────►│ │ set_params(port, fast, timeout, │ │ cached protocol) │ │ moveToThread(); thread.start() │ │ │── started → do_connect() │◄── connectionProgress(20, …) ──────│ │ │── obd.Async(port, fast=…, timeout=…, │ │ delay_cmds=0, protocol=…) │◄── connectionProgress(80, …) ──────│ │◄── connectionProgress(90, …) ──────│── read VIN / extra supported PIDs │◄── vehicleInfo(vin, pids) ─────────│ │◄── connectionComplete(conn, status)│ │ │ │ CAR_CONNECTED: watchers, conn.start() (python-obd's own polling thread), │ monitor thread (2 s), scan_vehicle() after 2 s, data watchdog (5 s) │◄── value signals (from python-obd callbacks)

python-obd logs every command and reply at DEBUG (write: / read:) on its own obd logger, which setup_logging() attaches to OCTAVE's handlers, so a failed session leaves a protocol transcript in octave-debug.log when run with --debug (see logging).

Thread Pools and Polled Futures

Short-lived work with a single result (an API call, a decode, a download) uses concurrent.futures.ThreadPoolExecutor rather than a hand-rolled thread. The futures are checked by a QTimer on the main thread, so the result is handled there and the pool thread never touches a Qt object: 

# backend/download_manager.py
self._executor = ThreadPoolExecutor(max_workers=2)
self._poll_timer = QTimer()
self._poll_timer.setInterval(200)
self._poll_timer.timeout.connect(self._poll_futures)

Sensor Read Loops

The I²C sensors are read in a loop on a daemon thread each, with values delivered to the main thread by signal. QTimers are used for the surrounding lifecycle — delayed start (1 s after construction for the IMU and gesture sensor), retry back-off, reconnect, the ESP32's 10 s port scan and 2 s keepalive — not for the sampling itself. Work a worker thread hands back to the GUI thread goes through run_on_main(), because a QTimer.singleShot started on a plain Python thread never fires.

UI Watchdog

UiWatchdog (backend/ui_watchdog.py) is started right after SettingsManager and stopped first in cleanup. A daemon thread emits a queued signal to the GUI thread every 2 s and records when it is answered; if the GUI thread has been silent for more than 5 s it logs UI thread blocked for N s and counting on octave.ui_watchdog, then UI thread responsive again after N s when the loop drains. It is purely observational — it never kills or restarts anything. Details on Utilities.

Volume System

Volume uses a quadratic curve: the 0–100 slider percent becomes a linear 0.0–1.0 gain through 

linear = (percent / 100.0) ** 2.0      # backend/volume_utils.py  to_linear(), input clamped to 0–100

The curve and its dispatch live in one class, VolumeController, registered as volumeController. Before it existed the curve was hard-coded in about nine call sites across main.py and QML (module docstring), and changing it meant editing every site in lockstep. applyVolume(percent) clamps to 0–100, stores the raw percent in SettingsManager (setCurrentVolume), computes the linear value and calls each output the controller was constructed with (any may be None):

OutputCall
Local mediamedia_manager.setVolume(linear)
Phone mirror audiophone_mirror_manager.setVolume(linear)
ESP32 LED ringesp32_manager.send_volume_update(percent)

The ESP32 manager adds its own 50 ms send debounce, so the ring never sees more than 20 updates a second.

Every source of a volume change routes through the same entry point:

SourceCall
UI sliders (BottomBar.qml, MediaRoom.qml)volumeController.applyVolume(Math.round(value))
ESP32 knobSerial → volumeChangeRequested(delta) → accumulator in main.py → applyVolume(currentVolume + change)
Gesture sensorI²C → actionTriggered("volume_up"/"volume_down") → applyVolume(currentVolume ± gestureVolumeStep)
Startupmain.py calls applyVolume(settings_manager.currentVolume) once, right after the controller is built

The knob sends fractional deltas; main.py accumulates them until a whole step is available:

# main.py — handle_esp32_volume_change()
_volume_accumulator += delta
if abs(_volume_accumulator) >= 1.0:
    change = int(_volume_accumulator)
    _volume_accumulator -= change
    volume_controller.applyVolume(settings_manager.currentVolume + change)
Rule: never call mediaManager.setVolume(), phoneMirrorManager.setVolume() or esp32VolumeManager.send_volume_update() directly for a user-driven change, and never re-implement the curve. Go through volumeController.applyVolume() (or toLinear() for pure math in QML). tests/test_smoke.py::test_volume_curve_math guards the curve.

Video into QML: Image Provider vs QVideoSink

Two external video sources reach the screen by different mechanisms, chosen by how the frames arrive:

Android Auto — an embedded window (and the dhuframe provider)

Google's Desktop Head Unit is a separate process with its own window. On Windows, AndroidAutoManager starts it minimised, moves its window off-screen and emits dhuWindowReady(hwnd); the EmbeddedDhuItem in AndroidAutoView.qml then strips the window's decorations and makes it a Win32 child of OCTAVE's window (SetParent), positioned over the item. On Linux and macOS the manager starts the DHU and polls for its window every second, but window lookup is implemented with Win32 only, so nothing is embedded there. See Android Auto.

main.py also registers a QQuickImageProvider (DhuFrameProvider in backend/android_auto/dhu_capture.py) as image://dhuframe. Its DhuCapture grabs a window with Win32 PrintWindow on a 30 fps timer once startCapture() is called (on other systems it emits "Screen capture only supported on Windows"). Only the non-Windows start path calls startCapture(), and only after it has found a window, which it cannot do there; and no QML file in frontend/ requests image://dhuframe. In practice the embedded window is the only Android Auto picture. 

# main.py
engine.addImageProvider("dhuframe", android_auto_manager._dhu_capture.frame_provider)

Phone mirror — QVideoSink

The phone streams H.264 over a socket that OCTAVE decodes itself with PyAV (av.CodecContext.create("h264", "r") in backend/phone_mirror/scrcpy_client.py). Decoded YUV420P planes are copied into a QVideoFrame without an RGB conversion and pushed to the QVideoSink that QML's VideoOutput exposes, so the GPU does the colour conversion and the frame never becomes a QImage: 

// QML (PhoneMirrorView.qml) — inside the VideoOutput
Component.onCompleted: if (phoneMirrorManager) phoneMirrorManager.videoSink = videoSink

videoSink is a Property(QObject) with a setter on PhoneMirrorManager. Audio comes over a second socket as PCM and is played through a QAudioSink on the GUI thread with a client-side gain (scrcpyAudioGain); sound detected in that PCM drives duckingChanged → MediaManager.setDucking() so local music dips under navigation prompts, and audioPlayed feeds the same PCM to AudioAnalyzer.feed_live_pcm() for the visualizer's live mode.

The Phone Server Fork

The Java program that runs on the phone during mirroring is OCTAVE's own fork of the scrcpy server (Apache-2.0, forked at v3.3.4, package org.octave.phoneserver), source in phone_server/. The prebuilt jar tools/phone-server/octave-phone-server is committed alongside it with its LICENSE and NOTICE. The client pushes the jar over adb to /data/local/tmp/octave-phone-server.jar every session and speaks the scrcpy 3.x protocol to it.

  • The version string must agree or the server refuses to start: SCRCPY_VERSION_NAME in phone_server/build_without_gradle.sh and SERVER_VERSION in backend/phone_mirror/scrcpy_client.py — both 3.3.4-octave.
  • adb comes from scripts/fetch_platform_tools.py (Google's pinned platform-tools, SHA-256 verified, into the gitignored tools/platform-tools/<os>/), else from PATH or a standard SDK location. Google publishes no aarch64 build, so ARM boards need the distro's or another compatible adb. See Running from Source.
  • Protocol byte layouts are documented in docs/PHONE_MIRROR_NATIVE_PLAN.md; re-verify them against DesktopConnection, control/ControlMessageReader and device/Streamer in phone_server/src/main/java/org/octave/phoneserver/ when pulling upstream changes.

Settings Persistence

All user settings live in one JSON file, settingsConfigure.json, under the directory returned by get_app_data_dir() in backend/settings_manager.py (created if missing). The same directory holds logs/, dashboards/ (user dashboards and .hidden-builtins) and metadata_cache.json (the media manager's persistent tag store).

PlatformPath
Windows%APPDATA%\OCTAVE\
macOS~/Library/Application Support/OCTAVE/
Linux / Raspberry Pi$XDG_CONFIG_HOME/OCTAVE/, default ~/.config/OCTAVE/

The file is read once: after the constructor has loaded and validated it, self._settings is authoritative and load_settings() returns a copy without touching disk. Writes are coalesced: every setter goes through save_settings(), which validates and updates memory, marks a pending flag and (re)starts a 500 ms single-shot timer; when it fires, flushPendingSave() (alias flush_pending_save()) writes the whole object atomically (temp file in the same directory, fsync, os.replace, directory fsync on non-Windows). The temp file is locked (fcntl.flock / msvcrt.locking, non-blocking; a failure only logs a warning), but writes are not serialised across running instances, so two instances can overwrite each other's settings. OBD parameter selections have a separate 800 ms debounce that flushPendingSave() does not drain. cleanup_on_quit() flushes the main store twice.

After the first clean parse in a session the file is copied to settingsConfigure.json.bak. If the file fails to parse (for example truncated by a power cut), it is moved to settingsConfigure.json.corrupt and the .bak copy is restored; with no usable backup the defaults are used. See Settings Manager for the registry, validation and every key.

Dashboards: JSON Specs + DashboardManager

OBD dashboards are data, not code. A dashboard is a JSON object with id, label, schema, a grid size and a list of cells, each naming a widget type from frontend/dashboards/WidgetCatalog.qml, a PID id from OBDParameterModel, a grid rectangle and per-widget props: 

{
  "id": "sport", "label": "Sport", "schema": 1,
  "gridColumns": 12, "gridRows": 8,
  "cells": [
    { "type": "DigitalReadout", "paramId": "SPEED",
      "col": 0, "row": 0, "colSpan": 6, "rowSpan": 7,
      "props": { "valueScale": 7.0, "padDigits": 3 } },
    ...
  ]
}
  • Sources — built-in presets in frontend/dashboards/presets/ (fullgrid, minimal, performance, sport, tj-wrangler) and user files in <appdata>/dashboards/. Built-ins are scanned first; a user file whose id collides with a built-in id (hidden ones included) is skipped with a warning, and saveDashboard refuses such an id.
  • API (backend/dashboard_manager.py) — dashboards property (list of {id, label, builtIn, path}, built-ins first), loadDashboard(id), isBuiltIn(id), saveDashboard(spec), deleteDashboard(id) (hides a built-in), restoreBuiltInDashboards(), hiddenBuiltInCount, duplicateDashboard(sourceId, newLabel), refresh(), sharing (exportDashboard, copyDashboardToClipboard, importDashboard, importDashboardFromClipboard, importDashboardFromText, lastShareError), dashboardsChanged.
  • Hot reload — a QFileSystemWatcher on the user directory, debounced and compared against a (name, mtime, size) signature so OCTAVE's own atomic saves do not double-fire.
  • Rendering — frontend/dashboards/DashboardRenderer.qml instantiates the cells from the spec; the chooser in OBDMenu.qml shows every dashboard as a live miniature; frontend/dashboards/editor/DashboardEditor.qml is the in-app drag-and-drop editor (pure QML on top of the manager's save/duplicate/delete; an abandoned draft is kept in the dashboardEditorDraft setting and offered as "Resume draft" in the chooser).
  • Primitives — frontend/gauges/: CircularGauge, ArcGauge, BarGauge, LinearGauge, DigitalReadout, SparklineGauge, WarningLight, plus the self-binding GForceGauge and CompassGauge.

The full spec (binding API, every prop, parameter bindings, recipes) is docs/GAUGE_AUTHORING.md; the wiki page is Gauges & Dashboards.

The 3D Vehicle (CarMenu)

frontend/CarMenu.qml shows a rigged 2003 Jeep TJ (frontend/JeepVehicle.qml) in a Qt Quick 3D scene, rolled and pitched live by berryIMU, with working doors, hood, rear glass, tailgate, lights, steering and spinning wheels. The model is an original reconstruction: the full frontend/assets/jeep_tj_2003.glb plus per-part GLBs under frontend/assets/jeep_tj/ with generated Rig.js / rig.json pivot metadata, built by tools/vehicle/build_jeep_tj.py (Blender 4.2, not needed at runtime). The photo references and the corrections they informed are catalogued in docs/vehicle/references.md.

Qt Quick 3D is an optional runtime dependency: frontend/SensorHome.qml probes it by creating the CarMenu.qml component and greys out the "3D View" card with "Requires the QtQuick3D module" when that fails. The GLBs are loaded through assetStore.localUrl() (MusicDeviceScene.qml, JeepHinge.qml), which in this backend simply resolves the path under frontend/assets/ to a file:// URL and logs a warning if the file is missing.

Logging, Crash Handlers and Diagnostics

OCTAVE runs in a car with no console attached, so "it was in the terminal" is not observability. The backend therefore writes rotating log files, leaves a trace on crash, notices a hung UI, and lets the user get the files off the head unit from the screen.

Log files — backend/logging_config.py

Python's logging with hierarchical loggers under octave.*, obtained through get_logger(__name__), which maps module paths to clean names (backend.obd_manager → octave.obd, backend.media_manager → octave.media, __main__ → octave.app, anything else → octave.<module> with the backend. prefix removed). python-obd's obd logger is given the same handlers so its per-command write:/read: lines become the ELM327 transcript. Files go to <app data dir>/logs/:

FileLevelMax sizeBackups

octave-error.logERROR+, plus crash tracebacks and faulthandler dumps2 MB5
octave-debug.logDEBUG+ (only with --debug)10 MB2

Maximum on disk: ~32 MB without debug, ~62 MB with. Formats:

# Console (stdout)

# File (adds date and source location)
2026-04-07 14:23:45 | INFO    | octave.media | media_manager.py:234 | scan_library() | Library scan complete

Crash handlers

_install_crash_handlers() runs at the end of setup_logging() when file logging is on: sys.excepthook and threading.excepthook log unhandled exceptions with tracebacks at CRITICAL (so they reach octave-error.log), and faulthandler is enabled on a descriptor of octave-error.log kept open for the process lifetime, so a native fault (SIGSEGV, SIGABRT, SIGFPE, SIGBUS, SIGILL — e.g. inside PySide6 or PyAV) dumps every thread's Python stack there. Details on Utilities.

Getting logs out of the vehicle — DiagnosticsManager

Settings → Device → Diagnostics (frontend/settings/DeviceSettingsPage.qml) is backed by diagnosticsManager: recentLogLines(200) shows the tail of octave.log followed by the tail of octave-error.log; copyLogsToClipboard(400) prepends a version/device header; exportLogs() copies every current and rotated log file plus a device-info.txt into <Downloads>/OCTAVE-logs-<timestamp>/ and updates lastExportPath; openLogFolder() opens the directory in the OS file manager (canOpenFolder is always true here). Constant properties logDir, appVersion (backend/version.py, 0.9.5), backendName ("Python") and deviceInfo feed the card's header.

Profiling and the Command Server

--profile makes main.py call setup_perf_profiling() after the QML has loaded. It imports three developer-local modules, each inside its own guard, because backend/perf_monitor.py, backend/command_server.py and backend/perf_patches.py are gitignored (as is the whole dev/ tree) and are not in a fresh clone:

  • PerfMonitor — event-loop latency, a GIL-jitter probe thread, per-label slot timings, CPU / memory (with psutil), written to dev/perf/logs/perf_<timestamp>.csv and .log and registered as perfMonitor. Without the module, --profile logs a warning and skips everything below.
  • CommandServer — a threaded TCP server on 127.0.0.1:9876 that accepts newline-delimited JSON actions and runs the UI-driving ones (navigate, click, drag, capture, record) on the GUI thread; stopped on aboutToQuit. The instance is kept in main.cmd_server so dev mode can register extra actions.
  • apply_patches() — wraps a few hot methods on the live managers with timers.

See Utilities for the internals and the action list, and Development for dev mode and the clients (MCP servers, screenshot and perf scripts).

Shutdown & Cleanup

cleanup_on_quit() is connected to aboutToQuit. The watchdog stops first; playback state, metadata and settings are saved before hardware cleanup; settings are flushed again at the end for anything a cleanup step saved. Each step catches its own exceptions and logs Cleanup failed: <name>, so one failing manager cannot skip the rest: 

# main.py — cleanup_on_quit()
steps = [
    ("ui watchdog", ui_watchdog.stop),
    ("playback state", media_manager._save_playback_state_now),
    ("metadata store", media_manager.flush_metadata_store),
    ("settings", settings_manager.flush_pending_save),
    ("android auto", android_auto_manager.cleanup),
    ("phone mirror", phone_mirror_manager.cleanup),
    ("obd", getattr(obd_manager, "close", None)),
    ("esp32", esp32_volume_manager.cleanup),
    ("berryimu", berryimu_manager.cleanup),
    ("gesture", gesture_manager.cleanup),
    ("network", network_manager.cleanup),
    ("downloads", download_manager.cleanup),
    ("settings (final)", settings_manager.flush_pending_save),
]
for name, step in steps:
    if step is None:
        continue
    try:
        step()
    except Exception:
        logger.exception(f"Cleanup failed: {name}")

SIGTERM/SIGINT reach this handler too (through app.quit() and the signal-pump timer); otherwise adb forwards, the DHU and the phone server would be orphaned when a launcher script or systemd stops the app. With --profile, separate aboutToQuit handlers stop the command server and the perf monitor and print the report.

Design Decisions — Why It Is Built This Way

Each rationale below is taken from a code comment, a docstring or a design doc in the repository, not inferred.

A manager per feature, registered as a context property

One QObject per feature keeps ownership obvious: each manager owns its state, timers and threads and cleans them up in cleanup(). Context properties are set from one place in a controlled order, can be handed to each other before the QML exists (Clock(settings_manager), connect_settings_manager()), can be swapped by the dev runtime (install_obd_manager()), and are reachable in every QML file with no import. A custom QML type is used only where something must be an item in the scene graph (the DHU embedding item).

Threading rule: I/O off the main thread, results back on it

The OBD connect, the sensor read loops, decoding and HTTP all run elsewhere because a stall on the GUI thread is visible on a dashboard gauge. Workers emit signals or call run_on_main(); pool results are collected by timer-polled futures. backend/qt_threading.py exists because QTimer.singleShot called from a plain threading.Thread never fires (module docstring). The UI watchdog exists so "a frozen head unit leaves a trace" (ui_watchdog.py).

Settings in memory, one coalesced atomic write

Re-reading the JSON per key "cost a parse + validate on every slider release, every track change and every get_setting() call from QML" (load_settings() comment). The in-memory copy is now authoritative and disk writes are debounced 500 ms, so bursts "coalesce into a single atomic write, which also spares the SD card on the Pi" (save_settings() docstring). The write is temp-file-then-replace with fsync "so a power cut leaves either the old file or the new one", and the .bak copy exists so a truncated file is restored instead of being replaced with defaults.

Volume curve in one place

A quadratic curve gives a more natural perceptual response than linear at low volume, but every output must apply the same curve "or they will drift out of sync when the user moves the slider" (volume_utils.py). Centralising both the math and the dispatch in VolumeController makes a curve change a one-line edit, and the smoke test pins the numbers.

Lazy imports

obd pulls in pint, numpy/av load large native extensions, and none are needed until the user connects an adapter or plays a track. Importing them eagerly "cost about a second before the first frame on the Orange Pi", so backend/lazy_import.py returns a proxy that imports on first attribute access (obd = lazy_module("obd")) and available(name) answers "is it installed" without importing. Used by obd_manager, audio_analyzer and the phone-mirror client.

A foreign window for the DHU, QVideoSink for the phone

The DHU is a foreign window that OCTAVE can only embed or capture; on Windows the backend embeds it as a child window (an image provider for captured frames is registered too, but unused). The phone mirror is a stream OCTAVE decodes itself, so it hands YUV frames straight to the video sink and skips both the RGB conversion and the disk. Qt's own FFmpeg media backend was rejected for the mirror because it refuses a raw Annex-B H.264 QIODevice; software decode with PyAV's bundled FFmpeg measured 12–15 % of one RK3588 core at 1280×800 (docs/PHONE_MIRROR_NATIVE_PLAN.md).

Fork the phone server

The goal of the native mirror was "no user-installed dependencies": no scrcpy binary, no v4l2loopback, no ffmpeg on PATH, no adb shell input for touch (docs/PHONE_MIRROR_NATIVE_PLAN.md). Forking the server (package renamed, version 3.3.4-octave) lets OCTAVE change the phone side, and committing the prebuilt jar means a checkout needs no Java or Android toolchain.

Dashboards as JSON, primitives as QML

Hand-written dashboard QML files could not be created by the user in the car. Moving the layout into a JSON spec rendered by DashboardRenderer made the in-app editor possible (pure QML on top of saveDashboard/duplicateDashboard/deleteDashboard), keeps built-ins and user files in the same format, and lets a file dropped into the user directory appear without a restart. The gauge primitives stay as QML because that is where the drawing belongs; the spec only names them.

QML loaded from disk

frontend/ is added to the import path and Main.qml is loaded from the file system relative to main.py, so a QML edit takes effect on the next start with nothing to rebuild. The one QML branch that would load a Qt resource (qrc:/shaders/dissolve_squares.frag.qsb in AlbumArtCarousel.qml) is Android-only; here the shader is read from frontend/shaders/.

Observability first

Logging is installed before anything else imports, the crash handlers write to the error log, the watchdog records stalls, and DiagnosticsManager exists so the driver can export the logs from the screen ("without a laptop", module docstring). All of that follows from OCTAVE running unattended in a vehicle. Errors are logged and surfaced through page-specific status text; a global notification layer is parked in TODO/error-notification-ui.md.
