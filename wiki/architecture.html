High-Level Architecture

OCTAVE is a backend/frontend split joined by Qt's signals and slots. There are two parallel backends designed around a shared QML API: a C++ / Qt 6 backend in src/ — the only binary that ships on every platform (Windows .exe, macOS .dmg, Linux x86_64 and aarch64 AppImages, Android .apk) — and a Python / PySide6 backend in backend/ + main.py used for desktop development, prototyping and hardware hacking. Either backend owns all business logic, hardware I/O, network calls and data processing; the QML frontend in frontend/ owns rendering, animation and interaction. Most desktop behavior is shared; the API reference records remaining differences.

Managers own hardware access and application state; QML consumes that state through the registered API. Some integrations explicitly cross the rendering boundary, such as frame providers, video sinks, and developer UI-driving tools. The only contract between them is the set of context-property names, signals, slots and properties — which is exactly why the two backends must expose the same surface (see Design Decisions).

Parity is the rule on desktop; mobile is C++-only
Desktop feature changes should be implemented in both src/managers/ and backend/, matching the QML-facing names and on-disk JSON formats. This is a contributor requirement, not a claim that every public method is already identical. Android/iOS-specific code lives behind #ifdef Q_OS_ANDROID / Q_OS_MOBILE in C++ and has no Python mirror. QML must not know which backend is running beyond typeof fooManager !== "undefined" guards for features legitimately absent on one platform.

The Manager Pattern

Every backend feature is a manager class inheriting QObject. In C++ it exposes state through Q_PROPERTY, Q_INVOKABLE / public slots and signals; in Python through the Property, Slot and Signal decorators. The two spellings of the same thing: 

// C++ — src/managers/examplemanager.h
class ExampleManager : public QObject {
    Q_OBJECT
    Q_PROPERTY(int value READ value NOTIFY valueChanged)
public:
    int value() const { return m_value; }
public slots:
    void setValue(int v) { m_value = v; emit valueChanged(v); }
signals:
    void valueChanged(int);
private:
    int m_value = 0;
};
# Python — backend/example_manager.py
from PySide6.QtCore import QObject, Signal, Slot, Property

class ExampleManager(QObject):
    valueChanged = Signal(int)          # QML listens to these

    def __init__(self):
        super().__init__()
        self._value = 0

    @Slot(int)                          # callable from QML
    def setValue(self, v):
        self._value = v
        self.valueChanged.emit(v)

    @Property(int, notify=valueChanged)  # bindable from QML
    def value(self):
        return self._value

Key principles:

  • Signals notify the UI (and other managers) when backend state changes
  • Slots are methods QML can call — method names are shared across backends even where they break the C++ naming convention (next_track, scan_library, connect_settings_manager)
  • Properties expose values with automatic binding updates
  • Managers are self-contained: each owns its state, timers and threads
  • The main entry points wire cross-manager signals and pass dependencies where needed. Examples include settings references, the Python VolumeController output managers, and OBDAdapterFinder handing a connection to OBDManager.

Backend-QML Communication

Context Properties

Managers are registered as QML context properties on the engine's root context. That makes them globally visible in every QML file without an import: 

// C++ (src/main.cpp)
QQmlContext *ctx = engine.rootContext();
ctx->setContextProperty("mediaManager", &mediaManager);

# Python (main.py)
engine.rootContext().setContextProperty("mediaManager", media_manager)
// QML — identical against either backend
Button {
    onClicked: mediaManager.next_track()
}
Text {
    text: mediaManager.get_display_name(mediaManager.get_current_file())
}

Every context property must exist before engine.load(Main.qml): bindings are evaluated at first load, and an unregistered name is an error, not a late binding. Both mains therefore register every manager (including dashboardManager, the last one) ahead of the load, and main.py exposes install_obd_manager() so the dev runtime can substitute a mock OBD manager before the QML is loaded.

Signals and Slots

Signals are the notification mechanism. QML reacts to them declaratively: 

// QML — react to a backend signal
Connections {
    target: mediaManager
    function onCurrentMediaChanged(filename) {
        albumArt.source = mediaManager.get_album_art(filename)
    }
}

Slots are methods QML calls. C++ uses public slots: or Q_INVOKABLE; Python uses @Slot(), with result= for return values:

// C++
Q_INVOKABLE QVariant loadDashboard(const QString &id);

# Python
@Slot(str, result='QVariant')
def loadDashboard(self, dashboard_id):
    ...

Qt Properties

Properties combine a getter, an optional setter and a notify signal into one bindable value. QML re-evaluates any binding that reads the property when its notify signal fires. CONSTANT / constant=True properties (e.g. diagnosticsManager.logDir) never notify and are read once.

Custom QML Types

One component is embedded as a QML item rather than a context property: the Android Auto frame item, registered with qmlRegisterType under the OCTAVE.AndroidAuto module: 

// C++ (src/main.cpp) — src/items/embeddeddhuitem.h, a QQuickItem
qmlRegisterType<EmbeddedDhuItem>("OCTAVE.AndroidAuto", 1, 0, "EmbeddedDhuItem");

# Python (main.py) — backend/android_auto/embedded_dhu.py, a QQuickItem
qmlRegisterType(EmbeddedDhuItem, "OCTAVE.AndroidAuto", 1, 0, "EmbeddedDhuItem")
// QML
import OCTAVE.AndroidAuto 1.0

EmbeddedDhuItem { anchors.fill: parent }

Phone mirroring does not use a custom type any more: it binds a stock VideoOutput's videoSink to phoneMirrorManager.videoSink (see video paths). The frontend's own singletons (Style, Spacing, EnvironmentTheme, OBDParameterModel, WidgetCatalog, MusicDevicePreference) are declared in frontend/qmldir.

Application Startup Sequence

The two mains follow the same shape — logging first, then settings, then everything that depends on settings, then signal wiring, then Main.qml — but the details differ and are documented separately so neither is misread as the other.

C++ — src/main.cpp

  1. Logging + crash handlers first — argv is scanned for --debug (and --smoke, which exits 0 five seconds after Main.qml loads; CI uses it to launch the packaged Windows build) and OctaveLog::install(debug) runs before QGuiApplication exists, so anything a manager constructor logs (and any crash) reaches the files.
  2. QGuiApplication — organization/application name OCTAVE; QQuickStyle::setStyle("Basic") so sliders are fully customisable.
  3. Auto-scale — screenAutoScale = min(width, height) / 720, clamped to 0.4–3.0. It scales off the shorter edge because Android reports the natural (portrait) size even when the app is locked landscape; using height alone gave a ~3× factor there.
  4. Scalar context properties — screenAutoScale, isAndroid.
  5. Phase 1 — SettingsManager (everything depends on it), UiWatchdog started, DiagnosticsManager, Clock, NetworkManager, VolumeController.
  6. Phase 2 — MediaManager, AudioAnalyzer. On Android the youtubedl-android bridge is initialised off-thread with QtConcurrent::run (first launch extracts Python + yt-dlp + ffmpeg, 10–20 s) and runtime permissions (READ_MEDIA_AUDIO, BLUETOOTH_CONNECT, BLUETOOTH_SCAN, …) are requested; a granted audio permission triggers a library scan.
  7. Phase 3 — empty (the "Online Features" header is left over; DownloadManager is created in Phase 5).
  8. Phase 4 — OBDManager, OBDAdapterFinder, ESP32VolumeManager, BerryIMUManager, GestureManager.
  9. Phase 5 — AndroidAutoManager + the dhuframe image provider, PhoneMirrorManager with its settings wiring (audio enable/gain, ducking → MediaManager::setDucking, phone-screen-off), qmlRegisterType<EmbeddedDhuItem>, DownloadManager (+ downloadComplete → scan_library(false)).
  10. Volume fan-out — VolumeController::volumeApplied → mediaManager.setVolume(linear), phoneMirrorManager.setVolume(linear), esp32VolumeManager.send_volume_update(percent) (desktop only; the ESP32 manager rate-limits itself) — the same three outputs as backend/volume_utils.py. Then applyVolume(settingsManager.currentVolume()) restores the saved volume.
  11. QML import path — assets:/frontend on Android; on desktop frontend/ next to the binary, or one directory up (so build/octave finds the checkout's frontend/).
  12. assetStore (src/util/assetstore.{h,cpp} / backend/asset_store.py) — localUrl(relativePath) returns a file:// URL for a file under frontend/assets/. Needed because Quick3D's RuntimeLoader hands the path to Assimp, which cannot read assets:/ files inside an Android APK ("IO Error: File not found" in v0.9.2); on Android the file is extracted once into the app data directory (asset-cache/, re-extracted when its size changes after an update), on desktop the path is simply resolved. MusicDeviceScene.qml (modelUrl()) and JeepHinge.qml load every .glb through it; Qt's own loaders (images, HDR light probes, fonts) keep using assets:/ directly.
  13. Offline wiki — registers wikiViewerAvailable and wikiHomeUrl. Desktop WebEngine builds prefer the local wiki, then qrc:/wiki/index.html; Android WebView reads file:///android_asset/wiki/index.html. Without the relevant Qt module the reader is unavailable.
  14. Phase 6 — DashboardManager with setPresetsDir(frontend/dashboards/presets) and setUserDir(<appdata>/dashboards).
  15. Developer tooling (OCTAVE_DEV_TOOLS builds only) — OctaveDev::Runtime::beforeLoad() reads --dev / --profile / --command-port; without them it does nothing. A build without the option warns and ignores the flags. See Profiling and the Command Server.
  16. Load Main.qml — returns -1 if no root object was created; then Runtime::afterLoad() (dev overlay, perf monitor, command server) and setQuitOnLastWindowClosed(true).
  17. Hardware wiring — gesture actions → media / volume; ESP32 volumeChangeRequested(float) through a fractional accumulator; muteToggleRequested; on desktop the ESP32 LED colour sync (albumArtColorsChanged in theme mode, esp32LedStaticColorChanged in static mode, esp32LedColorModeChanged re-sends the current colour, cyan (0, 255, 255) when a colour is missing or unparsable) and, 500 ms after the knob reports "Connected", a push of the current volume, mute state and colour — mirroring main.py.
  18. Signals — on Unix desktop, SIGTERM/SIGINT are turned into QCoreApplication::quit() with the self-pipe trick (socketpair + QSocketNotifier) so the aboutToQuit cleanup still runs under systemd or Ctrl-C.
  19. app.exec().

Python — main.py

  1. Environment — QT_QUICK_CONTROLS_STYLE=Basic is set before any Qt import.
  2. Arguments — argparse with --debug, --profile and --smoke (load Main.qml, run 5 s, exit 0; mirrors the C++ flag) (parse_known_args, so Qt flags pass through).
  3. Logging first — setup_logging(debug=...) runs before any backend import; it also installs the crash handlers and gives python-obd's logger the same handlers.
  4. Imports — all managers are imported unconditionally; the Python backend is desktop-only, so there is no platform branching here. Heavy optional libraries are deferred via backend/lazy_import.py (see why).
  5. QApplication (from QtWidgets) — auto-scale is min(width, height) / 720 of availableSize(), clamped 0.4–3.0, the same shorter-edge rule as src/main.cpp (it used to divide the height alone).
  6. Engine — QQmlApplicationEngine, screenAutoScale, qmlRegisterType(EmbeddedDhuItem, ...), frontend/ import path, isAndroid = False.
  7. Managers in dependency order — SettingsManager; UiWatchdog.start(); DiagnosticsManager; Clock; MediaManager; AudioAnalyzer; (obdManager is registered later through install_obd_manager()); AndroidAutoManager + engine.addImageProvider("dhuframe", ...); PhoneMirrorManager + settings wiring; ESP32VolumeManager; VolumeController (constructed with references to settings, media, phone mirror and ESP32) and applyVolume(currentVolume); BerryIMUManager; GestureManager; NetworkManager; DownloadManager (+ rescan on downloadComplete); DashboardManager.
  8. Signal wiring — gesture actions, ESP32 accumulator + mute, ESP32 LED colour sync (album-art accent or static colour), initial ESP32 state 500 ms after it connects.
  9. Shutdown hooks — cleanup_on_quit() on aboutToQuit; SIGTERM/SIGINT call app.quit(), with a 500 ms no-op QTimer so the interpreter gets a chance to run the signal handler while blocked in app.exec().
  10. __main__ — install_obd_manager(OBDManager(settings_manager)), load_main_qml() (exits -1 without root objects), setup_perf_profiling() if --profile, app.exec().
Why the OBD manager is installed late in Python
main.py is importable: dev/dev_runtime.py imports it, calls install_obd_manager(MockOBDManager(...)) and then load_main_qml(). (C++ dev mode keeps the real OBDManager and swaps the adapter underneath it instead.) Keeping the registration behind a function (and the QML load behind another) lets developer mode swap in simulated OBD data without patching the production entry point. The headless boot test (tests/test_boot.py) runs the real __main__ path offscreen.

OBD Worker Thread

Connecting to an ELM327 takes seconds (reset, protocol negotiation, supported-PID discovery), so it runs on a worker and reports progress by signal. Both desktop backends use a connection worker and progress signals; the diagram is schematic (Android uses its JNI BLE bridge):

Main Thread OBD Worker Thread (QThread) │ │ │── create worker ──────────────►│ │ moveToThread(thread) │ │ thread.start() │ │ │── open port, ATZ / ATE0 ... │◄── connectionProgress(20, …) ─│ │ │── negotiate protocol │◄── connectionProgress(60, …) ─│ │ │── query supported PIDs │◄── connectionProgress(100, …)─│ │◄── connectionComplete ────────│ │ │ │ (watchdog QTimer on main) │── poll loop: TX cmd / RX reply │◄── value signals ─────────────│ (C++: QTimer on the worker; │ │ Python: obd.Async thread)

In C++ every command and reply is logged on the octave.elm327 category (TX ... / RX ... (N ms)); Python routes python-obd's own write:/read: DEBUG lines into OCTAVE's handlers. Either way a failed session leaves a protocol transcript in the debug log (see logging).

Thread Pools and QtConcurrent

Short-lived work with a single result (an API call, a decode, a colour extraction) uses a pool rather than a hand-rolled thread: concurrent.futures.ThreadPoolExecutor in Python, QtConcurrent::run + QFutureWatcher in C++. Python marshals results back with a QTimer that polls the futures; C++ gets QFutureWatcher::finished on the main thread. 

// C++ — MediaManager colour extraction
auto *watcher = new QFutureWatcher<QVariantMap>(this);
watcher->setFuture(QtConcurrent::run([this, imagePath]() {
    return _extract_album_colors(imagePath);
}));

# Python — DownloadManager
self._executor = ThreadPoolExecutor(max_workers=2)
future = self._executor.submit(func, *args)

Sensor Read Loops

The I²C sensors are read in a loop on their own thread in both backends (a BerryIMUWorker / gesture worker on a QThread in C++; daemon threads in Python), with values delivered to the main thread by signal. QTimers are used for the surrounding lifecycle — delayed start (1 s after construction), retry back-off, reconnect, the ESP32's 10 s port scan and 2 s keepalive — not for the sampling itself.

UI Watchdog

UiWatchdog (src/util/uiwatchdog.cpp / backend/ui_watchdog.py) is started right after SettingsManager in both mains and stopped first in cleanup. A worker thread posts a queued call to the GUI thread every 2 s and records when it is answered; if the GUI thread has been silent for more than 5 s it logs UI thread blocked for N s and counting on octave.ui_watchdog, then responsive again after N s when the loop drains. It is purely observational — it never kills or restarts anything.

Volume System

Volume uses a quadratic curve: the 0–100 slider percent becomes a linear 0.0–1.0 gain through 

linear = (percent / 100.0) ** 2.0      # backend/volume_utils.py  to_linear()
// src/managers/volumecontroller.cpp  VolumeController::toLinearStatic()

The curve and its dispatch live in exactly one class per backend, VolumeController, registered as volumeController. Before it existed the curve was hard-coded in about nine call sites across main.py and QML, and changing it meant editing every site in lockstep. applyVolume(percent) clamps, stores the raw percent in SettingsManager (setCurrentVolume, idempotent), computes the linear value and fans it out:

OutputPython (VolumeController holds references)C++ (volumeApplied(percent, linear) signal, wired in main.cpp)
Local mediamedia_manager.setVolume(linear)mediaManager.setVolume(linear)
Phone mirror audiophone_mirror_manager.setVolume(linear)phoneMirrorManager.setVolume(linear)
ESP32 LED ringesp32_manager.send_volume_update(percent)esp32VolumeManager.send_volume_update(percent) (compiled out under Q_OS_MOBILE)

Both backends therefore drive the same three outputs from one call. The ESP32 manager adds its own 50 ms debounce, so the ring never sees more than 20 updates a second.

Every source of a volume change routes through the same entry point:

SourceCall
UI sliders (BottomBar.qml, MediaRoom.qml)volumeController.applyVolume(Math.round(value))
ESP32 knobSerial → volumeChangeRequested(delta) → accumulator in main → applyVolume(currentVolume + change)
Gesture sensorI²C → actionTriggered("volume_up"/"volume_down") → applyVolume(currentVolume ± gestureVolumeStep)
StartupBoth mains call applyVolume(settingsManager.currentVolume) once, after the outputs exist

The knob sends fractional deltas; both mains accumulate them until a whole step is available:

# main.py (the C++ lambda in main.cpp is the same shape with a static float)
_volume_accumulator += delta
if abs(_volume_accumulator) >= 1.0:
    change = int(_volume_accumulator)
    _volume_accumulator -= change
    volume_controller.applyVolume(settings_manager.currentVolume + change)
Rule: never call mediaManager.setVolume(), phoneMirrorManager.setVolume() or esp32VolumeManager.send_volume_update() directly for a user-driven change, and never re-implement the curve. Go through volumeController.applyVolume() (or toLinear() for pure math in QML). tests/test_smoke.py::test_volume_curve_math guards the curve.

Video into QML: Image Provider vs QVideoSink

Two external video sources reach the scene graph by two different mechanisms, chosen by how the frames arrive:

Android Auto — image://dhuframe

Google's Desktop Head Unit is a separate process with its own window. OCTAVE launches it and captures the window (C++: QScreen::grabWindow(); Python: Win32 PrintWindow — the Python capture path is Windows-only and emits an error elsewhere). C++ has a capture helper, but findDhuWindow() returns zero, so automatic embedded capture is incomplete. See Android Auto limitations. Captured frames are plain QImages, so a QQuickImageProvider named dhuframe serves the latest one and QML re-requests it: 

// C++
engine.addImageProvider(QStringLiteral("dhuframe"), androidAutoManager.frameProvider());
# Python
engine.addImageProvider("dhuframe", android_auto_manager._dhu_capture.frame_provider)

// QML
Image { source: "image://dhuframe/frame"; cache: false }

Phone mirror — QVideoSink

The phone streams H.264 over a TCP socket that OCTAVE decodes itself (libavcodec in C++, PyAV in Python). Decoded YUV420P planes are wrapped in a QVideoFrame without an RGB conversion and pushed to the QVideoSink that QML's VideoOutput exposes, so the GPU does the colour conversion and the frame never becomes a QImage: 

// QML (PhoneMirrorView.qml) — inside the VideoOutput
Component.onCompleted: if (phoneMirrorManager) phoneMirrorManager.videoSink = videoSink

videoSink is a Q_PROPERTY(QObject*) / Property(QObject) on PhoneMirrorManager in both backends. Audio comes over a second socket as PCM and is played through a QAudioSink with a client-side gain (scrcpyAudioGain); sound detected in that PCM drives duckingChanged → MediaManager.setDucking() so local music dips under navigation prompts.

The Phone Server Fork

The Java program that runs on the phone during mirroring is OCTAVE's own fork of the scrcpy server (Apache-2.0, forked at v3.3.4, package org.octave.phoneserver), source in phone_server/. The prebuilt jar tools/phone-server/octave-phone-server is committed alongside it with its LICENSE and NOTICE; the C++ build embeds all three as Qt resources (:/phone-server/) and writes the jar to a temp file at runtime, so no packaging target has to carry a loose file. Both clients push the jar over adb every session (the server's clean-up helper deletes it from /data/local/tmp once it is running) and speak the scrcpy 3.x protocol to it.

  • The version string must agree in three places or the server refuses to start: SCRCPY_VERSION_NAME in phone_server/build_without_gradle.sh, kServerVersion in src/phone_mirror/scrcpyclient.h, SERVER_VERSION in backend/phone_mirror/scrcpy_client.py — all 3.3.4-octave.
  • The phone-server CI job rebuilds the jar from source on every push and fails if the committed jar does not carry the expected package and version (a byte-level difference is reported as a warning because javac/d8 output differs across toolchains).
  • adb itself is bundled: scripts/fetch_platform_tools.py downloads Google's pinned platform-tools (SHA-256 verified) into the gitignored tools/platform-tools/<os>/, and CI ships it beside the binary. Google publishes no aarch64 build, so ARM boards fall back to the distro's adb.
  • Protocol byte layouts are documented in docs/PHONE_MIRROR_NATIVE_PLAN.md; re-verify them against DesktopConnection, control/ControlMessageReader and device/Streamer when pulling upstream changes.

Settings Persistence

All user settings live in one JSON file, settingsConfigure.json, under the directory returned by get_app_data_dir() / SettingsManager::getAppDataDir(). The same directory holds logs/, dashboards/ (user dashboards), metadata_cache.json (the media manager's persistent tag/cover store).

PlatformPath
Windows%APPDATA%\OCTAVE\
macOS~/Library/Application Support/OCTAVE/
Linux / Raspberry Pi$XDG_CONFIG_HOME/OCTAVE/, default ~/.config/OCTAVE/
Android (C++)Same code path as Linux: QDir::homePath() + "/.config/OCTAVE/", which resolves inside the app's private storage

Reads happen once: after the constructor has loaded and validated the file, the in-memory object is authoritative (loadSettings() returns m_settings / self._settings without touching disk). Writes are coalesced: every setter calls saveSettings(), which updates memory, marks a pending flag and (re)starts a 500 ms single-shot timer; when it fires, flushPendingSave() (the Python name too; flush_pending_save() remains as an alias) writes the whole object atomically (C++ QSaveFile; Python temp file plus replacement). Python attempts to lock its temporary file, but neither backend serializes writes across running application instances. OBD parameter selections have a separate 800 ms debounce, which flushPendingSave() does not drain. Both mains explicitly flush the main settings store on shutdown, but simultaneous instances can overwrite each other's settings. See Settings Manager for the registry, validation and every key.

Dashboards: JSON Specs + DashboardManager

OBD dashboards are data, not code. A dashboard is a JSON object with id, label, schema, a grid size and a list of cells, each naming a widget type from frontend/dashboards/WidgetCatalog.qml, a PID id from OBDParameterModel, a grid rectangle and per-widget props: 

{
  "id": "sport", "label": "Sport", "schema": 1,
  "gridColumns": 12, "gridRows": 8,
  "cells": [
    { "type": "DigitalReadout", "paramId": "SPEED",
      "col": 0, "row": 0, "colSpan": 6, "rowSpan": 7,
      "props": { "valueScale": 7.0, "padDigits": 3 } },
    ...
  ]
}
  • Sources — built-in presets in frontend/dashboards/presets/ (fullgrid, minimal, performance, sport, tj-wrangler) and user files in <appdata>/dashboards/. Ids must be unique across both; a user file that collides with a built-in id is rejected at load.
  • API (identical in dashboardmanager.h and dashboard_manager.py) — dashboards property (list of {id, label, builtIn, path}, built-ins first), loadDashboard(id), isBuiltIn(id), saveDashboard(spec), deleteDashboard(id) (hides a built-in), restoreBuiltInDashboards(), hiddenBuiltInCount, duplicateDashboard(sourceId, newLabel), refresh(), dashboardsChanged.
  • Hot reload — a QFileSystemWatcher on the user directory, debounced and compared against a (name, mtime, size) signature so OCTAVE's own atomic saves do not double-fire.
  • Rendering — frontend/dashboards/DashboardRenderer.qml instantiates the cells from the spec; the chooser in OBDMenu.qml shows every dashboard as a live miniature; frontend/dashboards/editor/DashboardEditor.qml is the in-app drag-and-drop editor (pure QML on top of the manager's save/duplicate/delete; an abandoned draft is rescued into settings and offered on the next chooser open).
  • Primitives — frontend/gauges/: CircularGauge, ArcGauge, BarGauge, LinearGauge, DigitalReadout, SparklineGauge, WarningLight, plus the self-binding GForceGauge and CompassGauge.

The full spec (binding API, every prop, parameter bindings, recipes) is docs/GAUGE_AUTHORING.md; the wiki page is Gauges & Dashboards.

The 3D Vehicle (CarMenu)

frontend/CarMenu.qml shows a rigged 2003 Jeep TJ (frontend/JeepVehicle.qml) in a Qt Quick 3D scene, rolled and pitched live by berryIMU, with working doors, hood, rear glass, tailgate, lights, steering and spinning wheels. The model is an original reconstruction: the full frontend/assets/jeep_tj_2003.glb plus per-part GLBs under frontend/assets/jeep_tj/ with generated Rig.js / rig.json pivot metadata, built by tools/vehicle/build_jeep_tj.py (Blender 4.2, not needed at runtime). The photo references and the corrections they informed are catalogued in docs/vehicle/references.md.

Qt Quick 3D is optional at build time: CMakeLists.txt probes for it, and frontend/SensorHome.qml probes by creating the CarMenu.qml component and greys out the "3D View" card with "Requires the QtQuick3D module" when it fails. RuntimeLoader also needs Qt's assimp asset-import plugin; on distro Qt that is often a separate package (see BUILD.md). JeepVehicle.qml assembles the part GLBs with public Qt APIs rather than reaching into an imported scene's internals, so a rebuild of the asset set does not break the QML.

Logging, Crash Handlers and Diagnostics

OCTAVE runs in a car with no console attached, so "it was in the terminal" is not observability. Both backends therefore write rotating log files, leave a trace on crash, notice a hung UI, and let the user get the files off the head unit from the screen.

Python — backend/logging_config.py

Python's logging with hierarchical loggers under octave.*, obtained through get_logger(__name__), which maps module paths to clean names (backend.obd_manager → octave.obd, backend.media_manager → octave.media, __main__ → octave.app, anything else → octave.<module>). python-obd's obd logger is given the same handlers so its per-command write:/read: lines become the ELM327 transcript.

Crash handlers

  • Python (_install_crash_handlers): sys.excepthook and threading.excepthook log unhandled exceptions with tracebacks to octave-error.log; faulthandler is enabled on a descriptor kept open for the process lifetime so a native fault (SIGSEGV, SIGABRT, SIGFPE, SIGBUS, SIGILL) dumps every thread's Python stack there.
  • C++: SIGSEGV/SIGABRT/SIGFPE/SIGILL/SIGBUS handlers write a ==== FATAL SIGSEGV ==== block and a backtrace_symbols_fd backtrace to octave-cpp-error.log over a raw descriptor opened at install time (no Qt in the signal path — not even OctaveLog::flush(), which the log files do not need because every line is flushed as it is written), then restore the default action and re-raise so the OS still produces its core / tombstone. Windows uses SetUnhandledExceptionFilter + CaptureStackBackTrace. Symbolise with addr2line -e octave against the same build. qFatal passes through the message handler first, which calls OctaveLog::flush() after a fatal message, so assertion text is on disk before the abort; the aboutToQuit handler calls the same flush last on a normal exit.

Getting logs out of the vehicle — DiagnosticsManager

Settings → Device → Diagnostics (frontend/settings/DeviceSettingsPage.qml) is backed by diagnosticsManager in both backends: recentLogLines(200) shows the tail of the running backend's main log followed by its error log; copyLogsToClipboard(400) prepends a version/device header; exportLogs() copies every current and rotated log file plus a device-info.txt into <Downloads>/OCTAVE-logs-<timestamp>/ (so on the Android head unit they can be attached from any mail or files app) and updates lastExportPath; openLogFolder() opens the directory in the OS file manager where canOpenFolder is true. Constant properties logDir, appVersion (from OCTAVE_VERSION / backend/version.py, both 0.9.5), backendName ("C++" / "Python") and deviceInfo feed the page header.

Profiling and the Command Server

Both backends have the same developer tooling behind the same flags. --profile creates a PerfMonitor (event-loop latency, a thread-wake jitter probe, per-label timings, CPU / memory) writing CSV and log files to dev/perf/logs/, registers it as the perfMonitor context property, and starts a command server: a threaded TCP server on 127.0.0.1:9876 that accepts newline-delimited JSON actions and runs the UI-driving ones (navigate, click, drag, capture, record) on the GUI thread. Both are stopped on aboutToQuit and the report is written to the log. Dev mode (--dev in C++, python -m dev.main_dev in Python) adds a simulated car.

  • C++ (src/dev/): compiled in only with the OCTAVE_DEV_TOOLS CMake option (default on only for Debug desktop builds) and inert without the flags. OctaveDev::Runtime is created in main.cpp after the managers; the simulated car talks to the real OBDManager through a fake ELM327 QIODevice (OBDConnectionWorker::setCustomTransport(), OBDManager::setPortOverride()), and hot paths are timed with OCTAVE_PERF_SCOPE (src/util/perfscope.h, empty without the option).
  • Python: setup_perf_profiling() imports backend/perf_monitor.py, backend/command_server.py and backend/perf_patches.py (method wrapping) lazily. They and the whole dev/ tree are in .gitignore; every import is guarded, so --profile on a fresh clone logs a warning and starts without them.

See Development for the protocol, the action list and the clients (MCP servers, screenshot and perf scripts), which drive either backend.

Shutdown & Cleanup

Both mains connect a cleanup handler to aboutToQuit. The watchdog stops first. Python saves playback, metadata and settings before hardware cleanup, closes OBD as well, then flushes settings again; each step catches exceptions so the remaining cleanup still runs. C++ flushes the stores after manager cleanup. The excerpts below summarize that order: 

# Condensed from main.py: each step is guarded independently.
steps = [
    ui_watchdog.stop,
    media_manager._save_playback_state_now,
    media_manager.flush_metadata_store,
    settings_manager.flush_pending_save,
    android_auto_manager.cleanup,
    phone_mirror_manager.cleanup,
    getattr(obd_manager, "close", None),
    esp32_volume_manager.cleanup,
    berryimu_manager.cleanup,
    gesture_manager.cleanup,
    network_manager.cleanup,
    download_manager.cleanup,
    settings_manager.flush_pending_save,
]
for step in steps:
    if step is not None:
        try:
            step()
        except Exception:
            logger.exception("Cleanup failed")
// src/main.cpp
QObject::connect(&app, &QGuiApplication::aboutToQuit, [&]() {
    uiWatchdog.stop();
    androidAutoManager.cleanup();  phoneMirrorManager.cleanup();
    esp32VolumeManager.cleanup();  berryIMU.cleanup();  gestureSensor.cleanup();
    obdManager.close();
    downloadManager.cleanup();     networkManager.cleanup();
    mediaManager._save_playback_state();   // before the settings flush
    mediaManager.flush_metadata_store();
    settingsManager.flushPendingSave();
    OctaveLog::flush();                    // last: everything the cleanup logged reaches disk
});

SIGTERM/SIGINT reach this handler too (self-pipe in C++, a periodic timer in Python), otherwise adb forwards, the DHU and the phone server would be orphaned when a launcher script or systemd stops the app. With --profile both backends also stop the command server and the perf monitor and write the report (C++: OctaveDev::Runtime::shutdown(), first in the handler).

Design Decisions — Why It Is Built This Way

Each rationale below is taken from a code comment, CLAUDE.md, BUILD.md or a design doc in the repository, not inferred.

Two backends, one frontend

C++ is the sole distribution path because every shipped artefact — including the Android APK, where Python cannot go — is built from one CMake tree by one CI matrix. Python stays alive on desktop because on a Pi with a new sensor on the I²C bus "a Python REPL beats a compile cycle" (README), and because most managers are a few hundred lines a newcomer can read in one sitting. The cost is the parity rule: a change in one backend is ported to the other in the same change set, matching class names, context-property names, method and signal names, property types and JSON formats, so the QML never learns which backend is running. The historical Python→C++ rewrite plan is superseded by this policy; Python is not slated for deletion. Python-on-Android (buildozer / p4a) was removed and must not return.

A manager per feature, registered as a context property

One QObject per feature keeps ownership obvious: each manager owns its state, timers and threads and cleans them up in cleanup(). Context properties (rather than QML singletons or qmlRegisterSingletonInstance) were chosen so the objects are constructed in a controlled order in one place, can be handed to each other before the QML exists (Clock(settingsManager), connect_settings_manager()), can be swapped by the dev runtime (install_obd_manager()), and are reachable in every QML file with no import. Custom QML types are reserved for things that must be items in the scene graph (the DHU frame item).

Mobile stubs in the headers instead of typeof checks everywhere

On Android, desktop-only managers such as ESP32, gesture, phone mirror and Android Auto expose stub APIs under Q_OS_MOBILE. These preserve the QML-facing names, though calls may report unavailability. BerryIMU is different: Android uses a QtSensors implementation. Some signal wiring is also platform-guarded. CMake currently defines Q_OS_MOBILE for Android; iOS builds are not wired up.

Threading rule: I/O off the main thread, results only by queued signal

The OBD connect, the sensor read loops, decoding and HTTP all run elsewhere because a 30 ms stall is visible on a dashboard gauge. Managers never call into QML from a worker; they emit signals, and Qt delivers them queued on the GUI thread. Python additionally uses timer-polled futures where a callback would otherwise run on the pool thread. The UI watchdog exists because a frozen head unit in a car has nobody watching a terminal.

Settings in memory, one coalesced atomic write

Re-reading the JSON per key "cost a parse + validate on every slider release and every track change, and always returned what we had just written" (settingsmanager.cpp). The in-memory copy is now authoritative and disk writes are debounced 500 ms and written temp-file-then-rename, which also "spares the SD card on the Pi". The one shared file format is why both backends can be pointed at the same config directory.

Volume curve in one place

A quadratic curve gives a more natural perceptual response than linear at low volume, but every output must apply the same curve or they drift apart as the slider moves. Centralising both the math and the dispatch in VolumeController means a curve change is a one-line edit and a new output is one more connection, and the smoke test pins the numbers. C++ chose a signal fan-out (volumeApplied) rather than holding pointers so the controller could be constructed in Phase 1 before the outputs existed.

Lazy imports in the Python backend

obd pulls in pint, numpy/av load large native extensions, and none are needed until the user connects an adapter or plays a track. Importing them eagerly "cost about a second before the first frame on the Orange Pi", so backend/lazy_import.py returns a proxy that imports on first attribute access (obd = lazy_module("obd")) and available(name) answers "is it installed" without importing. Used by obd_manager, audio_analyzer and the phone-mirror client.

Image provider for the DHU, QVideoSink for the phone

The DHU is a foreign window that can only be captured, producing QImages at a timer rate; an image provider is the natural fit. The phone mirror is a stream OCTAVE decodes itself, so it hands YUV frames straight to the video sink and skips both the RGB conversion and the disk. Qt's own FFmpeg backend was rejected for the mirror because it refuses a raw Annex-B H.264 QIODevice (docs/PHONE_MIRROR_NATIVE_PLAN.md, Phase 0); libavcodec / PyAV decode at 12–15 % of one RK3588 core and paint the first frame in about a second.

Fork the phone server, bundle adb

The goal of the native mirror was "no user-installed dependencies": no scrcpy binary, no v4l2loopback, no ffmpeg on PATH, no adb shell input for touch. Forking the server (package renamed, version 3.3.4-octave) lets OCTAVE change the phone side (the keeper that survives locks and cable blips, the screen-off policy) while CI checks the committed jar's package and version (hash mismatches only warn). Bundling platform-tools avoids a separate adb installation on the desktop targets that bundle it; Linux aarch64 needs a compatible adb installed separately.

Dashboards as JSON, primitives as QML

Hand-written dashboard QML files could not be created by the user in the car. Moving the layout into a JSON spec rendered by DashboardRenderer made the in-app editor possible (pure QML on top of saveDashboard/duplicateDashboard/deleteDashboard), keeps built-ins and user files in the same format, and lets a file dropped into the user directory appear without a restart. The gauge primitives stay as QML because that is where the drawing belongs; the spec only names them.

QML loaded from disk, not compiled in

frontend/ is added to the import path and Main.qml is loaded from the file system (from assets:/frontend on Android) so the same directory serves both backends and a QML edit does not require a rebuild. The one exception is the .qsb shader, which must be a Qt resource because RHI's ShaderEffect rejects assets:/ URIs on Android.

Observability first

Logging is installed before the application object, crash handlers use raw descriptors so they work when Qt cannot, the watchdog records stalls, and DiagnosticsManager exists so the driver can export the logs from the screen. All of that follows from OCTAVE being daily-driven in a vehicle: in-car reliability and after-the-fact debuggability are first-order requirements, not polish. Errors are logged and surfaced through page-specific status text; a global notification layer is parked in TODO/error-notification-ui.md.
