High-Level Architecture

OCTAVE follows a clean backend/frontend separation connected by Qt's signals and slots mechanism. OCTAVE maintains two parallel backends that expose the same API to the shared frontend: a C++ / Qt 6 backend (src/) — the only shipped binary on every platform — and a Python / PySide6 backend (backend/) used for desktop development and tinkering. Either one handles all business logic, hardware communication, API calls, and data processing; the QML frontend handles all rendering, animation, and user interaction, and works identically against either backend.

Backend / Frontend Split

LayerTechnologyLocationResponsibility
Backend (shipped) C++ / Qt 6 src/ Business logic, hardware I/O, API calls, data processing, state management — the only binary shipped on every platform
Backend (dev peer) Python 3.8+ / PySide6 backend/ API-equivalent backend for desktop development, prototyping, and Raspberry Pi tinkering
Frontend QML (Qt Quick 2.15) frontend/ UI rendering, animations, user interaction, layout — identical against either backend
Bridge C++ main / PySide6 src/main.cpp · main.py Registers managers as context properties, wires signals, manages lifecycle

The backend never touches the UI directly. The frontend never makes API calls or accesses hardware. All communication goes through Qt's signal/slot mechanism, which is thread-safe and decoupled.

The Manager Pattern

Every backend feature is encapsulated in a manager class that inherits from QObject. This is the fundamental pattern used throughout OCTAVE: 

from PySide6.QtCore import QObject, Signal, Slot, Property

class ExampleManager(QObject):
    # Signals — emitted when state changes, QML listens to these
    valueChanged = Signal(int)

    def __init__(self):
        super().__init__()
        self._value = 0

    # Slots — callable from QML
    @Slot(int)
    def setValue(self, v):
        self._value = v
        self.valueChanged.emit(v)

    # Properties — bindable from QML
    @Property(int, notify=valueChanged)
    def value(self):
        return self._value

Key principles:

  • Signals notify the UI when backend state changes
  • Slots are Python methods callable from QML
  • Properties expose readable (and optionally writable) values to QML with automatic binding
  • Managers are self-contained — each owns its state and logic
  • Cross-manager communication goes through signal wiring in main.py

Python-QML Communication

Context Properties

Backend managers are registered as QML context properties in main.py. This makes them globally accessible in every QML file without imports: 

# Python (main.py) — register a manager
engine.rootContext().setContextProperty("mediaManager", media_manager)
// QML — access it directly, no import needed
Button {
    onClicked: mediaManager.next_track()
}

Text {
    text: mediaManager.currentTrackTitle
}

Context properties are the primary bridge between Python and QML. Every manager listed above is accessible in QML by its context property name.

Signals and Slots

Signals are the notification mechanism. When something changes in Python, a signal fires. QML can bind to signals declaratively: 

// QML — react to a Python signal
Connections {
    target: mediaManager
    function onCurrentTrackChanged() {
        // Update UI when the track changes
        albumArt.source = mediaManager.albumArtPath
    }
}

Slots are Python methods that QML can call. Decorated with @Slot(): 

# Python — define a slot
@Slot()
def next_track(self):
    # ... advance to next track
    self.currentTrackChanged.emit()

Qt Properties

Properties combine a getter, an optional setter, and a notification signal into a single bindable value. QML automatically updates bindings when the notify signal fires: 

# Python — define a property
@Property(str, notify=currentTrackTitleChanged)
def currentTrackTitle(self):
    return self._current_title
// QML — bind to it (auto-updates when signal fires)
Text {
    text: mediaManager.currentTrackTitle
}

Custom QML Types

Some components need to be embedded directly as QML items (not just context properties). These are registered with qmlRegisterType: 

# Python (main.py)
qmlRegisterType(EmbeddedDhuItem, "OCTAVE.AndroidAuto", 1, 0, "EmbeddedDhuItem")

        
// QML — use as a component
import OCTAVE.AndroidAuto 1.0

EmbeddedDhuItem {
    anchors.fill: parent
}


        
These are used for video frame embedding where the Python side renders frames directly
          into the QML scene graph.

Threading Model

        

          OCTAVE's UI runs on the Qt main thread (event loop). All heavy I/O is offloaded to
          background threads to prevent UI freezes. Three patterns are used:
        


        
1. QThread Worker (OBD Connection)

        

          The OBD connection process is long-running (5–30 seconds) and uses a dedicated
          QThread with a worker object. Progress is reported via signals:
        


        

Main Thread                    OBD Worker Thread
    │                               │
    │── create worker ──────────────►│
    │   moveToThread(thread)        │
    │   thread.start()              │
    │                               │── connect to ELM327
    │◄── progressChanged(20%) ──────│
    │                               │── negotiate protocol
    │◄── progressChanged(60%) ──────│
    │                               │── query supported PIDs
    │◄── progressChanged(100%) ─────│
    │◄── connectionComplete ────────│
    │                               │
    │   (polling via QTimer)        │── read OBD values
    │◄── dataChanged ──────────────│
    │                               │


        
2. ThreadPoolExecutor (Spotify, Network, Download)

        

          Short-lived API calls use Python's concurrent.futures.ThreadPoolExecutor.
          The result is marshalled back to the Qt main thread via a QTimer or
          signal emission:
        


        
# Typical pattern (SpotifyManager)
from concurrent.futures import ThreadPoolExecutor

class SpotifyManager(QObject):
    def __init__(self):
        self._executor = ThreadPoolExecutor(max_workers=2)

    def _api_call(self, func, *args):
        future = self._executor.submit(func, *args)
        future.add_done_callback(self._on_result)


        
3. QTimer Polling (Sensors, ESP32)

        

          Hardware sensors are polled at regular intervals using QTimer. This keeps
          sensor reading on the main thread but at controlled intervals (typically 50–200ms):
        


        
# BerryIMU polling (main thread, timer-driven)
self._timer = QTimer()
self._timer.timeout.connect(self._read_sensors)
self._timer.start(50)  # 20 Hz


        

          
Why QTimer for Sensors?

          I2C reads are fast (<1ms) so they don't block the UI at 20 Hz. Using a QTimer avoids
          the complexity of cross-thread signal marshalling for high-frequency data. The 50ms interval
          is tuned for smooth UI updates without excessive CPU usage.
        


        
        
Volume System

        

          Volume uses a quadratic curve (y = x²) to match human perception. The raw
          0–100 slider value is transformed before being applied to linear audio outputs:
        


        
linear = (percent / 100.0) ** 2.0


        

          The curve math and its dispatch logic both live in backend/volume_utils.py.
          Before this module existed, the curve was hardcoded in ~9 call sites across main.py and QML;
          changing the curve meant editing every site in lockstep. Now the math lives in to_linear()
          and every source of a volume change funnels through a single VolumeController.applyVolume(percent)
          entry point.
        


        

          VolumeController is a QObject instantiated in main.py
          with references to every audio output manager and registered as the QML context property
          volumeController. A call to applyVolume(percent):
        

        
    
          
  • stores the raw percent in settings_manager.setCurrentVolume() (idempotent if unchanged)
    • 
          
  • applies to_linear(percent) to media_manager.setVolume() and phone_mirror_manager.setVolume()
    • 
          
  • forwards the raw percent to spotify_manager.set_volume() (Spotify Web API applies its own curve)
    • 
          
  • sends the raw percent to esp32_manager.send_volume_update() for the LED ring display
    • 
        


        
Every source of a volume change routes through the same entry point:


        

          
            
SourceCall

          
          
            

              UI Slider (BottomBar or MediaRoom)
              volumeController.applyVolume(Math.round(value)) from QML
            

            

              ESP32 Knob
              Serial → volumeChangeRequested signal → handle_esp32_volume_change() → volume_controller.applyVolume()
            

            

              Gesture Sensor
              I2C → actionTriggered("volume_up"/"volume_down") → handle_gesture_action() → volume_controller.applyVolume()
            

            

              Startup
              main.py calls volume_controller.applyVolume(settings_manager.currentVolume) once after all managers are constructed, restoring the saved volume to every output. QML's Component.onCompleted repeats this idempotently.
            

          
        


        
The volume accumulator pattern handles sub-integer ESP32 deltas:

        
# ESP32 sends fractional deltas; accumulate until >= 1.0
_volume_accumulator += delta
if abs(_volume_accumulator) >= 1.0:
    change = int(_volume_accumulator)
    _volume_accumulator -= change
    volume_controller.applyVolume(settings_manager.currentVolume + change)


        

          Rule: never call mediaManager.setVolume(), spotifyManager.set_volume(),
          phoneMirrorManager.setVolume(), or esp32VolumeManager.send_volume_update() directly
          for a new user-driven volume change. Always go through volumeController.applyVolume(), or the
          outputs will drift out of sync.
        


        
        
Image Providers

        

          Video frames from Android Auto and Phone Mirror are streamed directly to QML via custom
          QQuickImageProvider subclasses. This avoids writing frames to disk:
        


        
# Registration (main.py)
engine.addImageProvider("dhuframe", android_auto_manager._dhu_capture.frame_provider)



        
// QML — request frames via image:// protocol
Image {
    source: "image://dhuframe/frame"
    cache: false
}


        

          The image provider returns the latest captured frame on each request. QML periodically
          re-requests the image (via source binding or timer) to get new frames.

Getting logs out of the vehicle

        

          Settings → About → Diagnostics (DiagnosticsManager, both backends) shows the
          last 200 lines of the running backend's log with its errors, and offers Copy (clipboard), Export logs (every log
          file plus a device-info.txt into Downloads/OCTAVE-logs-<timestamp>/, so on the Android head unit
          they can be attached from any mail or files app) and, on desktop, Open folder.
        

        
UI watchdog

        

          A hung event loop is logged rather than lost: UiWatchdog (src/util/uiwatchdog.cpp /
          backend/ui_watchdog.py, started in both mains) pings the GUI thread from a worker every 2 s and
          logs UI thread blocked for N s and counting on the octave.ui_watchdog category once the
          GUI thread has been silent for 5 s, then responsive again after N s when it recovers. Legitimate
          slow work (a large library scan, dashboard JSON load) stays under the threshold; anything above it is worth a look.
        

        
Crash handlers

        

          Both backends leave a trace when they die. Python (logging_config._install_crash_handlers):
          sys.excepthook and threading.excepthook log unhandled exceptions with their traceback
          to octave-error.log, and faulthandler dumps every thread's Python stack to the same file
          on a native fault. C++: SIGSEGV/SIGABRT/SIGFPE/SIGILL/SIGBUS
          write a ==== FATAL SIGSEGV ==== block with a backtrace_symbols_fd backtrace to
          octave-cpp-error.log over a raw descriptor (no Qt in the signal path), then re-raise so the OS still
          produces its core / tombstone; Windows uses SetUnhandledExceptionFilter with
          CaptureStackBackTrace. Symbolise addresses with addr2line -e octave against the same build.
          qFatal goes through the message handler first, so assertion messages are on disk before the abort.
        


        

          The debug log is only created when running with --debug. Total max disk
          usage: ~62 MB with debug, ~32 MB without.

Shutdown & Cleanup

        

          When the application exits, cleanup_on_quit() is connected to
          app.aboutToQuit. It saves state and stops all background operations:
        


        
def cleanup_on_quit():
    media_manager._save_playback_state_now()  # Save current position
    media_manager._clear_temp_files()          # Remove temp audio files
    spotify_manager.cleanup()                  # Stop Spotify polling
    android_auto_manager.cleanup()             # Stop DHU, ADB, head unit
    phone_mirror_manager.cleanup()             # Stop scrcpy process
    esp32_volume_manager.cleanup()             # Disconnect ESP32
    berryimu_manager.cleanup()                 # Stop sensor reading
    gesture_manager.cleanup()                  # Stop gesture polling
    network_manager.cleanup()                  # Stop network polling
    download_manager.cleanup()                 # Clean up download engine


        

          If profiling is enabled, the PerfMonitor and CommandServer are
          also stopped, and the performance report is printed to console.
