Clock

src/managers/clock.{h,cpp} — QML name: clock

A QTimer-based clock that formats the current time once a second and emits it as a string. It reads three settings from SettingsManager on every tick — showClock, clockFormat24Hour and clockShowSeconds — so a settings change takes effect within a second without any signal wiring. Since commit 7777777 it emits timeChanged only when the text actually changed: without seconds the string changes once a minute, so the QML bindings that show the clock re-evaluate 60× less often, and hiding a previously visible clock emits the empty string once. If the clock starts hidden, nothing is emitted, because the cached text is already empty.

Emit-on-change

void Clock::update_time()
{
    QString text;
    if (m_settingsManager->showClock()) {
        // ... build "HH:mm[:ss]" or "hh:mm[:ss] AM/PM" ...
    }
    // Without seconds the text changes once a minute; re-evaluating every
    // binding that shows the clock 60 times for the same string is waste.
    if (text == m_lastText)
        return;
    m_lastText = text;
    emit timeChanged(text);
}

QML consumers

  • frontend/BottomBar.qml — one Connections { target: clock } at bar level writes a shared clockTimeText property that both the horizontal and the vertical layout bind to, so the layout loaded on an orientation switch shows the current time at once instead of waiting for the next emit
  • frontend/ClockMenu.qml — same signal drives the digital readout, the date line and the analog hands (time.split(":") for hours / minutes / seconds; a missing seconds field, i.e. clockShowSeconds off, counts as 0)

The Clock does not log.

Logging

src/util/logger.{h,cpp} (commit 053f587)

OCTAVE writes rotating log files into <app data dir>/logs/, where the app data dir is the same one that holds settingsConfigure.json (Windows %APPDATA%\OCTAVE, macOS ~/Library/Application Support/OCTAVE, Linux $XDG_CONFIG_HOME/OCTAVE or ~/.config/OCTAVE).

FileLevelMax sizeBackupsWhen
octave-cpp.logINFO and above (everything except QtDebugMsg)5 MB3Always
octave-cpp-error.logWARNING, ERROR (QtCriticalMsg) and FATAL, plus crash blocks2 MB5Always
octave-cpp-debug.logDEBUG and above (everything)10 MB2Only with --debug

Worst-case disk use: ~32 MB without --debug, ~62 MB with it — sized for an SD-card head unit that must keep several sessions of history.

The --debug flag

main() scans argv for the literal --debug with strcmp before the QGuiApplication exists and calls OctaveLog::install(debugLogging). With debug the category filter is *.debug=true\nqt.*.debug=false (OCTAVE categories on, Qt’s own off) and the debug file is opened; without it the rule is *.debug=false, so qCDebug calls are filtered at the source and cost nothing.

OctaveLog

namespace OctaveLog {
void install(bool debug);   // message handler + crash handlers; call before QGuiApplication
QString logDir();          // <app data dir>/logs, created on install
void flush();              // flush all three files: aboutToQuit (main.cpp) and after a QtFatalMsg
}

install() creates the log directory via SettingsManager::getAppDataDir(), opens the files in append mode, sets the category filter rules, installs a qInstallMessageHandler and then the crash handlers. The handler formats every qDebug / qInfo / qWarning / qCritical / qFatal and every qC* category call — and, because QML console.* goes through the same Qt message system, every QML log line too — as:

2026-09-10 12:00:00.123 | INFO    | octave.media | mediamanager.cpp:123 | message

Levels are named DEBUG, INFO, WARNING, ERROR (for QtCriticalMsg) and FATAL; uncategorised messages show the category default; the file column is the basename only, or - when Qt supplies no location. On desktop the line is echoed to stderr first (deliberately not chained to Qt’s default handler, which would print it a second time); on Android and iOS, where stderr goes nowhere, the message is handed to the previous (Qt default) handler instead so it still reaches logcat / os_log. It is then written under a QMutex to the debug file (if enabled), to the main file (unless it is a debug message), and to the error file (warning and above). Each write is flushed immediately. flush() has two callers: the aboutToQuit handler in src/main.cpp calls it last, after the settings and metadata flushes, so everything the cleanup logged reaches disk; and the message handler calls it after a QtFatalMsg, right before Qt aborts. It is never called from the crash (signal) handlers, which must stay Qt-free. Rotation happens before a write that would push the file past maxBytes, by a rename chain (.3 deleted, .2→.3, .1→.2, current→.1).

Crash handlers & signal shutdown

Commit 053f587 (crash handlers) and 3810e03 (SIGTERM/SIGINT cleanup). The rule from src/util/logger.h: a crash in the vehicle must leave a trace in the error log.

Signal / exception handlers in logger.cpp

  • Unix: installCrashHandlers() opens octave-cpp-error.log a second time with raw open(O_WRONLY|O_APPEND|O_CREAT) and installs crashHandler for SIGSEGV, SIGABRT, SIGFPE, SIGILL and SIGBUS. The handler uses low-level writes and backtrace functions (no Qt — not even OctaveLog::flush(), which takes a QMutex; the log files need no flush there because RotatingFile::write() flushes every line as it lands): it writes ==== FATAL SIGSEGV - backtrace (addresses; symbolise with addr2line against this build) ====, up to 64 frames, and ==== end ==== to the error log and a shorter block to stderr, then restores SIG_DFL and re-raises so the OS still produces a core dump / tombstone. Backtraces exist only where execinfo.h is available (glibc or macOS); elsewhere — Android’s bionic libc — the block reads (no backtrace support on this platform).
  • Windows: SetUnhandledExceptionFilter(crashFilter) writes ==== FATAL exception 0x<code> at <address> ==== plus up to 62 CaptureStackBackTrace frames via _write, then returns EXCEPTION_CONTINUE_SEARCH.
  • qFatal is not a signal: it goes through the message handler as FATAL, after which the handler calls OctaveLog::flush(), before Qt aborts (SIGABRT → crashHandler appends the backtrace), so assertion text is on disk before the SIGABRT block.

SIGTERM / SIGINT run the normal cleanup

Launcher scripts, systemd and Ctrl-C all deliver a signal; the default action would kill the process without running aboutToQuit, leaving child-process and device cleanup incomplete (adb, ffmpeg, the DHU) and leaking the phone-mirror adb forward. src/main.cpp (#if !defined(Q_OS_WIN) && !defined(Q_OS_MOBILE)) therefore turns the signal into QCoreApplication::quit() with the self-pipe trick. A socketpair() is created; the std::signal handler only writes one byte into it, and a QSocketNotifier on the other end reads the byte on the event loop, logs Signal received, shutting down and calls QCoreApplication::quit(). Nothing Qt-side runs in signal context.

The aboutToQuit cleanup stops the dev runtime (on OCTAVE_DEV_TOOLS builds: command server, perf monitor and any recording) and the UI watchdog first, cleans up Android Auto, phone mirror, ESP32, IMU, gesture, OBD, downloads and network, then saves playback with _save_playback_state(), flushes the metadata store and the settings (flushPendingSave(), which writes immediately), and finishes with OctaveLog::flush().

UI watchdog

src/util/uiwatchdog.{h,cpp} — class UiWatchdog, commit f157b97. Not registered as a QML context property; it is started in src/main.cpp just before the managers are built (AppCore) and stopped from the quit cleanup.

A hung event loop used to vanish without a trace — the screen froze and the log simply stopped. The watchdog is a worker thread that posts a “ping” to the GUI thread every pingMs (2000) and records when the GUI thread answers it. If the answer is older than stallMs (5000) it logs once UI thread blocked for N s and counting as a WARNING on octave.ui_watchdog, and when the GUI thread catches up (silence back under one ping interval) it logs UI thread responsive again after N s. The warning also lands in octave-cpp-error.log (that file is WARNING+). Time is measured on a monotonic clock (QElapsedTimer), so a wall-clock jump (the Orange Pi has no RTC, and NTP corrects its clock after boot) cannot register as a stall.

worker thread ("ui-watchdog") GUI thread │ │ │─ sleep pingMs (2 s) ─┐ │ │◄─────────────────────┘ │ │── queued invoke: lastPong = now ───────────────►│ (runs when the event loop gets to it) │ │ │ silent = now - lastPong │ │ silent > stallMs (5 s) → WARNING "blocked for N s and counting" (once) │ silent ≤ pingMs after a stall → WARNING "responsive again after N s"
MemberBehaviour
constructorUiWatchdog(QObject *parent = nullptr, int pingMs = 2000, int stallMs = 5000)
start()Starts a QThread named ui-watchdog; the loop runs from its started signal
stop()Clears the atomic running flag, quit() + wait(2000)
ping mechanismQMetaObject::invokeMethod(this, lambda, Qt::QueuedConnection) writing an std::atomic<qint64> (monotonic ms since the watchdog started)

A warning means the GUI failed to answer within the configured threshold; it does not identify the cause. Expected long operations can also trigger it, so use the surrounding logs to diagnose a stall.

VolumeController

src/managers/volumecontroller.{h,cpp} — QML name: volumeController. Introduced in commit d2b047b (“volume curve de-duplication”).

OCTAVE maps the UI volume percent (0–100) to a linear audio gain (0.0–1.0) through a quadratic curve, (percent / 100)2, which gives a more natural perceptual response at low volumes than a straight line. VolumeController owns the math and is the single entry point for routing a percent to every output; changing the curve means editing toLinearStatic() in one place.

Dispatch: who gets what

Settings store the percent, local media and the phone mirror take the linear gain, and the ESP32 LED takes the raw percent. The controller itself only emits; the fan-out is in main.cpp:

// src/main.cpp
QObject::connect(&volumeController, &VolumeController::volumeApplied,
                 [&mediaManager, &phoneMirrorManager, &esp32VolumeManager](int percent, float linear) {
    mediaManager.setVolume(linear);
    phoneMirrorManager.setVolume(linear);
#ifndef Q_OS_MOBILE
    esp32VolumeManager.send_volume_update(percent);   // the ESP32 manager rate-limits itself (50 ms)
#endif
});
volumeController.applyVolume(settingsManager.currentVolume());   // startup volume

The ESP32 leg is compiled out on mobile, where the manager is a stub.

Callers

  • frontend/BottomBar.qml (four slider / button sites) and frontend/MediaRoom.qml call volumeController.applyVolume(Math.round(value))
  • Gesture sensor volume_up / volume_down: applyVolume(currentVolume ± gestureVolumeStep)
  • ESP32 knob volumeChangeRequested(delta): fractional deltas are accumulated and applied once they reach a whole percent
  • AppCore::wireVolume() (src/appcore.cpp) calls applyVolume(settingsManager.currentVolume()) once after the outputs are constructed, so the configured startup volume reaches every output at startup
Rule

Never call an individual manager’s setVolume from QML or a hardware handler, and never re-derive the curve. Everything goes through volumeController.applyVolume(percent).

Version & update check

CMakeLists.txt — surfaced with the Diagnostics card (b5d47b8).

  • project(OCTAVE VERSION 0.9.5 LANGUAGES CXX) is the source of truth. CMake passes OCTAVE_VERSION="${PROJECT_VERSION}" as a compile definition (next to OCTAVE_ENABLE_DOWNLOADS) and reuses PROJECT_VERSION for MACOSX_BUNDLE_BUNDLE_VERSION / MACOSX_BUNDLE_SHORT_VERSION_STRING. diagnosticsmanager.cpp falls back to "dev" if the define is missing.
  • The APK's versionName / versionCode come from it as well (QT_ANDROID_VERSION_NAME / QT_ANDROID_VERSION_CODE, code = major×10000 + minor×100 + patch). Only the Windows installer (MyAppVersion in build_scripts/installer_windows.iss) carries its own copy; bump it in the same commit (CI patches it from the tag on release builds).
  • The version is surfaced to users only through diagnosticsManager.appVersion (Device diagnostics card and the log export header).

The update check does not use the version string. NetworkManager.checkForUpdates() compares the local git HEAD against https://api.github.com/repos/<repo>/commits/main and reports up-to-date / update-available / ahead / diverged / error through updateStatus; the About page and the settings layouts show a badge when it is update-available. See Network Manager.

Performance monitor & perf tooling

src/dev/perfmonitor.{h,cpp}, src/util/perfscope.h; client tools in dev/perf/, dev/mcp_server.py, dev/mcp_benchmark.py and .mcp.json. Compiled in only with OCTAVE_DEV_TOOLS.

Everything here is switched on by one flag: build/octave --profile. OctaveDev::Runtime (src/dev/devruntime.cpp) creates a PerfMonitor writing dev/perf/logs/perf_<yyyyMMdd_HHmmss>.csv and .log under the project root, registers it as the QML context property perfMonitor before Main.qml loads (no shipped QML binds to it; it is there for a HUD), and after the load starts it together with the command server. Runtime::shutdown(), first in the aboutToQuit cleanup, stops both; the detailed report is appended to the .log.

PerfMonitor internals

ComponentWhat it measures
RingBufferFixed-size sample window with mean(), max() and linear-interpolated percentile(p). Capacities: 1000 for loop latency (5 s of 5 ms ticks, cleared every report), 300 for thread jitter, 200 per timing label.

With dev tools built but no --profile, a scope costs one relaxed atomic load; without OCTAVE_DEV_TOOLS it compiles to nothing.

Reporting cycle (every 1 s)

  1. Loop latency avg / p50 / p95 / p99 / max from the ring buffer; jitter avg / p99; CPU, memory and thread count.
  2. Terminal line ([PERF]), colour-coded by average loop latency: green < 5 ms, yellow < 16 ms, red otherwise. Labels whose p95 exceeds 2 ms are listed every fifth report.
  3. Plain-text line in the perf .log tagged OK / WARN / STUTTER with the same thresholds, plus SLOW lines.
  4. CSV row: timestamp, loop_avg_ms, loop_p50_ms, loop_p95_ms, loop_p99_ms, loop_max_ms, gil_avg_ms, gil_p99_ms, cpu_pct, mem_mb, threads.
  5. Loop buffer cleared, metricsUpdated emitted.

QML properties (all notify on metricsUpdated)

loopLatencyMs, loopP99Ms, gilJitterMs, cpuPercent, memMb (double), threadCount (int), summaryText (str, a one-line HUD string). Invokable: getDetailedReport() → str, listing loop / jitter / CPU and every label with p95 > 1 ms sorted by p95.

Command server

src/service/commandserver.{h,cpp} (server), src/dev/coreactions.cpp (built-in actions), src/dev/uidriver.{h,cpp} (navigation, capture and input), src/dev/collagebridge.{h,cpp} (UI collage actions). Started by OctaveDev::Runtime when --profile is passed on an OCTAVE_DEV_TOOLS build. Listens on 127.0.0.1:9876; --command-port N (or --command-port=N) moves it. If the port is taken it logs command server could not listen on 127.0.0.1:9876 and the app carries on without it.

Protocol

One JSON object per line in, one per line out. args is optional.

{"action": "navigate", "args": {"page": "obd"}}
{"ok": true, "result": {"navigated_to": "obd"}}

{"action": "bogus"}
{"ok": false, "error": "Unknown action: bogus"}

Invalid JSON gets {"ok": false, "error": "Invalid JSON: …"}; an exception thrown by a handler (CommandError or any std::exception) is logged on octave.service and returned as error. A client may keep the connection open and send many lines.

Architecture

CommandServer (lifecycle: start / stop / registerAction) │ ├── CommandTcpServer QTcpServer on its own QThread ("cmd-server"), │ │ bound to QHostAddress::LocalHost │ └── one QThread per client reads JSON lines → handleLine() → dispatch() │ ├── handlers{} action → std::function, registration order kept │ for list_actions │ └── GUI-thread access from a handler CommandServer::postGui(fn) queued, fire and forget (navigation, sim_*) CommandServer::onGui(fn) queued + semaphore wait for the result (30 s timeout → "GUI thread did not answer")

Handlers run on the connection thread, so a slow GUI call on one client never blocks get_metrics on another. Anything that touches Qt objects goes through onGui() (screenshots, item lookup, clicks, settings reads) or postGui() (navigation). Calls into QML functions go through invokeByName(), which passes each argument as a QVariant when the parameter is untyped (a QML JS function), and converts it to the parameter type otherwise.

Service protocol

The way any frontend, in any language, reads and drives OCTAVE (TODO/open-backend.md, contract steps 1 and 4). It shares the command server's socket and line format, keyed on op instead of action: the arguments sit at the top level, and an optional id is echoed in the reply so a client can pipeline requests. The dev tooling's action form keeps working unchanged next to it.

Off unless asked for (src/service/serviceoptions.{h,cpp}; main.cpp owns the server). The protocol has no authentication, so it starts only with --service [PORT] (or --service=PORT; 9876 by default, 0 for any free port), the serviceEnabled setting, --headless (no UI, so the service is the only way in; hello reports app.headless: true), or --profile in an OCTAVE_DEV_TOOLS build, and it listens on 127.0.0.1 unless --service-bind ADDRESS says otherwise (0.0.0.0 for every interface; the log then warns that anything on the network can drive the app). --command-port N still picks the port. A bad port or address leaves it off with a warning. Plain --service serves the ops plus ping / list_actions; the UI-driving, screenshot, perf and sim_* actions are added only by --profile's dev runtime and are never built into a Release binary.

Browsers (src/service/websocket.{h,cpp}, RFC 6455 by hand: Qt WebSockets is in no build). The same port takes a WebSocket (ws://127.0.0.1:9876/): one request, reply or event per text frame, the same JSON as a line; ping gets pong, a client close ends the connection, a malformed or unmasked frame or a message over 1 MB closes it (1002). No extensions are negotiated. A plain GET / serves the reference client (sdk/web/index.html, embedded as :/web-client/index.html), so a browser reaches the service same-origin; any other path is a 404. The first byte of a connection picks the protocol ({ lines, G HTTP). Origin rule: a request without Origin (scripts, the SDK) is allowed; a browser only from the service's own page: the Origin's host and port must equal the Host header's, and that host must be an IP address or localhost, because a name could be DNS-rebound to the car by any website. null (file:// pages, sandboxed iframes) is refused. Refusals get a 403 with the reason and a log warning. The page goes out with nosniff, no-store and a Content-Security-Policy that limits it to this service. Open it by address, not by a .local name.

Your own web frontend (src/service/staticfiles.{h,cpp}): --web-root DIR (or the serviceWebRoot setting, edited in the file; the flag wins) serves a directory at GET / instead of the reference client, so a built frontend is same-origin with the socket and passes the Origin rule. It does not turn the service on by itself, and a directory without an index.html is not used (a warning, and the reference client is served): / or a home directory is never published by mistake. Types by extension (html, js / mjs, css, json, svg, png, jpg, gif, webp, avif, ico, woff / woff2 / ttf / otf, wasm, webmanifest; anything else application/octet-stream, with nosniff); a directory serves its index.html; a path with no extension that names nothing gets the root index.html (single-page-app routes); a missing file with an extension is a 404. Refused: .. (also percent-encoded) 403, a backslash or NUL 400, any segment starting with . 404 (.git, .env), anything whose canonical path leaves the root through a symlink 403, files over 64 MB 413, methods other than GET 405. Its Content-Security-Policy allows the page's own scripts (no inline script; WebAssembly allowed), inline styles, data: / blob: images and fonts, and sockets only to this service ('self' plus ws:// / wss:// the request's Host when that is an IP or localhost), with frame-ancestors 'none'. Requests from the page carry its Origin and pass the same rule; a page on another site gets 403.

Demand follows the connection (ServiceBridge::releaseOnClose, wired in src/main.cpp): a call to obdManager.setParameterDemand / setBackgroundDemand or berryIMU.setDemand is remembered against its connection, and when the connection closes, cleanly or not, each consumer it still holds is released (called again with [] / false), so a killed client never leaves the car polled until a restart. A consumer the client released itself, or one a later connection registered under the same name, is left alone.

Album art and other routes (CommandServer::addRoute): GET /art (any ?query ignored, so /art?rev=N busts caches) answers with nowPlaying's current cover, read from its own artUrl file, never from anything in the request; typed by its signature (JPEG, PNG, GIF, WebP, BMP), 404 for no art, a non-image or a file over 16 MB. Clients key their cache on nowPlaying.artRevision. /art?song=<library file name> serves a library song's cover, resolved only through MediaManager's own lookup (libraryArtFile: the song must be in the scanned library, the file must canonically sit in the app's art cache), and /art?queue=<id> a phone queue item's art (PhoneMirrorManager::queueArtFile: the id must be in mediaQueue, the file in the queue-art folder); anything else is a 404. GET /export/trip (?format=json for its JSON sibling), /export/dashboard and /export/logs serve what the app itself last exported (tripRecorder.lastExportPath, dashboardManager.lastExportPath, diagnosticsManager.lastExportPath) as an attachment (Content-Disposition with a sanitised name, 64 MB cap, 404 before any export); the logs export is a folder, so /export/logs is a JSON list of its file names and ?file=<name> one of exactly those. Routes are answered ahead of the web root and the page. Cross-site loads: a plain request whose Sec-Fetch-Site is anything but same-origin or none (the address bar) is refused with 403, because an <img> or <script> on another site sends no Origin; non-browser clients send no such header and are not affected.

Media streams (src/service/streamhub.{h,cpp}; the full record layout is in docs/api/README.md, "Streams"): stream {object, name} → {stream, format, codec?, width?, height?}, then binary records on the same connection (one binary WebSocket frame each; on the line protocol 0xFF + u32 length + record): u8 version | u8 stream | u8 flags (1 key, 2 config, 4 JPEG, 8 discontinuity) | u8 0 | u64 pts µs | payload. phoneMirrorManager.video is the phone's H.264 as it arrives (tapped in ScrcpyClient's video loop before decoding, so the in-app picture is untouched; nothing is copied while nobody watches), Annex-B, every keyframe with SPS / PPS first; androidAutoManager.frames is JPEG from the DHU frame provider, at most 15 a second. streamConfig events announce parameter-set changes; a joiner waits for the next keyframe, and the phone is asked for one (RESET_VIDEO) at most once a second across all clients; a client that falls behind (2 MB or 90 records queued) loses its queue, gets streamDropped and resumes at a keyframe. unstream {stream}, or closing the connection, ends it. The connection queue keeps events and records in order (Connection::pushRecord). Dev builds: sim_video loops tests/data/stream-test.h264 into the phone stream.

Pairing (protocol 2) (src/service/servicepairing.{h,cpp}, ServiceBridge::trusted, CommandServer::setTrust): a connection is trusted if its peer is loopback and serviceLoopbackOpen is true (the default), or after pair {code, name} or hello {token}. The check runs in handleLine before every op and action except hello and pair ({"ok": false, "code": "unauthorised"}), and for the HTTP routes (/art, /export: 401 unless trusted, a valid ?ticket= from mediaTicket, or Authorization: Bearer). Codes: 6 digits from the system CSPRNG, 2 minutes, single use, void after 5 wrong tries; one attempt a second overall; 10 wrong codes lock an address out until restart; refusals logged with the address only. Tokens: 32 random bytes, kept as SHA-256 in serviceTokens (file-only), compared in constant time. Revoke (Settings) closes the device's connections (closeConnectionsOf: cleanups run, the connection thread drops the socket) and voids its tickets. Every HTTP reply carries Referrer-Policy: no-referrer; request query strings are never logged. The head unit's side is Settings > Device > Service (frontend/settings/DeviceSettingsPage.qml): the service switch with its warning (takes effect at the next start), "Show a code" (the 6 digits and a countdown), and the paired devices with Revoke.

  • Version. kProtocolVersion in src/service/protocol.h (1). It is bumped on any breaking change: a removed or renamed op, object, property, method or signal, or a changed type or meaning. Additions don't bump it, and clients ignore fields they don't know.
  • Ops. src/service/servicebridge.{h,cpp} registers them on the server (CommandServer::registerOp). An unknown op is {"ok": false, "error": "Unknown op: …"}; an unknown object "Unknown object: …".
    • hello → {protocolVersion, app: {version, build, headless}, objects: [names]}.
    • describe {object?} → one object's {class, properties, methods, signals, enums?}, or every object's as {protocolVersion, objects: {name: …}} (about 110 KB for all 23). A property is {name, type, readable, writable, constant, notify?, enum?} (enum lists the keys of a Q_ENUM), a method {name, kind: "invokable" | "slot", params: [{name, type}], returns}, a signal {name, params}. Only what the app's own classes declare: members of Qt base classes (QObject, QAbstractItemModel, QQmlPropertyMap…) are left out, overloads are listed apart. src/service/metadescribe.{h,cpp}, which step 3's schema generator reuses.
    • get {object, property} → the value. On paramStore (a QQmlPropertyMap, keyed by parameter id) property is a key (null before its first reading), and without one the reply is every key that has a value.
    • set {object, property, value} → the value read back. Only writable properties: most manager state is read-only and changes through a method (settings through their save_* slots, e.g. call settingsManager save_gauge_temp_unit ["F"]), which keeps every rule in the manager.
    • call {object, method, args?: [...], timeoutMs?} → the return value (null for void). Overloads are told apart by argument count.
    • subscribe {object, signals?: [...], properties?: [...], throttleMs?} → {sub}, then events on the same connection (the reply always first: only the connection's own thread writes to the socket, and it writes a request's reply before the events queued meanwhile; tst_servicebridge subscribeReplyComesBeforeItsEvents), interleaved with replies (a reply has ok, an event event):
      • {"event": "property", sub, object, name, value, t}: the current value at once, then on every notify signal (read on the object's thread, so a notify with no argument still carries the value);
      • {"event": "signal", sub, object, name, args: [...], t};
      • {"event": "params", sub, object, values: {id: v}, t} on paramStore: its 33 ms batches of changed readings, filtered to properties (the ids; none = all), starting with what it holds;
      • {"event": "dropped", count} when a client stopped reading and more than 1000 events queued up (the oldest go).
      throttleMs coalesces: at most one event per name (one merged params event) per interval, the latest value winning. t is when the event was sent (a throttled one: the flush), in milliseconds on a monotonic clock that starts at the bridge's first event: for ordering and intervals, not wall time. A signal emitted on a worker thread is queued to the GUI thread first. A subscription ends with an unsubscribe {sub}, with its object, or with the connection.
    • List models (a property holding a QAbstractItemModel: today downloadManager.searchResults and downloadQueue). get gives {model: true, count, roles}; rows {object, property, from?, count?} the rows as {role: value} maps; subscribing to the property sends {"event": "model", …, name, change, first, last, rows?} with change one of reset (all rows; also the first event), insert and update (with the affected rows) and remove, which a client replays in order to keep its copy. List events ignore throttleMs.
    get, set and call run on the object's (GUI) thread, so a slow method holds the UI just as it would from QML; the client waits up to timeoutMs (default 30 s). Enum values travel as their key names ("Connected"; an enum property reads as its key); on the way in a Q_ENUM parameter takes the key or its number (convertTo() in commandserver.cpp), anything else is refused.
  • When it runs. For now with --profile in OCTAVE_DEV_TOOLS builds, like the command server; the dev runtime installs the bridge on its server.

Design decisions

Why the volume curve lives in one object

Commit d2b047b moved every copy of the curve, including those in BottomBar.qml and MediaRoom.qml, into VolumeController. The risk is plain: every output must use the same curve or they drift out of sync when the user moves the slider. The controller emits volumeApplied rather than holding the output managers so it can be constructed before the managers it feeds exist (“avoids tight coupling — VolumeController doesn’t need pointers to managers that may not exist yet”, volumecontroller.h).

Why the Clock emits on change

Commit 7777777: with seconds hidden the string changes once a minute, but the old code emitted it every second and every binding that shows the clock re-evaluated 60 times for the same value; a hidden clock emitted "" forever. Comparing against the last emitted text costs one string compare per second and removes the churn. Settings are still re-read on every tick rather than wired to change signals, which keeps the class free of any signal connections.

Why the crash handlers write where they do

The observability overhaul (053f587) exists because the head unit runs unattended in a vehicle: the only thing a user can do after a freeze or crash is export the logs from the Device settings page later. Crash traces are therefore written to the error log. Diagnostics exports both main and error logs, and its tail combines the main log with a shorter error-log tail. The code comments spell out the constraint: “a separate descriptor, opened once, so the signal path never touches Qt” and “async-signal-safe as far as practical” — the handler only calls write() and backtrace_symbols_fd() on that raw descriptor. It then restores SIG_DFL and re-raises so the OS still writes its core dump / tombstone; the file log is additive, not a replacement.

Why SIGTERM/SIGINT go through the event loop

Commit 3810e03: with the default action, a launcher or systemd stopping the app killed the process outright and the phone-mirror adb forward leaked. Calling QCoreApplication::quit() from inside a signal handler is not safe, so the handler only writes a byte into a socketpair and a QSocketNotifier does the real work on the event loop. It ends in the same aboutToQuit cleanup that a window close triggers.

Why a watchdog, and why it stops first

The header comment states the goal: “so a frozen head unit leaves a trace”. The watchdog (f157b97) is the smallest thing that turns a hang into evidence: one thread, one queued call, one warning per stall with the duration on recovery. The 2 s ping and 5 s stall threshold detect prolonged event-loop delays without logging on every normal tick. Commit 95dfb49 moved stop() to the head of the quit cleanup after a Pi run where the worker pinged a QObject Qt had already destroyed and the error was reported as CRITICAL — noise the whole effort exists to remove.

Why a TCP command server rather than an in-process test harness

The command server is what lets every external tool — the screenshot sweeper, the dashboard-editor scenario, the perf loops and the MCP servers — drive the real app process from outside without a display server: the app captures itself with grabWindow() and injects input from inside Qt (QTest mouse events, key events sent to the item), so the same scripts run on Wayland, X11, Xvfb and offscreen (an earlier xdotool + mss approach broke under Wayland). Newline-delimited JSON over localhost is trivially scriptable from any language and from an MCP tool. It is bound to 127.0.0.1, is only started with --profile, and is compiled only into OCTAVE_DEV_TOOLS builds, so release binaries do not contain it. registerAction() lets dev-only code such as the car simulator and the collage bridge add actions without touching the core table.

Why perf instrumentation is a macro

OCTAVE_PERF_SCOPE keeps profiling out of shipped binaries entirely: without OCTAVE_DEV_TOOLS it expands to static_cast<void>(0), and with the tooling built but --profile off it is one relaxed atomic load. The labels are plain strings, so the list of instrumented functions can grow without touching the monitor.
