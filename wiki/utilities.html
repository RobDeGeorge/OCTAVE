What Is Here

Media, the car, the sensors and the phone each have a page of their own. This page covers what sits underneath all of them: the code that writes the log files, notices a crash or a frozen screen, turns one volume number into sound on every output, tells the time, and lets other programs talk to OCTAVE.

Most of it has no screen. The one part a driver meets is the Diagnostics card, which gets the logs out of a head unit without a laptop. The rest is for people changing the code or writing a program that talks to OCTAVE.

The page starts with the parts you are most likely to need and gets more technical as it goes.

Logs

OCTAVE writes everything it reports to log files, so that a problem on the road can be understood later. They are in a logs folder inside the config folder, next to settingsConfigure.json:

SystemLog folder
Linux, Raspberry Pi, Orange Pi~/.config/OCTAVE/logs/
Windows%APPDATA%\OCTAVE\logs\
macOS~/Library/Application Support/OCTAVE/logs/
Started with --config DIRDIR/logs/

A --sim run without --config uses a throwaway config folder that is deleted at exit, and its logs go with it. On Android and iOS each line also goes to the system's own log (logcat on Android).

FileWhat is in itSize before it rotatesOld copies kept
octave-cpp.logEverything except debug messages. Read this first.5 MB3
octave-cpp-error.logWarnings and errors only, plus a block for every crash.2 MB5
octave-cpp-debug.logEverything, debug messages included. Only written when OCTAVE is started with --debug.10 MB2
hang-<time>.txtWhat every thread was doing during a freeze. Written by the UI watchdog on Linux.the newest 10

A full file becomes .1, the old .1 becomes .2, and so on; the oldest is deleted. The logs never take more than about 32 MB, or 62 MB with --debug.

Every line has the same shape: time, level, category, source file and line, message.

2026-09-10 12:00:00.123 | INFO    | octave.media | mediamanager.cpp:123 | message

The levels are DEBUG, INFO, WARNING, ERROR and FATAL. The category says which part of the app wrote the line: octave.media, octave.elm327, octave.phonemirror, octave.service and so on. A line with the category default came from code that names none, which includes console.log() in QML.

Logging from your code

Use Qt's own logging; nothing else is needed. Everything written with qInfo(), qWarning(), qCritical() or the category forms, and every QML console.* call, ends up in the files. 

Q_LOGGING_CATEGORY(lcFoo, "octave.foo")      // once, at the top of foomanager.cpp

qCInfo(lcFoo) << "Connected to" << port;       // main log
qCWarning(lcFoo) << "No answer from" << port;  // main log and error log
qCDebug(lcFoo) << "raw reply" << bytes;        // debug log, only with --debug

Without --debug, debug messages are switched off before they are built, so a qCDebug in a hot path costs nothing. With it, OCTAVE's own debug messages are on and Qt's internal ones stay off. To find the category a part of the app uses, search the sources for Q_LOGGING_CATEGORY.

How it works

OctaveLog::install() (src/util/logger.cpp) is the first thing main() calls, before the application object exists. It opens the files and replaces Qt's message handler with one that formats each message as above, prints it to the terminal, and writes it to the files it belongs in. Each line is written to disk at once, so nothing is lost if the app dies on the next line.

One lock guards the files. A thread that cannot get it within 2 seconds (another thread is stuck writing to a failing SD card, say) writes its line straight to the error log and carries on, so one stuck thread cannot stop the rest of the app from logging.

Crashes and Shutdown

From here on the page is for people who are changing the code or reading a log after a failure.

The rule is that a crash in the car must leave a trace. When the app dies, a block like this is added to octave-cpp-error.log: 

==== FATAL SIGSEGV - backtrace (addresses; symbolise with addr2line against this build) ====
...up to 64 frames...
==== end ====
SystemWhat is written
Linux, macOSThe signal (SIGSEGV, SIGABRT, SIGFPE, SIGILL or SIGBUS) and a backtrace of addresses. Turn them into function names with addr2line and the same build.
AndroidThe signal only: (no backtrace support on this platform). The system's own crash report (tombstone) has the stack.
Windows==== FATAL exception 0x<code> at <address> ==== and up to 62 frame addresses.

After writing the block the handler hands the crash back to the operating system, which still produces its core dump or crash report. A failed assertion (qFatal) is logged as a FATAL line first, so its text sits just above the block.

A stack overflow on the main thread (runaway recursion in QML or C++) is caught too: the handler has a stack of its own there. On any other thread a stack overflow still leaves no block.

Rule for the crash handler

It runs inside a signal, so it may only use raw write() calls on a file descriptor opened at startup. No Qt, no memory allocation, no locks. Keep it that way.

Stopping cleanly

Closing the window, Ctrl-C, a launcher script and systemd all end the same way. On Linux and macOS, SIGTERM and SIGINT are turned into an ordinary quit: the signal handler only writes one byte to a socket, and the event loop reads it, logs Signal received, shutting down and quits. Without this the app would be killed on the spot and leave child processes and the phone's adb forward behind.

The quit cleanup then runs in this order:

  1. The dev tooling stops, where it is built: the perf log is finished and a screen recording is closed.
  2. The service stops, so no client reaches a manager while it shuts down.
  3. The UI watchdog stops.
  4. AppCore::shutdown(): Android Auto, the phone mirror, the knob, the sensors, the open trip, the OBD adapter and the network are closed; then the playback position, the music metadata and the settings are written.
  5. The logs are flushed, last, so everything the cleanup logged is on disk.

When you add a manager that owns hardware, a child process or unsaved state, give it a place in AppCore::shutdown() (src/appcore.cpp).

Freezes: the UI Watchdog

A crash leaves a block in the log. A freeze used to leave nothing: the screen stopped and so did the log. The watchdog is a small thread that asks the main thread "are you there?" every 2 seconds and acts on how long it has gone without an answer:

No answer forWhat happensWhere
5 secondsOne warning: UI thread blocked for N s and counting. When the main thread answers again: UI thread responsive again after N s.Everywhere
15 secondsThe stack of every thread is written to hang-<time>.txt in the log folder. This needs gdb installed; without it the log says gdb not installed; no stack dump for this hang.Desktop Linux (not Android)
30 secondsOCTAVE logs UI thread blocked for N s; aborting so the launcher restarts OCTAVE and aborts. On the head unit the launcher script (deployment/orange-pi-5-plus/home/.local/bin/octave-start.sh) starts it again, so a frozen screen clears by itself and not by pulling the power.Desktop Linux (not Android)

Things to know when reading these lines:

  • The lines have the category octave.ui_watchdog. The warnings are in the main log and in octave-cpp-error.log; the abort line is in the error log only.
  • A warning says the main thread was busy; it does not say why. Look at the lines just before it, and at the hang file if there is one.
  • During the first 2 minutes after launch the watchdog does not abort: a first scan of a large music library can keep the main thread busy for a while.
  • The abort line has a UTC time ending in Z; every other line is in local time.
  • In the browser demo a hidden tab is not a freeze. The log says page hidden; the browser paused it.
  • Time is measured on a clock that never jumps, so the clock being corrected after boot on a board with no battery clock is not mistaken for a freeze.

The watchdog is the class UiWatchdog (src/util/uiwatchdog.{h,cpp}). main() starts it before the managers are built, with or without a screen (--headless has one too). The five times are constructor arguments. It is not available to QML or the service.

Volume

OCTAVE has one volume, a number from 0 to 100, and several places that play sound. volumeController is the only thing allowed to change it. A slider, the gesture sensor, the volume knob and a remote client all call the same method, and it tells every output.

Rule

Never call a manager's own setVolume or setMuted from QML or a hardware handler, and never work out the curve yourself. Everything goes through volumeController.

To do thisUse
Set the volumevolumeController.applyVolume(percent). Values outside 0 to 100 are clamped.
Show the volumeBind to volumeController.percent.
Mute buttonvolumeController.toggleMute()
Mute iconBind to effectivelyMuted: true when muted or when the volume is 0.
Mute without the button's rulesSet muted.
Convert between percent and gaintoLinear(percent), toPercent(linear); in C++ without an instance, VolumeController::toLinearStatic() / toPercentStatic().

The full list is in the API reference.

Slider {
    from: 0; to: 100
    value: volumeController.percent
    onMoved: volumeController.applyVolume(Math.round(value))
}

The rules every input shares

  • Turning the volume up while muted unmutes. It does not matter which input did it.
  • The mute button at 0 % restores the start-up volume and unmutes: there would be nothing to unmute to.
  • Two presses of mute within 150 ms count as one. The knob's button bounces.
  • Neither the volume nor mute is saved. After a restart the volume is the start-up volume from Settings and mute is off.
  • Five presses of mute within 4 seconds is the escape gesture (escapeGesture, experimental): while an installed program is the screen, it brings the built-in screen back. See Writing a Frontend.

How it works

Ears do not hear loudness in a straight line, so the percent is not used as the gain. OCTAVE squares it: gain = (percent / 100)². Half way on the slider is a gain of 0.25, and the bottom of the slider gives fine control where the ear is most sensitive.

applyVolume() stores the percent, works out the gain and emits volumeApplied(percent, gain). The controller knows no output. AppCore::wireVolume() (src/appcore.cpp) connects them:

OutputGets
Local music, phone mirror audio, Android Auto, AirPlayThe gain (0.0 to 1.0). Mute goes to the same four.
SpotifyThe percent, while Spotify is what is playing and mute is off. Spotify plays on another device, which applies its own curve.
The volume knob's LED ringThe percent. Not on phones.

To change the curve, edit toLinearStatic() and its inverse toPercentStatic() in src/managers/volumecontroller.{h,cpp}. Nothing else holds a copy.

Clock

clock.time is the time as text, in the format the user chose. Bind to it and you are done: the bottom bar and the hand-built Home screens do exactly that. 

Text { text: clock.time }
SettingsWithout secondsWith seconds (clockShowSeconds)
24-hour (clockFormat24Hour on)14:3014:30:05
12-hour02:30 PM02:30:05 PM
showClock offempty text

The three settings are in Settings > Display; see the Settings Reference. A change shows within a second. AM and PM are always written that way, whatever the system language.

The text only changes, and timeChanged only fires, when the time shown changes: once a minute without seconds. So do not use it as a one-second tick. The Clock page (frontend/ClockMenu.qml) needs a second hand and runs a timer of its own for that reason.

API: clock. Source: src/managers/clock.{h,cpp}.

Version and Update Check

The version is written in one place: project(OCTAVE VERSION x.y.z ...) at the top of CMakeLists.txt. From there it reaches:

  • the app, as diagnosticsManager.appVersion (the Diagnostics card, the log export, the service's hello reply) and octave --version;
  • the macOS bundle version;
  • the Android package: its version name, and its version code, which is major × 10000 + minor × 100 + patch. Android only installs an update whose code is higher.

The Windows installer keeps a copy of its own, MyAppVersion in build_scripts/installer_windows.iss. Change it in the same commit.

The build also records the git commit it was made from (OCTAVE_GIT_COMMIT and OCTAVE_GIT_DATE in the generated buildinfo.h; "unknown" when built without git).

The update check works in one of two ways. A packaged build (AppImage, Windows installer, .dmg, APK) asks GitHub for the latest release and compares its tag with its own version. A source checkout compares its commit with main on GitHub. Both belong to networkManager: see Network Manager.

Timing Code

To find out how long a function takes on the real device, put one line at its top:

#include "../util/perfscope.h"

void MediaManager::next_track()
{
    OCTAVE_PERF_SCOPE("media.next_track");   // times the rest of the function
    ...
}

Start a Debug build with --profile and the time is recorded under that label, from any thread. The same run measures how late the event loop is running (the cause of a stuttering screen), CPU and memory, prints a line every second and writes a CSV and a log to dev/perf/logs/. Reading the numbers, and the tools that collect them, are on the Development page.

The line costs nothing in a shipped app. Release builds compile it to nothing; a Debug build without --profile pays one check of a flag.

Dev tooling is in Debug desktop builds only

Everything under src/dev/ is built only with the CMake option OCTAVE_DEV_TOOLS, which is on by default for -DCMAKE_BUILD_TYPE=Debug on desktop and off everywhere else. Without it, --dev and --profile log a warning and the app starts normally.

Command Server

The command server is how scripts drive the running app: take a screenshot, open a page, tap a button, read the perf numbers. It is the same socket as the service protocol below, with a second kind of request, keyed on action: 

{"action": "navigate", "args": {"page": "obd"}}
{"ok": true, "result": {"navigated_to": "obd"}}

Two actions exist in every build: ping and list_actions. The ones that drive the screen, record video and read the perf monitor are added by the dev tooling when a Debug build is started with --profile, and the sim_* ones with --dev. They are never in a Release build. Send list_actions to see what the app you are talking to offers; the list and the scripts that use it are on the Development page.

To add an action, call registerAction(name, handler) on the server. Two things to know when writing a handler:

  • It runs on the connection's own thread, not the main thread. A slow request from one client never holds up another.
  • Anything that touches a Qt object must go through CommandServer::onGui(fn), which runs fn on the main thread and waits for its result (30 seconds at most), or postGui(fn), which does not wait.

Service Protocol

The built-in screen is one way to use OCTAVE. The service protocol is the way for everything else: a web page, a phone app, a script, a whole replacement screen. It serves the same objects QML uses (mediaManager, obdManager, volumeController ...) under the same names, so anything the built-in screen can do, another program can do.

This section says how the protocol behaves. To write a client, start with Writing a Frontend. What each object offers is in the API reference. The exact form of every message is in docs/api/protocol.json and docs/api/README.md.

When it runs

The service is off unless asked for. Any of these turns it on:

HowEffect
--service [PORT]On for this run. The port is 9876 unless given; 0 picks any free port.
Settings > Device > Developer > Service (serviceEnabled)On at every start. Takes effect at the next start.
--headlessNo screen at all, so the service is the only way in.
An installed web frontend chosen as the screenOn, to serve that frontend.
--profile in a Debug buildOn, with the dev actions added.

It listens on this device only (127.0.0.1). --service-bind ADDRESS opens it to the network (0.0.0.0 for every interface); clients from the network must then pair. A bad port or address leaves the service off with a warning in the log. --command-port PORT is an older way to give the port.

Talking to it

Connect to the port over TCP and send one JSON object per line; each gets one line back. A request names an op. An optional id comes back in the reply, so a client can send several requests without waiting. 

{"op": "hello", "id": 1}
{"ok": true, "id": 1, "result": {"protocolVersion": 3, "app": {"version": "0.9.6", "build": "debug", "headless": false}, "objects": ["settingsManager", ...], "auth": "trusted", "scopes": ["full"]}}

{"op": "get", "object": "volumeController", "property": "percent"}
{"ok": true, "result": 40}

{"op": "call", "object": "volumeController", "method": "applyVolume", "args": [55]}
{"ok": true, "result": null}
OpWhat it does
helloThe protocol version, the app's version, and the names of the objects.
describe {object?}The properties, methods, signals and enums of one object, or of all of them.
get {object, property}A property's value. On paramStore the property is a reading's id; with none given, every reading that has a value.
set {object, property, value}Writes a writable property. Most state is read-only and changes through a method, which keeps the rules inside the manager.
call {object, method, args?, timeoutMs?}Calls a method and returns what it returns.
subscribe {object, properties?, signals?, throttleMs?}Starts events. unsubscribe {sub} ends them.
rows {object, property, from?, count?}The rows of a property that holds a list model.
stream {object, name}Starts a video stream. unstream {stream} ends it.
pair, unpair, mediaTicketSee Pairing.

A failure is {"ok": false, "error": "..."}, for example Unknown op: ... or Unknown object: .... Some carry a code a program can test: unauthorised (pair first) and rateLimited (slow down; see Many Clients).

What an op can reach is exactly what describe lists:

  • call runs public slots and invokable methods, never a signal and never anything Qt's own base classes add.
  • get, set and subscribe see the object's own properties and signals only.
  • They run on the main thread, like a call from QML. A slow method holds the screen for as long as it would from QML; the client waits up to timeoutMs (30 seconds by default).
  • Enum values travel as their names ("Connected"). A parameter that is an enum accepts the name or the number.

Events

After subscribe, the reply {sub} comes first and then events arrive on the same connection, mixed with replies to later requests. A reply has ok; an event has event.

EventWhen
propertyThe current value at once, then every time it changes.
signalA signal fired; args has its arguments.
paramsOn paramStore: the readings that changed, as one {id: value} map, starting with what it holds. properties picks the ids; none means all.
modelA list model changed: reset, insert, update or remove, to replay in order.
droppedThe client stopped reading and more than 1000 events queued up. The oldest were thrown away.
streamConfig, streamDroppedA video stream changed format, or the client fell behind and resumes at the next keyframe.

throttleMs limits how often events arrive: at most one per name per interval, the latest value winning. Use it for anything that feeds a display. Each event carries t, milliseconds on a clock that only counts up: good for ordering and intervals, not the time of day.

A client that disappears leaves nothing behind. Its subscriptions end with the connection. So does what it asked the car and the sensors to do: a client that called obdManager.setParameterDemand or setBackgroundDemand, berryIMU.setDemand or audioAnalyzer.setDemand has those requests taken back when its connection closes, however it closed.

Video. Two streams exist: phoneMirrorManager.video, the phone's H.264 as it arrives, and androidAutoManager.frames, JPEG pictures at up to 15 a second. Nothing is copied while nobody watches. The record layout is in docs/api/README.md, "Streams".

From a browser

The same port speaks WebSocket (ws://127.0.0.1:9876/): one JSON message per text frame, the same content as a line. It also answers plain GET requests:

AddressWhat it serves
/The reference client, a page that shows and drives everything (sdk/web/index.html), or your own frontend (below).
/dashboardsThe browser dashboard editor. See Gauges & Dashboards.
/artThe cover of what is playing. /art?song=<file name> is a library song's cover, /art?queue=<id> a phone queue item's.
/export/trip, /export/dashboard, /export/logsWhat the app itself last exported, as a download. /export/trip?format=json is the trip's JSON file. /export/logs lists the files of the last log export and ?file=<name> fetches one.

None of these routes takes a path from the request. Each serves only a file the app chose itself, so a request can never be used to read some other file on the device.

A web page is a risk a script is not: any website open in a browser on the same network could try to talk to the car. Four rules stop that.

  • The Origin rule. A browser may connect only from the service's own page: the page's address and the address it connects to must be the same, and that address must be an IP address or localhost. A name is refused, because a website can point a name it owns at the car. So open the page by IP address, not by a .local name. Pages opened from a file are refused. Programs that are not browsers send no Origin and are not affected.
  • Only GET. Every other method gets a 405. A connection is treated as the line protocol only if its first character is {, so a form posted by another site can never be read as a command.
  • No loading from other sites. A picture or script tag on another site that points at /art or /export gets a 403.
  • Refusals are explained. A refused request gets a 403 with the reason.

Serving your own web frontend

--web-root DIR (or the serviceWebRoot setting, edited in the settings file; the flag wins) serves a folder at / in place of the reference client. Your page then comes from the service itself and passes the Origin rule. It does not turn the service on by itself.

  • The folder must hold an index.html. Otherwise it is not used, the log says so, and the reference client is served. This keeps / or a home folder from being published by mistake.
  • An address with no file extension that matches nothing gets index.html, so single-page apps can use their own routes. A missing file with an extension is a 404.
  • Never served: anything reached through .., any file or folder whose name starts with a dot (.git, .env), anything a symbolic link leads to outside the folder, files over 64 MB.
  • The page may run its own scripts but no inline script, and may open sockets only to this service.

Pairing

Programs on the device itself are trusted. Anything coming from the network must pair first, the way a phone pairs with a car:

  1. On the head unit, open Settings > Device > Developer > Service and tap Show a code. A 6-digit code appears, good for 2 minutes and one use. From a terminal on the device, octave --pair-code prints one.
  2. The client sends pair {code, name} and gets a token back.
  3. From then on it sends hello {token} when it connects.

Until it has done so, every op but hello and pair is answered unauthorised, and hello tells it only the protocol version and that it must pair. The paired devices are listed on the same Settings card, each with Revoke, which also closes that device's connections. OCTAVE stores a hash of each token, never the token.

Guessing is limited: one attempt a second from an address, and ten wrong codes lock that address out until OCTAVE restarts. A browser cannot put a token in a picture's address, so mediaTicket gives a paired client a short-lived ticket to use as /art?ticket=.... A paired device also holds permission scopes (read, media, vehicle and so on) that decide which methods it may call; they are listed in docs/api/README.md, "Permissions".

Trusting programs on the device is the setting serviceLoopbackOpen (on by default; edited in the settings file).

Versions

hello reports protocolVersion. It goes up only when something a client relies on is removed, renamed or changes meaning. Additions do not change it, and a client should ignore fields it does not know. The rules for changing the API are in docs/api/README.md, "Versioning".

Many Clients: Limits

The car and the screen come first. No client, however badly written, should slow the gauges or the readings from the car. Measurements showed that clients which only listen are cheap, and that the cost is in requests and new connections. So the limits are on those:

LimitValueWhat happens past it
Connections at once64 in all, 8 from one network addressRefused at once. 8 of the 64 are kept for programs on this device, so a flood from the network cannot lock out local tools.
New connections from one network address20 a second, 100 in a burstRefused. (From this device: 100 a second, 400 in a burst.)
Requests on one connection200 a second, 400 in a burst{"ok": false, "code": "rateLimited", "retryAfterMs": N}. Wait that long. A client that keeps flooding is disconnected.
A connection that sends nothing10 seconds after connecting; 60 seconds for one that has not pairedClosed.
One message1 MBThe connection is closed.
A client that does not read4 MB waiting to be sentFurther events queue (1000 at most, the oldest dropped, with a dropped event). Still not reading after 15 seconds: closed.

The values are CommandServer::Limits in src/service/commandserver.h. The client's side of them is in docs/api/README.md, "Limits per connection".

Measuring it. tools/stream/service_load.py starts one OCTAVE with the simulated car on a config of its own, runs a set of abusive clients against it, and measures what everyone else loses: how often the car is polled, how long a request takes to get through the main thread, CPU and memory.

python3 tools/stream/service_load.py build/octave 0 WORKDIR --check

--check is a short run that fails unless no subscriber lost events, the flooding client was limited, and the poll rate stayed within 20 % of idle. It runs with the tests as service_load_check.

Why It Is Built This Way

  • Everything goes to files. The head unit runs unattended in a car. After a crash or a freeze, the only thing its owner can do is export the logs later, so everything that matters must already be in them.
  • The crash handler writes to its own file descriptor. Inside a signal almost nothing is safe to call. A descriptor opened at startup and raw writes work even when the rest of the process is broken. The handler then hands the crash back to the system, so its own crash report is still made.
  • Signals quit through the event loop. Quitting from inside a signal handler is not safe. Writing one byte to a socket is, and the event loop does the rest in the same cleanup a closed window gets.
  • The watchdog aborts a long freeze. A frozen screen in a car can only be cleared by pulling the power. An abort is logged, leaves a stack dump, and the launcher brings the app back in seconds.
  • The watchdog stops early in the cleanup. Otherwise its thread can ping an object that has already been destroyed and log an error about a shutdown that was fine.
  • One object owns volume. Every output must use the same curve, or they drift apart when the slider moves. The controller emits a signal and holds no output, so it can be built before the outputs exist.
  • The clock reports changes, not ticks. With seconds hidden the text changes once a minute. Emitting it every second made every binding that shows the time work 60 times for the same text.
  • A socket, not a test harness inside the app. Line-by-line JSON on a local port can be driven from any language. The app takes its own screenshots and injects its own input, so the same scripts work on Wayland, X11 and with no display.
  • Off by default, local by default. A program that can drive the car's screen and read its data is opened by the owner, not found by accident.
