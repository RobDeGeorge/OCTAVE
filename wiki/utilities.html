Clock

src/managers/clock.{h,cpp} / backend/clock.py — QML name: clock (both backends)

A QTimer-based clock that formats the current time once a second and emits it as a string. It reads three settings from SettingsManager on every tick — showClock, clockFormat24Hour and clockShowSeconds — so a settings change takes effect within a second without any signal wiring. Since commit 7777777 it emits timeChanged only when the text actually changed: without seconds the string changes once a minute, so the QML bindings that show the clock re-evaluate 60× less often, and a hidden clock emits the empty string exactly once instead of forever.

Emit-on-change (both backends)

void Clock::update_time()
{
    QString text;
    if (m_settingsManager->showClock()) {
        // ... build "HH:mm[:ss]" or "hh:mm[:ss] AM/PM" ...
    }
    // Without seconds the text changes once a minute; re-evaluating every
    // binding that shows the clock 60 times for the same string is waste.
    if (text == m_lastText)
        return;
    m_lastText = text;
    emit timeChanged(text);
}
def _emit_if_changed(self, text):
    if text == self._last_text:
        return
    self._last_text = text
    self.timeChanged.emit(text)

QML consumers

  • frontend/BottomBar.qml — one Connections { target: clock } at bar level writes a shared clockTimeText property that both the horizontal and the vertical layout bind to, so the layout loaded on an orientation switch shows the current time at once instead of waiting for the next emit
  • frontend/ClockMenu.qml — same signal drives the digital readout, the date line and the analog hands (time.split(":") for hours / minutes / seconds; a missing seconds field, i.e. clockShowSeconds off, counts as 0)

Neither backend logs from the Clock (the octave.clock entry in the Python logger name map is unused).

Logging

backend/logging_config.py (Python) · src/util/logger.{h,cpp} (C++, commit 053f587)

Both backends write rotating log files into <app data dir>/logs/, where the app data dir is the same one that holds settingsConfigure.json (Windows %APPDATA%\OCTAVE, macOS ~/Library/Application Support/OCTAVE, Linux $XDG_CONFIG_HOME/OCTAVE or ~/.config/OCTAVE). The two backends use different file names so that a machine running both never interleaves them: Python writes octave*.log, C++ writes octave-cpp*.log. The sizes and backup counts are the same.

The --debug flag

  • Python: parsed by argparse in main.py (parse_known_args, so unknown Qt flags pass through) and handed to setup_logging(debug=args.debug) before any other backend import. It sets the octave root logger and the console handler to DEBUG and opens the debug file.
  • C++: main() scans argv for the literal --debug with strcmp before the QGuiApplication exists and calls OctaveLog::install(debugLogging). With debug the category filter is *.debug=true\nqt.*.debug=false (OCTAVE categories on, Qt’s own off) and the debug file is opened; without it the rule is *.debug=false, so qCDebug calls are filtered at the source and cost nothing.

Python: setup_logging(debug=False, console=True, file=True)

Called once at startup; a module-level _initialized flag makes later calls no-ops. It configures the octave logger (handlers cleared first) with:

  • a StreamHandler on stdout using the compact console format;
  • three RotatingFileHandlers (main, error, and — with debug — debug) using the detailed file format, encoding='utf-8';
  • the python-obd logger (obd): level matched to ours, propagate = False, and given the same handler objects, so an ELM327 session’s write:/read: transcript lands in octave-debug.log and its errors in octave-error.log;
  • the crash handlers (below) when file is true.

_get_log_dir() keeps its own copy of the platform-path logic rather than importing get_app_data_dir() from backend/settings_manager.py — the settings manager itself imports get_logger from this module, so the reverse import would be circular. The two functions compute the same directory.

C++: OctaveLog

namespace OctaveLog {
void install(bool debug);   // message handler + crash handlers; call before QGuiApplication
QString logDir();          // <app data dir>/logs, created on install
void flush();              // flush all three files: aboutToQuit (main.cpp) and after a QtFatalMsg
}

install() creates the log directory via SettingsManager::getAppDataDir(), opens the files in append mode, sets the category filter rules, installs a qInstallMessageHandler and then the crash handlers. The handler formats every qDebug / qInfo / qWarning / qCritical / qFatal and every qC* category call — and, because QML console.* goes through the same Qt message system, every QML log line too — as:

2026-09-10 12:00:00.123 | INFO    | octave.media | mediamanager.cpp:123 | message

Levels are named DEBUG, INFO, WARNING, ERROR (for QtCriticalMsg) and FATAL; uncategorised messages show the category default; the file column is the basename only, or - when Qt supplies no location. On desktop the line is echoed to stderr first (deliberately not chained to Qt’s default handler, which would print it a second time); on Android and iOS, where stderr goes nowhere, the message is handed to the previous (Qt default) handler instead so it still reaches logcat / os_log. It is then written under a QMutex to the debug file (if enabled), to the main file (unless it is a debug message), and to the error file (warning and above). Each write is flushed immediately. flush() has two callers: the aboutToQuit handler in src/main.cpp calls it last, after the settings and metadata flushes, so everything the cleanup logged reaches disk; and the message handler calls it after a QtFatalMsg, right before Qt aborts. It is never called from the crash (signal) handlers, which must stay Qt-free. Rotation happens before a write that would push the file past maxBytes, by the same rename chain as Python’s RotatingFileHandler (.3 deleted, .2→.3, .1→.2, current→.1).

Crash handlers & signal shutdown

Commit 053f587 (crash handlers, both backends) and 3810e03 (C++ SIGTERM/SIGINT cleanup). The rule from src/util/logger.h: a crash in the vehicle must leave a trace in the error log.

Python: logging_config._install_crash_handlers()

Called at the end of setup_logging() whenever file logging is on. Three hooks, all pointed at octave-error.log:

  • sys.excepthook — logs CRITICAL "Unhandled exception on the main thread" with the traceback, then chains to sys.__excepthook__. KeyboardInterrupt is passed straight through without logging.
  • threading.excepthook — the same for worker threads (OBD, IMU, gesture, phone mirror …), naming the thread.
  • faulthandler.enable(file=fh, all_threads=True) — on a native fault (SIGSEGV, SIGABRT, SIGFPE, SIGBUS, SIGILL) the interpreter dumps every thread’s Python stack to a descriptor opened on octave-error.log in append mode and kept open for the process lifetime. A failure to open it only logs a warning.

C++: signal / exception handlers in logger.cpp

  • Unix: installCrashHandlers() opens octave-cpp-error.log a second time with raw open(O_WRONLY|O_APPEND|O_CREAT) and installs crashHandler for SIGSEGV, SIGABRT, SIGFPE, SIGILL and SIGBUS. The handler uses only write() and backtrace_symbols_fd() (no Qt, no heap — not even OctaveLog::flush(), which takes a QMutex; the log files need no flush there because RotatingFile::write() flushes every line as it lands): it writes ==== FATAL SIGSEGV - backtrace (addresses; symbolise with addr2line against this build) ====, up to 64 frames, and ==== end ==== to the error log and a shorter block to stderr, then restores SIG_DFL and re-raises so the OS still produces a core dump / tombstone. Backtraces exist only where execinfo.h is available (glibc or macOS); elsewhere — Android’s bionic libc — the block reads (no backtrace support on this platform).
  • Windows: SetUnhandledExceptionFilter(crashFilter) writes ==== FATAL exception 0x<code> at <address> ==== plus up to 62 CaptureStackBackTrace frames via _write, then returns EXCEPTION_CONTINUE_SEARCH.
  • qFatal is not a signal: it goes through the message handler as FATAL, after which the handler calls OctaveLog::flush(), before Qt aborts (SIGABRT → crashHandler appends the backtrace), so assertion text is on disk before the SIGABRT block.

SIGTERM / SIGINT run the normal cleanup

Launcher scripts, systemd and Ctrl-C all deliver a signal; the default action would kill the process without running aboutToQuit, orphaning child processes (scrcpy, ffmpeg, the DHU) and leaking the phone-mirror adb forward. Both mains therefore turn the signal into app.quit():

  • C++ (src/main.cpp, #if !defined(Q_OS_WIN) && !defined(Q_OS_MOBILE)): the self-pipe trick. A socketpair() is created; the std::signal handler only writes one byte into it, and a QSocketNotifier on the other end reads the byte on the event loop, logs Signal received, shutting down and calls QCoreApplication::quit(). Nothing Qt-side runs in signal context.
  • Python (main.py): signal.signal(SIGTERM|SIGINT, lambda *_: app.quit()). CPython only services signal handlers while running bytecode, and inside app.exec() it is not, so a 500 ms no-op QTimer (_signal_pump) gives the interpreter a chance to see the signal.

The aboutToQuit cleanup itself (same order of concerns in both backends): stop the UI watchdog first (commit 95dfb49 — otherwise its worker could ping a QObject that Qt had already destroyed, which the new threading excepthook then logged as CRITICAL), save playback state and flush the metadata store, clean up Spotify / Android Auto / phone mirror / ESP32 / IMU / gesture / network / downloads, close OBD (C++), and flush the coalesced settings write so the last slider change reaches disk (flushPendingSave() in both backends; Python keeps flush_pending_save() as an alias). C++ ends with OctaveLog::flush() so the cleanup’s own log lines are on disk before the process exits. In Python, setup_perf_profiling() additionally connects cmd_server.stop() and perf_monitor.stop() to aboutToQuit when --profile is on.

UI watchdog

src/util/uiwatchdog.{h,cpp} / backend/ui_watchdog.py — class UiWatchdog, commit f157b97. Not registered as a QML context property in either backend; it is started right after SettingsManager in both mains and stopped from the quit cleanup.

A hung event loop used to vanish without a trace — the screen froze and the log simply stopped. The watchdog is a worker thread that posts a “ping” to the GUI thread every pingMs (2000) and records when the GUI thread answers it. If the answer is older than stallMs (5000) it logs once UI thread blocked for N s and counting as a WARNING on octave.ui_watchdog, and when the GUI thread catches up (silence back under one ping interval) it logs UI thread responsive again after N s. In C++ the warning also lands in octave-cpp-error.log (that file is WARNING+); in Python it appears in octave.log only, because octave-error.log is ERROR+.

VolumeController

src/managers/volumecontroller.{h,cpp} / backend/volume_utils.py — QML name: volumeController (both backends). Introduced in commit d2b047b (“volume curve de-duplication”).

OCTAVE maps the UI volume percent (0–100) to a linear audio gain (0.0–1.0) through a quadratic curve, (percent / 100)2, which gives a more natural perceptual response at low volumes than a straight line. Before this module existed the curve was hard-coded in about nine places across main.py and QML, so any change had to be made in lockstep everywhere. VolumeController owns the math and is the single entry point for routing a percent to every output; changing the curve means editing to_linear() / toLinearStatic() in one place per backend.

Dispatch: who gets what

The two backends deliberately differ in how they fan out, but the contract is the same: settings store the percent, local media and the phone mirror take the linear gain, Spotify and the ESP32 LED take the raw percent, and the Spotify leg is debounced 300 ms (trailing) so a slider drag does not fire a Web API call per pixel and trip its 429 rate limit.

# Python — backend/volume_utils.py
@Slot(int)
def applyVolume(self, percent: int) -> None:
    percent = max(0, min(100, int(percent)))
    linear = to_linear(percent)

    if self._settings is not None:
        self._settings.setCurrentVolume(percent)
    if self._media is not None:
        self._media.setVolume(linear)
    if self._spotify is not None:
        self._pending_spotify_volume = percent
        self._spotify_debounce.start()   # 300 ms single-shot QTimer → set_volume() if connected
    if self._phone_mirror is not None:
        self._phone_mirror.setVolume(linear)
    if self._esp32 is not None:
        self._esp32.send_volume_update(percent)
// C++ — src/main.cpp wiring (the controller itself only emits)
QObject::connect(&volumeController, &VolumeController::volumeApplied,
                 [&mediaManager, &phoneMirrorManager, &esp32VolumeManager](int percent, float linear) {
    mediaManager.setVolume(linear);
    pendingSpotifyVolume = percent;
    spotifyVolumeDebounce.start();   // 300 ms single-shot → spotifyManager.set_volume() if connected
    phoneMirrorManager.setVolume(linear);
#ifndef Q_OS_MOBILE
    esp32VolumeManager.send_volume_update(percent);   // the ESP32 manager rate-limits itself (50 ms)
#endif
});
volumeController.applyVolume(settingsManager.currentVolume());   // startup volume

Both wirings therefore reach the same four outputs; the only structural difference is that Python holds the manager references in the controller while C++ keeps the controller decoupled and does the fan-out in main.cpp (the ESP32 leg is compiled out on mobile, where the manager is a stub).

Callers

  • frontend/BottomBar.qml (four slider / button sites) and frontend/MediaRoom.qml call volumeController.applyVolume(Math.round(value))
  • Gesture sensor volume_up / volume_down: applyVolume(currentVolume ± gestureVolumeStep)
  • ESP32 knob volumeChangeRequested(delta): fractional deltas are accumulated and applied once they reach a whole percent
  • Both mains call applyVolume(settingsManager.currentVolume) once after every manager is constructed, so the saved volume reaches every output at startup
Rule

Never call an individual manager’s setVolume from QML or a hardware handler, and never re-derive the curve. Everything goes through volumeController.applyVolume(percent).

Lazy imports (Python)

backend/lazy_import.py — Python-only; introduced in commit ee5a23e (startup optimisations).

Several optional libraries are expensive to import — obd pulls in pint, spotipy pulls in redis, numpy and av load large native extensions — and none of them are needed until the user connects an adapter, logs in, or plays a track. Importing them eagerly cost about a second before the first frame on the Orange Pi. The module offers two helpers:

def available(name: str) -> bool:
    """True when the top-level package is installed (no import performed)."""
    try:
        return importlib.util.find_spec(name) is not None
    except (ImportError, ValueError):
        return False


class LazyModule:
    """Import ``name`` on first attribute access and forward everything to it."""
    def __getattr__(self, attr):
        return getattr(self._lazy_load(), attr)


def lazy_module(name: str):
    return LazyModule(name)

Because the proxy forwards attribute access, module code keeps its natural spelling (obd.commands.RPM); the real import happens on the first such access. available() answers “is it installed?” via find_spec without importing, so the *_AVAILABLE flags stay cheap.

Performance monitor & perf tooling (Python)

backend/perf_monitor.py, backend/perf_patches.py (both gitignored), dev/perf/, dev/mcp_server.py, dev/mcp_benchmark.py, .mcp.json. Python-only: there is no C++ perf monitor.

Everything here is switched on by one flag: python main.py --profile. main.py’s setup_perf_profiling() (called after the QML is loaded, also from dev/main_dev.py) creates a PerfMonitor writing dev/perf/logs/perf_<YYYYmmdd_HHMMSS>.csv and .log, registers it as the QML context property perfMonitor (no shipped QML binds to it; it is there for a HUD), starts it, starts the command server, applies perf_patches if the file exists, and connects both stop()s to aboutToQuit. Each of the three gitignored modules is imported inside its own try: a missing perf_monitor.py logs a warning and skips the whole block (monitor and server), a missing command_server.py skips only the server, a missing perf_patches.py only the instrumentation — so --profile on a fresh clone runs the app normally instead of crashing with ImportError. On quit the detailed report is printed to the terminal and appended to the .log.

PerfMonitor internals

ComponentWhat it measures
_RingBufferFixed-size deque with mean(), max_val() and linear-interpolated percentile(p). Capacities: 600 for loop latency (~10 s at 60 Hz), 300 for GIL jitter, 200 per slot timing.
Event-loop probeA QTimer with interval 0 and PreciseTimer; the delta between consecutive firings is one sample. Samples ≥ 500 ms are discarded (the first one has no reference point). A high delta means the loop was blocked — UI stutter.
_GILProbeA daemon thread that waits 10 ms on an Event and records how late it woke; the excess approximates time other threads held the GIL.
psutilProcess CPU % and RSS MB, if installed (otherwise those columns are 0 and a hint is printed).
Slot timingsModule-level _slot_timings: dict[str, _RingBuffer] fed by the @timed_slot decorator (key fn.__qualname__), by PerfMonitor.begin() / end(start, label), and by perf_patches.

Reporting cycle (every 1 s)

  1. Loop latency avg / p50 / p95 / p99 / max from the ring buffer; GIL avg / p99; threading.active_count(); CPU and memory.
  2. Terminal line, colour-coded by average loop latency: green < 5 ms, yellow < 16 ms, red otherwise. Slots whose p95 exceeds 2 ms are listed every fifth report.
  3. Plain-text line in the perf .log tagged OK / WARN / STUTTER with the same thresholds, plus SLOW lines.
  4. CSV row: timestamp, loop_avg_ms, loop_p50_ms, loop_p95_ms, loop_p99_ms, loop_max_ms, gil_avg_ms, gil_p99_ms, cpu_pct, mem_mb, threads.
  5. Buffers cleared, metricsUpdated emitted.

QML properties (all notify on metricsUpdated)

loopLatencyMs, loopP99Ms, gilJitterMs (float), cpuPercent, memMb (float), threadCount (int), summaryText (str, a one-line HUD string). Slot: getDetailedReport() → str, listing loop / GIL / CPU and every slot with p95 > 1 ms sorted by p95.

Command server (Python)

backend/command_server.py (gitignored) — Python-only, started by setup_perf_profiling() when --profile is passed and the file exists (otherwise a warning is logged and the server is skipped). Listens on 127.0.0.1:9876 (DEFAULT_PORT). Since commit b1db87c the instance is exposed as the module attribute main.cmd_server (None without --profile) so dev tooling can extend it.

Protocol

One JSON object per line in, one per line out. args is optional.

{"action": "navigate", "args": {"page": "obd"}}
{"ok": true, "result": {"navigated_to": "obd"}}

{"action": "bogus"}
{"ok": false, "error": "Unknown action: bogus"}

Invalid JSON gets {"ok": false, "error": "Invalid JSON: …"}; any exception raised by a handler is logged with its traceback and returned as error. A client may keep the connection open and send many lines.

Architecture

CommandServer (lifecycle wrapper: start / stop / register) │ ├── _ThreadedTCPServer socketserver.ThreadingMixIn + TCPServer, │ │ allow_reuse_address, daemon_threads; serve_forever() │ │ on a daemon thread named "CommandServer" │ ├── _Handler one per client; StreamRequestHandler reading JSON lines │ │ └── server.dispatch(action, args) │ └── _extensions{} action → handler(args), added by register() │ └── NavigationBridge (QObject on the GUI thread) navigation: QMetaObject.invokeMethod(..., Qt.QueuedConnection) screenshots / recording / UI driving: Qt.BlockingQueuedConnection, result read back from the bridge after the call returns

The TCP threads never touch Qt objects directly for anything that must happen on the GUI thread; NavigationBridge slots are invoked with QueuedConnection (fire and forget: navigation, window size, dev chrome) or BlockingQueuedConnection (screenshot, recording, item lookup, clicks) when the reply needs the result. navigate_to calls root.navigateTo(page) directly rather than via Q_ARG(str, …) because the QML function takes an untyped var and a typed invoke would silently match nothing. Extension handlers registered via register() run on the server thread and must marshal to the GUI thread themselves (the dev SimBridge does this with a queued Signal).

Design decisions

Why the volume curve lives in one object

Commit d2b047b replaced ~9 copies of (v/100)**2 spread across main.py, BottomBar.qml and MediaRoom.qml with VolumeController. The module docstring states the risk plainly: every output must use the same curve or they drift out of sync when the user moves the slider. Python takes the manager instances in its constructor; C++ emits volumeApplied instead so the controller can be constructed before the managers it feeds exist (“avoids tight coupling — VolumeController doesn’t need pointers to managers that may not exist yet”, volumecontroller.h).

Why the Clock emits on change

Commit 7777777: with seconds hidden the string changes once a minute, but the old code emitted it every second and every binding that shows the clock re-evaluated 60 times for the same value; a hidden clock emitted "" forever. Comparing against the last emitted text costs one string compare per second and removes the churn. Settings are still re-read on every tick rather than wired to change signals, which keeps the class free of any signal connections.

Why the crash handlers write where they do

The observability overhaul (053f587) exists because the head unit runs unattended in a vehicle: the only thing a user can do after a freeze or crash is export the logs from the About page later. So every trace must end up in the error log file, the one file the Diagnostics export and the tail both read. On the C++ side the code comments spell out the constraint: “a separate descriptor, opened once, so the signal path never touches Qt” and “async-signal-safe as far as practical” — the handler only calls write() and backtrace_symbols_fd() on that raw descriptor. It then restores SIG_DFL and re-raises so the OS still writes its core dump / tombstone; the file log is additive, not a replacement. Python routes to the same file because faulthandler needs a file object, opened in append mode and “kept open for the process lifetime”.

Why the C++ log files have different names

Commit 053f587 places the C++ files “next to the Python ones” in the same logs/ directory. The distinct octave-cpp prefix keeps the two histories apart on a machine that runs both backends against the same config directory, and DiagnosticsManager tails whichever belongs to the running backend. Sizes, backup counts and the line format are the same (“Rotation policy, same as the Python backend”, logger.cpp) so anyone reading them sees one convention.

Why SIGTERM/SIGINT go through the event loop

Commit 3810e03: with the default action, a launcher or systemd stopping the app killed the process outright and the phone-mirror adb forward leaked. Calling QCoreApplication::quit() from inside a signal handler is not safe, so the C++ handler only writes a byte into a socketpair and a QSocketNotifier does the real work on the event loop. Python has the opposite problem — the interpreter cannot see a signal while Qt’s exec() owns the thread — hence the 500 ms no-op timer that returns control to bytecode periodically. Both end in the same aboutToQuit cleanup that a window close triggers.

Why a watchdog, and why it stops first

The header comment states the goal: “so a frozen head unit leaves a trace”. The watchdog (f157b97) is the smallest thing that turns a hang into evidence: one thread, one queued call, one warning per stall with the duration on recovery. The 2 s / 5 s thresholds keep legitimate slow work (a big library scan, dashboard JSON) silent. Commit 95dfb49 moved stop() to the head of the quit cleanup after a Pi run where the worker pinged a QObject Qt had already destroyed and the brand-new threading excepthook reported it as CRITICAL — noise the whole effort exists to remove.

Why lazy imports instead of dropping the dependencies

The Python backend is the tinkering backend and deliberately keeps optional hardware / service libraries. Commit ee5a23e measured about a second of import time on the Orange Pi before the first frame for libraries nobody needs until an adapter is connected or a login happens. A proxy that imports on first attribute access preserves every existing call site (obd.commands.RPM keeps working) and find_spec-based availability keeps the “is it installed?” checks free. The C++ build has no equivalent cost.

Why a TCP command server rather than an in-process test harness

The command server is what lets every external tool — the screenshot sweeper, the dashboard-editor scenario, the perf loops and the MCP servers — drive the real app process from outside without a display server: the app captures itself with grabWindow() and injects input with QCoreApplication.sendEvent, so the same scripts run on Wayland, X11, Xvfb and offscreen (the header of dev/screenshots/auto.py records that the previous xdotool + mss approach broke under Wayland). Newline-delimited JSON over localhost is trivially scriptable from any language and from an MCP tool. It is bound to 127.0.0.1, is only started with --profile, and the file is gitignored, so it is never present in a normal run. The register() extension point (and exposing the instance as main.cmd_server, b1db87c) let dev-only code such as the OBD simulator add actions without touching the shipped module.

Why perf instrumentation is monkey-patched

perf_patches.py’s docstring: “This avoids polluting production code with timing decorators.” Hot paths are wrapped on the live instances only when --profile is on, so the shipped managers carry no profiling code and the list of instrumented methods can change without touching them.
