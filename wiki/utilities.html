Clock

backend/clock.py — QML name: clock

A QTimer-based clock that formats the current time once a second and emits it as a string. It reads three settings from SettingsManager on every tick — showClock, clockFormat24Hour and clockShowSeconds — so a settings change takes effect within a second without any signal wiring. It emits timeChanged only when the text actually changed: without seconds the string changes once a minute, so the QML bindings that show the clock re-evaluate 60× less often. Hiding the clock emits the empty string once; because the last-emitted text starts as None, a clock that starts hidden also emits "" on its first tick.

def _emit_if_changed(self, text):
    # Without seconds the text changes once a minute; re-evaluating every
    # binding that shows the clock 60 times for the same string is waste.
    if text == self._last_text:
        return
    self._last_text = text
    self.timeChanged.emit(text)

QML consumers

  • frontend/BottomBar.qml — one Connections { target: clock } at bar level writes a shared clockTimeText property that both the horizontal and the vertical layout bind to, so the layout loaded on an orientation switch shows the current time at once instead of waiting for the next emit
  • frontend/ClockMenu.qml — same signal drives the digital readout, the date line and the analog hands (time.split(":") for hours / minutes / seconds; a missing seconds field, i.e. clockShowSeconds off, counts as 0)

The Clock never logs (the octave.clock entry in the logger name map is unused).

Logging

backend/logging_config.py

Rotating log files go to <app data dir>/logs/, where the app data dir is the one that holds settingsConfigure.json (Windows %APPDATA%\OCTAVE, macOS ~/Library/Application Support/OCTAVE, Linux $XDG_CONFIG_HOME/OCTAVE or ~/.config/OCTAVE).

Worst-case disk use: ~32 MB without --debug, ~62 MB with it (the docstring's figures) — sized for an SD-card head unit that must keep several sessions of history.

The --debug flag

Parsed by argparse in main.py (parse_known_args, so unknown Qt flags pass through) and handed to setup_logging(debug=args.debug) before any other backend import. It sets the octave logger and the console handler to DEBUG and opens the debug file.

setup_logging(debug=False, console=True, file=True)

Called once at startup; a module-level _initialized flag makes later calls no-ops. It configures the octave logger (handlers cleared first) with:

  • a StreamHandler on stdout using the compact console format;
  • three RotatingFileHandlers (main, error, and — with debug — debug) using the detailed file format, encoding='utf-8';
  • the python-obd logger (obd): level matched to ours, propagate = False, and given the same handler objects, so an ELM327 session’s write:/read: transcript lands in octave-debug.log and its errors in octave-error.log;
  • the crash handlers (below) when file is true;
  • a final INFO line Logging initialized (debug=…, log_dir=…).

_get_log_dir() keeps its own copy of the platform-path logic rather than importing get_app_data_dir() from backend/settings_manager.py — the settings manager itself imports get_logger from this module, so the reverse import would be circular. The two functions compute the same directory.

Crash handlers & signal shutdown

The rule from the docstring: a crash must leave a trace in the error log.

logging_config._install_crash_handlers()

Called at the end of setup_logging() whenever file logging is on. Three hooks, all pointed at octave-error.log:

  • sys.excepthook — logs CRITICAL "Unhandled exception on the main thread" with the traceback, then chains to sys.__excepthook__. KeyboardInterrupt is passed straight through without logging.
  • threading.excepthook — the same for worker threads (OBD, IMU, gesture, phone mirror …): Unhandled exception in thread '<name>'.
  • faulthandler.enable(file=fh, all_threads=True) — on a native fault (SIGSEGV, SIGABRT, SIGFPE, SIGBUS, SIGILL) the interpreter dumps every thread’s Python stack to a file opened on octave-error.log in append mode and kept open for the process lifetime. A failure to open it only logs a warning.

SIGTERM / SIGINT run the normal cleanup

Launcher scripts, systemd and Ctrl-C all deliver a signal; the default action would kill the process without running aboutToQuit, leaving child processes (adb, the DHU) and the phone-mirror adb forward behind. main.py therefore installs signal.signal(SIGTERM|SIGINT, lambda *_: app.quit()). CPython only services signal handlers while running bytecode, and inside app.exec() it is not, so a 500 ms no-op QTimer (_signal_pump) gives the interpreter a chance to see the signal.

The aboutToQuit cleanup (cleanup_on_quit()) stops the UI watchdog first, saves playback with _save_playback_state_now(), flushes the metadata store and settings, cleans up Android Auto, phone mirror, OBD (close()), ESP32, IMU, gesture, network and downloads, and flushes settings again. Each step catches exceptions so later cleanup still runs. flush_pending_save() is an alias of flushPendingSave(). With --profile, separate quit handlers also stop the command server and performance monitor.

UI watchdog

backend/ui_watchdog.py — class UiWatchdog. Not registered as a QML context property; it is started right after SettingsManager in main.py and stopped first in the quit cleanup.

A hung event loop used to vanish without a trace — the screen froze and the log simply stopped. The watchdog is a daemon thread that posts a “ping” to the GUI thread every ping_s (2.0) and records when the GUI thread answers it. If the answer is older than stall_s (5.0) it logs once UI thread blocked for N s and counting as a WARNING on octave.ui_watchdog, and when the GUI thread catches up (silence back to at most one ping interval) it logs UI thread responsive again after N s. Both are WARNINGs, so they appear in octave.log but not in octave-error.log (ERROR+). Time is measured with time.monotonic(), so a wall-clock jump (NTP correcting a board with no RTC) is not reported as a stall.

worker thread ("ui-watchdog") GUI thread │ │ │─ sleep ping_s (2 s) ─┐ │ │◄─────────────────────┘ │ │── _ping.emit() (queued) ───────────────────────►│ _pong(): last_pong = monotonic() │ │ (runs when the event loop gets to it) │ silent = monotonic() - last_pong │ │ silent > stall_s (5 s) → WARNING "blocked for N s and counting" (once) │ silent ≤ ping_s after a stall → WARNING "responsive again after N s"
MemberBehaviour
UiWatchdog(parent=None, ping_s=2.0, stall_s=5.0)Connects the private _ping Signal to _pong() with Qt.ConnectionType.QueuedConnection
start()Starts a daemon threading.Thread named ui-watchdog (no-op if already running)
stop()Clears the flag and joins for ping_s + 0.5 s (unless called from the worker itself)
teardown safety_ping.emit() inside try/except RuntimeError, so a QObject torn down without stop() ends the loop quietly

A warning means the GUI failed to answer within the threshold; it does not identify the cause. Expected long operations (a large first library scan, which runs on the GUI thread) can also trigger it, so read the surrounding log lines to diagnose a stall.

VolumeController

backend/volume_utils.py — QML name: volumeController

OCTAVE maps the UI volume percent (0–100) to a linear audio gain (0.0–1.0) through a quadratic curve, (percent / 100)2, which gives a more natural perceptual response at low volumes than a straight line. Before this module existed the curve was hard-coded in about nine places across main.py and QML, so any change had to be made in lockstep everywhere. VolumeController owns the math and is the single entry point for routing a percent to every output; changing the curve means editing to_linear().

Dispatch: who gets what

Settings store the percent, local media and the phone mirror take the linear gain, and the ESP32 LED takes the raw percent:

# backend/volume_utils.py
@Slot(int)
def applyVolume(self, percent: int) -> None:
    percent = max(0, min(100, int(percent)))
    linear = to_linear(percent)

    if self._settings is not None:
        self._settings.setCurrentVolume(percent)
    if self._media is not None:
        self._media.setVolume(linear)
    if self._phone_mirror is not None:
        self._phone_mirror.setVolume(linear)
    if self._esp32 is not None:
        self._esp32.send_volume_update(percent)

The ESP32 manager rate-limits what it sends to the knob with a 50 ms debounce timer.

Callers

  • frontend/BottomBar.qml and frontend/MediaRoom.qml call volumeController.applyVolume(Math.round(value)) (BottomBar also passes an already-rounded currentValue at two sites)
  • Gesture sensor volume_up / volume_down: applyVolume(currentVolume ± gestureVolumeStep)
  • ESP32 knob volumeChangeRequested(delta): fractional deltas are accumulated in main.py and applied once they reach a whole percent
  • main.py calls applyVolume(settings_manager.currentVolume) once, right after constructing the controller, so the saved volume reaches every output at startup
Rule

Never call an individual manager’s setVolume from QML or a hardware handler, and never re-derive the curve. Everything goes through volumeController.applyVolume(percent). tests/test_smoke.py::test_volume_curve_math pins the numbers.

Lazy imports

backend/lazy_import.py

Several optional libraries are expensive to import — obd pulls in pint, numpy and av load large native extensions — and none of them are needed until the user connects an adapter or plays a track. Importing them eagerly cost about a second before the first frame on the Orange Pi (module docstring). The module offers two helpers:

def available(name: str) -> bool:
    """True when the top-level package is installed (no import performed)."""
    try:
        return importlib.util.find_spec(name) is not None
    except (ImportError, ValueError):
        return False


class LazyModule:
    """Import ``name`` on first attribute access and forward everything to it."""
    def __getattr__(self, attr):
        return getattr(self._lazy_load(), attr)


def lazy_module(name: str):
    return LazyModule(name)

Because the proxy forwards attribute access, module code keeps its natural spelling (obd.commands.RPM); the real import happens on the first such access. Its repr shows loaded / not loaded. available() answers “is it installed?” via find_spec without importing, so the *_AVAILABLE flags stay cheap.

Main-thread dispatch (qt_threading)

backend/qt_threading.py — run_on_main(fn, delay_ms=0)

The module docstring states the problem: QTimer.singleShot called from a plain threading.Thread never fires, because the timer belongs to the calling thread, which has no Qt event loop. Worker threads (the OBD monitor and scans, the sensor read loops, the ESP32 serial reader) use run_on_main() instead. It emits a private _invoke(object, int) Signal on a _MainThreadInvoker QObject connected with Qt.QueuedConnection; the slot runs on the main thread and either calls fn or, with a delay, starts QTimer.singleShot(delay_ms, fn) there. Called from the main thread it behaves like QTimer.singleShot(delay_ms, fn).

The invoker is created at import time when the module is first imported on the main thread (managers import it at startup). Only a first call from a worker thread would have to create it there and moveToThread() it to the application thread; the comment records that this path asks Qt for a QThread wrapper off the main thread, which PySide6 6.11.2 can later use to delete the main QThread and segfault at exit. Used by obd_manager, berryimu_manager, gesture_manager and esp32_volume_manager; tested by tests/test_qt_threading.py.

Atomic file writes (atomic_io)

backend/atomic_io.py — atomic_write_bytes(path, data), atomic_write_text(path, text, encoding="utf-8")

"The head unit loses power with the ignition, so any file rewritten while driving must be replaced in one step" (module docstring). The helper writes a temp file (.tmp-*.part) in the target's directory, fsyncs it, os.replace()s it over the target and, except on Windows, fsyncs the directory so the rename itself is durable. On any exception the temp file is removed and the exception re-raised. A cut at any point leaves either the old file or the new one. MediaManager uses it for metadata_cache.json and extracted cover files (and deletes stray .tmp- files from its cover cache at startup). SettingsManager has its own equivalent, _atomic_write_text(), which additionally takes a file lock on the temp file and sets its permissions.

AssetStore

backend/asset_store.py — QML name: assetStore

AssetStore(source_dir) is constructed in main.py with <checkout>/frontend/assets. Its one slot, localUrl(relativePath) (@Slot(str, result=QUrl)), returns a file:// URL for the file under that directory; an empty path or one containing .. returns an empty QUrl, and a missing file logs Asset not found: … but still returns the URL. Performance monitor & perf tooling

backend/perf_monitor.py, backend/perf_patches.py, dev/perf/, dev/mcp_server.py, dev/mcp_benchmark.py, .mcp.json — all developer-local (gitignored, not in a fresh clone).

Everything here is switched on by one flag: python main.py --profile (or python -m dev.main_dev --profile). main.py’s setup_perf_profiling(), called after the QML is loaded:

  1. imports PerfMonitor — if perf_monitor.py is missing it logs a warning and returns, skipping everything below;
  2. creates a PerfMonitor writing dev/perf/logs/perf_<YYYYmmdd_HHMMSS>.csv and .log (directory created if needed), registers it as the QML context property perfMonitor (no QML in frontend/ binds to it) and starts it;
  3. starts the command server if command_server.py imports, storing it in the module global cmd_server and connecting its stop() to aboutToQuit;
  4. imports apply_patches — if perf_patches.py is missing it logs a warning and returns;
  5. applies the patches and connects stop_perf_monitor() to aboutToQuit, which stops the monitor, prints the CSV / log paths and prints the detailed report.
Missing perf_patches.py also skips the report
Because step 4 returns before step 5, a checkout that has perf_monitor.py but not perf_patches.py never connects stop_perf_monitor(): the monitor is not stopped on quit and the final report is neither printed nor appended to the .log.

PerfMonitor internals

ComponentWhat it measures
_RingBufferFixed-size deque with mean(), max_val() and percentile(p). Capacities: 600 for loop latency (~10 s at 60 Hz), 300 for GIL jitter, 200 per slot timing.
Event-loop probeA QTimer with interval 0 and PreciseTimer; the delta between consecutive firings is one sample. Samples of 500 ms or more are discarded (this drops the first one, which has no reference point). A high delta means the loop was blocked — UI stutter.
_GILProbeA daemon thread named GILProbe that waits 10 ms on an Event and records how late it woke; the excess approximates time other threads held the GIL.
psutilProcess CPU % and RSS MB, if installed (otherwise those values stay 0 and an install hint is printed).
Slot timingsModule-level _slot_timings: dict[str, _RingBuffer] fed by the @timed_slot decorator (key fn.__qualname__), by PerfMonitor.begin() / end(start, label), and by perf_patches.

Reporting cycle (every 1 s)

  1. Loop latency avg / p50 / p95 / p99 / max from the ring buffer; GIL avg / p99; threading.active_count(); CPU and memory.
  2. Terminal status line, colour-coded by average loop latency: green < 5 ms, yellow < 16 ms, red otherwise. Slots whose p95 exceeds 2 ms are printed every fifth report.
  3. Plain-text line in the perf .log tagged OK / WARN / STUTTER with the same thresholds.
  4. CSV row: timestamp, loop_avg_ms, loop_p50_ms, loop_p95_ms, loop_p99_ms, loop_max_ms, gil_avg_ms, gil_p99_ms, cpu_pct, mem_mb, threads.
  5. metricsUpdated emitted.

QML properties (all notify on metricsUpdated)

loopLatencyMs, loopP99Ms, gilJitterMs, cpuPercent, memMb (float), threadCount (int), summaryText (str, a one-line HUD string). getDetailedReport() → str lists loop / GIL / CPU and every slot with p95 > 1 ms.

backend/perf_patches.py keeps timing decorators out of production code: apply_patches(...) replaces instance attributes on the live managers with a functools.wraps timer that feeds _slot_timings, skipping any method that does not exist. Its list names media._extract_colors, media._kmeans_colors, media._update_position, media.next_track, media.previous_track, audio._analyze_audio (FFT), obd._monitor_connection, esp32._read_serial and settings.save_settings; in this backend MediaManager._extract_colors and ESP32VolumeManager._read_serial do not exist, so those two are skipped. Because the wrapper replaces the attribute on the instance, a method that was already connected as a slot, or already running on a thread, keeps calling the original. The berryimu_manager and gesture_manager arguments are accepted but nothing is wrapped for them.

Command server

backend/command_server.py (developer-local, gitignored) — started by setup_perf_profiling() when --profile is passed and both it and perf_monitor.py are present. Listens on 127.0.0.1:9876 (DEFAULT_PORT); main.py has no option to change the port. The instance is exposed as the module attribute main.cmd_server (None without --profile) so dev tooling can extend it.

Protocol

One JSON object per line in, one per line out. args is optional.

{"action": "navigate", "args": {"page": "obd"}}
{"ok": true, "result": {"navigated_to": "obd"}}

{"action": "bogus"}
{"ok": false, "error": "Unknown action: bogus"}

Invalid JSON gets {"ok": false, "error": "Invalid JSON: …"}; an exception raised by a handler is logged with its traceback and returned as error. A client may keep the connection open and send many lines.

Architecture

CommandServer (lifecycle wrapper: start / stop / register) │ ├── _ThreadedTCPServer socketserver.ThreadingMixIn + TCPServer, │ │ allow_reuse_address, daemon_threads; serve_forever() │ │ on a daemon thread named "CommandServer" │ ├── _Handler one per client; StreamRequestHandler reading JSON lines │ │ └── server.dispatch(action, args) │ └── _extensions{} action → handler(args), added by register() │ └── NavigationBridge (QObject on the GUI thread) navigation: QMetaObject.invokeMethod(..., Qt.QueuedConnection) screenshots / recording / UI driving: Qt.BlockingQueuedConnection, result read back from the bridge after the call returns

The TCP threads never touch Qt objects directly for anything that must happen on the GUI thread; NavigationBridge slots are invoked with QueuedConnection (fire and forget: navigation, window size, dev chrome) or BlockingQueuedConnection (screenshot, recording, item lookup, clicks) when the reply needs the result. navigate_to calls root.navigateTo(page) directly rather than through QMetaObject.invokeMethod with Q_ARG(str, …), because the QML function takes an untyped parameter (registered as QVariant) and a typed invoke would silently match nothing. Extension handlers registered via register() run on the server thread and must marshal to the GUI thread themselves (the dev SimBridge does this with a queued Signal).

Design decisions

Why the volume curve lives in one object

The module docstring states the risk plainly: every output must use the same curve or they will drift out of sync when the user moves the slider, and the curve used to be copied into ~9 call sites across main.py and QML. VolumeController takes the output managers in its constructor so one call reaches all of them.

Why the Clock emits on change

With seconds hidden the string changes once a minute; emitting it every second made every binding that shows the clock re-evaluate 60 times for the same value. Comparing against the last emitted text costs one string compare per second. Settings are still re-read on every tick rather than wired to change signals, which keeps the class free of signal connections.

Why the crash handlers write where they do

The head unit runs unattended in a vehicle: the only thing a user can do after a freeze or crash is export the logs from the Device settings page later. Crash traces therefore go to the error log, which DiagnosticsManager both tails and exports. faulthandler needs a file object, so the error log is opened a second time in append mode and “kept open for the process lifetime”.

Why SIGTERM/SIGINT go through the event loop

"SIGTERM/SIGINT (launcher scripts, systemd, Ctrl-C) must run cleanup_on_quit too, otherwise child processes … are orphaned" (main.py). The interpreter cannot run a Python signal handler while Qt’s exec() owns the thread, hence the 500 ms no-op timer that returns control to bytecode periodically. The handler ends in the same aboutToQuit cleanup that a window close triggers.

Why a watchdog, and why it stops first

The module docstring states the goal: “so a frozen head unit leaves a trace”. The watchdog is the smallest thing that turns a hang into evidence: one thread, one queued signal, one warning per stall with the duration on recovery. It is stopped first in cleanup_on_quit() “before Qt tears the QObject down under the worker thread” (comment in main.py).

Why lazy imports instead of dropping the dependencies

The optional hardware and service libraries stay, but nobody needs them until an adapter is connected or a track plays. A proxy that imports on first attribute access preserves every existing call site (obd.commands.RPM keeps working) and find_spec-based availability keeps the “is it installed?” checks free.

Why a TCP command server rather than an in-process test harness

The command server lets external tools — the screenshot sweeper, the dashboard-editor scenario, the perf loops and the MCP servers — drive the real app process from outside without a display server: the app captures itself with grabWindow() and injects input with QCoreApplication.sendEvent, so the same scripts run on Wayland, X11, Xvfb and offscreen. Newline-delimited JSON over localhost is scriptable from any language and from an MCP tool. It is bound to 127.0.0.1, started only with --profile, and the file is gitignored. The register() extension point (and exposing the instance as main.cmd_server) lets dev-only code such as the OBD simulator add actions without touching the module.

Why perf instrumentation is monkey-patched

perf_patches.py’s docstring: “This avoids polluting production code with timing decorators.” Hot paths are wrapped on the live instances only when --profile is on, so the managers carry no profiling code.
