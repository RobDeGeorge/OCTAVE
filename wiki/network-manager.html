Overview

The NetworkManager has three jobs: report whether the head unit is online (and on which network), tell the user when the main branch on GitHub has moved past the running commit, and -- when OCTAVE runs from a git checkout -- pull that update in place and restart. It is defined in src/managers/networkmanager.{h,cpp} (C++) and backend/network_manager.py (Python) and registered as the QML context property networkManager in src/main.cpp / main.py. Both backends expose the same properties, signals, slots and status strings; where the mechanics differ the sections below say so.

Thread Safety
In the Python backend every blocking operation (subprocess calls, HTTP requests) runs on a ThreadPoolExecutor with a single worker, and results are polled back on the main thread by a 250 ms QTimer so Qt signals are only ever emitted from the GUI thread. The C++ backend has no worker thread: it uses asynchronous QProcess and QNetworkAccessManager whose completion slots already run on the main thread. The only synchronous calls in C++ are the short git queries (runGitSync(): status --porcelain, cat-file, merge-base, rev-list, and the rollback reset --hard) -- the header comment says they run on the GUI thread "deliberately: they gate a destructive action, so their answer must be current at the moment of the click".

The manager targets the GitHub repository WayBetterSolutions/OCTAVE (GITHUB_REPO) and compares the local git HEAD against the tip of the remote main branch.

Background Work Pattern (Python)

Only one background job runs at a time. _submit_work() takes a callable and a result-type tag, submits it to the executor, and starts the result poll timer: 

def _submit_work(self, fn, result_type):
    """Submit blocking work to the thread pool. Only one job at a time."""
    if self._pending_future and not self._pending_future.done():
        return  # Already busy
    self._pending_future = self._executor.submit(fn)
    self._pending_future._result_type = result_type
    self._result_poll_timer.start()

Each tick of _check_pending_result() first relays any pending progress message, then -- if the future is done -- stops the timer, unwraps the result and routes it by tag: "network_status", "update_check" or "self_update". An exception from the job maps to updateStatus = "error" ("Could not reach GitHub") or selfUpdateStatus = "error" ("Update failed unexpectedly"). A consequence of the single slot: a network poll that lands while a self-update is running is silently skipped.

The C++ port instead keeps one busy flag per activity (m_networkCheckBusy, m_updateCheckBusy, m_updating), so a connectivity probe and an update check can be in flight at the same time.

Connectivity Detection

Network status is polled every 30 seconds while online. After three consecutive failed probes the interval backs off to 2 minutes and returns to 30 s on the first success (POLL_ONLINE_MS / POLL_OFFLINE_MS / OFFLINE_STREAK_FOR_BACKOFF in Python, kPollOnlineMs / kPollOfflineMs / kOfflineStreakForBackoff in C++). The first probe runs 2 s after startup so the UI can paint first; the git --version probe behind canSelfUpdate runs at that same moment rather than in the constructor. Python runs the name lookup and the internet probe sequentially inside one worker job; C++ starts them in parallel.

Network Name Detection

_get_network_name_sync() (Python) / startNetworkNameCheck() + onNetworkNameCheckFinished() (C++) shell out to the platform's network tool. The WiFi command runs first; if it yields no SSID a second command looks for a wired link and reports the literal string "Ethernet".

PlatformWiFi SSIDWired fallback
Linux nmcli -t -f ACTIVE,SSID dev wifi -- first line starting yes: nmcli -t -f TYPE,STATE dev -- a line containing both ethernet and connected
macOS networksetup -getairportnetwork en0 -- text after Current Wi-Fi Network: ifconfig en0 -- output contains status: active
Windows netsh wlan show interfaces -- first SSID line that is not BSSID netsh interface show interface -- a line containing Connected and Ethernet
Android C++ only: no command is run; networkName is set to the fixed string "WiFi". (The Python backend is desktop-only.)

Python gives every subprocess a 5-second timeout. C++ waits up to 5 s for the process to start (waitForStarted(5000)) and otherwise lets it run to completion asynchronously; a name check that is still running when the next poll fires is simply skipped. When neither WiFi nor Ethernet is found both backends report an empty name: the C++ wired-fallback lambda on every desktop platform (and the failed-to-start path) calls clearNetworkName(), which clears networkName and emits networkNameChanged("") so a stale SSID is never left on screen.

Internet Connectivity Check

Reachability is a single HTTPS GET of Google's generate_204 endpoint (a captive-portal probe URL that returns an empty 204). Python uses urllib with a 5 s timeout; C++ uses QNetworkAccessManager with setTransferTimeout(5000) and treats any QNetworkReply error as offline. 

@staticmethod
def _check_internet_sync():
    """Check if the device has internet connectivity."""
    try:
        urllib.request.urlopen("https://clients3.google.com/generate_204", timeout=5)
        return True
    except Exception:
        pass
    return False

Auto Update Check on First Connect

The first time a probe succeeds (_auto_update_checked / m_autoUpdateChecked) the manager schedules checkForUpdates() 500 ms later. The flag is never reset, so this happens once per process; later checks are user-initiated from the About page.

Update Checking Mechanism

The update checker is git-based: it compares the local HEAD against the latest commit on the main branch and asks git how the two are related. There is no release-tag or version-number comparison, which has a consequence for packaged builds (see the box below).

Step-by-Step Flow

  1. Connectivity gate (Python only) -- _do_update_check_sync() re-runs the generate_204 probe and returns "error" / "No internet connection" without touching git or GitHub when offline. C++ goes straight to the next step and reports "Could not reach GitHub" if the request fails.
  2. Get local commit hash -- git rev-parse --short HEAD in the repository root. Python derives the root as the parent of backend/; C++ uses repoDir() = QCoreApplication::applicationDirPath() + "/..", which assumes the binary lives one level below the checkout (e.g. build/octave). Failure yields "error" / "Could not determine local version".
  3. Query GitHub API -- GET https://api.github.com/repos/WayBetterSolutions/OCTAVE/commits/main with a User-Agent: OCTAVE-Updater header and a 10 s timeout. The response's sha is truncated to 7 characters; the first line of commit.message becomes remoteCommitMsg.
  4. Classify the relationship -- _local_vs_remote_sync() / localVsRemote() returns one of same, ahead, diverged, behind (see below), and the working tree is checked for uncommitted changes at the same time.
  5. Emit result -- updateStatus becomes "up-to-date", "ahead", "diverged" or "update-available" with a matching updateMessage; remoteCommit, remoteCommitMsg and workingTreeDirty are refreshed. Both backends log local=… remote=… relation=… dirty=… status=… at info level.

Ancestry-Aware Classification

A bare remote != local test cannot tell "behind" from "ahead". Before commit 0c29e64 a source checkout with local commits reported an update to a commit older than HEAD, and the self-update path would then have hard-reset onto it. The classifier now asks git: 

@classmethod
def _local_vs_remote_sync(cls, remote_short, local_short):
    if not remote_short:
        return "behind"
    if remote_short == local_short:
        return "same"

    # Do we even have the remote commit locally? If the object is missing we
    # cannot be a descendant of it, so this is a normal "remote moved ahead".
    have_remote, _ = cls._run_git_sync(['cat-file', '-e', f'{remote_short}^{{commit}}'], timeout=5)
    if have_remote:
        is_ancestor, _ = cls._run_git_sync(
            ['merge-base', '--is-ancestor', remote_short, 'HEAD'], timeout=5)
        if is_ancestor:
            return "ahead"  # remote commit is already in our history

    # Remote commit is unknown to us. If we also carry commits the last-fetched
    # origin/main lacks, both sides moved -- that is a divergence, not an update.
    ok, count = cls._run_git_sync(['rev-list', '--count', 'origin/main..HEAD'], timeout=5)
    if ok and count.isdigit() and int(count) > 0:
        return "diverged"

    return "behind"

The C++ localVsRemote() runs the same three git commands through runGitSync(). Note that the diverged test compares against the last-fetched origin/main; the check itself never fetches.

Update Status Values

# updateStatus can be one of:
""                  # No check has run yet (About page hides the status row)
"checking"          # Currently checking
"up-to-date"        # Local matches remote
"update-available"  # Local is strictly behind the remote
"ahead"             # Source checkout with local commits (dev build)
"diverged"          # Both sides moved -- not a safe update
"error"             # Check failed (no internet, API error, not a git checkout)

Only "update-available" raises the badge on the settings button (frontend/BottomBar.qml, frontend/SettingsMenu.qml) and offers the self-update button. "ahead" and "diverged" are normal states when running from the source tree and must never trigger an "update" that would move the checkout backwards.

Packaged builds always report "error"
An AppImage, .dmg, .exe or .apk has no .git next to it, so git rev-parse fails in step 2 and the About page shows "Could not determine local version". The update check is a source-checkout feature today; there is no fallback that compares the build's version tag against GitHub releases.

Self-Update System

Availability
Self-update is only available when running from a git checkout. canSelfUpdate is probed 2 s after startup: Python requires git --version to succeed and the interpreter not to be frozen (sys.frozen); C++ additionally requires a .git directory in repoDir() and returns false unconditionally on Android. Packaged builds therefore report false and the About page shows its "not available" card instead.
Preconditions (checked at click time)
Step 2 below is git reset --hard origin/main, which discards every uncommitted change to tracked files. applySelfUpdate() therefore re-verifies state at the moment it is called -- not from the cached update status, which may be minutes stale -- and refuses to run when:
  • the working tree is dirty (git status --porcelain is non-empty) -- selfUpdateMessage "Uncommitted changes — commit or stash them first", or
  • updateStatus is "ahead" or "diverged", since resetting would discard local commits -- "Local commits would be lost — refusing to reset".
If git itself cannot be queried, the tree is assumed dirty -- the safe default is the one that destroys nothing. The About page additionally hides the update button while workingTreeDirty is true and shows a "commit or stash first" warning instead.

Pre-Conditions

@staticmethod
def _check_can_self_update():
    """Check if self-update is possible (requires git, not a frozen PyInstaller build)."""
    if getattr(sys, 'frozen', False):
        return False
    try:
        result = subprocess.run(
            ['git', '--version'],
            capture_output=True, text=True, timeout=5
        )
        return result.returncode == 0
    except Exception:
        return False

Update Pipeline

Python runs _do_self_update_sync() as one worker job. C++ implements the same sequence as a step machine (runSelfUpdateStep() / onSelfUpdateStepFinished()): each step starts one QProcess and the finished slot starts the next. A double-tap guard (_updating / m_updating) prevents concurrent update attempts.

  1. Save rollback point -- git rev-parse HEAD captures the full current hash (progress "Saving rollback point..."). A failure here is not fatal; the update proceeds without rollback.
  2. Fetch latest changes -- git fetch origin main (Python timeout 60 s; C++ none). Progress "Fetching latest changes...". Failure ends with "Fetch failed: <stderr>".
  3. Apply update -- git reset --hard origin/main (Python timeout 30 s). Progress "Applying update...". Failure ends with "Apply failed: <stderr>".
  4. Pre-flight verification -- if main.py exists, compile it with py_compile (Python uses sys.executable, C++ runs python3; 15 s timeout in Python). Progress "Verifying new code...". If the new code fails to parse the update is rolled back to the saved commit and ends with "Update rolled back — new code failed syntax check". C++ skips the step when there is no main.py.
  5. Install dependencies -- locate the venv pip (venv/bin/pip or venv/Scripts/pip.exe) and run pip install -r requirements.txt (Python timeout 600 s). Progress "Installing dependencies...". Failures are logged and the first 120 characters of stderr become a "(Some dependencies may need manual install)" suffix on the final message, but they do not roll back -- the code update already succeeded. A missing pip or requirements.txt skips the step with a warning.
  6. Confirm -- git log -1 --format=%h %s produces the final message "Update applied. Now on: <hash> <subject>" and selfUpdateStatus becomes "restart-required"; updateStatus flips to "up-to-date" with "Update applied — restart to complete".

Rollback Mechanism

Rollback is git reset --hard <old_commit> (30 s timeout) and is a no-op when step 1 failed to record a hash. Python rolls back on the syntax-check failure, on any subprocess.TimeoutExpired ("Update timed out and was rolled back") and on any other exception ("Update failed and was rolled back: ..."); a failed fetch or reset returns its error without a rollback call. C++ calls rollback() on fetch, reset and syntax-check failures, and on a git process that fails to start during steps 1-2; later steps that fail to start are skipped ("Update applied (some steps skipped)"). 

if old_commit:
    subprocess.run(
        ['git', 'reset', '--hard', old_commit],
        cwd=repo_dir, capture_output=True, text=True, timeout=30
    )
    logger.info(f"Rolled back to {old_commit[:7]}")

Progress Reporting

Worker-side progress is relayed through a lock-protected message slot. The worker calls _set_progress(msg) / setProgress(msg), and the 250 ms result poll timer on the main thread picks the message up and emits selfUpdateMessageChanged. In Python the timer is started by _submit_work(); in C++ applySelfUpdate() starts the same m_resultPollTimer before setting the initial "Fetching latest changes...", so every step's message ("Applying update...", "Verifying new code...", "Installing dependencies...") reaches the About page on both backends.

Self-Update Status Values

"idle"              # No update in progress (initial value)
"fetching"          # Pipeline running (About page shows a spinner + selfUpdateMessage)
"error"             # Refused, failed, or rolled back -- message says which
"restart-required"  # Update applied, restart needed

Application Restart

After a successful self-update the About page offers restartApp(). Both backends first run a pre-flight py_compile of main.py (Python always; C++ only when the file exists next to the repo root, using python3) and abort with selfUpdateStatus = "error" / "Restart aborted — code has errors" if it fails. The restart itself is platform-dependent:

  • Python, Windows: subprocess.Popen([python, main.py, *argv]), then QApplication.quit()
  • Python, Linux/macOS: os.execv is connected to aboutToQuit, then quit(). The current process is replaced in place once manager cleanup has run.
  • C++, Windows: QProcess::startDetached(appPath, args) immediately, then QCoreApplication::quit()
  • C++, Linux/macOS: the same startDetached() deferred to aboutToQuit, then quit() (a new process rather than execv).
Restart Safety
If the pre-flight syntax check fails, the restart is aborted and the user is notified via selfUpdateMessage. This prevents booting into broken code. (For the C++ binary the check only covers the Python entry point in a mixed checkout; it cannot validate the compiled executable.)

Device Shutdown

The shutdown_device() slot (the power button on frontend/settings/DeviceSettingsPage.qml) gives vehicle-mounted installs a clean power-off: it launches the OS shutdown command detached and then quits OCTAVE, so the aboutToQuit cleanup runs before the OS goes down. 

# Platform-specific shutdown commands (Popen / QProcess::startDetached):
Linux:   systemctl --no-block poweroff
macOS:   sudo shutdown -h +0
Windows: shutdown /s /t 5

Cleanup

cleanup() is called from the aboutToQuit handler in both entry points. It stops both timers; Python additionally calls executor.shutdown(wait=False), C++ kills and waits (3 s each) on any still-running git, connectivity or network-name process.

Design Decisions

Never emit from a worker thread

The Python class runs its subprocess and HTTP work on a single-worker executor and hands results back through a main-thread QTimer rather than emitting signals from the worker (the constructor comment: "avoids emitting signals from worker thread"). The same 250 ms relay carries progress text, so the worker never touches a Qt object. The C++ port gets the same guarantee for free from Qt's asynchronous process and network classes, which is why it has no worker thread at all.

Back off when the car is offline

Commit ee5a23e introduced the 30 s → 2 min backoff after three misses and moved the git --version probe off the constructor. The source comment states the motivation: "a car with no internet should not pay for an HTTPS timeout twice a minute forever." Recovery is immediate on the first successful probe, so a hotspot that comes back is noticed within one cycle.

Ancestry-aware update classification

Commit 0c29e64 replaced the hash-inequality test with the same / ahead / diverged / behind classifier after a dev checkout with local commits was offered an "update" to an older commit. The cat-file -e check comes first because an unknown remote object can never be an ancestor of HEAD, which avoids a misleading merge-base failure on the common "remote moved ahead" case.

Re-verify at click time; assume the worst when git is silent

Because step 2 is a hard reset, applySelfUpdate() re-runs git status --porcelain at the moment of the tap instead of trusting a check that may be minutes old ("the tree can be dirtied, or commits made, long after the last check ran"). If git cannot be queried the tree is treated as dirty -- "the safe default when we cannot tell is the one that refuses to destroy anything". workingTreeDirty is exposed as a property purely so the UI can hide the button before it "eats real work" (header comment).

Synchronous git only where it gates destruction (C++)

The C++ header explains why runGitSync() blocks the GUI thread: the queries are short, and their answer must be current at the instant of the click, not whatever an async check last cached. Everything else -- probes, the GitHub request, each update step -- stays asynchronous.

Verify before trusting the new code

A syntax error in a freshly pulled main.py would leave the head unit unable to boot, so the pipeline compiles it and rolls back on failure, and restartApp() repeats the check before exec'ing. Dependency install failures deliberately do not roll back: the code update already succeeded and "most deps are likely already installed from the prior version" (comment in _do_self_update_sync).

One automatic check, then user-driven

The update check runs once on first connectivity (500 ms later, so the connectivity state has settled) and afterwards only from the About page. There is no periodic polling of GitHub, which keeps the API call count negligible and avoids surprising the driver with a badge mid-journey.

Git as the update channel

The self-updater is git fetch + git reset --hard + pip install, which is exactly what a tinkerer running from a checkout would type. It intentionally does not try to replace a packaged binary; canSelfUpdate is false there and the About page says so.
