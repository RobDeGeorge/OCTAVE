What It Does

The network manager answers two questions: is this device online, and is there a newer OCTAVE than the one running? It also carries two actions that grew up beside those answers: updating OCTAVE in place when it runs from its own source code, and powering the device off.

You meet it in three places: the Network and Power sections of Settings > Device, the Software Updates card of Settings > About, and the orange dot on the Settings button when an update is waiting. It has no settings of its own.

This page starts with how to use it and gets more technical as it goes.

Network Status

Settings > Device > Device > Network shows a dot and two lines. The Device tile carries the same dot.

You seeMeaning
Green dot, a network name, "Internet connected"Online. The name is the Wi-Fi network, or "Ethernet" on a cable.
Green dot, "Connected", "Internet connected"Online, but OCTAVE could not find the network's name.
Red dot, "Not Connected", "No internet access"The internet did not answer. This is also what you see just after starting, until the first check has answered.

OCTAVE checks every 30 seconds. After three misses in a row it checks every 2 minutes, and goes back to 30 seconds at the first success. Refresh checks at once.

OCTAVE only reports the network. It does not join a Wi-Fi network or change one: do that in the operating system.

Software Updates

OCTAVE looks for a newer version once per run, the first time it finds itself online. After that it looks only when you tap Check for Updates in Settings > About. When there is one, an orange dot pulses on the Settings button, on the About entry and on the Check for Updates button.

Updating a Source Checkout

A head unit that runs OCTAVE from a git checkout can update itself from the screen: it fetches the new source, rebuilds, and restarts. Update Now appears when all of this is true:

  • The program runs from a CMake build folder directly inside the checkout (build/octave).
  • git and cmake are installed.
  • The check found an update.
  • The checkout has no uncommitted changes. If it has, the card says "This copy has uncommitted changes. Commit or stash them to update." and the button is hidden.
  1. Tap Update Now. It turns into Confirm Update with the warning "This will overwrite local changes". Tap again within 5 seconds, or it goes back.
  2. Wait. The card shows the step: "Fetching latest changes...", "Applying update...", "Configuring build...", then "Building... [45%]". The build can take minutes on a Raspberry Pi. OCTAVE keeps working meanwhile.
  3. When it says "Update applied. Now on: ...", tap Restart Now. OCTAVE closes and starts again with the same command-line options.

If a step fails, the card shows the reason in red and a Retry Update button. A failed build undoes itself: the source goes back to the commit it was on, the old program stays in place, and the message reads "Build failed — update rolled back to ..." with the first error line of the build.

Update Now replaces the checkout with GitHub's main
The update is git reset --hard origin/main. It refuses to run over uncommitted changes, over commits GitHub does not have, and on any branch other than main ("On branch … — switch to main to update"). It is still not meant for a checkout you develop in.

A checkout that cannot rebuild itself (no build folder, no cmake) shows "Pull the latest changes from GitHub to update." in place of the button.

Shut Down

Settings > Device > Device > Power has a Shut Down button for a head unit with no power switch. Tap it, then tap Confirm Shutdown. OCTAVE asks the operating system to power off and closes itself, saving its state on the way out.

With a phone mirrored, it first ends the drive being recorded and copies it to the phone, so the drive is on your phone when you get home. The card says "Sending the drive to your phone, then powering off…" and networkManager.poweringOff is true meanwhile. This takes a few seconds and never more than 30. See Drives to your phone and server.

Whether the device then powers off is up to the operating system: the user OCTAVE runs as must be allowed to do it. OCTAVE does not check.

How It Works

From here on the page is for people who want to know what happens underneath, or who are changing the code.

NetworkManager is one class with no thread of its own. Everything slow (a web request, a command-line tool, a build) is started and left to report back, so the screen never waits on the network. The rest of the app reaches it as networkManager, in QML and over the service API.

The online check

Two things run side by side, first 2 seconds after startup and then on the timer described above:

  • Is the internet there? One HTTPS request to clients3.google.com/generate_204, a page that exists to answer "yes" with no content. It has 5 seconds. Any error means offline. The result is isConnected.
  • What is the network called? The platform's own tool is asked for the Wi-Fi name. If there is none, a second command looks for a wired link. The result is networkName: a name, "Ethernet", or empty.

On Linux the Wi-Fi question is nmcli -t -f ACTIVE,SSID dev wifi list --rescan no. The --rescan no matters: without it nmcli scans for networks, which takes the radio off its channel for about 4 seconds. On a head unit whose Wi-Fi card also hosts the hotspot the phone mirrors over, that froze the mirrored picture once a minute. Keep it.

The update check

  1. checkForUpdates() sets updateStatus to checking.
  2. If there is a .git folder one level above the program's folder, it asks git for the current commit. No checkout, no git, or no answer: it does the release check instead (step 5). Android never looks for a checkout.
  3. Checkout: it asks GitHub for the newest commit on main (api.github.com/repos/RobDeGeorge/OCTAVE/commits/main).
  4. It asks git how the two commits are related, not just whether they differ: the same, the checkout behind, the checkout ahead (GitHub's commit is already in its history), or diverged. Only "behind" is an update. It also compares the checkout with the commit the running program was built from, and notes whether the checkout has uncommitted changes (workingTreeDirty).
  5. Package: it asks GitHub for the latest release (.../releases/latest) and compares the release's tag with the version built into the program. A release candidate sorts before its release: 0.9.6-rc2 is older than 0.9.6.

The answer lands in these properties:

PropertyHolds
updateStatusEmpty before the first check, then checking, up-to-date, update-available, ahead, diverged or error. Only update-available lights the orange dot.
updateMessageThe line shown on the card.
remoteCommit, remoteCommitMsgCheckout: the commit on main and the first line of its message. Package: the newer release's tag and title.
releaseUrlPackage with a newer release: the release's page. Otherwise empty. It is always a page of this repository on github.com, because the app opens it in a browser.

The update itself

canSelfUpdate is worked out once, 2 seconds after startup: a .git above the program's folder, a CMakeCache.txt beside the program, a cmake (the one named in that cache, else the one on PATH) and a git that runs. applySelfUpdate() then checks again, at the moment of the tap, that the checkout has no uncommitted changes, and refuses if the last check said ahead or diverged. If git cannot be asked, the checkout counts as changed and the update is refused. After that, one command at a time:

  1. Remember the current commit, to go back to.
  2. git fetch origin main
  3. git reset --hard origin/main
  4. cmake -S <checkout> -B <build folder>, so the commit built into the program matches the new source.
  5. Copy the program to octave.pre-update, then cmake --build with one job per core, under nice so the screen keeps its share of the processor.
  6. Read the new commit for the final message.

selfUpdateStatus is idle, fetching (for the whole run), restart-required or error, and selfUpdateMessage is the text beside it. A failure at steps 2 to 5 resets the source to the remembered commit. A failed configure or build also puts the copied program back if the build had touched it. The running program is not disturbed by a successful build either: the linker writes a new file, and the process keeps the old one until it restarts.

restartApp() starts the program again with the same arguments and quits. It first checks that the program file is there and executable; if not, it stays running and says "Restart aborted — the OCTAVE binary is missing".

Limits

  • "Online" means Google's check page answered. A network that blocks it reads as offline even when other sites work.
  • The network name on Linux needs NetworkManager's nmcli. On macOS only en0 is looked at.
  • The update check runs once by itself per run. A head unit that stays on for days learns of a new version only when someone taps Check for Updates.
  • GitHub is asked without an account, so its limit for anonymous requests applies. Past it, the check says "Could not reach GitHub".
  • The check never fetches. "Diverged" is judged against the origin/main the checkout last fetched.
  • The refusal over local commits uses the result of the last check, not a new one. Commits made after that check and before the tap are not seen.
  • The checkout is assumed to be the folder above the program's folder. A build folder elsewhere is treated as a package.
  • Shut Down does not wait for the operating system or check that it agreed.

When Something Goes Wrong

  1. The message on the card. A failed update says which step failed and why: "Fetch failed: ...", "Apply failed: ...", "Build failed — update rolled back to ...".
  2. The log files. Every update check writes one line under the octave.network category with both versions and the verdict. A failed build writes the end of the build output there. See Architecture for where the logs are.
  3. "Could not reach GitHub" on Windows. The log line names the TLS backend in use; it should say schannel. See the last section for why.

Why It Is Built This Way

  • Check less often when offline. A car with no internet should not pay for a request that times out twice a minute, forever. The first success puts the 30 seconds back, so a hotspot that returns is noticed quickly.
  • Ask git how the commits are related. "Different from GitHub" is not "older than GitHub". A checkout with its own commits would be offered an update to an older commit, and the update would then reset onto it and lose them.
  • Check again at the tap, and refuse when unsure. The update discards uncommitted work, and the last check may be minutes old. These few git questions are asked on the spot, blocking for a moment, because their answer must be true now. When git gives no answer, the safe guess is the one that destroys nothing.
  • Build before restarting, and keep the old program. Source that does not compile would leave a head unit with a program that no longer matches its source, or with none after a failed link. So the old program is copied aside, and a failed build puts source and program back.
  • The commit is built in through a generated header. Only the files that include it are recompiled after an update. As a compiler definition it rebuilt every file, which made each update on a Pi a full build.
  • Packages are compared with releases, not with main. A release is not the tip of main, and a package cannot rebuild itself. It is replaced by installing the next one, so the app only points at it.
  • One automatic check, then only on request. GitHub is asked once per run, which keeps the request count far below its limit.
  • Schannel on Windows. The Windows package ships OpenSSL for Android Auto, and with it present Qt would use OpenSSL for HTTPS. That trusts only the certificates already in the Windows store, and a fresh Windows has few, so the update check failed there. The manager selects Windows' own TLS (Schannel) before anything else in the app uses HTTPS. The choice is for the whole program.
  • Every helper process is ended at exit. A command still running when the manager is destroyed is an error in Qt ("Destroyed while process is still running"), seen with netsh on Windows.
