Overview

The NetworkManager is responsible for three core functions within OCTAVE: detecting network connectivity status, checking for application updates via the GitHub API, and performing git-based self-updates when running from source. It is defined in src/managers/networkmanager.{h,cpp} (C++) and backend/network_manager.py (Python) and registered as the QML context property networkManager in src/main.cpp / main.py. The sections below describe the Python implementation; the C++ port exposes the same properties, signals, slots, and status strings.

Thread Safety
In the Python backend all blocking I/O operations (subprocess calls, HTTP requests) run on a background ThreadPoolExecutor with a single worker. Results are polled back to the main Qt thread via a QTimer at 250ms intervals, ensuring signals are always emitted on the main thread. The C++ backend needs no worker thread: it uses asynchronous QProcess and QNetworkAccessManager calls whose completion slots run on the main thread (only the short git status / merge-base queries that gate the destructive self-update run synchronously).

The manager targets the GitHub repository WayBetterSolutions/OCTAVE and compares the local git HEAD against the remote main branch to determine update availability.

Background Work Pattern

Only one background job runs at a time. The _submit_work() method accepts a callable and a result type tag, submits to the executor, and starts the result poll timer: 

def _submit_work(self, fn, result_type):
    """Submit blocking work to the thread pool. Only one job at a time."""
    if self._pending_future and not self._pending_future.done():
        return  # Already busy
    self._pending_future = self._executor.submit(fn)
    self._pending_future._result_type = result_type
    self._result_poll_timer.start()

When the poll timer fires, _check_pending_result() checks if the future is done, extracts the result, and routes it to the appropriate handler based on the _result_type tag: "network_status", "update_check", or "self_update".

WiFi Connectivity Detection

Network status is polled every 30 seconds via _poll_timer while online; after three consecutive failed probes the interval backs off to 2 minutes (a car with no internet should not pay for an HTTPS timeout twice a minute) and returns to 30 s on the first success. The initial check runs 2 seconds after startup to let the UI load first; the git --version probe behind canSelfUpdate runs at the same moment rather than in the constructor. Internet Connectivity Check

The _check_internet_sync() method makes a lightweight HTTP request to Google's 204-response endpoint: 

@staticmethod
def _check_internet_sync():
    try:
        urllib.request.urlopen("https://clients3.google.com/generate_204", timeout=5)
        return True
    except Exception:
        pass
    return False

Auto Update Check on First Connect

When connectivity is first detected (_auto_update_checked flag), the manager automatically triggers checkForUpdates() with a 500ms delay. This ensures users are notified of available updates as soon as the system comes online.

Update Checking Mechanism

The update checker compares the local git commit hash against the latest commit on the main branch of the GitHub repository.

Step-by-Step Flow

  1. Get local commit hash -- Runs git rev-parse --short HEAD from the repository root directory to get the 7-character short hash.
  2. Query GitHub API -- Fetches https://api.github.com/repos/WayBetterSolutions/OCTAVE/commits/main with a User-Agent: OCTAVE-Updater header.
  3. Classify the relationship -- Truncates the remote SHA to 7 characters. A bare inequality test cannot distinguish "behind" from "ahead", so the check also asks git how the two commits relate: if the remote commit is already an ancestor of local HEAD, the checkout is ahead (a dev build), not out of date. If the remote commit is unknown locally but local commits exist that the last-fetched origin/main lacks, the branch has diverged.
  4. Emit result -- Sets updateStatus to one of: "up-to-date", "update-available", "ahead", "diverged", or "error". Also populates the remote commit hash and message, and refreshes workingTreeDirty.

Update Status Values

# updateStatus can be one of:
"checking"          # Currently checking
"up-to-date"        # Local matches remote
"update-available"  # Local is strictly behind the remote
"ahead"             # Source checkout with local commits (dev build)
"diverged"          # Both sides moved -- not a safe update
"error"             # Check failed (no internet, API error)

Only "update-available" raises the update badge and offers the self-update button. "ahead" and "diverged" are normal states when running from the source tree and must never trigger an "update" that would move the checkout backwards.

Self-Update System

Availability
Self-update is only available when running from a git checkout. The canSelfUpdate property checks that git is on the PATH (Python additionally requires a non-frozen interpreter; C++ additionally requires a .git directory next to the executable's repo root). Packaged builds (AppImage, .dmg, .exe, Android) report false.
Preconditions (checked at click time)
Step 2 below is git reset --hard origin/main, which discards every uncommitted change to tracked files. applySelfUpdate() therefore re-verifies state at the moment it is called -- not from the cached update status, which may be minutes stale -- and refuses to run when:
  • the working tree is dirty (git status --porcelain is non-empty), or
  • updateStatus is "ahead" or "diverged", since resetting would discard local commits.
If git itself cannot be queried, the tree is assumed dirty -- the safe default is the one that destroys nothing. The UI additionally hides the update button while workingTreeDirty is true.

Pre-Conditions

@staticmethod
def _check_can_self_update():
    if getattr(sys, 'frozen', False):
        return False
    # Check git is available
    result = subprocess.run(['git', '--version'], ...)
    return result.returncode == 0

Update Pipeline (5 Steps)

The _do_self_update_sync() method executes a multi-step pipeline with full rollback capability. A double-tap guard (_updating flag) prevents concurrent update attempts.

  1. Save rollback point -- Captures the current full commit hash via git rev-parse HEAD. This is used to roll back if any subsequent step fails.
  2. Fetch latest changes -- Runs git fetch origin main with a 60-second timeout. Progress message: "Fetching latest changes..."
  3. Apply update -- Runs git reset --hard origin/main with a 30-second timeout. This moves the working tree to the latest remote state.
  4. Pre-flight verification -- Compiles main.py with py_compile to catch syntax errors. If the new code fails to parse, the update is automatically rolled back to the saved commit.
  5. Install dependencies -- Locates the venv pip executable and runs pip install -r requirements.txt with a 10-minute timeout. Dependency install failures are logged but do not trigger a rollback, since the code update already succeeded.

Rollback Mechanism

On any failure (syntax check, timeout, unexpected exception), the manager rolls back: 

if old_commit:
    subprocess.run(
        ['git', 'reset', '--hard', old_commit],
        cwd=repo_dir, capture_output=True, text=True, timeout=30
    )
    logger.info(f"Rolled back to {old_commit[:7]}")

Progress Reporting

Worker thread progress is relayed through a thread-safe mechanism. The worker calls _set_progress(msg) which stores the message under a lock, and the main-thread poll timer picks it up and emits selfUpdateMessageChanged.

Self-Update Status Values

"idle"              # No update in progress
"fetching"          # Downloading changes
"error"             # Update failed (with rollback)
"restart-required"  # Update applied, restart needed

Application Restart

After a successful self-update, the user can trigger restartApp() from QML. This performs a pre-flight syntax check on main.py before restarting. The restart mechanism is platform-dependent:

  • Windows: Spawns a new process with subprocess.Popen, then calls QApplication.quit()
  • Unix (Linux/macOS): Connects os.execv to the aboutToQuit signal, then calls QApplication.quit(). This replaces the current process in-place after cleanup.
  • C++ backend: Launches a fresh copy of the executable with QProcess::startDetached() on every platform, then quits.
Restart Safety
If the pre-flight syntax check fails, the restart is aborted and the user is notified via selfUpdateMessage. This prevents booting into broken code.

Device Shutdown

The shutdown_device() slot provides a clean shutdown sequence for vehicle-mounted installations: it schedules an OS power-off command and then quits the OCTAVE application. 

# Platform-specific shutdown commands:
Linux:   systemctl --no-block poweroff
macOS:   sudo shutdown -h +0
Windows: shutdown /s /t 5

System Integration

The NetworkManager is registered in main.py as a QML context property: 

engine.rootContext().setContextProperty("networkManager", network_manager)

QML views access it directly for network status display and update management: 

// Check for updates from QML
networkManager.checkForUpdates()

// Display network name
Text { text: networkManager.networkName }

// Show update notification
visible: networkManager.updateStatus === "update-available"

// Apply update and restart
networkManager.applySelfUpdate()
// When selfUpdateStatus === "restart-required":
networkManager.restartApp()

Cleanup

The cleanup() method stops both QTimers and shuts down the thread pool. It should be called from the application's aboutToQuit handler.
