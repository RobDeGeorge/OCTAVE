Overview

The NetworkManager has three jobs: report whether the head unit is online (and on which network), tell the user when the main branch on GitHub has moved past the running commit, and -- because OCTAVE's Python backend runs from a git checkout -- pull that update in place and restart. It is defined in backend/network_manager.py and registered as the QML context property networkManager in main.py.

Thread Safety
The routine connectivity, update-check and update-pipeline work runs on a ThreadPoolExecutor with a single worker, and results are polled back on the main thread by a 250 ms QTimer so Qt signals are only ever emitted from the GUI thread. A few short calls still run synchronously on the GUI thread: the startup git --version probe, the click-time git status --porcelain check in applySelfUpdate(), and the py_compile check in restartApp().

The manager targets the GitHub repository RobDeGeorge/OCTAVE (GITHUB_REPO) and compares the local git HEAD against the tip of the remote main branch.

Architecture

NetworkManager (backend/network_manager.py) | |-- ThreadPoolExecutor (1 worker) -- one job at a time (_pending_future) | |-- _do_network_check() nmcli/networksetup/netsh + generate_204 | |-- _do_update_check_sync() GitHub API + git ancestry queries | |-- _do_self_update_sync() fetch / reset / py_compile / pip / log | |-- QTimer _poll_timer 30 s online, 120 s after 3 misses |-- QTimer _result_poll_timer 250 ms: future done? progress message? |-- QTimer.singleShot(2000) _startup_probe: git --version + first check | |-- Signals --> QML (all emitted from the main thread)

Background Work Pattern

Only one background job runs at a time. _submit_work() takes a callable and a result-type tag, submits it to the executor, and starts the result poll timer: 

def _submit_work(self, fn, result_type):
    """Submit blocking work to the thread pool. Only one job at a time."""
    if self._pending_future and not self._pending_future.done():
        return  # Already busy
    self._pending_future = self._executor.submit(fn)
    self._pending_future._result_type = result_type
    self._result_poll_timer.start()

Each tick of _check_pending_result() first relays any pending progress message, then -- if the future is done -- stops the timer, unwraps the result and routes it by tag: "network_status", "update_check" or "self_update". An exception from the job maps to updateStatus = "error" ("Could not reach GitHub") or selfUpdateStatus = "error" ("Update failed unexpectedly"). A consequence of the single slot: any job submitted while another is still running is silently dropped. A network poll that lands during a self-update is simply skipped; a checkForUpdates() tap that lands while a connectivity probe is running sets updateStatus to "checking" but never submits the check, so the status stays at "checking" until the next tap.

Connectivity Detection

Network status is polled every 30 seconds while online. After three consecutive failed probes the interval backs off to 2 minutes and returns to 30 s on the first success (POLL_ONLINE_MS / POLL_OFFLINE_MS / OFFLINE_STREAK_FOR_BACKOFF). The first probe runs 2 s after startup so the UI can paint first; the git --version probe behind canSelfUpdate runs at that same moment rather than in the constructor. The name lookup and the internet probe run one after the other inside one worker job.

Network Name Detection

_get_network_name_sync() shells out to the platform's network tool. The WiFi command runs first; if it yields no SSID a second command looks for a wired link and reports the literal string "Ethernet".

Internet Connectivity Check

Reachability is a single HTTPS GET of Google's generate_204 endpoint (a captive-portal probe URL that returns an empty 204) using urllib.request.urlopen with a 5 s timeout. Any exception counts as offline. 

@staticmethod
def _check_internet_sync():
    """Check if the device has internet connectivity."""
    try:
        urllib.request.urlopen("https://clients3.google.com/generate_204", timeout=5)
        return True
    except Exception:
        pass
    return False

Auto Update Check on First Connect

The first time a probe succeeds (_auto_update_checked) the manager schedules checkForUpdates() 500 ms later. The flag is never reset, so this happens once per process; later checks are user-initiated from the About page.

Update Checking Mechanism

The update checker is git-based: it compares the local HEAD against the latest commit on the main branch and asks git how the two are related. There is no release-tag or version-number comparison, which has a consequence for packaged builds (see the box below).

Step-by-Step Flow

  1. Connectivity gate -- _do_update_check_sync() re-runs the generate_204 probe and returns "error" / "No internet connection" without touching git or GitHub when offline.
  2. Get local commit hash -- git rev-parse --short HEAD in the repository root. The root is the parent of backend/ (_repo_dir()). Failure yields "error" / "Could not determine local version".
  3. Query GitHub API -- GET https://api.github.com/repos/RobDeGeorge/OCTAVE/commits/main with a User-Agent: OCTAVE-Updater header and a 10 s timeout. Any exception from here on (HTTP error, timeout, bad JSON) yields "error" / "Could not reach GitHub". The response's sha is truncated to 7 characters; the first line of commit.message becomes remoteCommitMsg.
  4. Classify the relationship -- _local_vs_remote_sync() returns one of same, ahead, diverged, behind (see below), and the working tree is checked for uncommitted changes at the same time.
  5. Emit result -- updateStatus becomes "up-to-date", "ahead", "diverged" or "update-available" with a matching updateMessage; remoteCommit, remoteCommitMsg and workingTreeDirty are refreshed. When an update is available but the tree is dirty, the message gains " — uncommitted changes block updating". The result is logged as local=… remote=… relation=… dirty=… status=… at info level.

Ancestry-Aware Classification

A bare remote != local test cannot tell "behind" from "ahead". Before commit 0c29e64 a source checkout with local commits reported an update to a commit older than HEAD, and the self-update path would then have hard-reset onto it. The classifier now asks git: 

@classmethod
def _local_vs_remote_sync(cls, remote_short, local_short):
    if not remote_short:
        return "behind"
    if remote_short == local_short:
        return "same"

    # Do we even have the remote commit locally? If the object is missing we
    # cannot be a descendant of it, so this is a normal "remote moved ahead".
    have_remote, _ = cls._run_git_sync(['cat-file', '-e', f'{remote_short}^{{commit}}'], timeout=5)
    if have_remote:
        is_ancestor, _ = cls._run_git_sync(
            ['merge-base', '--is-ancestor', remote_short, 'HEAD'], timeout=5)
        if is_ancestor:
            return "ahead"  # remote commit is already in our history

    # Remote commit is unknown to us. If we also carry commits the last-fetched
    # origin/main lacks, both sides moved -- that is a divergence, not an update.
    ok, count = cls._run_git_sync(['rev-list', '--count', 'origin/main..HEAD'], timeout=5)
    if ok and count.isdigit() and int(count) > 0:
        return "diverged"

    return "behind"

Each git query goes through _run_git_sync(), which returns (ok, stdout) and turns any exception into (False, ""). Note that the diverged test compares against the last-fetched origin/main; the check itself never fetches.

Update Status Values

# updateStatus can be one of:
""                  # No check has run yet (About page hides the status row)
"checking"          # Currently checking
"up-to-date"        # Local matches remote
"update-available"  # Classified as behind by the local-history check
"ahead"             # Source checkout with local commits (dev build)
"diverged"          # Both sides moved -- not a safe update
"error"             # Check failed (no internet, API error, not a git checkout)

Only "update-available" raises the badge on the settings button (frontend/BottomBar.qml, frontend/SettingsMenu.qml) and offers the self-update button. "ahead" and "diverged" are normal states when running from the source tree and must never trigger an "update" that would move the checkout backwards.

Only a git checkout can check for updates
The check needs a git repository at the parent of backend/. A copy of the source without its .git directory (for example an extracted source archive) fails git rev-parse in step 2 and the About page shows "Could not determine local version". There is no fallback that compares a version tag against GitHub releases.

Self-Update System

Availability
Self-update needs git on PATH. canSelfUpdate is probed 2 s after startup: git --version must succeed and the interpreter must not be frozen (sys.frozen, a guard left over from the removed PyInstaller builds). The probe does not check that the source directory is a git repository; in a copy without .git the click-time git status fails, the tree is treated as dirty and the update is refused. When canSelfUpdate is false the About page shows its "not available" card.
Preconditions (checked at click time)
The apply step below is git reset --hard origin/main, which discards every uncommitted change to tracked files. applySelfUpdate() therefore re-verifies state at the moment it is called for uncommitted changes, and refuses to run when:
  • the working tree is dirty (git status --porcelain is non-empty) -- selfUpdateMessage "Uncommitted changes — commit or stash them first", or
  • updateStatus is "ahead" or "diverged", since resetting would discard local commits -- "Local commits would be lost — refusing to reset".
If git itself cannot be queried, the tree is assumed dirty. The ahead/diverged check uses the cached updateStatus; ancestry is not rechecked after fetch or immediately before reset. These checks therefore do not guarantee preservation of commits or edits made after the checks. The About page additionally hides the update and "Retry Update" buttons while workingTreeDirty is true and shows a "commit or stash first" warning instead.

Pre-Conditions

@staticmethod
def _check_can_self_update():
    """Check if self-update is possible (requires git, not a frozen PyInstaller build)."""
    if getattr(sys, 'frozen', False):
        return False
    try:
        result = subprocess.run(
            ['git', '--version'],
            capture_output=True, text=True, timeout=5
        )
        return result.returncode == 0
    except Exception:
        return False

Update Pipeline

_do_self_update_sync() runs the whole sequence as one worker job. A double-tap guard (_updating) prevents concurrent update attempts; it is cleared when the result is applied.

  1. Save rollback point -- git rev-parse HEAD captures the full current hash (progress "Saving rollback point..."). A failure here is not fatal; the update proceeds without rollback.
  2. Fetch latest changes -- git fetch origin main (timeout 60 s). Progress "Fetching latest changes...". Failure ends with "Fetch failed: <stderr>".
  3. Apply update -- git reset --hard origin/main (timeout 30 s). Progress "Applying update...". Failure ends with "Apply failed: <stderr>".
  4. Pre-flight verification -- if main.py exists, compile it with sys.executable -m py_compile (15 s timeout). Progress "Verifying new code...". If the new code fails to parse the update is rolled back to the saved commit and ends with "Update rolled back — new code failed syntax check".
  5. Install dependencies -- locate the venv pip (venv/bin/pip or venv/Scripts/pip.exe) and run pip install -r requirements.txt (timeout 600 s). Progress "Installing dependencies...". A non-zero exit is logged; when its captured stderr is non-empty, the final message adds "(Some dependencies may need manual install)". Install failures do not roll back -- the code update already succeeded. A missing pip or requirements.txt skips the step with a warning.
  6. Confirm -- git log -1 --format=%h %s produces the final message "Update applied. Now on: <hash> <subject>" and selfUpdateStatus becomes "restart-required"; updateStatus flips to "up-to-date" with "Update applied — restart to complete".

Rollback Mechanism

Rollback is git reset --hard <old_commit> (30 s timeout) and is a no-op when step 1 failed to record a hash. The pipeline rolls back on the syntax-check failure, on any subprocess.TimeoutExpired ("Update timed out and was rolled back") and on any other exception ("Update failed and was rolled back: ..."); a failed fetch or reset returns its error without a rollback call. A failed dependency install never rolls back. 

if old_commit:
    subprocess.run(
        ['git', 'reset', '--hard', old_commit],
        cwd=repo_dir, capture_output=True, text=True, timeout=30
    )
    logger.info(f"Rolled back to {old_commit[:7]}")

Progress Reporting

Worker-side progress is relayed through a lock-protected message slot. The worker calls _set_progress(msg) (guarded by _progress_lock), and the 250 ms result poll timer started by _submit_work() picks the message up on the main thread and emits selfUpdateMessageChanged. Only the latest message per tick is shown, so a step that finishes within 250 ms may never appear.

Self-Update Status Values

"idle"              # No update in progress (initial value)
"fetching"          # Pipeline running (About page shows a spinner + selfUpdateMessage)
"error"             # Refused, failed, or rolled back -- message says which
"restart-required"  # Update applied, restart needed

Application Restart

After a successful self-update the About page offers restartApp(). It first runs a pre-flight py_compile of main.py (15 s timeout) and aborts with selfUpdateStatus = "error" / "Restart aborted — code has errors" if the check completes with a non-zero exit code; a timeout or inability to run the check is logged and does not block restart. The new process is [sys.executable, <repo>/main.py, *sys.argv[1:]], so command-line flags such as --debug carry over. The restart itself is platform-dependent:

  • Windows: subprocess.Popen(args), then QApplication.quit()
  • Linux/macOS: os.execv is connected to aboutToQuit, then quit(). The current process is replaced in place once manager cleanup has run.
Restart Safety
If the pre-flight check fails, the restart is aborted and the user is notified via selfUpdateMessage. This catches syntax errors in the entry point only; it does not validate imported modules or dependencies.

Device Shutdown

The shutdown_device() slot (the power button on frontend/settings/DeviceSettingsPage.qml) gives vehicle-mounted installs a clean power-off request: it starts the OS shutdown command with subprocess.Popen (not waited on) and then quits OCTAVE, triggering aboutToQuit cleanup. The manager does not verify that the OS accepted the request or wait for cleanup before requesting shutdown; the command also depends on the host's permissions. 

# Platform-specific shutdown commands (subprocess.Popen):
Linux:   systemctl --no-block poweroff
macOS:   sudo shutdown -h +0
Windows: shutdown /s /t 5

Cleanup

cleanup() is one step of the ordered cleanup list that main.py runs from aboutToQuit (each step wrapped so one failure does not stop the rest). It stops both timers and calls executor.shutdown(wait=False), so a job already running is not waited for.

Design Decisions

Never emit from a worker thread

The class runs its subprocess and HTTP work on a single-worker executor and hands results back through a main-thread QTimer rather than emitting signals from the worker (the constructor comment: "avoids emitting signals from worker thread"). The same 250 ms relay carries progress text, so the worker never touches a Qt object.

Back off when the car is offline

Commit ee5a23e introduced the 30 s → 2 min backoff after three misses and moved the git --version probe off the constructor. The source comment states the motivation: "a car with no internet should not pay for an HTTPS timeout twice a minute forever." Recovery is immediate on the first successful probe, so a hotspot that comes back is noticed within one cycle.

Ancestry-aware update classification

Commit 0c29e64 replaced the hash-inequality test with the same / ahead / diverged / behind classifier after a dev checkout with local commits was offered an "update" to an older commit. The cat-file -e check comes first because an unknown remote object can never be an ancestor of HEAD, which avoids a misleading merge-base failure on the common "remote moved ahead" case.

Re-verify at click time; assume the worst when git is silent

Because the apply step is a hard reset, applySelfUpdate() re-runs git status --porcelain at the moment of the tap instead of trusting a check that may be minutes old ("the tree can be dirtied, or commits made, long after the last check ran"). If git cannot be queried the tree is treated as dirty -- "the safe default when we cannot tell is the one that refuses to destroy anything". workingTreeDirty is exposed as a property purely so the UI can hide the button before it "eats real work" (comment on the property).

Verify before trusting the new code

A syntax error in a freshly pulled main.py would leave the head unit unable to boot, so the pipeline compiles it and rolls back on failure, and restartApp() repeats the check before exec'ing. Dependency install failures deliberately do not roll back: the code update already succeeded and "most deps are likely already installed from the prior version" (comment in _do_self_update_sync).

One automatic check, then user-driven

The update check runs once on first connectivity (500 ms later, so the connectivity state has settled) and afterwards only from the About page. There is no periodic polling of GitHub, which keeps the API call count negligible and avoids surprising the driver with a badge mid-journey.

Git as the source update channel

The self-updater is git fetch + git reset --hard + pip install, which is the update sequence for a source checkout running in its own venv/. Without git on PATH canSelfUpdate is false and the About page says so.
