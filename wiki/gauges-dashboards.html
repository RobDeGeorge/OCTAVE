Gauges & Dashboards

Overview

OCTAVE ships with a small library of gauge primitives under frontend/gauges/ and a set of pre-built dashboards defined as JSON specs under frontend/dashboards/presets/, rendered by frontend/dashboards/DashboardRenderer.qml. Dashboards render inline inside the OBD menu — the default view is the parameter-card grid, and selecting a dashboard swaps the grid for the chosen layout in place. Selection is persisted as the activeDashboard setting. DashboardManager (C++ and Python, full parity) enumerates built-in presets plus user-authored dashboards from the OS config dir and exposes save / delete / duplicate.

Entry point: a "Dashboards" pill at the top-right of the OBD menu opens a modal chooser listing "Parameter Cards" plus each registered dashboard. Tapping a choice swaps the content and closes the popup.

Gauges bind to the OBDParameterModel singleton by paramId (e.g. "RPM", "SPEED") — title, unit, min and max are auto-populated from the model, and the live value updates reactively as the backend polls each PID. No manual signal wiring is required.

Gauge primitives

PrimitiveUse for
CircularGaugeArc-sweep dial with optional tick marks, needle, redline and center readout. Flagship gauge for RPM, speed, coolant, etc.
BarGaugeHorizontal or vertical filled bar. Good for fuel, throttle, intake temps. Supports a warnAbove threshold that recolors the fill.
LinearGaugeHorizontal scale with tick marks and a sliding indicator. Best for bidirectional ranges that straddle zero (fuel trim, timing advance, EGR error).
DigitalReadoutBig numeric value with subdued label and unit. Use as the dominant element on a dashboard when an arc is overkill.
ArcGaugeHalf-dial (180° top arc with readout below the chord). Compact, wide-aspect alternative to CircularGauge for speedometer-style layouts. Shares the same arc/tick/needle/redline engine.
SparklineGaugeRolling history line showing recent values. Use when motion matters more than absolute value — boost, load, fuel trim. Timer-sampled so the x-axis scale stays stable; autoScale rescales the y-axis to the visible window for small-swing PIDs.
WarningLightBinary tell-tale indicator bound to a triggerAbove / triggerBelow threshold. Composable — drop several into a row for an idiot-light strip, or overlay one atop a larger gauge as a critical alert.
GForceGauge2D G-force dot with concentric rings, fading trail and total-G readout. Self-binding (no PID) — reads lateral/longitudinal acceleration from the BerryIMU.
CompassGaugeRotating compass card with cardinal letters, fixed lubber line, and degrees/cardinal readout. Self-binding (no PID) — reads the BerryIMU magnetometer heading.
NowPlayingWidgetAlbum art + title + artist + progress for the active media source (local or Spotify, following the app-wide source setting). Self-binding, display-only.
MediaControlsWidgetPrevious / play-pause / next transport buttons driving the active media source. Interactive in rendered dashboards.

Sensor data also flows through the regular PID system: the BerryIMU publishes PITCH, ROLL, HEADING, ALTITUDE, ACCEL_MAG, LATERAL_G, LONGITUDINAL_G and BARO_TEMP as parameters in OBDParameterModel, so any gauge can bind them (lateral G on a sparkline, pitch on a linear gauge…), they appear in the editor's PID picker, and demo mode sweeps them like any other PID.

Dashboard editor

Custom dashboards are built in-app, no file editing required. In the dashboard chooser, tap + New to start from a blank grid, or use the action buttons on each card: Copy duplicates any dashboard (the only way to derive from a read-only built-in), and Edit / Delete appear on user-authored dashboards. Deleting asks for a confirming second tap.

The editor is hybrid tap-and-drag, designed for an in-car touchscreen:

  • Tap an empty grid cell (marked +) to open the widget palette and place a primitive there. The PID picker opens immediately after placing.
  • Drag a placed widget to move it — it snaps to the grid, with a live green/red highlight showing whether the drop is valid. Invalid drops bounce back.
  • Tap a placed widget to select it. A floating panel (docked to whichever side is away from the selection, so the canvas never rescales) edits its PID (searchable picker, filtered to the kinds the widget supports), column / row / width / height via stepper buttons, and per-widget options such as needle, redline, warn and trigger thresholds.
  • Demo data (top bar toggle) sweeps plausible fake values through every PID so dashboards can be built and sized without a live OBD connection. It is editor-only and force-disabled when the editor closes.

Leaving the editor without saving (e.g. switching menus mid-build) stashes the work as a draft — the chooser then shows a ▲ Draft button next to + New. Saving or explicitly discarding clears the draft. Widgets scale their typography to their cell size and are clipped at the cell boundary, so no size you choose can spill data outside a widget's bounds.

Deleting the dashboard that is currently active (in-app, or by removing its JSON externally) falls back to the built-in Parameter Cards view. The user dashboards directory is watched on both backends, so a spec dropped in or removed from outside the app shows up in the chooser within a second — no restart. Specs are validated at render time: an unknown widget type is logged and skipped, an unknown paramId is logged and left unbound.

The whole editor flow is exercised end to end by dev/tests/drive_dashboard_editor.py (about 45 assertions against the running app through the command server; see Development → Command Server). It was verified on the desktop Python backend on 2026-09-08; the Android tablet check is still pending.

Saving writes a schema-1 JSON spec through dashboardManager.saveDashboard() into the user dashboards directory, and the new dashboard appears in the chooser immediately. The widget set, palette metadata, and editable options all come from the WidgetCatalog singleton (frontend/dashboards/WidgetCatalog.qml); editor sources live under frontend/dashboards/editor/.

Authoring new gauges & dashboards

The complete API reference, all 93 supported PID IDs, theme tokens, needle-angle math, and step-by-step recipes for adding a new dashboard or a new primitive live in docs/GAUGE_AUTHORING.md. That document is the source of truth — update it whenever the gauge API changes.

Quick recipe: build the dashboard in the in-app editor, or write a schema-1 JSON spec by hand — drop it in frontend/dashboards/presets/ to ship it as a built-in, or in the user dashboards directory (e.g. ~/.config/OCTAVE/dashboards/ on Linux) for a local custom board. New gauge primitives must implement the shared binding API and be registered in WidgetCatalog to render and appear in the editor palette.
