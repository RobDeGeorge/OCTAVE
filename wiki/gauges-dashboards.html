What It Is

A dashboard is a screen of gauges and other widgets laid out on a grid: a tachometer here, the speed in big figures there, the song that is playing along the bottom. OCTAVE's Home screen is one. You can keep the one that ships, pick one of the hand-drawn Home screens, or write a dashboard of your own.

A dashboard is not built on the car's screen. It is a small text file in JSON format that says which widget goes where and which reading it shows. You write it at a desk, or draw it in the editor OCTAVE serves to a web browser, and drop it in a folder. OCTAVE shows it at once.

This page starts with how to use it and gets more technical as it goes. Stop reading whenever you have what you came for.

Choosing What Home Shows

Open Settings > Display > Layout and find Home Screen. It shows a card with a picture for every choice. Tap one and it is Home.

CardWhat it is
HomeThe dashboard that ships: the phone's screen in the middle, the music under it, speed and RPM on the left, coolant temperature and system voltage on the right.
Cockpit, Glass, Trail, Retro, Rings, TelemetrySix Home screens drawn by hand, each with its own look. They are not grid dashboards and have no file to edit. See Hand-Built Home Screens.
ClassicThe older three-panel Home.
Your own dashboardsOne card for every file in the dashboards folder. A dashboard has no photo, so its card shows a plan of where its widgets stand.

What Home does on top of the dashboard it shows:

  • With no car connected it puts "No vehicle connected" and a Connect button over the car's readings, which would only show --.
  • With no music it puts the music prompt over the Now Playing widget, and "No sensor" on a widget that reads the motion sensor when there is none.
  • A tap on the music widget opens the music page. A tap on any other widget opens nothing yet.

If the dashboard you picked is deleted, Home goes back to the one that ships.

Making a Dashboard

  1. Write a file like the one below and save it as my-drive.json.
  2. Put it in the dashboards folder inside OCTAVE's config folder (table below). OCTAVE notices the new file within a second. There is no need to restart.
  3. Open Settings > Display > Layout > Home Screen and tap the My Drive card.
  4. Go Home. Edit the file and save it again whenever you like: Home redraws with the change.
{
  "id": "my-drive",
  "label": "My Drive",
  "schema": 1,
  "gridColumns": 12,
  "gridRows": 8,
  "cells": [
    { "type": "CircularGauge", "paramId": "RPM",
      "col": 0, "row": 0, "colSpan": 6, "rowSpan": 6,
      "props": { "showNeedle": true, "max": 7000, "redlineStart": 5500 } },

    { "type": "DigitalReadout", "paramId": "SPEED",
      "col": 6, "row": 0, "colSpan": 6, "rowSpan": 3,
      "props": { "frame": true } },

    { "type": "ArcGauge", "paramId": "COOLANT_TEMP",
      "col": 6, "row": 3, "colSpan": 3, "rowSpan": 3,
      "props": { "warnAbove": 100, "critAbove": 108 } },

    { "type": "BarGauge", "paramId": "FUEL_LEVEL",
      "col": 9, "row": 3, "colSpan": 3, "rowSpan": 3,
      "props": { "title": "Fuel", "critBelow": 10 } },

    { "type": "NowPlayingWidget",
      "col": 0, "row": 6, "colSpan": 8, "rowSpan": 2 },

    { "type": "ClockWidget",
      "col": 8, "row": 6, "colSpan": 4, "rowSpan": 2,
      "props": { "showDate": false } }
  ]
}

Read it as a sheet of squared paper 12 squares wide and 8 tall. Each entry in cells is one widget: its type, the reading it shows (paramId), the square its top-left corner sits on (col, row, counted from 0) and how many squares it covers (colSpan, rowSpan). props holds that widget's options.

You do not need a car to try a dashboard: connect the simulated car (see OBD Manager) and every gauge moves. If you would sooner drag widgets around than type, use the browser editor. It writes the same files.

The Dashboard File

KeyNeededWhat it is
idyesThe dashboard's name inside OCTAVE. Letters, digits, - and _, at most 64 characters. Use the file name without .json. home and grid are taken.
labelyesThe name on its card, up to 80 characters.
schemayes1, or 2 when the file has a portrait layout (below).
gridColumns, gridRowsnoThe size of the grid. 12 by 6 when left out, at most 48 each.
margins, spacingnoThe space around the grid and between widgets, 0 to 200. 20 and 16 when left out.
cellsyesThe widgets, at most 256.
alertBannernofalse turns off the red banner.

And in each cell:

KeyWhat it is
typeOne of the widgets.
paramIdThe id of the reading, such as RPM or COOLANT_TEMP. Leave it out for a widget that has its own data (the clock, the music). The ids are listed in the API reference; a custom PID of yours works too.
col, rowThe top-left square, counted from 0.
colSpan, rowSpanThe width and height in squares. 1 when left out.
propsThe widget's options: plain values only (true / false, numbers, text).

A screen that stands upright

When the screen is taller than wide, OCTAVE lays the same widgets out again for that shape by fixed rules, so a dashboard works either way up without any extra work. If you want to place them yourself, set "schema": 2 and add a position for every cell, in the same order as cells: 

"layouts": {
  "portrait": {
    "gridColumns": 8, "gridRows": 12,
    "cells": [ { "col": 0, "row": 0, "colSpan": 8, "rowSpan": 5 } ]
  }
}

The complete format, with every optional key, is in docs/GAUGE_AUTHORING.md §5 and, for programs, in docs/api/dashboard-spec.schema.json.

Options Every Gauge Has

A gauge needs only its paramId. Its title, unit and range come from the reading, and its colours from the theme. Put any of these in props to change them:

OptionWhat it does
title, unitThe words shown, in place of the reading's own.
min, maxThe ends of the scale. A reading's own range is wide (RPM runs to 8000); set these to fit your car.
decimalsDigits after the point.
warnAbove, warnBelow, critAbove, critBelowWarning and critical limits.
frametrue draws a card behind the widget. Every widget has this one (the phone and the vehicle call it showFrame).
A colourEach widget has its own colour options, such as fillColor. Write a colour as "#2ECC71". Left out, the widget follows the theme.

Three things to know:

  • Numbers are in the reading's own unit. Write min, max and every limit in the unit the reading has in the list: °C, MPH, metres. If the driver has chosen °F or km/h, OCTAVE converts the limit along with the value, so "critAbove": 108 on coolant still means 108 °C on a gauge that reads in °F.
  • No reading is not zero. Until a value arrives, a gauge shows --, draws no fill or needle and raises no warning. A missing fuel level never lights a low-fuel lamp.
  • Only listed options work. A widget accepts the options the widget catalog lists for it and ignores anything else, so a dashboard file cannot hide a widget, resize it or pin it to a made-up value.

Warnings and the Red Banner

Give a gauge a limit and it changes colour when the reading reaches it: amber for a warning (warnAbove, warnBelow), red for critical (critAbove, critBelow). Critical wins when both apply. "alertFlash": true also blinks the value while it is critical. The round dials draw the warning and critical bands on their scale, so you can see them coming.

A small gauge in a corner can go red without being noticed. So while any gauge on a dashboard is critical, a red strip along the top names it with its value. Put "alertBanner": false in the file to turn the strip off; the built-in Home does.

A level does not flicker when a reading sits right on its limit. It starts at the limit and ends only when the reading has come back inside by a small margin, 1 % of the gauge's range unless you set alertHysteresis.

The Browser Editor

OCTAVE can serve a dashboard editor to a web browser on a laptop or a phone. It is a web page, not a part of the app's own screen. You drag widgets around a picture of the grid and the car shows the result while you work.

  1. Turn on Service in Settings > Device > Developer and restart OCTAVE. The switch applies at the next start.
  2. In a browser on the same device, open http://127.0.0.1:9876/dashboards.
  3. From another device, OCTAVE must be started with --service-bind so it listens on the network. Open http://<the car's address>:9876/dashboards and pair the browser with the 6-digit code OCTAVE gives (octave --pair-code prints one).

What it does:

  • Lists your dashboards, and edits, copies, downloads and deletes them.
  • Starts a new one from a template (one big dial with four readouts, four half-dials, a track layout and so on), filled in with readings your car has.
  • Imports a dashboard someone gave you, pasted as text or as a file, and tells you what did not come across, such as readings your car does not report.
  • In the editor: drag to move, drag a corner to resize, pick each widget's reading and options, choose a coarse, normal or fine grid, arrange the portrait layout, undo and redo.
  • Show on the car: while this is ticked, the car's OBD page shows the dashboard as you change it, in place of its usual cards. It stops when you save or close the page, or a minute after the browser goes quiet.

An imported dashboard is always saved as a new one under a new id. It never replaces one you have.

How It Works

From here on the page is for people who want to know what happens underneath, or who are changing the code.

The idea is that a dashboard is data, not code. A file names widgets from a fixed list and gives them plain values. Nothing in it is run. That is what makes a dashboard safe to take from a stranger, and what lets the app, the browser editor and any other frontend show the same file the same way.

PieceJob
DashboardManagerC++. Finds the dashboard files, checks and tidies each one, saves, deletes, copies, imports and exports, remembers which is Home, and watches the folder for changes. It is dashboardManager in QML and in the service API.
The widget catalogOne JSON file listing every widget type: its name, its usual size, the options a dashboard may set on it and their limits. The manager serves it as dashboardManager.widgetCatalog, so every frontend sees the same list.
DashboardRendererQML. Takes one dashboard and draws it: works out each cell's rectangle and loads the widget into it.
The widgetsQML. Each draws one thing. A gauge is told only its paramId.
OBDParameterModelQML. Where a widget asks for a reading's value, title, unit and range.

What happens when Home appears:

  1. Home asks the manager which dashboard is Home (homeDashboardId) and loads it (loadDashboard(id)). The manager returns the file tidied.
  2. The renderer divides its area into the grid. A cell's rectangle follows from its column, row and spans, so a cell three rows tall is exactly three times the height of a one-row cell. On an upright screen it uses the portrait positions.
  3. For each cell it looks the type up in the catalog and loads that widget. A type it does not know leaves the cell empty.
  4. It sets the widget's paramId, then the options from props, each one only if the catalog lists it for that type. Limits and ranges are tied to the unit settings, so they follow a change of unit.
  5. Home tells the OBD manager which readings the dashboard shows, so only those are polled.
  6. When a dashboard file changes, the manager announces it and Home loads again. If the content is the same as before, the widgets are left alone.

Where a Gauge Gets Its Value

No widget talks to the OBD manager. The latest value of every reading sits in paramStore (described on the OBD Manager page), and frontend/OBDParameterModel.qml is the one place QML reads it from. The model adds two things: what each reading is called and how it is measured, taken from the C++ parameterCatalog, and the driver's choice of units. A binding to one reading is re-evaluated only when that reading changes.

To do thisUse
Bind a number to a readingOBDParameterModel.sample(id): the value in the driver's units, or NaN when there is none
Get the value as it isliveValue(id): the same, but undefined when there is none
Get the value in the reading's own unitrawValue(id)
Get title, unit, min, max, kind and decimalsdisplayInfo(id) in the driver's units; nativeInfo(id) in the reading's own
Convert one valuetoDisplay(id, v), fromDisplay(id, v); toDisplayDelta(id, d) for a difference
Check that an id existshasParameter(id)

Every reading has a kind: percentage, temperature, voltage, pressure, bidirectional (goes both sides of zero) or numeric (everything else). The catalog says which kinds each widget suits, and the browser editor offers only readings that suit the widget. A file written by hand is not checked for this.

The seven value gauges (Circular, Arc, Bar, Segmented, Linear, Digital, Sparkline) share one base, frontend/gauges/ValueGaugeBase.qml. The base holds the binding, the defaults taken from the reading and the alert rule; each gauge only draws.

Readings the Car Does Not Have, and Polling

A dashboard may name any reading, so it can be written for another car or passed around. After connecting, OCTAVE asks the car which readings it supports. From then on, a cell whose reading this car does not report shows the reading's title and "Not supported by this vehicle", not a gauge stuck at nothing. The answer describes the car connected now: it is forgotten on disconnect, and until a car has answered, every cell is drawn. Readings from the motion sensor are never held back this way.

In QML: OBDParameterModel.vehicleKnown, isSupported(id) and vehicleParameters (the supported readings, which the OBD page's Live Data cards list).

Only what is on screen is polled. An adapter answers one question at a time, so OCTAVE asks only for readings somebody shows. A dashboard needs no wiring for this: the renderer lists its readings in paramIds, and the page that hosts it passes them to obdManager.setParameterDemand(consumer, ids) while it is on screen and takes them back when it leaves. How the lists are joined is on the OBD Manager page under Which Readings Get Polled.

What OCTAVE Does to a File

A file written by hand will have mistakes, and it must never take the Home screen down in a moving car. So one set of rules is applied every time a dashboard is loaded, saved or imported, and a bad part is dropped or mended, never fatal:

  • A file that is not valid JSON, has no id, or uses an id already taken is left out of the list. The reason goes to the log.
  • Keys OCTAVE does not know are dropped. Options keep plain values only; text is cut at 200 characters.
  • A cell that hangs off the grid is moved back in. It shrinks only if it is wider than the grid.
  • Two cells never overlap. The one earlier in the file stays; the later one shrinks, and is dropped only if its corner is taken.
  • An option of the wrong sort (text where a number belongs) is dropped and the widget uses its default. A number outside the catalog's limits is brought inside them.
  • A widget type or a reading OCTAVE does not know is kept in the file, so a dashboard made with a newer OCTAVE survives being saved by an older one. The unknown widget's cell stays empty; a gauge with an unknown reading shows --.
  • A file whose schema is newer than this build reads shows one line, "This dashboard needs a newer version of OCTAVE", and nothing else.
  • Import is stricter: it refuses text over 512 KB, more than 256 cells, a newer schema, or anything with no list of cells, and always gives the result a new id.

The folder is watched. A file added, changed or removed, by hand or by a sync client, is picked up within a second.

The dashboard that ships, home, lives with the app (frontend/dashboards/presets/home.json) and cannot be changed or deleted. To change it, copy it into your folder under another id and edit the copy.

Hand-Built Home Screens

Home does not have to be a grid. The six screens in frontend/home/ are drawn freely in QML, each for one idea:

ScreenThe idea
CockpitAn instrument cluster: the tachometer in the middle with the speed inside it, a shift strip across the top.
GlassBuilt around the music: blurred album art fills the screen, with the drive in panes of glass.
TrailFor off-road: a heading tape, an artificial horizon that tilts with pitch and roll, the G-force bubble.
RetroA 1980s digital dash: seven-segment speed, a bar-graph tachometer, one colour on black.
RingsFour readings as concentric rings that fill with their level.
TelemetryA data logger: the last half minute of four readings as live traces, and the black box's state.

Each is built on frontend/home/HomeScreen.qml, which gives a screen what it needs so that it only has to draw: text(id) (the reading as text, -- for none), value(id), norm(id) (where the reading stands in its range, 0 to 1), unitOf(id), what is playing, portrait, and u, which is 1 % of the screen's short side. Sizing everything from u is what makes a screen work at any size and either way up. A screen lists the readings it shows in paramIds, and they are polled while it is on screen.

To add one: write the file in frontend/home/, add a row to frontend/home/HomeScreens.js with a preview picture (a 640 by 310 JPEG in frontend/assets/home/), and add it to the homeScreens test in tst_dashboardwidgets. It then has a card in Settings. The recipe is in docs/GAUGE_AUTHORING.md §5.5b.

When Something Goes Wrong

  1. The dashboard has no card in Settings. The file was left out. Check that it is valid JSON, has an id of its own, ends in .json and is in the right folder. The log says why a file was skipped (octave-cpp.log, category octave.dashboards; see Architecture for where the logs are).
  2. A cell is empty. The type is misspelt. Types are case-sensitive.
  3. A gauge shows --. No value has arrived: no car is connected, or the paramId is misspelt.
  4. A cell says "Not supported by this vehicle". The car does not report that reading. Pick another.
  5. A widget is smaller than you wrote, or missing. It overlapped one earlier in the file.
  6. An option does nothing. It is not one of that widget's options, or its value is of the wrong sort. Check the widget in docs/GAUGE_AUTHORING.md §3.

Adding a Widget

docs/GAUGE_AUTHORING.md is the complete guide for anyone adding a gauge: every widget's options with their defaults, the theme colours to use, the angle arithmetic for needles, and the recipe step by step (§7). Keep it up to date in the same change. In short, a new widget needs:

  1. A QML file in frontend/gauges/, built on ValueGaugeBase if it shows one reading.
  2. An entry in widget-catalog.json: its name, usual size, the kinds of reading it suits, and each option a dashboard may set with its real default.
  3. Its file in the urls list of WidgetCatalog.qml. Without both the entry and the file it cannot be drawn.
  4. A row in the table on this page and a section in the guide.

A new reading from the car is added on the OBD side; see OBD Manager. Gauges can show it with no further work.

Why It Is Built This Way

  • A dashboard is data. A file can only name widgets from the catalog and set options the catalog lists. That makes sharing safe, and gives the app, the browser editor and other frontends one format to agree on.
  • No editor on the car's screen. Designing a dashboard on a touchscreen in a car took more interface than the result was worth. A dashboard is written at a desk or in a browser, and the app only shows it.
  • A grid, not free placement. Dashboards people write are grid-shaped, a grid can be turned for an upright screen by rule, and overlaps can be mended by rule.
  • The renderer places cells itself. Qt's own grid layout does not give a cell that spans three rows three times the height of one that spans one. Working each rectangle out from the grid does.
  • One catalog for everyone. What can be drawn and what can be set are the same list in every frontend, because all of them read the same file.
  • Gauges never touch the OBD manager. They read a value by id from one place. The same gauge then works with a real car, the simulated car, the motion sensor or a test.
  • Mend and carry on. A mistake in one cell costs that cell. It is logged, and the rest of the screen is drawn.
  • Limits in the reading's own unit. A dashboard written by someone who drives in °C warns at the same temperature for someone who reads °F.
  • Home can also be drawn by hand. A grid of widgets cannot express every idea for a Home screen, so a screen may be written freely in QML and chosen from the same list.
