# Frontend platform: anyone can build an OCTAVE frontend

**Status:** active (started 2026-10-23)
**Last updated:** 2026-10-23

**Goal:** someone who has never built OCTAVE can download one file, get a simulated car, write a frontend in any language against a published contract that won't break under them, and install it on a head unit where the user picks it as the screen.

## Where this starts

The open backend is done (`TODO/open-backend.md`): every manager is served over the service protocol (`src/service/`), `docs/api/` is generated by `--dump-api` and checked by `tst_apidocs`, `kProtocolVersion` is 2 (pairing), `--headless` runs with no QML engine, `--web-root` serves a web frontend, media streams and `/art` / `/export` exist, and `sdk/python`, `sdk/web` and `sdk/typescript` (types generated from `docs/api/`) are the clients. Five full frontends in five languages proved that every QML feature is reachable; they are kept on the `frontends-experiment` branch, not `main`, because maintaining them is not the goal. Making it easy for other people to write theirs is.

What stops an outside developer today, in order of how much it hurts:

1. The simulated car (`--dev`) exists only in builds with `OCTAVE_DEV_TOOLS` (`CMakeLists.txt:189`, default ON only for Debug), so a frontend author must compile OCTAVE and Qt from source.
2. (Done, step 1.) The versioning rule was not enforced.
3. Only the TypeScript SDK is generated; the envelope (ops, errors, events, streams) is described in prose, so a new language means reading `sdk/python` and porting by hand.
4. There is no way to install a frontend: `--web-root` / `serviceWebRoot` takes one folder, a native frontend is a separate program the user starts themselves, and nothing restarts it.
5. A paired device gets full control. A dashboard someone downloaded can change settings, delete trips and start downloads.
6. No starter projects; the smallest examples are the SDKs themselves.
7. Unmeasured behaviour with many clients: subscription floods, a slow reader, a client that never reads (`tools/stream/service_load.py` is the baseline).

## Steps

### 1. The contract: stability you can build on
**Done (2026-10-23):** `tools/api/check_compat.py` in CI (`lint`), stability / deprecation annotations (`Q_CLASSINFO`, `src/service/metadescribe.h`) in `describe`, `docs/api/` and the API reference, `docs/api/CHANGELOG.md`. **Left:** surface `deprecated` / `experimental` in the generated SDK types (JSDoc `@deprecated` in `sdk/typescript`; folded into step 3).

### 2. A downloadable simulator
**Effort:** M. **Device:** desktop, then the release CI matrix.
- Split what `--dev` needs for a frontend author (the simulated car `src/dev/carsim` + `simelm327`, `devimufeed`, the `sim_*` actions, `sim_pairing_code`) from the UI-driving tooling (`uidriver`, `perfmonitor`, the dev overlay), and build the first part in every configuration as `--sim`, inert unless asked for.
- `octave --headless --sim` in the release AppImage / exe / dmg gives a car, test media, and the service with no window, on a throwaway config unless told otherwise (so trying it never touches a real install: see the isolation rules in `TODO/open-backend.md`).
- Document it as the first step of `wiki/writing-a-frontend.html`.
- Keep the wasm browser build's `webdemo` on the same simulator.

### 3. One machine-readable protocol spec, SDKs generated from it
**Effort:** L. **Device:** desktop.
- `docs/api/protocol.json`: every op with its arguments and reply, the error codes, the event shapes, the stream record format, the pairing flow. Written once, checked against the server by a test that runs each op (extend `tst_conformance` or the `sdk_python` ctest).
- A generator that turns `protocol.json` + the object files into a client: TypeScript first (replace the hand-written parts of `sdk/typescript`), then Python, then one compiled language (Go, Rust or Kotlin) to prove it isn't TypeScript-shaped.
- A conformance kit for SDK authors: a recorded session plus a fake server they can run their client against.

### 4. Installable frontends
**Effort:** L. **Device:** desktop, Pi.
- A manifest (`octave-frontend.json`): id, name, version, supported protocol versions, the permissions it asks for (step 5), and either `web` (a folder served like `--web-root`) or `exec` (a program and its arguments per platform).
- `<config>/frontends/<id>/` holds installed ones; `FrontendManager` lists, installs (from a folder or a zip, validated, never runs anything at install time), removes, and chooses the active screen. The QML UI is the built-in default and the fallback.
- With an `exec` frontend active, OCTAVE runs headless, starts it, restarts it on a crash with back-off, and falls back to QML after repeated failures; a key combination or a file on the boot volume forces QML back.
- Settings > Frontends page in QML.

### 5. Permissions per paired device
**Effort:** M. **Device:** desktop.
- Scopes on a token, asked for in `pair` and shown to the user with the code: `read` (get, subscribe, rows, streams), `media` (playback and volume), `vehicle` (OBD connect, demand, trouble-code clear), `settings`, `files` (downloads, imports, exports, deletes), `full`.
- Every method and settable property gets a scope, from one table next to the stability table in step 1, published in `docs/api/`.
- Loopback trust stays full by default (it is the head unit's own screen); an installed frontend's manifest permissions apply to it too.
- Bumps the protocol version only if `pair` without scopes stops meaning `full`.

### 6. Starter templates
**Effort:** M. **Device:** desktop.
- `templates/` with a "hello car" in plain JavaScript (served with `--web-root`), Python, and one compiled language: connect, pair if needed, show RPM and speed, play/pause, the cover. Under 200 lines each.
- CI runs each against `--headless --sim` (the step 2 build), so they cannot rot.
- Each is copy-and-go: its own README, no path dependencies into the repo.

### 7. Many clients at once
**Effort:** M. **Device:** desktop, then Pi.
- Extend `tools/stream/service_load.py`: 20 clients each subscribed to every PID, one client that never reads, one that floods `call`; measure what the car side and the QML UI lose.
- Per-connection limits (queued bytes, ops a second) with a clear error code, and dropping a reader that stays behind, without slowing the others.
- Results on the Pi, since that is the slowest head unit.
- This is also the groundwork for the process split in `TODO/open-backend.md`.

## Order

1 and 2 first (a contract that holds and a car to build against are the minimum for anyone outside), then 5 (before step 4 makes it easy to install other people's code), 4, 3, 6, 7. Step 6 can start as soon as step 2 lands.
