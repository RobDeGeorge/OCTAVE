# Follow-ups found while testing the 0.9.5 release candidates

**Status:** deferred: none of these block 0.9.5. Each one was triaged during RC testing on 2026-10-17.
**Last updated:** 2026-10-17

## Why this is parked here

These came out of 0.9.5 RC testing: agent 9 on the kora VMs (Win11, Ubuntu 22.04, Fedora 44, Pi OS) and agent 8 on the Orange Pi with an S26 Ultra. Each one either predates 0.9.5, happens only once (on a first launch or the first plug-in after a phone boot), or needs an installer change that would have cost another full Windows test round. The release blockers found at the same time are fixed in 0.9.5: the BlueZ startup freeze (c621683) and the Settings QR modal covering Phone Mirror (32f5460).

## Items

1. **Windows Firewall prompt for adb (new in 0.9.5, S).** The first QR pairing on Windows shows "Do you want to allow public and private networks to access this app? adb, Publisher: Unknown". mDNS pairing opens a listening socket, and adb.exe is unsigned.
   - Fix: in `build_scripts/installer_windows.iss`, add a `[Run]` entry `netsh advfirewall firewall add rule name="OCTAVE adb" dir=in action=allow program="{app}\platform-tools\adb.exe" profile=private` and remove the rule in `[UninstallRun]`.
   - This only works for all-users (admin) installs. A per-user install keeps the prompt.
   - Retest on kora: an interactive install, then QR pairing with no prompt.
2. **Reattach after a USB reset wastes ~4 s (S).** With `scrcpyAutoWifi` on, the first plug-in after a phone boot runs `adb tcpip`. The phone's USB re-enumerated twice: once for the adbd restart, and again about 4 s later (Samsung S26, Android 17). The second reset killed the session that had just started, along with its server. The manager then tried to reattach to that dead server (`phonemirrormanager.cpp`, `onDisconnected` persist and `continueStart` attach), which wasted the 4 s attach deadline, so plug to stable picture took 14.4 s.
   - Option: skip the reattach when the USB transport changed (the transport_id from `adb devices -l` differs, or the kernel re-enumerated).
   - Option: after tcpip, wait until the device has been stable for about 3 s before starting.
   - Option: cap the attach deadline on USB at about 1.5 s.
   - Do it in both backends.
3. **Windows first-launch stall, 10–20 s before the first frame (M).** It happened on 2 of 5 fresh first launches and never on a second launch. 0.9.4 showed about 7 s. The stall ends at the first frame, which points at first-run work: QML compile and cache (QML loads from `<appDir>/frontend` at runtime), the D3D pipeline cache, and Defender scanning new DLLs. adb was measured at ≤1.1 s cold, so it isn't the cause.
   - Next: have kora capture a stalled run's full octave-cpp.log plus a `%LOCALAPPDATA%\OCTAVE` listing before and after the launch.
   - If the logs don't show the phase, add `qInfo("startup: <phase> +N ms")` lines in `src/main.cpp`.
   - If it's QML compilation, consider compiling QML into the binary or shipping a pre-warmed cache.
4. **ESP32 knob auto-connects to the first serial port (S, predates 0.9.5).** With no port saved (`esp32VolumePort` = "", `esp32VolumeEnabled` defaults to true), `esp32volumemanager.cpp` (~290–305) auto-selects a port. On Win11 and Pi OS VMs it picked COM1 / ttyS0, wrote `M0`, `C0,255,255` and `V32` to it, and Settings showed "Volume Knob: Connected" with no knob attached. This can send bytes to unrelated serial hardware.
   - Fix: only auto-select a port whose USB VID/PID matches the ESP32-S3 (the `m_esp32S3Port` path already exists), and report "Connected" only after the knob answers.
   - Do it in both backends. See also `project_audit_2026_09_26` (ESP32 items still open).
5. **A dead Wi-Fi transport offered in the phone picker costs ~50 s (S).** After the phone moves to another network, adb keeps listing the old `ip:5555` as `device`. Picking it in ⇄ led to the prep's pkill and getprop timing out (13 s), then `adb push` timing out (30 s), then the stale-retry. It recovered on its own and the UI stayed responsive, but the spinner ran for 49.6 s (Orange Pi, S26, 2026-10-17).
   - Option: probe each network transport (`adb -s X shell true`, 2 s) before listing it as usable in `devices`.
   - Option: on a network serial, treat a prep timeout as stale (`adb disconnect`, re-probe, pick again) and use a ~10 s push timeout.
   - Do it in both backends.
6. **Reattach is keyed on time, not on the phone (S, predates 0.9.5).** Since c0898bc, reattach works over any transport, so a cable pull fails over to Wi-Fi and keeps the DeX apps. But if phone A drops and phone B is picked automatically within the ~55 s persist window, the manager tries A's scid on B. That fails after the 4 s attach deadline, then starts fresh. It never lands on the wrong phone (the forward targets B's `localabstract:scrcpy_<A-scid>`, which doesn't exist), but it costs 4 s.
   - Fix: record `getprop ro.serialno` in the start prep (next to the sdk getprop) and reattach only when it matches. mDNS serials embed it; ip:port serials don't, so probing beats parsing.
   - Do it in both backends.

## Recommended order

Do 4 first: it writes to unknown hardware. Then 1, 2, 5 and 6, then 3 once there's a stalled log.
